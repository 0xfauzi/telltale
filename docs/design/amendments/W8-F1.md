# W8-F1: a flag varies by its minority share, a block hole costs rows, advise finds a frame

Amends design 6.12's readiness checklist (check 7), step (2) of the same section as
W8-T3 rewrote it, and the shadow advisory of spec 14.6. Three changes, each one a thing
W8-T3 measured and reported and could not fix inside its own OWNS, and each one a thing
E16 stops at.

## 1. Check 7 on a flag is the minority share, not the scaled MAD

Check 7 asks whether the target moves at all. Its number was the scaled median absolute
deviation (1.4826 x MAD) of the target over the rows a run would score, needed above 0,
and the case it exists for is `fresh_input_tokens` on capture S1, which is 2 on all
seven rows: a constant target makes every baseline perfect and leaves skill without a
denominator.

On a 0/1 column that number is 0 whatever the base rate, and the reason is arithmetic
rather than data. The median of a flag whose base rate is below a half is 0. Every
absolute deviation from 0 is then the value itself, 0 or 1, and the median of a list
that is mostly 0 is 0 again. Measured on this repository's own first-parent history,
176 commits imported on 2026-09-06: `rework_within_3_lag3` carries 37 ones over the
173 rows its frame retains, and read `variation FAIL, measured 0`.

**The rule now.** For a target whose ColumnSpec unit is `flag`, check 7 measures the
minority share, min(p, 1 - p) with p the share of 1s over the known rows, needed above
0. Every other unit is unchanged, down to the rounding. The share is 0 exactly when one
value is present, which is the constant target the check was written for, so a flag
with one value still fails and for the stated reason. The detail line names both counts:

    variation  pass  0.2139  0  37 of 173 known rows are 1: minority share 0.2139
                              = min(p, 1 - p) for rework_within_3_lag3 in 173 rows,
                              needed above 0

The unit is read off the Series column and not off the registry entry. They agree on
every flag today and they do not agree in general: `verification_cycles` is `cycles` in
`forecast.TARGETS` and `runs` in `series_changes._CHANGE_COLUMNS`, and the column this
check reads is the one in the frame.

What this does NOT change: nothing about a backtest, which never calls the checklist.
E16 would have run either way; what it would have printed beside every flag target is
`NOT ready: variation`, which is the checklist reporting on its own arithmetic.

## 2. `retained` takes the conditioning block, so a hole in it costs rows

W8-T3 made step (2) row-level for the TARGET: a target is forecast over the rows where
it is known, and `forecast/frame.py`'s `retained(series, target)` builds that frame. The
candidate protocol's conditioning block was left at the window: `candidate._known`
refuses the whole run when a block column holds an unknown anywhere inside
[ctx_start, o], because a candidate whose features cannot be read is not a candidate the
protocol says anything about.

That refusal is right about one candidate and wrong about a run. `git diff --numstat`
prints `-` for a file it will not count lines in, so `lines_added` and `lines_removed`
are unknown on a commit that touched a binary file, and a count that is partly unknown
is unknown. Two such commits sit at rows 0 and 5 of this repository's 176-row lineage,
and every context of a lineage shorter than MAX_CONTEXT starts at row 0, so the run
refused at its first origin:

    origin 16: candidate column lines_added holds an unknown inside [ctx_start, o].
    Nothing here imputes one.

E16 conditions on block A on four repositories. One binary commit in any of them
refused the whole run there.

**The rule now.** `retained(series, target, columns=())` keeps a row only when the
target AND every column named in `columns` is known. `candidate.conditioned` names the
A block, minus the target, and BOTH runs of the pair are cut from that one frame, so
the pairing rule of design 6.12 (the two runs differ in the covariate and in nothing
else) holds by construction rather than by two exclusions happening to agree. The block
is never narrowed: a run that dropped two of six columns would be the unconditioned run
wearing the conditioned run's name.

This is the same exclusion by a named policy AGENTS.md invariant 5 allows, applied to
one more set of columns, and nothing imputes. What a reader is owed is which columns
cost which rows, and three records carry it.

- The frame's cohort key `excluded_reason` names every column that cost a row and how
  many each cost. With no block it reads exactly as W8-T3 wrote it, `target <name>
  unknown`; with one it reads `target <name> unknown on k rows; lines_added unknown on
  2 rows; lines_removed unknown on 2 rows`.
- The frame's cohort key `excluded_by_column` holds the row keys per named column, and
  `frame.for_columns` reduces it to `{count, row_keys, by_column}`. A row missing two
  of the named columns is ONE row in `excluded_rows` and appears under each column here:
  "how many rows went" and "which column cost a row" are two questions.
- Both runs of the pair record `candidate.excluded_for_block` and the paired report
  prints it on its face:

      retained 172 rows  excluded_for_block 2 {'lines_added': 2, 'lines_removed': 2}

  172 and 2 are consistent, not contradictory: rows 0 and 5 are the two the block
  cannot be read on, and row 0 was already out of the frame because the lagged label is
  undecidable on the first three rows of any lineage. The block cost the run one more
  row than the target had already taken.

`candidate._known`'s refusal is now unreachable on a frame `conditioned` cut, and it
stays as the guard behind it. `_attach` is a `prepare` hook whose caller chooses the
frame, and a block read that imputed a cell rather than refusing is the failure this
whole protocol is built to avoid.

**The plain backtester is unchanged.** `telltale forecast backtest` still excludes a
`partial` covariate from the variant by name (W7-T3), and still drops a window whose
covariate holds a hole. E13's runs are untouched for the reason W8-T3 gave: `retained`
returns the PARENT OBJECT when nothing is excluded, and a block with no hole in it
changes nothing about the frame either.

One consequence worth naming rather than leaving to be discovered. A block column with
holes carries the coverage word `partial`, and the plain backtester excludes a partial
covariate from the past-only variant by name. Naming the block to `retained` fixes what
the CONDITIONED run reads; it does not put `lines_added` back into the past-only
covariate list, because that is the backtester's rule and E13 continuity depends on it.
Both runs of the pair are affected identically, so nothing about the comparison moves.

**One string moved on the wire.** `frame.excluded(frame)["reason"]` was the constant
`target unknown` on every run. It is now the frame's own reason, so a run says which
columns cost it rows rather than repeating one word. The identity case is unchanged: a
frame that excluded nothing has no such cohort key and the constant is still what a
reader gets, which is what `test_forecast_ablation.py` asserts and still asserts.

## 3. `telltale advise` finds a frame's run, and asks the checklist at H

Two defects, both measured by W8-T3 and both in `cli_advise.py`, which was outside its
OWNS.

**The lookup.** A holed target's run is stored under the FRAME's id, which is the
parent's with the suffix `:<target>`, because that is the series the run was made of.
`_latest` looked runs up by the parent id alone, so a `forecast backtest --target
rework_within_3_lag3` that stored a row was reported as `no stored true-order backtest
of this target on this series`. Measured here on 2026-09-06: three stored runs under
`ser_8362bf51029c70ecc438417d:rework_within_3_lag3` and none under
`ser_8362bf51029c70ecc438417d`.

`_latest` now tries the parent id FIRST and the suffixed id after it, and returns which
one answered. Parent first is what keeps every request-clock pair and every hole-free
change target on the id it has always had. The id that answered rides in the target's
`run` block as `series_id`, because which id a row is under is a fact about the store
rather than something to infer from a coverage word.

**The horizon.** `cli_advise.HORIZON = 1` was a module constant, and
`rework_within_3_lag3` is registered for H = 4 alone: row j of that column carries
change j - 3's label, so only the fourth step from an origin is about the candidate.
The checklist was asked at 1 and `backtest.registered` refused with `horizon 1 is not
one of [4]`, so the page printed `readiness: refused` about the advisory's own constant
rather than about the series. The constant is gone and the horizon is
`candidate.horizon(target)`, which W8-T3 added and which the registry fills for every
candidate target.

## What did NOT change, and why

`candidate.one_step`, the forecast of the row a candidate would become, still cuts its
frame with `retained(series, target)` and no block. Extending it is a separate decision
about what a refused advisory should say, and it is not this task's; the measured
consequence is in the log's UNSURE section with the line that produces it.
