# W8-T3: a target with holes runs over its known rows, and the lagged label at H = 4

Amends design 6.12, steps (2) and (6), the readiness checklist and the candidate
protocol. Four changes, two splits forced by the length ratchet, and two numbers that
moved on stored goldens.

## 1. Step (2) is row-level for the target

Design 6.12 step (2) reads: "keep only rows where the target's coverage is observed ...
drop any window containing None in the target or a selected covariate". The first
clause is about ROWS and the backtester had only ever implemented the second. The
difference did not matter while every target was a request-clock column that a capture
either filled or did not have at all. It decides everything on a change lineage, where
every post-merge column has holes by construction:

- `merge_verification_ms` and `merge_verification_failed` are unknown on a commit with
  no check run. A push of several commits gets one run, on its head.
- `rework_within_3` is undecidable on the last three rows of any lineage.
- `rework_within_3_lag3` is undecidable on the first three.

Measured on this repository on 2026-09-06, 169 first-parent commits imported with check
runs (`telltale import git-history --repo .`, 77 s, 349 observations, 143 check-run
outcomes, 34 rework outcomes, 26 commits with no check run, 0 diagnostics):
`merge_verification_ms` and `merge_verification_failed` are `partial` with 26 unknown
cells, `rework_within_3` and `rework_within_3_lag3` `partial` with 3.

Window-level exclusion cannot run any of them. Every context of a lineage shorter than
MAX_CONTEXT starts at row 0, so one unknown cell low in the column drops nearly every
window; the coordinator measured 16 of 146 windows kept for `merge_verification_ms` and
0 of 143 for the lagged label at H = 4 on the 162-commit tree of the same repository.
And it never got that far: `backtest._variant` refused a `partial` target outright, and
`forecast readiness` printed `target merge_verification_ms has coverage partial: a
target must be one of ['observed', 'derived']` and stopped.

**The rule now.** A target is forecast over the rows where it is known, in lineage
order. `forecast/frame.py` builds that frame:

    retained(series, target) -> Series

the same Series with only the rows whose target cell is not None, `row_meta` filtered
the same way, changepoints remapped to where those rows now are (a changepoint at index
i becomes the number of retained rows below i; 0 and N' are dropped, because a boundary
at either end of a frame divides nothing), and four cohort keys: `retained_rows`,
`excluded_rows`, `excluded_row_keys` and `excluded_reason`. The frame's `series_id` is
the parent's with the suffix `:<target>`, so a stored run names the series it came from
and the target that shaped it.

When no row is excluded the PARENT OBJECT is returned. That identity is not an
optimisation: it is what makes every request-clock run over a hole-free target the run
it was before this amendment, down to the series id and the stored bytes.

This is an exclusion by a named policy, which AGENTS.md invariant 5 allows, and it is
not imputation. What it costs a reader is one sentence, which every run carrying it now
states in its assumptions:

> k of N rows were excluded because the target was unknown on them; the context is the
> lineage without those rows, so the previous row means the previous change with a
> known target.

and one record on the run and the stored row: `excluded_rows: {count, row_keys,
reason}`. The row keys are shas on a lineage, so a reader can name the commits that are
not in the frame.

The second clause of step (2) is untouched. A covariate with a hole still drops the
window that reads it, with its reason counted, and a `partial` or `unavailable`
covariate is still excluded from the variant by name (W7-T3).

Measured after the change, same series: `merge_verification_ms` retains 143 rows and
plans 127 windows at H = 1, all eight readiness lines pass, and the backtest drops none.
`rework_within_3_lag3` retains 166 rows and plans 37 windows at H = 4 (stride is H, so
the count is `floor((166 - 16 - 4) / 4) + 1`, not `N' - 19`).

## 2. What a target may be, and what check 1 fails on

`backtest.FORECASTABLE` is now the COVARIATE rule and `backtest.TARGET_COVERAGE` is the
target rule, one word wider:

    covariate:  observed, derived
    target:     observed, derived, partial

`partial` is admissible for a target precisely because of section 1: on the frame the
run scores, a partial column has no hole. `unavailable` is still refused, because a
column no row could carry has no rows to retain.

Readiness check 1 changes with it, and in the same direction W7-T3 moved it. W7-T3
stopped failing on an `unavailable` column, because `backtest._variant` excluded such a
column by name and ran, so the checklist was refusing a run the backtester was willing
to make. A `partial` covariate was in exactly that position and is now excluded by name
too, with its word printed beside it. What check 1 fails on is the target's own
coverage, and nothing else.

Every line of the checklist is measured over the retained frame, because that is the
frame `backtest.run` will score: the windows, the missing cells, the shortest context,
the regimes, the variation and tau. A checklist over the parent series would count
windows nobody runs. The header line prints all three counts, so a reader is not left to
subtract:

    policy exclude  rows 169  uncaptured 169  retained 143  excluded 26  changepoints none

## 3. The candidate protocol at H = 4, scored on step 4

`rework_within_3_lag3` (W8-T2) joins `TARGETS` and `CANDIDATE_TARGETS` with
`horizons=(4,)`. It is the first registry entry whose horizon is not 1, so the protocol
no longer has a module-wide `HORIZON`; `forecast.CANDIDATE_HORIZON` maps each candidate
target to its own, and `candidate.horizon(target)` is the one read of it.

Row j of that column carries change j - 3's label. From origin o the FOURTH step is
therefore change o's own label, and steps 1 to 3 are the labels of changes o - 3 to
o - 1, which a merge decision is not asking about. `forecast.SCORED_STEPS` names the
steps a target is scored on, `rework_within_3_lag3` is scored on step 4 alone, every
target absent from that map is scored on every step, and both runs of the pair record
`scored_steps` beside `horizon`. The paired report prints it on its face:

    scored on step 4 of 4

The projection is `frame.scored(record, steps)`, which cuts a window record down to the
scored steps for the metrics only. The window RECORDS keep every step, because they are
what a reader recomputes a number from, and `backtest.metrics` keeps its signature: the
step selection is a transform of the records the candidate protocol applies, not a
parameter of the metric. Nothing else in the package can score part of a horizon by
accident.

**The future block at H > 1.** The conditioned run's A block spans `[ctx_start, o]` from
the series and is then edge-padded to `n_ctx + H` by repeating row o's own value
(`frame.edge_padded`). It never reads a row past the origin. Before W8-T3 the span was
`[ctx_start, o + H)`, which is correct at H = 1 and is look-ahead at H = 4: it would
have handed the forecaster the A blocks of the three changes after the candidate. The
padding is recorded on the run as
`candidate.future_beyond_step_1: "edge-replicated from the candidate row"`, so a reader
is told what the forecaster saw rather than left to know that the model pads a short
horizon covariate the same way and says nothing.

**The delayed-label ceiling is gone.** W3-T2 stopped `rework_within_3` at
`o <= N - REWORK_TAIL` because the last three rows of a lineage carry no label. Section
1 does that job at the row level for every target, so the ceiling is removed rather than
kept: an unknown row is not in the frame, and the backtester's own `o <= N' - H` over
that frame is the whole ceiling. Keeping both would have dropped three origins whose
labels ARE known. `candidate._limit` now carries only the `origin_range` a caller asked
for, and says so in its reason string.

## 4. The splits, and the two numbers that moved

`forecast/candidate.py` was at 800 lines, the length ratchet's limit, and this work adds
about 30. The git-diff extractor (`features`, `NotACandidate`, `PROVENANCE` and their
helpers) moved to `forecast/features.py`: it is the one job in that file the protocol
does not touch, it imports no window, forecaster or registry, and the three public names
are re-exported from `candidate` because `telltale advise`, `telltale forecast
candidate` and the protocol's own tests reach them through the protocol module. A split
is not a rename. One consequence to name: `cli_advise.POLICY_VERSION` hashes
`forecast/candidate.py`, so a change to the extractor alone no longer moves it.

The tests split the same way and for the same hook: `tests/integration/test_forecast_frame.py`
holds the four tests of which rows a run is made of, which is not one of the two
contracts `test_forecast_contracts.py` is named for.

`backtest.threshold` and its private half moved to `forecast/frame.py` as `threshold`,
for the reason section 1 gives: tau is q80 of the first c_min rows OF THE FRAME A RUN
SCORES, and a tau read off the parent series would be computed over rows that run never
saw. `backtest.py` had no line budget for the move either way.

**What moved on disk.** Two golden summary fields, both on captures that were never
forecastable and never scored:

    fixtures/golden/codex/S6/show.json               changepoints: measured 11 -> 10
    fixtures/golden/codex/rollout-import/show.json   changepoints: measured 2 -> 1

Both are readiness check 5 (the longest regime) measured over the retained frame.
`fresh_input_tokens` and `output_tokens` each hold one unknown cell on those captures
while their coverage word is `observed`, because the word is a capability of the surface
and not a census of the cells. Both captures fail `windows` with 0 either way, so no
scored number moved and no run was ever made of them. E13's 596 backtests are unaffected
for a reason that is worth stating rather than assuming: E13 only scored triples that
passed the whole checklist, check 3 fails on any unknown cell inside a planned window,
and on a series with no changepoint every row is inside some window, so a target with a
hole anywhere could not have been ready. That is an argument from the rule and not a
re-run; a re-run needs the owner's store and the forecast extra.
