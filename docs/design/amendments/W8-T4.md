# W8-T4: the tracked base defines the change clock's rows

Amends design 6.12, "Change clock", and design 6.8's commit statistics. Three changes to
what a row of the change clock IS, one change to what a merge reports, and one count the
cohort now carries.

## 1. A git-history import defines the tracked base

Before this amendment the change clock's rows were "every commit any capture of this
repository recorded". W8-T2 added a second recorder, `telltale import git-history`, which
records every first-parent commit of a branch. On a store holding both, the two sets were
concatenated and ordered by commit time.

Measured on the owner's E16 store on 2026-09-06 (a copy of
`experiments/E16/out/home/telltale.db`, repo_id `d9f783b1...`):

- 219 rows: 168 at the `unlinked` rung from the import, plus 51 distinct shas from 56
  `repo_commit` activities the launcher linked.
- **None of the 51 is on main's first-parent history.** Every one is a commit on a task
  branch that was later squash-merged, so the commit never landed on main as itself.
- 5 of the 51 share a TREE with a first-parent commit. The gate protocol merges main into
  the task branch before the squash, so the branch tip after that merge has exactly the
  tree the squash commit put on main: `723dc1b3 -> 13f88fa4`, `441c6262 -> 2114f7ea`,
  `593e276d -> 79c9073e`, `2aff5886 -> 863d950a`, `0a867064 -> 681d027b`.
- The other 46 are intermediate branch commits whose trees landed nowhere.

So a lineage the E16 pre-registration calls "the first-parent history of main" held 51
rows that are not on it, interleaved with the 168 that are. Two histories in one frame.

**The rule.** When a repository has a capture whose provider is `git`
(`importer_git.PROVIDER`), the commits that capture recorded are the TRACKED BASE, and
the change clock's rows are exactly those commits in committed order. Without such a
capture there is no base and the rows are the captured commits, unchanged.

## 2. How a captured commit reaches its row

A captured `repo_commit` activity joins a row two ways and there is no third.

**By sha.** Its sha is on the base. This is W8-T2's case unchanged: one row, at the best
rung any recorder gave it, reading the payload recorded AT that rung, so a sha the
launcher linked and the import also wrote reads the launcher's numbers.

**By tree.** Its sha is not on the base and its `tree` equals exactly one base commit's
tree. The row is then the BASE commit:

| what the row takes | from |
| --- | --- |
| `row_key`, clock position, the six repository columns | the base commit |
| `link_confidence` (the rung), the process columns, `attempts_to_land`, the environment fingerprint | the capture that recorded the captured commit |
| provenance | both, and `series check` resolves every id |
| `captured_sha=<sha>` in `row_meta.flags` | the captured commit |

The repository columns come from the base commit and not from the captured one because
they describe a diff: the branch tip's diff against its own parent is the last increment
of a branch, and what landed on the base is the squash commit's diff against the base.
The two are different numbers about different commits, and the row is the second one.

`captured_sha=<sha>` is spelled `name=value` inside `RowMeta.flags` because `RowMeta` has
no field for it and design 6.2 fixes its shape. Without it a row keyed on the base commit
gives a reader no way back to the session's own commit.

**Neither.** The captured commit is not a row. It is listed in the build's `dropped`
table with the reason

> not on the tracked base: a commit that did not land as itself

and counted in the cohort as `off_base_commits`.

**Refusing rather than picking.** Two cases are refused by name rather than resolved,
because duplicate is not one:

- a tree that more than one base commit carries (a revert puts one tree on a branch
  twice): `two commits of the tracked base carry this tree: refusing to pick`;
- two captured commits claiming one base commit by tree: `two captured commits carry the
  tree of one base commit: refusing to pick`.

Neither occurs on the E16 store: its 168 base commits have 168 distinct trees, and each
of the five twins comes from a different capture and claims a different base commit.

## 3. One row per sha, and the cohort counts the collapse

W8-T2 already grouped `repo_commit` activities by sha, so two activities naming one sha
were already one row at the best rung, with the provenance of both. What was missing was
the count: a reader of a built frame could not tell one row from two collapsed into one.
The cohort now carries `collapsed_links`, the number of shas more than one `repo_commit`
activity named. On the E16 store it is 5 (`e5aa5c5d`, `a3585324`, `111ff108`, `5d42f2cd`,
`65ccb108`; four are one sha at `tree_match_during` twice, one is `tree_match_during` and
`provider_reported`).

`captured_rows` counts ROWS and not activities, which it already did; on the E16 store it
is now 5 rather than 51, because 46 of the 51 captured commits are not rows.

## 4. A first-parent merge reports the diff the base took

`repo_link._commit_stats` returned every count and `per_file` as unknown for a commit with
more than one parent, on the ground that "a merge's numbers depend on which parent you
pick". That is the right answer for a caller who picked no parent, and the wrong answer
for `importer_git`, which walks `git log --first-parent`: there the parent was chosen by
the walk before the function ran, and the row is what the branch took when the merge
landed.

`_commit_stats` gains a keyword `first_parent: bool = False`. When it is True and the
commit has more than one parent, the counts and `per_file` come from `diff-tree -r -M
--no-commit-id parents[0] sha`. When it is False, nothing changes: a merge inside a
launcher capture (a `git merge main` into a task branch, say) was reached with no parent
chosen, and it still reports unknown. `importer_git.commit_payload` passes True.

Measured, `import git-history --no-checks` then `series build --clock change`:

| repository | rows | `files_changed` nulls before | after | merges |
| --- | --- | --- | --- | --- |
| deckgen | 118 | 79 | 0 | 79 |
| kstrl (`~/Documents/code/ralph`) | 252 | 100 | 0 | 100 |

The nulls were exactly the merges. What remains unknown after the change is unrelated to
merges: `lines_added`/`lines_removed` on 27 deckgen rows, where a changed file is binary
and `repo.totals` refuses the sum rather than silently dropping the file; and
`subsystems_touched`/`test_files_changed`/`dependency_delta` on 5 deckgen and 4 kstrl
rows, where the 8 KB payload bound truncated `per_file` and `series_paths` refuses a
prefix.

`series_paths.NO_PATHS` still names a merge as one cause of an absent path list, and that
is still true: a merge linked inside a launcher capture carries none.

## What this does not do

It does not decide whether the base is the right population for E16; that is the
pre-registration's question and this amendment only makes the population buildable. It
does not attach a capture to a squash commit by anything but the tree, so a task branch
whose tip tree differs from what landed (a rebase, a change made during review) is off
the base and is counted, not guessed at.
