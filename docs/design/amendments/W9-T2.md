# W9-T2: a change row folds the process columns of whoever recorded the change

Amends design 6.12, "Change clock". One change to where the seven process columns come
from, one statement of what stays unknown when they come from there, and one thing the
cohort now names.

Design 6.12 spells the change clock's process columns "summed over the attempts that
landed it". Until this amendment `series_changes._change_row` read that literally: the
seven columns were folded over `landed_by`, the attempts among the captures that recorded
the commit, and a capture that recorded a commit and never said which attempt of which
task it was contributed nothing to the row holding the commit it had made.

That was a reasonable reading while the launcher was the only way a session got recorded.
It stopped being one on 2026-09-06, when the owner switched on day-to-day capture: a
session started by hand behind `telltale daemon` has no `--task-id` and no `--attempt`,
because nothing launched it. W9-T1 gave such a capture its repository, so its commits
reach the change clock; this amendment is what the row does with them.

## What the row does now

A change-clock row is one change landed on the tracked base. Its seven process columns
are folded over **the attempts that landed it where there are any, and otherwise over the
captures that recorded it at a rung of spec 12.3's ladder, attempt or not.**

A capture that recorded the commit at a ladder rung and named no attempt is a RECORDER
(`series_changes.Recorder`). It carries the five things an `Attempt` carries about the
capture behind it, read off the same lifecycle row (`series_lineage.capture_row`): the
capture id, the start, the provider, the `READ_TYPES` slice of its activities, its
coverage map and its environment fingerprint. It carries none of the four an attempt
identity supplies, and that split is the whole rule: a recorder can fill columns that are
measurements of a session, and cannot fill columns keyed on an identity it never stated.

A git-history import is not a recorder. It writes `unlinked`, which is not a rung, and
folding its activities into a row would turn the `uncaptured` flag of W8-T2 into a process
measurement of the importer.

### Cell by cell, for a row that no attempt landed but a session recorded

| Column | Before | After |
|---|---|---|
| `files_changed`, `lines_added`, `lines_removed` | the commit payload | unchanged |
| `subsystems_touched`, `test_files_changed`, `dependency_delta` | the commit's stored path cells | unchanged |
| `attempts_to_land` | None | **None**, and see below |
| `fresh_input_tokens_total` | None | the sum over the recorders' `model_request` activities |
| `cache_read_tokens_total` | None | the same sum over `cache_read_tokens` |
| `compactions` | None | how many compaction activities the recorders have, which may be 0 |
| `verification_cycles` | None | how many verification_run activities they have, which may be 0 |
| `edit_turnover_ratio` | None | edits over distinct files edited, None when there was no edit |
| `stable_state_intervals` | None | spec 13.5's intervals, None without a repo_snapshot |
| `unique_files_read` | None | distinct `file_path` over their file_read activities |
| `merge_verification_ms`, `merge_verification_failed`, `rework_within_3`, `rework_within_3_lag3` | the attempts' outcomes | unchanged: see below |
| `env_changed` | None | from the recorders' fingerprints, which a daemon capture has none of, so still None |

The row's coverage words move with the fold. A column's coverage is the weakest cell any
capture in the frame recorded (`series_lineage.worst_coverage`), and it is now taken over
whatever each row folded rather than over the attempts alone: reading it off the attempts
would put an attempt's word on a column a capture the map does not describe had filled.

The row's `activities` move with it too, which is what keeps the claim testable. `end_of`
takes the row's end from that list and `series check` resolves every provenance id against
that end, so a cell built from an activity the row does not name is a claim no check can
test. A row folding a recorder names the recorder's activities.

## What stays unknown, and why it is not 1

`attempts_to_land` is the maximum attempt ordinal among the attempts that landed the
change, and it is None when none did. It is not 1.

The rejected answer was 1: a day-to-day session that landed a change did land it in one
session, so "1" looks like the number. It is not a number this system measured. The column
asks how many attempts it took, and a session that never numbered itself says nothing
about how many sessions tried the change before it: the owner may have run three and kept
the third, and only the third would ever be recorded. Writing 1 would make a forecaster
read "landed first time" off a row where nobody counted, and `attempts_to_land` would stop
meaning what it means on the rows an orchestrator numbered. Unknown stays unknown.

The four post-merge columns keep the attempts as their input for the same kind of reason.
An outcome reaches a change through the task id and the attempt ordinal it names
(`series_outcomes.columns`), and a recorder that stated neither cannot be found by one.
The other route into those cells is the sha an outcome carries, and that is the `own`
argument an uncaptured row already passes.

## What the cohort names

`process_from_recording_captures` is the list of row keys whose process columns came from
a recording capture rather than from an attempt, in row order, cut to the retained rows
like `captured_rows` and `uncaptured_rows` beside it. Named rather than counted, because
`attempts_to_land` is None on exactly these rows and on the uncaptured ones and those are
two different unknowns, and a reader who cannot tell them apart cannot read the column.

The dropped list stops calling such a capture something this clock knows to be false.
`series_lineage.lineage` drops every capture that named no attempt with

> no task_id and attempt: not an attempt of this lineage

which on the change clock is true and misleading in one sentence: the capture is not a row
of the attempt clock AND it filled seven columns of a row of this one. On the change clock
that sentence becomes

> recorded &lt;sha&gt; at &lt;rung&gt;: process columns folded, attempts_to_land unknown

Only for a capture something was taken from. A capture that recorded nothing keeps
today's sentence, and so does one whose change an attempt landed: that row folded the
attempt, and nothing of that capture reached the frame.

A capture that recorded a commit at a rung and has no capture lifecycle activity is
refused by name instead, with `series_changes.NO_COVERAGE`, and its process columns are
not folded. No coverage word is assumed for it: a capability map is a measurement of one
capture, and defaulting one would put a word on a column nobody measured. Measured on the
E16 store copy on 2026-09-07, this refusal has never fired: all 33 captures that recorded
a commit at a rung have the row, as do all 1459 codex captures.

## What it changed on the data that exists

Measured on the E16 store copy (`experiments/E16/out/home/telltale.db`, 2026-09-07):

- 713 `telltale.repo.commit` observations: 657 `unlinked`, 54 `tree_match_during`, 2
  `provider_reported`.
- 33 captures recorded a commit at a rung of the ladder. 61 captures carry an
  `external.correlation` and 161 name a task id and an attempt on `capture_started`.
- **All 33 are attempts.** Zero rows of any of E16's four repositories fold from a
  recording capture, so `process_from_recording_captures` is empty on all four, and the
  rows and row_meta of all four frames (179, 108, 118 and 252 rows) are byte-identical
  before and after, including the five telltale rows that carry an attempt's process
  columns.

That is the honest size of this change on the store E16 ran against: none. The store it
changes is the one day-to-day capture is now filling. W9-T1's live capture
`cap_786c594857d404824628c2ae`, a haiku session in a temporary checkout that made one
commit at `provider_reported`, is the first row anywhere that folds from a recorder:
before this task its `series build --clock change` row printed six repository columns
observed and seven process columns unavailable, and the cohort called the capture "not an
attempt of this lineage". See `docs/log/W9-T2.md` for that row before and after.

The series id of a change-clock frame changes with this task whether or not any row folds
from a recorder, because `series.REDUCER_VERSION` is the hash of `series.py`,
`series_lineage.py` and `series_regime.py`, and this task edits the second. That is the
right direction (a series built by a different fold must not compare equal to one built by
this fold) reached by an accident: `series_changes.py`, `series_outcomes.py` and
`series_paths.py` are not in that hash, so a change to the change clock's fold alone would
not have moved it. Recorded here rather than fixed, because fixing it re-ids every stored
series and is not this task's decision to take.
