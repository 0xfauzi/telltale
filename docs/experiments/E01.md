# E01: which Claude Code facts does each capture surface actually carry on this machine, does capture fail open, and how long after a session exits do records still arrive?

Why this matters (30 seconds): every later wave assumes a fact can be recovered from a
surface. The provider module's `CAPABILITIES` constant, the coverage field on every
Evidence, and the launcher's decision about when a capture is finished all depend on
answers that were assumptions until this run. Two of them were wrong, and one of the two
was wrong in the direction that would have made Telltale claim a number it cannot see.

Decision rule, written before the run (from `briefs/W0-E01`, restated here): the pilot S2
runs first, and the remaining scenarios run only if it stays under 5 minutes and 200,000
tokens. For S7, compaction counts as reproduced if a PreCompact hook, a
`compact_boundary` stream message or an `api_request` with `query_source=compact` is
observed; otherwise S7 is recorded as "not reproducible cheaply", which is a valid
outcome and not a failure. For each fact in the matrix, a surface is `observed` when a
named field carries it, `partial` when something related is carried and the note says
what is missing, and `unavailable` when nothing carries it.

## What we did

8 sessions, one per scenario, all `claude -p --model sonnet` on Claude Code 2.1.257,
macOS 25.6.0 arm64, run on 2026-09-01 between 20:03 and 20:14 UTC. Every session ran in
its own fresh copy of `experiments/E01/fixture_repo` with its own git history, against a
throwaway sink (`experiments/common/capture_receiver.py`) bound to a free port, with the
OTel exporter and eleven matcher-less http hooks pointed at that one port and stdout teed
to `stream.jsonl`. The runner is `experiments/E01/run.py`; every number below comes from
`experiments/E01/out/<scenario>/meta.json` or from the raw `*.jsonl` beside it.

The command line, exactly as issued (this is S2; `meta.json` carries the full argv for
each scenario, including the settings JSON):

```
claude -p --model sonnet --permission-mode bypassPermissions --max-turns 40 \
  --output-format stream-json --verbose \
  --session-id <uuid4> \
  --settings '{"hooks":{"SessionStart":[{"hooks":[{"type":"http","url":"http://127.0.0.1:<port>/hooks/claude","timeout":5}]}], ... eleven events ... }}' \
  "Explain how divide in pkg/calc.py handles zero. Do not edit any file."
```

with cwd set to the scenario's repository copy and this environment added to the
inherited one:

```
CLAUDE_CODE_ENABLE_TELEMETRY=1
OTEL_LOGS_EXPORTER=otlp
OTEL_METRICS_EXPORTER=otlp
OTEL_EXPORTER_OTLP_PROTOCOL=http/json
OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:<port>
OTEL_LOG_TOOL_DETAILS=1
OTEL_LOGS_EXPORT_INTERVAL=1000
OTEL_METRIC_EXPORT_INTERVAL=5000
OTEL_RESOURCE_ATTRIBUTES=telltale.capture_id=<uuid4 hex>,telltale.scenario=<S>
```

`OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_ASSISTANT_RESPONSES` and `OTEL_LOG_TOOL_CONTENT` are
removed from the inherited environment before the child starts, so they are off by
construction rather than by default.

Three scenarios differ from that line:

- S5 (resume) replaces `--session-id <uuid4>` with `--resume <the session id S2
  reported>` and runs in S2's repository copy, because `claude --resume` looks a session
  up under the directory it started in.
- S6 (receiver-down) is S2's prompt with the OTel endpoint and the hook URLs pointed at a
  port nothing is listening on. `capture_receiver.py --down` prints `PORT=0` and exits,
  which is the protocol saying there is no listener; 0 is not a port a client can be
  aimed at, so the port used is an ephemeral one bound and released by the runner.
- S7 (compaction attempt) prefixes S1's prompt with "First read every file in the project
  twice, one file per Read call" and adds `"env": {"CLAUDE_AUTOCOMPACT_PCT_OVERRIDE":
  "5"}` to the settings JSON.

The pilot gate: S2 took 8.772 s and 99,661 tokens against limits of 300 s and 200,000
tokens, so the remaining seven ran. Cost for all 8 sessions: 1.165149 USD, 1,145,266
tokens, 302.2 s of child wall time.

`claude -p` started with `CLAUDECODE=1` still in the environment. The first attempt
succeeded, so nothing was unset, and `experiments/E01/out/claudecode-probe.json` records
that measurement (`{"drop_claudecode": false, "measured_by": "S2",
"first_attempt_refused": false, "claudecode_in_parent_env": true}`). The runner would
have retried once with `CLAUDECODE` removed had the first attempt exited non-zero in
under 20 s with no result message.

### The late-export window

Zero, in every scenario. The sink was kept alive for 15 s after each child exited, and
across all seven scenarios with a live sink not one request arrived after the exit. The
closest any surface came to the boundary was 0.24 s BEFORE it (S4), and the largest gap
was 0.561 s before it (S3).

| scenario | last request relative to child exit (s) | requests after exit | late-export window (s) |
|---|---|---|---|
| S1 | -0.291 | 0 | none observed |
| S2 | -0.470 | 0 | none observed |
| S3 | -0.561 | 0 | none observed |
| S4 | -0.240 | 0 | none observed |
| S5 | -0.516 | 0 | none observed |
| S6 | no requests (receiver down) | 0 | not measurable |
| S7 | -0.244 | 0 | none observed |
| S8 | -0.284 | 0 | none observed |

Maximum over the whole experiment: no request at all after exit, so the observed
late-export window is 0.0 s and the largest measured value is a negative number, which
means Claude Code 2.1.257 flushes both exporters before the process ends. `meta.json`
records this as `late_export.late_export_window_s = null` rather than 0, because "nothing
arrived late" and "something arrived 0.0 s late" are different statements.

This is measured under `OTEL_LOGS_EXPORT_INTERVAL=1000` and
`OTEL_METRIC_EXPORT_INTERVAL=5000` on sessions of 4 to 183 s. It does not license
dropping the wait: it says the wait was never needed here, on 7 sessions, with these two
intervals.

The whole of S6's stderr, from `experiments/E01/out/S6/stderr.txt`:

```
SessionEnd hook [http://127.0.0.1:65009/hooks/claude] failed: connect ECONNREFUSED 127.0.0.1:65009
```

One line, for one hook, at the end. The PreToolUse and PostToolUse http hooks pointed at

on stderr, and it never changes the exit code or the answer.

### S7, the compaction attempt: kept

The decision rule asked for any one of three markers. All three appeared.

| marker | count | source |
|---|---|---|
| `claude_code.compaction` OTel event | 4 | `out/S7/otel_logs.jsonl` |
| `system/compact_boundary` stream message | 3 | `out/S7/stream.jsonl` |

| PreCompact http hook delivered | 4 | `out/S7/hooks.jsonl` |
| PostCompact http hook delivered | 3 | `out/S7/hooks.jsonl` |

The four compaction events and their numbers, verbatim from the attributes:

| trigger | success | pre_tokens | post_tokens | duration_ms | error |
|---|---|---|---|---|---|
| auto | false | 34181 | absent | 2 | too_few_groups |
| auto | true | 35113 | 3909 | 54248 | |
| auto | true | 38398 | 8138 | 46295 | |
| auto | true | 42366 | 5193 | 53323 | |

The first attempt failed and reported it, which is why the event carries `success` and
`error` at all, and why a reducer must not read `pre_tokens` without checking `success`.
The stream's `compact_metadata` adds `cumulative_dropped_tokens` (31204, 61464, 98637)
and a `preserved_segment` of message uuids.

S7 is also the only scenario that exited non-zero. It ended after 22 turns with
`terminal_reason: rapid_refill_breaker` and this result text: "Autocompact is thrashing:
the context refilled to the limit within 3 turns of the previous compact, 3 times in a
row." That is the expected consequence of setting the auto-compact threshold to 5 percent
and then asking for every file to be read twice. The result message's `subtype` is
`success` while `is_error` is true, so a reader that trusts `subtype` alone reads a
failed session as a successful one.

Beyond the names above, four differences matter enough to state in prose:

1. **The digest says "No compaction OTel event exists." It does exist.**
   `claude_code.compaction` carries `trigger`, `pre_tokens`, `post_tokens`,
   `duration_ms`, `success` and `error`. Section 2.1 needs correcting, and the correction
   is worth a claim: compaction pre and post token counts are available on the OTel log
   surface alone, without the stream.
2. **`claude_code.user_prompt` carries a `prompt` attribute even with
   `OTEL_LOG_USER_PROMPTS` unset, and its value is the literal string `<REDACTED>`.**
   Same for `response` on `claude_code.assistant_response`. The attribute exists; the
   content does not. A parser must not treat the presence of the key as the presence of
   the prompt.
3. **`--max-turns` is not in `claude --help` for 2.1.257 and still works.** The binary
   contains the option string `--max-turns <turns>`; every scenario passed
   `--max-turns 40` and no session reported an unknown option. The flags that ARE
   documented for budget control are `--max-budget-usd` and `--autocompact`.
4. **`query_source` is `sdk` in headless mode**, not `repl_main_thread` as the digest's
   example list suggests, and `compact` during compaction.

### Which hooks fired, and which did not

The owner's global hooks are in `~/.claude/settings.json` and were neither edited nor
suppressed. They all fired, and all succeeded. From
`claude_code.hook_execution_complete` in S2 (`num_hooks` is how many hooks ran for that
event, `num_success` how many succeeded):

| event | num_hooks | num_success | which hooks |
|---|---|---|---|
| SessionStart:startup | 3 | 3 | 2 from `~/.claude/settings.json` (`praxis nudge`, `context_handoff_restore.sh`) plus 1 plugin hook. The declared http hook is NOT among them. |
| UserPromptSubmit | 2 | 2 | 1 from `~/.claude/settings.json` (`context_handoff.sh`) plus 1 plugin hook |
| PreToolUse:Bash | 1 | 1 | the declared http hook only |
| PostToolUse:Bash | 2 | 2 | 1 plugin hook plus the declared http hook |
| PostToolUse:Edit (S1) | 4 | 4 | includes `complexity_advisory.py` from `~/.claude/settings.json` |
| Stop | 3 | 3 | 1 from `~/.claude/settings.json` (`praxis reflect --session-end`) plus 1 plugin hook plus the declared http hook |

Two absences, both measured rather than inferred:

- **The SessionStart http hook is registered and never executed.** The registration is
  visible: `claude_code.hook_registered` shows 4 SessionStart hooks in S2, one of them
  `hook_type=http, hook_source=flagSettings`. The execution is visible too:
  `hook_execution_start` reports `num_hooks=3` for `SessionStart:startup`, and no request
  ever reaches `/hooks/claude` for SessionStart in any of the seven scenarios with a live
  sink. The same is true of `SessionStart:compact`, which fires 3 times in S7 with
  `num_hooks=3`. A launcher that wants a session-start signal over http cannot have one
  on 2.1.257; SessionEnd, which does fire, is the only bracketing hook available.
- **PreCompact and PostCompact http hooks are delivered but produce no
  `claude_code.hook_execution_*` events.** S7's sink received 4 PreCompact and 3
  PostCompact requests while `hook_execution_start` in the same session names only
  PostToolUse, PostToolUseFailure, PreToolUse, SessionStart, SubagentStop and
  UserPromptSubmit. The hook telemetry does not cover the compaction hooks.

`PostModelSwitch` was declared and never fired, which is expected: no scenario switched
model, so this is an absence of the event and not evidence about the hook.

### What reached which surface: the privacy probes

`secrets_note.txt` in the fixture holds three fake credentials, each carrying the marker
TELLTALEFAKE. S3 prints the file with `cat`; S7 reads every file twice. Lines containing
the marker, per surface:

| scenario | otel_logs | otel_metrics | hooks | stream |
|---|---|---|---|---|
| S3 | 0 | 0 | 3 | 4 |
| S7 | 0 | 0 | 4 | 3 |
| all others | 0 | 0 | 0 | 0 |

With `OTEL_LOG_TOOL_DETAILS=1` and the two content switches off, the OTel surfaces
carried no file content at all: `tool_input` and `tool_parameters` describe the CALL
(`{"command":"cat secrets_note.txt"}`), never its result. The http hooks carry the file
content in `PostToolUse.tool_response.stdout` and in `Stop.last_assistant_message`, and
the stream carries it in the `tool_result` block, in `tool_use_result` and in the
assistant's own text. The sanitizer that wave 1 builds therefore has to be a hook-and-
stream sanitizer first; on the OTel surfaces there is nothing of that kind to remove.

### Fixtures

`fixtures/sources/claude/2.1.257/` holds one directory per scenario, S1 to S8, each with
a `MANIFEST.md` listing requests per surface, observation counts by event name, and the
replacement table. S6 has only `stream.jsonl`, because its receiver was down and the
other three files were never written; its MANIFEST reports 0 for those surfaces.
`grep -r TELLTALEFAKE fixtures/sources/claude | wc -l` is 22.

`experiments/E01/sanitize_fixture.py` replaced two classes of thing and nothing else: the
machine (repository path, home directory, both in slash and dashed-slug form, and the
account name on its own, which `ls -l` prints in the owner column) and the person
(`user.id`, `user.email`, `user.account_id`, `user.account_uuid`, `organization.id`,
each with a fixed fake value so the same person stays the same person across scenarios).
It refuses to write a fixture if a real value survives, or if the TELLTALEFAKE count
changes.

## What it means

The pilot stayed inside its budget, so the experiment ran in full: 8 sessions for 1.17
USD. Every branch of the decision rule that could be taken was taken, and S7 was kept
rather than recorded as not reproducible.

For the design, three consequences:

1. **Nothing needs a late-export grace period on this version, and the launcher should
   keep one anyway.** The measurement says the flush happens before exit on 7 sessions.
   It does not say it always will, and the cost of waiting is bounded while the cost of
   not waiting is a truncated capture. What the measurement does NOT give is a number to
   size the wait with: there is no positive lateness to scale, so the only defensible
   inputs are the export intervals themselves (1000 ms for logs, 5000 ms for metrics as
   configured here). The size of a launcher's grace period needs measuring on a version
   or a session shape that does export late, and this one does not.
2. **The four surfaces are not four views of one thing. They are four different
   instruments.** Only the stream has the context window size and the subagent's parent
   link. Only the OTel logs have tool input sizes, per-request cost and compaction token
   counts in one place. Only the hooks have the permission mode on every tool call.
   Nothing except the OTel logs has a tool exit status, and nothing at all has a bash
   exit code.
3. **Capture fails open on this version without Telltale doing anything.** The 0.9 s and
   the single stderr line in S6 are the cost of a dead receiver, and design rule 8 (any
   Telltale exception becomes a diagnostic row and never changes the child) is consistent
   with what the provider already does.

## What we rejected

**That the digest's list of OTel events was complete enough to build against.** It named
10 log events; the capture produced 12, of which 6 are not in the digest, and one of
those 6 (`claude_code.compaction`) is a fact the digest explicitly says does not exist on
this surface. Building `CAPABILITIES` from the digest would have declared compaction
unavailable on OTel and sent a reducer to the stream for a number the OTel surface
carries.

**That an attribute's presence means its content is present.** `user_prompt.prompt` and
`assistant_response.response` are always there. Their value is `<REDACTED>` unless the
content switches are on. A capability check written as "does the payload have a prompt
field" answers yes and is wrong.

**That "no requests after exit" could be recorded as a 0.0 s late-export window.** It is
recorded as null. Zero is a measurement; null is the absence of one, and the distinction
is the same one AGENTS.md invariant 5 makes about coverage.

**That the SessionStart http hook not arriving might be a receiver bug.** It is not: the
sink answered 200 to the other 198 requests across the same runs, the hook is registered
(`hook_registered` with `hook_type=http`), and `hook_execution_start` counts 3 executions
where 4 hooks are registered. The provider does not run it.

## What downstream may now say

Claim class `observed` is available for anything the matrix marks `observed`, cohort
"Claude Code 2.1.257, headless `-p`, macOS arm64, one machine, 8 sessions", with the
coverage caveat that S6 has one surface and every other scenario has four. A `partial`
cell may be used only with its note attached, and the note is part of the coverage
statement rather than a footnote to it: "tool success on the hooks surface" means "the
event name differed", not "a success field said so". An `unavailable` cell is a coverage
statement of its own, and per AGENTS.md invariant 5 it must reach a report as "not
observable on this surface" and never as 0. No comparative or predictive claim is
supported by this experiment: 8 sessions on one machine with one model is not a sample.
