# E02: which Codex facts can a launcher actually observe, on which surface, and what does it cost the session being recorded?

Why this matters (30 seconds): the design says Telltale captures a Codex session from the
launcher alone, through `codex exec --json`, OTel over otlp-http, hooks, and the rollout
file, and that any failure of that capture leaves the recorded session untouched. Four
things have to be true for that to hold. The exact `-c` spelling for the OTel exporter has
to exist, because the config reference documents the keys and not the TOML shape. Hooks
have to fire under `codex exec` at all, because `exec` is not the interactive TUI. Every
fact a measure needs has to appear on at least one surface, or the measure is not
computable. And a receiver that is not listening has to cost the session nothing.

Decision rule, written before the run (recorded 2026-09-01, before the first `codex exec`
of this experiment):

- If one `-c` spelling produces OTLP requests at the sink, that spelling is what
  `telltale run --provider codex` will pass, verbatim. If none does, Codex OTel is not a
  Telltale surface and the digest's OTel bullet is wrong.
- If hooks fire under `exec`, hooks are a capture surface for Codex. If they do not, the
  design's hook-derived facts come from the exec stream and the rollout or not at all.
- Any fact that no surface carries is `unavailable` and the measure that needs it is not
  built. Unknown stays unknown; nothing is inferred from an adjacent field.
- If pointing the exporter and the hooks at a closed port changes the child's exit code,
  its output, or its wall time beyond noise, capture is not fail-open and the launcher
  design changes before anything else is built.

## What we did

Codex CLI 0.150.1 (`codex --version` -> `codex-cli 0.150.1`), macOS 25.6.0, the owner's
own `~/.codex/config.toml` loaded (model `gpt-5.6-sol`, sandbox `workspace-write` with
network, five MCP servers). Nothing in `~/.codex` or `~/.claude` was written.

Each scenario copies `experiments/E02/fixture_repo/` to `experiments/E02/out/<S>/repo`,
gives it its own git history and one commit, starts
`experiments/common/capture_receiver.py` on an ephemeral port, writes a project-level
`<repo>/.codex/hooks.json` registering all twelve hook events against
`experiments/E02/hook_post.py`, and runs:

```
codex exec --json -C <repo> -s workspace-write --skip-git-repo-check \
  --dangerously-bypass-hook-trust \
  -c model_reasoning_effort="low" \
  -c 'otel.exporter={ "otlp-http" = { endpoint = "http://127.0.0.1:PORT", protocol = "json" } }' \
  -c 'otel.trace_exporter={ "otlp-http" = { endpoint = "http://127.0.0.1:PORT", protocol = "json" } }' \
  -c 'otel.metrics_exporter={ "otlp-http" = { endpoint = "http://127.0.0.1:PORT", protocol = "json" } }' \
  -c otel.environment="telltale-e02" \
  "<prompt>"
```

stdout to `out/<S>/exec.jsonl`, stderr to `out/<S>/stderr.txt`, the sink kept alive 15
seconds past the child's exit. `experiments/E02/rollouts.py` then finds the rollout by
thread id and copies it in, `sanitize_fixture.py` rewrites the lot into
`fixtures/sources/codex/0.150.1/<S>/`, and `matrix.py` builds the table below by searching
those bytes rather than by asserting anything.

## What we measured

### The `-c` spelling

The exporter is a serde externally tagged enum. `strings` on the binary shows
`struct variant OtelExporterKind::OtlpHttp with 4 elements` (endpoint, headers, protocol,
tls) and `OtelConfigToml` with eight fields: `tool_result`, `log_user_prompt`,
`environment`, `exporter`, `trace_exporter`, `metrics_exporter`, `span_attributes`,
`tracestate`. Struct variant means the tag alone is not a value.

Every candidate below was tested with `experiments/E02/config_probe.py`, which uses
`codex doctor --json` (same config loader, no model call) as the accept/reject oracle and
`codex exec` for the verbatim message. Zero tokens. Raw record:
`experiments/E02/out/config_probe.json`.

| candidate | verdict | what Codex said |
|---|---|---|
| `-c 'otel.exporter={ "otlp-http" = { endpoint = "URL", protocol = "json" } }'` | accepted | config loaded; 4 OTLP requests at the sink |
| `-c otel.exporter.otlp-http.endpoint="URL" -c otel.exporter.otlp-http.protocol="json"` | accepted | config loaded (dotted keys build the same table) |
| `-c otel.exporter="otlp-http"` alone | REJECTED | `Error loading config.toml: invalid type: unit variant, expected struct variant` / `in \`otel.exporter\`` |
| `-c otel.exporter=42` | REJECTED | `Error loading config.toml: invalid type: unit variant, expected string only` / `in \`otel.exporter\`` |
| `-c otel.exporter="none"` | accepted | `none` is a unit variant of the same enum |
| `-c otel.exporter="otlp-http"` followed by the dotted member keys | accepted, but not on its own merits: the later dotted overrides replace the string with a table before the enum is ever deserialized |

`otel.trace_exporter` and `otel.metrics_exporter` take the same shape and load.
`otel.environment="telltale-e02"` loads and appears as the resource attribute `env`.

**The endpoint is used verbatim. Codex appends no signal path.** Measured twice, with the
same prompt and the same failure point: with `endpoint = "http://127.0.0.1:PORT"` all four
OTLP requests arrived on `/` (`out/S2/other.jsonl`); with
`endpoint = "http://127.0.0.1:PORT/v1/logs"` all four arrived on `/v1/logs`
(`out/S2-signalpath/otel_logs.jsonl`). A launcher must therefore spell the full path it
wants, or the receiver must accept any path.

### Config validation: `--strict-config` exists and cannot be used here

`codex exec --strict-config` is the only config-validation flag on any subcommand
(`codex doctor` rejects it with `error: unexpected argument '--strict-config' found`).
It does validate `-c` overrides, in preference to the file:
`Error loading config.toml: unknown configuration field \`otel.definitely_not_a_key\` in
-c/--config override`. Without it an unrecognised key under `otel.` is silently ignored,
which is how a misspelled exporter key would look exactly like a working one.

It cannot be used for a capture that runs beside the owner's own config. The first S2
attempt used it and exited 1 in 0.036 s having spent no tokens:

```
Error loading config.toml:
/Users/wumpinihussein/.codex/config.toml:72:1: unknown configuration field `features.multo_agent`
   |
72 | multo_agent = true
   | ^^^^^^^^^^^
```

The owner's config carries a feature key this Codex build does not recognise, so strict
mode refuses the whole file. The overrides are validated separately instead: run under
`--strict-config` from a neutral cwd, spellings (a) and (c) produce the `features.multo_agent`
complaint and no override complaint, which is only possible if every key in them is known.

### Hooks under `codex exec`

The project-level `<repo>/.codex/hooks.json` is read and honoured with
`--dangerously-bypass-hook-trust`. Two facts about the file format came out of it.

`~/.codex/hooks.json` on this machine does not parse:
`failed to parse hooks config /Users/wumpinihussein/.codex/hooks.json: invalid type: map,
expected a sequence at line 3 column 4`. That file is a list of `{event, command}` objects
written by `praxis`; Codex 0.150.1 wants the Claude Code shape, a map of event name to a
list of `{matcher?, hooks: [{type, command, timeout}]}`. **The owner's praxis Codex hooks
are not running.** This is reported, not fixed: Telltale never edits that file.

**Hook timeouts are clamped.** With `"timeout": 15` on every event, Codex emitted
`clamping SessionEnd hook timeout to 3s` and `clamping Interrupt hook timeout to 3s`,
naming the file. The other ten events were not clamped. A hook on session end therefore
cannot block the child for more than 3 seconds whatever the config says.

`Interrupt` is a twelfth hook event that `00-digest.md` 2.2 does not list; Codex accepted
it and clamped its timeout, so the name is real in this build. The enum in the binary is
`PreToolUse, PermissionRequest, PostToolUse, PreCompact, PostCompact, SessionStart,
SessionEnd, UserPromptSubmit, SubagentStart, SubagentStop, Stop, Interrupt`.

### `--ephemeral`

`out/S7-quotablock` ran the same prompt with `--ephemeral`. `rollouts.py` searched
`~/.codex/sessions` for its thread id `01a05ea8-e443-7480-9971-36701d8aa316` and reported
`no rollout file`, against `copied` for every non-ephemeral run. **`--ephemeral` disables
the rollout surface.**

### `codex exec resume`

`out/S4-quotablock` resumed S2's thread. It accepted the same `-c` overrides (4 OTLP
requests arrived), found the same project-level `.codex/hooks.json` (the clamping message
names `out/S2/repo/.codex/hooks.json`), fired the same three hooks, and reported the SAME
`thread_id` on `thread.started`. `codex exec resume` takes neither `-C` nor `-s`: the cwd
of the process is what makes the project hooks discoverable.

**Resume APPENDS to the existing rollout file.** The S2 rollout went from 12 records to 19
under the same filename. One rollout file can hold turns from several separate process
invocations, which the backfill importer has to expect.
