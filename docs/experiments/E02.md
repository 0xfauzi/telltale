# E02: which Codex facts can a launcher observe, on which surface, and what does capture cost the session being recorded?

Why this matters (30 seconds): the design says Telltale captures a Codex session from the
launcher alone, through `codex exec --json`, OTel over otlp-http, hooks, and the rollout
file, and that any failure of that capture leaves the recorded session untouched. Four
things have to be true. The exact `-c` spelling for the OTel exporter has to exist,
because the config reference documents the keys and not the TOML shape. Hooks have to fire
under `codex exec`, which is not the interactive TUI. Every fact a measure needs has to
appear on at least one surface, or the measure is not computable. And a receiver that is
not listening has to cost the session nothing.

Decision rule, written before the run (recorded 2026-09-01, before the first `codex exec`
of this experiment):

- If one `-c` spelling produces OTLP requests at the sink, that spelling is what
  `telltale run --provider codex` passes, verbatim. If none does, Codex OTel is not a
  Telltale surface and the digest's OTel bullet is wrong.
- If hooks fire under `exec`, hooks are a capture surface for Codex. If they do not, the
  hook-derived facts come from the exec stream and the rollout, or not at all.
- Any fact that no surface carries is `unavailable` and the measure that needs it is not
  built. Unknown stays unknown; nothing is inferred from an adjacent field.
- If pointing the exporter and the hooks at a closed port changes the child's exit code,
  its output, or its wall time beyond noise, capture is not fail-open and the launcher
  design changes before anything else is built.

## What we did

Codex CLI 0.150.1 (`codex --version` -> `codex-cli 0.150.1`), macOS 25.6.0, the owner's
own `~/.codex/config.toml` loaded (model `gpt-5.6-sol`, sandbox `workspace-write` with
network, five MCP servers). Nothing under `~/.codex` or `~/.claude` was written.

Each scenario copies `experiments/E02/fixture_repo/` to `experiments/E02/out/<S>/repo`,
gives it its own git history and one commit, starts
`experiments/common/capture_receiver.py` on an ephemeral port, writes a project-level
`<repo>/.codex/hooks.json` registering all twelve hook events against
`experiments/E02/hook_post.py`, and runs:

```
codex exec --json -C <repo> -s workspace-write --skip-git-repo-check \
  --dangerously-bypass-hook-trust \
  -c model_reasoning_effort="low" \
  -c 'otel.exporter={ "otlp-http" = { endpoint = "http://127.0.0.1:PORT", protocol = "json" } }' \
  -c 'otel.trace_exporter={ "otlp-http" = { endpoint = "http://127.0.0.1:PORT", protocol = "json" } }' \
  -c 'otel.metrics_exporter={ "otlp-http" = { endpoint = "http://127.0.0.1:PORT", protocol = "json" } }' \
  -c otel.environment="telltale-e02" \
  "<prompt>"
```

with `codex exec resume <thread id>` in place of the first three arguments for S4, and
`--ephemeral` added for S7. stdout goes to `out/<S>/exec.jsonl`, stderr to
`out/<S>/stderr.txt`, and the sink is kept alive 15 seconds past the child's exit.
`experiments/E02/rollouts.py` finds the rollout by thread id and copies it in,
`sanitize_fixture.py` rewrites the lot into `fixtures/sources/codex/0.150.1/<S>/`, and
`matrix.py` builds the table below by searching those bytes.

Seven scenarios, all exit code 0, 568,665 model tokens in total, 180.4 seconds of child
wall time. Five further `codex exec` invocations ran while the account's usage limit was
exhausted; they created threads, exported OTel, ran hooks and wrote rollouts, and spent no
model tokens, so they are used below wherever a question is about startup rather than
about a turn. They are in `out/<S>-<label>/` and are not part of the matrix.

## What we measured

### The `-c` spelling

The exporter is a serde externally tagged enum. `strings` on the binary shows
`struct variant OtelExporterKind::OtlpHttp with 4 elements` (endpoint, headers, protocol,
tls) and `OtelConfigToml` with eight fields: `tool_result`, `log_user_prompt`,
`environment`, `exporter`, `trace_exporter`, `metrics_exporter`, `span_attributes`,
`tracestate`. A struct variant means the tag alone is not a value.

Every candidate was tested with `experiments/E02/config_probe.py`, which uses
`codex doctor --json` (the same config loader, no model call) as the accept/reject oracle
and `codex exec` for the verbatim message. Zero tokens. Raw record:
`experiments/E02/out/config_probe.json`.

| candidate | verdict | what Codex said |
|---|---|---|
| `-c 'otel.exporter={ "otlp-http" = { endpoint = "URL", protocol = "json" } }'` | ACCEPTED | config loaded, and OTLP requests arrive |
| `-c otel.exporter.otlp-http.endpoint="URL" -c otel.exporter.otlp-http.protocol="json"` | accepted | dotted keys build the same table |
| `-c otel.exporter="otlp-http"` alone | rejected | `Error loading config.toml: invalid type: unit variant, expected struct variant` / `in \`otel.exporter\`` |
| `-c otel.exporter=42` | rejected | `Error loading config.toml: invalid type: unit variant, expected string only` / `in \`otel.exporter\`` |
| `-c otel.exporter="none"` | accepted | `none` is a unit variant of the same enum |
| `-c otel.exporter="otlp-http"` then the dotted member keys | accepted, but not on its own merits: the later dotted overrides replace the string with a table before the enum is deserialized |

`otel.trace_exporter` and `otel.metrics_exporter` take the same shape.
`otel.environment="telltale-e02"` appears as the resource attribute `env`.

**The endpoint is used verbatim. Codex appends no signal path.** Measured twice with the
same prompt and the same failure point: with `endpoint = "http://127.0.0.1:PORT"` the
requests arrive on `/` (`out/S2/other.jsonl`, and the receiver files them under `other`);
with `endpoint = "http://127.0.0.1:PORT/v1/logs"` they arrive on `/v1/logs`
(`out/S2-signalpath/otel_logs.jsonl`). The launcher must spell the full path it wants.

### Config validation: `--strict-config` exists and cannot be used here

`codex exec --strict-config` is the only config-validation flag on any subcommand
(`codex doctor` rejects it with `error: unexpected argument '--strict-config' found`). It
validates `-c` overrides in preference to the file:
`Error loading config.toml: unknown configuration field \`otel.definitely_not_a_key\` in
-c/--config override`. Without it, an unrecognised key under `otel.` is silently ignored,
so a misspelled exporter key looks exactly like a working one.

It cannot be used for a capture that runs beside the owner's config. The first S2 attempt
used it and exited 1 in 0.036 s having spent nothing:

```
Error loading config.toml:
/Users/wumpinihussein/.codex/config.toml:72:1: unknown configuration field `features.multo_agent`
   |
72 | multo_agent = true
   | ^^^^^^^^^^^
```

The overrides are validated separately instead: run under `--strict-config` from a neutral
cwd, spellings (a) and (c) produce the `features.multo_agent` complaint and no override
complaint, which is only possible if every key in them is recognised.

`otel_traces` is measured and is not a column, and the reason is cost rather than
content. It is the CLI's internal Rust tracing, one span per function (`receiving`,
`handle_responses`, `append_items`, `auth`), with `code.file.path`, `thread.name` and
`busy_ns`. It does carry matrix facts, 13 of the 21, some on proper `gen_ai.usage.*`
attributes: `spans[111].attributes[7].gen_ai.usage.input_tokens` is a real per-span token
count. **It carries none of them uniquely.** Every one is also on the rollout or the exec
stream, and the price of the duplicate is the whole argument: S6 produced **5707 spans in
72 seconds**, 5.8 MB from one scenario, and indexing the sanitized fixture yields 797,634
distinct paths against the rollout's 5,510 for 19 of the same 21 facts. A surface that is
145 times the size for strictly less information is not a trade.

The token counts on `otel_metrics` are `partial` for a reason that matters: they are ONE
histogram, `codex.turn.token_usage`, dimensioned by a `token_type` label whose values are
`input`, `cached_input`, `cache_write_input`, `output`, `reasoning_output`, `total`. The
value is in the data point's `sum`; the buckets are lossy. Use the exec stream or the
rollout for a per-turn count and the metric for nothing.

`model_context_window` is on the rollout ONLY, and not where the digest says. It is
`event_msg/task_started.model_context_window` (258400 on every one of the six scenarios
that wrote a rollout), not `event_msg/token_count.info.model_context_window`, which is
also present but null on the turns measured here.

| event | fired | count over the seven scenarios |
|---|---|---|
| SessionStart | yes | 7 |
| UserPromptSubmit | yes | 7 |
| PreToolUse | yes | 20 |
| PostToolUse | yes | 19 |
| Stop | yes | 7 |

| PreCompact | no | 0 |
| PostCompact | no | 0 |
| SubagentStart | no | 0 |
| SubagentStop | no | 0 |

All twelve were registered in the same `<repo>/.codex/hooks.json`. The six that never
fired were never provoked: no approval was requested (exec forces
`approval_policy = "never"`, confirmed in `turn_context`), no compaction occurred, no
subagent ran, and no interrupt was sent. `unavailable` here means "not observed in this
cohort", not "does not exist".

**PreToolUse and PostToolUse do not pair.** S6 fired 8 PreToolUse against 7 PostToolUse,
for tools `Bash, Bash, apply_patch, Bash, Bash, Bash, Bash, Bash` and
`Bash, Bash, apply_patch, Bash, Bash, Bash, Bash`. Anything that counts tool calls by
pairing them will be wrong by one per session.

Three more facts about the hook configuration, from
`out/<S>/exec.jsonl` where Codex reports them as `item.completed` errors:

- **Hook timeouts are clamped.** With `"timeout": 15` on every event, all seven runs
  emitted `clamping SessionEnd hook timeout to 3s` and `clamping Interrupt hook timeout
  to 3s`, naming the file. The other ten events were not clamped. A hook on session end
  cannot block the child for more than 3 seconds whatever the config says.
- **`~/.codex/hooks.json` on this machine does not parse.** All seven runs reported
  `failed to parse hooks config <home>/.codex/hooks.json: invalid type: map, expected a
  sequence at line 3 column 4`. That file is a list of `{event, command}` objects written
  by `praxis`; Codex 0.150.1 wants the Claude Code shape, a map of event name to a list of
  `{matcher?, hooks: [{type, command, timeout}]}`. The owner's praxis Codex hooks are not
  running. Reported, not fixed: Telltale never edits that file.
- `--dangerously-bypass-hook-trust` prints its warning twice per run, once per hooks file
  considered.

`Interrupt` is a twelfth hook event that `00-digest.md` 2.2 does not list. Codex accepted
it and clamped its timeout, so the name is real in this build.

### Fail-open

S5 is S2's prompt with the exporter and the hook command pointed at a port nothing is
listening on (`capture_receiver.py --down` prints `PORT=0` and exits; the scenario then
reserves and releases an ephemeral port so the connection is REFUSED rather than
malformed).

| | S2, live sink | S5, closed port |
|---|---|---|
| exit code | 0 | 0 |
| wall time | 20.840 s | 16.730 s |
| input tokens | 60,827 | 60,837 |
| output tokens | 391 | 347 |
| exec stream shape | 10 `item.completed`, 2 `item.started` | 10 `item.completed`, 2 `item.started` |
| hook invocations | 8 | 8 |
| hooks delivered | 8 | 0, all `URLError` |
| total hook delivery time | 0.0979 s | 0.0968 s |
| requests at the sink | 8 hooks, 18 OTLP | none |

The closed-port run was FASTER, which is the honest reading of a sample of one against
model-latency variance rather than a claim that capture saves time. Nothing in the child
changed: same exit code, same event shape, the same eight hooks fired, and the hook
command exited 0 every time. The refused connection costs about 12 ms per hook
(`delivery_elapsed_s_max` 0.0145 s), and 8 hooks make 0.0968 s across a 16.7 s session,
which is 0.6 percent.

### The late-export window

Seconds between the child's exit and the last request the sink saw, per scenario, from
`out/<S>/meta.json` `sink.late_export_window_s`:

| scenario | S1 | S2 | S3 | S4 | S6 | S7 |
|---|---|---|---|---|---|---|
| latest ingest, relative to child exit | -0.029 | -0.024 | -0.012 | -0.015 | -0.053 | -0.030 |

**Every value is negative: the last export lands 12 to 53 milliseconds BEFORE the process
exits.** Codex flushes its exporters during shutdown and then exits. A launcher needs no
linger to catch a late export on this version. The 15 seconds this experiment waited
caught nothing on any scenario, which is the measurement, not a disappointment.

### `--ephemeral`

S7 ran S2's prompt with `--ephemeral` and completed a turn (exit 0, 59,513 tokens).
`rollouts.py` searched `~/.codex/sessions` for its thread id and reported `no rollout
file`, against `copied` for every other scenario. **`--ephemeral` removes the rollout
surface, and with it `model_context_window`, which no other surface carries.**

### `codex exec resume`

S4 resumed S2's thread. It accepted the same `-c` overrides (11 OTLP requests arrived),
found the same project-level `.codex/hooks.json` (the clamping message names
`out/S2/repo/.codex/hooks.json`), fired 4 hooks, and reported the SAME `thread_id` on
`thread.started`. `codex exec resume` takes neither `-C` nor `-s`: the process cwd is what
makes the project hooks discoverable.

**Resume APPENDS to the existing rollout file.** S2's rollout went from 12 records to 19
under the same filename during the rehearsal, and S2 and S4 share one rollout file in the
final run. One rollout file can hold turns from several separate process invocations.

### What the surfaces carry that a sanitizer must remove

S3 asked the agent to `cat secrets_note.txt`, whose three TELLTALEFAKE probes are the
test. Counting occurrences in the sanitized S3 fixture:

| surface | lines carrying TELLTALEFAKE | occurrences |
|---|---|---|
| `exec.jsonl` | 2 | 6 |
| `hooks.jsonl` | 2 | 6 |
| `hooks_local.jsonl` | 2 | 6 |
| `otel_logs.jsonl` | 1 | 10 |
| `otel_metrics.jsonl` | 0 | 0 |
| `otel_traces.jsonl` | 0 | 0 |
| `rollout.jsonl` | 5 | 23 |

**The OTel hit is the one that was not expected.** `codex.tool_result` log records carry
an `output` attribute holding the command's stdout, with no content switch enabled and
`otel.log_user_prompt` left off (`codex.user_prompt` correctly shows
`prompt: "[REDACTED]"`). Anything a captured agent prints reaches the receiver.

There is a bound for it. `otel.tool_result` is a `ToolResultLogConfig`, not a boolean:
`-c otel.tool_result=false` gives `invalid type: boolean \`false\`, expected struct
ToolResultLogConfig`. Under `--strict-config`, `enabled` and `context_size` are rejected
as unknown fields and **`-c 'otel.tool_result={ max_bytes = 0 }'` is accepted**.

Every OTel log record also carries `user.account_id` and `user.email` as attributes, on
every event, unconditionally.

**The same defect caught this experiment's own sanitizer.** After a clean regeneration,
five S6 fixture files still held the owner's login name. S6 ran `ls -la`, and `ls` prints
the file owner, so `drwxr-xr-x@ 13 <name>  staff` reached `exec.jsonl`, both hook files,
`rollout.jsonl` and the OTel `codex.tool_result` output attribute, in a session where no
path anywhere near it was the home directory. A sanitizer that rewrites paths does not
catch it, because command output is not a path. `sanitize_fixture.py` now carries a bare
login-name rule and the fixtures are clean: `grep -rl <name> fixtures/sources/codex`
is 0 files, and the ten replacements are visible as `<user>`.

The one path that survives is `/Users/runner/.cargo/registry/...`, which is not the
owner's. It is the GitHub Actions machine that built the Codex binary, baked into
`code.file.path` on the trace surface. It stays, because it is a fact about Codex and a
fixture that hides it would be lying about what the surface emits.

## What it means

Every branch of the rule resolved the same way.

One `-c` spelling produces OTLP requests, and it is the inline table form with the full
signal path in the endpoint. Codex OTel IS a Telltale surface, for logs and metrics; the
trace exporter is not one, because what it emits is the CLI's own function-level tracing
at 80 spans per second and it answers no question the matrix asks.

Hooks fire under `codex exec`. Six of the twelve events were provoked by these seven
scenarios and all six fired, delivered, and cost the child nothing measurable.

Three facts are single-sourced, and each is a dependency worth naming.
`model_context_window`, the occupancy denominator the digest was pleased about, exists
ONLY in the rollout, only in `task_started`, and disappears under `--ephemeral`. `cwd` is
on hooks and the rollout but not the exec stream. `effort` is on OTel logs and the
rollout, not the exec stream and not hooks.

Capture is fail-open on this version, and the launcher needs no shutdown grace period.

## What we rejected

**That the exporter appends the OTLP signal path.** It is the convention
(`OTEL_EXPORTER_OTLP_ENDPOINT` is a base URL in the OTel spec) and it is what a receiver
author would assume. Two runs with identical prompts and endpoints differing only by
`/v1/logs` put the requests on `/` and on `/v1/logs` respectively. The receiver in this
experiment records the request path on every line, which is the only reason the difference
was visible rather than an empty `otel_logs.jsonl` blamed on a wrong spelling.

**That `--strict-config` could guard the capture.** It is the right tool and the first S2
attempt used it. The owner's config.toml contains `features.multo_agent`, which this build
does not recognise, so strict mode refuses the file before anything runs. Keeping it would
have made Telltale's Codex capture fail on the owner's own machine.

**That the fifteen-second linger was needed.** It was in the design because Claude Code's
`OTEL_LOGS_EXPORT_INTERVAL` defaults to 5000 ms and a launcher that tears the receiver
down at exit would lose the tail. Codex flushes before exit on all six scenarios that
exported anything, by 12 to 53 ms. The linger is kept in the runner because it costs
nothing and it is what proved the number.

**That `grep -c reasoning` over the fixture tree can be 0.** The brief's VERIFY line asks
for it. It cannot pass: `reasoning_effort` is how the effort row of the matrix is
observed on OTel logs, `reasoning_output_tokens` is a token row on two surfaces, and the
MANIFEST has to be able to name what it stripped. The check that tests the intent is
`grep -rlE '"(agent_)?[Rr]easoning"' fixtures/sources/codex | wc -l`, which is 0. 22
reasoning rows were dropped from the S1 and S6 rollouts.

## What downstream may now say

Telltale may record Codex sessions as **observed** facts from four surfaces and cite the
field path for each, using the exec stream for per-turn tokens, command text, exit code,
status and file changes; the rollout for `model_context_window`, cwd, effort, sandbox
policy and the same token counts as a cross-check; OTel logs for model, effort, sandbox
policy, cli version and the MCP server list; and hooks for cwd, model, tool name and the
session boundary. The cohort is one machine, one model (`gpt-5.6-sol`), effort low, seven
single-prompt sessions of 8 to 72 seconds, so anything about compaction, subagents, MCP
tool calls, approvals or long sessions is **uncovered**, and a measure needing them must
report coverage rather than a number. Two coverage caveats travel with every Codex claim:
`--ephemeral` removes the rollout and with it the only source of `model_context_window`,
so an occupancy ratio is not computable for an ephemeral session and must be `None`
rather than a default window; and `PreToolUse`/`PostToolUse` do not pair, so a tool-call
count derived from hooks is an upper bound on one side and a lower bound on the other.
