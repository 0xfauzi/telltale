# E03: does TimesFM 3.0.0 install and run on this machine, and what does one forecast cost?

Why this matters (30 seconds): design 6.12 builds the whole forecasting laboratory on a
model that has never been run here. Four claims depend on this experiment. That the
`forecast` extra resolves on Python 3.12 at all, because the collector's zero-dependency
rule means the model stack only ever arrives through that extra. That a backtest is
affordable, because the backtester calls `predict_batch` once per origin and a run has
tens of origins. That the adapter's refusal to pass NaN is a real guard rather than
superstition, because the forecaster interpolates internally and would silently accept
what the adapter refuses. And that `device="cpu"` is the right pin, because design 6.12
pins it "unless E03 shows MPS works" and this is the machine that decides.

## Decision rule, written before the run

Recorded before the first `uv sync --extra forecast` of this experiment and committed
ahead of `experiments/E03/run.py`, which did not exist when this section was written.

- **(a) Installation.** If `uv sync --extra forecast` fails on Python 3.12, report the
  resolver error verbatim and propose the smallest change: a different torch pin, or
  Python 3.11 for the extra alone. The runtime dependency list is not touched either way.
- **(b) Per-call cost.** If a horizon-64 forecast on one 64-point univariate context takes
  more than 60 s on CPU and MPS is unavailable or wrong, the backtester must batch every
  origin of a run into one `predict_batch` call, and the wave 2 backtest brief carries the
  measured per-call cost. Under 60 s, per-window calls are affordable and the measured
  number goes into the brief.
- **(c) The NaN guard.** If a context with NaN produces output differing from the same
  series with the NaN linearly interpolated by less than 1e-6 absolute, the forecaster's
  internal interpolation is confirmed and the adapter's `np.isfinite` assertion is what
  keeps a silent imputation out of a predictive claim. If the difference is larger, record
  it: the adapter still refuses NaN, and the reason changes from "it imputes silently" to
  "it does something else with NaN that we have not characterised".
- **(d) The device pin.** If MPS output differs from CPU output by more than 1e-3 relative
  on any point, `device="cpu"` is pinned in the adapter. Otherwise MPS is allowed, and the
  measured speed factor is what justifies it.

## What we did

Apple M5, 32 GiB (34,359,738,368 bytes), macOS 26.6.2 build 25G83, kernel Darwin 25.6.0,
arm64. CPython 3.12.8, uv 0.11.29. No agent session was started and no token was spent.

```
uv sync                                                  # default env, no extras
uv sync --extra forecast
uv run --extra forecast python -c "import torch; print(torch.__version__)"
uv run --extra forecast python experiments/E03/run.py
uv run --extra forecast python experiments/E03/run.py --canonical
```

`run.py` writes `experiments/E03/out/results.json` and exits 0 (`out/exit_code.txt`, with
its tables in `out/stdout.txt`); `--canonical` is the control that turns the warmup off
and puts the cells back in canonical order, writing `out/results_canonical.json`. Those
two files are the two runs quoted throughout, 108 `predict_batch` calls each, 216 in
total. `experiments/E03/report.py` renders either file without touching the model.

`out/install.json` and `out/import_cost.json` were produced by driving the commands above
from a throwaway script and recording each one's argv, exit code, wall time and output;
every row of the install and import tables below carries its own `cmd` field in those
files, so the command that produced a number is beside the number.

Sample sizes: n=3 per matrix cell (36 cells), n=3 per device arm, n=1 for each of the
seven single probes, replicated once by the canonical run. The matrix is 3 series shapes
(seeded random walk, AR(1) with phi 0.8, step change) x 3 context lengths (16, 64, 512) x
2 horizons (8, 24) x 2 variate counts (1 target; 1 target + 1 past-only covariate + 1
past-future covariate with `padding_mode="edge"`).

The checkpoint is `google/timesfm-3.0-pytorch` under `experiments/E03/out/hf`, which is
gitignored. The weights are `timesfm-non-commercial-license-v1.0`: research use only, and
the licence string is recorded in `out/results.json` under `checkpoint.license` because
design 6.12 puts it in every ForecastRun.

Wall time is taken around `list(forecaster.predict_batch(...))`. `predict_batch` is a
generator: timing the call alone measures the construction of a generator object.

## What we measured

### Installation, decision rule (a)

`uv sync --extra forecast` succeeds on Python 3.12. It did not fail, so no resolver error
exists to report. Raw: `out/install.json`, `out/uv_sync_forecast.txt`,
`out/uv_sync_forecast_cold.txt`.

| step | wall | packages | note |
|---|---|---|---|
| `uv sync` (default) | 1.719 s | 30 installed, 20 removed | removes the forecast extra again |
| `uv sync --extra forecast` | 0.318 s | 20 added | uv cache warm, resolution from `uv.lock` |
| `uv sync --extra forecast`, empty isolated cache | 7.103 s | 50 prepared | `UV_CACHE_DIR` pointed at a throwaway directory |

**There is no resolution step to time.** Both syncs print `Resolved 71 packages in 4ms`,

### What the model stack costs to import, and what ADR-009 says about it

Not asked for by the brief. Measured because the `forecast-isolation` hook's comment
asserts a number ("torch alone is several seconds of import and hundreds of megabytes of
resident memory") that nothing in this repository had measured. Median of 3 fresh
processes each, `out/import_cost.json`:

| module | import wall | RSS after import |
|---|---|---|
| `telltale` | 0.0193 s | 26,525,696 B |
| `numpy` | 0.0261 s | 31,227,904 B |
| `torch` | 1.0224 s | 200,867,840 B |
| `timesfm3` | 1.2963 s | 217,088,000 B |

**The memory half of that comment is right and the time half is 3x too pessimistic on this
machine.** torch is 1.02 s, not several seconds. The rule is unaffected: importing torch
in the collector would multiply its startup by 53 and its resident memory by 7.6, in a
process that runs beside the agent it is recording.

### The checkpoint

`out/results.json` key `checkpoint`, replicated in `out/results_canonical.json`.

| measure | value |
|---|---|
| bytes on disk under `cache_dir` | **1,322,900,328** |
| bytes if symlinks are followed | 2,645,800,425 |
| files | 8 (2 blobs, 2 symlinks, refs, locks, `CACHEDIR.TAG`) |
| first construct, empty cache: download plus load | **32.462 s** |

Both stop conditions are clear: 1.32 GB against a 10 GB limit, 32 s against 30 minutes.

### Per-call cost, decision rule (b)

108 calls per run, n=3 per cell, `device="cpu"`, `torch.get_num_threads()` = 4.

| run | min | median | max |
|---|---|---|---|
| `out/results.json` (12 warmup calls, shuffled cell order) | 0.1480 s | **0.3071 s** | 0.5221 s |
| `out/results_canonical.json` (no warmup, canonical order) | 0.1680 s | 0.3820 s | 0.7245 s |

Medians by factor, main run, over the 36 calls at each context length and the 54 at each
horizon and variate count:

| factor | level | median wall |
|---|---|---|
| context length | 16 | 0.2945 s |
| context length | 64 | 0.2840 s |
| context length | 512 | 0.3698 s |
| horizon | 8 | 0.2994 s |
| horizon | 24 | 0.3157 s |
| variates | 1 target | 0.2913 s |
| variates | 1 target + 2 covariates | 0.3267 s |

**Horizon 8 and horizon 24 cost the same, and that is the model, not the noise.**
`predict_batch` rounds the horizon up to a multiple of `output_patch_length` = 64, so
every horizon from 1 to 64 is one 64-step generation that is then sliced. Design 6.12
already says this; the table is what confirms it here. The two runs disagree about which
horizon is faster (0.2994 s against 0.3157 s here, 0.3876 s against 0.3768 s in the
control run), which is what no difference looks like.

Only the 512-point context is separable from the noise, at about 1.3x the shorter ones.
Two hundred and sixteen calls put every other difference inside the spread.

The slowest calls anywhere are the 33-variate probes, 0.7849 s and 0.8141 s. **The
slowest call measured is 73 times inside the 60 s threshold.**

Model load, which the backtester pays once per process, is 1.900 to 2.145 s on CPU
(`cpu_load_s` and `checkpoint.warm_construct_s`) and 2.041 s and 4.924 s on MPS across the
two runs (`device.mps_run.load_s`).

Peak RSS for the whole run, one CPU forecaster plus one MPS forecaster at the end:
**4,249,731,072 bytes**, from `resource.getrusage(RUSAGE_SELF).ru_maxrss`, which is bytes
on Darwin. It reads 4,223,172,608 after the model loads and does not move through the
matrix or the probes: the checkpoint is the memory, and the calls are not. The remaining
26,558,464 bytes are the second forecaster on MPS.

### Timing noise, and one rehearsal that is not in these files

A rehearsal of this matrix ran the same 36 cells in canonical order with no warmup and
reported medians falling by roughly a factor of four between its first third and its
last, which reads off the table as "step changes forecast far faster than random walks".
Its output was overwritten by the runs above and is therefore not cited as a measurement.
What is cited is the control that was built to test the reading, and it does not support
it:

| control | `out/results.json` | `out/results_canonical.json` |
|---|---|---|
| first half of the matrix, mean of cell medians | 0.3078 s | 0.3952 s |
| second half of the matrix, mean of cell medians | 0.3610 s | 0.4244 s |
| control cell before the matrix, median | 0.2724 s | 0.3599 s |
| control cell after the matrix, median | 0.2968 s | 0.3685 s |
| after / before | 1.090 | 1.024 |

The canonical run reproduces the rehearsal's exact arrangement and its two halves differ
by 7 percent, in the direction of getting slower. **Cell order does not explain the
rehearsal.** The
warmup and the shuffle stay in `run.py` because they make a per-cell median mean
something, not because they explained anything.

What the spread does mean for a caller: identical work on this machine varies by roughly
a factor of two (0.1812 s to 0.3225 s across the 12 identical warmup calls of
`out/results.json`), and the 216 matrix calls of the two runs span 0.1480 s to 0.7245 s
with a median of 0.3458 s. A single timing is not a cost model. Budget 0.35 s and treat
1 s as the worst seen.

### Quantiles

`return_quantiles=True` gives `(V, H, 9)` beside a `(V, H)` point forecast, the point
being quantile index 4. Every matrix call in both runs returned a quantile axis sorted at
every step (`quantile_order.steps_disordered` = 0 in all 72 cells).

That is uninformative on its own, because `sort_quantiles` defaults to True and sorts the
axis. Measured with the sort switched off, over 9 series-and-length combinations at
horizon 24 (`raw_quantiles` in both files):

**0 of 216 forecast steps are non-monotone across the 9 quantiles, in each run** (9
combinations x 24 steps). The head is ordered before anything sorts it. The adapter keeps
`sort_quantiles` at its default anyway: this is one cohort of synthetic series, not a
proof about the head.

### NaN, decision rule (c)

Context length 64, horizon 24, each NaN variant compared against the array a caller would
have had to build instead. Identical to the last decimal in both runs (`nan_probe`).

| the input | compared against | max abs difference |
|---|---|---|
| one interior NaN at index 30 | the same series with that point linearly interpolated | **0.0** |
| one leading NaN at index 0 | the series with the first point dropped (63 points) | **0.0** |
| one leading NaN at index 0 | the series with the first point back-filled from index 1 | 0.15572166442871094 |
| one trailing NaN at index 63 | the series with the last point forward-filled | **0.0** |
| one trailing NaN at index 63 | the series with the last point linearly extrapolated | 1.5816993713378906 |
| a 2-target context whose second row is all NaN | the same context with that row zeroed | **0.0** |

Every one of those calls returned a finite forecast and raised nothing.

Three of these are exact zeros, not small numbers: the forecaster is doing precisely the
substitution named, and the arithmetic is identical.

**One line of design 6.12 is wrong.** It says the forecaster "trims leading all-NaN
columns, interpolates interior and trailing NaN". Interior, yes, to the last bit. Trailing,
no: `linear_interpolation` calls `np.interp`, which clamps outside the sample range, so a
trailing NaN is FORWARD-FILLED. The two rows above separate those readings by 1.58 on a
series whose values run to about 30, and the forward fill matches at 0.0.

### A five-point context

`contexts=[array of shape (1, 5)]`, horizon 8. **No error.** Forecast `(1, 8)`, quantiles
`(1, 8, 9)`, all finite, 0.2763 s (`short_context`). Five points is below one 32-point
input patch: the forecaster left-pads to 32 with a mask and forecasts. It enforces no
minimum and gives no signal that the context was shorter than a patch.

The context and its forecast are in `out/results.json` so the shape of the answer can be
looked at: context `[-0.489, -0.493, 0.241, -1.188, -2.202]`, forecast beginning
`[-2.029, -1.745, -1.660, ...]`.

### CPU against MPS, decision rule (d)

Same 64-point context, horizon 64, calls interleaved one CPU then one MPS so the
comparison is not charged for whatever the machine was doing during a block.

| measure | `out/results.json` | `out/results_canonical.json` |
|---|---|---|
| `torch.backends.mps.is_available()` | True | True |
| cpu median, n=3 | 0.3136 s | 0.3526 s |
| mps median, n=3 | 0.1559 s | 0.1868 s |
| cpu / mps | **2.012** | **1.888** |
| forecast, max absolute difference | 2.288818359375e-05 | same |
| forecast, max relative difference per point | **9.072e-07** | same |

### The 32-variate cap

Design 6.12 says the forecaster does not enforce it. It does not, and it is worse than
that: it produces a full, plausibly shaped answer.

| probe | result | shapes |
|---|---|---|
| 33 target variates in one context | **no error**, 0.7849 s | forecast (33, 24), quantiles (33, 24, 9) |
| 1 target + 31 past-only + 1 past-future = 33 | **no error**, 0.8141 s | forecast (1, 24), quantiles (1, 24, 9) |

Nothing warns, nothing truncates visibly, and the output is the shape a caller asked for.
The adapter's assertion is the only thing between a 33-variate call and a number nobody
can defend.

### Past-future covariates and `padding_mode`

Design 6.12 says past-future covariates "must span context + 64 unless
`padding_mode="edge"`". Three calls with context 64 and horizon 24:

| probe | covariate length | result |
|---|---|---|
| `padding_mode="none"` | 88 (context + H) | **no error**, quantiles (1, 24, 9), 0.2846 s |
| `padding_mode="none"` | 128 (context + 64) | no error, quantiles (1, 24, 9), 0.3225 s |
| `padding_mode="edge"` | 88 (context + H) | no error, quantiles (1, 24, 9), 0.2771 s |

**The first row is not a "must".** `decode` computes `horizon = past_future.shape[-1] -
context`, so a covariate of length context + H silently makes the model generate H steps
instead of 64 and slice nothing.

**And the two produce different forecasts.** The same covariate under
`padding_mode="none"` and `padding_mode="edge"` differs by **1.4114360809326172** at its
worst point, on a series whose values run to about 30. Identical in both runs.
`padding_mode` is not plumbing: it is part of the answer.

### Determinism

Every value that is not a wall time is bit-identical across the two runs, which were
separate processes in different cell orders: the NaN differences to their last decimal,
the padding difference, the short-context forecast, the CPU-MPS differences. The model is
reproducible on this machine.

## What it means

**(a) Installation: resolved and installed on Python 3.12.** No resolver error, so the
fallback branch has nothing to report. torch 2.13.0 and numpy 2.5.2 come with it, and both
stay out of the default environment: `import torch` fails there, and the 33 integration
tests pass without it.

**(b) Per-call cost: per-window calls are affordable, and the number for the wave 2
backtest brief is 0.35 s.** Median 0.3458 s over the 216 calls of the two runs, worst
single call 0.8141 s, threshold 60 s. A 50-origin backtest is about 18 seconds of model
time plus one 2 s load. The backtester may still batch, because design 6.12 already tells
it to sort a run's windows by length into one `predict_batch`, but it does not have to in
order to be affordable, and that changes what W2 has to build first.

**(c) NaN: internal interpolation confirmed, at 0.0 rather than at a tolerance.** An
interior NaN is exactly a linear interpolation, a leading NaN is exactly a trim, an
all-NaN row is exactly a row of zeros, and a trailing NaN is exactly a forward fill.
Nothing raises and nothing is reported. This is the strongest possible case for the
adapter's `np.isfinite` assertion: a gap that reaches the model comes back as a number
with no marking on it, and Telltale's rule is that unknown stays unknown. The zero-fill of
an all-NaN row is the same defect the invariants call out by name.

**(d) Device: MPS is allowed, and the adapter may use it.** 9.072e-07 relative against a
1e-3 rule, and 1.9x to 2.0x faster on the case the rule names. The pin in design 6.12
("device="cpu" pinned unless E03 shows MPS works") is released for this machine.

Two caveats travel with (d). The speed factor is 1.888x and 2.012x across two
measurements of three calls each, not a stable constant, and the MPS load cost is
unstable too: 2.041 s in one run against 4.924 s in the other, where CPU is 1.900 to
2.145 s. A process making a handful of calls can be slower overall on MPS. And this is
one machine: the adapter should take the device as configuration with `cpu` as the
default, record the device in the ForecastRun, and let MPS be chosen rather than
assumed.

## What we rejected

**That "step changes forecast faster than random walks".** The first rehearsal's table
said exactly that, and the shape of the claim was attractive: a step is a simpler series.
It is an artefact of when each cell ran. Shuffling the cell order and discarding 12 warmup
calls removes it, and the canonical control that recreates the original arrangement does
not reproduce it. Series shape is not a resolvable cost factor at this
sample size, and the write-up says so instead.

**That the checkpoint is 2.6 GB.** The obvious directory sum says so, and it is the
symlink counted twice. 1,322,900,328 bytes is one blob and `du -sh` agrees.

**That a past-future covariate of the wrong length is an error.** Design 6.12 says
covariates must span context + 64 without edge padding, which reads as a precondition.
Passing context + H runs, returns the right shape, and returns different numbers. The
dangerous version of this finding is the one where the adapter drops
`padding_mode="edge"` as redundant because a test still passes.

**That `sort_quantiles=True` proves the quantile head is monotone.** It proves the output
is sorted. Turning the sort off is what asks the question, and the answer on these series
is that the head is already ordered at every one of 216 steps.

**That the ru_maxrss unit could be assumed.** It is bytes on Darwin and kibibytes on
Linux, a factor of 1024 between two readings of the same field. `run.py` records which
platform it was on beside the number.

## What downstream may now say

The forecast adapter may be built against TimesFM 3.0.0 on Python 3.12 with torch 2.13.0,
loading `google/timesfm-3.0-pytorch` (1.32 GB, about 30 s on first fetch, about 2 s per
process afterwards) and recording `timesfm-non-commercial-license-v1.0` in every
ForecastRun, which is a research licence and not a production one. Per-call cost is a
**derived** number, median 0.3458 s over 216 calls of one cohort (synthetic series, three
shapes, contexts 16 to 512, horizons 8 and 24, up to 3 variates, one machine, `cpu`, 4
torch threads), and a forecast made with it is **predictive** and never causal. The cohort
does not cover contexts beyond 512, batches of more than one series per call, horizons
beyond 64, real Telltale series, or any machine but this one, so a cost quoted for a
backtest of a real run is an estimate until that run is timed. Four behaviours are now
measured rather than assumed and the adapter must guard all of them, because none of them
raises: NaN of any position is silently substituted (interior interpolated, leading
trimmed, trailing forward-filled, an all-NaN row zeroed), a context shorter than one
32-point patch is silently padded, a 33rd variate is silently accepted, and
`padding_mode="none"` on a covariate of length context + H silently changes the forecast
rather than refusing it. `device` may be `mps` on this machine, at 9.072e-07 relative
agreement with `cpu` and about twice the speed, but the default stays `cpu` and the
device goes in the ForecastRun, because a device that changes a number is part of the
provenance.
