# E04: what does recording cost the session it records, and does it still fail open when the receiver is overwhelmed?

Why this matters (30 seconds): Telltale's whole claim is that it changes nothing about
the session it records. The only number behind that claim today is E01's single pair,
S2 against S6, +0.913 s on a 9 second session, and one pair cannot tell an overhead from
a slow morning. Everything downstream that compares a recorded session to an unrecorded
one, and every owner deciding whether to leave the recorder on, is standing on that one
number. The second half is worse: nothing has ever measured what the receiver does when
it cannot keep up. Design 6.5 says a full queue drops droppable records and makes
everything else wait at most 250 ms, and spec 5.2 says every POST is answered 200
whatever happened. Both were read, not run.

## Decision rule, written before the run

Copied verbatim from the brief for W1-E04, which was written before any session started.

(1) Overhead. delta_i = wall_on_i - wall_off_i over 5 interleaved pairs, where wall is
the whole process wall time as the user experiences it (perf_counter around the
subprocess: the launcher process for ON, the claude process for OFF), and separately
delta_api_i from the stream result's duration_ms (the child's own clock). Report the
median and scaled MAD of each delta and the scaled MAD of the OFF arm's wall. If the
median delta exceeds the OFF arm's scaled MAD, the gate report says "the overhead
exceeds run-to-run noise at n = 5" and quotes both numbers; otherwise "not resolved at
n = 5". No threshold is invented: the number is reported, not judged.
(2) Fail-open under load. During a fake-agent capture whose receiver is flooded by a load
generator, every load POST is answered 200 within 300 ms (record the max), the fake
agent's exit code and stdout byte count equal the unloaded run's, and the stream
observations stored for the flooded capture equal the unloaded count, or the difference
is accounted for by /healthz drop counts and diagnostics of kind dropped, listed by
surface. Any POST over 300 ms or unanswered, or a changed exit code or stdout, is a
fail-open violation and the headline of the write-up.
(3) Completeness. In the ON arm, every capture's telltale.capture_ended records
non-zero surfaces_received for hook, otel_logs, otel_metrics and stream; a zero names
the surface and the session in the write-up.

## What we did

Ten `claude -p --model sonnet` sessions, five ON and five OFF, interleaved ON, OFF, ON,
OFF, ..., on Claude Code 2.1.258, macOS 25.6.0 arm64, on 2026-09-02 between 10:07:58 and
10:09:44 UTC. Every session ran in its own fresh copy of `experiments/E01/fixture_repo`
with its own git history, made by E01's own `prepare_repo`. The prompt is E01's
`EXPLORE_PROMPT`, imported rather than retyped: "Explain how divide in pkg/calc.py
handles zero. Do not edit any file."

The runner is `experiments/E04/run.py`. Every number below comes from
`experiments/E04/out/results.json`, which is assembled from
`experiments/E04/out/pair<k>/<arm>.meta.json`, `experiments/E04/out/floor.json` and
`experiments/E04/out/load/results.json`. The raw stream and stderr files are under
`experiments/E04/out/` and are not committed.

The ON arm, per pair k:

```
uv run --project <repo root> telltale run --provider claude --level 1 \
  --task-id E04 --attempt <k> --experiment E04 -- \
  claude -p --model sonnet --permission-mode acceptEdits --max-turns 8 \
    --output-format stream-json --verbose \
    "Explain how divide in pkg/calc.py handles zero. Do not edit any file."
```

The OFF arm, per pair k, with the environment stripped as below:

```
claude -p --model sonnet --permission-mode acceptEdits --max-turns 8 \
  --output-format stream-json --verbose \
  "Explain how divide in pkg/calc.py handles zero. Do not edit any file."
```

`--project` is a deviation from the brief's `uv run telltale run` and it is forced:
`uv run` resolves its project from the current directory, every session runs inside a
copy of E01's fixture repository, and that copy carries a `pyproject.toml` of its own
(`e01-fixture`, no telltale dependency). A bare `uv run` from there resolves the wrong
project. `--project` pins it to this checkout and changes nothing else.

### The environment, and what was taken out of it

This experiment ran inside a `telltale run` capture of its own, so the orchestrator's
launcher had already put its capture variables into the environment every child would
inherit. A child that inherits them exports to the ORCHESTRATOR's receiver and is not
off. The OFF arm therefore removes, from the environment it hands the child, every name
beginning `OTEL_` and the name `CLAUDE_CODE_ENABLE_TELEMETRY`. Removed, never emptied:
`CLAUDE_CODE_ENABLE_TELEMETRY=1` with no endpoint still turns an exporter on.

The names actually removed, identical in all five OFF sessions, recorded in
`out/pair<k>/off.meta.json` as `env_removed`:

```
CLAUDE_CODE_ENABLE_TELEMETRY
```

That is the whole list. No `OTEL_` variable was present. This is a measurement and not
the expected answer: the orchestrator's launcher sets eight OTEL variables on the
`claude` process it starts, and none of them reached a subprocess of that process on
this machine. What did reach it: `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`,
`CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_BRIDGE_SESSION_ID`, `CLAUDE_CODE_CHILD_SESSION`,
`CLAUDE_CODE_EXECPATH`, `CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_CODE_MESSAGING_TOKEN`
and `CLAUDE_CODE_ENABLE_TELEMETRY`. Only the last is in the rule's list, and only the
last was removed. Both arms inherit the other eight equally.

Both arms also inherit the owner's global hooks from `~/.claude/settings.json`, which
Telltale never edits and never disables (AGENTS.md invariant 7). Five are declared:
`SessionStart` (`praxis nudge --format claude-code` and
`~/.claude/hooks/context_handoff_restore.sh`), `Stop` (`praxis reflect --session-end`),
`UserPromptSubmit` (`~/.claude/hooks/context_handoff.sh`), `PostToolUse` on
`Edit|Write|NotebookEdit` (`~/.claude/hooks/complexity_advisory.py`) and `PostCompact`
(`~/.claude/hooks/context_reset.sh`). They fire in BOTH arms and are part of both wall
times. They are not part of the delta, because they are the same on both sides, but
they are part of why a 9 second session is 9 seconds.

The ON arm's `telltale run` sets its own capture environment for its child, which is
the point of the arm. It is not stripped.

### The load arm, which spends no tokens

Two captures of the scripted agent in `tests/integration/fake_agent.py`, each in a
throwaway git repository holding `answer.txt` and `README.md`, one against a quiet
receiver and one against a receiver being flooded. The child is
`experiments/E04/child.py`, which writes the receiver endpoint into `endpoint.txt`,
waits 6 s, runs the scripted agent with `--seed 7`, and waits 16 s more. The generator
is `experiments/E04/load.py`: 4 threads, 20 s, starting 1 s into the capture, each
posting a 129,282 byte OTLP JSON batch of 100 synthetic `claude_code.api_request`
records to `/v1/logs` on one keep-alive connection, recording the status and the latency
of every POST.

The waits are what make it a comparison. The scripted agent finishes in well under a
second and the flood runs for 20 s, so without them the capture would be over before
the flood started. Both captures wait the same, so the only difference between them is
whether the generator ran.

## What it means

**Rule (1) takes the "exceeds" branch, and design 6.12 says that branch is not yet
safe to lean on.** The median delta is 0.986 s and the OFF arm's scaled MAD is 0.7265 s,
so by the rule as written the gate report says: the overhead exceeds run-to-run noise at
n = 5, 0.986 s against 0.7265 s. The child's own clock agrees on direction and size:
the median delta_api is 891 ms, so most of the wall difference happens inside the child
rather than in the wrapper around it.

The rule was written before the numbers existed and it is followed here as written. It
should also be read against design 6.12's own yardstick, which is stricter. The minimal
detectable median difference is `MDD = 2.8 s sqrt(2 / n)`, with `s` the scaled MAD. With
s = 0.7265 s and n = 5, MDD = 1.2865 s. The measured median delta, 0.986 s, is smaller
than that. So the honest statement is: a difference of this size is not resolvable at
five pairs, and the rule's comparison against the raw MAD is a weaker test than the
design's own. `N_needed = ceil(2 (2.8 s / delta)^2)` gives n = 9 pairs per arm for
delta = 0.986 s, or n = 21 for the matched-turn median of 0.642 s.

**Rule (2) passes on every clause, and one clause was never exercised.** Every one of
1555 POSTs was answered 200; the slowest took 186 ms against the 300 ms bound; the
scripted agent exited 0 in both captures and wrote the same 5636 bytes; and the flooded
capture stored the same 17 stream observations as the quiet one. No fail-open violation.

The clause that was never exercised is the drop path. The queue is 10,000 deep and it
held 580 at the moment the flood ended, with 501 more in flight, and `drops_total` was
0. The store kept up: 155,500 observations accepted in 20 s, about 7,800 a second. So
this run measured that the receiver answers fast while it is NOT saturated. What
happens at the 250 ms wait, and whether a droppable batch is really dropped rather than
lost silently, is still unmeasured. That needs a load that outruns the writer, which
means either many more threads or a slower disk, and it is the obvious next experiment.

**Rule (3) passes with no zero.** All four surfaces delivered in all five ON captures.

## What we rejected

**That the +0.913 s E01 saw is a stable overhead number.** It is inside the spread
measured here. The five deltas run from -0.043 s to 6.104 s, and pair 4 is negative: the
recorded session was 43 ms FASTER than the unrecorded one. A single pair of sessions
cannot separate the recorder from the session.

**That pair 1 should be dropped.** It is the largest delta by a factor of three and its
OFF session did visibly less work: 2 turns and 67,151 tokens where the other nine
sessions all took 3 turns and about 101,000. Dropping it would improve the answer by
choosing which data to keep after seeing it. It stays in the rule's numbers and it is
reported separately in the matched-turn row so a reader can see both.

**The brief's load-arm child, `bash -c 'echo ...; exec python fake_agent.py -p ...
--output-format stream-json --seed 7'`.** It was run once and the capture recorded, as
`argv_probe` in `out/load/results.json`: capture cap_01M1GSPCQ6J9H23PHHJCDJ17NP, exit 0,
`surfaces_received` EMPTY, 5 observations, all of them the launcher's own. The launcher
decides what to configure by scanning the child's argv
(`src/telltale/providers/claude_launch.py`): it tees stdout only when `--output-format`
and `stream-json` are separate tokens of that argv, and it inserts `--session-id` only
when it sees `-p`. Flags inside a `bash -c` string are not tokens of the child's argv,
so that child configured no stream surface and rule (2) would have had no stream
observations to compare. `experiments/E04/child.py` puts the same flags where the
launcher can see them.

**The first flooded capture, and its 2-byte stdout difference.** The first run of the
load arm gave 5639 bytes unloaded against 5637 loaded, recorded in
`out/load-unequal-names.json`. The cause was the harness: the scripted agent prints its
working directory in its `system` init line, and the two repository copies were named
`unloaded` and `loaded`, which differ by exactly two characters. The directories were
renamed to `quiet` and `flood` and the arm was re-run, giving 5636 both. The first
capture is superseded and its rows are still in the database.

## How sure we are

| claim | how sure |
|---|---|
| The median wall delta over 5 pairs is 0.986 s and the OFF arm's scaled MAD is 0.7265 s | measured, `out/results.json`, n = 5 |
| Most of the delta is inside the child: median delta_api 891 ms | measured, from each child's own `duration_ms`, n = 5 |
| A difference of 0.986 s is not resolvable at n = 5; MDD is 1.2865 s | measured input, arithmetic from design 6.12's formula |
| 9 pairs per arm would resolve 0.986 s, 21 would resolve 0.642 s | reasoned, from the same formula, assuming the spread stays 0.7265 s |

## What downstream may now say

A report may say, as a `derived` claim over the cohort "10 `claude -p --model sonnet`
explore-only sessions of one prompt on Claude Code 2.1.258, macOS 25.6.0 arm64,
2026-09-02", that the median wall-time difference between a recorded and an unrecorded
session was 0.986 s on a 9.584 s median unrecorded session, with the OFF arm's scaled
MAD at 0.7265 s and the minimal detectable difference at this n at 1.2865 s, and that
the difference is therefore not resolved at n = 5. It may not say the overhead IS
0.986 s, it may not present a percentage without both spreads beside it, and it may not
carry the word impact. A `comparative` claim about capture overhead needs n = 9 at this
spread and does not exist yet. Coverage is complete on all five ON captures, four
surfaces of four, so nothing here is caveated by a missing surface. The fail-open
result is `derived` and its cohort is one flooded capture of a scripted agent at
7,800 observations a second; it says nothing about a receiver whose queue is full,
because this one's never was.
