# E06: does one launch flag move a measure further than the run-to-run floor?

Why this matters (30 seconds): E05 measured how far a number moves when nothing varies
except the run. H3 asks the next question, and it is the one every later claim about an
environment rests on: when we change one thing on the command line, does anything move
further than that floor? If nothing does, then a fingerprint change is not a changepoint
and a series may be modelled straight through it. If something does, that measure has to
treat the fingerprint as a break, and the report has to say which measure and how far.

**The answer, in one line: three of the 28 measures moved further than five sessions per
arm can separate from run-to-run variation, four moved and did not clear it, twenty did
not move at all, and one has no value in any session.** All ten sessions passed
acceptance. The three that moved are `output_tokens`, `cache_read_tokens` and
`stable_state_tokens`, all of them counts of the model's own consumption; every measure
counted from what the agent DID (files read, files changed, edits, searches, test runs,
turns, tool calls) is identical in all ten sessions.

The one thing that separated the two arms and is not in the vector: **all five low-effort
sessions wrote the byte-identical patch, and the five high-effort ones wrote three
different patches.** That is in the repository snapshot, not in a measure.

## Decision rule, written before the run

Copied verbatim from the brief for W2-E06, which was written before any session started,
and stored in `experiments/E06/out/decision.json` under `rule` so the two cannot drift.

> Per measure: the factor has a material environment effect iff |HL shift| > MDD, where
> MDD = 2.8 s sqrt(2 / n) with s the pooled scaled MAD the runner prints; otherwise "not
> resolved at n = 5", never "no effect". A measure whose s is 0 in both arms and whose
> values are identical across arms reads "no variation and no shift at n = 5". The
> per-arm demotion rule of E05 applies to each arm's own floors. A material effect makes
> the effort fingerprint a changepoint for that measure (design 6.12); the write-up says
> which measures, and says that a changepoint is a statement about this task on this day.

E05's per-arm rule, which the last sentence but two imports, is also verbatim from its
own brief:

> Per measure over the five captures: n, median, s (scaled MAD), MDD = 2.8 s sqrt(2 / n),
> demoted from repository comparison while MDD > 0.25 median,
> N_needed = ceil(2 (2.8 s / (0.25 median))^2).

The pre-registered constants of design 6.12 travel with every table:
`2.8 = z_{0.975} + z_{0.80}`, relative resolution `0.25`, scaled MAD `1.4826 MAD`,
n = 5 per arm, exact test computed up to 20 per arm.

## What it means

**Three measures take the material branch of the rule, and the effort fingerprint is a
changepoint for those three and for no others:**
`context_token_burden.cache_read_tokens`, `context_token_burden.output_tokens` and
`stable_state_work.stable_state_tokens`. All three are counts of tokens. A series of any
of them that crosses a change of `--effort` has a break at that row, and design 6.12's
backtester excludes windows that straddle it.

**A changepoint here is a statement about this task on this day.** It is one fix-the-test
task with essentially one solution shape, one model, one repository, ten sessions inside
four minutes. The finding is that the effort flag reaches the token counters far enough
to clear five-against-five at this size, not that it does so on every task or that the
size of the shift transfers anywhere.

**Four measures moved and did not clear the floor, and that is not the same as not
moving.** `duration_ms` moved 646 ms against an MDD of 1463 ms; the high arm's own spread
is 1152 ms, which is six times the low arm's 196 ms, and it is that spread rather than the
shift that swallows the difference. `final_diff_lines` and `max_diff_lines` moved 4 lines
against an MDD of 5.6, and their `N_needed` is 621 per arm. The label on all four is a
statement about n = 5.

**Everything the agent DID is identical in all ten sessions.** One file read, one file
edited, one edit, two test runs, four tool calls, five turns, zero searches, zero
compactions, in the low arm and in the high arm alike. Whatever the effort flag changed,
it did not change the shape of the work on this task.

**The one place the work genuinely differed is not in the vector.** The low arm wrote one
patch five times; the high arm wrote three. `final_diff_lines` reports 2 against 6 and
does not say whether that is a different patch or the same patch measured differently, and
its verdict is "not resolved at n = 5". `diff_hash` on the `capture_end` snapshot is what
separates them, and it is the same gap E05 recorded and did not fix.

## What we rejected

**"Higher effort makes the model do more work."** Not on this task, and the measures say
so: identical tool calls, identical file reads, identical edits, identical test runs,
identical turn counts across all ten sessions. What moved is what the model spent inside
those five turns, not what it did with them.

**"The high arm is slower."** `duration_ms` moved 646 ms on an MDD of 1463 ms and a p of
0.690, and the high arm contains both the fastest session of the ten (10,724 ms) and the
slowest (13,218 ms). Cliff's delta is 0.20, which is the number saying the two arms
overlap heavily. This experiment cannot separate a duration shift of this size from
run-to-run variation at n = 5, and no reading of it as "slower" is available here.

**"`cache_read_tokens` moving 168 tokens on a median of 155,782 is a finding about the
model."** It is a finding about the measure at this n. The shift is 0.1 per cent of the
median. It clears the MDD only because the low arm's five values are byte-identical
(155,782 five times, scaled MAD 0), which pulls the pooled spread down to 58.7. Design
6.12's rule is what it is and this row takes the material branch, but the whole shift is
one twentieth of the between-arm demotion threshold, and the sensible reading is that the
low arm is degenerate rather than that 168 tokens matter.

**"Twenty measures with no variation and no shift means the flag does nothing to them."**
It means ten samples cannot see a difference. This task admits one solution shape: read
the file, guard the zero, run the tests. A task with more branches in it leaves room for
the counts to move, and nothing here measures that. The verdict string says "no variation
and no shift at n = 5" for that reason.

**"The two arms can be compared with E05's five sessions to make a three-way
comparison."** They cannot. E05r2 ran at a different base commit under a command with no
`--effort` flag at all, which is a third condition and a third fingerprint. Its numbers
are quoted in this file exactly once, as the observation that `01abbb17ef6b` is a patch it
also produced, and never in a table with these.

**"The effort flag did not reach the child, because effort is a Claude Code setting."** It
reached the fingerprint, which is built from the argv the owner wrote, and the two arms'
stored `telltale.environment` payloads differ in the `effort` field and in nothing else.
What no measurement here establishes is what the binary did with the value beyond that.
Claude Code 2.1.258 accepts low, medium, high, xhigh and max and WARNS on anything else
while running at the default, so a mistyped value is a silent third condition; both values
used here are in the accepted set.

## What downstream may now say

Comparative, between two stated conditions of one task: the difference between
`claude -p --model sonnet --effort low --permission-mode bypassPermissions --max-turns
40` and the same command with `--effort high`, on E01's fix-the-test prompt, content level
1, base commit `0ed533da22f1ea1a2c7c1c077f41a70ec680bfd0`, environments
`env_8a226fb2c88f52f6d9901f0e1727064db531979269ed59d9029829be197a2083` and
`env_1603028c029dc2060decf957e00a44bf8037d2c25989aa196ab4e4b471044097`, five captures
each, on 2026-09-02.

Within that cohort: `context_token_burden.cache_read_tokens`,
`context_token_burden.output_tokens` and `stable_state_work.stable_state_tokens` show a
material environment effect, so the effort fingerprint is a changepoint for those three
measures and a series of any of them may not be modelled straight through a change of
`--effort`. Every other measure in spec 13.7's vector is unresolved at n = 5 or did not
move, and neither reading endorses modelling straight through: "not resolved at n = 5" is
a statement about five samples per arm.

Nothing here is about another task, another model, another repository or another day, and
nothing here is a statement about which effort value is better at anything. The three
words ADR-014 refuses appear nowhere in this experiment's output, and design 6.12's label
vocabulary is two strings which this file uses and does not extend, plus the one narrowing
the pre-registered rule names.

Coverage caveats. `compactions.pre_compaction_tokens` has no value in any of the ten,
because no session compacted, and a sum over an empty set is null rather than 0.
`verification_cycles.failed_test_runs` and `fail_to_pass_cycles` are 0 in all ten although
the fixture starts with a genuinely failing test: every session piped pytest into `tail`,
so the shell's exit status is `tail`'s 0. That is E05's caveat unchanged, it applies
identically in both arms here, and it is a caveat on the measure rather than a defect in
the reducer.

## NEXT

Scaling to `N = min(20, N_needed)` is indicated for exactly one measure and it is cheap:
`context_token_burden.output_tokens` has `N_needed` 4 per arm between the arms, which is
below the 5 already run, and the three material rows have `N_needed` 1, 4 and 1. The rows
that a larger n could settle are `duration_ms` (`N_needed` 2) and
`stable_state_work.stable_state_total_ms` (`N_needed` 1), both of which are already at or
below the n that ran, so their unresolved label is not a sample-size problem that 20 fixes;
it is a shift smaller than the spread. `final_diff_lines` and `max_diff_lines` need 621 per
arm, which is past design 6.12's ceiling of 20, so the honest reading is that the diff-line
measures are not going to separate two efforts at any n this protocol pays for, and the
thing that does separate them is `diff_hash`, which is already recorded and is not a
measure. Whether to add one is an owner decision.

The other H3 factor design 6.12 names, the model, has not been run. That is a new
experiment id and a new spend.
