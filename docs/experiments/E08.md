# E08: on captured data, does anything the request clock can be forecast for survive its own chronology placebo?

Why this matters (30 seconds): E07 scored TimesFM-3 against four one-line baselines on
the sessions that built Telltale and labelled all 19 of its pairs "baseline sufficient".
It could not do more, because design 6.12's rule has a second half, the chronology
placebo, and `block_shuffle` did not exist until W3-T2. Two claims rest on running that
half. That the laboratory can label a real pair at all under the full rule, because a
rule whose second half has never run on real data is a rule nobody has tested. And that
the request clock of a coding-agent session carries the thing a time-series result is
read as being about: order. If it does not, every forecast this system could offer about
a session is a statement about the LEVEL of a column, and the report has to say so.

## Decision rule, written before the run

Quoted from design 6.12 (`docs/design/01-design.md`), which was written before
`experiments/E08/run.py` existed and before any pair had been scored.

> **Chronology placebo.** `block_shuffle(rows, B, seed)`: cut the context into
> consecutive blocks of B whole rows, permute the blocks, concatenate. Whole rows move
> together, so the multiset of rows and the contemporaneous covariate-target relations
> are preserved exactly; recency and dependence at lags above B are destroyed. Second
> control: B = 1 (destroys dependence at every lag). Only the context is shuffled;
> origin, test rows and actuals stay true, so every placebo window is paired with its
> true-order twin. R = 5 seeds; median and range reported. Baselines also run on
> shuffled contexts: persistence must get worse, otherwise the placebo is broken and the
> run is invalid.
>
> Decision per (target, clock, variant): E_M = mean MAE of the model in true order; E_B =
> min over baselines in true order; E_P = median over seeds of the model's mean MAE on
> shuffled contexts; W_MB = share of windows where the model beats the best baseline;
> W_MP = share of windows where the true-order model beats its placebo twin.
> - n_windows < k_min: not assessable, no label.
> - baseline sufficient: `E_M > (1 - delta) E_B` or `W_MB < w`.
> - temporal evolution: not baseline sufficient, and `E_M <= (1 - delta) E_P` and
>   `W_MP >= w`, and both inequalities hold separately in each half of the origin range
>   (spec 15.7 anti-cherry-pick clause).
> - conditional prediction: otherwise. For a covariate-free variant the report says
>   "level prediction: the gain is distributional".

## What we did

Every command ran against a copy of the owner's store, never the store itself. The
runner takes a `.backup` snapshot of `$TELLTALE_HOME/telltale.db` into
`experiments/E08/out/home/telltale.db`, points TELLTALE_HOME at the copy, and refuses to
run if that path then resolves to `~/.telltale`.

```
uv run --extra forecast python experiments/E08/run.py --stage copy
uv run --extra forecast python experiments/E08/run.py --stage survey
uv run --extra forecast python experiments/E08/run.py --stage pairs --capture <ID>
uv run --extra forecast python experiments/E08/run.py --stage pooled
uv run --extra forecast python experiments/E08/run.py --stage lineage

uv run --extra forecast python experiments/E08/aggregate.py
```

The last two lines answer a question the rule leaves open. Design 6.12's placebo is the
block shuffle, and B = 1 is a second control that the reading guide says is reported and
is not part of the rule, but `placebo.sentinel` counts all ten runs. Counting the five
block runs alone changes nothing: no row reaches 5 of 5, and the most any row reaches is
4.

Not one of the 38 rows cleared the validity check design 6.12 states as a precondition
for any label, so not one label was written. Shuffling the context makes persistence
BETTER, by 18 percent in the median.

## What it means

**Every one of the 38 rows takes the first branch of design 6.12's rule: not assessable,
because the control failed.** The rule's own precondition is that the placebo made
persistence worse; on this data it made persistence better in 8 of 10 runs in the median
pair. Design 6.12 names the two readings of that outcome: "either the shuffle did not
reach the forecasters, or the series carries no recency at all". The first was ruled out
by measurement (below); the second is what the data says.

The reason is a property of the request clock rather than of the laboratory.
`output_tokens` alternates between short tool-call turns and long text turns, so the step
from one request to the next is LARGER than the distance between two requests picked at
random: on the pilot capture the mean distance from `y_{o-1}` to the actuals is
932.343949044586 tokens, and from a uniformly chosen earlier row of the same context it
is 784.4585987261147 tokens (median over 5 seeds), a ratio of 0.8413832679774284. The
lag-1 autocorrelation of the column has median 0.0592 across the 36 pairs. A shuffle that destroys recency therefore helps the one
baseline whose whole method is recency, and design 6.12 refuses to label a run whose
control behaves that way.

What that costs, precisely: the laboratory cannot say anything about temporal evolution
or conditional prediction on this data, and it also cannot repeat E07's "baseline
sufficient". Reading the same 36 stored true-order runs through E07's half-rule gives 35
"baseline sufficient" and 1 "not baseline sufficient at this n, placebo pending"
(`out/aggregates.json`, key `e07_baseline_only_labels`), so E07's headline reproduces
exactly. The full rule withholds it, because a run whose control controlled for nothing
licenses nothing, including the comfortable conclusion.

On the lineage clocks the answer is a count rather than a failure. The attempt clock has
29 rows and no registered target; the change clock has 23 rows, of which the window
formula allows 7 origins at H = 1 and 1 at H = 4, against k_min 20. Twenty windows would
need 37 changes at H = 1 and 96 at H = 4. Nothing about that is a defect to fix: it is
one repository's lineage being younger than the pre-registered floor.

## What we rejected

**That the placebo is broken.** This is the reading the STOP rule in this task's brief
exists for, and it was checked before anything else was written.

- The true-order run was not shuffled. Persistence MAE over the pilot pair's 157 retained
  origins, computed by hand from the series rows as `mean |y_o - y_{o-1}|`, is
  932.343949044586. The stored true-order run's persistence `mae_mean` is
  932.343949044586.
- Only the context moved. Every placebo window has the same `origin`, the same `actual`
  and the same `last_context` (`y_{o-1}` as recorded) as its true-order twin, window for
  window across all 157.
- The shuffle did reach the forecasters. The persistence POINT forecasts differ between
  the true run and the placebo run, which is only possible if the last row of the context
  changed.
- The forecasters see a permuted context and not a permuted history: `block_shuffle`
  moves whole rows, so every row still carries the values it was measured with.

**That the model is beaten by the baselines, or beats them.** Both readings are available
in the table and neither is licensed. E_M is below E_B on 24 of the 38 rows and above it
on 14, and the median W_MB is 0.5398729710656316. Under the full rule none of that is a
label, because the run that produced it has no valid control.

**That a bigger n would settle it.** The pooled H = 1 row has 1947 windows, 12 times
k_min, and its placebo is invalid in the same way (3 of 10 worse). This is not a
resolution problem.

**That `rolling_median` is the interesting winner.** It is the best baseline on 37 of the
38 rows, which reads as a finding until the placebo says the window's ORDER carries
nothing: a median of the last 8 values is then simply a robust estimate of a level, which
is the thing there is to estimate.

## What downstream may now say

On the request clock of this cohort (29 Claude Code launcher captures of the Telltale
build, 36 (capture, target, horizon) pairs on `output_tokens` plus 2 pooled rows, 2278
windows, TimesFM-3 on cpu against four baselines and a stub), the forecasting laboratory
may say exactly this and no more: **not assessable**. The chronology placebo of design
6.12 did not make persistence worse on any of the 38 rows, so no run met the
precondition the rule sets for a label, and the claim class of every number in this
experiment stays `derived` for the metrics and `predictive` for the forecasts, with no
label attached to either. Nobody may say that TimesFM-3 beat or did not beat the
baselines here, that the request clock evolves, or that a forecast of `output_tokens` in
a Claude Code session is supported by this evidence. What may be said, and is measured
rather than inferred, is that `output_tokens` on this clock carries almost no lag-1
structure (median autocorrelation 0.0592 over 36 pairs), which is a statement about the
column and about this cohort only.
