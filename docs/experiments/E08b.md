# E08b: does the true-order comparison alone earn "baseline sufficient" when the chronology control failed?

Why this matters (30 seconds): E08 ran design 6.12's chronology placebo on 38 real pairs
and the control failed on every one of them. Under the rule as W3-T2 implemented it, a
failed control withheld every label, so the laboratory could not repeat even E07's
finding that TimesFM-3 does not beat a rolling median. The owner approved an amendment on
2026-09-02. This experiment is the amendment applied: the placebo gates the two labels
that read the placebo, and the baseline comparison, which reads no placebo, stands.

Nothing was re-run. No model, no shuffle, no session, no token. E08 stored every term the
decision rule reads, so the only thing that moved between E08 and E08b is the rule.

## Decision rule, written before the run

The amendment was committed as `a351cac6030ab415bc83cdc0082372f70a3bf7e6`
("W3-E08b pre-register the amendment") before `experiments/E08b/run.py` existed and before
any row had been re-labelled. `out/summary.json` records that hash under `rule_commit`,
read from `git log -1 -- src/telltale/forecast/decide.py` at run time rather than typed,
so the order is in the artefact and not only in the prose.

Quoted from `docs/design/01-design.md`, "Amendments from wave 3", entry
"6.12 (W3-E08b, pre-registered before the re-labelling, owner-approved 2026-09-02)":

> The placebo validity check (persistence must be worse under every placebo run)
> gates the two labels that read the placebo, temporal evolution and conditional
> prediction. It does not gate "baseline sufficient", which is a paired comparison of
> the model against the best baseline on the same true-order windows and reads no
> placebo. An invalid placebo therefore yields: "baseline sufficient" when E_M >
> (1 - delta) E_B or W_MB < w, with the warning "placebo invalid: the positive labels
> were not assessable"; otherwise "not assessable: placebo invalid" with the
> inequalities shown. "Not assessable" for n_windows < k_min is unchanged and comes
> first. E08's 38 rows are re-labelled under this rule as E08b; E08's labels stand as
> the record of the rule before the amendment.

The constants are E08's and unchanged: `delta = 0.10`, `w = 0.60`, `k_min = 20`,
`c_min = 32`, `baseline_window = 8`, `threshold_rule = q80_first_c_min`, placebo block
`B = max(2, H)`, `R = 5` seeds plus the five `B = 1` controls. Every one of them is stored
on the rows this experiment reads and none is restated in its code.

### The expectation, stated before the run

From E08's own aggregate (`experiments/E08/out/aggregates.json`, key
`e07_baseline_only_labels`), which re-ran E07's half of the rule on E08's 36 per-capture
true-order runs: **35 baseline sufficient and 1 not**. The 2 pooled rows carry no entry
there, because that aggregate needs a stored `forecast_runs` row and a pooled row is not
one; they are labelled by the same two inequalities on their own stored terms, so the
prediction for the full 38 was 35 baseline sufficient plus whatever the pooled rows do,
and 1 refusal. A mismatch would be a finding about `relabel` and not something to tune.

## What we did

1. Committed the amendment: the design block above, and the code that makes it the one
   rule. `decide.decide` now takes a required `placebo_valid` and the validity check
   reaches a label through `decide._label` alone; `placebo.paired` hands it the sentinel's
   verdict instead of overriding the label afterwards. Two integration tests, one per
   branch of the amendment.
2. Added `decide.relabel(terms, placebo_valid=...)`: the same `_label`, applied to terms
   already computed. It reads each term off a stored decision BY NAME and raises on a
   missing one.
3. Ran `experiments/E08b/run.py`, which reads E08's 38 per-pair JSON files, hands each
   one's stored `decision` terms and stored `sentinel.valid` to `relabel`, and writes
   `out/summary.json`.

What was NOT run, and it matters: `uv run telltale forecast placebo` was not re-run, on
any pair. Nothing about the placebos changed, so re-running them would spend about 45
minutes of CPU to reproduce numbers that are already stored, and any drift in the result
would be drift in the environment rather than in the rule.

## What we measured

All 38 rows carried every term `relabel` reads (`n_rows_missing_a_term: 0`), so no row was
labelled "not assessable: term missing". All 38 placebos are invalid, exactly as E08
recorded them (`n_placebo_invalid: 38`).

```

labels_e08    {"not assessable": 38}
n_rows 38   n_pooled 2   n_placebo_invalid 38   n_rows_missing_a_term 0

```

The expectation held. 35 of the 36 per-capture pairs are baseline sufficient and 1 is not,
which is E08's `e07_baseline_only_labels` to the row; both pooled rows are baseline
sufficient on their own terms, giving 37 of 38.

Every one of the 37 carries the warning the amendment names, and it is the same string on
all of them, because all 38 controls failed:

```
notes: ["placebo invalid: the positive labels were not assessable"]
```

### Which clause did the work

| clause | rows where it holds, of 38 |
|---|---|
| `E_M > (1 - delta) E_B` | 37 |
| `W_MB < w` | 30 |
| both | 30 |
| `W_MB < w` alone | 0 |

The margin clause decides every label here: there is no row where the model cleared the
margin and was refused on the share alone. The ratio `E_M / E_B` runs from 0.8634 to
1.1725 over the 38 rows, and `rolling_median` is the best baseline on 37 of them
(`persistence` on the one remaining row, which is the refusal).

This is the row E08's write-up already singled out as "the only pair where the crude rules
did NOT win", and it is the only row where the amendment changes nothing: it was not
assessable before and it is not assessable now, for a reason that is now stated as the
placebo rather than as everything at once. `W_MB` is exactly 0.60 against a threshold of
0.60, and a tie is not a win anywhere in this rule, so the share clause fails by the
smallest margin the rule can express.

## What it means

**The laboratory may now repeat, on real data and under the full rule, the sentence both
E07 and E08 measured: TimesFM-3 does not beat `rolling_median` on `output_tokens` per
request.** On 35 of 36 captures and on both pooled rows, with a control that failed and is
named as failed.

The amendment is narrow and its narrowness is the point. Every one of the 37 labels rests
on two numbers, E_M and W_MB, that are computed from the SAME true-order windows and never
touch a placebo run. Nothing that reads a placebo was licensed: no row is labelled
temporal evolution or conditional prediction, and the warning on every row says the two
positive labels were not assessable. The count of what the laboratory may claim about
order on this data is still zero, which is what E08 established and what E08b does not
touch.

What the re-labelling does not do is make the data better. All 38 controls failed for the
reason E08 measured, and the median row still has only 2 of 10 placebo runs coming out
worse. `output_tokens` on this cohort carries almost no recency (lag-1 autocorrelation
median 0.0592, E08's `out/aggregates.json`), and a target with no recency should not be a
forecasting target at all: that is a finding for the registry, not for the rule.

## What we rejected

**"Run the placebos again."** Nothing about them would change. The placebo definition, the
seeds, the generator and the block size are stored on every one of E08's rows, the shuffle
is `random.Random(seed).shuffle` over consecutive whole-row blocks, and E08 measured that
TimesFM-3 is deterministic in this environment across three repeats
(`experiments/E08/out/determinism.json`). Re-running would spend about 45 minutes of CPU
to arrive at the stored numbers, and any difference it did produce would be a difference
in the environment, which is a question about the machine and not about the rule. The
whole design of this experiment is that only the rule moved.

**"Drop the validity check."** The positive labels still need a control. Without the
placebo there is no way to tell temporal evolution from conditional prediction, and both
of them are claims about the ORDER of the past; a rule that dropped the check would hand
one of those labels to a run in which nothing about order had been tested. The amendment
narrows what the check gates and does not weaken the check: `placebo.sentinel` still
refuses on one seed out of ten, and `placebo.INVALID` still lands in the warnings of every
run of an invalid pair.

**"Re-label E08's stored rows in the database."** The re-labelling lives in
`experiments/E08b/out/summary.json` and E08's stored `forecast_runs` rows keep the label
they were given. An observation is immutable and a derived row is rebuildable, and E08's
labels are the record of the rule that was in force when they were written. A reader who
wants the amended label for a stored row runs the amended code.

**"Say the model is worse than the baselines."** It is not what "baseline sufficient"
licenses. E_M is BELOW E_B on 24 of the 38 rows and above it on 14; what the label says is
that the model did not beat the best baseline by the pre-registered margin, on this
target, at this horizon, on this cohort.

## What downstream may now say

On the request clock of this cohort (E08's 29 Claude Code launcher captures of the
Telltale build, of which 24 produced a scored pair: 36 (capture, target, horizon) pairs on
`output_tokens` over 2278 windows, plus 2 pooled rows over 1947 and 331 windows; TimesFM-3
on cpu against four baselines):

**The model does not beat `rolling_median` on `output_tokens` per request**, on 35 of the
36 captures and on both pooled rows. Claim class `predictive`, coverage `observed`.

With this caveat, which travels with the sentence: this target carries no recency. The
chronology control failed on all 38 rows, so the two labels that would license any claim
about the ORDER of a session were not assessable, and the one remaining pair (W2-T8 at
H = 4, 20 windows) is not assessable at all. Nobody may say that the request clock evolves,
that the model reads the sequence, that a longer session would forecast better, or that
`rolling_median` is a good forecaster: it is a robust estimate of a level, and a level is
what there is to estimate here.
