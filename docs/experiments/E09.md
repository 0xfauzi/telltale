# E09: can a fixed probe of this repository be answered by an agent, and how consistently?

Why this matters (30 seconds): H1 says repository structure changes how hard an agent
has to work. Every experiment before this one measured only effort, and spec 14.3 says
in as many words that effort alone is not a finding: "measure correctness of the probe
answer as well as work quantities. Cheap behaviour with a wrong answer is not an
improvement." E09 is the first run in this build that measures correctness. It is also
the calibration E10 needs: E10 asks whether a scoped refactor makes a question easier to
answer, and that comparison is meaningless against a question that is already answered
perfectly every time, or against one that nothing could answer. E09 finds out which
questions this repository actually is.

**The answer is in "What it means" below.** Six probes, three repetitions each, all 18
sessions captured with full coverage and none scored unknown. Three probes were answered
(median precision and median recall both 1.0), two were partially answered (median recall
1.0, median precision below it), one was not answered (median recall 0.667). The two
least legible probes, and so E10's targets, are **P5-identify-the-storage-contract** and
**P3-trace-show-to-store**.

Two things went wrong and are reported before the numbers rather than after them. Four
of the 21 sessions crossed the brief's 200,000-token stop bound, which was only visible
after the suite had run. And the privacy verification the brief specifies could not be
run in the form it specifies, for a reason that is a fact about the runner. Both are in
"What we rejected" and in `docs/log/W4-E09.md`.

## Decision rule, written before the run

Quoted verbatim from `briefs/W4-E09.md`, which was written before any session started.

> Pre-registered decision rule, written here before the run:
>
> - A probe is "answered" when the median precision and the median recall over its 3
>   repetitions are both 1.0; "partially answered" when the median recall is 1.0 and the
>   median precision is below 1.0; "not answered" otherwise; "not scored" when the runner
>   reports unknown on 2 or more repetitions (the result text could not be read).
> - A measure (the 22 of spec 13.7 plus the two scores) is "resolvable at n = 3" for a
>   probe when MDD <= 0.25 median (6.12's demotion rule); otherwise the report prints
>   N_needed and says "not resolved at n = 3", never "no difference".
> - Nothing in E09 compares probes to each other as better or worse repositories; the
>   probes are one repository under six questions, and the comparison E10 needs is
>   between commits, not between questions.

The pre-registered constants of design 6.12 travel with every table: `2.8 = z_{0.975} +
z_{0.80}`, relative resolution `0.25`, scaled MAD `1.4826 MAD`, `MDD = 2.8 s sqrt(2 / n)`
and `N_needed = ceil(2 (2.8 s / (0.25 median))^2)`, at n = 3 and `sqrt(2 / 3) = 0.816497`.

The answer keys are `experiments/E09/answer_keys.json`, written by the orchestrator
before any session ran and not edited by this task. The two spec files carry the same
keys; the one field this task changed in them is `base_sha`, re-pinned at dispatch, which
is what the brief instructs and what the runner checks the keys against.

## What we did

Six probes, three repetitions each, plus a three-repetition pilot of P1 run first and
reported separately. Every repetition is one headless Claude Code session on Claude Code
2.1.259, macOS 25.6.0 arm64, on 2026-09-03, in its own fresh detached worktree of this
repository, added and removed by the runner.

```
uv run telltale experiment probe experiments/E09/pilot.json --out experiments/E09/out
uv run telltale experiment probe experiments/E09/spec.json  --out experiments/E09/out
```

The argv of every session, verbatim from the spec files, with the probe's prompt
substituted for `{prompt}`. The launcher adds `--settings` and `--session-id` itself and
configures OTel through the child's environment:

```
claude -p --model sonnet --permission-mode bypassPermissions --max-turns 40 \
  --output-format stream-json --verbose "<the probe's prompt>"
```

Base commit `4c4c4484e397a6c5d5f6f8f8b4901771241de8ad`, which is `main` at dispatch. The
brief's trap says to re-pin `base_sha` in both spec files to `git rev-parse main` and to
check every key path exists there. Both spec files carried
`7d825221ce4fd94fe649fdc872efe66f0acdc1c7`, which is not `main`, so both were re-pinned.
`main` then moved once while the checks were running, from `e1f94c56` to `4c4c4484`, and
the difference between the two is one added file under `briefs/` and no source file, so
the later commit was taken and held for both runs rather than re-pinned again. All 12
key paths are in the tree at `4c4c4484` (470 tracked paths there) and all four key
symbols are in the files the keys name, each checked with `git ls-tree` and `git show`
before anything ran.

One environment fingerprint over all 21 sessions, the pilot's and the suite's:
`env_6b7fa5a673d7cb66ef38a40670fcfc031a02b7f2d6d833ae6fd5c69084f1ce34`. That is the
assertion spec 14.3 asks for, and the runner makes it over the whole suite rather than
per probe.

No acceptance command. A probe is read-only and the answer key is the acceptance
criterion; every prompt ends "then stop. Do not edit anything." No session changed a
file: `edit_turnover.unique_files_changed` is 0 in all 21.

Total spend: 3,701,121 tokens over the 21 scored sessions, 2.688383 USD, and 312,951 ms
of wall time inside the runner (313.0 s), against 5 minutes 12 seconds for the suite's
own invocation and 25.6 s for the pilot's. One further session, described under "What we
rejected", was spent on the privacy verification.

**The contamination check, because this repository carries its own answer keys.**
`experiments/E09/answer_keys.json`, `pilot.json`, `spec.json`, `briefs/W4-E09.md` and
`docs/gates/wave-4.md` are all tracked at `base_sha`, so every worktree the runner made
carried the answers to its own question. Whether any session found them is a fact in the
capture, not a thing to assume: `experiments/E09/store_facts.py` reads every `file_read`,
`file_edit` and command activity of all 21 captures out of the store and looks for
`answer_keys`, `experiments/E09`, `briefs/W4-E09` and `docs/gates`. None appears in any
of the 21. Every path any session read is under `src/telltale/`, and the full list is in
`experiments/E09/out/store_facts.json`.

## What we measured

Every number below is in `experiments/E09/out/`: the runner's own
`E09/probe.json` and `E09-pilot/probe.json`, and `store_facts.json`, which carries the
per-capture `total_cost_usd` and `capture_ms` that the runner's report does not.
`experiments/E09/check_numbers.py` reads them back out of this file and is run in VERIFY.

**How to check every number in this file.** `uv run python experiments/E09/check_numbers.py`
reads every number out of this prose and asks whether any number anywhere under
`experiments/E09/out/` matches it at the precision it was written to. Its output is
pasted in `docs/log/W4-E09.md`. What it leaves unmatched is five kinds of thing, none of
them a measurement of this run: section numbers of the spec and the design, the
pre-registered constants of design 6.12, the runtime and OS version strings, hexadecimal
runs inside commit shas, and the three numbers quoted from E05 beside the two counts
produced by `git ls-tree` and by `strings ... | grep -c`, which are measurements of
something else and are shown with the command that produced them.

`tokens` is `stable_state_work.stable_state_tokens`, the same measure E05 quoted, which
sums each model request's whole context and so counts a cached prefix once per request.
The four components are in the table below. `capture_ms` is the launcher's arrival clock
from `telltale.capture_started` to `telltale.capture_ended`; `wall_ms` is the runner's
`perf_counter` around the whole child; `duration_ms` in the stats tables is the agent's
own, from the stream result. They are three spans and nothing here adds them.

## What it means

**Three of six probes were answered, two partially, one not.** Under the rule, taking the
median precision and the median recall over each probe's three repetitions:

| P1-locate-evidence-writer | 1.000 | 1.000 | answered | named `src/telltale/store.py` and `replace_evidence`, nothing else, three times |
| P2-tests-covering-privacy | 1.000 | 1.000 | answered | named `tests/integration/test_privacy.py`, nothing else, three times |
| P6-model-stack-isolation | 1.000 | 1.000 | answered | named both paths and the hook name, nothing else, three times |
| P3-trace-show-to-store | 0.833 | 1.000 | partially answered | found all five files every time and added `src/telltale/cli_common.py` every time, plus `pyproject.toml` once |
| P5-identify-the-storage-contract | 0.600 | 1.000 | partially answered | found all three twice and two of three once, and added `src/telltale/allowlist_codex.py` and `src/telltale/commands.py` every time |

No probe is "not scored": the runner read a result message from all 21 sessions and
scored every one, so its `_answer` works against a real `claude -p`, which W4-T1 said it
had not verified.

**The two failure modes are different and the two numbers separate them, which is the
whole point of spec 14.3.** P3 and P5 fail on precision: they find everything and bring
extra files back. P4 fails on recall: it brings back nothing wrong and misses a third of
the key. An effort measure cannot tell those apart. P4's median session is 3 tool calls,
4 turns and 147,446 tokens; P5's is 5 tool calls, 6 turns and 192,028 tokens; the cheaper
one is the one that answered less.

**A wrong path here is not obviously a wrong answer, and the write-up says so rather than
hiding it in the ratio.** P3's extra file every time is `src/telltale/cli_common.py`, and
all three sessions read it: `telltale show` really does route through it, and the answer
key does not carry it. P5's two extra files are `src/telltale/allowlist_codex.py`, which
is the Codex half of the same allowlist the key names, and `src/telltale/commands.py`,
which normalizes a command before it is stored. Precision counts a named path that exists
in the repository and is not in the key as wrong by design, and that design is what makes
the denominator finite. What it measures on these two probes is the distance between the
key's reading of "which files decide this" and the agent's, and a reader who wants to
call the agent right and the key narrow may: the per-repetition `wrong_paths` are printed
above for exactly that.

**Precision here is an upper bound, and P4 is the probe where that bites.** W4-T1's UNSURE
says a wrongly named symbol is counted nowhere, so an answer that names the right file and
four functions that do not exist scores precision 1.0. P4's three answers score precision
1.000 and their recall is 0.667, and the reason is `_RULES`: two of the three sessions
named `classify` and did not name `_RULES`, which the key asks for. `matched_symbols` is
in the repetition table for every probe for that reason. What is NOT measured anywhere is
whether those two sessions named some other, wrong table instead of `_RULES`; if they did,
precision 1.000 does not know it.

**The measured cost of a probe on this repository, which the brief said to measure rather

of their six sessions; P3 costs more than twice one in its cheapest session and nearly
four times one in its dearest. The pilot,
which ran P1 only, measured the cheap end and cannot predict the expensive end, which is

## What we rejected

**"The pilot bounded the suite's cost."** It did not, and this is the one thing in E09
that went wrong on its own terms. The brief's stop rule is 200,000 tokens per session, and
the pilot's three P1 sessions came in at 70,825, 72,643 and 72,597, a third of it, so the
suite was started. Four of the suite's 18 sessions then crossed the bound: P3 at 648,183,
461,295 and 427,873 tokens, and P4 attempt 2 at 227,192. Nothing was over the 5-minute
bound (the longest session is 40,914 ms of wall, 40,704 ms of capture) and nothing was
over the pilot's own 15-minute total. The overrun was only visible after the fact, because
`telltale experiment probe` runs all 18 repetitions inside one invocation and writes its
report at the end, so there is no point during a suite at which a token count can stop it.
A pilot of one probe measures that probe: P1 is a one-grep question and P3 is a
sixteen-turn trace, and no amount of repeating P1 would have said so. A pilot that bounds
a suite has to run one repetition of every probe in it. That is a change to the brief's
protocol, not to the runner, and it is in NEXT.

**"The privacy check in VERIFY was run as specified."** It could not be. The brief asks
for a five-word phrase from one agent's final answer, "read from the runner's stdout, not
from any file", and grepped for in the database bytes. The runner's stdout does not carry
any agent's answer: `experiments._launch` runs the child under `capture_output=True`, so
`launch._tee`'s echo goes into the captured buffer that the scorer reads and never reaches
a terminal. W4-T1's own docstring describes the echo and is what the brief was written
from; the buffering is one line below it. So the check was run in the closest form that
proves the same thing and costs one session: one further `claude -p` under `telltale run`
directly, which does echo, with P1's prompt at the same `base_sha` in a detached worktree
that was removed afterwards. Its answer was 54 characters long, read in the terminal, and
never written to any file under this repository. It contains no five-word run of prose at
all, so the grep was done with the WHOLE answer instead of a phrase of it, which is the
stronger test:

```
$ strings ~/.telltale/telltale.db | grep -c -F -f <the whole 54-character answer>
0
$ strings ~/.telltale/telltale.db | grep -c -F ' <the answer's prose punctuation run> '
0
$ strings ~/.telltale/telltale.db | grep -c -F 'src/telltale/store.py'
754
$ strings ~/.telltale/telltale.db | grep -c -F 'precision:1.000'
30
$ strings ~/.telltale/telltale.db | grep -c -F 'probe:P3-trace-show-to-store'
6
```

The last three numbers are the control, and without them the first two would only prove
the file had been grepped badly. The paths are in the store because a Read tool_use
carries `file_path`; the scores are in the store as `external.outcome` categories; the
sentence around them is not there. That session is capture
`cap_01M1KBEEWP5MACT5A5MV8QPWSG` under task id `E09-verify`, experiment `E09-verify`, and
it is deliberately not in any table above: it is not one of the 21 scored sessions and it
must not enter their statistics.

**"P1 is a legible question, because every session answered it in one grep."** P1 may be
answered from `AGENTS.md` without reading any source at all. That file is read at session
start, it is in every worktree, and its fourth architecture invariant says "Every derived
number is an Evidence, and it is written through store.py". All six P1 sessions (three
pilot, three suite) made exactly one Bash call, and the normalized command of each names
`src/telltale/store.py` as a literal argument, so the file was known before the command
ran and the grep was for the function name. What P1 measures is the legibility of this
repository's instruction file, which is part of the repository and a fair thing to
measure, but it is not the legibility of `store.py`. E10 should not use P1.

**"The suite's numbers might be the answer keys leaking."** They are not, and this was
checked rather than assumed. Every worktree carried `experiments/E09/answer_keys.json`,
`spec.json`, `pilot.json`, `briefs/W4-E09.md` and `docs/gates/wave-4.md`, each of which
holds the answers. None of the 21 captures records a read of, or a command naming, any of
them (`experiments/E09/out/store_facts.json`, `paths_touched` and `commands`). The check
is not airtight: a `grep -r` whose pattern happened to match inside the key file would
show as a search with no file argument, and `command_norm` redacts the pattern. What it
rules out is a session that opened the key.

**"Something in the suite drifted, because the pilot's P1 and the suite's P1 are not the
same numbers."** They are the same to within the run-to-run spread of a two-turn session:
70,825 / 72,643 / 72,597 tokens in the pilot against 70,709 / 72,629 / 72,617 in the
suite, all six precision 1.000 and recall 1.000, all six one Bash call and two turns. The
two conditions have their own task ids and are never in one table, for the reason E05
gives, but nothing separates them.
