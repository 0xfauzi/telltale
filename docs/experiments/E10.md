# E10: does an AGENTS.md that names the key files change how the same two questions are answered, and what they cost?

Why this matters (30 seconds): H1 says repository structure changes how hard an agent has
to work, and spec 14.2 puts the INSTRUCTION surface inside "structure": the files an agent
is told to read before it reads any code. E09 measured six probes on this repository and
found the two least legible, `P3-trace-show-to-store` and `P5-identify-the-storage-contract`.
E10 asks the smallest version of the question that can be answered: take those two probes,
run them at two commits that differ in `AGENTS.md` and in nothing else, and measure what
moved. If nothing moves, the instruction surface is not a lever on this repository and the
forecasting lab should not carry it as one. If something moves, the size of the move at
n = 5 per arm is the first measured number anybody here has for it.

**The answer is in "What it means" below.** 20 sessions, all captured with full coverage
(4/4 surfaces), none scored unknown, and none crossed a stop bound. The effort measures
moved a long way and in one direction: on P5 the `after` arm answered with **zero tool
calls in all five repetitions** against a median of 7 in `before`, and spent 36,492 tokens
against 235,228 on the median session. Recall stayed at 1.000 everywhere. **The
pre-registered prediction about precision is FALSIFIED, and the reason is a measurement
artefact this experiment created**: in the `after` arm the answers name `AGENTS.md`
itself, which exists in the repository and is not in the answer key, so the scorer counts
it as a wrong path. That is reported first, under "What it means", rather than buried.

## Decision rule and prediction, written before the run

Quoted verbatim from `briefs/W4-E10.md`, which was written before any E10 session started.

> The prediction is written down BEFORE the run and is part of the decision file: the
> `after` arm's AGENTS.md names exactly the key files of both probes, so the prediction
> is precision 1.000 on both probes in every `after` repetition, recall unchanged at
> 1.000, and fewer tool calls (Read and Bash) than `before`. Whether that happened is
> the result; the label per measure comes from 6.12's rule at n = 5 per arm: "material
> environment effect" iff |HL shift| > MDD, else "not resolved at n", never "no effect".

The rule it points at, quoted verbatim from `docs/design/01-design.md` 6.12:

> H3 per factor: material environment effect iff `|HL shift| > MDD` (the fingerprint
> becomes a changepoint for that measure); otherwise "not resolved at n", never "no
> effect".

and, from the same paragraph, the two numbers the label is computed from:

> Minimal detectable median difference at the current n: `MDD = 2.8 s sqrt(2 / n)`
> (2.8 = z_{0.975} + z_{0.80}, the two-sample normal approximation at alpha 0.05 and
> power 0.80, with s the scaled MAD as a robust spread). Demotion: a measure is withheld
> from repository comparison while `MDD > 0.25 median`; the report prints
> `N_needed = ceil(2 (2.8 s / (0.25 median))^2)`.

The answer keys and the spec were written before any session too, and are in git:
`experiments/E10/answer_keys.json` and `experiments/E10/spec.json`.

## What we did

One command, foreground, once:

```
uv run telltale experiment intervention experiments/E10/spec.json --out experiments/E10/out
```

Two arms of the same two probes, five repetitions per arm, 20 sessions. Every session is
`claude -p --model sonnet --permission-mode bypassPermissions --max-turns 40
--output-format stream-json --verbose <prompt>`, byte-identical on both arms, in a fresh
detached worktree of this repository at that arm's commit, removed afterwards. The two
arms are:

| arm | commit | what it is |
|---|---|---|
| `before` | `46ce655a17fd4b5bac90732a3768fa5c151300d5` | this repository at the W4-E09 gate |
| `after` | `99ea05a3b7bbf7770732c71e7099491beb3cc46d` | the same tree with one commit on the branch `e10/instructions`, which adds a "Where things live" section to `AGENTS.md` naming exactly the key files of both probes and changes nothing else |

The whole run took 567.9 s of session wall (`before` 448.0 s, `after` 119.8 s) and cost
5,523,456 tokens of every kind. Raw output is `experiments/E10/out/` (gitignored):
`E10/intervention.json`, `E10-before/probe.json`, `E10-after/probe.json`, and `run.log`,
which is the terminal output every table below is pasted from.


Two checks, at the two moments each can be made. Before any session,
`git diff --name-only -z` between the two commits must name at least one path and every
path it names must be an instruction surface `env.py` hashes. It named `AGENTS.md` and
nothing else, which the reader can repeat:

```
$ git diff --name-only 46ce655a17fd4b5bac90732a3768fa5c151300d5 99ea05a3b7bbf7770732c71e7099491beb3cc46d
AGENTS.md
```

After the sessions, the two arms' environment fingerprint payloads must differ in
`instruction_hashes` and in no other field. They did, and the report names the file inside
that field, with each arm's digest and size: `AGENTS.md: before=sha256 714b4371bb8b,
6197 bytes, after=sha256 3919689a056a, 7164 bytes`.

Neither check is the other. The fingerprint carries no commit, so it cannot tell an
instruction rewrite from an instruction rewrite that also edited a module; the diff check
is what rules the second one out, and it runs before any token is spent.

## What it means

**The prediction was half right, and the half that failed says something about the
measurement rather than about the agent.** Recall came out exactly as predicted: 1.000 in
all ten `after` repetitions and in nine of ten `before` ones. Effort came out as predicted
and further: on both probes, every measure labelled "material environment effect" moved
DOWN, without exception, and the rows labelled "not resolved at n" are exactly the rows
whose HL shift is 0. Precision did not: the prediction was 1.000 in every `after`
repetition, and the measured values are 0.857 five times out of five on P3 and 1.000 four
times out of five on P5.

**The reason is one path, and it is `AGENTS.md`.** In all five `after` P3 repetitions and
one of five `after` P5 repetitions, the wrong path the scorer found is `AGENTS.md`. The
answer named the file that told it the answer. `AGENTS.md` exists in the repository, is
not in the answer key, and precision counts a named path that exists and is not in the key
as wrong by design, because that design is what makes the denominator finite (W4-T1). The
key was written before the run, when nobody had seen an answer from the `after` arm, and
it could not have anticipated a citation of the instruction file. This is E09's "a key can
be narrow" lesson arriving in a new form: the intervention itself created a path the key
does not carry, and the write-up says so rather than reporting `after` as less precise.

| P5 | `probe_score.precision` | 0 | 0 | 1 | 0 | 0 | not resolved at n |

P3's precision row is labelled material because MDD is 0, and MDD is 0 because the scaled
MAD is 0 in both arms: `before` is 1.000 four times and 0.857 once, `after` is 0.857 five
times, so over half of each arm's values are identical and design 6.12's formula returns
0. The runner warns about exactly this on the row. A label computed against a spread of
zero is a statement about the spread, and the substantive finding is the one above it:
the `after` arm's precision loss is one file name, the same file name every time, and it
is the instruction file.

**The effort finding is large, one-directional and separates the two probes.** Every row
labelled "material environment effect" on both probes has a negative shift, and on P3
Cliff's delta is -1 for eleven of them, which means every `after` session is below every
`before` session on that measure. The three that matter most:

| probe | measure | before median | after median | HL shift | Cliff's delta | exact p | MDD | N_needed | demoted | label |
|---|---|---|---|---|---|---|---|---|---|---|
| P3 | `tool_calls` | 12 | 7 | -5 | -1 | 0.008 | 4.151 | 16 | True | material environment effect |
| P3 | `context_token_burden.cache_read_tokens` | 453649 | 167002 | -316122 | -1 | 0.008 | 93563.566 | 8 | True | material environment effect |

P5 is the extreme case and it is not a matter of degree. In `after`, all five P5 sessions
made ZERO tool calls, took one turn each, read no file and ran no command, and still
named every file the key asks for: recall is 1.000 in all five and precision is 1.000 in
four. `num_turns` is 1,1,1,1,1 against 2,7,8,8,9, `unique_files_read` is 0,0,0,0,0
against 2,2,3,3,5, and the token total is 36,492 against a median of 235,228. P3 kept
working, but the work changed shape: the `after` sessions ran 4 to 6 shell commands,
almost all of them greps over files `AGENTS.md` names and no others, and their
`unique_files_read` is 1,1,1,2,2 against 0,3,3,4,4 in `before`, which ran 7 to 10
commands. The instruction file did not make P3 free; it turned discovery into
confirmation.

**Demotion, per design 6.12.** Of the rows with a label, the ones marked `demoted` are
those whose MDD is still above a quarter of the pooled median at n = 5, and they are
withheld from repository comparison until n reaches `N_needed`: on P3 that is 8 for
`cache_read_tokens`, 13 for `num_turns`, 16 for `tool_calls`, 69 for `unique_files_read`;
on P5, 31 for `tool_calls`, 37 for `duration_ms`, 45 for `fresh_input_tokens`, 123 for
`num_turns`, 276 for `search_ops` and `unique_files_read`. Design 6.12 caps scaling at
`N = min(20, N_needed)`, so several of these are not reachable within the protocol, and
that is a fact about the protocol rather than about this repository.

## What we rejected

**"The `after` arm answered less precisely."** Rejected. The measured difference on P3
precision is one path in each of five answers, and it is `AGENTS.md` every time. That path
is in the repository, so the scorer counts it; it is not in the key, because the key was
written before anyone could know the `after` answers would cite their source. Reading
0.857 as an agent that got something wrong requires ignoring `wrong_paths`, which is
printed per repetition for this reason. What would settle it is a key that names the
instruction surface as an allowed citation, and that key would have to be pre-registered
for a future experiment; changing this one now would be writing the rule after seeing the
result.

**"The instruction rewrite made the agent better."** Rejected, and not for lack of a
number. The words cause and impact are refused in this layer (ADR-014), and every row
above is COMPARATIVE between two commits of one repository under one model, one provider
and n = 5 per arm. What was measured is that two versions of one file are followed by
different work quantities in every repetition. That the second version is BETTER is a
judgement about what the owner wants, and this experiment does not make it: an instruction
file that pre-answers a question also removes the reading that would have caught it if the
answer had gone stale.

**"P5 at zero tool calls shows the agent did not check."** Not rejected, but not
established either. Both readings are consistent with what is stored: the answer was
correct against a key written before the run, and it was produced without opening a file.
This measurement cannot distinguish "it knew from AGENTS.md and was right" from "it
repeated AGENTS.md and would have repeated it if AGENTS.md were wrong". The experiment
that separates those is an arm whose AGENTS.md names the WRONG files, and it is not this
one. It is named here so that nobody reads the zero as verification.

**"The `tool_calls.Read` and `tool_calls.Bash` rows show the after arm is unknown on
P5."** Rejected as a reading of the data, and it is a real gap in the report. Those two
rows print `n_b 0` and `-` for the `after` arm because a per-tool column exists in an
arm's table only if some capture in that arm used the tool, and no `after` P5 session used
either. The `after` sessions all recorded a stream, so their true Read and Bash counts are
zero and not unknown; the row that carries the fact correctly is `tool_calls`, whose value
list for that arm is `0,0,0,0,0`. This is written up rather than fixed here because fixing
it changes `experiments_measure._filled`, which is not this task's to change, and because
the number a reader needs is on the page either way.

**"The stop bound was not needed, so it did nothing."** Rejected. It was compared after
every one of the 20 sessions, and it is why session 11's 1,007,870 tokens are a line in
this write-up rather than a surprise found afterwards. E09's bound was in a brief and
could not act; four of its sessions crossed it and nobody saw until the end.

## What downstream may now say

Every number above is COMPARATIVE and stays comparative. A report, a series or a
forecast may say: on this repository, at these two commits, under `claude -p --model
sonnet`, with n = 5 repetitions per arm and the environment fingerprint differing in
`instruction_hashes` alone, an `AGENTS.md` that names the key files of a question is
followed by less work on both probes: the median tool-call count goes 12 to 7 on P3 and 7
to 0 on P5, with Hodges-Lehmann shifts of -5 and -7 and an exact p of 0.008 on both, and
recall unchanged at 1.000. It may not say that the rewrite CAUSED the
change, that the effect would hold on another repository, another question or another
model, or that the `after` arm is more correct: precision is an upper bound (a wrongly
named symbol is counted nowhere), the answer key does not carry the instruction file, and
the demotion rule withholds `tool_calls`, `cache_read_tokens`, `num_turns` and
`unique_files_read` from repository comparison until n reaches the `N_needed` printed
beside each. Coverage is 4/4 on all 20 captures; `compactions.pre_compaction_tokens` and
`exploration_scope.read_to_edit_ratio` are unknown on every capture in both arms, which is
what a read-only probe that never compacts and never edits leaves behind, and they are
unknown rather than zero everywhere they appear.
