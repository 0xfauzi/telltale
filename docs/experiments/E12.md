# E12: can a reviewer who sees only Telltale's summary of a session diagnose it as well as one who sees the raw stream, and at what cost?

**The full run happened.** Twelve reviewer sessions, six sessions in each arm, on the
material store rebuilt after W4-F3, at the token bound the owner raised after the pilot.
Under the rule written before any reviewer ran, eight of the ten questions are labelled
"summary sufficient" and two, Q2 and Q8, are labelled "summary insufficient". No question
is labelled "neither". The raised bound is a budget guard and nothing else: the decision
rule, the answer key and the questionnaire are exactly the ones committed before the
pilot, and the amendment of 2026-09-03 moved only the per-session token ceiling.

Why this matters (30 seconds): H1 is the claim that Telltale's summary is worth reading.
If a reviewer answers the same diagnostic questions from a 38,063 byte summary as from a
1,440,338 byte stream, the recorder earns its place; if it answers worse, the summary is
a convenience and not evidence. Everything downstream that quotes a summary instead of a
stream rests on this.

## Decision rule, written before the run

Quoted verbatim from `experiments/E12/protocol.md`, section "Pre-registered decision
rule", which was written and committed before any reviewer session existed:

> - Per question and arm: agreement = the number of sessions (of 6) whose answer equals
>   the key exactly. An `unknown` counts as disagreement, and is tallied separately as
>   "declared unknown" because in arm S it is the designed answer wherever Telltale's
>   coverage says partial (a masked exit status, W3-T3).
> - Per question: "summary sufficient" when arm S agrees on at least as many sessions as
>   arm R; "summary insufficient" when arm S agrees on fewer; "neither" when both agree on
>   fewer than 4 of 6. No pooled score across questions is computed: the ten questions
>   are not one thing.
> - Cost: per reviewer session, wall time and total tokens from the launcher's own
>   capture (the reviewer runs under `telltale run --experiment E12`), reported as the
>   median and the full sorted list per arm. H1's claim about cost is a comparison of
>   these two lists, stated with n = 6 per arm and no significance test at that n.
> - What the result can support: a statement about these six sessions, this
>   questionnaire and one reviewer model, claim class comparative. It cannot support a
>   statement about sessions in general or about human reviewers.

One bound moved between the pilot and this run, and protocol.md records it under
"Sessions":

> Amended 2026-09-03 after the pilot: the per-session token bound is 2,000,000 (was
> 400,000). The pilot's raw arm spent 588,848 tokens on the 1.44 MB stream (cache reads
> 534,249) and the largest stream is 1.97 MB; the owner approved the raised bound on
> 2026-09-03. The wall bound of 10 minutes and the answered-questions bound are unchanged.

A stop bound decides whether a run continues. It is not a term in the rule above, it does
not enter any score, and no answer changes because of it. The six constants the runner
writes into `out/summary.json` under `bounds` are `stop_tokens` 2000000, `stop_wall_ms`
600000, `stop_min_answers` 5, `sessions_per_arm` 6, `max_turns` 60, `reviewer_model`
opus.

At six scored sessions per arm the three labels are defined, so `run.py` prints a verdict
rather than the refusal it printed for the pilot.

## What we did

The material store was checked first, because the protocol names the store this run may
use. `TELLTALE_HOME=experiments/E12/out/store uv run python experiments/E12/make_key.py
experiments/E12/manifest.json --check --material` prints 30 of 36 agreeing cells, with
Q1, Q4, Q6, Q7 and Q10 agreeing on all six sessions and Q2 differing on all six because
Telltale prints null where a test run's exit status is masked. That is the last row of
protocol.md's table of checks, and it is the store this run used.

Environment: one fingerprint for all twelve reviewer sessions,
`env_03cf6eeaf72643855ffdf33cf9b8867154a18d6f8dbb284f75cd59ff5f373edc`, Claude Code
2.1.259, model `claude-opus-5`, this branch at `efd75b7`.

1. For each of the six sessions and each arm, built the material. Arm S is the text of
   `telltale show`, `telltale timeline` and `telltale vector` for that session's
   `material_capture_id` in the E12 material store (`TELLTALE_HOME=experiments/E12/out/store`,
   read-only: no `rebuild`, no `outcome`), written as `summary.txt`, `timeline.txt` and
   `vector.txt`. Arm R is the archived raw stream copied to `session.jsonl`.
2. Put each arm's material in a fresh temporary directory holding nothing else, OUTSIDE
   this repository. Outside is load-bearing twice over: `claude` walks up from its
   working directory looking for a CLAUDE.md, and this checkout has one, with `key.json`
   beside it.
3. Launched one reviewer per session and arm, serially, in the foreground:

   ```
   telltale run --provider claude --task-id E12-<n>-<S|R> --attempt 1 --experiment E12 -- \
     claude -p --model opus --permission-mode bypassPermissions --max-turns 60 \
     --output-format stream-json --verbose "<the prompt>"
   ```

   The prompt is built from `key.json`'s own question text, so the questions asked and
   the questions the key answers cannot drift. It is byte-identical in every one of the
   twelve sessions and identical to the pilot's: sha256
   `1ff3588bf878e2f6013b50819cc5826451abc75222f83a605796dc1c76a6666f`, recorded in every
   run file. It names no task, no session, no arm and no date, and `run.py` refuses to
   launch if any of the six task ids appears in it. No run needed the read restriction
   restated: `restated` is false in all twelve.
4. Parsed the last JSON object carrying the ten keys out of the `result` message on each
   child's stdout, scored it against `key.json` by exact match, and wrote
   `out/<session>-<arm>.json`. No reviewer's prose was written to disk.
5. Read wall, tokens and `total_cost_usd` back from each reviewer's own capture, never
   from the reviewer's words, and read each capture's file_read paths back to check the
   blinding held.

The twelve ran between 16:28 and 17:03 local time on 2026-09-03, one at a time, with
2108311 ms of reviewer wall in total.

## What it means

The rule applies: six sessions were scored in each arm, so every label below is a verdict
and not a refusal.

**Q1_pytest_runs, summary sufficient.** 6 of 6 in both arms. The summary carries
`verification.agent_test_runs`, and after W4-F2 raised the stored-command bound to 512
this number matches the key on all six.

**Q2_failed_pytest_runs, summary insufficient, and this is the designed answer.** Arm S
declared `unknown` on all six sessions. Arm R answered 5 of 6, missing W3-E08b/1 with 2
against a key of 1. protocol.md predicted exactly this: every test run of every one of the
six sessions pipes into `tail`, so the exit status is masked, and since W4-F3 Telltale
prints null for `failed_test_runs` and moves the stated-run counts into the warning
instead of printing a count that means "I could not see". Six reviewers read that and six
said unknown. The label is "insufficient" because the rule counts an unknown as a
disagreement, and the number the reviewer could not give is a number the summary does not
have. The pilot is the contrast that makes the point: on the pre-W4-F3 store the same
question printed `failed_test_runs: 0` with a warning beside it, and the pilot's arm S
reviewer answered 0 and was wrong. Withholding the number produced six honest unknowns
where printing it produced one confident error.

**Q3_edit_after_last_pytest, summary sufficient.** Arm S 6 of 6, arm R 5 of 6. The one
raw-arm error is W3-V/1, where the reviewer answered yes and the key says no. This is the
only question where the summary arm beat the raw arm outright.

**Q4_files_edited, Q5_tool_errors, Q6_compactions, Q7_subagents, Q9_result and
Q10_output_tokens, summary sufficient.** 6 of 6 in both arms on each. Q6 and Q7 are zero
on all six sessions, so they test that neither arm invents a compaction or a subagent, and
neither did. Q9 and Q10 are carried verbatim in the summary and both arms read them off.

**Q8_commits, summary insufficient.** Arm S agreed on 1 of 6, disagreed on 2 and declared
unknown on 3. Arm R agreed on 4 of 6. The summary does not carry a commit count for the
agent's own `git commit` calls, so three arm S reviewers said unknown and two guessed from
the timeline. The two arm S disagreements are W4-T1/1, answered 2 against a key of 1, and
W3-V/1, answered 1 against a key of 7. Arm R's two disagreements are W4-T1/1, answered 3,
and W3-T4/1, answered 7 against a key of 9.

The wording defect the pilot found is in this question and it is not rescored. Q8 asks how
many Bash tool calls ran `git commit`; `make_key.py` counts calls, and a call whose script
contains the string twice is one call. Both pilot reviewers answered 2 where the key says
1, and this run's W4-T1/1 reviewers answered 2 and 3 for the same reason. The question was
frozen before any reviewer ran and it stays frozen: the key is right, and the wording lets
a careful reader answer differently. What the full run adds is that the defect is not the
whole story, because arm R still agreed on 4 of 6 and arm S on 1 of 6.

**Cost.** The raw arm cost more tokens and less wall. Median tokens 696509 against 422835.5,
a ratio of 1.647; median wall 138098.5 ms against 177974.0 ms, a ratio of 0.776. The
pilot's 3.943 token ratio does not survive at n = 6: arm S's material grew after the W4-F3
rebuild (W4-T1/1's arm S material is 38063 bytes here against 34649 at the pilot), arm S
reviewers took more turns on it, and one arm S session, W4-T1/1, took 486416 ms, more than
twice any other and the single largest wall in the run. Strip the cache reads and the two
arms are close: median 46686 tokens for arm S against 51666 for arm R. Almost all of both
arms' totals is context re-read on every request, 0.8785 of arm S's median session and
0.9225 of arm R's.

**Nothing crossed a bound.** The largest session was 975489 tokens against the amended
2000000, and the longest was 486416 ms against 600000. The old 400000 bound would have
been crossed by all six raw sessions and by four of the six summary sessions.

## What we rejected

**Treating the raised bound as part of the decision rule.** Rejected: the rule quoted
above never mentions a bound. The bound decides whether the run continues, and the key,
the questionnaire and the scoring are identical to the pilot's, byte for byte, prompt
sha256 included.

**Quoting `summary.json`'s `derived.cache_read_share` and

a reducer change would be a change to the runner in the middle of the run it is running.

**Averaging the four failed launches into an arm.** Rejected: every token counter on them
is zero or absent and the reviewer never answered. A zero-token session in a cost median
would be a claim that a reviewer did the work for nothing. They are counted and named in
their own table.

**Scrubbing the task ids out of arm S's timeline.** Rejected, for the reason attempt 1
gave and this run did not change: protocol.md defines arm S's material as the text of
three commands, the raw arm is explicitly not scrubbed, and editing one arm's material
after seeing what it contains is a second experiment under a new id. Measured instead: 2
to 15 mentions per session in arm S, 162 to 503 in arm R.

**Re-running the ten runs whose commands named a path outside the material.** Rejected:
the protocol's invalidation test is the file_read path list, which is empty in all twelve,
and every flagged command decodes to the reviewer's own directory, its own scratch file,
or a `sed` expression that is not a path. Promoting a stricter test after seeing which
runs trip it is the same error as loosening a bound after seeing which arm crosses it.

**Rescoring Q8.** Rejected: the question and the key were committed before any reviewer
existed. A question whose wording admits a second reading is a finding about the
questionnaire, and it is reported as one.

**Reading the raw streams to adjudicate a disagreement.** Rejected on the brief's
instruction and on the design: `key.json` is the key, it was written from the streams
before any reviewer ran, and a scorer who goes back to the stream to decide who was right
has replaced the pre-registered answer with a fresh judgement.
