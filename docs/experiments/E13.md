# E13: does TimesFM-3 clear the baselines anywhere in the whole Claude population, launcher captures and imported day-to-day transcripts alike?

Why this matters (30 seconds): the final report's open decision 4 is whether gathering
more data is worth the owner's time. Every forecasting label the laboratory has produced
is "baseline sufficient" or "not assessable", and every blocker has a count behind it.
Before asking anyone to capture more sessions, the cheapest question is what the sessions
already on disk buy: the store holds 49 launcher captures of the build with at least 32
model requests (E07 scored 15 of them) and 545 imported Claude transcripts with at least
32, none of which the laboratory has ever scored. (An earlier draft of this paragraph
said 59 and 930: those are the census counts at 16 requests, the change-clock c_min the
census script used, not at the request clock's 32. The run applied 32.) If the model
beats the baselines nowhere in a population forty times E07's, more data of the same
kind is not the lever.

## Decision rule, written before the run

Per (capture, target, H), E07's rule, unchanged: E_M = mean MAE of timesfm in true order,
E_B = min over the four baselines in true order, W_MB = share of windows where timesfm
beats the best baseline. Baseline sufficient iff E_M > (1 - delta) E_B or W_MB < w, with
delta 0.10 and w 0.60. Otherwise "not baseline sufficient at this n, placebo pending":
E08 measured the chronology control failing on this clock (persistence was not worse
under every placebo run), so no positive label is reachable here and none is claimed.
Constants: delta 0.10, w 0.60, k_min 20, c_min 32, H in {1, 4}, stride H, baseline
window 8, tau q80 of the first c_min rows.

Two cohorts, pooled inside each and never across them:

1. `claude/launcher/level 1`: every launcher capture of a Claude session. E07's rule
   verbatim, the pre-registered variant `request_past_only`, all eight readiness checks
   must pass.
2. `claude/import/level 1`: every imported Claude transcript. The census measured, on
   every one of the 930, that two of the eleven request-clock columns are `unavailable`
   on the transcript surface: `request_duration_ms` (a transcript records no request
   duration) and `env_changed` (an import emits no environment fingerprint). Readiness
   check 1 therefore refuses every import under `request_past_only`, and E07's cohort
   rule had excluded imports before it could be seen. This run pre-registers a second,
   named variant, `transcript_past_only`: the nine forecastable columns as past-only
   covariates. Check 1 is waived for an import only when its not-forecastable set is
   exactly those two columns; checks 2 to 8 must pass as written. The variant name is
   stored on every `forecast_runs` row and on every per-capture file, and no pooled row
   mixes the variants. Two assumptions ride on every import row: regime boundaries
   inside a transcript are not observable (no fingerprint, so no changepoint, so check 5
   passes on one regime), and request duration is not observable on this surface.

What the outcome means. Any label other than baseline sufficient, in either cohort, is
the number that says a placebo-capable run on that cohort is worth a brief. Baseline
sufficient everywhere means the request clock's targets are not where more data helps,
and the owner's decision 4 turns to the other clocks, whose blockers are outcomes, not
sessions.

What is not in the population and why. Codex captures: 1,459 on the store, every one
builds to 0 request-clock rows because the Codex reducer emits `turn` activities and the
request clock reads `model_request` (measured on imp_869276e15eb90a31ac51856f: 5,736
`token_count` rows, 0 series rows). That is a gap in the reducer, recorded in the carried
items, not a property of the data. Captures with fewer than 32 model requests: 1,397,
below c_min by the pre-registered constant. Telltale's own captures (provider generic or
None, 13): not sessions.

Everything else is E07's code, imported by `experiments/E13/run.py` and unchanged: the
store copy, the census query, the series build, the readiness checks, the backtest, the
persisted run read back out of the copy, the per-capture files and the pooled rows.

## What we did

`uv run --extra forecast python experiments/E13/run.py --device mps` on 2026-09-05,
against a copy of `~/.telltale/telltale.db` taken at 20:31:23 UTC (1,692,192,768 bytes,
3,463 captures). E03 had released the MPS pin at a relative difference of 9.072e-07
against CPU, and the pilot measured 101 ms per window on MPS against 154 ms on CPU. Wall
time 8,963 s (2 h 29 min), of which the model's own forward passes took 144.0 min on the
import cohort and 4.2 min on the launcher cohort. Every number below is in
`experiments/E13/out/summary.json`; per-capture files are under
`experiments/E13/out/<capture>/<target>-H<horizon>.json` and the pooled rows under
`experiments/E13/out/pooled/`.

Population, from the copy: 3,463 captures on disk. Excluded before readiness: 1,397 with
fewer than 32 model requests, 1,459 Codex captures (0 request-clock rows each, the reducer
gap named above), 13 of Telltale's own (provider generic or None). Assessed: 545 imported
Claude transcripts and 49 launcher captures, 594 captures, 3,564 (capture, target,

## What it means

The rule's second branch: baseline sufficient, in both cohorts, on every pooled row and
on 583 of 596 runs. TimesFM-3 is within a few percent of a rolling median of the last
eight values on the request clock, on both the build's own sessions and the owner's
day-to-day sessions, at both horizons, over 77,442 windows. The thirteen runs labelled
"not baseline sufficient at this n, placebo pending" are 2.2 percent of the runs, they
are small (median 24 windows), they clear the skill line by at most 0.068, and the pooled
row that contains each of them is baseline sufficient. The pre-registered rule makes no
multiplicity correction and none is applied here after the fact; the count is reported
as it is, and the pooled rows are the cohort decision.

For the owner's decision 4: more request-clock data of the same kind is not the lever.
Forty times E07's population moved the median skill from 0.084 (E07's best single run)
to 0.011 at H = 1 and 0.030 at H = 4, which is the direction a real effect does not take.
Where more data still matters is the change clock (E11: 0 windows on every target,
36 rows needed inside one regime), and its blocker is linked accepted changes with
outcomes, not sessions.

## What we rejected

That TimesFM-3 was handicapped by the missing covariates on imports. The launcher cohort
carries all eleven columns under `request_past_only` and its medians (0.989 at H = 1,
0.966 at H = 4) match the import cohort's (0.989, 0.970) to two decimal places.

That the thirteen pending runs are a subpopulation where the model works. They share no
target beyond `output_tokens`, twelve of thirteen are H = 4, and every one is among the
shortest runs; the five runs above 1,000 windows sit between 0.927 and 1.011 of the baseline, and none clears W_MB 0.60.
A placebo-capable run on those thirteen would test that reading and this file does not
claim it either way.

That E07's decision function is stale. The `label_reason` string stored on every run
still says block_shuffle "does not exist"; it exists since W3-T2 and E08 ran it. E13
inherited E07's code unchanged by design, so the string is wrong about the codebase and
right about this run: no placebo was run here, and no positive label was reachable.

## How sure we are

- The counts, ratios, skills, calibration and lead-time numbers: measured, from
  `out/summary.json`, reproducible from the store copy and the run file.
- The 594-capture population being everything the store holds with 32 or more requests
  on the request clock: measured (the exclusion tally sums to 3,463).
- "More request-clock data is not the lever": reasoned from the two cohorts agreeing and
  from the skill falling as n grew.
- Whether a placebo on the thirteen pending runs would upgrade any of them: unknown; not
  run.
- Codex sessions: unknown for this experiment; W7-T1 has since given the Codex reducer a
  request clock, and the census must be rerun before anything is said about them.

## What downstream may now say

Predictive, cohort `claude/import/level 1` under variant `transcript_past_only` and cohort
`claude/launcher/level 1` under `request_past_only`, coverage as each run records it: on
the request clock, TimesFM-3 is baseline sufficient for `output_tokens` at H = 1 and 4,
for `fresh_input_tokens` at H = 1 and 4, and for `tool_calls_since_prev` at H = 1, with
rolling median the best baseline in 584 of 596 runs. No run may be described as temporal
evolution or conditional prediction. Nothing here speaks for Codex, for the attempt or
change clocks, or for any horizon other than 1 and 4.
