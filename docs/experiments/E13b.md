# E13b: does TimesFM-3 clear the baselines on the Codex sessions, the cohort E13 could not build?

Why this matters (30 seconds): E13 answered "baseline sufficient" over 596 runs on Claude
sessions and excluded every Codex capture by measurement: before wave 7 a rollout built a
request clock of 0 rows. W7-T1 gave rollouts a request clock (one model request per
`event_msg/token_count`), and the post-wave-7 census (docs/gates/wave-7.md) counts 781
Codex imports with 32 or more requests, 2,005 ready (capture, target, horizon) triples
and 289,373 windows: four times the Claude population by windows, on a different provider,
a different model family and a surface whose `fresh_input_tokens` varies request to
request (ready on 659 captures at H = 1, against 9 on Claude). If TimesFM-3 is baseline
sufficient here too, H6 is answered on both providers Telltale records.

## Decision rule, written before the run (2026-09-06)

E13's rule, verbatim, on one cohort, `codex/import/level 1`: per (capture, target, H),
E_M = mean MAE of timesfm in true order, E_B = min over the four baselines, W_MB = share
of windows where timesfm beats the best baseline. Baseline sufficient iff
E_M > (1 - delta) E_B or W_MB < w, delta 0.10, w 0.60; otherwise "not baseline sufficient
at this n, placebo pending". Constants: k_min 20, c_min 32, H in {1, 4}, stride H,
baseline window 8, tau q80 of the first 32 rows. Pooled rows per (target, H) over the
cohort are the cohort decision; per-capture labels are reported as counts.

Variant: the registry's `request_past_only`, with the columns readiness check 1 (as
amended by W7-T3) excludes by name because they are `unavailable` on this surface:
`request_duration_ms` (the rollout timestamp rule failed its own bar in W7-T1 and stays
None) and, on captures imported before W7-T2, `env_changed`. The excluded set is recorded
on every run; runs with different excluded sets are not pooled (W7-T3's pooling rule).

Targets: output_tokens, fresh_input_tokens, tool_calls_since_prev, whichever pass
readiness. The census expects tool_calls_since_prev to fail variation on 1,001 of 1,562
triples and output_tokens and fresh_input_tokens to be ready on 659 captures at H = 1 and
343 at H = 4.

What the outcome means: as E13. Baseline sufficient everywhere means more request-clock
data is not the lever on either provider. Any pooled row that is not baseline sufficient
is the number that says a placebo-capable run on this cohort is worth a brief.

Excluded before the run: Claude captures (E13 and E07 scored them), captures with fewer
than 32 model requests (2,095 on the copy), Telltale's own captures.

Runner: experiments/E13b/run.py, E13's mechanics imported by path with the provider
constant flipped; store copy under experiments/E13b/out/home (never ~/.telltale). Pilot
first (`--limit 3`), then the whole cohort on MPS; the pilot's windows per second decide
whether the whole cohort runs in one night or is split.
