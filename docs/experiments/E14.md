# E14: does a transcript's own timestamps reproduce the request duration OTel states?

Why this matters (30 seconds): `request_duration_ms` is the one request-clock column an
imported Claude capture cannot fill. Design 6.12 gave it to the OTel `api_request`
record, which states `duration_ms`, and a transcript line states nothing of the kind, so
every backfilled capture wrote the column as all None and readiness check 1 counted it as
not forecastable. That is not a small accounting matter: E13's census measured 930
imported Claude captures with at least c_min model requests, and every one of their 5580
(capture, target, horizon) triples failed at the same first line, `coverage: measured 9,
needed 11`, before any of the other seven checks got a word in. A transcript does date
every line, and the assistant lines of one request share a `requestId`. If the gap
between the line before a request and the line that closes it is the request's duration,
930 captures gain a measured column instead of an absent one. If it is not, the column
stays `unavailable` and nothing may be built on it.

## Decision rule, written before the run

Adopt the last-line derivation if at least 90 percent of matched requests agree with the
OTel duration within 10 percent relative. Below that, `request_duration_ms` stays None on
transcripts and the capability row's transcript cell stays `unavailable`.

Three definitions are measured, not one, because the choice between them is the decision:

| name | request ends at | request opens at |
| --- | --- | --- |
| `last_raw` | the LAST assistant line of the requestId | the nearest earlier line of any other type carrying a timestamp |
| `last_obs` | the LAST assistant line | the nearest earlier line the PARSER stores: a user line, or a `system` line whose subtype is `compact_boundary` |
| `first_raw` | the FIRST assistant line | as `last_raw` |

`last_obs` is the only one a reducer can implement. `activities.py` sees observations,
not lines, and the fifteen transcript line kinds `claude_transcript.py` counts and does
not read (attachment, queue-operation, mode, and the rest in `claude_drift.DRIFT`) leave
no observation behind. `last_raw` is here to measure what that restriction costs, and
`first_raw` is the obvious definition this run exists to reject or keep.

## What we did

```
uv run python experiments/E14/measure_transcript_duration.py
```

The runner is `experiments/E14/measure_transcript_duration.py`. It reads two things and
writes neither: E13's store copy at `experiments/E13/out/home/telltale.db`, opened
`mode=ro` with `pragma query_only`, for every `claude.otel.api_request` observation with
its `request_id` and `duration_ms`; and the owner's own `~/.claude/projects`, line by
line, for the session file each capture's `provider_session_id` names. The cohort is
therefore the sessions that have BOTH surfaces: the build's own launcher captures, whose
OTel records the store holds and whose transcripts Claude Code wrote at the same time.

Sample: 6533 api_request records over 128 sessions, 6518 of them matched to the same
requestId in that session's transcript file. Wall time 2.0 s. The per-request records are
in `experiments/E14/out/summary.json` (not tracked: raw output, regenerated by the
runner).


Units: `med otel`, `med derived` and `med |diff|` are milliseconds; `med rel` and `p90
rel` are (derived - otel) / otel, dimensionless; `within 10pc` is the share of matched
requests with |relative difference| <= 0.10. `none` counts the matched requests a rule
could compute no number for, and it is 0 for all three: every matched request in this
cohort has a line before it.

A request is 1 to 5 assistant lines sharing one requestId in 6517 of 6518 cases, and 7 in
one. Two lines is the commonest shape, 3314 of 6518, which is why the first line and the
last line are different questions.

## What it means

The rule takes its first branch. `last_obs`, the definition a reducer can implement,
agrees with the provider's own duration on 99.7 percent of 6518 requests, with a median
absolute difference of 21 ms against a median duration of 4683.5 ms, and a median
relative difference of -0.0034. The derivation is adopted:
`providers/claude_drift.py` gains a `request_duration` capability whose transcript cell
is `derived`, and `activities._request` writes `duration_ms` with
`duration_source: transcript_timestamps` and both observation ids as its provenance.

`derived` and not `observed`, and the distance between those two words is the whole of
what this experiment licenses. No transcript line states this number. It is computed
here, it is 21 ms away from the number the provider states, and design 6.3's word for a
number read out of a surface rather than stated by it is the weaker of the two.

## What we rejected

`first_raw`, the definition anyone would write first: end the request at the assistant
line that carries its usage. It agrees on 54.7 percent of the same requests, with a
median absolute difference of 425.5 ms and a median relative difference of -0.0571. The
reason is in the line histogram above: a request writes 2 or more lines 3675 times out of
6518, and the first of them lands when the first content block completes rather than when
the request does. A rule adopted on that definition would have shortened one request in
two by a median of nearly half a second and called it measured.

The restriction to lines the parser stores costs nothing measurable and is very slightly
better: `last_obs` beats `last_raw` (99.7 against 99.4 percent, 21 ms against 23 ms). The
lines it skips are the ones a transcript writes between a request and the line before it
without the session having done anything (attachment, queue-operation), so skipping them
moves the opening timestamp back to the last event that was really an event.

## How sure we are

- The agreement of `last_obs` with OTel on this cohort: **measured**, n = 6518, 128
  sessions, one machine, Claude Code 2.1.257 to 2.1.258.
- That `first_raw` is the wrong definition: **measured**, same n.
- That the same agreement holds on an INTERACTIVE session: **unknown**. Every session in
  this cohort is a headless launcher capture of this build, because a launcher capture is
  the only kind that has an OTel record to check against. The 930 imported transcripts
  the derivation is for are interactive sessions with no OTel record, so nothing here
  measures them. What is measured is the parser, the clock and the line structure, which
  are the same on both; what is not measured is whether an interactive session puts a
  different kind of pause between the line before a request and the request.
- That a request with no line before it is rare: **measured on this cohort only**, 0 of
  6518. An imported transcript whose first request follows a line kind the parser does not
  read gets None and a `dropped` diagnostic that counts it, and that path is exercised by
  `tests/integration/test_request_duration.py` rather than by this cohort.

## What downstream may now say

`request_duration_ms` on an imported Claude transcript is a **derived** number, coverage
`derived`, cohort "Claude Code transcripts, one capture per session file", computed as
the interval from the last stored user or system line before a request to the last
assistant line of that request, with both observation ids on the row. It may be a
forecast covariate and a forecast target wherever an `observed` column may be, and
readiness check 1 accepts it by the same rule it accepts any derived column. It may not
be described as the provider's own timing: the row carries `duration_source`, and
`otel_api_request` and `transcript_timestamps` are different statements about where a
number came from. Nothing here licenses a claim about an interactive session's agreement
with a duration nobody recorded for it.
