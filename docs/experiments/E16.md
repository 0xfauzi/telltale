# E16: on the change clock of the owner's own repositories, backfilled from git and GitHub, can a candidate change's known features condition a one-step forecast of what happens after it lands (H8), and do the baselines or the chronology survive the placebo (H5, H6)?

Why this matters (30 seconds): H7 and H8 are the two goals of the specification that the
laboratory has never been able to assess. E11 got 0 windows on every candidate target: the
change clock held 40 rows, all from Telltale building itself, merge_verification_ms was
unavailable on every one and rework_within_3 was 0 on every decided row. The rule needs 36
rows inside one regime. The owner's four repositories landed 569 first-parent commits on
`main` in the 90 days to 2026-09-06 and Telltale saw none of them, because day-to-day
capture was never switched on. Wave 8 (W8-T1, W8-T2) makes those commits rows: the
repository block from git, the verification outcome from GitHub check runs, the rework
label from git. This experiment is the first time H8 has rows to be wrong on.

## Decision rule, written before the run (2026-09-06, before W8-T1 and W8-T2 land)

Population: the first-parent history of `main` in four repositories the owner wrote,
imported by `telltale import git-history` with check runs: telltale, systemap, deckgen and
kstrl (the directory ~/Documents/code/ralph). chopin is excluded before the run: 592 of
594 first-parent commits in its last 90 days are by two other authors. Whole history, not
90 days; the 90-day pilot numbers below are what was measured before the rule was written.

Pilot, measured read-only on 2026-09-06 with the same line-overlap rule W8-T1 implements
(a later first-parent commit within the next three removes, in the same file, a line this
commit added, ignoring lines of 3 characters or fewer):

| repository | first-parent commits, 90 days | decided | rework_within_3 rate | check runs per commit |
|---|---|---|---|---|
| telltale | 156 | 153 | 0.170 | 1 |
| systemap | 108 | 105 | 0.667 | 18 |
| deckgen | 118 | 115 | 0.522 | 3 to 4 |
| kstrl | 187 | 184 | 0.495 | 7 |

Every row is an uncaptured row: the seven process columns are unavailable and are
excluded by name (W7-T3's rule), `env_changed` is unavailable (no fingerprint), and the
run's assumptions say so. The frame is one regime per repository by construction, which
is a stated weakness, not a finding: the model, effort and runtime behind those commits
were not observed, so a changepoint that E06 would have marked is invisible here.

Three targets, each on its own lineage, never pooled across repositories:

1. `merge_verification_ms` (H = 1, unconditioned and conditioned).
2. `merge_verification_failed` (H = 1, unconditioned and conditioned).
3. `rework_within_3_lag3` (H = 4, scored on step 4 only), the column W8-T2 adds: row j
   carries the label of change j - 3, decided by change j's commit time. At origin o the
   fourth step is change o's own label and no context cell was decided after the origin.
   `rework_within_3` itself is NOT forecast here: its context rows o - 3 to o - 1 carry
   labels decided by commits at index >= o, which is look-ahead (recorded in
   docs/design/amendments/W8-T2.md).

Unconditioned run: E07's constants (delta 0.10, w 0.60, k_min 20, c_min 16 on this clock,
stride H, baseline window 8, tau q80 of the first 16 rows), TimesFM-3 against the four
baselines in true order, then the block-shuffle placebo (B = max(2, H), R = 5 seeds) as
W3-T2 built it. Labels per (repository, target) by design 6.12's rule as amended by E08b
(true-order numbers decide baseline sufficiency; the placebo decides between temporal
evolution and conditional prediction only when the model is not baseline sufficient; the
placebo is valid only when persistence gets worse under it).

Conditioned run (H8): the same origins, plus the candidate's own A block (files_changed,
lines_added, lines_removed, subsystems_touched, test_files_changed, dependency_delta of
row o) as a past-future covariate, edge-padded past step 1 exactly as the adapter records.
Paired by origin. The pre-registered readings, per (repository, target):

- "the candidate's features move the forecast" iff the paired median difference in MAE
  (conditioned minus unconditioned) is below zero in both halves of the origin range and
  the conditioned run's calibration is not flagged where the unconditioned one is not.
- "no measurable conditioning at this n" otherwise.
- Every output carries the sentence design 6.12 requires: the difference measures how much
  the candidate's known features change the forecast; it is not the effect of merging the
  candidate, because only one future is observed. The report writer refuses cause, impact
  and would.

For the flag targets, MAE of the median forecast against a 0/1 label is reported as it is
and the base rate is printed beside it; a run whose best baseline is a constant at the base
rate is what "baseline sufficient" means on a flag, and this file will say so rather than
switch to a classification metric after seeing the numbers.

Missingness on the target, added 2026-09-06 after W8-T1 and W8-T2 merged and before any
run. Every post-merge column on a lineage has holes: `merge_verification_ms` and
`merge_verification_failed` are unknown on a commit without a check run (a push of several
commits gets one run, on its head), `rework_within_3` on the last three rows and
`rework_within_3_lag3` on the first three. Measured on this repository's 162 first-parent
commits with check runs: 135 check-run outcomes, 24 commits with no run, 3 diagnostics, so
the two verification targets are `partial` with 27 unknown cells. Dropping every window
whose context or actual holds an unknown target cell keeps 16 of 146 windows for
`merge_verification_ms` (below k_min) and 0 of 143 for the lagged label at H 4, because
every context starts at row 0 on a lineage shorter than 512 rows. The rule is therefore
row-level, as design 6.12 step (2) reads ("keep only rows where the target's coverage is
observed"): a target is forecast over the rows where it is known, in lineage order, and
the run records how many rows were excluded and which; the previous row of the context
means the previous change with a known target. That keeps 135 rows and 119 windows for
`merge_verification_ms`, 159 rows and 140 windows for the lagged label, on this repository.
W8-T3 implements it (forecast/frame.py); the readiness checklist runs over the retained
frame. Nothing is imputed. The excluded count per (repository, target) is a column of the
results table, and a target whose retained rows are fewer than c_min + H + k_min - 1 = 36
on a repository is not assessable there.

Not assessable, per (repository, target): fewer than k_min = 20 windows after exclusions,
or a placebo under which persistence did not get worse. Each is reported with its count.

What the outcome means. Any (repository, target) that is not baseline sufficient in true
order, with a valid placebo, is the first row of evidence for H5 on the change clock, and
any conditioned run that moves the forecast is the first for H8. Baseline sufficient
everywhere on hundreds of rows means the candidate block and the recent history of these
three outcomes do not forecast them one step ahead on this data, and H8's next lever is
the process columns, which only captured sessions supply (E17).

What is not in the population and why. Captured rows, corrected 2026-09-06 after
measuring the merged lineage: the launcher-linked commits of this repository are
task-branch commits that were squash-merged, and none is on main's first-parent history.
W8-T4 made the git-history capture define the tracked base: 5 of the 51 linked commits
share a tree with the squash commit that landed them and carry their capture's process
columns on that row; the other 46 are dropped by name and counted (`off_base_commits`),
so the telltale lineage is 168 rows with 5 captured, not 219. Five rows are too few to
change any label and are not separated out. Codex or Claude
sessions: none; this clock reads commits. Other branches: not first-parent history of
`main`, so not rows.

Runner: experiments/E16/run.py, importing E07's and E13's mechanics where they apply;
store copy under experiments/E16/out/home/ (never ~/.telltale); every number below maps to
a file under experiments/E16/out/.

## What we did

`experiments/E16/run.py` with `experiments/E16/rows.py` beside it, on 2026-09-06 at
18:23:38 UTC. Wall 18 min 12 s (1,091,901 ms inside the runner), device `mps`, TimesFM-3
against the four baselines. Another TimesFM process was on the same GPU throughout, so
this wall is a measurement of this machine on this afternoon and not of the protocol.

The experiment was run twice, at 14:59:55 UTC and again at 18:23:38 after the runner was
split into two files. Every field of every one of the twelve rows is identical between
the two runs, and so is the synthetic control: the walls are the only difference. The
numbers below are the second run's.

The store is the owner's rebuilt store plus `telltale import git-history` with check runs
for the four repositories. The runner never opens it for writing: `snapshot` copies
2,105,470,976 bytes through a read-only connection and sqlite3's backup API into
`experiments/E16/out/run-home/telltale.db` in 1,893 ms, points `TELLTALE_HOME` at the
copy, and refuses if that path resolves to `~/.telltale`. Everything below was computed
against the copy (`out/summary.json`, key `snapshot`).

Per repository, and never pooled across them, the change clock was compiled fresh
(`series build --clock change --repo <id>` in code) and stored in the copy. Per
(repository, target) the runner then ran four things in this order:

1. **Readiness over the retained frame.** `readiness.check(series, target, H)` cuts
   `frame.retained(series, target)` itself, so every one of the eight lines is measured
   over the rows the backtester will score. The whole checklist is in each target's JSON
   under `readiness.checks`.
2. **The unconditioned true-order run, its placebo and its label.**
   `placebo.paired(series, target, H, forecasters, "timesfm")`: one true-order backtest
   under the registry's variant `change_past_only`, five block placebos at B = max(2, H),
   five B = 1 controls, the persistence validity check and design 6.12's label as amended
   by E08b.
3. **The conditioned pair**, `candidate.conditioned(...)`, over the whole origin range of
   the conditioned frame and over each half of it. H is the registry's per target: 1 for
   the two verification columns, 4 for `rework_within_3_lag3`, scored on step 4 alone.
4. **The pre-registered reading**, from the paired median MAE difference in each half and
   the two runs' calibration flags.

Twelve (repository, target) rows, one file each:
`experiments/E16/out/<repository>/<target>.json`, with `summary.json` beside them and
`out/control/control.json` for the synthetic control. `out/run.log` is the whole stdout.
The store copy holds 90 `forecast_runs` rows this run wrote (12 rows and 3 control
targets, each three origin ranges, each an unconditioned and a conditioned run).

Two readings of the pre-registered rule were fixed in the runner before any number was
seen, because the pre-registration does not spell them out and choosing afterwards is
choosing a result. They are printed in `out/run.log` above the first table and stored
in `summary.json` under `rule`.

- The calibration clause is read on the pair over the **whole** origin range, because
  "the conditioned run" and "the unconditioned one" are the two runs of one pair; the
  halves clause is written about the difference alone. Both halves' flags are recorded.
- The "fewer than k_min windows" clause is applied per question, over the run that
  answers it: the unconditioned run's window count gates the label, the conditioned
  pair's paired-window count gates the reading. The two counts differ by construction,
  because the conditioned frame also drops the rows where the A block cannot be read,
  which the paragraph above anticipated for deckgen. The placebo-validity clause gates
  the label alone: the H8 rule reads no control and names none.

Nothing was lowered, nothing was widened, and no origin range was chosen after a number
was seen. Every constant is `telltale.forecast`'s and is printed in
`summary.json.constants`: delta 0.10, w 0.60, k_min 20, c_min 16, max_context 512,
placebo seeds 5, A block the six of `ABLATION_A`, past-only set `ABLATION_C`.

## What it means

**Per row, the branch the pre-registered rule took.** For the label (H5 and H6), branch
(c) on six rows, all with the same answer, "baseline sufficient": telltale, systemap and
deckgen `merge_verification_ms`, deckgen and kstrl `merge_verification_failed`, kstrl
`rework_within_3_lag3`. Branch (b) on the other six, "not assessable", every one of them
for the placebo clause rather than for a count: the smallest window count in the table is
22 and k_min is 20, so no row failed on rows. For the reading (H8), branch (c)
on eleven rows and branch (b) on deckgen `rework_within_3_lag3`, where the block holes
leave 18 paired windows against k_min 20. Of the eleven that reached the reading, ten
read "no measurable conditioning at this n" and one, systemap `merge_verification_ms`,
read "the candidate's features move the forecast".

**What the twelve rows say.** On the git-backfilled change clock of these four
repositories, in one regime each, the four one-line baselines are sufficient for all
three post-merge targets at every horizon tried: twelve labels, twelve times baseline
sufficient, and on the six rows whose chronology control was valid that label was
earned with the control standing. H5 asks whether the true order of an accepted-change
index carries forecastable temporal structure, and this run does not reach the two
labels that read that control on any row, because the baseline clause fires first on
every one of them. H6, whether TimesFM-3 repeatably clears the baselines, is answered no
on this clock and this population: the largest share of origins on which it beat the best
baseline is 0.5308, against the pre-registered 0.60. H8 asks whether a candidate's known
features condition the one-step forecast, and eleven rows could answer: ten say the
paired median difference does not hold below zero in both halves, and the single row that
does say so, systemap `merge_verification_ms`, rests on 23 paired windows over 39 rows,
which is three windows above the floor. One row out of eleven at that n is a result to
carry forward and not a finding to build on, and the pre-registration's own words for the
alternative are the honest reading of the other ten. The next lever for H8 is the one the
pre-registration named: the process columns, which are `unavailable` on 174 of telltale's
179 rows and on every row of the other three, and which only captured sessions supply
(E17).

## What we rejected

**"TimesFM-3 forecasts merge verification time on this repository."** Rejected by
W_MB. On telltale's `merge_verification_ms` the model's mean error is below the best
baseline's, 14 774.7 ms against 16 107.7 ms, and a table stopping there reads as a win.
It beat persistence on 0.5308 of the 130 origins, against the pre-registered 0.60, and
the margin clause `14 774.7 > 0.9 x 16 107.7 = 14 496.9` holds as well. Two clauses, both
firing, and the label is baseline sufficient.

**"The chronology of these lineages carries information."** Rejected by the sentinel on
six rows and unreachable on the other six. Design 6.12 admits the two labels that read
the placebo only after the baseline clause has failed, and it never failed here.
Separately, on six rows the control itself did not control: persistence was worse under 0 of 10
placebo runs on telltale `merge_verification_failed` and kstrl `merge_verification_ms`,
1 of 10 on telltale `rework_within_3_lag3`, 2 of 10 on systemap
`merge_verification_failed`, 4 of 10 on systemap `rework_within_3_lag3`, 7 of 10 on
deckgen `rework_within_3_lag3`. Design 6.12 requires 10 of 10.

**"The candidate block moves the forecast on this data."** Rejected by the halves. Four
rows have a negative paired median difference over the whole origin range and fail the
rule: telltale `merge_verification_ms` (-193.05 ms whole, -335.18 first, +136.61
second), telltale `merge_verification_failed` (-9.71e-06 whole, exactly 0 first), deckgen
`merge_verification_failed` (-0.0045 whole, -0.2272 first, +0.0025 second) and kstrl
`rework_within_3_lag3` (-0.0667 whole, -0.0915 first, +0.0024 second). Each has a sign
that does not survive being asked of both halves separately, which is the anti-cherry-pick
clause of spec 15.7 doing its work rather than a technicality.

**"deckgen's conditioned pair is thin but usable."** Rejected by k_min. 27 of deckgen's
118 commits touched a binary file, so `lines_added` and `lines_removed` are unknown on
them, and the conditioned frame for `rework_within_3_lag3` is 91 rows and 18 paired
windows against k_min 20. The pre-registration anticipated this row and said to report it
as the rule says. The rule says not assessable, and lowering k_min to 18 for one row after
seeing 18 is the edit the pre-registration exists to forbid.

**"Widen the block, or drop `lines_added` from it, so deckgen fits."** Rejected before it
was tried. A pair whose conditioned run dropped two of the six A-block columns is the
unconditioned run wearing the conditioned run's name, and `candidate._block` refuses to
narrow for exactly that reason. The number that forbids the swap is 27: dropping the two
line-count columns changes what the conditioned run reads on 91 rows in order to add 27,
which answers a different question.

**"The single positive row is the beginning of an H8 result."** Rejected by n and by the
population. systemap `merge_verification_ms` reads "the candidate's features move the
forecast" on 23 paired windows drawn from 39 rows, after 66 of 108 commits were excluded
for having no check-run outcome and 7 more for a binary file. One row out of eleven, at
the smallest n in the table, is the thing the pre-registration's k_min clause is meant to
keep from being read as more than it is; it is reported and it is not built on.

**"Switch the flag targets to a classification metric."** Rejected by the
pre-registration, which said before the run that MAE against a 0/1 label is reported as
it is with the base rate beside it, and that a best baseline sitting at a constant near
the base rate is what baseline sufficient means on a flag. deckgen
`merge_verification_failed` is the clearest instance: base rate 0.5000, best baseline
persistence at 0.1053, model at 0.1734.

## What downstream may now say

A report, a gate document or a README may state the following, and nothing stronger.

- On the first-parent history of four of the owner's repositories, backfilled from git
  with GitHub check runs (657 rows across the four lineages, 888 scored windows in the
  twelve unconditioned runs), TimesFM-3 was labelled baseline sufficient for all three
  post-merge targets against persistence, rolling median, rolling mean and local drift.
  The claim class is `derived` for the metrics and `predictive` for the forecasts, and
  neither is ever upgraded.
- The candidate protocol ran on eleven of the twelve rows. Ten read "no measurable
  conditioning at this n"; one, systemap `merge_verification_ms` on 23 paired windows,
  read "the candidate's features move the forecast". The twelfth, deckgen
  `rework_within_3_lag3`, is not assessable at 18 paired windows against k_min 20.
- Any statement of the paired difference carries the mandatory sentence of design 6.12
  and spec 15.8 with it. The difference is between two forecasts of one observed history,
  and none of the three words ADR-014 refuses may be used about it.
- H5 is still not reachable on this clock. The baseline clause fires before the two
  labels that read the chronology control, on every one of the twelve rows, and on six
  of them the control did not control.
- What is not licensed: any claim about a repository outside these four, any claim about
  a regime boundary (none of the four lineages carries one), any claim that the process
  columns do or do not add information (they are `unavailable` on 174 of telltale's 179
  rows and on every row of the other three, so this run says nothing about them), and any
  reading of a paired difference as an effect of merging.
