# E17: do the process columns of a captured session add information about what happens after its change lands (H7)?

Why this matters (30 seconds): H7 is the last hypothesis in the specification with no
reading at all. E16 gave the change clock 657 rows and answered H5, H6 and H8 on them, but
every one of those rows came from git history, so the seven process columns (tokens,
compactions, verification cycles and the rest) were unavailable on all but 5 and were
excluded by name. The question "does what the agent did while making the change tell you
anything about what happens after it lands" has never had rows to be wrong on. Only a
captured session supplies those columns. That is what the daemon is collecting.

## Why the daemon runs

`com.telltale.daemon` is a launchd agent since 2026-09-07: KeepAlive, port 47311, logs in
`~/.telltale/daemon.log`. The pasted Claude and Codex snippets point day-to-day sessions at
it. A session started inside a git checkout binds to that repository (W9-T1), its commits
are linked at session end, and the change it landed folds its process columns from the
capture that recorded it (W9-T2). Every day of ordinary work therefore adds change-clock
rows whose process half is known. Nothing else in the system produces them, and no
experiment can be re-run to get them: they only accrue.

## Decision rule, written before the run (2026-09-08, before any row is scored)

Population: change-clock rows on one repository's first-parent history whose process
columns are available, meaning a capture recorded the session that landed the commit.
Never pooled across repositories, as in E16.

Start condition: a repository has at least `c_min + H + k_min - 1 = 36` retained rows with
process columns available inside one regime. Below that the run is not assessable and this
file says so with the count rather than lowering the bar.

Targets and constants: E16's, unchanged. `merge_verification_ms` and
`merge_verification_failed` at H = 1, `rework_within_3_lag3` at H = 4 scored on step 4
only; delta 0.10, w 0.60, k_min 20, c_min 16, stride H, baseline window 8, tau q80 of the
first 16 rows; TimesFM-3 against the four one-line baselines; block-shuffle placebo
B = max(2, H), R = 5 seeds. Rows with an unknown target cell are excluded row-level and
counted. Nothing is imputed.

The H7 comparison is paired by origin, two conditioned runs against the same origins:

- **A only**: the candidate's own diff block, which is E16's conditioned run.
- **A + P**: the same block plus the process columns of the session that landed the row.

Pre-registered readings, per (repository, target):

- "the process columns move the forecast" iff the paired median difference in MAE (A + P
  minus A) is below zero in both halves of the origin range and the A + P run's calibration
  is not flagged where A's is not.
- "no measurable process information at this n" otherwise.
- Every output carries design 6.12's required sentence: the difference measures how much
  the process columns change the forecast, not the effect of the process on the outcome,
  because only one future is observed. Cause, impact and would are refused.

A reading either way is H7's first. "No measurable process information" at this n is not
"the process does not matter"; it is the honest label the count supports.

## What day-to-day capture still cannot supply

From the wave 9 gate, unchanged:

- `env_changed` stays None: a daemon capture has no launched argv, so no environment
  fingerprint.
- `attempts_to_land` stays None: a hand-started session is not a numbered attempt.
- Post-merge outcomes still arrive from GitHub check runs, not from the session.
- Codex sessions bind no repository yet: command hooks only, no cwd on OTel.
- Codex metrics are unattributed in daemon mode (wave 9 defect 4).

Each of these is a column the run will exclude by name, and the exclusion list is part of
the result.
