# W0-E01 Claude capture feasibility

## OUTCOME

All 8 scenarios ran. The pilot S2 took 8.772 s and 99,661 tokens against limits of 300 s
and 200,000, so the run continued without stopping. Total spend: 8 sessions, 1,145,266
tokens, 1.165149 USD, 302.2 s of child wall time. `claude -p` started with `CLAUDECODE=1`
still set, so nothing had to be unset.

The four surfaces were captured together in one session each, so a fact present on one
and absent from another is a property of the surfaces rather than of two different runs.
The matrix, the drift record and every number are in `docs/experiments/E01.md`; the
sanitized fixtures are in `fixtures/sources/claude/2.1.257/S1` through `S8`, each with a
MANIFEST.md, and `grep -r TELLTALEFAKE fixtures/sources/claude | wc -l` is 22.

Four results decide things downstream:

1. **Capture fails open.** Same prompt, receiver alive (S2) and receiver dead (S6): exit
   code 0 both times, 8.772 s against 9.685 s (+0.913 s, +10.4%), 0 bytes of stderr
   against 99 bytes, which is one line naming the SessionEnd hook. The unreachable OTLP
   endpoint produced nothing at all.
2. **There is no late-export window on this version.** The sink outlived each child by
   15 s and not one request arrived after any exit, across 7 scenarios and sessions from
   4 s to 183 s long. The last request always arrived before the exit, by between 0.240 s
   and 0.561 s.
3. **Compaction is fully observable, and the digest says it is not.**
   `claude_code.compaction` exists on the OTel log surface with `trigger`, `pre_tokens`,
   `post_tokens`, `duration_ms`, `success` and `error`. S7 produced 4 of them, 3
   `compact_boundary` stream messages, 4 PreCompact and 3 PostCompact hook deliveries and
   `api_request` with `query_source=compact`. S7 is KEPT, not "not reproducible cheaply".
4. **The SessionStart http hook is registered and never runs.** 4 SessionStart hooks
   registered in every session, `num_hooks=3` executed, 0 requests to the sink across all
   7 live-sink scenarios. SessionEnd is the only bracketing hook available over http.

## WHAT WAS WRONG

**1. `--max-turns` is not in `claude --help` for 2.1.257, and still works.** The brief
specified it as the runaway guard. It is absent from the option list that `claude --help`
prints (`--max-budget-usd` and `--autocompact` are the documented budget controls), and
`strings` on the binary contains `--max-turns <turns>`, so it is hidden rather than
removed. All 8 sessions passed `--max-turns 40` and none reported an unknown option. Kept
as specified; recorded in `docs/experiments/E01.md` as drift.

**2. `docs/design/00-digest.md` 2.1 says "No compaction OTel event exists". It does.**
Building `CAPABILITIES` from the digest would have declared compaction unavailable on the
OTel surface and sent a reducer to the stream for a number the OTel logs carry directly.
Five more log events are also missing from the digest (`hook_registered`,
`hook_execution_start`, `hook_execution_complete`, `plugin_loaded`,
`subagent_completed`), and twelve stream message types.

**3. `claude_code.user_prompt` carries a `prompt` attribute with the content switches
off, and its value is the literal string `<REDACTED>`.** Same for `response` on
`claude_code.assistant_response`. A capability check written as "does the payload have a
prompt field" answers yes and is wrong. This is the one that would have made Telltale
claim it can see something it cannot.

**4. `capture_receiver.py --down` prints `PORT=0`, which is not a port a client can be
aimed at.** For S6 the runner therefore runs `--down` (confirming the protocol answer)
and then binds and releases an ephemeral port, which is a port nothing is listening on.
Documented in `run.py:down_port` and in the write-up.

**5. Two repository gates broke on files the brief requires, and fixing them needed
pyproject.toml, which is outside this task's OWNS list.** Three edits, each with a
comment naming the measurement:
  - `uv run mypy .` stops at `Duplicate module named "pkg"` as soon as one scenario has
    run, because every `out/<S>/repo` copy is another `pkg/__init__.py`. Fixed with
    `[tool.mypy] exclude` for `experiments/*/fixture_repo` and `experiments/*/out`. ruff
    already excludes `experiments/*/out` for the same reason and says so in its comment;
    mypy had no experiment output to trip over until now.
  - `uv run deptry .` reports DEP001 for `pkg`, the fixture's own package, imported by
    the fixture's failing test. Fixed with `[tool.deptry] extend_exclude` for the same
    two trees.
  - `uv run deptry .` then reports DEP001 for `matrix`, which `sanitize_fixture.py`
    imports so that "how many observations of this event" has one definition rather than
    two. Fixed by adding it to `known_first_party`, which is a statement of fact rather
    than a suppression.
  **The orchestrator should decide whether these three belong in pyproject.toml
  permanently or whether experiments/ should be excluded from mypy and deptry wholesale.**

**6. The child inherits `VIRTUAL_ENV` from `uv run`, and it breaks `uv run pytest` inside
the fixture copy.** The brief says the environment is `os.environ` plus the OTel
variables, so this was left as specified and it cost real turns: S1 spent a turn on
`rm -rf .venv && uv sync` before its tests would run, and S7's first `uv run pytest`
failed with exit 2 and `warning: VIRTUAL_ENV=... does not match the project environment
path .venv`. It did not affect any capture measurement, and both scenarios still
finished, but a launcher that shells out to an agent inside a `uv run` will hand it a
broken Python environment. **W1's launcher should decide explicitly which variables it
passes through.**

**7. The sanitizer needed a rule the brief did not name: the bare account name.** S4 and
S7 captured `ls -la` output, so `wumpinihussein` reached `hooks.jsonl` and `stream.jsonl`
in the owner column with no path around it, where the home-directory rule could not match
it. `path_rules` now replaces the account name on its own with `<user>` (42 occurrences),
applied after the two path rules because it is a substring of both.

**8. A stray `experiments/E01/fixture_repo/uv.lock` appeared and was removed.** Running
`uv run` from inside the fixture directory locks the fixture project. The capture ran
without that file, so committing it would have made the tracked fixture different from
the one that produced the fixtures.

## UNSURE OR NOT DONE

- **One machine, one version, one model, no repeats.** S6's +0.913 s is a single pair
  against S2. The direction (a dead receiver costs a little and changes nothing else) is
  solid; the size is one measurement.
- **The late-export window has no positive value to size a launcher's grace period
  with.** Nothing ever arrived late, so there is nothing to scale. Sizing that wait needs
  measuring on a version or a session shape that does export late.
- **UserPromptSubmit was not among the eleven declared hooks** (the brief's list omits
  it), so the hooks cell for "user prompt length" is "not measured here", not
  "unavailable". `matrix.py` keeps those two statements apart in the drift record.
- **`PostModelSwitch`, `api_error`, `api_refusal`, `auth`, `permission_mode_changed`,
  `result:error` and `system/api_retry` were never seen**, because no scenario switched
  model, hit an API error or was refused. Absence here is absence of the situation, not
  absence of the event.
- **`--include-hook-events` was not exercised.** Without it the stream still carries
  `system/hook_started` and `system/hook_response`, but only for SessionStart command
  hooks. What the flag adds is unmeasured.
- **Traces were never enabled** (`OTEL_TRACES_EXPORTER` unset), so `otel_traces.jsonl`
  does not exist in any scenario and the traces surface is untested.
- **S7 ended non-zero** with `terminal_reason: rapid_refill_breaker` after 3 compactions
  in 3 turns. Compaction was observed, but under an auto-compact threshold of 5 percent,
  which is not a normal session. Its `subtype` is `success` while `is_error` is true,
  which a reader that trusts `subtype` alone gets wrong.
- **The bash exit code is not on any surface.** OTel has `success` and `error_type`, the
  hooks have stdout and stderr with no status, and the stream has the number only inside
  the error text ("Exit code 2"). If a measure needs exit codes, they have to come from
  somewhere else.

## EXPLAIN FOR THE OWNER

**What was at stake.** Telltale is going to say things like "this session spent 40,000
tokens recovering from a failed test". Every one of those sentences depends on a fact
being visible somewhere. Before this experiment, "somewhere" was a research summary
written from documentation. This run replaced the summary with a capture: eight real
sessions, every reporting channel switched on at once, everything they said written to
disk.

**The four channels, in plain terms.** Claude Code can tell an outside listener about
itself in four ways. It can send structured records over the network the way any
monitored server does, and those come in two flavours: events (one record per thing that
happened) and counters (running totals). It can call a URL of your choosing at fixed
moments, such as just before a tool runs, which is what a "hook" is. And when it is run
headlessly, it prints its whole conversation as one JSON object per line, which is the
"stream". Events, counters, hooks, stream. Four instruments, not four views of one thing,
and the whole point of the experiment was to find out which one holds which fact.

**Why one session and not four.** If you ask about tokens in one session and about tool
names in another, and one of them is missing, you cannot tell whether the channel lacks
the fact or that session simply never produced it. So every scenario ran with all four
channels pointed at the same small web server, listening on the same port, at the same
moment. When a fact shows up on one channel and not another, that is now a property of
the channels.

**A real example, with the real numbers.** Scenario S8 asked for the bug to be fixed and
committed with the message E01. The agent ran `git add pkg/calc.py && git commit -m
"E01"`. Here is that single action as each channel described it. The events channel
recorded a `tool_result` with `tool_name=Bash`, `success=true`, `duration_ms=28`,
`tool_input_size_bytes=58`, and, inside a field called `tool_parameters`,
`{"bash_command":"git","full_command":"git add pkg/calc.py && git commit -m \"E01\"",
"git_commit_id":"cb10af7"}`. The hook channel received a PostToolUse call carrying the
command, the permission mode (`bypassPermissions`), the working directory, and a
`tool_response` holding git's own output plus a structured
`gitOperation.commit.sha = "cb10af7"`. The stream printed the tool call and then its
result with the same sha. The counters channel added 1 to `claude_code.commit.count` and
never mentioned which commit. Four descriptions of one `git commit`, and only three of
them can tell you which commit it was.

**How the fail-open number was measured.** The worry was that pointing an agent at a
recorder that is not running might slow it down or break it. So S2 and S6 are the same
prompt in the same fixture, differing only in that S6's receiver was not there: the
runner asks the receiver to stand down, then binds a port and lets it go, which leaves a
port with nothing behind it. S2 took 8.772 seconds, S6 took 9.685. That is 0.913 seconds
more, on a nine second session, and both exited with code 0. S6 printed one line to
standard error, 99 bytes, naming the SessionEnd hook it could not reach. Nothing else
complained. That is the whole cost of a dead recorder on this version. One caveat: this
is one pair of runs, not an average of many, so treat 0.913 seconds as "about a second"
and not as a constant.

**How the late-export number was measured, and why the answer is a null.** Monitoring
systems usually batch: they hold records for a second or a minute and send them together.
If Claude Code did that, the last records of a session could arrive after the session had
already ended, and a recorder that stops listening at the moment the process exits would
lose them. So after each session ended, the runner kept the little web server alive for
15 more seconds and wrote down the arrival time of every request. Across seven sessions,
from 4 seconds long to 183 seconds long, nothing arrived after the exit. Not one request.
The closest was 0.240 seconds before the exit. The file records this as null rather than
as 0.0, and the distinction is deliberate: "nothing arrived late" is a different sentence
from "something arrived exactly on time", and only the first one is true here.

**The answer I rejected, and what killed it.** My first instinct was to trust the
research digest for the list of things each channel emits, and to spend the sessions only
on the questions the digest could not answer. Two findings killed that. First, the digest
states in bold that there is no compaction event on the events channel. There is one:
`claude_code.compaction`, and it carries the before and after token counts, which is
exactly the number the digest sends you to the stream for. Had I trusted the digest, the
Claude provider module would have declared compaction invisible on that channel. Second,
and worse in the other direction: the events channel does carry a field called `prompt`
on the user_prompt event, even with prompt logging switched off. Its value is the literal
text `<REDACTED>`. A capability check that asks "is there a prompt field" gets "yes" and
concludes Telltale can measure prompt content. It cannot. Both of these are the same
mistake in two directions, and both were only visible by looking at bytes that actually
arrived.

**One more thing worth knowing.** There is a hook called SessionStart, and on this
version it is registered and then never called over http. The evidence is three
independent counts from the same runs: the registration record says four SessionStart
hooks exist, the execution record says three of them ran, and the web server received
zero SessionStart requests across seven sessions. Your own SessionStart hooks in
`~/.claude/settings.json`, the praxis nudge and the context handoff, are two of the three
that did run, and all of them succeeded. So a launcher cannot get a "session began"
signal over http on 2.1.257. It can get "session ended", and the stream's first line
carries the session id anyway, which is where the start belongs.
