# W0-E02 Codex capture feasibility

## OUTCOME

All four questions are answered and the fixtures exist.

The accepted `-c` spelling is the inline table, verbatim:

```
-c 'otel.exporter={ "otlp-http" = { endpoint = "http://127.0.0.1:PORT/v1/logs", protocol = "json" } }'
```

with `otel.trace_exporter` and `otel.metrics_exporter` taking the same shape and
`otel.environment="telltale-e02"` arriving as the resource attribute `env`.

Hooks fire under `codex exec`. Six of the twelve registered events fired across the seven
scenarios: SessionStart 7, UserPromptSubmit 7, PreToolUse 20, PostToolUse 19, Stop 7,
SessionEnd 7, 67 invocations in all, every one delivered to the sink and every one exiting
0. PermissionRequest, PreCompact, PostCompact, SubagentStart, SubagentStop and Interrupt
were registered and never provoked, which is not the same as never fire.

Capture is fail-open. S5 is S2's prompt with the exporter and the hook pointed at a
refused port: same exit code 0, same exec-stream shape, the same eight hooks fired, 60,837
input tokens against 60,827, and a total hook delivery cost of 0.0968 s across a 16.7 s
session.

The late-export window is zero. On all six scenarios that exported anything, the last
OTLP request reached the sink 12 to 53 ms BEFORE the child exited. The 15 second linger
caught nothing.

Seven scenarios, all exit 0, 568,665 model tokens, 180.4 s of child wall time. The S2
pilot was 20.84 s and 61,218 tokens against the owner's 5 minute / 200k token limit.

The decision write-up with every number is `docs/experiments/E02.md`; the fixtures are
`fixtures/sources/codex/0.150.1/S1..S7/`, 2.0 MB with a MANIFEST per scenario.

## WHAT WAS WRONG

**1. `--strict-config` cannot be used, and the reason is in the owner's config.** The
brief asked me to look for a config-validation flag before trusting stderr. It exists,
`codex exec --strict-config`, and it does validate `-c` overrides:
`unknown configuration field \`otel.definitely_not_a_key\` in -c/--config override`. It
also refuses the owner's `~/.codex/config.toml` at line 72, `features.multo_agent`, a key
this build does not recognise. The first S2 attempt used it and exited 1 in 0.036 s having
spent nothing. It is out of the scenario command line, and the overrides are validated
separately by running strict mode from a neutral cwd, where an override error is reported
in preference to the file error.

**2. My first probe of `--strict-config` reported the opposite, and I had to unpick why.**
To test strict mode against the owner's config without starting a session, I combined it
with a `-C` naming a directory that does not exist, on the theory that config load comes
first. It does not: the process aborts with `Error: No such file or directory (os error
2)` before reading any config. The probe therefore reported a clean load that had never
happened. `experiments/E02/config_probe.py` now runs those probes from a real cwd, and the
comment records the ordering.

**3. The OTLP endpoint is used verbatim; the exporter appends no signal path.** The
convention is a base URL plus `/v1/logs`. Codex does not follow it. Measured with two runs
differing in one argument: `endpoint = "http://127.0.0.1:PORT"` puts every request on `/`,
and `endpoint = ".../v1/logs"` puts them on `/v1/logs`. The receiver logs the request path
on every line, which is the only reason this was visible instead of an empty
`otel_logs.jsonl` blamed on the wrong TOML spelling.

**4. `model_context_window` is not where the digest says it is.** 00-digest.md 2.2 puts it
in `event_msg/token_count` under `info`. It is in `event_msg/task_started`, value 258400
on all six scenarios that wrote a rollout. `token_count.info` was null on every turn
measured here. It is single-sourced: no other surface carries it, and `--ephemeral`
removes the rollout entirely.

**5. Command output is on the OTel logs surface by default.** S3 asked the agent to `cat`
a file of fake credentials. The TELLTALEFAKE marker turns up 2 times in the exec stream, 2
in hooks, 5 in the rollout, and once in OTel logs, in the `output` attribute of a
`codex.tool_result` record. No content switch was enabled and `otel.log_user_prompt` was
left off (the prompt correctly shows `[REDACTED]`). There is a bound:
`-c otel.tool_result=false` is refused with `expected struct ToolResultLogConfig`, and
under `--strict-config` the fields `enabled` and `context_size` are rejected while
**`-c 'otel.tool_result={ max_bytes = 0 }'` is accepted**. Whether `max_bytes = 0`
actually suppresses the output NEEDS MEASURING; only the key was validated. Every OTel log
record also carries `user.account_id` and `user.email`, unconditionally.

**6. `PreToolUse` and `PostToolUse` do not pair.** S6 fired 8 against 7. Any tool-call
count that pairs them is wrong by one per session.

**7. The owner's `~/.codex/hooks.json` does not parse under Codex 0.150.1.** All seven
runs reported `failed to parse hooks config <home>/.codex/hooks.json: invalid type: map,
expected a sequence at line 3 column 4`. That file is a list of `{event, command}` objects
written by praxis; this build wants a map of event name to a list of
`{matcher?, hooks: [...]}`. **The owner's praxis Codex hooks are not running.** Reported,
not fixed: Telltale never edits that file.

**8. Hook timeouts are clamped to 3 seconds on SessionEnd and Interrupt.** With
`"timeout": 15` on all twelve events, every run emitted `clamping SessionEnd hook timeout
to 3s` and the same for Interrupt, naming the file. The other ten were left alone.

**9. `otel.trace_exporter` is not a Telltale surface, and my first reason for saying so
was wrong.** I wrote that it carries no fact the matrix asks for. Checked against the
built matrix, it carries 13 of the 21, some of them on proper `gen_ai.usage.*` attributes.
The true reason is that it carries NONE of them uniquely and charges enormously for the
duplicates: S6 produced 5707 spans in 72 seconds, 5.8 MB from one scenario, and the
sanitized fixture indexes 797,634 distinct paths against the rollout's 5,510 for 19 of the
same 21 facts.

**10. The VERIFY line `grep -rc reasoning fixtures/sources/codex | grep -v ':0' | wc -l`
cannot be 0.** Run, it is 33, and it counts FILES. Every hit is a field NAME or
manifest prose: `reasoning_effort` in 25 files, and it is how the effort row of the matrix
is observed on OTel logs; `reasoning_output_tokens` in 22, a token row on two surfaces;
`reasoning_token_count` in 13; `reasoning_summary` in 13; `model_reasoning_effort` in 6;
and 28 lines across the seven MANIFESTs describing what was stripped. The check that tests the intent is
`grep -rlE '"(agent_)?[Rr]easoning"' fixtures/sources/codex | wc -l`, which is **0**. 22
reasoning rows were dropped, from the S1 and S6 rollouts.

**11. The reasoning detector was wrong when written, and only real data showed it.** The
seven scenarios' own rollouts had few reasoning rows, so I validated the detector against
one of the owner's existing rollouts, read-only, writing to a scratch path. Counted
independently: 442 `response_item/reasoning` rows. The detector dropped 884, and the extra
442 are `event_msg/item_completed` records whose `item.type` is `Reasoning` with a capital
R. The first version of the rule matched neither `agent_reasoning` (4139 occurrences
across the six largest rollouts on this machine) nor the capitalised item type.

**12. The sanitizer left the home directory in two fixtures, because a path can be a
KEY.** `item.changes` is keyed BY the absolute path of each changed file. A scrub that
rewrites values only left `/Users/<name>/...` in the S1 and S6 rollouts after a clean run.
`rewrite_key` now applies the path rules to keys and raises on a collision rather than
silently merging two files into one.

**13. The sanitizer leaked the owner's login name, and paths were not how.** A clean
regeneration left five S6 fixture files carrying it. S6 ran `ls -la`, `ls` prints the file
owner, and `drwxr-xr-x@ 13 <name>  staff` went out on four surfaces with no home path
anywhere near it. The rules were path rules; command output is not a path. Fixed with a
bare login-name rule, and re-verified at 0 files. This is the same finding as the OTel one
above, arriving from the other direction: whatever a captured agent prints is arbitrary,
and it goes everywhere.

**14. Two repository gates went red on files this task adds, and the fix is outside my
OWNS list.** `uv run mypy .` stopped at `Duplicate module named 'pkg'` and checked nothing
at all, because every scenario copies the same fixture package to a different path under
`experiments/E02/out/`; that directory is gitignored, but mypy reads the filesystem.
`uv run deptry .` reported DEP001 for `pkg` in `experiments/E02/fixture_repo/tests/`,
which is one project's import read as another project's missing dependency. I added
`exclude` to `[tool.mypy]` and `extend_exclude` to `[tool.deptry]`, both matching
`experiments/<any>/(out|fixture_repo)/`, both with a comment naming this task and the
measurement. **This edits pyproject.toml, which W0-E02 does not own.** The patterns are
generic so W0-E01 needs no second edit, but if E01 makes the same change there is a small
conflict in that file.

## WHAT CHANGED

- `experiments/E02/run.py`. One scenario end to end: copy the fixture repo, git init and
  one commit, start the sink, write `<repo>/.codex/hooks.json` for all twelve events,
  build the argv, run with stdout and stderr to files, linger, then record wall time, exit
  code, `turn.completed` usage, per-surface request counts and the late-export window into
  `out/<S>/meta.json`. `--label` writes to `out/<S>-<label>` for a rehearsal that must not
  overwrite a scenario. `--print-otel-args` hands the spellings to the probe.
- `experiments/E02/config_probe.py`. The zero-token spelling oracle. `codex doctor --json`
  for accept or reject, `codex exec` for the verbatim message, plus the exec-only probes
  that establish what `--strict-config` does and in what order the checks run.
- `experiments/E02/hook_post.py`. The `command` hook. Reads the hook JSON on stdin, writes
  it to a LOCAL file first so a scenario with a dead sink still proves the hook fired, then
  POSTs. stdout stays empty and the exit code is always 0, because Codex parses a non-empty
  stdout as a decision document and treats exit 2 as a block.
- `experiments/E02/rollouts.py`. Finds each rollout by thread id in the FILENAME and
  confirms it against `session_meta.id` before copying. Records the path pattern, the
  `session_meta` and `turn_context` field reports and every `token_count`, keeping
  present-with-a-value, present-but-null and absent apart.
- `experiments/E02/sanitize_fixture.py`. Rewrites `out/<S>/` into
  `fixtures/sources/codex/0.150.1/<S>/`, routing the sink's `other.jsonl` into
  `otel_logs`, `otel_metrics` and `otel_traces` by the payload's one top-level key. Drops
  reasoning rows, replaces the repo path, the home directory, the bare login name,
  `user.account_id`, `user.email` and `host.name`, and placeholders five bulk fields (`base_instructions`,
  `agents_md`, `host_skills`, `permissions`, developer and system message text) keeping
  their character counts. Trims OTLP requests to 20 spans and 20 metrics each. MANIFEST.md
  per scenario with rows captured against rows kept.
- `experiments/E02/matrix.py`. Builds the matrix by indexing every JSON path, OTLP
  attribute name and OTLP attribute VALUE on each surface, then running suffix probes. The
  ambiguous probes are anchored to a parent: the first version probed `path`, `status` and
  `kind` by bare name and three cells read `observed` for facts nothing had observed.
- `experiments/E02/fixture_repo/`. `pkg/calc.py` with an unguarded `divide`, a failing
  test, `pyproject.toml`, and `secrets_note.txt` with the three TELLTALEFAKE probes.
- `fixtures/sources/codex/0.150.1/S1..S7/`, 2.0 MB, 5 surfaces plus a MANIFEST each.
- `docs/experiments/E02.md`, `docs/log/W0-E02.md`.
- `pyproject.toml`: the two excludes described in WHAT WAS WRONG 14.

## UNSURE OR NOT DONE

- **Six hook events were registered and never fired.** PermissionRequest, PreCompact,
  PostCompact, SubagentStart, SubagentStop, Interrupt. None was provoked: exec forces
  `approval_policy = "never"` (confirmed in `turn_context`), no session compacted, none
  spawned a subagent, none was interrupted. This cohort cannot tell "does not fire" from
  "was not triggered", and the matrix says `unavailable` rather than "no".
- **`otel.tool_result={ max_bytes = 0 }` is accepted but its effect is unmeasured.** The
  key survives `--strict-config`; whether it actually keeps command output off the wire
  needs one more run.
- **`otel.metrics_exporter` defaulting to statsig is carried from the digest, unmeasured.**
  I set it explicitly in every scenario and never observed the default.
- **The fail-open comparison is one pair.** S5 was 4.1 s faster than S2 on the same prompt.
  That is model-latency variance and I am not claiming capture is free; I am claiming
  nothing about the child changed, which the exit code, the event shape and the token
  counts do support.
- **`--ignore-user-config` was never used.** The brief said one scenario would need it and
  named none. No scenario needed it.
- **The trace fixture is truncated to 20 spans per request** and the metrics to 20 series,
  with the captured counts in each MANIFEST. Untrimmed, the seven scenarios are 17 MB.
- **The mypy and deptry excludes touch a file this task does not own.** See WHAT WAS
  WRONG 14. If the orchestrator would rather revert them, both gates go red on any machine
  that has run an experiment, and W0-E01 will hit the identical problem.
- **Five `codex exec` invocations ran while the account's usage limit was exhausted.** They
  spent no model tokens and are the source of the endpoint, resume and ephemeral findings.
  They are in `out/<S>-<label>/` and excluded from the matrix and the fixtures.

## NEXT

The Codex provider module (W1) has its field list, with a path for every fact and a named
surface for every gap. Three things it must be built around: `model_context_window` is
single-sourced in the rollout and vanishes under `--ephemeral`, so occupancy is `None` for
an ephemeral session and must not fall back to a constant; `PreToolUse` and `PostToolUse`
do not pair; and the sanitizer has to drop `command_execution.aggregated_output` and the
OTel `codex.tool_result.output` attribute, both of which carry arbitrary command output,
and both of which are still in the fixtures on purpose. Dropping those two fields is the
whole fix, and the login-name leak is why: a redaction pass over command output that
matches patterns rather than removing the field will keep missing things, because what a
command prints is not a shape.

The launcher needs no shutdown grace period for Codex and it must point each exporter at
the full signal path. It must not pass `--strict-config`.

Two things belong to the orchestrator rather than to me. The owner's praxis Codex hooks
are silently not running, which is a fact about the owner's machine and not about
Telltale. And the pyproject.toml excludes need a decision.

## EXPLAIN FOR THE OWNER

A recorder that changes what it records is not a recorder. Everything below is downstream
of that one sentence, and most of the work was finding the places where it nearly stopped
being true.

### The thing that had to be settled first

Codex can be told to send telemetry to a local address. The documentation names the
settings but not their shape, and the shape matters because the setting is not a string.
Written out, the value Codex wants is a small table nested inside another table, and the
short spelling that looks obvious is refused:

```
-c otel.exporter="otlp-http"
```
```
Error loading config.toml: invalid type: unit variant, expected struct variant
in `otel.exporter`
```

The one that works carries the whole configuration inline:

```
-c 'otel.exporter={ "otlp-http" = { endpoint = "http://127.0.0.1:PORT/v1/logs", protocol = "json" } }'
```

Finding that out normally costs a session per attempt, and sessions here come out of your
subscription. It did not, because `codex doctor` loads exactly the same configuration file
and never talks to a model. Six candidate spellings were tested for nothing.

### The example worth having, with the real values

Scenario S3 asks the agent to print a file. The file is bait: it holds three fake
credentials, each carrying the marker TELLTALEFAKE so that no scanner ever confuses them
for real ones, and their only job is to be followed through the plumbing. Counting where
the marker ends up:

- the JSON stream Codex prints: 2 times
- the hooks: 2 times
- the rollout file on disk: 5 times
- the telemetry sent over the network: **1 time**

The last one is the finding. The telemetry record is called `codex.tool_result` and it has
an attribute called `output`, which holds what the command printed. Nothing was switched
on to make that happen. The prompt itself is redacted by default, correctly, and the
command's output is not. So a receiver listening to a Codex session receives whatever that
session's commands print, which on a real machine is logs, environment dumps and
occasionally a key.

There is a control, and it is not the obvious one. Turning the whole thing off with a
plain `false` is refused, because the setting is a small table rather than a switch. Codex
also rejects the two field names I guessed. The one it accepts is
`otel.tool_result = { max_bytes = 0 }`. I have confirmed Codex accepts that key. I have
not confirmed it silences the output, and I have written that down as needing one more
measurement rather than reporting it as done.

### How each number was measured

**The cost of capture.** Two runs, same prompt, same fixture. One with the receiver
listening, one with it pointed at a port where nothing is running so the connection is
refused outright. The recorded session finished the same way both times: exit code 0, the
same shape of output, the same eight hook calls, 60,837 input tokens against 60,827. The
refused connections cost about twelve milliseconds each, and eight of them across a
seventeen-second session is under one percent. The closed-port run was actually the faster
of the two, which is the model varying rather than anything I did, and the report says so.

**How long a receiver must wait.** The design assumed telemetry keeps arriving for a few
seconds after the agent exits, so the launcher would have to keep listening. Measured, the
opposite is true: on all six sessions that sent anything, the last packet arrived between
12 and 53 milliseconds BEFORE the process exited. Codex flushes and then leaves. The
experiment still waits fifteen seconds after every run, and catching nothing in that
window seven times is what makes the number a measurement rather than an assumption.

**The size of one decision, and the first answer being wrong.** Codex can also emit
traces. Turning them on produced 5,707 of them in a 72-second session, 5.8 MB, and they
are the internal machinery of the program itself, function by function, with source file
names and nanosecond timings. I wrote that none of them answers a question this project
asks, and that was a guess dressed as an observation: the matrix was already built and I
had not looked. Looked at, traces answer 13 of the 21 questions, some on the proper
`gen_ai.usage.*` attribute names. What is true is narrower and is the actual reason.
Traces answer nothing that the rollout or the exec stream does not already answer, and the
rollout answers 19 of 21 while indexing 5,510 distinct paths where traces index 797,634.
Paying 145 times the size for strictly less is not a trade, and that is why traces are
measured in the write-up and are not one of the four surfaces.

### The answer I rejected, and why

There is a flag, `--strict-config`, that turns a misspelled setting from a silent no-op
into a loud error. That is exactly what a recorder wants: if I typo the telemetry key, I
want a failure, not an empty file I spend an hour misdiagnosing. I put it in.

The first real run exited in 36 milliseconds:

```
/Users/wumpinihussein/.codex/config.toml:72:1: unknown configuration field `features.multo_agent`
```

Your own configuration file contains a setting this version of Codex does not know about.
Strict mode refuses the entire file, so the flag that protects Telltale from its own typo
also stops Telltale running on your machine. It is out. The safety it offered is bought
back a different way: the settings are validated under strict mode from an empty
directory, where an error in the command-line settings is reported ahead of the error in
your file, so I can still prove the keys are recognised without ever passing the flag
during a real capture.

That episode is also why the report says what it says about `features.multo_agent` and
about a second file. Your `~/.codex/hooks.json`, the one praxis writes, does not parse
under this version of Codex either. Every one of the seven runs said so:

```
failed to parse hooks config ~/.codex/hooks.json: invalid type: map, expected a sequence
```

Codex 0.150.1 expects that file in the format Claude Code uses; praxis writes an older
one. Those hooks are not running, and have not been for some time. Telltale does not touch
files outside its own repository, so this is reported and left alone. It seemed worth
knowing.
