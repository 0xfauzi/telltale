# W0-T1 bootstrap

## OUTCOME

The repository exists, every gate runs, and CI is green. `0xfauzi/telltale` is private on
GitHub with two commits on `main`; the first CI run passed in 150 seconds with every cache
cold and the second passed in 27 seconds warm. Locally: `uv sync` installs 30 packages,
`uv run telltale --version` prints `0.0.1`, `uv run pytest -m integration` is 1 passed,
`uv run mypy .` finds no issues in 8 files, `uv run ruff check .` and `ruff format --check .`
are clean, `uv run deptry .` is clean, and `pre-commit run --all-files` is 29 passed, 3
skipped for having no matching files, 0 failed. Both refusal probes fire and name the
offending file: a test outside `tests/integration/` makes pytest exit 4, and a model-stack
import outside `forecast/timesfm.py` fails the `forecast-isolation` hook.

Six things in the brief turned out to be wrong or incomplete when run. They are below, with
what replaced them.

## WHAT WAS WRONG

**1. `pep621_dev_dependency_groups = ["dev"]` does nothing here, and deptry is withdrawing
it.** The brief specified this line. Run, deptry 0.25.1 answers: `Warning: Trying to extract
the dependencies from the optional dependency groups ['dev'] as development dependencies,
but the following groups were not found: ['dev']`, plus a second warning that the option is
being discontinued. It names groups in `[project.optional-dependencies]`, which here are
`forecast` and `export`. The `dev` group lives in `[dependency-groups]`, which is PEP 735,
and deptry already reads that as development dependencies: measured, none of pytest, ruff,
mypy, deptry, codespell, vulture, pre-commit or pytest-timeout is reported as an unused
dependency, which is exactly what would happen if they were being read as runtime ones. The
line is not in pyproject.toml, and the comment in `[tool.deptry]` records this measurement
so the next reader does not add it back.

**2. deptry called the package's own name a transitive dependency.** `from telltale import
__version__` in `src/telltale/cli.py` reported DEP003, because `uv sync` installs the
project into `.venv` like any other distribution. Fixed with `known_first_party =
["telltale"]`, which is the mechanism deptry provides for it, and which every later absolute
import needs.

**3. deptry called the four extras unused, which they are, for now.** numpy, torch, timesfm
and pyarrow are declared and nothing imports them, because the modules that will are in
later waves. They are in `per_rule_ignores.DEP002` with a comment naming the task that
retires each entry. This is the one piece of config here that is a promise rather than a
rule, and it is written so a stale entry is visible.

**4. `ruff format .` rewrites Python inside Markdown fences.** Measured with ruff 0.16.5: it
reformatted the dataclass listing in `docs/design/01-design.md`, which is a verbatim copy of
the approved plan and carries a header saying so. The pre-commit ruff hooks never saw it,
because they pass only python, pyi and jupyter files, so this was visible only in the
documented local command `ruff check --fix . && ruff format .`. `docs` is now in ruff's
`extend-exclude` with the reason: everything under it is a copy of an approved source, a
conversion of the owner's specification, or a record of a run that already happened.

**5. `check-added-large-files` refuses the specification document, and the shared block is
not mine to edit.** `docs/spec/telltale-architecture.docx` is 890 KB against the hook's 500
KB cap. The shared pre-commit block is copied byte-identical from deckgen by instruction,
and its excludes are deckgen's to change. The docx is committed because it is the authority
behind the Markdown conversion beside it. So the first commit, and only that commit, was
made with `SKIP=check-added-large-files`, which skips that one hook and runs the other 31.
This is safe to leave as it is: the hook inspects only files ADDED by the commit in
progress, so it is live again from the second commit onwards, and on CI it passes because a
fresh checkout has nothing staged. It is not free, either. If a second oversized file is
ever added deliberately, somebody has to make this decision again with no record in the
config to prompt them. **The standing decision for the orchestrator: either
`docs/spec/.*\.docx$` joins the shared exclude in every repository that copies the block, or
this stays a one-time skip recorded here.**

**6. The conftest hook as specified cannot fire on the command everybody runs.** The brief
asked for `pytest_collect_file` or `pytest_ignore_collect` in
`tests/integration/conftest.py`. Both are called only for paths under the directory that
owns the conftest, and `testpaths = ["tests/integration"]` means a bare `uv run pytest` never
descends into `tests/` at all. Measured: with a stray `tests/test_probe.py` present, the
collect hook alone lets the run finish green. `pytest_configure` runs once per session
whatever the collection roots are, so the file now scans `tests/` there and raises the
UsageError. The collect hook is kept for `pytest tests/`, where it names the file the moment
pytest opens it. Probe result: `uv run pytest` exits 4 with
`ERROR: tests live under tests/integration/ only; move or delete: tests/test_probe.py`.

Three smaller findings, none of which needed a change:

**`uv run mypy .` prints a note, not an error.** `pyproject.toml: note: unused section(s):
module = ['pyarrow.*', 'timesfm3.*', 'torch.*']`, because `warn_unused_configs = true` and
no module imports those yet. Exit code 0. The note disappears when
`src/telltale/forecast/timesfm.py` lands. Reported here so nobody deletes the overrides to
silence it.

**`pre-commit run --all-files` does not see a file git does not know about.** This matters
to anyone re-running the VERIFY lines of this task. The probe for `forecast-isolation`
writes `src/telltale/store.py` and runs pre-commit. Measured both ways: with the file merely
created, the run exits 0 and the hook reports Passed, because `--all-files` means every file
in the index rather than every file on disk. With `git add -N src/telltale/store.py` first,
the same run exits 1 and reports `src/telltale/store.py:1:import torch`. A probe that skips
the `git add` reads as a broken hook.

**Inside one `pre-commit run --all-files`, ruff's autofix can remove the line a later hook
looks for.** The probe put `import torch` in `src/telltale/store.py`; `ruff-check --fix`
deleted it as an unused import before `forecast-isolation` ran, so that run failed on ruff
rather than on the invariant hook. Run alone, `forecast-isolation` reports
`src/telltale/store.py:1:import torch` and fails. The gate is not weakened, because the two
outcomes are the only two: either the import is used and ruff leaves it for the hook to
catch, or it is unused and ruff deletes it, which also satisfies the invariant.

## UNSURE OR NOT DONE

- **The one-time `SKIP`.** Recorded above as a standing decision for the orchestrator. I did
  not edit the shared block, and I did not create a second mechanism to work around it.
- **Two ruff versions are in play.** `uv run ruff` is 0.16.5 from the lock; the ruff
  pre-commit hook pins v0.16.4. They agree on this tree today, measured: both `ruff format
  --check .` and the `ruff-format` hook pass. They could disagree after any release, and the
  failure would look like two gates fighting over the same file. Pinning the dev-group ruff
  to the hook's rev would end it; I did not, because deckgen does not, and matching the
  model was the instruction.
- **The `DEP004 = ["pytest"]` entry is dormant.** deptry's default exclude drops `tests`, so
  the 6 files it scans are `src/` and `scripts/precommit/` only. The entry is correct the
  day this file sets its own `extend_exclude`, and does nothing before then.
- **`mypy` has no `platform` setting.** deckgen pins `platform = "linux"` because its CI is
  the environment that matters and a darwin-only branch reads as reachable locally and
  unreachable on CI. Telltale is the other way round: the launcher runs on the owner's Mac,
  so pinning to linux would hide the branches that actually run. Left out deliberately, and
  worth revisiting when `launch.py` grows its first `sys.platform` comparison.
- **Dependabot has already opened PR #1** (`Bump astral-sh/setup-uv from 10.0.0 to 10.0.1`)
  and its CI run is green. I did not merge it; moving a pinned action SHA is a decision for
  the orchestrator, and the 7-day cooldown in the config is the reason to check the release
  date before taking it.
- **`uv audit` is a preview feature.** It passes today (`no known vulnerabilities ... in 70
  packages`) and the CI step carries `--preview-features audit-command`. If a uv release
  changes the flag, the step breaks and should be fixed rather than deleted.
- **Not measured: whether the 500 KB cap ever fires again.** Only one file has exceeded it.

## EXPLAIN FOR THE OWNER

A repository that starts green is a repository where the next person's first red is their
own fault. That is the whole point of this task, and it is worth thirty seconds on why it
was not just copying files: five of the eight configuration decisions changed after I ran
them.

### The thing that had to be decided first

Everything else waited on one question: what is this package allowed to depend on? Telltale
runs beside a coding agent while that agent works. If Telltale imports a large library, the
agent's session pays for it, in start-up time and in memory, every single time. So the
runtime dependency list is empty, and the standard library does all the recording: the
database, the small web server that receives the telemetry, the JSON, the hashing.

That decision then wrote most of the rest of the file. The forecasting library, which is
large, sits behind an optional install, and one pre-commit hook (a check that runs before
every commit) greps the source for the line that would import it and fails if that line
appears outside the single file allowed to have it. The rule and its enforcement arrived
together, which is the pattern the owner asked for: a rule with no mechanism is a wish.

### The example worth having

Here is one real case, with the real values. The gate configuration was copied from deckgen,
the owner's other repository, on the reasonable theory that it was already thought through.
One line said `pep621_dev_dependency_groups = ["dev"]`. I ran the tool. It said: the group
`dev` was not found. That option looks at a different table in the file from the one this
project uses, and the tool is in the middle of withdrawing it anyway. The setting was doing
nothing except printing two warnings.

The interesting part is what proved that the tool was already doing the right thing without
it. If the eight development tools (pytest, ruff, mypy and the rest) were being read as
production dependencies, the tool would have reported all eight as declared-but-never-used.
It reported none. That is the measurement, and it took one command. The line is gone and the
comment in its place records the finding, so the next person who copies from deckgen does
not add it back.

The same shape happened four more times: a formatter that quietly rewrites Python code
inside Markdown documents (it edited a document that says "verbatim copy" at the top), a
dependency checker that thinks the project is a third-party package, a spell checker that
thinks the statistical term WQS is a misspelling of "was", and a test-placement rule that
could not possibly fire on the command people actually type. Each was found by running the
thing rather than by reading it.

### The one I could not fix cleanly

The specification document, the Word file, is 890 KB. One of the shared hooks refuses any
newly added file over 500 KB, and that hook's configuration is shared byte for byte with the
owner's other repositories, so it is not this repository's to edit. The Word file has to be
committed: it is the authority, and the Markdown beside it is only a conversion.

So the first commit skipped that one hook, by name, and the other 31 ran. This is safe in a
specific way that is worth knowing rather than trusting: that hook only ever looks at files
being added by the commit in front of it. From the second commit onwards it is fully live,
and on the server it passes because a fresh checkout has nothing staged. What it costs is a
decision with no home: nothing in the configuration will remind the next person that this
happened, which is why it is written here twice. The alternative I rejected was editing the
shared block to name this file. That would have worked today and quietly broken the property
the shared block exists for, which is that `diff` between any two of the owner's repositories
prints only their own hooks.

### How long it takes, and how I know

The first run of the checks on GitHub took 150 seconds. 125 of those seconds are two tools,
actionlint and gitleaks, being compiled from source the first time; the numbers come from
the run's own step timings (run 33550237068, job 99997595689), not from a stopwatch. The
second run, with those two cached, took 27 seconds. Everything this repository actually
owns is a rounding error at either extreme: types 3 seconds, lint under 1, the test suite 0.

The time limit on the job stays at 15 minutes, which is six times the slow case. That number
is not a budget or a target. It is the point at which a run that has hung should be killed
rather than billed, and the comment in the workflow now says that in place of the word
"provisional".

### What I am not sure about

Two versions of the linter are in the tree: the one the hook pins, and the one the lock
resolves. They agree today, and I checked rather than assumed. They can disagree after any
release, and the symptom would be confusing: two gates disagreeing about the same file.
Pinning them together would end it. I left them apart because deckgen leaves them apart, and
matching deckgen was the instruction. That one is a judgement, and somebody could reasonably
differ.
