## WHAT WAS WRONG

**1. Two of the four files could not fit under the 800-line hook as written.** First pass:
`store.py` 966 lines, `sanitize.py` 806. The file-length ratchet fails any file a commit
ADDS above 800, and the brief fixes the module list, so splitting was not available. Two
of the three compressions were worth having on their own merits. The column list of each
table is now `tuple(f.name for f in fields(Observation))` rather than a hand-written
tuple, which removed 25 lines and removed a defect class with them: one tuple now drives
both the INSERT text and the row values, so they cannot disagree, and a field added to a
shape with no column added to the table fails at the first write instead of vanishing.
The five INSERT statements are generated from those tuples for the same reason. The third
compression was ordinary prose trimming. Final: `store.py` 798, `sanitize.py` 799. That
is tight, and the next task that adds to either has to split it first: the natural cut in
`store.py` is the 110-line `--selfcheck` block, and in `sanitize.py` the 300-line
allowlist.

**2. A single lone UTF-16 surrogate killed the writer thread, silently.** Measured, not
reasoned. `json.loads('{"e": "\\ud800"}')` is legal and produces a string that sqlite3
cannot encode. `_run_batch` caught `sqlite3.Error`, and `UnicodeEncodeError` is not one,
so the exception left the writer loop, the thread died, and `append()` went on reporting
success into a queue nobody drained: `stored 0, diagnostics []` with the process still
running. That is precisely the failure spec 5.2 forbids. Two changes. The writer now
catches `Exception`, with the measurement in the comment beside it. The sanitizer now
guarantees every string it emits is UTF-8 encodable, replacing what is not and recording
`field:encoding` in `redaction.redacted`; the check is `str.isascii()` first, which is the
fast path almost every provider string takes.

**3. One bad row took its whole transaction with it.** Batching up to 500 jobs per
transaction (design 6.5) means one row SQLite refuses loses the other 499. That is
tolerable for a hostile string but not for what will actually cause it: a STRICT type
violation from a provider module written in wave 1. After the retry schedule is exhausted
the writer now replays the batch one job at a time, so one bad row costs one row, and the
diagnostic names every DISTINCT failure in the batch. Measured on a batch of three
carrying two different faults: `2/3 failed: IntegrityError: UNIQUE constraint failed:
observations.observation_id; UnicodeEncodeError: 'utf-8' codec can't encode character
'\ud800'`, one row stored, writer alive.

**4. `shlex.split` does not split `ls;pwd`.** Design 6.4 says shlex-split, then split on
`|`, `&&`, `||` and `;`. Done in that order, `ls;pwd` comes back as the single token
`ls;pwd` and a second command hides inside the first; done in the other order, splitting
the raw string cuts inside quotes, and `echo "a;b"` becomes two commands. Measured:
`shlex.shlex(text, posix=True, punctuation_chars=True)` with `whitespace_split = True`
gives `['ls', ';', 'pwd']` for the first and `['echo', 'a;b']` for the second, which is
the only spelling that gets both right.

**5. "fallback: one token" has two readings and one of them stores the command
verbatim.** Design 6.4 says shlex-split with "fallback: one token" for a line it refuses,
which an unbalanced quote produces. Read as "the whole line is the token", the normal form
of `echo "unbalanced` is `echo "unbalanced`, which is the raw text the normal form exists
to prevent. This implementation takes the executable basename and an underscore if
anything followed it: `echo _`, under `normalization_version = "cmdnorm-v1-fallback"` so
it is never compared against a command that parsed.

**6. A trailing slash is load-bearing, and path normalization ate it.** Measured after
writing the classifier: `python -m pytest -q tests/` classified as scope `full`. Path
normalization turns `tests/` into `tests`, `classify` reads only the normal form, and
`tests` with no slash is indistinguishable from a subcommand. The normalizer now restores
a trailing slash the input had. `python -m pytest -q tests/` is now `('test',
'targeted')`.

**7. Design 11.1 and 6.4 disagree about commands at level 0.** The content-level table in
spec 11.1 excludes commands entirely at level 0; design 6.4 says level 0 "keeps only the
basenames". Taken: 6.4, because it is the sanitizer's own specification and the more
specific rule, and because an executable basename is the name of a program rather than
content. `uv run pytest tests/x.py && git status` at level 0 is `uv && git`. Flagged here
rather than resolved silently.

**8. The STOP check, written out.** Design 6.3's field list for a Claude `tool_result`
with `OTEL_LOG_TOOL_DETAILS=1` includes `tool_parameters` and `tool_input` (digest 2.1),
and 6.4 says edit contents and tool_response bodies are never persisted. That reads like
the conflict the brief says to stop on, and it is not one, because 6.3 resolves it in its
own next paragraph: a `git_commit_id` is taken FROM `tool_parameters` and kept, and a Bash
exit code is derived from the result text BEFORE the text is dropped. So the container is
never an allowlisted field and never reaches the sanitizer: the provider parser lifts the
named scalar out of it, `git_commit_id` and `exit_code` are allowlisted, and
`tool_parameters`, `tool_input`, `tool_response` and `tool_result` are all in
NEVER_PERSIST, which is checked at every depth of the payload after the allowlist. The
same move is why `codex.exec.error` allowlists `error` and not `message`.

**9. `value REAL` means an integer metric reads back as a float.** Design 6.5 fixes the
column type. `Evidence.derived(metric="model_requests", value=2)` comes back from the
store as `2.0`. Measured, and left as the design has it; `report.py` will need to format
from the unit rather than from the Python type.

**10. `Activity.claim_class` has no column to live in.** The dataclass in 6.2 carries
`claim_class: str = "derived"`; the activities table in 6.5 has no such column. Storing it
was not an option (that is the design's table) and dropping it silently would mean an
Activity built with any other value round-trips as `derived`. So `Activity.__post_init__`
refuses any value but `derived`, which is also what invariant 1 says an activity is.

**11. The `captures` view asks for two facts that are not per-row.** 6.5 gives the view
the columns `capture_id, provider, repo_id, first_ts, last_ts, observation_count`, but
provider and repo_id belong to the capture while the rows carry them individually, and
`repo_id` is legitimately NULL on some observations of a capture with a repository.
Grouping by them would split one capture into two rows. The view takes provider from the
earliest observation (observation_id is arrival order) and the first non-null repo_id, and
says so in a comment beside the SQL.

## WHAT CHANGED

**`src/telltale/model.py` (310 lines).** The five dataclasses of design 6.2 plus `RowMeta`
and `ColumnSpec`, `ulid()`, `new_id(prefix)`, `now_iso()`, `to_json`/`from_json`,
`CLAIM_CLASSES` and `COVERAGE`.

`ulid()` is 26 Crockford base32 characters: 48 bits of millisecond time and 80 bits of
randomness, where the randomness is a COUNTER inside one millisecond rather than a fresh
draw, under a lock. Without the counter two observations recorded in the same millisecond
by two request threads sort in random order, and the observation id IS the arrival order.
The millisecond is `max(now, last)`, so a clock step backwards cannot produce an id that
sorts before one already handed out.

`Evidence` has four constructors, `derived`, `comparative`, `associative` and
`predictive`, and no others. `__post_init__` rejects a claim class outside the four
(so `causal` and `observed` are refused by construction, not by review), rejects a coverage
outside the four, and rejects an empty source list unless coverage is `unavailable`, which
is the one case where there is nothing to point at.

**`src/telltale/store.py` (798 lines).** Six STRICT tables, one view, three indexes on
observations and one on activities, WAL, `synchronous = NORMAL`, `busy_timeout = 5000`.
One writer thread owning one connection; readers open their own `file:...?mode=ro` URI
connection per call. `append` builds the row tuples on the calling thread and hands one
job to a `queue.Queue(maxsize=10000)`; a batch whose observation types are all droppable
is dropped the moment `put_nowait` fails, anything else waits `put(timeout=0.25)`. Drops
increment a per-surface counter, which the writer flushes as one `dropped` diagnostics row
when the queue drains, and a second cumulative counter that `health()` reports and nothing
clears. The writer takes one item, drains up to 500 more, and commits them in one
transaction, retrying a failed transaction five times over about 1.5 s before replaying it
job by job. `Store.reducers` is the registration list `rebuild` walks in order.
`pause_writer()` and `resume_writer()` are named TEST-ONLY in their docstrings and exist
for W0-T5's fail-open test.

**`src/telltale/sanitize.py` (799 lines).** `Kind`, `ALLOWLIST` (60 observation types),
`NEVER_PERSIST`, `sanitize`, `relativize`, `scrub`. Three gates in order: the allowlist
(an unlisted field is dropped and its name returned for an `unknown_field` diagnostic),
the per-Kind clean (a path is made repo-relative or hashed, a command normalized, a string
scrubbed and bounded), and NEVER_PERSIST at every depth of the payload whatever the
allowlist says. Nothing here touches the filesystem, because it runs on the receiver's
request thread.

**`src/telltale/commands.py` (310 lines).** `normalize` and its two version constants,
`classify` and `CLASSIFIER_VERSION`. The classifier version is the hash of the rule table
rather than a literal somebody remembers to bump: `commands-v1-38ab5066`. Hashing the
table and not the source file is deliberate, so that editing a comment does not invalidate
every golden file while editing a rule does.

## UNSURE OR NOT DONE

  quoted above and the gates. Each behaviour claim in this report has a command behind it.
- **Provider field names are partly from the digest and partly guessed.** The attribute
  lists for `claude.otel.permission_mode_changed`, `claude.otel.mcp_server_connection` and
  the codex item types are not in any document I have; they are named plausibly and marked
  for E01 and E02 to correct. A wrong guess costs a dropped field and an `unknown_field`
  diagnostic, never a silent persist, which is the whole point of failing closed.
- **Three type families have no allowlist entry at all:** `codex.otel.*` (E02 fixes the
  vocabulary), `claude.transcript.*` and `codex.rollout.*` (wave 2 backfill). Until they
  have one, every field of those types is dropped and reported.
- **`MAX_ITEMS = 256` and `MAX_DEPTH = 6` are decisions, not measurements.** Design 6.4
  bounds strings and payloads and says nothing about containers.
- **The 8 KB payload bound drops a large `per_file` list whole.** Measured: a
  `telltale.repo.snapshot` with 400 per-file entries keeps `files_changed` and loses
  `per_file` entirely, recorded as `per_file:items` and `per_file:payload_bound`. Dropping
  the field beats keeping a prefix, because a reducer that sees 100 of 400 entries can
  compute a confident wrong number while one that sees none cannot. W1's repository
  observer needs to know that per-file detail does not survive a large change.
- **Scope is computed for test commands only**, which is what 6.10 says. `pytest tests`
  without a trailing slash reads as `full`, because nothing in the normal form marks
  `tests` as a path.
- **The secret patterns are exactly the design's list.** `ASIA...` (AWS temporary
  credentials, the same shape as `AKIA...`) is not covered. Widening a redactor is safe;
  I did not do it because the list is the contract W0-T5 tests against.
- **`store.py` and `sanitize.py` sit one and two lines under the file-length gate.**
- **The retry schedule (0.05, 0.1, 0.2, 0.4, 0.8 s) and the 30 s synchronous-write

  measurement that would justify them is how long a competing writer holds a lock on this

## EXPLAIN FOR THE OWNER

### Why any of this exists

Telltale records another program while it runs. That single sentence sets every hard
constraint in these four files. The recorder shares a machine with an agent that is doing
real work, so it may not make that agent wait; it receives text written by a model that
had credentials in its environment, so it may not store what it is handed; and it is
supposed to be believed later, so a number it prints has to be traceable to something
observed. Four files, one for each of those problems and one to hold the shapes they all
pass around.

### The first question: what can two threads agree on

Everything else waits on this one. Observations arrive on several HTTP connections at
once, and SQLite lets one connection write at a time. So the work splits: the thread that
took the request does the reading and cleaning, then hands a finished batch to a queue,
and one writer thread does nothing but drain that queue.

A queue with no bound is a memory leak with a polite name, so this one holds 10000
batches. That means it can be full, and what happens then is a decision rather than an
accident. Some observations can be lost without losing information: a metric is a rollup
of events already stored, so it is dropped immediately rather than making the agent wait.
Everything else waits up to a quarter of a second for room and is then dropped too, which
is the promise that no request thread is ever blocked longer than that.

Here is the part that matters more than the dropping. A drop nobody counted is
indistinguishable from a quiet session. So each drop increments a counter for the surface
it came from, and when the queue next empties the writer puts one row in the database
saying so. Held the writer still and pushed 10051 batches at it, the 51 that did not fit
produced exactly one row: `{"per_surface":{"otel_metrics":51},"total":51}`. One row, not
51, because a flood of drops that floods the diagnostics table is its own kind of lying.

### The bug I would not have found by reading

The writer caught database errors and retried them. Reasonable, and wrong, and I only know
that because I fed it a hostile string on purpose.

JSON permits `"\ud800"`, half of a character. Python's `json.loads` hands back a string
holding that half, and sqlite3 refuses to encode it: `UnicodeEncodeError`, which is not a
database error, so it went straight past the retry logic, out of the writer loop, and
killed the thread. The store then accepted everything it was given and stored none of it.
The probe printed `stored 0, diagnostics []` with the process still happily running.

That is the exact failure mode this whole design is supposed to make impossible, and it
survived my own review of my own code. Two fixes: the writer now catches every exception,
and the sanitizer guarantees the strings it emits can be encoded at all, replacing what
cannot and recording that it did.

While fixing it I noticed a second thing. Jobs commit in batches of up to 500, so one row
SQLite refuses used to lose the other 499. The likely cause is not a hostile string, it is
a provider module written next month putting a float where the schema says integer. So
when a batch fails, the writer now replays it one job at a time, and the diagnostic names
each distinct reason. On a batch of three carrying two different faults, one row survived
and both reasons were recorded.

### The second question: what is safe to keep

The rule is an allowlist, not a blocklist. A named list of what may be stored per event
type, and anything not on it is dropped and its name recorded so somebody can notice the
provider changed. A blocklist has to predict the next field Anthropic adds; an allowlist
does not.

A real example, all four hazards in one payload. A Claude tool result arrives carrying the
prompt text, an error message with an API key in it, the absolute path
`/Users/wumpinihussein/.ssh/config`, and a field called `brand_new_field` that no version
of this code has heard of. What is stored:

```
{'tool_name': 'Bash', 'error_type': 'auth <redacted:1>', 'file_path': '<outside>/af7edc17'}
dropped:  ['prompt:never_persist', 'brand_new_field:unknown']
redacted: ['error_type']
unknown:  ['brand_new_field']
```

The prompt is gone and the record says why. The key is gone and the record says one thing
was removed from that field. The path is gone, but not entirely: `<outside>/af7edc17` is
the same eight characters every time that same directory appears, so "the agent read four
files somewhere outside the repository" is still a fact you can see, while the place is
not. A path inside the repository keeps its relative name, because that is the
engineering fact the whole system is for. The home directory never survives either way.
And the unknown field is named, so the next person knows the parser is behind its
provider.

The third gate is the one that matters when the first is wrong. A set of field names,
`prompt`, `content`, `old_string`, `tool_response`, `aggregated_output` and the rest, is
removed at every depth of every payload whatever the allowlist says. If somebody adds
`content` to the allowlist by mistake next year, it still does not get stored.

### The third question: when are two commands the same command

Verification cycles are a headline measure, and counting them means deciding that this
pytest run and that one are the same kind of thing. Storing the command line does that
and also stores a search string, a filename and possibly a token. So a command is reduced
to a normal form: the executable, up to two subcommand words, the flags with their values
stripped, paths made repo-relative, and an underscore for everything else.

`uv run pytest tests/test_calc.py -k zero && git status`
becomes
`uv run pytest tests/test_calc.py -k _ && git status`.

Two runs against different test names now produce the same string, `-k _` records that the
run was narrowed without recording to what, and the classifier reads that string and
answers `test`, scope `targeted`.

Two things I got wrong here, both found by running it rather than reading it. Python's
`shlex.split`, which the design names, leaves `ls;pwd` as one token, so a second command
hides inside the first; the fix is `shlex.shlex` with `punctuation_chars`, which separates
the operators and still does not cut inside quotes. And path normalization was quietly
turning `tests/` into `tests`, after which the classifier could no longer tell a directory
from a subcommand and called `python -m pytest tests/` a full run. The trailing slash is
now preserved because it is load-bearing.

### What I decided rather than measured, and where the numbers are not mine

The retry delays (0.05 to 0.8 seconds), the container bound of 256 items and the depth
bound of 6 are decisions. They are marked as decisions in the code, next to what happens
when they bind. The numbers that came from the design (10000 queue slots, 500 rows per
transaction, 250 ms of waiting, 512 characters per string, 8 KB per payload, 200
characters per command) are the design's, and the code names the section they came from so
you can change one place.

One consequence you should know about, because it will surprise somebody in wave 1. The 8
KB payload bound is enforced by dropping whole fields, largest first. A repository
snapshot of a 400-file change therefore keeps `files_changed: 400` and loses the per-file
list entirely, and says so in the record. I chose that over keeping the first hundred
entries, because a reducer that sees 100 of 400 files can compute a confident wrong number
and one that sees none cannot.

### The one thing the design and the specification disagree about

Spec 11.1's table says level 0 stores no commands. Design 6.4 says level 0 keeps the
basenames. I took 6.4, since it is the sanitizer's own section and the more specific rule,
and an executable name is not content: at level 0, `uv run pytest tests/x.py && git
status` is stored as `uv && git`. It is written down here rather than settled quietly,
because it is your call and not mine.
