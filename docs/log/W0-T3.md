returning a plain JSON-serializable payload dict in the field names of design 6.3:
`identity`, `snapshot`, `Debouncer`, `commits_since`, `overlaps`, `fingerprint`. Neither
module imports `telltale.model`, opens a store, or lets a patch body out: what leaves is
counts, repo-relative paths and sha256 hashes.

## WHAT WAS WRONG

**1. A numstat parser that silently answered zero.** `_commit_stats` ran
`git diff-tree --numstat` without `-z`. The parser splits on NUL, git separated the
records with newlines, no NUL was found, and the function returned an empty list. A
commit that changed three files reported `files_changed 0, additions 0, deletions 0`,
with no error anywhere. It was caught by a probe assertion that a linked commit's numbers
must equal the numbers of the snapshot it matched. The fix is not the missing flag: every
numstat view now goes through one `_numstat` helper that appends `--numstat -z` itself,
so a caller cannot leave it off. This is exactly the failure AGENTS.md names, absence
converted into a confident zero, and it was in the code for about an hour.

**2. An empty repository hashed the same as a clean checkout.** `dirty_tree_hash` was
defined as sha256 of the numstat plus the status. With no HEAD there is no numstat, so
the numstat half was empty bytes, and a fresh `git init` and a clean clone of this
repository both produced `6e340b9cffb37a98...`. Measured, not reasoned: V3 printed the
same hash V1 did. Those are two different states, "there is nothing to compare against"
and "nothing differs", and the whole system turns on keeping them apart. With no HEAD the
hashed left half is now the marker `<no-head>`, and the empty repository gives
`c07f7969...`. No real numstat can equal the marker, because a numstat record always
carries tabs and a NUL.

**3. worktree_id is not unique, and `overlaps` cannot be keyed on it alone.** Design 6.8
defines worktree_id as the sha256 of the git dir relative to the common dir. For the main
worktree of any repository that path is ".", so every main worktree everywhere has
worktree_id `cdb4ee2aea69cc6a8...`: measured, a fresh `git init` and a clone of this
repository agree on it (V2 and V3 above). The brief says `overlaps` returns pairs "on the
same worktree_id"; keyed that way it would report two captures in two unrelated
repositories as concurrent on one worktree, which is an invented attribution inside the
one function whose job is to refuse to invent attribution (spec 12.4). `overlaps` reads
`repo_id` as well and groups on the pair. The payload field is unchanged, so this is a
requirement on the caller: a capture record passed to `overlaps` must carry both ids.

**4. `git rev-parse HEAD` prints "HEAD" on stdout and exits 128 in a repository with no
commits.** Reading stdout alone would have recorded the word HEAD as a commit sha. Every
helper here decides on the exit code and returns None on any non-zero, which is why V3
gives `head: null` rather than a string.

**5. `Debouncer(seconds=2.0, fn)` cannot be written in Python.** A parameter with a
default cannot precede one without. The class is `Debouncer(fn, seconds=2.0)`.

**6. `commits_since` needs a window end the caller controls.** The brief's ladder puts
`tree_match_during` inside the capture and `tree_match_after` within ten minutes after it
ends, but the signature carries only a start. Taking "now" as the end is right at capture
end and wrong for `sessions --link-commits` run days later, which would then call every
commit since "during". There is a keyword-only `until_ts` defaulting to now, and the
capture's real end is what the re-link path must pass.

**7. `origin/HEAD` is not set in this repository.** `git symbolic-ref --short
refs/remotes/origin/HEAD` exits 1 here, so a default-branch resolution that trusted it
would give `base_sha` None on the repository we are building. The chain is origin/HEAD,
then origin/main, origin/master, main, master, and the first `merge-base` that resolves
wins. On this worktree that yields `base_sha 42d0bcb6...`.

**8. repo.py came out at 866 lines, over the 800-line ratchet.** The module is the size
the brief asks for (five observers, a demo entry point, one module by OWNS), so the
excess was prose and single-use helpers. Six helpers were folded into their only callers
and the longest docstrings were compressed: 797 lines, with every constraint still stated
in the file. This is worth flagging to the orchestrator, because the next module with a
docstring density like this one will hit the same wall.

Two findings that changed the design rather than fixing a defect:

**`git diff HEAD --numstat --patch -z` returns both views in one call, and the patch half
is byte-identical to plain `git diff HEAD`.** Measured on git 2.47.1: 665-byte patch,
identical bytes, with the numstat block closed by one empty record. That matters because
the agent is editing the tree while the recorder reads it. Two calls would be two
different moments, and the per-file counts would be attached to a patch describing a
state they never described. `snapshot` makes one such call and cuts the patch into
per-file sections in this process, so `diff_hash`, every `patch_hash` and every per-file
count come from one atomic read of the tree, and the sections concatenate back to exactly
the bytes that were hashed.

**`dirty_tree_hash` hashes the -z forms, not the human-readable ones design 6.8 names.**
The -z output carries the same content with paths unquoted and records NUL-delimited. It
costs two fewer git calls per snapshot, removes git's quoting rules from the hash, and
lets `identity` and `snapshot` hash the same bytes for the same state, which is the
property the field exists for. An independent implementation following 6.8 literally
would produce different hashes for the same tree, which is why it is recorded here.

## WHAT CHANGED

- `src/telltale/repo.py`, new, 797 lines. Git through `subprocess` with an argv list, a
  5 s timeout and never a shell. Every diff carries `--no-ext-diff --no-textconv`,
  because both are configured inside the repository under observation and both name a
  program for git to run. The environment adds `LC_ALL=C` (git localizes "Binary files
  a/x and b/y differ", which is inside the bytes that become `diff_hash`),
  `GIT_OPTIONAL_LOCKS=0` (a lock taken here is a lock the recorded agent waits for) and
  `GIT_TERMINAL_PROMPT=0`.
  - `identity(cwd) -> dict` with repo_id (sha256 of the root commit sha, or of the common
    git dir path when there are no commits), worktree_id, root_hash (sha256 of the
    checkout's absolute path: spec 12.1 says the path is not the identity), head, branch
    (`symbolic-ref`, so a detached HEAD is None rather than the literal "HEAD"), base_sha,
    remote_fingerprint (sha256 of the origin URL as configured) and dirty_tree_hash.
  - `snapshot(cwd, trigger) -> dict` with trigger, head, dirty_tree_hash, diff_hash,
    files_changed, additions, deletions, renames, staged_files, unstaged_files,

  - `commits_since(cwd, since_ts, snapshots, provider_reported=(), explicit=(), *,

  capture_modes, content_level and fingerprint_id. model comes from `--model` or `-m`,
  effort from `--effort` or `-c model_reasoning_effort=...`, both accepting the `=` form,
  and a repeated flag reads as its last occurrence. `extra` is a closed set of six keys
  and an unknown key is refused by name, because a misspelled `capture_mode` would

  share an id. instruction_hashes covers CLAUDE.md, AGENTS.md and `.claude/rules/*.md`

  payload without the id.
- `docs/log/W0-T3.md`, this report.

The exact commit-matching rule, since the brief asks for it in full. A snapshot holds
head H and diff_hash D, where D is the sha256 of the bytes `git diff HEAD` printed. A
commit C with exactly one parent P matches that snapshot when P equals H and the sha256
of `git diff P C` equals D. Same base, byte-identical patch, therefore the same resulting
tree. Measured: with an edit, a rename and a staged new file in the working tree, the
patch before the commit and the patch of the commit were the same 665 bytes with the same
sha256. What the rule cannot see: a file the agent never staged is absent from
`git diff HEAD` and present in the commit, so committing an untracked file does not
match; nor does a commit of only part of the working tree; an amend or a rebase moves the
parent away from every snapshot head; and a merge has more than one parent and is never
matched. Each miss falls to a lower rung, which is the point of a ladder.

## UNSURE OR NOT DONE

- **The Debouncer can starve.** A trigger arriving every second forever never falls
  quiet, so fn never runs. A maximum delay would fix it and is not built, because nothing
  has yet measured how a real session's edits are spaced. E01 fixtures would answer it.
- **`git rev-list --since` prunes by commit date.** A commit with a date before the
  capture start hides the commits behind it, so a repository with clock skew or a
  rewritten date can leave a real commit out of the candidate set. Not worked around.
- **repo_id differs between a shallow and a full clone** of one repository, because a
  shallow clone's boundary commit is parentless and is what `rev-list --max-parents=0`
  returns. A repository with several root commits uses the lexicographically smallest, so
  two clones holding different sets of refs can disagree.
- **`heuristic=True` will link a teammate's commit.** It returns any commit on a local ref
  inside the window with no other evidence. That is what the rung means, and it is why it
  is off unless a caller asks.
- **The flag vocabulary is the brief's, not a measured one.** `-c model=` for codex is not
  read, nor is a model or sandbox setting that lives in a config file rather than in argv.
  The "last occurrence wins" rule for a repeated flag matches argparse and clap, and has
  not been checked against the real binaries.
- **`.claude/rules/*.md` is not searched recursively**, and only the working directory and
  the repository root are searched, as specified. A rules file in a subdirectory between
  them is not fingerprinted.
- **`LC_ALL=C` makes diff_hash reproducible across machines**, at the cost that an
  operator in another locale who runs `git diff HEAD` by hand can see different bytes from
  the ones that were hashed.
- **No tests.** The brief excludes them. Verification was by running the two scripts whose
  outputs are pasted above; they live in the session scratchpad and are not committed, so
  W1-T1's integration tests are where these assertions become permanent.
- **`additions` and `deletions` go null when any changed file is binary.** The rejected
  alternative was to sum the text files, which prints a confident number that silently
  excludes a file. per_file keeps every count that is known, so nothing is lost, but a
  consumer that wants a partial sum has to compute it and say what it excluded.

## EXPLAIN FOR THE OWNER

### What was at stake

If Telltale is going to say "this session produced 40 lines of change across 6 files, and
that work became commit abc123", then somebody has to look at the repository while the
agent works. Two things make that harder than it sounds. The first is that we are looking
at a moving target: the agent is editing files at the same moment we are reading them. The
second is that we must never store what it wrote. A diff body is the most revealing thing
in the whole system, and design 6.3 lists it among the things never persisted at any
level.

So the shape of the answer was fixed before any code: read the repository, and let nothing
out except numbers, file paths, and fingerprints. A fingerprint here means a sha256 hash,
a 64-character string computed from some bytes, which is equal when the bytes are equal
and different otherwise, and from which the bytes cannot be recovered.

### The first question: what is "this repository", if not its path?

A capture happens in a directory. The obvious identity is that directory's path, and the
specification says plainly that it is the wrong one: the same project on your laptop and
on a build machine sits at two different paths, and one project checked out twice sits at
two paths on one machine. An identity that changes when nothing about the project changed
is not an identity.

What is the same in every copy? The first commit ever made. Git gives every commit a name
computed from its contents and its history, so the first commit of this repository is
`03bb5450...` in every clone that has it. `repo_id` is the sha256 of that name. Measured:
a temporary clone of this worktree and two extra worktrees of that clone all report
`repo_id d9f783b1d318c0d6...`.

Then there is the other half of the question. Right now you have this repository checked
out several times at once, one directory per agent, which git calls a worktree. Those are
one project but genuinely separate desks, and if two agents work at once, "who changed
this file" has two possible answers. `worktree_id` is what tells them apart: git keeps
each worktree's bookkeeping in its own subdirectory, and the hash of that subdirectory's
name relative to the shared one is different for each desk and the same every time you
ask. Measured: `ebdf039c...` and `4a5b5f82...` for two worktrees whose `repo_id` is
identical.

Here is where the specification and reality disagreed, and it is worth your knowing about.
For the ORIGINAL checkout, that relative path is ".", so its hash is the same string,
`cdb4ee2aea69cc6a8...`, for every project on earth. I checked: a brand new empty
repository and a clone of this one give the same worktree_id. On its own that is harmless,
because the field is only ever read next to a repo_id. It stopped being harmless in the
one function that has to decide whether two recorded sessions were touching the same desk
at the same time. Keyed on worktree_id alone, that function would have said that a session
in Telltale and a session in some unrelated project overlapped, and marked both of their
work as ambiguous. It now compares the pair (repo_id, worktree_id). That is a small
deviation from my brief and it is the kind that would have been very hard to find later,
because the wrong answer looks exactly like a right one.

### The second question: how do you record a change without recording it?

`git diff` prints the actual before and after lines. We want the count and a fingerprint,
never the lines. That much is easy. The hard part is the moving target.

The first design ran git twice: once for the summary of counts per file, once for the
patch itself, hashing the second. That is wrong in a way that only shows up under a
working agent. The two commands run a few milliseconds apart, and in those milliseconds
the agent can save another file. You would then have counts from one moment and a hash
from another, and the per-file counts would be lined up against a patch that does not
contain them.

I measured whether git will give both in a single command, and it will:
`git diff HEAD --numstat --patch -z` prints the per-file counts, then one empty record,
then the patch, and the patch half is byte-for-byte identical to what plain `git diff
HEAD` prints. One read, one moment. The per-file hashes are then cut out of that same
patch inside the recorder, by splitting at each `diff --git ` header, which is safe
because every line inside a patch body begins with a space, a plus, a minus or a
backslash, so those words can never appear at the start of a line by accident. The pieces
join back to exactly the bytes that were hashed.

You can see the result in V1 above: one file changed, one line added, a `diff_hash`, and a
`patch_hash` that equals it, because with a single changed file the whole diff is that
file's section. Not one line of the demo's output starts with a plus or a minus.

### The third question: which commit was this session's work?

This is the one the specification is most insistent about, and the reason is worth stating
plainly. If a session ran from 10:00 to 10:30 and a commit exists at 10:29, the tempting
conclusion is that the session made it. That conclusion is worth nothing. You were also
sitting at the same repository, and so was another agent. Time alone proves nothing, and
the specification says so in one line: temporal proximity alone is insufficient.

So there is a ladder of five rungs, strongest first. Somebody stated it (`explicit`). The
agent itself reported the commit id (`provider_reported`). The commit makes exactly the
change we watched being made, during the session (`tree_match_during`) or just after it
(`tree_match_after`). And last, `heuristic`, which is the guess, and which this code only
ever produces if the caller asks for it by name.

The interesting rung is the tree match, because it had to be made mechanical. What we hold
in a snapshot is the commit the work started from, and the fingerprint of the uncommitted
change at that moment. What a commit holds is a parent and a change. So: the commit
matches the snapshot when its parent is the commit we started from, and the fingerprint of
its change equals the fingerprint we recorded. Same starting point, identical change,
therefore the same result. I checked this on a working tree holding an edit, a rename and
a newly added file: the patch before committing and the patch of the commit were the same
665 bytes with the same hash.

I want to be equally clear about what this cannot see, because a confidence rating that
overstates itself is worse than none. If the agent creates a new file and does not tell
git about it before we look, our snapshot does not contain it and the commit does, so the
fingerprints differ and there is no match. A commit of half the working tree does not
match. An amended or rebased commit has a different parent. A merge has two parents and is
never matched. Every one of those falls to a lower rung rather than producing a wrong
link, which is the entire point of having rungs.

### What running it found that reading it did not

Two defects, both mine, both found by running the code rather than reviewing it.

The first: a commit that changed three files was reported as changing zero. The cause is
almost silly. I ask git to separate its output with NUL bytes rather than newlines,
because a file name can contain a newline but never a NUL, and the parser therefore splits
on NUL. In one of the five places I call git for counts, I left the flag off. The parser
looked for a NUL, found none, and returned "no files changed" without any error. It was
caught by a check I had added on a hunch: a commit that matched a snapshot must report the
same numbers as the snapshot did. It reported 0 against the snapshot's 3.

The fix is not the missing flag. Every one of those calls now goes through a single
function that adds the flag itself, so there is no longer a place where it can be
forgotten. That is the difference between fixing a bug and removing the class.

The second: an empty repository and a spotless checkout produced the same "state of the
mess" fingerprint. That fingerprint is built from what differs from the last commit plus
what git reports as changed. In a repository with no commits yet, there is no last commit
to differ from, so that half was empty, and empty produced the same hash as "there is
nothing to report". Those two states are different in the way this whole system cares
about: "I cannot compare" versus "I compared and found nothing". The empty half is now a
marker that says so, and the two hashes differ.

### The environment fingerprint, and why it exists at all

Suppose next month a session takes twice as long. The natural conclusion is that the
change was harder. But the model may have changed, or your CLAUDE.md may have gained a
paragraph, or the permission mode may be different, and none of those appear anywhere in
the repository. The environment fingerprint is a single id computed from all of them, so
that a comparison across time can first ask whether it is comparing like with like.

It stores the model name and the effort setting, hashes of the tool list and the MCP
server names, a hash of the settings, the sandbox posture, and for each instruction file
its sha256 and its size in bytes. Never any content: for your global CLAUDE.md what is
recorded is `<home>/.claude/CLAUDE.md`, 2029 bytes, hash `5b9ccfde...`. The `<home>`
placeholder is deliberate, because a fingerprint travels with a report and a real home
path carries your account name.

The demo proves the property that matters. Run twice in one directory, the id is
`env_4793c2d1...` both times. Append one line to that directory's CLAUDE.md and the id
becomes `env_30628b24...`, with the file's entry going from 11 bytes to 25. Nothing about
the added line is anywhere in the output.

### The snapshot timer, and the answer I did not build

Spec 12.2 asks for snapshots to be debounced. The idea before the name: an agent that
writes six files in one second is doing one piece of work, and running git six times over
a tree that is still moving describes six states that never mattered. So a signal arriving
restarts a short clock, and the snapshot happens once the signal stops. Measured: 50
signals arriving over 77 milliseconds produce exactly one snapshot.

What I did not build, and you should know it: if signals keep arriving forever with a gap
just short of the timer, the snapshot never happens. The fix is a second rule, a maximum
delay after which it fires regardless. I left it out because choosing that number needs
measurements of how a real session's edits are spaced, and this repository's rule is that
I do not invent numbers. The E01 fixture sessions will produce that data, and it is one
number and about five lines of code once it exists.
