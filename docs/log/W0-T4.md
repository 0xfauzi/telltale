## WHAT WAS WRONG

**1. The digest denies an OTel event that exists, and omits five more.**
`claude_code.compaction` is emitted by 2.1.257 with `trigger`, `pre_tokens`,
`post_tokens`, `duration_ms`, `success` and `error`, and E01 caught 4 of them in S7. The
digest says there is no compaction OTel event. Five further events are absent from the
digest and present in the capture: `hook_execution_start`, `hook_execution_complete`,
`hook_registered`, `plugin_loaded`, `subagent_completed`. E01 wins, all six are in the
allowlist, and the disagreement is item 1 and 2 of `DRIFT` so no later reader has to
rediscover it. Symmetrically, four documented events never arrived in eight sessions
(`api_error`, `api_refusal`, `auth`, `permission_mode_changed`); their entries stay,
unexercised and marked as such.

**2. OTLP numbers arrive in three different encodings, and guessing would have been
silent corruption.** Measured across the fixtures: `intValue` is a JSON number,
`timeUnixNano` is a decimal string, and `duration_ms`, `pre_tokens`, `num_hooks`,
`prompt_length`, `tool_input_size_bytes` and `tool_result_size_bytes` arrive as
`stringValue`. Booleans arrive both as `boolValue` and as the strings `"true"` and
`"false"`. So no value is coerced by looking at it. Each is coerced by the `Kind` its
allowlist entry declares, and a string that is not a number is left as a string
deliberately, so the sanitizer drops it as `not_a_number` and names it, rather than the
parser inventing a 0. Unknown stays None.

**3. Three of the fields that carry the most information are NEVER_PERSIST containers.**
`tool_input`, `tool_parameters` and `tool_response` hold `file_path`, `command`,
`full_command` and the sizes, and the sanitizer refuses all three at every depth, by name,
which is correct: `tool_input` on an Edit carries the whole new file contents. The parser
therefore lifts the named scalars out to the top level of the payload before calling
`sanitize()` and lets the sanitizer drop the containers. `_lifted` is the only place that
does it and it copies a fixed list of names; nothing else in those containers is read.
That is why S3's `cat secrets_note.txt` keeps its command and loses its stdout.

**4. Two surfaces report different sizes for the same tool result.** For one S1 Bash call
the OTel `tool_result_size_bytes` is 910 and the stream's `tool_result` block is 568
characters. They agree in S3 and disagree in S1, so they are not the same measurement. The
stream number is therefore stored as `tool_result_content_bytes` and never under the
provider's own field name, and no size is derived for hooks, which report none.

**5. W0-T2's stream observation types named messages that do not exist and missed twelve
that do.** The capture has `rate_limit_event` and eleven `system` subtypes the digest
omits, including `hook_started`, `hook_response`, `hook_progress`, `status`,
`thinking_tokens` and `task_notification`. Keeping `claude.stream.init` as a type would
have meant inventing a name per subtype forever, so system messages became
`claude.stream.system.<subtype>`, which renames W0-T2's `claude.stream.init` and
`claude.stream.compact_boundary`. That is a rename inside a table nothing has stored yet.

**6. Three fields carry model or user prose and are not in NEVER_PERSIST.** `result` on
the final message holds the assistant's whole answer, `summary` on
`system:task_notification` holds a subagent's answer, and `compact_summary` on the
PostCompact hook holds the compacted transcript. All three are dropped today, because the
allowlist gate drops what it does not name, but they are dropped by the weaker of the two
gates. They are named here so W0-T5 can add them to NEVER_PERSIST, where a future
allowlist entry cannot undo them.

**7. Exit codes exist only as English.** A failed Bash call reports failure in the text
`Exit code 1`, and nothing structured carries the number, on any surface. The parser reads
it only when `is_error` is true and only from an anchored prefix, stores it with
`exit_code_source: "stream_text"`, and `CAPABILITIES` marks exit codes `derived` on the
stream and `unavailable` everywhere else. Design 6.3's word for a number produced by
reading prose is `derived`, and it is the weaker claim of the two on offer.

**8. Unattributable records were being recorded as parse failures, which is a lie about
what happened.** The first version wrote `parse_failure` when no capture could be found.
The record parsed perfectly; what failed was the wiring that should have named a capture.
Design 6.6 spends the word `parse_failure` on exactly one thing, "any exception", and
W0-T5 will count it. All three ways a capture id can arrive (the query parameter, the
resource attribute, the session map) are things the launcher sets, so the kind is now
`launcher`. This is why S6 reports 19 `launcher` diagnostics and 0 `parse_failure`, and
why the truncated-line test can report exactly one `parse_failure` and mean it.

**9. `ThreadingHTTPServer` prints tracebacks to stderr, and stderr belongs to the agent.**
Replaying a scenario produced `ConnectionResetError` tracebacks on stderr from
socketserver's default `handle_error`. A recorder that prints into the terminal of the
process it is recording has changed that process's output. `_Server.handle_error` now
records a `launcher` diagnostic and prints nothing, and `log_message` is silenced for the
same reason.

**10. Two ratchets bit, and both were right to.** `_otel_walk` scored 22 against the
cognitive-complexity limit of 15 and became a dispatcher plus four small readers, one per
OTLP shape; `providers/claude.py` reached 898 lines against the 800-line hook and came
down to 790, mostly by making `CAPABILITIES` a comprehension over one row per capability
instead of forty hand-written cells, which also made the E01 matrix legible as a matrix.

## EXPLAIN FOR THE OWNER

### What this task actually built

Two pieces that only make sense together. The receiver is a small HTTP server on
127.0.0.1 that Claude Code talks to without knowing what it is: its OTel exporter posts
to `/v1/logs` and `/v1/metrics`, its hooks post to `/hooks/claude`, and the launcher tees
its stdout line by line to `/v1/stream/claude`. The provider is the module that knows what
those bodies mean. The receiver knows nothing about Claude, and the provider knows nothing
about HTTP. That seam is the reason a second provider is a new file rather than an edit.

Three rules shape the receiver more than anything else.

It always answers 200. Never 400, never 500, whatever arrived. This looks wrong until you
remember who the client is: it is the agent being recorded. An OTLP exporter retries a 5xx
and backs off; an http hook waits for its answer inside a 5 second timeout and blocks the
agent's tool call while it waits. An error returned from here would change the behaviour of
the process we are trying to observe, which would make the measurement a measurement of
Telltale. So every failure becomes a diagnostic row and a 200. `/healthz` is the one
endpoint that tells the truth, and it is where you look to find out whether the recorder is
healthy.

It never guesses which capture a record belongs to. A record is attributed by the `capture`
query parameter, then the `telltale.capture_id` resource attribute the launcher set, then
the session-id map. If none of the three answers, the observation is still stored, under
the capture id `unattributed`, with a diagnostic naming what was missing. Dropping it would
turn a wiring mistake into a session that merely looks quiet, and a quiet session is
indistinguishable from a session where nothing happened. That distinction is the whole
point of the product.

It learns bindings, and says so when they change. Any record that carries both a session id
and a capture id teaches the map, which is what makes hooks attributable when the launcher
could not know the session id in advance. When a session that was bound to one capture
turns up bound to another, which is exactly what resuming a session does, the newer binding
wins and a `conflict` diagnostic keeps the older one visible. Nothing is silently
overwritten.

### What the provider had to be careful about

The most valuable fields in the capture live inside three containers that the sanitizer
refuses by name at every depth: `tool_input`, `tool_parameters` and `tool_response`. The
refusal is correct. `tool_input` on an Edit call contains the entire new contents of the
file. But `file_path` and `command` are inside there too, and without them a tool call is
an event with no subject. So the parser lifts a fixed list of allowed scalars out to the
top level before it calls the sanitizer, and lets the sanitizer drop the containers whole.
Nothing else is copied out. S3 is the proof: the fixtures contain a secret marker seven
times, the database contains it zero times, and `cat secrets_note.txt` is still fully
visible as a command on five observations across three surfaces.

The second care is about numbers. OTLP encodes the same quantity three different ways in
one payload, so a parser that reads a value by looking at its shape will eventually read a
size as a string and store 0. Every value here is coerced by the `Kind` its allowlist entry
declares, and anything that does not convert is left alone so the sanitizer drops it and
names it. A dropped field with a reason is recoverable. A zero is not.

### The DRIFT list

`DRIFT` in `providers/claude.py` is the list of places where the observed product differs
from its documentation or from what W0-T2 assumed. It is kept in code, next to the parser
it constrains, because every entry is a thing that will otherwise be rediscovered by
someone who trusted a document.

1. `claude_code.compaction` exists, against the digest's "no compaction OTel event", with
   `trigger`, `pre_tokens`, `post_tokens`, `duration_ms`, `success`, `error`. `post_tokens`
   is absent when `success` is false, so a reducer reads `success` first.
2. Six OTel log events the digest omits: `compaction`, `hook_execution_start`,
   `hook_execution_complete`, `hook_registered`, `plugin_loaded`, `subagent_completed`.
3. Four documented OTel events never arrived in 8 sessions: `api_error`, `api_refusal`,
   `auth`, `permission_mode_changed`. Their allowlist entries stay, unexercised.
4. `code_edit_tool.decision` is a metric the digest omits; `pull_request.count` is
   documented and was never seen.
5. `user_prompt.prompt` and `assistant_response.response` arrive with the literal value
   `<REDACTED>`: dropped, and only the lengths kept.
6. OTLP number encoding is mixed. `intValue` is a JSON number, `timeUnixNano` a decimal
   string, and `duration_ms`, `pre_tokens`, `num_hooks`, `prompt_length` and both size
   attributes are `stringValue`. Every value is coerced by its allowlist `Kind`.
7. OTel attribute keys are dotted (`event.name`, `session.id`, `prompt.id`,
   `message.uuid`, `agent.name`, `terminal.type`, `plugin.name`); the parser rewrites the
   dot.
8. `tool_input` and `tool_parameters` are JSON strings inside an attribute, not objects,
   and `tool_input` carries whole Edit contents.
9. `query_source` is `sdk` in headless mode, not `repl_main_thread`, and `compact` while
   compacting.
10. Hook bodies carry no timestamp, so `provider_ts` is None on every hook observation.
11. Twelve stream types the digest omits: `rate_limit_event` and the system subtypes
    `hook_started`, `hook_response`, `hook_progress`, `notification`, `status`,
    `task_started`, `task_progress`, `task_notification`, `task_updated`,
    `thinking_tokens`, `vcs_state_changed`. System messages are
    `claude.stream.system.<subtype>`, renaming W0-T2's `claude.stream.init` and
    `claude.stream.compact_boundary`.
12. A `result` can carry subtype `success` while `is_error` is true (E01 S7): `is_error` is
    the field that says whether the session failed.
13. The `result` message holds the final assistant text in `result`, and
    `system:task_notification` a subagent's answer in `summary`. Neither is in
    NEVER_PERSIST, so the allowlist gate drops them and neither is ever added to it.
14. The `SessionStart` http hook registers and never fires, so the plan declares it and the
    launcher may not wait for it.
15. `service.version` is a resource attribute on every record without
    `OTEL_METRICS_INCLUDE_VERSION`; kept as `service_version`.
16. OTel `tool_result_size_bytes` and the stream block it names are different numbers (910
    against 568 on one S1 Bash call), so the stream number is stored as
    `tool_result_content_bytes`.
