## WHAT WAS WRONG

**1. The fixtures cannot be replayed as they are committed, and replaying them that way
makes the privacy test pass by asking nothing.** E01's sanitizer replaced the machine's
repository path with the literal `<repo>` and the home directory with `<home>` before the
fixtures were committed. Neither is an absolute path. The sanitizer's whole question
about a path is "inside the repository, or outside it", and `relativize` answers a
relative path with no repository root by storing the string as it stands. Measured: a
replay of S1 exactly as recorded stores
`<home>/.claude/projects/<home-slug>-Documents-code-telltale--claude-worktrees-.../<uuid>.jsonl`
verbatim in `transcript_path`, 17 times in S1's database and 51 in S7's. So `replay` in
conftest.py writes a copy of the scenario with `<repo>` and `<home>` substituted by this
test's temporary directories, and hands the receiver a `Ctx` naming those two. That is
the only edit made to the recorded bytes, and it is a restoration rather than a fixture:
on the wire, Claude Code sends absolute paths. After it, `transcript_path` becomes
`<outside>/925b4935` and `cwd` becomes `.`.

There is a live consequence for the wave 1 daemon. `Receiver`'s default
`ctx_for_capture` returns `Ctx()`, which has no repository root, and `telltale daemon`
has no launcher to give it one. Every PATH field in a daemon capture would therefore be
stored as written, home directory included. The launcher path is fine because it knows
the repository. Naming it here so the daemon task does not have to rediscover it.

**2. `/healthz` does not answer 503 while drops are pending.** The brief's injected facts
say it does. It does not: `Receiver.health` computes `ok = store["writer"] == "alive" and
not store["down"]`, and a paused writer is alive. Measured with 37 drops pending and the
writer held: HTTP 200, body `drops_unreported: 37`,
`drops_by_surface: {"otel_metrics": 37}`. Design 6.5 says "`/healthz` alone tells the
truth: 503 with writer state, per-surface last-received time and drop counts", which
reads to me as the body of a 503 rather than as a rule about when the status flips, and
`receiver.py` is READS for this task. So `test_fail_open.py` asserts the body (which is
the fact design 6.5 fixes), asserts the 200 the code actually returns, and says in a
comment beside it that the status is an open receiver decision. If the answer is that
pending drops should be 503, the change is one line in `Receiver.health` and this test
fails loudly until somebody updates it, which is what I want it to do.

**3. An absolute machine path reaches the database at level 1, in prose.** Measured on
S7: `claude.hook.PostToolUseFailure.error` holds
`error: "Exit code 2 ... Querying Python at \`<repo>/.venv/bin/python3\` failed with exit
status signal: 6 (SIGABRT) ..."`. `error` is `Kind.SCALAR`, so it is scrubbed for secrets
and bounded to 512 characters and never path-rewritten, because only `Kind.PATH` fields
are. On this machine that string starts with the home directory. W0-T2's NEXT item 1
predicted this class for `claude.otel.api_error.error`; it turns out to be live on a hook
field instead, in a fixture. Fixing it means teaching the scrubber to find paths inside
free text, which is a change to `sanitize.py` beyond the NEVER_PERSIST addition this task
owns, so it is not fixed. It is pinned:
`test_the_repository_root_survives_only_in_known_free_text` allows exactly
`{("claude.hook.PostToolUseFailure", "error")}` and fails on any other field or type,
across all eight scenarios.

**4. The AWS probe in the fixtures cannot exercise the AWS scrub rule.** This came out of
the break-and-restore rather than out of reading. With `tool_response` added to the
allowlist AND `tool_response` and `stdout` removed from NEVER_PERSIST, S3's database
holds `AKIATELLTALEFAKE00001` once, and holds the sk-ant key and the private key header
zero times. The two that vanished were scrubbed. The one that survived was not, because
design 6.4's pattern is `\bAKIA[0-9A-Z]{16}\b`, an AWS access key id is 20 characters,
and the probe is 21. It never matched, in any scenario, and nothing said so, because the
allowlist gate was dropping the field anyway. So the fixture probe has only ever tested
the first gate. `test_secrets_are_scrubbed_out_of_the_one_free_text_field` now posts an
`api_error` record whose `error` field carries four secrets built to the real shapes, and
asserts all four are replaced and none reaches the file. It is the field W0-T2 aimed
W0-T5 at, and no E01 session ever produced one.

**5. `<redacted:N>` counts patterns, not positions.** `scrub`'s docstring says "N is the
position of the redaction inside this string, so two secrets in one value read
`<redacted:1>` and `<redacted:2>` and a reader can tell one leak from two". Measured on
one string carrying four different secrets: `request failed: <redacted:2> <redacted:3>
<redacted:4> <redacted:1>`. The counter advances per pattern pass, and the private key
pattern runs first, so the secret at the END of the string is numbered 1. A reader can
still tell one leak from four, which is what the field is for, so this is a docstring
that overstates rather than a defect. Not fixed (sanitize.py is NEVER_PERSIST-only here);
the assertion counts markers instead of matching their numbers, and says why.

**6. Ten lifecycle POSTs cannot be both held and stored.** The brief asks that every
lifecycle observation be stored AND that lifecycle records be posted against a full
queue. Those are the same records, and design 6.5 says a non-droppable batch offered to a
full queue waits 250 ms and is then dropped. Whether it survives therefore depends on
when the writer is released, which is a coin flip dressed as a test. The file splits the
claim in two: one test posts the ten lifecycle records after the writer is resumed and
asserts all ten are stored with the exact drop arithmetic, and a second posts six against
a held writer and asserts that the last three, which certainly met a full queue, were
each answered 200 in at least 250 and at most 300 ms and that their loss was written
down. Both facts are real, and neither is timing-dependent.

**7. The store's queue size was a module constant, so it could not be filled.** Filling
10000 slots to see what happens at 10001 costs seconds and megabytes; rebinding
`QUEUE_MAX` would change every store in the process. `Store.__init__` now takes
`queue_max`, and `health()` reports the queue's real size rather than the constant, since
a health report saying 10000 about a queue that holds 2 is the kind of lie this system
exists to prevent.

**8. A process mistake worth recording.** Mid-task I ran `git checkout --
src/telltale/cli.py` to undo a deliberate break, on a file that had never been committed,
and deleted the whole command. It was rewritten from the working notes and is verified
identical by the eight tests in `test_doctor_setup.py` and by the `doctor` output quoted
below, but the honest record is that the recovery is a reconstruction. The lesson is in
the brief already and I did not follow it: commit before you break.

## EXPLAIN FOR THE OWNER

### The promise these tests are here to keep

Telltale reads everything a coding agent says and does, and writes some of it to a file
on your machine. The whole product depends on one sentence being true: a secret that
passed through a session is not in that file. Nobody can check that by reading the code,
because the code is three gates in three places and the interesting failures are the ones
where a gate is not where you think it is.

So the test asks the disk. It replays a recorded session, closes the database, opens the
FILE, and searches the raw bytes for strings that must not be there.

That last part is not fussiness. SQLite does not erase. A row you delete leaves its bytes
in a page marked free; a row written recently may live only in the `-wal` sidecar file; a
third file, `-shm`, indexes the second. A test that runs a query and finds nothing has
proved that today's schema hides the value. A test that reads all three files has proved
something about the machine.

### The probes, and the file the test cannot get at

E01 planted three fake credentials in a file called `secrets_note.txt` in the fixture
repository, then asked Claude Code to print it and summarize it. Two of those sessions,
S3 and S7, therefore contain a real API key shape, a real AWS key shape and a real
private key header, in prompts, in tool output and in the assistant's reply. The
credentials are fake; the shapes are exact. A fixture with the secret removed cannot
demonstrate that the secret was removed.

The privacy test replays all eight sessions and looks for those three strings, for the
two markers that stand where the home directory used to be, and for S3's prompt text. It
finds none of them, in any of the eight databases.

### The first thing that went wrong, and why the fix is not a cheat

Before the fixtures were committed, they were themselves sanitized: the machine's
repository path was replaced by the four characters `<repo>` and the home directory by
`<home>`. That is right for a file in a public repository, and it quietly breaks the
test.

Here is why. When the sanitizer meets a path, it asks one question: is this inside the
repository being recorded? If yes, the path becomes relative to it, because "the agent
edited pkg/calc.py" is the engineering fact this whole system exists to record. If no,
the path becomes `<outside>/` and eight characters of hash, so that "the agent read two
files somewhere it should not have" survives while the place does not.

That question can only be asked of an absolute path. `<repo>/pkg/calc.py` is not one. Fed
a relative path with no repository to compare it against, the sanitizer stores the string
as it stands. I measured what that produces: replaying S1 as committed puts
`<home>/.claude/projects/<home-slug>-Documents-code-telltale-...` into the database
seventeen times.

So the replay puts the two paths back before it posts: `<repo>` becomes a temporary
directory this test made, `<home>` becomes another one, and the receiver is told which is
which. Nothing about Telltale is changed or replaced. It is the recording restored to the
shape it had on the wire. After it, that same field reads `<outside>/925b4935`.

This one has a consequence you will meet later. There are two ways to run Telltale. Under
`telltale run`, the launcher knows the repository and tells the receiver. Under `telltale
daemon`, which is the day-to-day capture the setup snippet is for, there is no launcher,
and today the receiver would have no repository root, which means every path would be
stored raw. That is written down in NEXT so the daemon task does not have to find it the
hard way.

### The thing I found by breaking my own test

There are three gates between an arriving field and the database, and they are not equal.

The first is an allowlist: a named list of which fields may be stored, per event type.
Anything not named is dropped and recorded as unknown. The second cleans what survives:
paths are rewritten, commands are reduced to a normal form, and every string is scanned
for secrets and rewritten as `<redacted:1>`. The third is a list of field names that are
removed at every depth whatever the first two say: `prompt`, `content`, `stdout`,
`tool_response` and about thirty more. It exists for exactly one situation, which is that
the first gate is wrong.

A passing test cannot tell you which gate did the work. So I made the first gate wrong on
purpose, which is what W0-T4 warned might happen by accident one day: I added
`tool_response` to the allowlist, as a plausible mistake, and ran the suite. Everything
passed. That is the third gate earning its place, and it is a measurement rather than an
argument.

Then I took `tool_response` and `stdout` out of the third gate as well, so both were
wrong at once, and the database filled with the contents of `secrets_note.txt`. Which is
when the interesting thing showed up. Of the three planted credentials, two were gone,
scrubbed by the second gate. One was there: `AKIATELLTALEFAKE00001`.

An AWS access key id is the four letters AKIA and sixteen more characters. Twenty. The
probe in the fixtures is twenty-one. The pattern in the design is written to match a real
key, so it never matched the probe, in any of the eight sessions, and nothing ever said
so, because the allowlist was dropping the field before the scrubber could get it wrong.

Read that carefully, because the failure mode generalizes: a gate that never runs is a
gate that passes. The credential scrubber has been in the system since W0-T2 and, on this
evidence, the AWS half of it has never been executed on a value it was supposed to catch.

There is now a test that posts an error message carrying four secrets, each built to the
real shape, through the real receiver, and checks all four out of the file. It aims at
`error` on an api_error event, which is the one free-text field kept at content level 1,
which is the field W0-T2's own report pointed the next task at.

### What "fails open" means, and what it costs

The second file tests a different promise. Telltale runs beside the agent it records, and
the agent talks to it: OpenTelemetry posts batches to it, and every hook the agent fires
posts to it and WAITS for the answer, inside a five second timeout, holding up the tool
call. Which means a slow recorder is a slow agent, and a recorder that returns an error
is a recorder that changes the behaviour of the thing it is measuring.

So the rule is that every endpoint answers 200 whatever happened, no request waits longer
than a quarter second, and the losses are counted.

To see that hold, the queue has to be full. The store's queue holds ten thousand batches,
which takes seconds to fill and would make a slow test that mostly measures itself. So
`Store` now takes the queue size as an argument, the test builds one that holds two, and
the writer thread is held still by the two methods that say TEST-ONLY in their own
docstrings. Three POSTs fill it. Everything after that meets a full queue, for real.

The numbers, over five runs:

| what was posted | worst case |
| --- | --- |
| 40 metric batches, queue full, writer held | 1.7 to 5.7 ms |
| 10 hook bodies, writer running | 0.3 to 4.9 ms |
| 3 hook bodies, queue full, writer held | 253.4 to 258.9 ms |
| 1 hook body carrying a broken character | 0.7 ms |

The third row is the design working. A metric is thrown away the instant there is no
room, because a metric is a rollup of events that are already stored, so it costs 1.7 ms.
A hook is not: a session ends once, so the request waits up to 250 ms for room before
giving up. The measured 253 to 259 is that quarter second plus three to nine milliseconds
of network, parse and clean. The agent never waits longer, and it never sees an error.

The arithmetic then has to close, and this is the part that matters more than the speed.
Forty metric observations were posted and three were stored. The store reports thirty
seven dropped on the `otel_metrics` surface, and writes exactly one diagnostic row saying
`{"per_surface": {"otel_metrics": 37}, "total": 37}`. One row for the flood, not thirty
seven. And all ten hooks are stored, none dropped. A recorder that loses data and says so
is a recorder you can reason about. A recorder that loses data quietly turns a wiring
mistake into a session that merely looks quiet, and those two are indistinguishable
afterwards.

One more thing in that file. W0-T2 measured that a single half-character in a string,
which JSON permits and SQLite refuses, once killed the writer thread and left the store
accepting everything and storing nothing. There is now a test that posts one, and checks
that the writer is alive afterwards and that the next record still lands.

### The test I would not write

The brief asked for one assertion I could not make honestly. It said that ten lifecycle
records should be posted against a full queue and that all ten should end up stored. They
cannot both be true on purpose: a record that meets a full queue waits 250 ms and is then
dropped, so whether it survives depends on when the writer happens to be released. That
test would pass most runs and fail some, and a test that fails one run in twenty teaches
people to rerun it rather than read it.

So the claim is split. One test posts the ten after the writer is running and asserts all
ten are stored and that the drop arithmetic closes. Another posts six while the writer is
held and asserts that the three which certainly met a full queue were each answered 200
in at least 250 and at most 300 milliseconds, and that their loss was recorded. Every
fact the brief wanted is checked. Neither check is a coin flip.

### The command that tells you it is working

`telltale doctor` was a placeholder that printed "not implemented" and exited 2. It now
starts a receiver on a temporary database, posts one made-up record to each of the seven
endpoints in the exact shapes Claude Code uses, reads each one back, and prints what came
back:

```
otel_logs             ok      claude.otel.api_request
hook                  ok      claude.hook.SessionEnd
```

The right-hand column is the point. "ok" alone would tell you a request was accepted, and
every endpoint here accepts everything by design. The observation type is proof that the
record went all the way through: a route, a parser, an allowlist entry, a queue, a writer
thread, a table, and back out through a read connection. Any one of those can be missing
while the other five are fine.

It also checks the port the daemon would use. Nothing listening is the normal answer and
passes. A Telltale daemon answering is fine too. Something else holding the port and not
answering is a failure, and it is the one that matters, because in that state the daemon
would bind nothing and every hook would post into the void. Doctor exits non-zero and
names it.

And it reports whether git, claude, codex, uv and timesfm are on the machine, without
letting any of them change the exit code. That line is deliberate. The build server has
no claude binary and no forecasting stack, and Telltale works there. A doctor that failed
for a missing agent binary would be a doctor whose exit code means nothing.

### The command that refuses

`telltale setup claude --print` prints a settings snippet you may paste into
`~/.claude/settings.json` if you want your day-to-day sessions recorded. It prints. It
does not write, and `--apply` prints a refusal that names your decision of 2026-09-01 and
exits 2. Two of the tests compare a listing of the temporary home directory before and
after the command, which is how they would catch it writing anything at all: I checked
they can, by making the command write a file and watching both fail.

What it prints is not written out by hand. It comes from the same function the launcher
will call to configure a child process, so the hook list and the OpenTelemetry variables
in the snippet cannot drift away from the ones a real capture gets. A test also checks
that the three switches which would make Claude Code send prompt text, assistant text and
tool contents are absent from it. That is the one place where turning telemetry up too
far would be invisible: it would be sitting in your own settings file, pasted from us.

The codex half prints no configuration keys at all, only a note that the spelling is
pending E02 and what the settings need to achieve. A key name nobody has run would be
worse than nothing: you would paste it, it would do nothing, and it would look like
Telltale failing to record.
