# W1-E03 TimesFM-3 smoke on this machine

## OUTCOME

All four decision rules resolved, and none of them took the bad branch.

**(a) Installation.** `uv sync --extra forecast` succeeds on Python 3.12.8. There is no
resolver error to report. torch **2.13.0**, numpy 2.5.2, timesfm 3.0.0, 20 packages.
0.318 s with the uv cache warm; 7.103 s for the whole environment against an empty
isolated cache, of which the torch wheel is 106.1 MiB. The extra is optional in fact:
in the default environment `import telltale` works in 0.073 s, `import torch` and
`import timesfm3` both fail with `ModuleNotFoundError`, and `uv run pytest -m integration`
is 33 passed in 18.16 s.

**(b) Per-call cost: per-window calls are affordable, and the number for the wave 2
backtest brief is 0.35 s.** 108 `predict_batch` calls in the main run, replicated by 108
more in the control run. Median 0.3458 s over all 216, 0.3071 s in the main run alone;
min 0.1480 s, max 0.7245 s. The slowest call anywhere is the 33-variate probe at
0.8141 s, 73 times inside the 60 s threshold. Model load, paid once per process, is
1.900 to 2.145 s on CPU. A 50-origin backtest is about 18 s of model time.

**(c) NaN: internal interpolation confirmed, at exactly 0.0 rather than at a tolerance.**
An interior NaN gives a forecast identical to the linearly interpolated series, to the
last bit. A leading NaN is identical to the trimmed series. An all-NaN row is identical to
a row of zeros. Nothing raises and nothing is reported.

**(d) Device: MPS is allowed.** The largest relative disagreement with CPU on any forecast
point is 9.072e-07 against a rule of 1e-3, and MPS is 1.888x and 2.012x faster on the two
measurements of the case the rule names.

Checkpoint `google/timesfm-3.0-pytorch`: **1,322,900,328 bytes on disk, 32.462 s to
download and load on an empty cache**, 2.145 s to load in a later process. Against the
stop conditions of 10 GB and 30 minutes, neither was close. Peak RSS for a process
holding a CPU forecaster and an MPS forecaster: 4,249,731,072 bytes.

Files: `experiments/E03/run.py` (702 lines), `experiments/E03/report.py` (163),
`docs/experiments/E03.md`. Raw output is `experiments/E03/out/` (gitignored):

## WHAT WAS WRONG

**1. My first per-call table said "step changes forecast far faster than random walks",
and it was an artefact of when each cell ran.** The first rehearsal ran the 36
cells in canonical order with no warmup. Medians fell by roughly a factor of four from the
early cells to the late ones, and because the cells are grouped by series shape, the trend
landed on the series column. The obvious explanation was cell order. **It is not.**
`run.py --canonical` recreates that exact arrangement, and its two halves differ by 7
percent in the other direction (`out/results_canonical.json`: first half mean 0.3952 s,
second half 0.4244 s, slower rather than faster). So the runner now discards 12 warmup
calls, shuffles the cell order under a fixed seed and runs a fixed control cell either
side of the matrix, and the
rehearsal's speed-up is recorded as unexplained rather than as an ordering effect. Its
output was overwritten, so no number from it is cited.

**2. The checkpoint is not 2.6 GB, and the obvious measurement says it is.** The Hugging
Face cache keeps one blob and symlinks a snapshot path to it. `Path.stat()` follows
symlinks, so summing every file counts the model twice: 2,645,800,425 apparent against
1,322,900,328 real. `du -sh` agrees with the smaller number. `on_disk_bytes` in `run.py`
counts inodes once.

**3. Design 6.12 is wrong about trailing NaN.** It says the forecaster "trims leading
all-NaN columns, interpolates interior and trailing NaN". Interior is exact linear
interpolation, measured at 0.0 difference. Trailing is **a forward fill, not an
interpolation**: `linear_interpolation` calls `np.interp`, which clamps outside the sample
range. Measured, a trailing NaN matches a forward fill at 0.0 and differs from a linear
extrapolation by 1.5816993713378906 on a series whose values run to about 30. I added the
probe for this after reading the source; it was not in the brief's list.

**4. Design 6.12 is wrong that past-future covariates "must span context + 64 unless
`padding_mode="edge"`".** A covariate of length context + H runs under
`padding_mode="none"` and raises nothing: `decode` computes
`horizon = past_future.shape[-1] - context`, so the model quietly generates H steps
instead of 64. **And it gives a different answer.** The same covariate under `"none"` and
under `"edge"` differs by 1.4114360809326172 at its worst point. `padding_mode` is part of
the result, not part of the plumbing, and an adapter that drops it because a test still
passes will change numbers silently.

**5. The 32-variate cap is worse than unenforced.** Both readings of "33 variates" run
without error and return a full, correctly shaped answer: 33 target variates gives
(33, 24) and (33, 24, 9); one target plus 31 past-only plus one past-future gives (1, 24)
and (1, 24, 9). Nothing warns and nothing visibly truncates.

**6. The `forecast-isolation` hook's comment overstates torch's import time by 3x.** It
says "torch alone is several seconds of import and hundreds of megabytes of resident
memory". Measured on this machine, median of 3 fresh processes: torch imports in 1.0224 s
and reaches 200,867,840 B resident; `import telltale` is 0.0193 s and 26,525,696 B. The
memory claim is right. The time claim is not. The rule is untouched, and its true numbers
are better: torch multiplies the collector's startup by 53 and its memory by 7.6. I did
not edit the hook comment, because `.pre-commit-config.yaml` is not this task's to change.

**7. Quantile monotonicity cannot be measured with the default settings.**
`sort_quantiles` defaults to True and sorts the quantile axis, so "the output is sorted"
is true by construction and answers nothing. Measured with the sort off, 0 of 216 forecast
steps are non-monotone in each run. The adapter still keeps the default.

**8. `predict_batch` is a generator, so a naive timing measures nothing.** It returns
before doing any work. Every wall time here is taken around `list(...)`.

**9. `ru_maxrss` means different things on different platforms.** Bytes on Darwin,
kibibytes on Linux, a factor of 1024 between two readings of the same field. `run.py`
records which platform produced the number.

**10. `experiments/E03/run.py` hit the 800-line ratchet at 817 lines.** I split the eight
table-printing functions into `experiments/E03/report.py`, which reads a results file and
never touches the model. That also makes the tables re-renderable from a saved run:
`uv run python experiments/E03/report.py experiments/E03/out/results_canonical.json`,
and it needs no extra because it imports only the standard library.

## UNSURE OR NOT DONE

- **The rehearsal's factor-of-four speed-up is unexplained.** Two later runs, one of them
  recreating its exact arrangement, do not reproduce it. I do not know what caused it. It
  does not change any decision, because even the slow numbers are 60x inside the
  threshold.
- **The MPS speed factor is a range, not a constant.** 1.888x and 2.012x on the two runs
  whose files survive, three calls each. Rehearsals of the same probe ran higher; their
  output was overwritten and I do not cite it. The MPS load cost is unstable too: 2.041 s
  in one run against 4.924 s in the other, where CPU is 1.900 to 2.145 s. A process making
  a handful of calls can be slower on MPS overall.
- **CPU-MPS agreement was measured on one input.** One 64-point random walk, horizon 64,
  no covariates. It is not swept over lengths, horizons or variate counts. A sweep would
  measure it.
- **Peak RSS is for a process holding both a CPU and an MPS forecaster.** A CPU-only
  process was not measured separately. `rss_after_load_bytes` and `peak_rss_bytes` are
  equal in the main run, so the calls themselves add nothing measurable, but the 4.16 GB
  figure includes the second model.
- **The cohort is synthetic.** Three seeded shapes, contexts 16 to 512, horizons 8 and 24,
  at most 3 variates, one series per call. No real Telltale series, no batch of more than
  one series per `predict_batch`, no context beyond 512, no horizon beyond 64. A cost
  quoted for a real backtest is an estimate until that backtest is timed.
- **The 33-variate call returns a plausible answer and I did not check whether it is a
  correct one.** I measured that it does not raise. Whether the extra variates are used,
  ignored or corrupt the result is not measured, and the adapter's assertion means Telltale
  never needs to know.
- **`out/uv_sync_forecast_cold.txt` is one cold install on a fast connection.** The 7.103 s
  and the 32.462 s checkpoint fetch are network numbers and will differ elsewhere.
- **Two design corrections are not applied to the design documents.** Finding 3 (trailing
  NaN is a forward fill) and finding 4 (`padding_mode="none"` does not raise and changes
  the numbers) both contradict `docs/design/01-design.md` 6.12. `docs/design/00-digest.md`
  2.4 also carries two placeholders that this experiment fills: "Size and download time:
  measured in E03" and "M5 CPU/MPS timing is measured in E03". I did not edit either file:
  it is not in this task's DO list, and wave 0 handled design corrections as a separate
  task. The exact edits are listed under NEXT.

## NEXT

The forecast adapter (`src/telltale/forecast/timesfm.py`) can now be written against
measured behaviour. Four of those behaviours are silent, and the adapter is the only place
that catches them:

1. NaN in any position is substituted without a word: interior interpolated, leading
   trimmed, trailing forward-filled, an all-NaN row zeroed. `np.isfinite` on every array
   before the call, refusing with a named reason.
2. A context shorter than one 32-point patch is left-padded and forecast. The adapter
   enforces `c_min` itself.
3. A 33rd variate is accepted and answered. The adapter asserts
   `1 + past_only + past_future <= 32` and never subsamples.
4. `padding_mode="none"` on a covariate of length context + H changes the forecast by 1.41
   rather than refusing it. The adapter passes `n_ctx + H` with `padding_mode="edge"` and
   records that horizon covariates beyond step H are edge-replicated.

The wave 2 backtest brief gets: **0.35 s median per `predict_batch` call (0.3458 s over
216 calls), 0.81 s worst observed, 1.900 to 2.145 s to load the model once per process.**
Per-origin calls are affordable. Batching a run's windows into one call remains the
design, but as an efficiency, not a necessity, which changes what W2 must build first.

`device` should be adapter configuration with `cpu` as the default and `mps` permitted on
this machine, recorded in the ForecastRun beside the licence, because a device that can
change a number is provenance.

Three things for the orchestrator:

- The two design-document corrections in UNSURE, and the two `00-digest.md` 2.4
  placeholders this experiment fills: checkpoint size 1,322,900,328 bytes, first fetch
  32.462 s, warm load 2.145 s, CPU median 0.3458 s per call, MPS about twice as fast and
  agreeing to 9.072e-07 relative.
- The `forecast-isolation` hook comment in `.pre-commit-config.yaml` says torch is
  "several seconds of import". It is 1.0224 s here. The rule is right; the number is not.

## EXPLAIN FOR THE OWNER

Telltale is going to forecast. Before writing a line of the code that does it, somebody
had to find out whether the model it depends on actually runs on your laptop, what one
forecast costs, and what it does when you hand it something imperfect. That last question
turned out to be the important one.

### The first question: does it install at all

The forecasting model is deliberately kept out of Telltale's normal install. Telltale runs
beside the agent it is recording, so every library it loads is a delay somebody else's
session pays for. The model stack lives behind an opt-in, and the opt-in has to work.

It works. `uv sync --extra forecast` succeeds on Python 3.12 and pulls torch 2.13.0. There
was no error, so there is nothing to work around.

The more interesting half is proving the opt-in is real. In the ordinary environment:

```
uv run python -c "import torch"
ModuleNotFoundError: No module named 'torch'
```

and the 33 integration tests still pass. So the model genuinely is not there unless you
ask for it.

While checking that, I measured something the project had been asserting without a number.
A rule in the repository says torch must never be imported by the recorder, and the reason
given is that torch costs "several seconds" to import and hundreds of megabytes of memory.
Measured here, over three fresh processes: torch takes **1.02 seconds** and 201 MB.
Telltale itself takes 0.019 seconds and 27 MB. So the memory claim is right, the time
claim is about three times too pessimistic, and the rule is still obviously correct: torch
would make the recorder start 53 times slower. I have written that down rather than fixed
the comment, because that file is not this task's to edit.

### The second question: what does one forecast cost

The model is 1.32 GB. It downloads once, in about 30 seconds. After that any process can
load it from disk in about 2 seconds.

One forecast takes **0.35 seconds**, median of 216 of them.

That number decides something concrete. Telltale's backtest works by standing at many
points in the past and asking the model to predict what came next, one call per point. If
a call cost a minute, that design would be impossible and the code would have to be built
differently from the start. At a third of a second, fifty of those calls is eighteen
seconds. The design stands.

### The mistake worth showing you

My first table said something satisfying: step changes forecast three times faster than
random walks. There is even a story for it. A step is a simpler shape, so of course it is
cheaper.

It was false, and the way it was false is the useful part. The table runs the cases in a
fixed order, grouped by shape: all the random walks, then all the step changes. The times
fell steadily as the run went on. Because the order and the grouping line up, a trend over
time is indistinguishable from a difference between shapes. The table cannot tell them
apart, and it reports the wrong one.

So I fixed the method: throw away the first twelve calls, then run the cases in a
shuffled order, and run one identical case at the start and again at the end to see
whether the machine drifted. Shuffling breaks the alignment. If shapes really differ, the
difference survives; if it was the clock, it spreads out and vanishes.

It vanished. And then I checked my own explanation, which is the step people skip. I added
a mode that recreates the original arrangement exactly, so the "it was the order" theory
could be tested rather than assumed. It failed: in that run the first half and the second
half of the table differ by seven percent, in the opposite direction. **So I do not know
what made the rehearsal speed up.** It is written down as unknown. What I can say is that
the shape of a series is not a cost you can measure at this sample size, and the honest
number is one median with a spread around it.

### The third question, and the one that matters

The forecasting model is polite in the worst way. Hand it a broken series and it does not
complain. It quietly repairs the series and gives you a number.

Telltale's core rule is that a missing value stays missing. Not zero, not a guess: missing,
all the way through to the report. A number computed from a silently invented value is a
lie with a decimal point on it.

So I gave the model four kinds of broken series and compared each result against what a
person would have had to write instead:

- **A gap in the middle.** The result is identical, to the last decimal place, to the
  series with that gap filled in by drawing a straight line between its neighbours. Not
  approximately: the difference is exactly zero.
- **A missing first value.** Identical to simply deleting that point.
- **A missing last value.** Identical to repeating the previous value. This one matters
  because Telltale's own design document says the model interpolates a trailing gap. It
  does not. It copies the last value forward. The two answers differ by 1.58 on a series
  whose values run to about 30, and I only found it because I read the model's source and
  added a probe the task list did not ask for.
- **An entire missing row**, which is what a covariate with no data looks like. Identical
  to a row of zeros. Filling absence with zero is exactly the failure the project's
  invariants name out loud.

Every one of those returned a finished forecast and raised nothing.

That is the justification for a check that would otherwise look like paranoia. The adapter
Telltale writes will refuse to pass any array containing a gap, with a named reason,
before the model ever sees it. Without that check, a session with three missing rows
produces a confident prediction that no measurement supports.

### Two more places it says yes when it should say no

The model has a documented limit of 32 series in one call. I gave it 33. It ran, and
returned an answer of exactly the right shape, in one second. No warning, no truncation
you can see. The limit is real in the documentation and absent from the code.

And there is a setting called `padding_mode` that controls how the model is told about
values you already know about the future. Telltale's design describes it as a validity
requirement: get it wrong and the call fails. It does not fail. It succeeds, and returns a
**different forecast**, off by 1.41 on that same 30-unit scale. That is the dangerous kind
of setting: one that looks like plumbing, so somebody removes it because the tests still
pass, and the numbers move.

### Can it use the graphics chip

Your M5 has one, and torch can use it. The question is whether it gives the same answer,
because a forecast that changes depending on which chip ran it is not a measurement.

Run on both, alternating call by call so neither gets a warmer machine: the largest
disagreement on any point is **0.0000009 relative**, against a limit of 0.001 that I wrote
down before running. It is about twice as fast.

So the graphics chip is allowed. Two cautions go with that, both measured. Twice as fast
is a range, not a constant: 2.01x and 1.89x on the two runs whose numbers I kept, and
higher on rehearsals I did not keep. And loading the model onto the graphics chip cost
2.0 seconds in one run and 4.9 in the other, against 1.9 to 2.1 for the processor, so a
short job can be slower overall. The sensible default stays the processor, with the
graphics chip as a choice, and whichever was used gets recorded alongside the forecast.

### What this cost

Nothing. No agent session was started and no tokens were spent. The only outlay was a
1.32 GB download and a few minutes of laptop time per run.

One thing to know rather than to act on: the model's weights are under a
**non-commercial, non-production licence**. Research use, which is what this is, is fine.
The licence string is recorded in every result file and the design already puts your
acknowledgment of it at the wave 5 gate.
