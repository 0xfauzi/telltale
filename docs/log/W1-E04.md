# W1-E04 perturbation and fail-open under load

## OUTCOME

Ten `claude -p --model sonnet` sessions, five ON and five OFF, plus a load arm that
spent nothing, and the two questions the experiment was built on now have numbers
instead of one pair.

Overhead: the median wall difference between a recorded and an unrecorded session is
**0.986 s** on a **9.584 s** median unrecorded session, and the OFF arm's scaled MAD is
**0.7265 s**. By the brief's rule that is "the overhead exceeds run-to-run noise at
n = 5". By design 6.12's own yardstick it is not: `MDD = 2.8 s sqrt(2 / n)` gives
**1.2865 s** at n = 5, which is larger than the difference. Both numbers are in the
write-up and the second is the one to act on. The child's own clock agrees on direction
and size: median delta_api **891 ms**, so most of the difference happens inside the
child, not in the wrapper around it.

Fail-open under load: **no violation**. 1555 of 1555 POSTs answered 200, slowest
**186 ms** against the 300 ms bound, the scripted agent exited 0 and wrote the same
5636 bytes in both captures, and the flooded capture stored the same **17** stream
observations as the quiet one. The drop path was NOT exercised: the queue held 580 of
10,000 and `drops_total` was 0, so the receiver was never saturated.

Completeness: all five ON captures record non-zero `surfaces_received` for hook,
otel_logs, otel_metrics and stream. No zero anywhere, 4/4 coverage on all five.

New: `experiments/E04/run.py` (797 lines), `experiments/E04/load.py` (271),
`experiments/E04/child.py` (52), `docs/experiments/E04.md`, and the committed evidence
under `experiments/E04/out/`: `results.json`, `floor.json`, `load/results.json`,
`load/load.json`, `load-unequal-names.json` and the ten `pair<k>/<arm>.meta.json` files.
No source file changed. `uv run ruff check experiments/E04` and
`uv run ruff format --check experiments/E04` pass; `pre-commit run --all-files` passes.

## WHAT WAS WRONG

**The brief's load-arm child configures no stream surface, so rule (2) would have had
nothing to compare.** The brief specifies `bash -c 'echo $OTEL_EXPORTER_OTLP_ENDPOINT >
endpoint.txt; exec python fake_agent.py -p "..." --output-format stream-json --seed 7'`.
The launcher decides what to configure by SCANNING the child's argv
(`src/telltale/providers/claude_launch.py:launch`): it tees stdout only when
`--output-format` and `stream-json` are separate tokens of that argv, and it inserts
`--session-id` only when it sees `-p`. Flags inside a `bash -c` string are not tokens of
the child's argv. Measured rather than reasoned: that exact command was run once and
recorded as capture cap_01M1GSPCQ6J9H23PHHJCDJ17NP, which ended with
`surfaces_received` EMPTY and 5 observations, all of them the launcher's own.
`experiments/E04/child.py` puts the same two flags where the launcher can see them, and
adds the two waits that let a 20 s flood overlap a sub-second agent.

**`uv run` from inside the fixture repository resolves the wrong project.** The brief's
ON command is `uv run telltale run ...` with the session's cwd set to a copy of E01's
fixture repository. That copy carries its own `pyproject.toml` (`e01-fixture`, no
telltale dependency) and `uv run` resolves its project from the current directory. The
runner passes `--project <repo root>`, which pins the resolution and changes nothing
else. Stated in the write-up as a deviation.

**A `dropped` diagnostic carries no capture id, so the brief's verification query cannot
find one.** `Store._diagnose_here` writes the row on the writer thread with
`capture_id = None` (`src/telltale/store.py`), because a drop is a property of the queue
and not of any one capture. The brief's `select kind, count(*) from diagnostics where
capture_id in (<the two load capture ids>)` therefore reports zero drops for a receiver
that dropped thousands. The runner records both: the diagnostics that name the capture,
and the `dropped` rows whose `ingest_ts` falls inside the capture's window. On this run
both are empty, which is a real zero rather than a query artefact: `select count(*) from
diagnostics where kind='dropped'` over the whole database is 0.

**My own first load run measured the harness, not the recorder.** The two stdouts came
out 5639 and 5637 bytes. The scripted agent prints its working directory in its `system`
init line and the two repository copies were named `unloaded` and `loaded`, two
characters apart. The directories were renamed to `quiet` and `flood` and the arm was
re-run: 5636 both. The superseded run's numbers are kept in
`experiments/E04/out/load-unequal-names.json` because the write-up cites them.

**The two arms are the same prompt and not the same session.** In pair 1 the OFF
session took 2 turns and 67,151 tokens where the other nine sessions all took 3 turns
and about 101,000, and that pair's delta is 6.104 s against a median of 0.986 s. It is
kept in the rule's numbers, because dropping it would mean choosing data after seeing
it, and reported separately as a matched-turn row (n = 4, median 0.642 s).

## WHAT CHANGED

Nothing under `src/`. Three new scripts under `experiments/E04/`, one write-up, one log.

The order the reasoning ran:

1. Read the launcher, the receiver and the store to find out what a capture actually
   configures and what the receiver does when its queue fills. That is where the
   `bash -c` finding and the capture-id-less `dropped` row came from, before any
   session ran.
2. Read this process's own environment, because the brief said it would carry the
   orchestrator's OTEL variables. It does not: only `CLAUDE_CODE_ENABLE_TELEMETRY`
   survives into a subprocess on this machine. The strip rule is still applied by
   prefix and name rather than by a list, and the names removed are recorded per
   session rather than assumed.
3. Measured the floor (`--floor`, no tokens): the wrapper around an empty child costs
   0.3507 s. Without it the delta cannot be read as anything but a sum.
4. Rehearsed the whole load arm at 3 s and 2 threads before running it at 20 s and 4.
   That rehearsal is what surfaced the parse path and the row volume.
5. Ran the pilot pair, checked both sides against the 60 s and 200,000 token limits,
   then the remaining four pairs. Ten sessions, the budget exactly.
6. Ran the load arm, found the 2-byte stdout difference, fixed the harness, re-ran.

## UNSURE OR NOT DONE

**The receiver's drop path is untested.** 4 threads for 20 s put 155,500 observations
through the store at about 7,800 a second and the queue never rose above 580 of 10,000.
So this run shows the receiver answers fast when it is NOT saturated, which is a weaker
statement than the one design 6.5 makes. Saturating it needs more threads or a slower
disk, and until then the 250 ms wait and the droppable-type policy are read and not run.

**Whether the 0.986 s is the recorder.** The direction is consistent in 4 of 5 pairs and
the child's own clock agrees, but n = 5 cannot resolve a difference this size, and the
ON arm also carries `uv run` (0.3507 s of floor). Nine pairs per arm at this spread
would resolve 0.986 s; twenty-one would resolve 0.642 s.

**One prompt, one model, one machine, one afternoon.** Nothing here says what a session
that edits files or runs tests costs, and the hook surface fires more on such a session.

**This experiment left 475 MB in `~/.telltale/telltale.db` plus a 99 MB write-ahead
log**, mostly synthetic: 155,500 rows in the flooded capture, 176,200 in the superseded
one, 37,800 in the rehearsal. The database also holds this session's own capture, since
the inner and outer captures share the store by design. Nothing was purged: deleting
rows from the owner's flight recorder is the owner's call. `telltale purge <capture_id>`
removes one capture, and the ids are in `experiments/E04/out/load/results.json` and in
`uv run telltale sessions`.

**The `unknown_field` diagnostics are mine, not a defect.** The flooded capture logged
1555 of them, one per batch, naming `claude.otel.api_request.organization_id` and
`claude.otel.api_request.user_id`. Those attributes are on the real E01 records too and
the allowlist does not carry them. Worth a look in a task that owns the allowlist; it is
not a finding of this experiment.

## NEXT

1. **Saturate the receiver.** The load arm as specified never filled the queue. A
   follow-up should raise threads until `queue_depth` approaches `queue_max`, then check
   that droppable types are dropped, non-droppable ones wait at most 250 ms, every POST
   is still 200, and a `dropped` diagnostic appears with the right per-surface counts.
2. **Nine pairs, not five,** if the owner wants a comparative claim about capture
   overhead. That is nine more sessions at about 10 s each, and the spread may change.
3. **Give a `dropped` diagnostic a capture id, or document that it has none.** Today a
   reader who filters diagnostics by capture sees a quiet session where records were
   lost. The row is written outside any capture on purpose; the fix may be a note in
   design 6.5 rather than a code change.
4. **Consider whether `--project` belongs in the launcher's own documentation.** Any
   experiment that runs a wrapped session inside a repository copy will meet the same
   uv resolution problem.

# EXPLAIN FOR THE OWNER

## What was at stake

Telltale's promise is that it changes nothing about the session it records. Until today
the evidence for that was one pair of sessions from E01, where the recorded one took
0.913 s longer than the unrecorded one on a 9 second job. One pair cannot tell you
whether that second is the recorder or just a slow morning, and everything downstream
that compares recorded work to unrecorded work is standing on it.

## What "overhead" means here, and how it was measured

An overhead is a difference between two things that are otherwise the same. So the
experiment ran the same session twice: once with `telltale run` wrapped around it, once
without. Same prompt, same model, same flags, a fresh copy of the same throwaway
repository each time. Five times, alternating, so that if the machine got slower during
the afternoon both arms felt it.

Wall time here is the plain thing: a stopwatch started before the process and stopped
when it exits. That is what a person waiting at a terminal experiences. Alongside it,
the session reports its own duration in its final output line, measured by its own
clock inside the process. Having both matters, because they answer different questions:
the stopwatch includes the wrapper starting up, and the session's own clock does not.

One thing had to be got right before any of it meant anything. This experiment itself
ran inside a recorded session, so the environment it hands to a child already carries
the recorder's settings. A child that inherits them exports its telemetry to the
recorder that is watching ME, which makes the OFF arm not off. The runner removes every
variable whose name starts with `OTEL_` and the variable
`CLAUDE_CODE_ENABLE_TELEMETRY`, and writes down which names it actually removed. On this
machine that turned out to be one name: `CLAUDE_CODE_ENABLE_TELEMETRY`. The eight
`OTEL_` variables the outer launcher sets do not reach a subprocess of the session at
all. That is a measurement, not the answer I expected.

## One real pair, with its numbers

Pair 3, from `experiments/E04/out/pair3/on.meta.json` and `off.meta.json`:

- Recorded: 9.971 s on the stopwatch, 7407 ms on its own clock, 3 turns, 101,016 tokens,
  exit 0.
- Not recorded: 9.673 s on the stopwatch, 7193 ms on its own clock, 3 turns, 101,125
  tokens, exit 0.
- Difference: 0.298 s on the stopwatch, 214 ms on the session's own clock.

Now put it next to pair 4, where the recorded session was 43 ms FASTER than the
unrecorded one. Two pairs, two answers, opposite signs. That is the whole problem in two
rows.

## Why five pairs cannot settle this, and what number would

Line the five differences up in order: -0.043, 0.298, 0.986, 2.136, 6.104 seconds. The
middle one is 0.986 s. Is that a real cost, or is it what you get from five noisy
measurements of nothing?

To answer that you need a measure of how much the sessions vary on their own. The one
this project uses is the scaled MAD: take the median, take how far each value sits from
it, take the median of THOSE distances, and multiply by 1.4826 so the number is
comparable to a standard deviation for well-behaved data. For the five unrecorded
sessions that is 0.7265 s. So the unrecorded arm alone wanders by about three quarters
of a second from run to run.

The brief's rule says: if the median difference is bigger than that spread, report that
the overhead exceeds run-to-run noise. 0.986 is bigger than 0.7265, so that is what the
gate report says, and both numbers are quoted.

Design 6.12 sets a harder bar, and it is the one worth trusting. It asks the smallest
difference you could reliably detect at the sample size you actually have:

    MDD = 2.8 s sqrt(2 / n)

`s` is that spread, 0.7265 s. `n` is the number of pairs, 5. The 2.8 is the sum of two
standard normal cut-offs, one for a 5 percent false-positive rate and one for 80 percent
power; the `sqrt(2 / n)` is there because you are comparing two arms, each with its own
sampling error. Put the numbers in: 2.8 times 0.7265 is 2.034, times sqrt(2/5) which is
0.632, gives **1.2865 s**.

The difference we measured, 0.986 s, is SMALLER than the smallest difference this design
can detect at five pairs. So the correct reading is that a difference of this size is
not resolved at n = 5, and the rule's simpler comparison flattered it.

Rearrange the same formula to ask how many pairs it would take. Set MDD equal to the
difference you want to detect and solve for n:

    N_needed = ceil(2 (2.8 s / delta)^2)

For delta = 0.986 s: 2.8 times 0.7265 divided by 0.986 is 2.063, squared is 4.256, times
2 is 8.51, so **9 pairs per arm**. If you take the more conservative difference from the
four pairs where both sessions did the same number of turns, 0.642 s, the same formula
gives **21 pairs**. Nine more sessions is about two minutes of agent time. Twenty-one is
a different conversation.

One honest caveat about pair 1, the 6.104 s outlier. Its unrecorded session took 2 turns
and 67,151 tokens, where all nine other sessions took 3 turns and about 101,000. It did
less work, so it finished sooner, and none of that is about the recorder. I left it in,
because deciding which data to drop after seeing it is how you get the answer you
wanted, and reported the four matched pairs separately so you can see both.

## The load run: what it showed and what it did not

The second question was what the receiver does when it cannot keep up. The receiver is
the small HTTP server the launcher starts inside itself; every surface the agent
produces is posted to it. The rule the design commits to is that it always answers,
quickly, no matter what: an agent's hook waits for that answer inside a 5 second
timeout, so a slow or missing answer is a change to the behaviour of the process being
recorded, which is the one thing this system must never do.

So: a scripted agent that spends no tokens was captured twice. Once against a quiet
receiver. Once while four threads posted 129 KB batches of a hundred synthetic records
each at it as fast as they could go, for twenty seconds. The scripted agent was made to
wait six seconds before doing its work and sixteen after, so that its whole run sits
inside the flood; both captures wait the same, so the only difference between them is
the flood.

What it showed: every one of the 1555 POSTs was answered 200. The slowest took 186
milliseconds, against a 300 ms bar. The agent exited 0 in both runs and wrote exactly
the same 5636 bytes of output. The flooded capture stored the same 17 records from the
agent's own output stream as the quiet one. Nothing about the agent changed.

What it did NOT show, and this is the part to hold on to. The queue in front of the
database holds 10,000 records. At the moment the flood ended it held 580, with 501 more
already being written. It was never close to full. So the flood proved the receiver is
fast when it is not saturated, and said nothing about the behaviour the design actually
promises for saturation: that low-value records are thrown away on purpose, that
everything else waits at most 250 ms, that a POST is still answered 200, and that the
loss is counted and written down. Four threads on this machine could not outrun the
writer, which turns out to swallow about 7,800 records a second. Finding the edge means
pushing harder, and that is the next experiment rather than a footnote to this one.

One cost you should know about. The load arm writes its synthetic records into your real
capture database, which is what makes it a test of the real store instead of a stub.
`~/.telltale/telltale.db` is now 475 MB with a 99 MB write-ahead log, most of it
synthetic rows from this experiment. I did not delete any of it: removing rows from your
flight recorder is your call, not mine. `telltale purge <capture_id>` removes one
capture, and the ids are in `experiments/E04/out/load/results.json`.
