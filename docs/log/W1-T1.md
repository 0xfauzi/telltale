`telltale run` records a wrapped child, `telltale daemon` records the sessions the owner
starts by hand, and `telltale sessions` lists what either wrote. New:
`src/telltale/launch.py` (761 lines), `tests/integration/test_launcher.py` (387),
`docs/design/03-capture-howto.md`. Changed: `cli.py` (447 to 621), `receiver.py` (576 to
677), `store.py` (699 to 765), `allowlist.py` (three fields), `docs/README.md` (one row).

`uv run pytest -m integration`: 40 passed in 6.95 s (33 before this task, 7 added). Every
gate green: `uv run mypy .` (25 source files), `uv run ruff check .`,
`uv run ruff format --check .`, `uv run deptry .`, `uv run pre-commit run --all-files`
(29 passed, 3 skipped, 0 failed).

Measured, with the command that produced each number in VERIFY at the end:

- The launcher costs 213 ms per capture: `telltale run -- true` is 214.7 ms median over
  ten runs against 1.8 ms for `true` alone. Cold, on the first run of the day, it was
  306 ms. Where it goes: git 98 ms (repository identity 57, end-of-capture snapshot 41),
  Python startup and imports 57 ms, receiver stop 48 ms, commit linkage 16 ms,
  environment fingerprint 5 ms, store open and two flushes 3 ms.
- Four captures started at once finish in 244 ms of wall time against 206 ms for one,
  and all four are recorded. Five bursts of four wrote 20 captures, 20 listed. The
  5000 ms busy timeout in store.py was never approached.
- A per_file entry of this repository's snapshot is 133 to 145 bytes, so the brief's cap

- Removing any one of five mechanisms makes exactly one test fail, checked by patching

  environment removal, the receiver's default capture, and the flush before commit

- CI found a real concurrency bug that this machine hid, and it is fixed and measured:
  see the last entry of WHAT WAS WRONG.

## WHAT WAS WRONG

**`Receiver.stop()` was 391 ms of the 659 ms every capture cost.** socketserver's
`serve_forever` looks for a shutdown request every 0.5 s by default and `shutdown()`
waits for the next look, so every `telltale run` paid up to half a second to close a
server that had nothing left to do. Measured by timing each phase of one capture in
order (VERIFY 5). `poll_interval=0.05` in `Receiver.start` takes the same stop to 48 ms.
The whole integration suite fell from 22.5 s to 8.6 s with that one line, because every
test that starts a receiver was paying it too.

**An empty queue is not a write barrier**, which W0-T5 measured and W0-T4's
`receiver._replay` still relied on: `_drain()` polls `queue_depth` and the writer takes
its job off the queue BEFORE it opens the transaction. `Store.flush(timeout)` puts a job
of its own at the back of the queue and waits for the writer to reach it; because every
job's Event is set after the `with conn` block that committed its batch, a set Event
means committed and readable. `_replay` now flushes before it counts, and the launcher
flushes before it reads its own capture back.

**The brief's per_file cap of 100 entries does not fit the payload bound.** A per-file
entry of this repository is 133 to 145 bytes (a repo-relative path, two counts and a
sha256), so 100 of them are about 13 KB against the 8 KB bound of design 6.4, and
sanitize drops an oversized field WHOLE. Capping at 100 alone would have left exactly the
empty per_file list that W0-T2 asked W1-T1 to prevent. `_capped` now cuts to 100 and then
drops one entry at a time until the payload fits, which on this repository keeps 54.
`files_changed` still carries the true count, so nothing about the size of the change is
lost, and `per_file_truncated` says the list is a prefix. The loop costs 3.9 ms for a
300-entry list, on the debounce timer thread or at capture end, never on a request
thread.

**At content level 0, per_file survived as a list of empty objects.** Every field of an
entry is cleaned as a path and level 0 keeps no path, so four changed files stored
`[{}, {}, {}, {}]`: no information, shaped like information. It is now `None`, which is
what "not recorded at this level" looks like everywhere else in this system.

**The daemon's one line per capture never appeared when its output was a pipe.** Python
block-buffers stdout when it is not a terminal, so a reader watching the daemon saw
nothing until it exited. Found by writing the verification script, which hung. Both the
header and the per-capture line now flush.

**Three fields the design's own vocabulary needs had no allowlist entry**, so the
launcher's records would have been dropped and diagnosed rather than stored:
`telltale.capture_started.env_removed` (E01 finding 6), `telltale.capture_ended`
`.worktree_id` (the wave 0 amendment that keys a capture on the repo_id and worktree_id
pair), and `telltale.repo.snapshot.per_file_truncated` (W0-T2). Added to
`allowlist.py`, which this task does not otherwise own.

**A diagnostic that fires on every capture is not a diagnostic.** The first version wrote
a `launcher` row saying "provider generic has no launch plan" for every
`telltale run -- make test`. It is not a failure, it is what wrapping something that is
not an agent means, so `generic` now takes the same path silently. A missing `codex`
module still writes the row, because that one is a fact worth seeing.

**`PRAGMA journal_mode = WAL` is the one statement SQLite does not apply the busy
timeout to, and two concurrent captures on a new database therefore raced.** CI failed
the two-capture test with `telltale: not recording this run: OperationalError('database
is locked')`, which is the launcher failing open correctly around a store that would not
open. Setting the journal mode needs an exclusive lock and answers "database is locked"
at once when any other connection holds the database, whatever the busy timeout says.
Measured with four processes released by a barrier onto a fresh database, 100 opens: 30
raised. Reading the mode first fixes every open after the first, because WAL is a
property of the file; it does not fix the first, where all four read `delete` and all
four try to change it (23 of 100). Both together, with the store's existing retry
delays: 0 of 100. The test now starts four captures rather than two, because two is a
coin flip; with the fix removed it fails 1 run in 5 on this machine, and CI's Linux
runner failed the two-way version on its first attempt.

## WHAT CHANGED

**`src/telltale/store.py`**. `flush(timeout) -> bool`, the barrier described above, and
`in_flight` in `health()`: how many jobs the writer has taken off the queue and not yet
committed, which is exactly the set `queue_depth` hides. `open()` splits into `_prepare`
and `_create`: read the journal mode before setting it, and retry the whole schema step
while another process is doing the same.

**`src/telltale/receiver.py`**. `default_capture`: `telltale run` serves one capture, so
every otherwise-unattributable record falls into it instead of `unattributed`, with no
diagnostic. `derive_captures`: the daemon serves many, so an unregistered provider
session id becomes `cap_<sha256(session id)[:24]>`, derived so that the same session
lands in the same capture across daemon restarts. The two are exclusive by construction.
`bind_capture` gives a capture the repo_id and environment fingerprint id the launcher
observed, so every provider record carries them in its columns. `on_new_capture` is the
callback the daemon prints from. Plus the poll interval and the replay flush.

**`src/telltale/launch.py`**, new. `run(args)` opens the store, starts the receiver on a
free port with this capture as its default, asks the provider module for a launch plan,
emits `telltale.repo.identity`, `telltale.environment` and `telltale.capture_started`,
registers the session id when the plan actually used one, wires a 2 s debounced
repository snapshot to file mutations, spawns the child, tees stdout when the plan says
to, and on exit stops the receiver, flushes, takes a final snapshot, links commits, emits
`telltale.capture_ended`, flushes again and closes. It returns the child's exit code, or
128 plus the signal number. There is no linger: E01 and E02 measured the last request
arriving before the child exits on all 13 exporting scenarios, so what is waited for has
already been accepted and `flush()` is what proves it is on disk. Every step runs inside
`_guard`, which turns any exception into a `launcher` diagnostics row.

**`src/telltale/cli.py`**. `run`, `daemon` and `sessions`, plus `_configured`, which
generalises the old `_daemon_port` so that `content_level` can come from `config.json`
the same way and with the same refusal to fall back on a value that is not a number.

**`tests/integration/test_launcher.py`**, new, seven tests, all driving the installed
console script as a subprocess: the exit code, the byte-for-byte tee of three recorded
Claude Code stream lines, SIGTERM to 143, four concurrent captures, stdin passthrough
with the environment names removed, a `--settings` of the owner's own merged rather than
replaced, and one test that runs the whole loop (the child reads the
hook URL out of the `--settings` the plan gave it, POSTs a PostToolUse body naming a
commit, and the launcher attributes it with no session binding and links the commit).

**`docs/design/03-capture-howto.md`**, new, for the owner.

## UNSURE OR NOT DONE

- **SIGINT is absorbed and not forwarded, and that is a judgement.** Nothing here starts
  a new session, so the child shares this process's group and the terminal delivers
  Ctrl-C to it directly; forwarding a second copy would be a second Ctrl-C, which in
  interactive Claude Code quits the session instead of cancelling the turn. The cost is
  that `kill -INT <launcher pid>` alone does not reach the child. I did not test the
  interactive double-Ctrl-C behaviour, because it needs a real session. SIGTERM is
  forwarded and tested; SIGHUP and SIGQUIT are not handled at all.
- **`runtime_version` on the environment fingerprint is always None.** Reading it costs a
  process spawn per capture and the provider's own records carry `service.version`
  (W0-T4), so the parser should fill it in. Nothing does yet, so every capture's
  fingerprint is computed without it and two runs of different Claude Code versions
  currently fingerprint the same.
- **The coverage column counts REQUESTS, not observations.** `receiver.counts()` counts
  one per POST, so a surface that delivered a request which parsed to nothing still reads
  as delivered. The real per-capture coverage is the activities reducer's job (design
  6.7) and this column is a summary; a surface that delivered nothing at all is still
  visibly short.
- **`sessions --link-commits` only links captures in the repository you are standing in**,
  because a capture stores the sha256 of its root and not the root. It also skips
  captures that already have a linked commit, which is the brief's rule and means a
  second commit for the same session is never picked up.
- **A daemon capture has no repository identity, environment fingerprint or snapshot.**
  Nothing told the daemon which repository the session is in. The session's own records
  are all it has, and `sessions` shows those captures with `-` in the coverage column.
- **The concurrency test is a stochastic guard, not a deterministic one.** With the
  store's open fix removed it fails 1 run in 5 on this machine, because four `telltale
  run` processes start about 30 ms apart and the race needs them inside the same few
  milliseconds. It never fails when the code is right (0 of 100 barrier-aligned opens).
  The deterministic evidence for the fix is the barrier-aligned reproduction quoted in
  VERIFY, which is a scratchpad script rather than a committed test: making it a test
  would mean spawning processes from inside pytest with a shared barrier, and I judged
  the end-to-end version plus the reproduction to be the better trade. Someone could
  reasonably differ.
- **The fail-open path where the store cannot be opened has no test**, although CI ran it
  for real: the launcher wrote `telltale: not recording this run` to stderr and the child
  still exited 0. That is the behaviour I wanted; it is covered by evidence rather than
  by a test.
- **`launch.py` is 761 lines against the 800-line ratchet.** The next change to it has to
  move something out. The reading half (`Facts`, `facts`, `link_commits`, about 110
  lines) is the obvious candidate and is only there because no other module owns "read a
  stored capture" yet.
- **The 0.05 s receiver poll is a decision, not a measurement.** It bounds `stop()` at
  50 ms and costs one select wakeup 20 times a second; I measured the stop, not the CPU
  cost of the wakeups over a long daemon run.
- **`telltale purge` does not exist**, so the how-to tells the owner to delete the
  database file or call `Store.purge` from Python. The store has the function; the design
  gives the command to a later task.
- **Level 2 still records what level 1 records**, unchanged from W0-T4 and W0-T5.

## EXPLAIN FOR THE OWNER

### What was at stake

A recorder that cannot say which session a record belongs to is a recorder that mixes two
sessions and reports the average. Everything below is about attribution, and about the
one moment where it is easy to lose data without noticing: the end.

### First question: how does a record know which session it is from?

Claude Code sends its telemetry to a web address. Telltale runs a small web server on
your own machine to receive it. When two sessions are running, both send to a server, and
something has to sort the records out.

The design's answer was a map: the launcher generates a session id, passes it to the
agent on the command line, and remembers "this session id belongs to this capture". That
works when the launcher started the agent. It does not work at all for a session you
started yourself in a terminal, because nobody was there to generate an id.

So there are two answers, one for each way of starting an agent, and the code now says
which one it is using rather than guessing.

When you wrap a command with `telltale run`, the server that gets started serves exactly
one session, its own. So it is told which capture that is, and anything that arrives
belongs to it. There is nothing to work out.

When you run `telltale daemon`, it serves whatever sessions you start, and no launcher
named any of them. Here the session's own id becomes the capture id, by hashing it:
`cap_cf4c4732fd3b8f8a55b60871` in the verification below is the SHA-256 of the session id
Claude Code generated, cut to 24 characters. Hashing rather than counting matters for one
reason: restart the daemon in the middle of a session and the same session still lands in
the same capture, because nothing is remembered between runs.

### Second question: when is it safe to stop?

The launcher stops when the agent stops. But the records arrive over a network
connection, get parsed, and then get handed to a queue that one background thread writes
to the database. So "the agent has exited" does not mean "everything is on disk".

The original plan was to wait a few seconds after the child exits, in case the agent sent
something late. Two experiments killed that idea: on both Claude Code and Codex, the last
record arrives BEFORE the child exits, every time, across thirteen sessions. So there is
nothing to wait for, and a fixed wait would have been dead time added to every capture.

What is left is a real question: has the writer finished with what it already accepted?
The previous answer was to watch the queue until it was empty. That answer is wrong, and
the wave 0 work had already measured why: the writer takes a job OFF the queue before it
starts writing it, so the queue reads as empty while the last batch is still in flight.
Read the database at that instant and you see fewer records than you sent.

The fix is a queue job that does nothing. Put it at the back of the queue and wait for it
to be reached. It cannot be reached until everything ahead of it has been written and
committed, so when it comes back, everything is on disk. That is `Store.flush`, and it is
four lines of behaviour with one line of purpose.

I did not take this on trust. I deleted the flush call, ran the test that depends on it
five times, and watched it fail five times out of five.

### Third question: what may the recorder change about your session?

Nothing that you would notice, and the code is arranged around that.

Your exit code comes back unchanged, including 143 when the agent was killed by a signal.
Your standard output is passed through byte for byte, and when the agent is producing
JSON, each line is echoed first and recorded second, so nothing waits on the recorder.
Your standard input and standard error are the terminal's, untouched. Every failure
inside Telltale becomes a row in a diagnostics table instead of an error you see.

There is one deliberate exception, and it is a fix rather than a cost. When Telltale runs
under `uv run`, it holds a virtual environment of its own, and a child would inherit it
and then run the wrong Python inside your repository. Experiment E01 watched a session
lose a whole turn to that. So two environment variables are removed from the child, and
which ones were removed is recorded in the capture, because a recorder that changes the
thing it records must say so in the record.

Ctrl-C deserves a paragraph of its own, because I chose the less obvious answer. The
obvious design forwards every signal to the child. I do that for SIGTERM, which nothing
else sends. I deliberately do not do it for Ctrl-C, because your terminal already sends
Ctrl-C to the child directly, and a second copy from the launcher would read as a second
Ctrl-C, which in Claude Code quits the session rather than cancelling the current turn.
The price is that killing the launcher with `kill -INT` by hand will not reach the agent.
That is a real gap and I am telling you rather than hiding it. If you would rather have
the forwarding, it is one line.

### Fourth question: how much does it cost you?

213 milliseconds per session, measured ten times over. Not per turn: per session. Almost
half of it is git, reading what your repository looked like at the start and what changed
by the end.

I found one bad number while measuring, and it is the kind worth telling you about
because it was invisible. Shutting down the little web server was costing 391 of the
659 milliseconds a capture took, because Python's server checks for a shutdown request
twice a second and my code waited for the next check. Checking twenty times a second
instead took that to 48 milliseconds. The same line took the whole test suite from 22.5
seconds to 8.6, since every test that starts a server was paying it too. That is the
value of timing each step rather than the whole.

### The one thing I am least sure about

Coverage. The `sessions` table prints a fraction like `0/3`, meaning three record sources
were configured and none delivered. It counts a source as having delivered if at least
one request arrived on it, which is not quite the same as "it produced facts". The proper
computation belongs to the next task, which reads the records rather than counting the
requests. For now the fraction is honest about the direction and rough about the detail,
and where a source was never configured it prints a dash rather than a zero, which is the
distinction the whole system exists to keep.
