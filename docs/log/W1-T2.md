# EXPLAIN FOR THE OWNER

## What was at stake

Telltale records what an agent did. Until this task it could only replay the recording.
There was no way to ask "how many times did it run the tests", and no way to check an
answer if there had been one.

The risk in answering is not that a number comes out wrong. It is that a number comes
out confident. A recorder that says "0 compactions" when it simply could not see
compaction has told you something false in a calm voice, and you have no way to tell
which kind of zero you are holding.

So the work is in two halves. Compute the numbers. Make every one of them walkable
back to the bytes a provider sent.

## The first question: what is one thing?

An agent runs a shell command. Four separate channels report it.

The hooks report it twice, once before and once after. The provider's telemetry reports
a decision and a result. The stream reports the assistant asking for it and the user
channel carrying the output back. That is six records for one command, arriving on
three transports at three different times.

Before you can count anything you have to decide which records are the same event.

The obvious answer is time: records that happened together belong together. It is
wrong here, and the reason is worth holding on to. Hook bodies carry no timestamp at
all. I checked every hook observation across the eight E01 captures: `provider_ts` is
null on all of them. Their only clock is the moment they reached the receiver, which is
a fact about Telltale's network stack.

And even with perfect clocks it would fail, because agents run tools in parallel. Two
`Read` calls issued together genuinely overlap. Any rule that puts them in order is
inventing one.

The answer that works is that the provider already did it. Claude Code puts a
`tool_use_id` on every record of a tool call, on all four surfaces. So the rule is:
group by the id, never by the clock. A group is a tool call. There are six such ids in
S1, and the reducer produces exactly six tool activities.

The same rule handles the rest. Model requests group by `request_id`. Subagents group
by an agent id that the hooks and the stream both carry. Once you have the groups, an
activity is one group.

## The second question: which surface do you believe?

A group has six records and they do not agree.

Take S1's first model request. The provider's telemetry says the model produced 136
output tokens. The stream's assistant message for the same request says something
different, because the stream reports usage as it streams and the telemetry reports it
when the request finishes. Both are honest. They are measurements of different moments.

Averaging them would produce a number no surface reported. Taking the last one to
arrive would make the answer depend on network timing. So neither.

The rule is a fixed ranking of surfaces, per field, decided once and written down in
`correlate.SOURCE_ORDER`. The highest-ranked surface in the group that carries the
field supplies the value. The disagreement is not discarded: it becomes a `conflict`
row in the diagnostics table naming both observation ids, the field, both values, and
which one was kept. S1 has seven of these, one per request.

A surface that is not in the ranking contributes its timestamps and its ids and no
values at all. That is deliberate. An unranked surface is one nobody has compared
against the others, and a value from it would be trusted by accident.

## The third question: where did this number come from?

Every value written carries the id of the observation it came from. Not the activity,
the individual field: `output_tokens` records which observation supplied it, separately
from `duration_ms`.

That is what makes `telltale explain` possible. Ask it about a number and it walks:
the Evidence row, then each activity in its source list, then each observation those
activities point at, then the raw payload the provider sent. Every step resolves or the
reducer has a bug, and there is a test that fails if any id anywhere fails to resolve.

Here is the top of a real walk, `telltale explain S1-L1 model_requests`:

```
metric           model_requests
value            7 requests
claim_class      derived
coverage         observed
sources          7

  act_b5c036d73163ac6cafc5e9c4a6  model_request  agent  2026-09-01T20:04:21.422Z
    output_tokens <- 01M1FTTMKCNQTAVR1H4FEWT0N6
    01M1FTTMKCNQTAVR1H4FEWT0N6  claude.otel.api_request  otel_logs  ...
      {"cache_creation_tokens": 14823, ..., "output_tokens": 136, ...}
```

The number 7 is not printed by anything that computed it. It is a stored Evidence row
with a claim class, a coverage word and seven sources.

## The compaction problem, which had no id

Compaction is when the agent's context gets full and the session summarizes itself to
make room. Three surfaces see it. A hook fires before, another after, the telemetry
emits an event, and the stream emits a boundary marker with token counts.

None of them shares an id. There is nothing to group by.

S7 compacted four times, so I could measure rather than guess. What I found:

- The hooks and the telemetry arrive interleaved in real time, in a repeating order:
  PreCompact, then the telemetry event, then PostCompact.
- The stream does not, because a replay posts the whole stream file after the whole
  hooks file. Its arrival order relative to the others is an artefact of how Telltale
  replays, not of what happened.

So the rule has two parts. Cut episodes in arrival order over the two surfaces that
arrive live: a record whose role the open episode already holds starts the next one.
Then attach each stream boundary by exact match on its two token counts, because
`pre_tokens` and `post_tokens` on a boundary equal the telemetry event's to the token.
A boundary matching nothing becomes its own episode rather than being attached to a
guess.

On S7 this reproduces the four compactions with pre-token counts 34181, 35113, 38398
and 42366. The first one failed with `too_few_groups`, reported no post-token count,
and produced no stream boundary. Its `surfaces` field is `["hook", "otel_logs"]`; the
other three are `["hook", "otel_logs", "stream"]`.

That failure is the reason `post_compaction_tokens` is 17240 with coverage `partial`
and a warning saying one of four compactions carried none. A total of 17240 with
coverage `observed` would be a smaller number that looks complete.

## The subagent problem, which had a clock going backwards

S4 delegates to a subagent. The first version produced a subagent activity whose start
was after its end.

The cause: `SubagentStart` and the stream's `task_started` carry no timestamp. Their
only clock is arrival. The subagent's completion record, from the telemetry, does carry
a provider timestamp, and it is earlier than the arrival stamp of its own start.

The fix is to borrow the start of the tool call that spawned it. That is defensible
because the two are the same span, and E01 measured how nearly: the parent `Agent` call
reports 24885 ms, the child reports 24876 ms. Nine milliseconds apart on a
twenty-five-second call. The activity records `start_source: "spawning tool call"` so
the borrowing is visible rather than silent.

Subagents also raise a counting trap. The child's requests are already inside the
capture's totals, because they are requests. The provider separately reports a token
total for the subagent. On S4 those are 92479 and 20093. They are different quantities
measured different ways, so they are stored under different names,
`attributed_total_tokens` and `provider_total_tokens`, and neither is added to the
other. Spec 13.6 says never sum a subagent twice; two fields with two names is how.

## Two clocks, and why the timeline shows a dash

Some activities have no provider timestamp anywhere in their group. The session-end
row is one: it is built from a hook and the stream result, and neither carries a clock.

The activity still needs a `started_at`, so it gets the arrival time. But arrival time
is when a packet reached Telltale, which depends on the machine and the transport. Two
replays of the same fixture produce different arrival times, so a golden file built
from them would differ from itself.

Every activity now records which clock it is on, `provider` or `arrival`. The timeline
prints the time for provider-clock rows and a dash for arrival-clock rows, while
keeping the row in its position. The reader sees the order without being shown a time
that means something else than the times above it.

## Rebuilding twice must change nothing

`telltale rebuild` recomputes the derived tables. If it produced different rows each
time, no golden file could exist and no two captures could be compared.

Two things had to go. Activity ids were random; they are now the sha256 of the capture
id, the activity type and the observation that opened the activity. Evidence
`created_at` was the wall clock; it is now the capture's last arrival time.

Measured, on a real capture, with a sha256 over every column of both derived tables:

```
== before
activities  rows=  17  sha256=a1787199b9b1955b859b0cc0db326397377b6193a7d162f9fc3600b3fda2ed57
evidence    rows=  18  sha256=748edf625667a283fcf07f97ab6d986b1b62bdd2b2a119d2010e3b2cedb22bbf
== after rebuild 1   (identical)
== after rebuild 2   (identical)
```

There was a third leak, and it was the least obvious. Diagnostics are append-only and
`store.rebuild` does not clear them, so every rebuild added seven more conflict rows
and the summary's diagnostics count grew without anything changing. The reducer now
reads what is already recorded and writes only what is not there. One conflict is one
fact, recorded once.

## The capture with nothing in it

W1-T1's launcher landed on main while this was being written, so I rebased and got
something no fixture could give me: a capture where the recorder was configured and the
agent never spoke.

```
telltale run --provider claude -- bash -c 'echo hello'
```

Three surfaces configured. None delivers, because `bash` is not Claude Code. Five
observations, all from the launcher itself.

The summary said 0 model requests, 0 test runs, 0 files read and 0 compactions.

Every one of those is false in the way that matters. Nothing was observed, so nothing
is known, and a zero says the session did those things zero times. This is the exact
substitution the whole coverage vocabulary exists to prevent, and it was sitting in my
own code because the arithmetic is right: a sum over an empty list IS zero.

The rule that fixes it is one sentence. A count over an empty set is 0 only when the
capability was observable. When coverage says `unavailable`, the count is null and a
warning says the surfaces could not show it. It is applied in one function, `_honest`,
so no future metric can forget it.

The same capture found a second bug. `repo_id` and `environment_fingerprint_id` were
null in the summary, and both were recorded. Design 6.2 puts them on the observation
ROW, as columns, rather than inside the payload, and my reader only read payloads. The
data had been there the whole time and the reducer walked past it.

I want to be plain about what that means. Both defects were invisible to the three
replayed fixtures, because in those every capability is observed and no row carries a
repository. Fifteen passing tests did not catch either. What caught them was running
the thing once against a case the fixtures do not contain, which is a better argument
for the launcher landing first than any I would have made in advance.

## The number that can still mislead you

S1's summary says three test runs, zero failed. The scenario is "fix the failing test".

Both are true. The agent ran `uv run pytest 2>&1 | tail -50`, three times. A shell
pipeline reports the exit status of its last program, which is `tail`, which always
succeeds. Every surface faithfully recorded a successful command. The first run's
captured output says "1 failed, 1 passed".

This is not a gap in the recorder and there is no surface that would fix it. The exit
status was destroyed by the command the agent chose to run.

I could not find a rule that recovers the truth without guessing, and parsing the
output text for "failed" would be a guess dressed as a measurement. So the number
stands and says what it rests on. The Evidence carries an assumption naming the
definition, and when a capture has test runs and none of them failed, it carries a
warning:

> no test run reported a failing exit status, which is not the same as every test
> passing: a run whose command pipes the test runner into another program reports that
> program's status (S1 measured exactly this)

S7's one test run was `uv run pytest` with no pipeline. It reports failure with exit
code 2, and no warning appears.

I want to be plain about my confidence here. The measurement is certain: I read the
commands out of the fixture and the outputs out of the stream. The choice to warn
rather than to compute is my judgement, and someone could reasonably prefer that
`failed_test_runs` be null in this case. I chose the warning because zero failing
commands IS what the surfaces observed, and spec 13 defines a verification run by its
exit status.

Writing that check found one thing worth knowing. Counting the pytest calls through
`PostToolUse` hooks gives 0 for S7, not 1, because a tool call that FAILS emits
`PostToolUseFailure` instead. The reducer already relies on this (it is one of the three
ways a tool outcome is established), but a check that did not know it would have
disagreed with the reducer and looked like a bug in the reducer. Counting `PreToolUse`,
which fires once per call whatever happens, gives 3 / 0 / 1.

The two paths for the four token counters are genuinely independent: the reducer sums
per-request telemetry records, and the check also reads the stream's own end-of-session
total, which the provider computed separately. They agree to the token in all three
captures. That agreement is the strongest evidence in this task that the correlation is
right, because a double-counted or dropped request would break it.

Sums over an empty set are null, not zero. S1 has no compaction, so
`pre_compaction_tokens` is null: there is no token count to report, and 0 would be a
measurement nobody made. Counts over an empty set ARE zero, and they are supported by
the capture's own lifecycle row, which carries the coverage saying the capability was
observable. That is why S1's summary can say `compactions: 0` with coverage `observed`
and mean it.

## What the tests actually check

There are seven tests, in `tests/integration/test_capture_to_summary.py`. Each replays
a real captured session over HTTP into a real receiver and a real store, then invokes
the command through `cli.main`. Nothing is stubbed.

Three are goldens: `show` and `timeline` for each scenario, compared byte for byte
apart from the reducer version, which is a hash of the source and would otherwise make
every golden a diff of itself.

The other four hold the rules that a golden would not catch if the golden were
regenerated carelessly. Two rebuilds produce identical rows. Every source id and every
provenance id resolves to something stored. S7's four compactions carry the right
counts on the right surfaces. S4's subagent has both token numbers and they are not
added together.

## Running it

Nothing here writes to any capture. `timeline`, `show` and `explain` open the database
read-only. `rebuild` writes, and only to the derived tables, which it recomputes from
observations it never touches.

```
uv run telltale timeline <capture-id>     # one row per activity, in start order
uv run telltale show <capture-id>         # the Appendix B summary as JSON
uv run telltale explain <capture-id> <metric>   # one number, walked back to bytes
uv run telltale rebuild [capture-id]      # recompute activities and evidence
```

`telltale show` with no stored capture, or a capture id that does not exist, prints the
ids it does have rather than an empty result.
