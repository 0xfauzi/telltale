## WHAT WAS WRONG

**1. Codex writes absolute paths into its own error prose, and prose is not a path.**
This is the one that would have shipped a real leak. `Kind.SCALAR` scrubs secrets out of
a string and bounds its length. It does not rewrite paths, because the value it is handed
is not a path. But `codex.exec.error.error` is Codex's own message, and on all seven E02
scenarios one of them reads `failed to parse hooks config <home>/.codex/hooks.json`.
Measured, before the fix: the home directory was in the database file on all seven, and
the repository root twice per session. `providers.prose()` now runs the same
`sanitize.relativize` the PATH kind uses over each absolute run inside the text, so
`.../home/.codex/hooks.json` becomes `<outside>/09983486` and
`.../repo/.codex/hooks.json` becomes `.codex/hooks.json`. A slash that is not a path is
left alone: `https://example.com/x`, `10/20` and `read/write` come through untouched, and
at level 0 the run becomes `<path>` rather than a relative path. Broken deliberately, the
two whole-database tests fail on all seven Codex sessions.

`claude.py` has the same gap on its own `error` field, where W0-T5 exempted it for the
repository root. It is not exempted for the home directory, and Claude has not been seen
to put one there. The fix lives in `providers/__init__.py` rather than in `codex.py` so
that lifting it into `sanitize.py`, where it belongs, is a move and not a rewrite.
`sanitize.py` is READS for this task.

**2. The command a reducer wants is not the command Codex reports.** Codex runs
everything through a login shell, so both the exec stream (one string) and the rollout
(an argv list) spell a `git status` as `/bin/zsh -lc 'git status'`. Left alone,
`commands.normalize` keeps argv[0] and the flags and makes `_` of the quoted script, so
every Codex command in the store would read `zsh -lc _` and the whole `commands`
capability would be worthless. The parser unwraps first. Measured before trusting it: on
all 10 calls that appear on both the rollout and the hooks, the unwrapped script equals
the hook's bare `tool_input.command` exactly, so this makes two surfaces agree rather
than inventing a third answer. The shell test is an explicit list of five names, not a
suffix test, because `ssh` also ends in `sh` and also takes a `-c`.

**3. The rollout spells a working directory as a URL.** `CommandExecution.cwd` is
`file:///Users/...`. A URL is not an absolute path, so the rewriter joins it to the
repository root and hands back `file:/Users/...` with the machine path intact. The scheme
comes off first. Broken deliberately, this fails on Codex S1 through S6 and not S7, which
is the scenario with no rollout.

**4. Three E02 matrix cells are wrong, and all three understate what Codex gives you.**
Each is a reading of E02's own fixtures, each is in `DRIFT` with the record that shows
it.

- Command text IS on `otel_logs`. `codex.tool_result` carries `arguments`, a JSON STRING
  holding `{cmd, workdir}` when `tool_name` is `exec_command`. E02's probe indexed JSON
  paths and could not see inside a string. The parser parses it, lifts `cmd` and
  `workdir`, and `arguments` itself stays NEVER_PERSIST, because for `apply_patch` the
  same attribute is the entire patch.
- Per-request token counts ARE on `otel_logs`, on `codex.sse_event` with `event.kind`
  `response.completed`. The wire names are kept (`input_token_count`,
  `cached_token_count`, `reasoning_token_count` and the rest) because `tool_token_count`
  was input plus output on every record and is not a count of tools.
- File change KIND is on the rollout too, as the `type` of each entry of `item.changes`,
  which is a dict keyed by absolute path where the exec stream has a list of
  `{path, kind}`.

**5. Every OTel record carries the operator's identity.** `user.account_id` and
`user.email` are on all 211 log records of the six exporting scenarios. They are removed
by the parser before `sanitize()` sees them, which is the opposite of what the Claude
parser does with an unwanted attribute, and the reason is arithmetic: leaving them to the
allowlist gate writes one `unknown_field` diagnostic per OTLP request forever and buries
the next field a Codex release adds.

**6. `timeUnixNano` is the string `"0"` on every OTel log record, all 211.** The time is
in `observedTimeUnixNano`, and in the `event.timestamp` attribute where there is one.
`provider_ts` reads those two, in that order, and never the field whose name says time.

**7. Six OTel log records carry no `event.name`.** They are DEBUG lines from the CLI's
own Rust tracing, body `flushing OTEL metrics`. They become `codex.otel.log` rather than
failing the batch of up to 20 records they arrived in, because one unnamed record must
not cost the other nineteen.

**8. `model_context_window` is not where the digest says.** It is in
`event_msg/task_started` (258400). `event_msg/token_count.info` carries a field of the
same name and it was null on every turn E02 measured. Each is stored under its own record
type and neither is ever copied to the other.

**9. The rollout and the exec stream disagree about capitalization.** The rollout spells
item types `CommandExecution`, `FileChange`, `Reasoning`; the exec stream uses snake
case. The parser lowers the rollout spelling, so `item_type` means one thing on both, and
so the reasoning rule matches. That rule is W0-E02 finding 11: it has to match
`reasoning`, `agent_reasoning` and `Reasoning`, because a rule that matched only the
first missed 442 of 884 rows.

**10. `apply_patch` puts the whole patch in a field called `command`.** New file contents
included, in the hook body's `tool_input.command`. The parser lifts `command` for every
other tool and stores `patch_bytes` instead: a normalized command is bounded prose, a
patch is file content.

**11. Metrics cannot be attributed, because they carry no conversation id.** Codex has no
`OTEL_RESOURCE_ATTRIBUTES`; the only launcher-settable resource attribute is
`otel.environment`, which E02 measured arriving verbatim as `env`. So the capture id
rides there behind a `telltale:` prefix, and `hints()` strips it. A value without the
prefix is somebody else's environment name and names no capture, which is why E02's own
`telltale-e02` fixtures replay unattributed unless `--capture` is passed.

**12. Two ratchets bit, and both were right to.** `allowlist.py` reached 973 lines
against the 800-line hook, so the Codex table moved to `allowlist_codex.py`;
`allowlist_codex` imports `Kind` from `allowlist`, so one direction has to be deferred
and the import sits inside `_build_allowlist`. `codex.py` reached 885 and came down to
exactly 800, mostly by moving the OTLP walk that both providers do into
`providers/__init__.py` as `otlp_points`, which also split at the cognitive-complexity
limit (16 against 15) into a log walk and a metric walk.

## UNSURE OR NOT DONE

**The hook surface is not configured by `launch()`, and this is the STOP condition.** The
brief allowed inline hooks through `-c` if 0.150.1 accepts them. It does. Measured with
`codex doctor --json`, which reports `checks["config.load"]["status"]` and costs zero
tokens: `-c 'hooks={ PreToolUse = [ { hooks = [ { type = "command", command = "true",
timeout = 5 } ] } ] }'` loads, and `-c 'hooks="nonsense"'` is rejected, so the loader
validates the shape rather than ignoring the key, and `command` must be a string. What is
NOT measured is whether a hook registered that way FIRES under `codex exec`; E02 only
ever saw hooks fire from a project-level `.codex/hooks.json` with
`--dangerously-bypass-hook-trust`, and answering it costs a real session. Writing that
file is forbidden by invariant 8. So `LaunchPlan.surfaces` declares `otel_logs`,
`otel_metrics` and `exec_json` and not `hook`, nothing is written into any repository's
`.codex/`, and the hook PARSER ships and is exercised by the fixtures. This needs
measuring in the first launcher capture. There is also no `telltale hook` command for
such a hook to call yet, which is W1-T1's.

**`otel.tool_result={ max_bytes = 0 }` is accepted and its effect is unmeasured.** The
loader takes it (re-measured here with `codex doctor --json`; it is a `ToolResultLogConfig`
and not a boolean, so `-c otel.tool_result=false` is refused). Whether it actually bounds
the `output` attribute needs measuring on the first launcher capture. Until then the
parser drops `output` unconditionally through NEVER_PERSIST, which records the drop on
every record, so the answer changes nothing about what is stored.

**The reasoning-drop path is exercised only by a hand-built test.** E02's own sanitizer
removed the 22 reasoning rows from the S1 and S6 rollouts before they were committed, so
no fixture can reach it. The test posts three spellings to `/v1/stream/codex` and asserts
no observation, three `dropped` diagnostics and nothing on disk. Broken deliberately, it
fails with three `codex.exec.item` rows where it expects none.

**Three fields carry command output or model text that `sanitize.NEVER_PERSIST` does not
name.** The rollout's `CommandExecution.formatted_output` and `item.changes[].unified_diff`,
which no item container is copied so neither is, and `event_msg/task_complete.last_agent_message`,
which the Stop hook spells `last_assistant_message` and NEVER_PERSIST does name. All
three are dropped today by the allowlist gate alone, and the last of them is one of the
three `unknown_field` diagnostics every scenario reports. `sanitize.py` is READS for this
task, so making that permanent is someone else's line.

**`otel.log_user_prompt=false` is accepted and is not passed.** A `-c` override that some
build rejects exits the child 1 before the session starts, and `prompt` is dropped by
NEVER_PERSIST on both surfaces that carry it anyway, so passing it buys nothing and risks
the capture.

**Turn usage cannot be joined to a rollout turn.** `turn.started` and `turn.completed`
carry no turn id on the exec stream. The rollout carries `turn_id` on `task_started`,
`task_complete`, `item_completed` and `turn_context`, so the join exists on one surface
and not across the two.

**Nothing names a commit the agent made.** `commit_ids` is `unavailable` on all five
surfaces. `session_meta.git.commit_hash` is HEAD at session start, which is a different
fact, stored under its own name.

**Four capability rows read `unavailable` on all five surfaces** (`compaction`,
`subagents`, `commit_ids`, and `context_window` on four of five). That means "not observed
in E02's cohort of seven single-prompt sessions", not "does not exist". Nothing compacted
and no session spawned a subagent, so those cells are about the cohort.

## EXPLAIN FOR THE OWNER

### What a provider module is for, in one Codex example

You ask Codex to fix a failing test. It reads two files, runs `pytest`, edits
`pkg/calc.py`, runs `pytest` again. Five different channels tell five different halves of
that story, and none of them tells all of it.

The exec stream, which is Codex's own stdout when you pass `--json`, says an item
finished with `exit_code: 0`. The OTel logs, which Codex ships to an HTTP endpoint if you
give it one, say how many tokens that turn's model response cost and which model answered.
The OTel metrics say how many tool calls happened, in a histogram, with no way back to
which. The hooks, if you can get them to fire, are the only place that says which
directory the command ran in and what permission mode was active. The rollout file, which
Codex writes to disk as it goes, is the only place that says the context window is 258400
tokens.

A provider module's whole job is to turn each of those into the same shape, an
Observation, and to be honest in a table about which of them can answer which question.
That table is `CAPABILITIES`, and the interesting entries are the ones that say
`unavailable`. Nothing anywhere in Codex names a commit that the agent made. So the row
for commit ids reads `unavailable` five times, and no later code is allowed to quietly
produce one.

### The bug that mattered, and how a test caught it

The rule Telltale exists to keep is that a secret which passed through a session is not
in the file on your disk. The privacy test asks the disk directly: it replays a recorded
session, closes the database, opens the raw bytes of all three SQLite files, and searches
for strings that must not be there.

Extending that test to Codex failed immediately, on all seven sessions. Not on a
credential. On this:

```
failed to parse hooks config /Users/<you>/.codex/hooks.json: invalid type: map,
expected a sequence at line 3 column 4
```

That is Codex complaining about its own configuration, and the complaint has your home
directory in it.

Here is why it got through. The sanitizer sorts every field into a kind. A field of kind
PATH is rewritten: inside the repository it becomes relative, because "the agent edited
`pkg/calc.py`" is the fact the whole system exists to record, and anywhere else it becomes
`<outside>/` plus eight characters of hash, so "the agent read a file somewhere it should
not have" survives while the place does not. A field of kind SCALAR is a sentence. It gets
its secrets scrubbed and its length bounded, and it is not rewritten, because a sentence
is not a path.

`error` is a sentence. It just happens to have a path inside it.

The fix reuses the existing machine rather than building a second one: find the runs
inside the sentence that look absolute, and hand each one to the same `relativize` the
PATH kind uses. The message survives, and it now reads

```
failed to parse hooks config <outside>/09983486: invalid type: map,
expected a sequence at line 3 column 4
```

which still tells you what broke. The other one, which named a file inside your
repository, reads `clamping SessionEnd hook timeout to 3s in .codex/hooks.json`.

I checked what it does NOT touch, because a rewriter that is too eager corrupts prose:
`https://example.com/x`, `10/20` and `read/write` all come through unchanged, because the
rule refuses a slash that follows a word character, a colon or another slash.

The answer I rejected was adding `codex.exec.error` to the test's list of known
exceptions. There is already one such exception, for a Claude field, and it covers the
repository root. Adding a second, for the HOME directory, would have turned a leak into a
policy.

### The thing I could not measure, and what I did instead

Hooks are the only Codex surface that says which directory a command ran in. E02 got them
to fire by writing a `.codex/hooks.json` into the repository being recorded. Telltale is
not allowed to do that: invariant 8 says configuration reaches an agent through the
launched process and never through a file that outlives the capture, because a file left
behind changes the next session too.

So the question was whether hooks can be configured for one launch only, through the
command line. I could test half of that for free. `codex doctor --json` reports whether
the configuration loaded, and it costs nothing. It says the inline spelling loads, and it
says a deliberately wrong one is rejected, so the loader is really validating the shape
and not ignoring the key.

The half I could not test for free is whether a hook registered that way actually fires
during `codex exec`. That needs a real session and real tokens.

I did not guess. `launch()` ships declaring the three surfaces it can prove it configures,
the hook parser ships and is exercised by the recorded fixtures, and the open question is
written into `DRIFT` with the words `NEEDS MEASURING` next to the command that would
answer it. The cost of that choice is one capability row that reads `unavailable` until
someone spends a session. The cost of the other choice would have been a launcher that
claims a surface it may not deliver.

### One number worth knowing

Codex's rollout file spells a command as an argv list wrapped in a login shell:
`["/bin/zsh", "-lc", "git status --short"]`. If you store that as-is, the command
normalizer keeps the program and the flags and replaces the quoted argument with `_`, so
every command Codex ever ran appears in your database as `zsh -lc _`.

The parser unwraps the shell first. Before trusting that, I checked it against a surface
that reports commands the other way: on all 10 calls that appear on both the rollout and
the hooks, the unwrapped script is character-for-character the hook's own
`tool_input.command`. That is two independent recordings agreeing, which is a different
thing from a transformation that looks reasonable.

### WHAT WAS WRONG

**13. One Codex tool call is named in three id spaces, and two of them lie about the
count.** Measured on S6: the EXECUTION id (`exec-<uuid>`) is on the hooks, on the OTel
tool_decision, tool_result and sandbox_outcome, and on the rollout's item_completed,
and there are 8 of them. The MODEL's call id (`call_<random>`) is on a SECOND
`codex.otel.tool_result` and on the rollout's response_item pair, and carries no
command, no path and no exit code. `item_N` is private to the exec stream and shares no
id with anything. `codex.otel.tool_result` appears 16 times for 8 calls, so a reducer
grouping by "any call id" reports 16 tool calls. Activities are keyed by the execution
id, which is the only key more than one surface agrees on and the only one that reaches
the command. The exec stream's items are not used for tool activities at all: joining
them would take text or time, and both are forbidden. Broken deliberately, the S6 test
counts 25 tool activities instead of 8.

**14. A turn is not a request, and Codex reports both.** `codex.exec.turn_completed` and
the rollout's `token_count` are TURN totals. S1 has ONE turn and SEVEN model responses,
and the numbers are not the same quantity: the turn reports 125350 input tokens where
the seven responses report 136787 between them (the difference, 11437, is the first
response, which the turn total excludes). Turn totals go on a `turn` activity, which no
summary metric reads, and per-request usage comes only from
`codex.sse_event` with event.kind `response.completed`. `turn` is not in design 6.10's
list of activity types; it is here because the alternative is either discarding the
turn totals or adding them to numbers they are not part of.

**15. Codex's `input_token_count` includes the cached tokens. Claude's does not.**
Design 6.11 defines `fresh_input = input_tokens`, so putting the wire value in that
field would print 203844 as S6's fresh input where the fresh part is 20804. Measured two
ways: `last_token_usage.total_tokens` is input plus output and never mentions cached
(20148 = 20006 + 142), and one S6 response reports input 20006 with cached 19200, which
cannot be disjoint. So `input_tokens` is the difference and `total_input_tokens` is the
wire value, both with provenance. The subtraction is skipped, and the field absent, if
either number is missing or the cached part is larger: a token count is never negative
and unknown stays unknown. Broken deliberately, the usage test fails on
cache_read_tokens as well as on fresh input.

**16. Two activities of one type could open on one observation.** The capture's own
lifecycle row opens on the capture's FIRST observation, and on Codex S3 that observation
is `codex.otel.conversation_starts`, which is also a session start with a lifecycle row
of its own. Both hashed to the same activity id: `UNIQUE constraint failed:
activities.activity_id`, measured, not reasoned. `correlate.activity` now takes an
optional `key` that defaults to the primary observation, and the capture row passes
`capture:<id>`. Nothing else's id changes.

**17. The timeline's tie break was a ULID minted at ingest, so a golden of it was not
reproducible.** Same two rows: they share a `started_at` AND a `primary_observation`, so
`report._order` returned equal keys and the order fell through to the database's
`ORDER BY started_at, activity_id`, where the id is a hash of an observation id that is
different in every run. Measured: the S3 timeline swapped those two rows between runs.
The order now ends with the activity type and the lifecycle event, which are properties
of the reduction and identical on every rebuild. Three consecutive runs of the golden
tests pass.

**18. `UV_CACHE_DIR uv run pytest` is classified `git`, not `test`.** Measured with
`commands.classify` on the eight S6 commands. The normal form keeps the environment
assignment's NAME as the first word of the first segment, `classify` finds no category
for `UV_CACHE_DIR`, and design 6.10's "first segment with a known category wins" then
lands on the `git diff --check` that follows the `&&`. So S1 and S6 each report
`agent_test_runs` 1, counting only the run whose command begins with `uv run pytest`,
and the timeline shows the others as `command`. This is `commands.py`, which this task
does not own, and it affects Claude equally. It is in NEXT with the measurement.
