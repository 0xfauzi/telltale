# W1-T4 repeat runner and fake agent

## OUTCOME

`telltale experiment repeat <spec.json>` runs N independent captures of one task in one
environment, records each attempt through `/v1/correlations`, records the harness's own
acceptance result through `/v1/outcomes`, refuses to compute statistics when the captures
are not one environment, and prints robust statistics with a claim class on every row.
`telltale purge <capture_id>` deletes one capture. The environment fingerprint now
carries `runtime_version`, read once per binary upgrade rather than once per capture. A
scripted agent that spends nothing drives all of it.

New: `src/telltale/experiments.py` (564 lines), `src/telltale/facts.py` (103),
`tests/integration/fake_agent.py` (279), `tests/integration/test_experiments.py` (360),

to 782, after 66 lines moved out), `docs/design/03-capture-howto.md` (one stale
paragraph, see WHAT WAS WRONG).

## WHAT WAS WRONG

**The scaled MAD of one value is 0, and 0 there is a lie with consequences.** Running a
one-repetition condition printed `MAD_SCALED 0` for every metric. Design 6.12 uses the
scaled MAD as the spread in `MDD = 2.8 s sqrt(2 / n)`, the smallest median difference
resolvable at the current n, and a spread of 0 makes the MDD 0, which says every
difference is resolvable from one observation. One value has a median and no dispersion.
`stats()` now returns None for both `mad_scaled` and `iqr` when n < 2, for the same
reason `quantiles()` refuses: a spread estimated from one point was not estimated.

**A tool column absent from a capture is two different facts, and one of them is zero.**
The metrics of a condition are the union of the per-capture metrics, so if repetition 3
never called Edit, the column exists and repetition 3 has no entry. Filling that with
None would say Edit could not be seen, when the stream was recorded in full and Edit
simply was not used, which is a real zero. Filling it with 0.0 unconditionally would say
a capture with no stream at all made no tool calls. `_filled()` distinguishes them by the
one field that answers the question: `tool_calls` is None exactly when no stream
observation exists, and only then are that capture's tool columns unknown.

**Probing an arbitrary child with `--version` is a thing a recorder must not do.** The
brief says to fill `runtime_version` by running `<binary> --version`. Done literally,
`telltale run -- deploy prod` starts `deploy --version` first, and Telltale would have
run a program the owner did not ask it to run, with a flag it invented, before the
capture began. The probe is therefore limited to binaries this system has a provider
module for, which today is `claude` and `codex`. A generic child's runtime is None, which
is what "not observed" looks like everywhere else here, and it is still equal across the
repetitions of one condition, which is what the fingerprint assertion needs.

**The scripted agent's fabricated numbers ran away.** Without `--seed` it draws one, and
the first version drew from `os.urandom(2)`, so the first real table printed
`input_tokens 5109093` for a five-turn session. Every fabricated number is linear in the
seed, so the draw is now bounded to 0..99. While checking this I got a five-run condition
whose seeds were 3, 42, 57 and 96 twice, all divisible by 3, which made every repetition
identical in turn count. I suspected a biased draw and measured 3000 draws instead of
assuming: `Counter({1: 1020, 0: 1013, 2: 967})` by residue mod 3. The draw is fine and
that condition was a coincidence, 1 in 243.

**`external.correlation` and `external.outcome` rows carry no environment fingerprint.**
A test asserting that every row of a capture carries the capture's fingerprint id failed
on three row types. Two of them are the external API rows: `receiver._store_external`
builds its Observation without `environment_fingerprint_id`, whatever the receiver knows
about the capture. The third is `telltale.repo.identity`, which the launcher emits before
the fingerprint has been computed. Nothing is lost, because both are joinable through
their capture, but an experiment that wants "every outcome under fingerprint X" cannot
ask SQL for it directly. Recorded rather than fixed: `receiver.py` is not this task's to
change, and the fix belongs with whoever needs the query.

**launch.py could not take the probe.** It was 761 lines against the 800-line ratchet.
`Facts`, `facts()` and the two coercions moved to `src/telltale/facts.py` in a separate
commit with no behaviour change. The brief suggested moving `link_commits` with them; it
stayed, because it WRITES observations through the launcher's private `_Capture` and
moving it would have made facts.py import launch.py. As it is, the dependency runs one
way: facts.py imports nothing of the launcher, and both launch.py and cli.py read a
stored capture through it.

**`docs/design/03-capture-howto.md` told the owner that `telltale purge` does not
exist**, and printed a five-line Python snippet to use instead. That paragraph is now the
command. It is the only file outside this task's OWNS list that I changed, and I changed
it because this task made its text false.

## WHAT CHANGED

**`src/telltale/experiments.py`**, new. `repeat(spec, home, out=None) -> dict` runs one
condition: for each repetition it adds a detached worktree of the target repository at
the base commit, runs `telltale run --task-id --attempt --experiment` there as a
subprocess, identifies the capture that run wrote, POSTs the correlation, runs the
acceptance command in the worktree and POSTs the outcome, then removes the worktree in a
`finally`. Then `one_fingerprint()` over the captures, `vector()` per capture,
`stats()` per metric, and a report dict.

Four things in it are decisions rather than mechanics. The launcher is shelled out to
rather than called, because a capture assembled any other way is a capture of a different
process tree. The capture id is proved rather than assumed: the ids that are new since
this repetition started are filtered by what each capture SAYS about itself
(`task_id`, `attempt`, `experiment` in its `capture_started`), and anything other than
exactly one is refused, because a daemon or another launcher may be writing to the same
database. The spec is validated whole before anything runs, with every key required and
an unknown key refused, because a spec that does not state its content level is a spec
whose captures cannot be compared. And nothing is written to the `evidence` table: the
per-capture vector is a placeholder for W2-T4's real evidence vector, and evidence
written for a placeholder would be deleted by the next `store.rebuild()` anyway. The
claim class travels in the report and in the printed table instead.

**`src/telltale/launch.py`**. `runtime_version(executable)` and its cache. The answer
goes into `env.fingerprint(runtime_version=...)`, so two runs of two Claude Code versions
are now two environments; before this they fingerprinted the same (W1-T1's UNSURE list).
The cache is `$TELLTALE_HOME/versions.json`, keyed by the binary's resolved path and its
mtime, so an upgrade in place is a new key. It is written through a temporary file and
`replace()`, because four `telltale run` processes can start at once and one of them
must not read a half-written file. A None answer is cached like any other, so a binary
that has no `--version` is probed once and not once per capture.

**`src/telltale/facts.py`**, new. The reading half of launch.py, unchanged except for
`runtime_version` joining `Facts`.

**`src/telltale/cli.py`**. `experiment repeat <spec.json> [--out DIR]`, which prints two
tables: one row per repetition with claim class `derived`, and one row per metric with
claim class `comparative`, followed by the sentence that says what the second table may
be compared with. `purge <capture_id>`, which refuses an id the database does not hold
rather than reporting that it deleted nothing. The `sessions` table gains a `runtime`
column beside `provider`.

**`tests/integration/fake_agent.py`**, new. A real child process that prints the
stream-json lines Claude Code prints and does the work they describe: it reads files,
rewrites `answer.txt` and runs a command, in the working directory it was started in.
Its lines parse through `providers/claude.py` with nothing dropped as an unknown field.
Every number it reports is fabricated and the module says so in its first paragraph.
`--seed` fixes them, `--effort` and `--model` change them, and `--fail` makes it write
the wrong answer so the acceptance command fails while the agent still exits 0.

**`tests/integration/test_experiments.py`**, new, six tests, each against a git
repository it makes itself. **`tests/integration/test_live.py`**, new, two tests that
spend tokens and were not run.

## UNSURE OR NOT DONE

- **`runtime_version` is the whole first line of `--version`, verbatim.** On this machine
  that is `2.1.258 (Claude Code)` and `codex-cli 0.150.1`. The string is bounded to 64
  characters and hashed into the fingerprint as it is, which means a cosmetic change to a
  vendor's version banner changes the fingerprint id and reads downstream as an
  environment change. Parsing a version number out of it would need a per-provider rule
  that nobody has measured against a version bump, and inventing one is the worse error.
- **A generic child's runtime is None,** for the reason in WHAT WAS WRONG. So a condition
  that runs `make test` under `telltale run` fingerprints without the make version.
- **The cache is keyed by path and mtime.** A binary replaced in place with its mtime
  preserved would keep the old answer. I judged that acceptable and did not measure how
  any installer behaves.
- **Nothing here writes an Evidence row,** so `telltale explain` will not find these
  numbers. Deliberate, and the reason is in WHAT CHANGED. If the owner would rather have
  them persisted, the decision to make is whether they survive `rebuild`.
- **The between-arm statistics of design 6.12 are not built.** Hodges-Lehmann shift,
  Cliff's delta, exact Mann-Whitney, `MDD = 2.8 s sqrt(2 / n)` and
  `N_needed = ceil(2 (2.8 s / (0.25 median))^2)` compare two conditions, and this task
  makes one. `stats()` returns the scaled MAD they all need.
- **The correlation and outcome POSTs go to a receiver in the runner's process,** not to
  the capture's own, which exited with the launcher. They are attributed by the `?capture=`
  query parameter, which is design 6.6's mechanism for exactly this. The HTTP route is
  therefore exercised, but not the route as an agent would reach it.
- **Repetitions run one at a time,** so a condition of 20 takes about 11 seconds. Running
  them in parallel would be faster and would make them share machine load, which is a
  measure this system reports. Not measured, and I would want a measurement before
  changing it.
- **The runner does not check the target repository beyond what git tells it.** A dirty
  worktree, a base sha on no branch, a repository with no commits: each fails inside
  `git worktree add` with git's own message, which is clear, but the failure arrives
  after the store has been opened rather than in the spec check.
- **`_new_capture` refuses when a concurrent writer produces a second matching capture,**
  and that path has no test: producing it needs two runners agreeing on a task id and an
  attempt number at the same instant.
- **launch.py is 782 lines against the 800-line ratchet.** The next change to it moves
  something out again. `link_commits` and `reported_commits` are the obvious pair, and
  they want a home that owns writing to a stored capture.
- **The scripted agent varies its numbers and its tool counts, not the SHAPE of a
  session.** It never compacts, never spawns a subagent, never fails a tool call and
  never emits an OTel record. W2-T3 needs between-arm differences and will get them from
  `--effort` and `--model`; if it needs a different shape of session, this file is where
  that goes.
- **Content levels 0 and 2 are not exercised by the runner's tests.** Every spec here
  runs at level 1.
- **The two live tests were not run,** so the claim that they pass is not made. What is
  claimed is that they collect, skip without `TELLTALE_LIVE=1`, and assert the smallest
  thing that could only be true if the whole path worked.

## EXPLAIN FOR THE OWNER

### What was at stake

You want to know whether a change to how an agent is run made it better. Before any of
that can mean anything, you need to know how much the same run varies when nothing
changes at all. If two runs of the identical setup differ by 40 percent, then a 30
percent improvement is not an improvement, it is Tuesday. This task builds the instrument
that measures the noise floor, and nothing about comparing two setups is worth building
until it exists.

### First question: what is one run?

A run is one agent session on one task, recorded. That sounds simple and it is where all
the traps are.

Two sessions on one task in one directory are not independent. The second one starts from
whatever the first one left behind: a half-finished edit, a file that now exists, a test
that now passes. So each repetition gets its own checkout of the repository, made fresh
from the same commit, used once and deleted. Git can do this without copying the whole
repository, with a thing called a worktree: a second working directory attached to one
repository's history. Adding one costs 25 milliseconds on this machine and removing it
costs 10, which I measured rather than guessed.

The other trap is who decides whether the run worked. If the agent runs the tests and
tells you they passed, you have measured the agent's opinion of itself. So the check is a
command written into the spec, run by this harness, after the agent has exited, in that
repetition's worktree. The agent never sees it. Its result is recorded as an observation
of the capture, so the record of the session and the record of whether it worked live
together.

Five of those, on one task, with the setup held still, is a condition. Five is the pilot
size design 6.12 fixes.

### Second question: how do I know the setup was held still?

This is the part I care most about, and it is the reason the runner has a refusal in it.

Everything about a session that is not the repository gets hashed into one string: which
agent, which version of its binary, which model, which effort setting, the contents of
every instruction file it will read, the permission mode, the content level. That string
is the fingerprint. Two runs with the same fingerprint had the same setup. It is
`env_8f96c6e0...` in the table below.

The runner computes statistics only if all five captures carry the same one. If they do
not, it refuses and names the fields that differ, like this, which is the real output of
two runs that differed only in the model flag:

```
2 environment fingerprints across 2 captures (cap_01M1..., cap_01M2...);
fields that differ: model=['"haiku"', '"opus"']
```

Why refuse rather than warn. A median over five numbers from two different setups is a
number with no meaning, and it looks exactly like a number with meaning. Nobody reading a
table can tell. The only place that difference is visible is here, before the median is
taken, so this is where it has to stop.

This is also why I had to fill in a field the launcher was leaving blank. Until this task,
the fingerprint recorded no version of the agent binary, so a session on Claude Code
2.1.257 and one on 2.1.258 fingerprinted the same, and the runner would have called them
one condition. Reading the version costs a process spawn, which is real money on a system
that promises not to slow your session down, so it is read once per binary and cached
under Telltale's own directory, keyed by where the binary is and when it was last
modified. Measured: 9.6 milliseconds the first time, 0.10 milliseconds every time after.
Upgrade the binary and the key changes, so the next run pays the 9.6 again.

There is one thing I deliberately did not do, and it is worth your knowing. The brief said
to run `<binary> --version`. Taken literally, wrapping any command at all would make
Telltale run that command with a flag first, so `telltale run -- deploy prod` would start
`deploy --version` before the capture began. A recorder that runs unrequested programs is
not a recorder. So the probe only runs for binaries Telltale has a parser for, which is
Claude Code and Codex, and anything else records its runtime as unknown. That is a real
gap: a condition that wraps `make` will not notice a make upgrade. I chose the gap over
the hazard.

Read the `num_turns` row across. Five sessions made 4, 5, 5, 6 and 6 model requests. The
middle one is 5, so the median is 5. The spread beside it says how far a typical run sits
from that middle: take the distance of each value from 5, which gives 1, 0, 0, 1, 1, take
the middle of those, which is 1, and multiply by 1.4826. That scale factor is there so
the answer is comparable to a standard deviation on well-behaved data; on this row it
gives 1.483.

Why that and not the average and the standard deviation. One session that hits a retry
storm and makes 40 requests would move an average a long way and a median not at all.
Agent sessions produce exactly that kind of outlier. The full sorted list is printed in
the last column precisely so you never have to trust my summary of five numbers: you can
see them.

Now read `tool_calls.Bash`. Every run made exactly one, so the spread is 0. That is a
real zero and it is the most interesting cell in the table: it says this part of the task
does not vary at all, so any future difference in it would be worth looking at.

And read `input_tokens`. The middle is 2277 but the largest is 5925, more than twice it.
The scaled spread is 360 while the gap between the quartiles is 1152. Those two numbers
disagreeing is the signature of one run sitting far out on its own, and it is why both
are printed.

One cell type that is not in this table but matters. If a run had recorded nothing on the
surface these numbers come from, its entry would be blank, `N` would read 4 instead of 5,
and `UNKNOWN` would read 1. It would never read 0. "The agent made no tool calls" and "no
tool call could be seen" are different statements, and a zero in the second case is an
observation nobody made. I broke this on purpose to check that the tests catch it: I made
the reader return 0 where it returns unknown, and
`test_a_capture_with_no_stream_has_unknown_numbers_and_not_zeros` failed with
`assert {0.0} == {None}`. Then I put it back.

### Fourth question: what does the claim class column mean?

Every number this system prints says how strong a statement it is. The two words in that
table are `derived` and `comparative`, and the difference is what you are allowed to say
next.

`derived` means the number was computed from one session's own records. "This session made
five model requests" is derived: nothing was compared, nothing was predicted, the records
say it.

`comparative` means the number is a summary placed against a stated group. The median of
5 is not a fact about any session; it is a fact about these five, taken together, and only
because they were the same setup on the same task from the same commit. That group is
printed with the report as `cohort`, and it names the experiment, the task, the base
commit, the content level and the fingerprint.

So "comparative within the condition" is a fence. Inside it, the sentence "this task takes
about 5 model requests, give or take 1" is supported. Outside it, nothing is. You may not
carry that median to a different task, a different model, a different repository, or the
same task next month after the agent updated, because each of those is a different
condition and the fingerprint would say so. The runner prints that fence under the table
in words rather than leaving it to be inferred.

The one thing you cannot say from any of it is that something caused something. That word
is not available at any claim class in this system, and it is not available here.

### The thing I am least sure about

The per-session numbers are a stand-in. They read the summary line an agent prints at the
end of a session and count the tool calls by name, which is what a capture holds today
without any further processing. The real vector, the one spec 13.7 defines, needs the
reducers that a later task builds: verification cycles, edit turnover, exploration,
stable-state intervals. The shape of everything above stays the same when it arrives,
because the runner only asks for "a dictionary of names to numbers, with unknown allowed".
But the table you would print today is thinner than the one you will print later, and the
numbers in it come from a scripted agent that fabricates them, which the fake agent's own
first paragraph says in capitals.
