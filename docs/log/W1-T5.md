## WHAT WAS WRONG

Nothing in wave 1 was wrong. Four things were unknown and each was measured.

1. **`content_level` is not on any activity, so the cohort cannot carry it.** The brief
   defines the request-clock cohort as `{capture_id, provider, repo_id,
   environment_fingerprint_id, content_level}`, and it forbids this task from reading an
   observation payload. Measured: `grep -rn content_level src/telltale/` finds it in
   `env.py` (the environment fingerprint input), `launch.py:329` (the
   `telltale.capture_started` payload), `cli.py` and `allowlist.py`, and in no activity
   field. `activities.py:_configured` already opens that same payload for
   `surfaces_configured`, so lifting `content_level` beside it is a one-line change to a
   file this task does not own. So the cohort carries `content_level: null` on every
   capture today, read by the name it will have (`fields.get("content_level")`) so that
   it fills in the moment a later task lifts it. This is the STOP the brief asked for:
   reported, not invented.

2. **The brief's level rule for `files_edited_since_prev` is the wrong way round.** It
   says the column is level 1 only and None at level 0. Measured, by replaying S1 at
   content level 0 into its own database: the `file_edit` activity still exists, because
   the activity type is decided by `tool_name` ("Edit"), which survives level 0; only its
   `file_path` is dropped. Counting edits works at both levels. What actually breaks at
   level 0 is a different column. All three of S1's `verification_run` activities become
   plain `command` activities, because level 0 keeps command basenames only and the
   classifier can no longer see `pytest`:

   ```
   level 1: command 1  file_edit 1  file_read 1  lifecycle 4  model_request 7  verification_run 3
   level 0: command 4  file_edit 1  file_read 1  lifecycle 4  model_request 7
   ```

   So `files_edited_since_prev` takes its coverage from the `tool_calls` capability and
   `verification_runs_since_prev` from `commands`, and both mappings are that
   measurement rather than a guess. Since the content level is not readable from
   activities anyway (finding 1), no column is gated on it.

3. **`check(series)` cannot check the invariant it is named for.** A `Series` carries
   activity IDS in `row_meta.provenance`, and an id has no clock position until the
   activities table is read. The signature in the brief has no store, so the
   provenance-versus-row-end comparison could only have been skipped, which is a check
   that passes for the wrong reason. It is `check(store, series)`, matching
   `build(store, ...)` beside it. An unresolvable provenance id is reported as a
   violation of its own.

4. **store.py was 765 lines, not 798.** The brief and the wave-0 amendment both say 798;
   `wc -l` said 765 at `e2aa6a9`'s parent. The move was still worth doing (the readers
   would have taken it to 802) and the DDL is now `src/telltale/schema.py`. `cli.py` is
   the file to watch next: 795 against the 800 ratchet, five lines of headroom.

# EXPLAIN FOR THE OWNER

## What was at stake

Telltale can now say what happened in a session. It could not yet hand any of that to
something that forecasts, because a forecaster does not read a session. It reads a
sequence, and a sequence has a rule about what one step is.

Getting that rule wrong does not produce an error. It produces a number that looks fine
and is worthless, and the way it fails is specific enough to have a name.

## A clock is a decision about what counts as one step

Suppose you want to know whether a session is heading for trouble. You need a row of
numbers, then another row, then another, so that something can learn how row 40 follows
from rows 1 to 39.

But a session is not a list of rows. It is a mess of overlapping things: requests to the
model, shell commands, file reads, two tool calls running at once, an occasional
compaction where the session summarizes itself to make room.

So somebody has to choose. One row per model request? One row per attempt at a task? One
row per change that lands in the repository? Each choice gives a different sequence over
the same session, and each answers a different question.

That choice is the clock. This task builds one of the three the design names, the
request clock: one row per model request. The other two, the attempt clock and the
change clock, belong to a later task, and asking for one today gets a refusal that says
so rather than a series built from a definition nobody has agreed:

```
$ uv run telltale series build --clock attempt --capture capS1
the attempt clock is not built yet (W3-T1)
$ echo $?
2
```

## The first six rows of S1, and what every column says

S1 is one of eight real Claude Code sessions recorded in September 2025 and stored under
`fixtures/sources/claude/2.1.257/`. The scenario is small and complete: a test is
failing, the agent finds it, edits one file, and the test passes. It made seven requests
to the model, so the request clock gives it seven rows.

Here are the first six, exactly as the compiler produced them. `-` means unknown.

```

--  -------------  ---------  -----------  -----  -------  -----  ------  ------  ------  ----------  -----
0   20:04:21.422   2          18549        136    2796     0      0       0       0       -           -
1   20:04:24.172   2          33372        155    2174     0      1       0       1       0           -
2   20:04:25.665   2          33989        63     1451     0      1       0       0       0           -
3   20:04:27.534   2          34458        117    1565     0      2       0       1       0           -
4   20:04:30.479   2          35325        329    2940     0      0       0       0       0           -
5   20:04:31.843   2          35774        63     1200     0      1       1       0       0           -
```

**`row_end_ts`** is when the row closed, which is when that request happened. Seven
timestamps, twelve seconds apart end to end.

**`fresh_in`, `cache_read`, `out`** are the three token counts the provider reports for
each request: text it had to read fresh, text it read out of the prompt cache, and text
it produced. Every one of these came off the provider's own `api_request` record.

I checked them a second way, with a command that does not run any of my code:

```
$ jq -r '... select(.body.stringValue=="claude_code.api_request") ...' \
    fixtures/sources/claude/2.1.257/S1/otel_logs.jsonl
2  18549  136  2796
2  33372  155  2174
2  33989   63  1451
2  34458  117  1565
2  35325  329  2940
2  35774   63  1200
2  36323   73  1203
```

Seven records, and all twenty-eight numbers match the table. That is a measurement, not
a claim: the check reads the recorded bytes and walks them itself.

Two things in that column are worth pausing on. `fresh_in` is 2 on every request, which
looks broken and is not. Almost the whole prompt is being served from the cache, which
is what `cache_read` climbing from 18549 to 36323 shows: the conversation is growing and
the model is re-reading it from cache each time. And `cache_read` is nearly monotonic,
which is exactly the kind of structure a forecaster can learn something from, and also
exactly the kind that a trivial baseline can learn too. Which of those it is, is W1-T6's
question, not mine.

**`dur_ms`** is how long the request took, from the same record.

**`comp`** is 1 when a compaction finished between the previous request and this one.
S1 never compacted, so it is 0 all the way down. That zero is a real statement: S1's
surfaces could see compaction, and none happened. The next section is about the case
where that is not true.

**`tools`, `files`, `verif`** count what the agent did between the previous row and this
one: tool calls of any kind, file edits, and test runs. Row 3 has `tools 2` because two
things finished in that gap, the second `pytest` run and a `Read` of `pkg/calc.py`. Row
5 has `files 1` because that is where the edit lands.

Down the whole column, tools sum to 6, files to 1, and verifications to 3, which are the
counts W1-T2 measured for S1 from the fixture directly. That is not a coincidence and it
is not quite an invariant either: it holds because every one of those activities finished
before the last request. An activity after the last request would be counted by nothing,
correctly, and the sums would no longer match. The test asserts the equality as a fact
about S1 and says so.

**`last_exit`** is 0 when the last test run passed, 1 when it failed. Row 0 is `-`,
because at that point no test had run at all. Nobody had passed and nobody had failed,
and writing 0 there would say the tests were passing.

**`env`** is `-` on every row, and that is the most interesting cell in the table.

## Why an unavailable column is not a column of zeros

`env` is short for `env_changed`, and it is 1 on the first row after the environment
changed underneath the session: a different model, a different tool set, a different
content level. The environment is identified by a fingerprint, which is a hash of all of
that, and Telltale stamps it onto every observation.

Except that it only does so when Telltale launched the session. These fixtures are
recorded provider bytes replayed from disk. No launcher ever ran, so nothing stamped a
fingerprint onto them, so there is no fingerprint on any row.

Now consider what the compiler could have written. It has seven rows and no fingerprint
on any of them. "Did the environment change between row 3 and row 4?" No fingerprint
differed, so the arithmetic answer is no, so the honest-looking output is a column of
seven zeros.

That column would be a lie told calmly. Seven zeros says the environment was watched and
held still. What happened is that nobody was watching. A forecaster handed that column
would learn that the environment never changes, and it would be learning an artefact of
how the fixture was recorded.

So the column is seven `-` and its coverage word is `unavailable`, and `series build`
prints the two together:

```
COLUMN                        UNIT       ROLE            COVERAGE     NULLS
----------------------------  ---------  --------------  -----------  -----
compaction_before             flag       past_covariate  observed     0
env_changed                   flag       past_covariate  unavailable  7
```

Read those two lines against each other. `compaction_before` is zeros with coverage
`observed`: the surfaces could see compaction and there was none. `env_changed` is all
unknown with coverage `unavailable`: nothing could see it, so nothing is claimed. Same
shape of output, opposite meanings, and the coverage word is the only thing that tells
them apart.

W1-T2 found this exact defect in its own summary and fixed it in one function. This is
the same rule applied one layer up, per column instead of per number, and there is a
test that fails if `env_changed` ever comes back as zeros.

## The failure that has a name: no look-ahead

Here is the way a forecast can be worthless while every test passes.

Row 3 of the table says `verif 1`: one test run finished between request 2 and request
3. Suppose the code that built that row had instead counted every test run in the whole
session, or even just up to request 4. Row 3 would then contain information that did not
exist when request 3 was made.

Train a model on that and it does beautifully. It has been shown the answer. Deploy it on
a live session, where the future genuinely has not happened, and it collapses. Nothing in
the training run reports a problem, because from the inside the numbers look excellent.

This is the reason the design specifies not just what each column holds but when it may
be known.

The compiler avoids it by construction, and "by construction" here means something
specific rather than a reassurance. The activities are sorted by clock position, which is
when each one ended, or when it started if nothing observed it ending. Then one loop walks
that list once. Counters go up as activities are consumed. When the loop reaches a model
request, it writes a row from the counters and resets them.

A row is written from state that has consumed only what came before it in the list. There
is no second pass and nothing holds a reference to the rest of the list. To introduce
look-ahead you would have to add code that reaches forward, which is a visible edit rather
than an oversight.

## How `series check` catches it anyway

Writing the loop carefully is not evidence that the loop is careful. So every row also
records which activities it was folded from, and `series check` tests the claim against
the stored rows rather than against the loop.

Row 3 of S1 records three:

```
3  act_bde84e0cd34756f300ff0fbe6b  ['act_3b7353bc7b7045e951ef3a54a0',
                                    'act_200e4fb4858d73722625406e63',
                                    'act_bde84e0cd34756f300ff0fbe6b']
```

Two activities consumed in the gap, plus the request itself. `series check` looks up each
one, finds when it happened, and compares it against when the row closed. Every one must
be at or before it. Separately, the row ends must never go backwards.

To see that it works, I broke a stored series on purpose. Copy the database, take row 3's
end timestamp and move it back to row 0's, change nothing else:

## Two ways to handle a hole, and neither fills it

Look at row 0's `last_exit` again. It is unknown, and it is unknown for an ordinary
reason: the first request came before the first test run.

A forecaster cannot consume an unknown. There are two honest answers and the command
takes whichever one you ask for.

`--policy exclude`, the default, leaves the unknown alone and counts it. The `NULLS`
column in the output above is that count, so you can see how many windows a forecaster
will have to drop before it runs. Nothing is dropped and nothing is filled at this stage.

`--policy refuse` stops instead, and says exactly where:

```
$ uv run telltale series build --clock request --capture capS1 --policy refuse
policy refuse: column last_verification_exit has coverage observed and no value in row 0 (activity act_964124f3aed6d95027ba8fb167)
$ echo $?
2
```

The third option, the one that does not exist, is the important one. No policy fills a
hole with an average, a zero, or the previous value. Filling one would put a number in
the series that nobody measured, and every later number computed from it would inherit
that invention without carrying any mark of it.

I should be plain about a judgement inside this. `refuse` fires on nearly every real
capture, because almost every session makes a request before it runs a test, so row 0's
`last_exit` is almost always unknown. Someone could reasonably say that is a structural
gap rather than a missing measurement, and should be exempt. I implemented the rule as
specified because changing what `refuse` means is a decision for the owner, not for the
compiler, and the specified rule is at least testable as written.

## Running it

Nothing here writes to a capture. `series build` writes one row to the series table, and
that row's id is a hash of its own contents, so building the same capture twice replaces
rather than accumulates. `series check` and `series list` open the database read-only.

```
uv run telltale series build --clock request --capture <id> [--policy exclude|refuse]
uv run telltale series check <series-id>
uv run telltale series list
```
