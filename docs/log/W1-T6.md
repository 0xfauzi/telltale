# W1-T6 forecast core

## OUTCOME

The forecasting laboratory runs end to end: a stored Series goes in, a rolling-origin
backtest comes out, five forecasters plus the TimesFM-3 adapter are scored against each
other, and the run is written through `store.put_forecast_run` with its constants, its
dropped windows and the weights licence attached.

New: `src/telltale/forecast/__init__.py` (213 lines), `baselines.py` (160),
`backtest.py` (689), `timesfm.py` (211), `tests/integration/test_forecast_contracts.py`
(361). Changed: `src/telltale/cli.py` (+71, now 659) and `pyproject.toml`.
`tests/integration/synthetic_series.py` already existed from W1-T5 and is unchanged.

`uv run pytest -m integration` in the DEFAULT environment: **76 passed, 2 deselected in
14.10 s**, 5 of them new, with no torch installed (`uv run python -c "import torch"` is
`ModuleNotFoundError` in that same environment). Every gate is green: `uv run mypy .`
(45 source files), `uv run ruff check .`, `uv run ruff format --check .` (87 files),
`uv run deptry .`, `uv run pre-commit run --all-files` (every hook, including
`forecast-isolation` and `derived-writes-only-in-store`).

The 200-row synthetic series at H = 1 gives 136 windows, and the headline is the one the
laboratory exists to be able to report: **no forecaster beats persistence on a random
walk**, TimesFM-3 included, at skill -0.0253. That is the correct answer for this input
and the reason the baselines are in the table.

## WHAT WAS WRONG

Twelve things. Four are deviations from the brief with a reason, five are facts that
were unknown until they were measured, and three are traps in the brief's own wording
that would have produced code that passes its tests and answers wrongly.

### 1. `run(store, series, ...)` would have taken an argument it never uses

The brief specifies `run(store, series, target, horizon, forecasters, variant=None)`. A
backtest reads the Series it was handed and the `TARGETS` registry, and nothing else:
there is no query it could make. Measured: with `store` in the signature,
`uv run ruff check .` reports ARG001, because ruff can see the parameter is dead.

Worse than the lint. A store handle is the one thing design 6.12 forbids a Window to
carry, and a function that holds one is one edit away from passing it down.

So the signature is `run(series, target, horizon, forecasters, variant=None, *,
c_min=None)` and `persist(store, backtest)` takes the store. This is a deviation and it
is recorded here rather than made quietly.

### 2. `local_drift` at h = 0 is persistence, and H = 1 is the default horizon

Design 6.12 gives local drift as `y_{o-1} + h (y_{o-1} - y_{o-9}) / 8` without saying
where h starts. The actuals are `target[o:o + H]`, so the forecast steps could be
indexed h = 0..H-1 or h = 1..H, and the design does not choose.

Read as h = 0..H-1, the first forecast step is `y_{o-1} + 0`, which is exactly
persistence. At H = 1 the two baselines become the same function, and the default
horizon of `forecast backtest` is 1. One of the four baselines would have carried no
information at the horizon the design says to run.

Read as h = 1..H, the step index counts rows from `y_{o-1}`, which is what a drift per
row means: `y_o` is one row after `y_{o-1}`, so it gets one slope.

I took the second reading. It is a judgement and someone could differ; what settles it
for me is that the first reading silently deletes a baseline. The reading is in the
function's docstring, in the run's `assumptions` list and in the stored row, and the
H = 1 table above shows local_drift and persistence with different numbers (101.19
against 90.43), which is the check that the choice actually took effect.

### 3. The brief's array layout would have made the covariates into targets

The brief says the adapter builds "the contexts (target row plus past-only covariates as
a (V, n_ctx) array)". Measured, by reading the signature rather than assuming it:

```
$ uv run --extra forecast python -c "import inspect; from timesfm3 import TimesFM3Forecaster; print(inspect.signature(TimesFM3Forecaster.predict_batch))"
(self, contexts: 'list[np.ndarray]', horizon: 'int',
 past_only_covariates: 'list[np.ndarray | None] | None' = None,
 past_future_covariates: 'list[np.ndarray | None] | None' = None, ...)
```

`contexts` is a batch of arrays and each array's rows are TARGETS. Stacking the
covariates into it asks the model to forecast all ten request-clock columns and to treat
none of them as a covariate of the others, and it returns a (10, H) answer with no
complaint. E03's own `phase_variate_cap` probe already used the right arrangement:
`contexts=[target (1, n_ctx)]`, `past_only_covariates=[covariates (P, n_ctx)]`,
forecast shape (1, H). The adapter does that, and the same probe is what makes the
brief's own variate assertion (`1 + past_only + past_future <= 32`) coherent.

### 4. The no-look-ahead test cannot poison every origin at once

The brief says to "set every row at index >= each origin to 1e9 in a copy of the series
and run again". There is no single copy that does this. The origins run from 32 to 59 on
the test series, and rows 32 onwards are the CONTEXT of every origin above 32: poisoning
them destroys the windows the test is trying to compare.

So the test does it once per origin. For each of the 28 origins it builds a copy with
rows at index >= o replaced by 1e9 in every column, re-runs the whole backtest, and
compares the window recorded at o against the true one. That is 28 full backtests and it
costs 0.11 s.

Two things are excluded from the comparison and both are excluded on purpose. `actual`
IS the poisoned future (row o is the first row replaced), so the test asserts separately
that it became 1e9, which is how it knows the poison landed. `wall_ms` is a measurement
of this machine at that instant, not a property of the window.

I broke it to see it fail. Changing one line of `_at_origin` so the context is
`rows[ctx_start : o + H]` rather than `rows[ctx_start : o]`:

```
E  AssertionError: origin 32: the window changed when the future was replaced by 1e9
E  Differing attributes: ['rows']
3 failed, 2 passed
```

Restored, and the file is byte-identical to before the break (`git diff` prints
nothing). Note which three failed: the look-ahead test, the hand-computed metrics test
(the window contents moved), and the random-walk test, whose persistence MAE went to
exactly 0.0 because a forecaster shown the answer scores perfectly. That last line is
what a look-ahead defect looks like from the inside, and it is why the test exists.

### 5. A column nobody could see would have dropped every window in the run

Design 6.12 step 2 says to drop any window containing None in the target or a selected
covariate. The variant for the request clock is "the other request-clock columns", and
on a replayed capture `env_changed` has coverage `unavailable` and is None in every row
(W1-T5 measured that and refused to write zeros). Applied literally, every window of
every real capture drops, for a reason that is a property of the capture rather than of
any window.

The design answers this two paragraphs later, in the readiness checklist: "coverage:
target and variant columns observed or derived-from-observed on retained rows". So a
column whose coverage is not `observed` or `derived` is excluded from the variant by
name, with its coverage printed beside it, and a TARGET with that coverage is a refusal.
Measured on the real S1 capture:

```
warnings:
  column env_changed was excluded from the variant: coverage unavailable
  0 windows is below k_min 20: design 6.12 labels this run not assessable, and no decision is written
```

Both lines are true statements about S1: it has no environment fingerprint because no
launcher stamped one on a replayed fixture, and it has seven rows against a c_min of 32.

### 6. `changepoint_in_horizon` is unreachable on the synthetic series

The synthetic series puts its only changepoint at row 120, and 120 is itself an origin at
both H = 1 and H = 4. At that origin the regime began on the same row, so the context is
empty and the window is dropped as `regime_too_short` before the changepoint rule is
reached. The reason recorded is the first one that fires, and design 6.12 lists them in
that order.

So the branch had no test. It has one now, on a series whose changepoint sits at row 122
with H = 4: the window at origin 120 spans [120, 124), the changepoint is strictly
inside it, and it is the only origin excluded for that reason. Without this the rule
would have been code nobody had run.

### 7. echo and persistence have exactly equal mean MAE, and it is not a bug

On the 200-row seed-1 series at H = 1, both report 90.4338235294. echo is persistence
plus 1.0, so this looks like the offset never being applied.

It is applied. The series values are integers, so each window's error moves by exactly
+1 or -1: `|d - 1| - |d|` is -1 when `d >= 1` and +1 when `d <= 0`. Measured over the
136 windows: 68 have `d >= 1` and 68 have `d <= 0`. The two changes cancel exactly.

The medians differ (75.0 against 74.5), which is what shows the two forecasters are not
the same object. A coincidence of this seed, and I would not have believed it without
counting.

### 8. `timesfm3` carries no `__version__`

`getattr(timesfm3, "__version__", "unknown")` returns "unknown", and "unknown" in a
provenance field of a stored run says nothing at all. The adapter reads
`importlib.metadata.version("timesfm")` instead, which returns `3.0.0`. The pin in
pyproject.toml is exact for the reason this field records: a minor release that changes
padding or quantile handling would silently change numbers earlier runs are compared
against.

### 9. deptry reports one correct import as two problems

With `forecast/timesfm.py` importing `timesfm3`, `uv run deptry .` reported both
DEP002 ('timesfm' declared but not used) and DEP001 ('timesfm3' imported but not
declared). The distribution is `timesfm` and the module it installs is `timesfm3`, and
deptry maps one to the other by name unless told. `package_module_name_map = { timesfm =
"timesfm3" }` in `[tool.deptry]` is the telling. Measured with deptry 0.25.1.

The DEP002 ignore list also lost `numpy`, `timesfm` and `torch`, which its own comment
instructed: "DELETE EACH ENTRY WHEN ITS IMPORTER LANDS". `pyarrow` stays, for W6-T3.

### 10. numpy has to join the mypy override, for the reason the file already gives

`uv run mypy .` passed with the forecast extra absent and failed with it installed, and
the reverse would have been just as bad. numpy ships `py.typed`, so with the extra
installed mypy infers real array types and without it the module is not found at all,
which makes the gate answer a different question depending on who ran it. That is
exactly the failure `[[tool.mypy.overrides]]` in pyproject.toml was written to prevent
for torch, timesfm3 and pyarrow. numpy joins the list with `follow_imports = "skip"`,
and the two array locals in the adapter carry an explicit `: Any`, which is correct in
both environments. Verified by running `uv run mypy .` in each.

### 11. E03's checkpoint cache no longer exists, so it was downloaded once

The brief says to reuse `experiments/E03/out/hf` when it exists. It does not: `out/` is
gitignored, and neither this worktree nor the main checkout has it. There is no
timesfm entry in the default Hugging Face cache either.

So the checkpoint was fetched once, into
`experiments/E03/out/hf` in this worktree, pointed at by `TELLTALE_HF_CACHE`. **29.0 s
to download and load into an empty cache; 1,322,900,328 bytes across 8 files, counting
each blob once rather than following the symlinks.** That byte count matches E03's to
the byte, which is a small check that the cache is the same artefact E03 measured.
A warm load in a later process was 912.6 ms, faster than E03's 1.9 to 2.1 s; one
measurement, not a claim about the distribution.

### 12. cli.py had 200 lines of headroom, not five

W1-T5's log says `cli.py` is at 795 lines against the 800-line ratchet and that "the
next command that lands there has to move something out first". Measured: `git show
9350adc:src/telltale/cli.py | wc -l` is 795 and `git show 902820c:src/telltale/cli.py |

## WHAT CHANGED

`src/telltale/forecast/__init__.py` holds the interface and nothing that computes. The
`Window` a forecaster is handed is a frozen copy of the context rows with no store
handle. `TARGETS` is the pre-registered registry, three targets on the request clock,
each carrying c_min 32, horizons (1, 4), k_min 20 and the q80 threshold rule.
`FORECASTERS` maps a name to a FACTORY, never to an instance, and the timesfm entry
imports `telltale.forecast.timesfm` inside the factory body. `EchoStub` is persistence
plus 1.0 with a band of point plus `(q - 0.5) * 2.0`, and it appends every Window it
receives to `self.seen`, which is what the no-look-ahead test reads.

`baselines.py` holds four pure functions of the context array and a `Baseline` wrapper
that puts them behind the Forecaster signature. `residual_quantiles` builds a band from
the baseline's own one-step residuals inside the context and returns None with a warning
below eight of them. `quantile` is a named rule (linear interpolation between order
statistics, the same as numpy's default and `statistics.quantiles(method="inclusive")`),
used both for those bands and for tau, because a different rule would move tau and move
the whole lead-time table.

`backtest.py` is `run`, `metrics`, `persist` and `report`. `run` enumerates origins,
builds one Window per surviving origin, hands the identical Window to every forecaster
and times each call. `metrics` computes MAE mean and median, skill against the best of
the four baselines, calibration coverage with its binomial flag, WQS and the lead-time
table. `persist` builds the exact `FORECAST_RUN_COLUMNS` mapping. `report` prints the
constants, the command line, one table, the dropped-window reasons with counts, the
warnings and the weights licence whenever a checkpoint was involved.

`timesfm.py` loads one checkpoint per instance and makes one `predict_batch` call per
window, consumed with `list()` inside the timer because `predict_batch` returns a
generator. Every guard in it is a guard against something E03 measured the model doing
silently: `np.isfinite` on every array before the call, the 32-variate assertion, the
c_min refusal, and `padding_mode="edge"` fixed and recorded. `device` defaults to cpu and
`--device mps` is the opt-in.

`cli.py` gains `forecast backtest --series ID --target T [--horizon 1|4] [--forecasters
a,b,c] [--device cpu|mps]`. The forecasters are built before the store is opened, so a
refusal (an unknown name, a missing extra) does not leave a writer thread waiting behind
a 1.32 GB checkpoint load. A refusal is exit 2, the code `setup --apply` and `series
build` already spend.

## UNSURE OR NOT DONE

- **No forecast has been made on a real series long enough to backtest.** The longest
  real capture on this disk is eight model requests against a c_min of 32, so every
  number above comes from a seeded random walk. `forecast backtest` on the replayed S1
  capture runs, refuses nothing, and reports 0 windows with the two warnings that say
  why. The shapes are exercised; the behaviour of a forecaster on real request-clock
  data is not measured and cannot be until a long capture exists.
- **The 0-window run is still written to the database.** A run that produced no windows
  records that it was attempted, under which constants, and that k_min was not met. I
  think that is right, because "we tried and there was nothing to score" is a different
  answer from "nobody asked". Someone could reasonably want it refused instead.
- **`decision` and `placebo_seed` are null in every run, by design.** The chronology
  placebo, the four decision labels and the anti-cherry-pick halves are W3-T2. The
  `ordering` column is 'true' in every row this module writes, and the CHECK constraint
  already accepts the other two spellings.
- **Contract test 3 of design 6.12 is not written**, and the brief did not ask for it: it
  tests the decision labels, which do not exist yet. It belongs with W3-T2.
- **The calibration flag has never fired.** The rule is `|coverage_q - q| > 2 sqrt(q (1 -
  q) / n)`, and on the hand fixture n is 2, which makes the bound 0.42 at q = 0.1 and
  wider everywhere else. Two windows cannot flag a calibration. On the 200-row run
  nothing flagged either. The branch is exercised in the sense that it is computed on
  every run; it has not been seen to return True.
- **The lead-time hit branch is not reachable in a two-window H = 1 run**, and this took
  working out. Window A's actual is `y_o`, and window B's eligibility test is `y_o <
  tau`: a hit at A needs `y_o >= tau`, which makes B ineligible. So the fixture produces
  a miss and a false alarm, and the hit is asserted by calling `metrics(run["windows"],
  11.5)` on the same two windows at a lower threshold. Both sets of numbers are computed
  by hand in the test's comments.
- **The lead-time denominators are mine.** Design 6.12 names hit rate, false-alarm rate,
  median lead and timing error without saying what each rate divides by. I used hit rate
  = hits / (hits + misses) and false-alarm rate = false_alarms / (false_alarms + quiet),
  over windows with `y_{o-1} < tau`. Both are printed in the run's `assumptions` and both
  are hand-checked in the test. Somebody could reasonably use eligible windows as the
  denominator for both.
- **MPS is measured on one series and one horizon.** It runs, it is about twice as fast
  per call, and it agrees with CPU to the fourth decimal of the MAE median. That is one
  more data point than E03 had and it is still one machine and one input.
- **The 33-variate and NaN guards in the adapter are untested here.** E03 measured the
  model's silent behaviour and the assertions are written against those measurements, but
  no test in this repository drives them, because doing so needs torch and the suite runs
  without it. A live-marked test could.
- **`report()` prints `command` from `sys.argv`**, so a run made from a Python session
  rather than the CLI records that session's argv. It is stored in the `scenario` column
  beside the constants, which is the one free JSON column on the row.

# EXPLAIN FOR THE OWNER

## What was at stake

Telltale can now say what a session did, and W1-T5 turned that into a sequence a
forecaster can read. The obvious next move is to point a large time-series model at it
and report what comes out.

That move is where forecasting projects go wrong, and the way they go wrong is specific.
You get a number. The number looks plausible. Nothing tells you that a coin flip would
have done as well, and nothing tells you that the model was quietly shown the answer.

This task builds the apparatus that can tell you both things.

## Scoring a forecast on a past that already happened

Start with the problem. You have 200 rows of a session's history and a model that claims
to predict row 201. The history is over. How do you find out whether the model is any
good?

You cannot wait for row 201, because it happened already and you have it. And you cannot
just fit the model to all 200 rows and see how well it matches, because a model that has
seen the answer will match beautifully and tell you nothing.

So you pretend. Pick row 100. Hand the model rows 1 to 99 and nothing else. Ask for row
100. Compare its answer against the row 100 you already hold, which it has never seen.
That is one honest test.

One test is a coin flip. So you move the pretend-present forward and do it again: rows 1
to 100 predict row 101, rows 1 to 101 predict row 102, and so on to the end of the
history. Each of those is a separate out-of-sample test, and the score is over all of
them.

The row you are pretending to stand on is the **origin**, and moving it forward through
the history is a **rolling origin**. On the 200-row test series with a one-step horizon
there are 136 of them, so the table below is 136 separate tests per forecaster, not one.

Two details matter and both are refusals.

The context does not always start at row 1. It starts at the later of two places: 512
rows back, or the last point where the environment changed underneath the session. A
different model, a different tool set, a different content level: the rows before that
change came from a different machine in every sense that matters, and feeding them in as
context is feeding in somebody else's history. When a regime has not yet accumulated 32
rows, the window is not shortened or padded. It is dropped, and the reason
`regime_too_short` is counted. The 200-row series has one environment change at row 120,
and that is where 32 of the 32 dropped windows come from.

And a window with a hole in it is dropped rather than filled. If any value in the
context or the actual is unknown, the window goes, with the column that was missing named
in the reason. No policy fills a hole with an average, a zero or the previous value.

## The table, and what every column of it says

This is the real output of the real command on the 200-row test series, at horizon 1.

```
FORECASTER      N_WINDOWS  MAE_MEAN  MAE_MEDIAN  SKILL    CAL_MAX_DEV  COVERAGE80  WQS     LEAD_HIT_RATE  FALSE_ALARM_RATE  MEDIAN_LEAD  CLAIM_CLASS
--------------  ---------  --------  ----------  -------  -----------  ----------  ------  -------------  ----------------  -----------  -----------
echo            136        90.4338   75.0        0.0      0.4          0.0074      0.0914  0.0            0.0               -            derived
local_drift     136        101.1866  80.875      -0.1189  0.0574       0.7647      0.0816  1.0            0.0435            0            derived
persistence     136        90.4338   74.5        0.0      0.0324       0.7794      0.0742  1.0            0.0435            0            derived
rolling_mean    136        166.648   126.1875    -0.8428  0.0765       0.7132      0.1317  0.0            0.0652            -            derived
rolling_median  136        168.7721  132.25      -0.8662  0.0691       0.6985      0.1358  0.0            0.0652            -            derived
```

**FORECASTER.** Five of them. Four are baselines, which are deliberately stupid rules
written in one line each. Persistence says "tomorrow equals today". Rolling median and
rolling mean say "tomorrow equals the middle, or the average, of the last eight days".
Local drift measures how fast the series has been moving over the last eight rows and
carries that speed forward. The fifth, echo, is a test instrument rather than a
forecaster: it is persistence plus exactly 1, which makes it recognisable in a table, and
it keeps a copy of every window it was handed so a test can check what it was shown.

**N_WINDOWS.** How many of those separate tests this row is the average of. 136 here.
Below 20 the run prints a warning and refuses to draw any conclusion, because a score
over five tests is not a score.

**MAE_MEAN and MAE_MEDIAN.** The average and the middle of the 136 errors, where each
error is how far the forecast was from what actually happened, in tokens. Persistence was
off by 90 tokens on average and by 74.5 tokens in the typical window.

Both, rather than one, and the difference is informative: the mean is above the median
everywhere in this table, which says a few windows went badly wrong and dragged the
average up. That is the shape of these measures. Two other summaries were considered and
rejected on purpose: RMSE, which squares the errors and would let one compaction outweigh
fifty ordinary rows, and MASE, which divides by how much the series usually moves and
therefore divides by zero on a session that sat still.

**SKILL.** The number that answers "is this worth having". It is one minus this
forecaster's error divided by the best baseline's error. Zero means exactly as good as
the best baseline. Positive means better. Negative means worse: rolling_mean at -0.84 is
84 percent worse than persistence.

**CAL_MAX_DEV and COVERAGE80.** These are about the forecaster's honesty rather than its
accuracy. A forecaster does not only say "1200 tokens", it says how sure it is, as nine
levels: a value it thinks 10 percent of outcomes fall below, one for 20 percent, and so
on to 90 percent. If it is well calibrated, then over 136 windows about 10 percent of the
real values should actually fall below its 10 percent line.

CAL_MAX_DEV is the worst of those nine gaps. Persistence at 0.032 is well calibrated:
its bands mean what they say to within three percentage points. COVERAGE80 is how often
the truth landed inside the middle 80 percent of its band, which should be about 0.8.
Persistence gets 0.779.

Now look at echo: 0.4 and 0.0074. Its band is plus or minus 0.8 tokens on a series whose
steps are around 100 tokens, so the truth almost never lands inside it. That row is what
a confidently wrong forecaster looks like, and it is in the table so you can see the
shape.

**WQS.** One number that scores the accuracy and the honesty together, scaled by the size
of the series so it can be compared across targets. Lower is better. Persistence at
0.074 is the best here, which agrees with the two calibration columns.

**LEAD_HIT_RATE, FALSE_ALARM_RATE, MEDIAN_LEAD.** A different question from all of the
above: not "how close was the number" but "would this have warned me in time". Set a
threshold, here the 80th percentile of the first 32 rows. Look only at windows that start
below it, meaning the session was in a quiet state. Ask two things. Did the truth cross
the threshold? Did the forecaster's 80 percent line cross it? Both is a hit, with the
lead being how many steps of warning you got. Truth only is a miss. Forecaster only is a
false alarm.

Persistence hits every crossing (1.0) with a median lead of 0, meaning it warns exactly
when the crossing happens and not before. It also raises a false alarm in about 4 percent
of quiet windows. Echo hits nothing, because its band is too narrow to ever cross
anything.

**CLAIM_CLASS.** `derived`, on every row. This is Telltale's rule that a number never
gets presented as stronger evidence than the layer that produced it. Every number in this
table was computed by comparing forecasts against real values that were observed, so it
is derived. The forecasts themselves are `predictive`, and the stored row carries that
word on itself. A reader of this table is looking at measurements of predictions, not at
predictions.

## Why a one-line baseline beats a 330 million parameter model here

Add TimesFM-3 to the same run and it comes out behind persistence:

```
persistence  136  90.4338  74.5     0.0      0.0324  0.7794  0.0742
timesfm      136  92.7228  72.9603  -0.0253  0.0618  0.7868  0.0737
```

Skill -0.0253. Two and a half percent worse than "tomorrow equals today".

That is the correct answer, and the reason is in how the test series is built. It is a
random walk: each row is the previous row plus a fresh random number with no memory. For
a series like that, the best possible forecast of the next value is the current value.
Not "a good enough forecast" but the best one that exists, because the change from here
is by construction unpredictable. Persistence is not a weak competitor on this input. It
is the answer.

So a model that finishes 2.5 percent behind it has done well. It found nothing that was
not there, and it paid a small price in noise for looking.

This is the whole point of the four baselines, and it is worth being blunt about the
failure they prevent. Run TimesFM-3 on its own, with no baselines, and the table says
"mean absolute error 92.7 tokens". That number is not wrong and it is not useful. It
sounds like a finding. Put persistence beside it and you learn the thing that matters:
there was nothing here to forecast. The design's decision rule is built on exactly this
comparison, and it has a label for this case, `baseline sufficient`, which W3-T2 will
attach automatically.

Notice also which columns TimesFM does win. Its typical error is lower (72.96 against
74.5), its WQS is slightly better, and its 80 percent band is slightly better covered.
It is a bit better in the middle and a bit worse in the tails, which on a random walk is
a fair description of what a large model buys you: nothing about the direction, a little
about the spread.

## What the licence line means for later waves

Every run that touched the model prints this, and every stored row carries it:

```
weights: google/timesfm-3.0-pytorch under timesfm-non-commercial-license-v1.0 (research use, not production), device cpu, padding_mode edge
```

Read it as three separate facts, because they constrain different things.

The **licence** is the one with consequences outside this repository. Telltale's own code
is MIT. The model weights are not: `timesfm-non-commercial-license-v1.0` is a research
licence, so a forecast produced with these weights may not be shipped in a product or
sold as a service. Nothing about the recorder is affected, because the recorder never
loads them, and that separation is enforced rather than intended: `dependencies` in
pyproject.toml is empty, the model stack lives behind an optional extra, and a pre-commit
hook fails any file except `forecast/timesfm.py` that imports torch or timesfm. The
proof it holds is that the whole test suite passes in an environment where `import torch`
raises.

For later waves the practical rule is that a number carrying this line may go in a
report, a paper or a decision, and may not go in a product. The line is stored on the run
rather than printed once, so a number found in the database six months from now still has
it attached.

The **device** is there because it changes the answer. CPU and MPS agree to the fourth
decimal place, which is far inside anything that matters, but they are not identical, and
a run that cannot say which one produced it cannot be reproduced exactly.

The **padding mode** is there for a sharper reason. E03 measured that the same input
under `padding_mode="none"` and `padding_mode="edge"` gives forecasts differing by 1.41
on a series whose values run to about 30. That is not a rounding difference. It means
padding is part of the answer rather than part of the plumbing, so it is fixed in the
adapter and recorded on every run, and the day somebody deletes it as redundant because
the tests still pass, the stored runs will disagree with each other and the reason will
be on the row.

## Running it

Nothing here writes to a capture, and nothing here needs the model unless you name it.
The four baselines and the stub run in the default environment with no extra packages at
all.

```
uv run telltale forecast backtest --series <id> --target fresh_input_tokens
uv run telltale forecast backtest --series <id> --target output_tokens --horizon 4
uv run --extra forecast telltale forecast backtest --series <id> \
    --target fresh_input_tokens --forecasters persistence,timesfm [--device mps]
```

The first time you name `timesfm` it downloads 1.32 GB of weights, which took 29 seconds
here. Point `TELLTALE_HF_CACHE` at a directory to control where they land.
