# W10-F1: an unrecognized OTLP service.name is refused, not defaulted to claude

## OUTCOME

Done and measured. An OTLP batch on `/v1/logs` or `/v1/metrics` whose resource carries a
`service.name` that is not in `providers.SERVICE_NAMES` now gets a 200, stores zero
observations, and writes one `parse_failure` diagnostic that names the value:

```
/v1/logs: ValueError: unrecognized service.name 'some-other-app'
```

A batch in which no block carries `service.name` at all still goes to the receiver's
default provider, exactly as before. Every E01 and E02 fixture replay (15 scenarios, not
only S1) prints byte-identical output before and after, excluding the `health` line,
which carries wall-clock timestamps and a temp path. That line is identical too once
those two fields are removed. `uv run pytest -m integration -q`: 436 passed, 2 skipped.
The new tests are in `tests/integration/test_receiver_routing.py`.

The STOP condition was checked first and was not met. I parsed every OTLP block in every
fixture file (32 `otel_*.jsonl` files under `fixtures/`, script below): 91 blocks carry
`service.name = "claude-code"`, 117 carry `"codex_exec"`, and none carries another value
or lacks the key. The OTLP bodies the tests and `doctor.py` build by hand (grep of
`service.name` over `tests/` and `src/`) all use `"claude-code"` or `"codex_exec"`.
`SERVICE_NAMES` is not widened.

## WHAT WAS WRONG

`Receiver._otlp_provider` (`src/telltale/receiver.py`, before this change) did this for
each resource block:

```python
name = providers.SERVICE_NAMES.get(str(attrs.get("service.name")))
if name:
    return name
...
return self.default_provider
```

Two different cases gave the same answer:

- No `service.name` key: `attrs.get` gives `None`, `str(None)` is `"None"`, which is not
  in the map, so it fell through.
- A `service.name` nobody declared: not in the map, so it fell through.

Both reached `return self.default_provider`, and `telltale daemon` builds its `Receiver`
without a `provider` argument (`cli.py:363`), so the default is the constructor's
`"claude"`. The `.get()` over untrusted structure turned "I do not know who sent this"
into "Claude Code sent this". AGENTS.md names that defect class.

The brief gives the result on the owner's daemon, measured on 2026-09-14. I did not open
`~/.telltale` and have not re-measured it. It reports 18,897 observations under capture
`unattributed` since 2026-09-07, all with provider `claude` and types
`claude.otel.metric` (14,256), `claude.otel.codex.api_request` (1,717),
`claude.otel.codex.browser_use.security_check` (834), `claude.otel.codex.tool_result`
(752) and nine more `claude.otel.codex.*`. The claude allowlist knows none of those
fields, so the payloads are empty: `claude.otel.codex.api_request` is `{}`.

A second defect sat in the same loop. The first block with a known name decided the
provider for the whole batch, so a batch with a `claude-code` block and a stranger block
was stored in full as `claude`, the stranger's records included. The live replay below
shows it: two rows before, none after.

## WHAT CHANGED

**`src/telltale/receiver.py`.** `_otlp_provider` now reads every block's `service.name`.
It raises `ValueError(f"unrecognized service.name {value!r}")` if any present value is
not a key of `SERVICE_NAMES`, returns the first known block's provider otherwise, and
returns `self.default_provider` only when no block carried the key. A present value that
is not a string (an `intValue`, say) is refused as unrecognized. Before, `str()` turned
it into a string that could not match anyway, so no name that used to route is lost.
`_route`, `handle` and the handler's `parse_failure` catch are unchanged. The raise
reaches `_Handler.do_POST`, which writes the diagnostic and answers 200. It happens
before `_attribute`, so no capture is announced, no `launcher` row is written and no
surface count goes up.

## EXPLAIN FOR THE OWNER

**One port serves every provider, so the receiver has to be told who is talking.**

The daemon listens on one port. Claude Code and the codex CLI both send their telemetry
there, to the same two paths: `/v1/logs` and `/v1/metrics`. The path says what kind of
data it is. It does not say who sent it. That is in the body, as a resource attribute
every OpenTelemetry exporter sets:

```json
"resource": {"attributes": [{"key": "service.name", "value": {"stringValue": "claude-code"}}]}
```

Telltale keeps a short table of the names it knows:

```python
SERVICE_NAMES = {"claude-code": "claude", "codex": "codex", "codex_exec": "codex"}
```

The name picks the parser, and the parser picks the labels on every row it writes:
`provider = "claude"` and an `observation_type` beginning `claude.`.

**The mistake: "I do not know this name" was treated as "this must be Claude".**

The lookup had three possible outcomes and handled two of them:

1. The name is in the table. Use it. Correct.
2. There is no name at all. Use the daemon's default, `claude`. Reasonable: a bare test
   POST has no resource, and that is someone not saying, not someone lying.
3. There is a name, and it is not in the table. The code sent this to the default as
   well.

Case 3 is a different fact from case 2. Something told us who it was, we did not
recognise it, and we wrote its records down as Claude's anyway. On your machine,
another program has been sending OTLP to the daemon's port since 2026-09-07 (what it is,
and whether Telltale should record it, is your call and not part of this change). By
2026-09-14 that had produced 18,897 rows labelled `provider = claude`. Here is the same
thing reproduced against a fresh temporary database, with a receiver built the way
`telltale daemon` builds it, sending one record from `some-other-app`, and then one batch
with a `claude-code` block and the stranger's block together:

Before (HEAD `f43b834`):

```
--- stranger only: HTTP 200
  observation ('unattributed', 'claude', 'claude.otel.codex.api_request', '{}')
  diagnostic  ('launcher', 'unattributed', 'unattributed otel_logs record, session absent: no capture query, no attribute, no binding')
  diagnostic  ('unknown_field', 'unattributed', 'claude.otel.codex.api_request.event_name claude.otel.codex.api_request.model')
--- claude-code then stranger: HTTP 200
  observation ('unattributed', 'claude', 'claude.otel.codex.api_request', '{}')
  observation ('unattributed', 'claude', 'claude.otel.codex.api_request', '{}')
  diagnostic  ('launcher', ...)
  diagnostic  ('unknown_field', ...)
```

This matches your daemon's rows: capture `unattributed`, provider `claude`, type
`claude.otel.codex.api_request`, payload `{}`. The payload is empty because the claude
allowlist keeps only fields it knows, and it knows none of this program's. That is why
nothing leaked. It is also why the rows look like Claude records with nothing in them,
not like records from a different program.

After:

```
--- stranger only: HTTP 200
  diagnostic  ('parse_failure', None, "/v1/logs: ValueError: unrecognized service.name 'some-other-app'")
--- claude-code then stranger: HTTP 200
  diagnostic  ('parse_failure', None, "/v1/logs: ValueError: unrecognized service.name 'some-other-app'")
```

The sender still gets a 200, because Telltale must never change the behaviour of a
process that talks to it (AGENTS.md invariant 8). No row is written. One diagnostic says
exactly what arrived and why it was refused.

**The rejected answer: keep defaulting to `claude` and let the empty payload be the
hint.**

That was the old behaviour, and it can look harmless because nothing leaked. The problem
is who reads the rows later. A report, a series or a forecast that counts Claude Code
activity selects `provider = 'claude'`. It has no way to know that 14,256 of those metric
rows and 4,641 of those log rows came from something else, because the row says, in the
one column meant to answer "who sent this", that Claude did. A wrong provider is worse
than a missing one. A reader discounts a gap because they can see it. A wrong label they
have no reason to question, so they build on it. Telltale's rule is that unknown stays
unknown (AGENTS.md invariant 5), and this change applies it to the provider field. A
name we do not recognise is recorded as a name we do not recognise, in the diagnostics
table, and nothing is invented on its behalf.

**Why "no name" still defaults.** Refusing everything without a name would be the
opposite mistake. A bare test POST, or a new surface that has not set a resource yet,
would be dropped. That the name is missing tells us nothing about who
sent it, so the old default stands. The fixture scan found no recorded session in that
case (every block in E01 and E02 carries a known name), so this path is covered by the
new test only, and that test passes both before and after the change on purpose.

**Why one stranger refuses the whole batch.** A batch is one HTTP request from one
exporter, and there is one parser per request. If a batch mixes a known block and an
unknown one, the only way to "keep the known part" is to parse the unknown block with
the known block's parser. That is the same mislabelling, just harder to see. So the
whole request is refused and the diagnostic names the value.
