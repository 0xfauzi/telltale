The limit: **a rerun is a no-op for a session that is already stored, including one that
has grown since.** The importer imports a session whole or skips it whole. A session
that is still being written when a run fires is stored as far as it had got, and no
later run adds the rest. Measured below (WHAT WAS WRONG). The plist, the printed
instructions and the how-to paragraph all say this. The fix belongs in the importer,
which this task does not own (NEXT).

## WHAT WAS WRONG

Four things in the brief or the code turned out different from what the brief says.
None of them stopped the task.

**1. Rerunning is safe, but it does not keep a session up to date.** The brief says the
task rests on `import_files` being idempotent and asks me to verify it. The idempotence
is real, but it is whole-session. `importer.import_files` (src/telltale/importer.py:230)
does:

```python
stored = {str(row["capture_id"]) for row in store.captures()}
...
if source.capture_id in stored:
    result["skipped"] += 1
    continue
```

and `Source.capture_id` (importer_scan.py:100) hashes the provider and the session id
only. A file that gains lines keeps its capture id and is skipped. The docstring says
this is on purpose: observations are append-only, so re-reading the file would double
every count. The consequence for a timer is new, though. On an hourly schedule, any
session that runs for more than an hour while the machine is awake is caught part way,
and it stays cut off.

Measured with `/tmp/w11_append_probe.py`. It is not committed, because it reads the
owner's real sessions. The script is reproduced below. It copies the real root to a
temp dir, cuts the largest real session transcript (1,269 lines) to its first half,
imports it into a temp store, puts the full file back, imports again, and then imports
the full file into a fresh store to compare:

```python
ROOT = Path.home() / "Library/Application Support/Claude/local-agent-mode-sessions"

def run(home, root):   # `telltale import claude-transcripts --root ROOT`, last line
    env = {**os.environ, "TELLTALE_HOME": str(home)}
    return subprocess.run(["uv", "run", "--no-sync", "telltale", "import",
        "claude-transcripts", "--root", str(root)], cwd=REPO, env=env,
        capture_output=True, text=True, check=True).stdout.strip().splitlines()[-1]

work = Path(tempfile.mkdtemp()); src = work / "src"
shutil.copytree(ROOT, src, symlinks=True)
sessions = [p for p in src.rglob("*.jsonl")
            if p.is_file() and not p.is_symlink() and '"sessionId"' in p.read_text()]
target = max(sessions, key=lambda p: len(p.read_text().splitlines()))
full = target.read_text(); lines = full.splitlines(keepends=True)
target.write_text("".join(lines[: len(lines) // 2]))
run(partial, src); target.write_text(full); run(partial, src); run(fresh, src)
# then SELECT COUNT(*) FROM observations in each store, opened mode=ro
```

**3. The importer's "already imported" counter is called `skipped`, not
`already_stored`.** `import_files` returns `result["skipped"]`, and the CLI prints it

**4. The daemon's printed save pipeline saves more than the plist.** This is outside my
files and I have not fixed it. `setup_daemon.INSTRUCTIONS` and the how-to
(03-capture-howto.md, "Starting the daemon at login") both say:

```
telltale setup claude --print --daemon | sed -n '/<?xml/,/<\/plist>/p' > ~/Library/LaunchAgents/com.telltale.daemon.plist
```

The instruction line that names that sed itself contains `<?xml`. So sed opens a second
range there and prints to the end of the output. Measured: the saved file is 186 lines,
the plist followed by the comments and the settings JSON. `plutil -lint` says OK,
because the CoreFoundation parser stops at the first `</plist>`, so launchd very likely
loads it. `plistlib.loads` refuses the same file (`ExpatError: not well-formed (invalid
token): line 32`). I hit this in my own instructions first and fixed them there: the sed
now quits at the first `</plist>` (`sed -n '/<?xml/,/<\/plist>/p;/<\/plist>/q'`). The
new test runs the printed pipeline through `/bin/sh` and parses the result with
plistlib, so the defect cannot come back in this plist. The existing daemon test takes
the XML out with `str.index` and never runs the sed, which is how the daemon's copy got
through.

## WHAT CHANGED

**`src/telltale/setup_import.py` (new, 179 lines).** It has the same shape as
setup_daemon.py:

- `plist(root, interval_s, home, binary, kind, level) -> str` builds the agent with
  plistlib: `Label`, `ProgramArguments = [binary, "import", kind, "--root", root,
  "--level", level]`, `EnvironmentVariables = {"TELLTALE_HOME": home}`, `StartInterval`
  (an integer), `RunAtLoad = True`, and no `KeepAlive`. `KeepAlive` would respawn a job
  that exits, which is what an import does. launchd.plist(5): a firing is missed while
  the job is still running or the machine is asleep. A missed firing costs nothing here,
  because the next run reads the same files. `StandardOutPath` and `StandardErrorPath`
  are `$TELLTALE_HOME/<label>.log` and `.err`.
- `label(root, kind)` returns `com.telltale.import.<root's last name, slugged>.<8 hex>`.
  The 8 hex are sha256 of `kind:root`, so two roots with the same last component get two
  labels, two plist files and two logs instead of overwriting each other. The label is
  stable for the same absolute root, which the unload line depends on.
- `INSTRUCTIONS` uses the daemon's wording: PRINTED only, the save pipeline, `launchctl
  load` and `launchctl unload`, the whole-session limit in three lines, and the AGENTS.md
  invariant 7 sentence. The save line is built with `shlex.join`, so the space in
  `Application Support` is quoted.
- `add_flags(parser)` registers `--import-schedule ROOT` and `--import-interval
  SECONDS`. `text(args, home) -> str` returns the plist and instructions, or `""` when
  there is no schedule. It returns a string instead of printing because ruff's T201 is
  allowed only in `cli*.py` and `report.py` (pyproject.toml, not mine), and
  setup_daemon.py already splits the work the same way.
- `binary()` and `INSTALL_DIR` are imported from setup_daemon, not copied. I checked
  that `binary()` has nothing daemon-specific in it.

Refusals, all through `SystemExit` the way `cli._level` refuses a bad level, and all
before anything is printed:

- `--import-interval` without `--import-schedule`. Otherwise the flag would look like it
  had set something.
- a ROOT that is not a directory. That would be a job that fails on every firing.
- an interval below 1 or not a whole number (an argparse type). launchd has no meaning
  for either.

ROOT is `expanduser().absolute()`: launchd does no `~` expansion, and its cwd is `/`.

Two choices that differ from the brief's sketch:

- **`--level` is in `ProgramArguments`.** The brief's list omits it. I added it because
  `setup` already takes `--level`, and without it `setup ... --level 2
  --import-schedule X` would quietly schedule an import at whatever `config.json` says
  when the job fires. The daemon plist passes its level for the same reason.
- **The flag names are `--import-schedule` and `--import-interval`.** The second is
  prefixed so it cannot be read as an interval for `--daemon`.

## UNSURE OR NOT DONE

- **The plist was never loaded into launchd.** Loading it would mean writing to
  `~/Library/LaunchAgents` or registering a job in the owner's launchd domain. Both are
  outside this repository, and that is the owner's call under invariant 7. What I
  verified is the closest stand-in: the plist parses (`plutil -lint` and plistlib), and
  the job runs correctly with launchd's argv, environment, cwd and PATH. Still untested:
  launchd's own `RunAtLoad` and `StartInterval` firing, and whether the log files
  appear. Running `launchctl load` once, then `launchctl list | grep
  com.telltale.import` and a look at `$TELLTALE_HOME/<label>.log`, would settle it.
- **Runs under launchd's PATH were compared with runs under the shell's PATH on this
  machine only.** Both imports of the real root agree on every row once observation ids
  and lifecycle payloads are set aside (0 rows differ by capture, type, repo and
  environment fingerprint, and 0 non-lifecycle payloads differ). `repo_id` is None for
  all 61 local-agent-mode captures in both runs, so this root never exercised git
  resolution under the minimal PATH. A root whose sessions ran inside git checkouts
  would need its own comparison.
- **Each rerun writes 70 diagnostics rows**, one per file under the root that names no
  session (plugin caches under `cowork_plugins/`, measured: 70 files with no
  `"sessionId"`). That is 70 rows a firing, up to 1,680 a day at 3600 s. `telltale
  purge --diagnostics-older-than N` is the existing retention. I have not measured what
  that growth costs the store.
- **The default of 3600 is the brief's example, not a measured optimum.** A no-op
  rerun costs 0.58 s wall on 131 files, so frequency is cheap in time. The costs that
  do grow with frequency are the diagnostics above and, until the importer changes, the
  chance of freezing a session part way.
- **One edit outside OWNS: `docs/README.md`, "70 reports" changed to "71 reports".**
  The `docs-links-resolve` hook refuses the commit without it (`docs/README.md:0: log
  count (71) is not stated`). W9-T1, W9-T2 and W10-F1 each made the same one-word
  change alongside their log.

## NEXT

1. **The importer needs a way to finish a session it has already imported.** This is
   what would make a schedule do what this brief wanted. Two mechanisms, neither
   measured yet:
   (a) Skip only files that have not changed for a quiet period, by mtime. This keeps
   whole-session import and delays a live session by the quiet period plus one interval.
   (b) Record the line count or byte offset imported per source, and later append the
   tail. This conflicts with the `capture_ended` row already written, so it needs a
   design decision about what an ended capture that grows means.
   Either one changes `importer.py` or `importer_scan.py`, so it is a new task.

## EXPLAIN FOR THE OWNER

Telltale has two ways to hear about a session you did not start through `telltale run`.
The daemon listens: Claude Code, once its settings point at the daemon, sends telemetry
and hook calls as the session happens. The Claude desktop app's local-agent-mode sends
nothing. It writes each session to a transcript file under `~/Library/Application
Support/Claude/local-agent-mode-sessions` and that is all. For that app, the daemon has
nothing to receive.

What does work is reading the files afterwards, which `telltale import
claude-transcripts --root <that directory>` already does. On this machine it finds 131
files and imports 61 sessions, 15,248 observations, in under 3 seconds. The other 70
files are plugin caches that name no session. This task adds nothing to the import. It
adds the way to rerun it without you remembering to:

```
telltale setup claude --print --import-schedule ~/Library/"Application Support"/Claude/local-agent-mode-sessions
```

That prints a launchd plist: run this import at login, then every hour. The plist
names the absolute path of `telltale`, the folder and your `TELLTALE_HOME`, because
launchd starts jobs with almost no environment. After the plist come the lines that
save it to `~/Library/LaunchAgents` and load it. Telltale does not run those lines
itself. That is the same rule as the daemon's plist and your settings file: anything
that keeps running after you close the terminal is yours to install.

Running the import again is harmless. The second run on your folder added 0 in 0.6
seconds, because each session is recognised by its id and skipped if it is already
stored.

That same skip is the catch. The importer treats a session as done once it has been
stored. If the hourly run fires while you are in the middle of a desktop session, it
stores the session up to that point. When you carry on, the file grows, but every later
run sees an id it already has and skips it. I measured this on a copy of your folder: I
cut one real session to half its lines, imported, put the full file back and imported
again. The store stayed 504 observations short of a fresh import, and the second run
reported "0 observations" as if nothing had happened.

So the schedule keeps new sessions arriving. It does not keep a session up to date
while it is still being written. Today every one of the 61 imported sessions in your
real store matches a fresh import (checked read-only), so nothing has been cut off yet.
Whether to load the schedule before the importer learns to finish a grown session
(NEXT 1) is your decision. If you do load it now, a session that was cut off can be
repaired by hand. `telltale purge <capture>` removes the partial capture, and the next
import stores the whole file. That was measured on the test fixture: 19 observations
before, 37 after, equal to a fresh import.
