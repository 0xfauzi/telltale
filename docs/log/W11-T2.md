**`src/telltale/providers/codex_app.py`** (new). In the order a record meets it:

1. `parse("otel_logs", ...)` walks records with the shared `providers.otlp_points`, which
   already turns OTLP attributes into a dict through `otlp_attrs`.
2. `_classify` reads the attribute KEY LIST off the wire record, not off that dict. The
   dict keeps the last of two attributes with one key and skips an item it cannot read,
   and either would let a malformed record pass as a measured shape. A repeated or
   unreadable key gives the note `codex_app.otel:unreadable_attributes`. A missing
   `event.name` gives `codex_app.otel:no_event_name`. A name outside the twelve gives
   `codex_app.otel:unknown_event_name`, and the name itself is not written, because a
   name outside the twelve is an unmeasured value. A name inside the twelve whose key set
   is not one of the four gives `codex_app.otel.<name>:unmeasured_shape`. The receiver's
   existing `_report_notes` turns a request's notes into one `dropped` diagnostic with
   counts.
3. For a matched record: dots become underscores, `conversation.id` goes to the session
   column and not the payload, and `_admit` checks each LISTED field's type before the
   sanitizer sees it. A list or an object is refused as `not_a_scalar`. A Kind.SCALAR
   field is admitted only as a boolean or the strings "true" and "false" (the CLI's
   spelling of `success`), and anything else is refused as `not_a_bool`. A Kind.SIZE
   field given as a decimal string is converted, as E02 measured the CLI sending
   durations and token counts. Each refusal is appended to the row's `redaction.dropped`
   as `field:reason`, so the row says what arrived and went. Unlisted names go to
   `sanitize.sanitize` untouched, which drops `arguments` and `output` as
   `never_persist` and `user_account_id` and `user_email` as `refused`.
4. `provider_session_id` and the `call_id` correlation are written only if they match
   `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}`, because those two columns bypass the sanitizer.
   `provider_ts` is `event.timestamp` only if `datetime.fromisoformat` reads it, else the
   record's own clock, and a zero clock is treated as unknown rather than 1970.
5. `parse("otel_metrics", ...)` stores nothing and notes `codex_app.otel.metric:unmeasured`
   once per data point. Pass 1 names no metric and no metric attribute was measured.

Only record attributes are ever read. The log record's body, the resource attributes
other than `service.name`, and the scope are never read, so none of them can be stored.

## EXPLAIN FOR THE OWNER

### What the problem is

The desktop app sends its telemetry to the same port as Claude Code and the codex CLI.
Telemetry here means small structured records, one per event, each a list of named
fields. Until this change Telltale refused all of it, because it did not know the sender.
Accepting it means deciding, field by field, what may be written to your disk. Some of
these records carry what a tool printed, and that must never be stored.

The difficulty is what we know. The orchestrator measured the app for about 50 seconds in
total and wrote down only field NAMES. It found four distinct lists of names. Separately
it knows twelve event names the app uses. Nobody saw which event name goes with which
list.

### The example: the tool-call record

Here is the first list, with the value each field held in the test that replays it:

| field on the wire | stored as | what happened, and why |
|---|---|---|
| `arguments` | nothing | refused at every level. It is the tool's input (on the CLI, a JSON string holding the command or a whole patch). The name is in `sanitize.NEVER_PERSIST`, the hard-stop list that wins over any allowlist. |
| `output` | nothing | refused, same list. It is what the tool printed. |
| `user.account_id`, `user.email` | nothing | refused. The parser turns the dot into an underscore, and `user_account_id` and `user_email` are in `sanitize.REFUSED`, the list for identity we read and will not keep. Counted as refused, not as an unknown field. |
| `conversation.id` | the session column | it names the session, and the daemon hashes it into the capture id. It must look like an id (letters, digits, `.`, `_`, `:`, `-`, at most 128), because that column bypasses the sanitizer. |
| `call_id` | `call_id`, max 128 | an id. Also joins a tool decision to its outcome. |
| `duration_ms`, `tool_result_seq` | numbers | a count or a duration. A value that is not a number is dropped as `not_a_number`. |
| `success`, `output_truncated` | booleans only | flags. A flag that arrives as anything but a boolean or "true"/"false" is dropped as `not_a_bool`. This matters most for `output_truncated`: if it ever held a preview of the output, the plain Kind.SCALAR rule would have kept 512 characters of it. |
| `tool_name`, `tool_namespace`, `mcp_server`, `mcp_server_origin`, `agent_name`, `slug`, `originator`, `auth_mode`, `model`, `app.version`, `terminal.type` | short names, max 64 | symbolic names. The 64-character cap truncates a longer value and records that it did. Their lengths on the app were not measured, which is why they are capped rather than trusted. |
| `event.name` | `event_name`, max 64 | one of the twelve names, and only those twelve get this far. Kept so the rows record which name carried this list. |
| `event.timestamp` | `event_timestamp`, max 64, and the row's time | used as the row's provider time only if it reads as a timestamp. |

The rule under the table: nothing stored from this provider can be longer than 128
characters, no field is a path, a command or free text, and a field of the wrong type is
named and dropped.

### How a record gets classified

A record is stored only if its list of field names is exactly one of the four measured
lists. One field more and it is refused whole: that extra field is exactly where a
renamed content field would sit, and nobody has seen it. One field fewer and it is also
refused, because nobody measured which fields are optional.

That is stricter than the allowlist alone. The allowlist would store a record with an
extra `result_text` and drop just that field, and the drop would be safe. But the record
would then look like a known shape with one oddity, when it is really a shape nobody has
seen. So the whole record goes, and the diagnostic says `unmeasured_shape` with the event
name.

### The answer the brief rejected, and why it is wrong

The tempting answer: take all twelve event names, guess which list goes with each, and
give the other eight a best-guess allowlist built from the four lists.

Take `codex.tool_result`. By analogy with Claude Code, a tool result is the event most
likely to carry raw content. `NEVER_PERSIST` only stops field names it already knows:
`output` yes, `result_text` or `payload` no. A guessed allowlist for an unmeasured event
could therefore store content under a name nobody thought to block. So no event name gets
an allowlist here, and no list is guessed for any name.

### The answer I rejected, and why it is the owner's call

The brief also says: leave every `codex.tool_result` record unstored. I checked the CLI
fixtures, and the first list above is, field for field, what the CLI sends as
`codex.tool_result` (36 of 36 records). So on the app, the tool-call list and
`codex.tool_result` are very likely the same record.

I could have refused `codex.tool_result` by name as well. I did not, because it would
refuse this exact list, whose every field is accounted for in the table above. The
privacy risk the brief names is a field nobody measured, and a record with any such
field is already refused whole by the exact-match rule; the `[field_added]` test is that
case. A name rule would add no protection against that risk and would probably mean the
tool-call list is never stored. That is my judgement, the brief's author may reasonably
differ, and NEXT 1 is the one-line reversal.
