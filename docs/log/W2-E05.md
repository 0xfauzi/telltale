## WHAT WAS WRONG

**`--permission-mode acceptEdits` in a headless run is a session that cannot do
anything.** The mode auto-accepts file edits and nothing else, so the first `Bash` call
raises a permission request, and `claude -p` has no keyboard to answer it from. The tool
result comes back as an error, the model tries twice more, and the session ends. E01's
S1 ran this same prompt with `--permission-mode bypassPermissions --max-turns 40` and
fixed the test in 7 turns; the flag is the whole difference. The flag came from the
brief, so the five sessions bought the answer to a question nobody asked. It is now a
refusal: `experiments._approvable` rejects a spec whose argv is headless `claude`
without `bypassPermissions`, before the store is opened and before a token is spent, and
names the reason.

The check sits in `repeat` and NOT in `_checked`, deliberately. It is a rule about
starting a session, and `from_store` has to be able to rebuild the report of a condition
that already ran under the wrong flag. A recovery path that refused to recover the record
of a mistake deletes the evidence of it.

**`telltale experiment repeat` writes nothing until every repetition is done.** The
orchestrating session ended while attempt 5 was in flight; the runner died with it and
took the `claude` process with it (attempt 5's capture records `exit_code` 143). Five
captures existed and there was no report, no decision file and an empty
`repeat.stdout.txt`. `experiments.from_store` now rebuilds the report from the captures
themselves and launches nothing, and `experiments.finish` records the correlation and
outcome of a repetition the runner never closed by RUNNING the acceptance command in the
worktree it left behind, so attempt 5's fail is still a result the harness measured
rather than one a person decided. `experiments/E05/run.py` line-buffers its own stdout
for the same reason.

One field cannot come back and is not substituted: `wall_ms`, the wrapper's
`perf_counter` around `telltale run`, is None in a recovered report, and
`capture_span_ms` (capture_started to capture_ended, arrival clock) sits beside it under
its own name. An acceptance the harness never recorded reads `unknown`, never `fail`.

**`experiments.vector()` was still W1-T4's placeholder.** It read the stream result's
four token counters and the tool calls by name, and W1-T4 left it for W2-T4 to replace;
W2-T4 built spec 13.7's vector in cohorts.py and did not touch experiments.py. The H2
statistics were on course to be computed over four token counts and a turn count instead
of over the 22 metrics design 6.12 names. It now reads the evidence table: the 22 metrics of
`cohorts.VECTOR` keyed `family.metric`, value or None as the row has it, beside the three
stream facts no reducer measures (`duration_ms`, `num_turns`, the tool calls by name). A
capture with no evidence row at all is refused by id rather than reported as 22 unknowns.

**`failed_test_runs` counts refused tool calls the same way it counts failing tests.**
All five captures report `agent_test_runs` 3 and `failed_test_runs` 3, and no test ever
ran. `activities._tool_outcome` takes `success` from OTel `tool_result.success`, from a
`PostToolUseFailure` hook, or from the stream's `is_error`; a permission denial sets
`is_error`, so `success` is false by the same route a failing test sets it. Not a defect
in the reducer, which recorded what the surfaces said, and the distinction IS in the
capture (`claude.stream.system.permission_denied`, and the activities carry no exit
code). Recorded rather than fixed: activities.py is not this task's file, and the fix is
a decision about what `success` means when a call was never made.

**Two of the 22 metrics are unknown for a fake-agent capture, and the reason is a key
name.** `activities._request` fills a stream-only request's usage fields through
`correlate.USAGE_KEYS`, which is the OTel spelling; the stream spells two of them
`cache_read_input_tokens` and `cache_creation_input_tokens`. So a capture with no OTel
`api_request` has `cache_read_tokens` null at coverage partial. Measured, not reasoned:
the real sessions here have OTel up and report `cache_read_tokens` 119,496. Recorded, not
fixed, for the same reason as above.

# EXPLAIN FOR THE OWNER

## What a permission mode is

Claude Code will not run a shell command or write a file just because the model asked. In
between the model's request and the machine there is a gate, and the permission mode is
the setting that says what the gate lets through without asking a person.

There are a few of them. `bypassPermissions` opens the gate: everything the model asks
for happens. `acceptEdits` opens it a crack: file edits happen, and anything else stops
at the gate and raises a request. The default stops almost everything.

Our spec said `acceptEdits`. Read literally that is a sensible-sounding choice for an
experiment: let it edit the file it is meant to fix, and keep it from running arbitrary
commands. The trouble is that the task we asked for begins with running a command. The
prompt is "Run the tests with `uv run pytest`, fix the bug, run the tests again, and
stop". The very first thing the model tried to do was the one thing the gate was set to
stop.

## What "requires approval" means when nobody is at the keyboard

When you use Claude Code interactively and it wants to run something the gate stops, you
get a prompt: allow, allow always, or deny. You answer, and the session continues.

`claude -p` is the headless form. There is no terminal to draw a prompt on and no person
watching. So when the gate stops a call, there is nothing to wait for. The call comes
back to the model as an error, and the text of that error is what our capture recorded:

```
This Bash command contains multiple operations. The following part requires approval:
uv run pytest 2>&1
```

and then, twice:

```
This command requires approval
```

The model did what a reasonable person does when a command keeps being refused. It tried
a simpler version of the command, tried again, and then said so and stopped. Four turns,
about eight seconds, roughly 135,000 tokens, and no work.

The thing worth noticing is that this is not a crash. Nothing errored. The session
reported `is_error: false` and `stop_reason: end_turn`, which is the same thing a
successful session reports. Looking only at exit codes calls all five a
success. What told us otherwise was the recorder: three
`claude.stream.system.permission_denied` records per session, zero files read, zero files
changed, and the harness's own `pytest` run afterwards still failing. That is the point
of measuring the result rather than believing the report.

## Why five sessions of seven seconds still tell us the harness works

The experiment failed. The recorder did not, and the two are worth separating.

Everything Telltale is supposed to do, it did, against five real Claude Code sessions
rather than a scripted stand-in:

- All four capture surfaces delivered on all five sessions. That is the `4/4` in the
  coverage column, and it is the first time the launcher has been measured at 4/4 five
  times in a row on real sessions.
- The five sessions produced one environment fingerprint. That is the assertion design
  6.12 asks for: two of the five differing in model or runtime version stops the runner
  from computing statistics at all, and it names the field that differs. It never had to
  here, because they did not differ.
- Attempts 1 to 5 were each recorded as an attempt of the task, and each got an
  acceptance result that the harness measured by running the tests itself. Not one of the
  five agents was asked whether it had succeeded.
- The reducers turned all of it into the 22 numbers of the evidence vector, and
  `telltale vector` on session 1 prints the same 22 numbers the experiment's statistics
  were computed from. Two readers of the same capture cannot disagree about a number.
- And the defect was diagnosable from the database alone. We did not have to open a log
  or reconstruct what happened from memory: the store holds the permission mode, the
  refusals, and the absence of any file being touched.

That last one is the whole product thesis in miniature. Something went wrong in a batch
of agent sessions; the flight recorder said what, without anyone having thought in
advance to instrument it.

## What the numbers in the write-up are and are not

The tables in `docs/experiments/E05.md` look like the H2 result. They are the right
shape: per measure, five values, a median, a robust spread, a minimum detectable
difference, a verdict. They are not the H2 result, because all five sessions did the
identical nothing.

Eighteen of the twenty-six rows say "no within-condition variation observed at n = 5".
That phrase is doing careful work, and it is worth being precise about why it is not "no
variation".

Five identical values tell you that the spread is smaller than five samples can see. They
do not tell you it is zero. If you flip a fair coin five times and get five heads, you
have not measured a two-headed coin; you have measured that five flips cannot tell the
two apart. The same holds here with more force: `unique_files_changed` was 0 in all five
sessions, and a spread of zero on that measure says nothing about how much it varies when
an agent is actually editing files, because none of these agents was.

This matters because a spread of zero has consequences downstream. The minimum detectable
difference is `2.8 * s * sqrt(2/n)`, so a spread of zero makes it zero, which claims every
difference is resolvable. Reporting that as "this measure does not vary" is the error the
phrase exists to prevent.

## One measure, computed by hand

Take `context_token_burden.output_tokens`, the tokens the model produced. Its five values,
sorted:

```
301, 303, 317, 366, 477
```

The median is the middle one, 317.

The spread is the scaled median absolute deviation. Take each value's distance from 317:

```
16, 14, 0, 49, 160
```

The median of those five distances is 16. Multiply by 1.4826, the constant that makes a
median absolute deviation comparable to a standard deviation on normal data:

```
s = 1.4826 * 16 = 23.72
```

Now the minimum detectable difference at five samples:

```
MDD = 2.8 * 23.72 * sqrt(2/5) = 2.8 * 23.72 * 0.6325 = 42.0 tokens
```

That is the smallest difference in median output tokens that a five-against-five
comparison could reliably separate from noise. Compare it against a quarter of the
median, which is design 6.12's demotion threshold: 0.25 * 317 = 79.3. Since 42.0 is
below 79.3, the measure is not demoted. The number of samples needed for MDD to reach
that threshold is 2, so five is already more than enough.

Notice what the robust spread did with 477. That value is nearly 60 per cent above the
median and it moves the answer hardly at all, because the median absolute deviation only
cares where the middle of the distances is. A standard deviation over the same five
numbers is about 73, three times larger, and it is set almost entirely by that one
session. That is why design 6.12 specifies the scaled MAD and not the standard
deviation: agent sessions produce occasional very large values, and a spread that one
outlier can triple is a spread that reports the outlier rather than the process.

## Which measures are demoted, and what N_needed says

Exactly one: `stable_state_work.stable_state_total_ms`, the time the session spent with
the repository unchanged. Its values are 3125, 4092, 7983, 8188 and 33274 ms; median
7983, s = 5768.8, MDD = 10215.8. Since 10215.8 is larger than a quarter of 7983 (1995.8),
the measure cannot resolve a difference smaller than itself, and it is withheld from
repository comparison.

`N_needed` answers "how many samples per side does it take?" Rearranging the formula:

```
N_needed = ceil(2 * (2.8 * 5768.8 / 1995.8)^2) = 132
```

132 sessions per side. Design 6.12 caps scaling at 20, so the honest reading is that this
measure is not going to be resolvable at any sample size we will pay for, and comparisons
that need it will have to be built differently or dropped.

Three measures came out resolvable, needing 1 or 2 samples per side:
`cache_read_tokens`, `output_tokens` and `stable_state_tokens`. Four were not judged at
all: two (`pre_compaction_tokens`, `read_to_edit_ratio`) had no value in any session, and
two (`duration_ms`, `num_turns`) had four of five, because the session that was cut short
never produced the message they come from. A measure with fewer than five known values
reports its n and gets no verdict, which is the rule refusing to judge on partial data
rather than filling the gap.

All of these verdicts are about five permission failures. They will need to be measured
again on five sessions that were allowed to work.

## WHAT WAS WRONG

**The validation gate was run before the other four sessions were paid for, and it
passed.** Attempt 1 was run alone under `E05_REPETITIONS=1`, and `telltale timeline` on
its capture had to show a `file_edit` on `pkg/calc.py` with a `verification_run` after

Two defects in the runner were found by rehearsing the resume path on the fixture agent,
before any real session, and both are fixed:

1. A second invocation re-ran `prepare()`, which rebuilt the fixture repository and

**Two measurement caveats that this run made visible, neither of which is a bug in the
reducer.**

all five, although the fixture starts with a genuinely failing test and every session ran
the tests before editing. The agent piped pytest into `tail`, so the shell's exit status

recorded the exit status of the command that was run. The caveat belongs on the measure:
in the pilot `failed_test_runs` was 3 for three refused calls, and here it is 0 for one
genuinely failing test run. Reading it as "tests that failed" is unsafe in both

different fix. That is the one place the work genuinely varied, and no measure in spec
13.7's vector reports it.

## WHAT CHANGED

`src/telltale/experiments.py`, one behaviour added and it is the change the amendment
asked to be declared: **a condition now resumes the attempts the store already holds.**
`repeat` asks `_resumed(checked, store, attempt)` for each attempt before running it.
That returns the read-back run when exactly one capture in the store claims
`(experiment, task_id, attempt)` at this environment fingerprint, None when none does, so
the repetition runs, and raises `SpecError` when more than one does, because two captures
claiming one attempt is a cardinality question the runner may not answer by picking. It
is the same read-back `from_store` uses, so a resumed attempt and a recovered attempt are
one code path. Runs carry `"source": "run"` or `"source": "store"`, and the report's
`recovered_from_store` flag is computed from them rather than passed in.

This is what let attempt 1 be validated alone and attempts 2 to 5 be run afterwards
without a sixth session replacing attempt 1. Its `wall_ms` is null in the report for that
reason: the wrapper that measured it belonged to the first invocation, which printed
14185 ms.

A test covers it: `test_a_condition_resumes_the_attempts_the_store_already_holds` runs
one repetition, then runs two against the same spec and asserts the store gained exactly
one capture and the report holds one `store` run and one `run` run. Break-and-restore
done: forcing `_resumed` to return None made the store gain a third capture and the test
failed.

`experiments/E05/run.py` gained `--finish-attempt N`, `_grown()` and the `condition()`
reuse described above, and line-buffered stdout so a foreground run prints as it goes.
`TASK_ID` defaults to `E05r2` and is overridable by `E05_TASK_ID`; `REPETITIONS` by
`E05_REPETITIONS`.

`docs/experiments/E05.md` keeps the pilot as "The pilot condition (E05)" with its own
section on what it cost and what it bought, and gains "The measured condition (E05r2)":
the argv, the fingerprint, the five-session table, the per-measure table with n, median,
scaled MAD, IQR, min, max and the full sorted values, the decision table with MDD and
N_needed, the demotion table, the acceptance results, and "what downstream may now say"
written from those numbers.

Artefacts committed with `git add -f` (the `out/` directory is gitignored):
`experiments/E05/out/spec-E05r2.json`, `experiments/E05/out/E05r2/report.json`,
`experiments/E05/out/decision.json`.
