## WHAT WAS WRONG

Nothing in `src/` was wrong. This task is an experiment and it changed no product code.
Six things were not known before it ran, and three of them contradict what the brief and
the design assumed.

### 1. The brief's per-capture request counts were all low, because the store is live

The brief lists nine captures with 65 or more model requests (175, 158, 130, 120, 111,
86, 80, 73, 65). At 17:15 UTC on 2026-09-02 there were eleven, and the counts had moved:
189, 175, 158, 154, 120, 111, 102, 86, 83, 80, 65. Three of them are sessions that did not
exist when the brief was written (W2-T4, W2-T7 and this one), and W2-T6's clock ran from
130 to 189 while its own session finished.

That is not a discrepancy to reconcile. It is the experiment's own reproducibility
problem, and it is the reason `out/summary.json` records `taken_at`
`2026-09-02T17:15:00Z` and the reason those files are committed rather than regenerated.
A later run of `experiments/E07/run.py` reads a bigger store and answers with different
numbers.

### 2. The design's "all windows of one run go to one predict_batch call" is not what the
adapter does, and the brief repeated it

The brief says "All windows of one run go to one predict_batch call (design 6.12), so a
run costs one call plus the model load". `backtest._forecast_window` calls
`forecaster.forecast(window, horizon)` once per window and `TimesFM.forecast` makes one
`predict_batch` call, so a 157-window run makes 157 calls. W1-T6 built it that way on
purpose after E03 measured per-call cost at 0.35 s median, and the wave 0 amendment in
`docs/design/01-design.md` records the release.

I did not change it, and the reason is a number. Measured here: the per-window median is
90.1 to 108.2 ms across the seventeen runs, min 81.4, max 168.4. The whole experiment,
1,174 windows over seventeen runs plus a 43 MB store copy, a rebuild of 36 captures,
fifteen series builds and ninety readiness checks, is 120.665 s. Batching saves a fraction
of two minutes and costs an edit to the module every forecast in this project goes
through.

### 3. "Fewer than three captures pass" is the outcome for two of the three targets

The brief names this as a valid outcome to write up, and it happened. `fresh_input_tokens`
has a scaled MAD of exactly 0 on all fifteen build captures. `tool_calls_since_prev` has 0
on fourteen of fifteen; the exception is a five-row series that fails the window check
anyway. Readiness check 7 refuses both, at both horizons, on every capture.

W2-T7 saw this on one capture and said the registry decision belonged to E07. Here it is,
on fifteen: these are not thin targets, they are columns that do not vary in a Claude Code
session, and no length of session changes a MAD of 0.

### 4. The decision never reached the second clause, let alone the placebo

Design 6.12's rule is `baseline sufficient iff E_M > (1 - delta) E_B or W_MB < w`. I
expected the placebo's absence to be the binding limitation of this experiment. It is not.
`E_M > 0.9 E_B` holds in all seventeen per-capture runs and both pooled rows, so the rule
terminated on its first clause every time and W3-T2's `block_shuffle` never came up. The
strongest TimesFM-3 run on this cohort is skill 0.0844 against a bar of 0.10.

The placebo still matters for what may be SAID (see "What downstream may now say" in the
write-up), and it changed no verdict here.

### 5. The pooled lead-time cell had a wrong reason attached to it, and I caught it by reading the output

`backtest.metrics(windows, tau)` returns the string "tau is not computable: the first
c_min rows of the target hold an unknown" when tau is None. The pooled rows pass tau None
deliberately, because tau is q80 of each capture's own first 32 rows and a cohort of
twelve captures has no single threshold. So the file said the head of a column held a gap,
which is not what happened. `pooled_row` in `run.py` now overwrites that cell with the
reason this caller actually has, and the per-forecaster lead-time block of
`out/pooled/output_tokens-H1.json` reads "tau is q80 of each capture's own first c_min
rows, so the cohort has no single threshold and lead time is not assessable over pooled
windows".

### 6. Part of the calibration difference is the baselines proposing impossible numbers

`output_tokens` is `nonnegative` in the registry, and that flag reaches TimesFM-3 as
`make_positive=True`. A baseline's band is its point forecast plus the empirical quantiles
of its own one-step residuals, and nothing clips it. Over all 14,805 quantile points of
all seventeen stored runs: 20.5 percent of `local_drift`'s and 6.1 percent of
`rolling_median`'s are below zero, against 0 of 14,805 for TimesFM-3 and for the stub.

I did not go on to clip the baselines and re-measure, because changing a pre-registered
baseline definition after seeing results is the move this whole apparatus exists to
prevent. It is written down as a measured fact and as the obvious W3 question.

## EXPLAIN FOR THE OWNER

### What was at stake

Telltale can now forecast. The question nobody had asked is whether the forecast is worth
having, and there is only one honest way to ask it: score the clever thing against a dumb
thing, on data neither of them has seen, and see if the clever thing wins. This experiment
is that comparison, run for the first time on your own sessions rather than on a synthetic
series. The answer is that the dumb thing wins, and the shape of that answer is the useful
part.

### What a rolling origin is

Here is the problem it solves. You have a session that already happened: 189 model
requests, each with a token count. You want to know whether a forecaster can predict the
next one. You cannot just fit something to the whole session and admire the fit, because a
forecaster that has seen the answer always looks brilliant.

So you pretend. Pick a row, say row 94. Hand the forecaster rows 0 to 93 and nothing else:
not the row you are asking about, not any row after it, and no handle it could use to go
and fetch one. Ask for row 94. Then compare its answer with what row 94 actually was.

That is one test. Now move forward one row and do it again: rows 0 to 94 in, row 95 out.
And again. Each test is separate and each is genuinely out of sample, and the score is the
average error over all of them. The row you pick is called the **origin**, and rolling it
forward through the session is the whole method. On the 189-request session that gives 157
tests. The first origin is row 32, because design 6.12 says a forecaster gets at least 32
rows of context before it is allowed to answer.

Two things make it honest rather than merely plausible. The window handed to the forecaster
is a copy of the rows with no database connection attached, so there is nothing it could
reach through even if it tried. And W1-T6's contract test poisons every row from the origin
onwards with the value 1e9, re-runs, and asserts the window the forecaster received is
byte-identical. If any look-ahead existed, the poison shows up in the window.

### One real window, with the real numbers

Origin 94 of `cap_01M1HE3XS4E3S2XTSNB99C7WQT`, the session that did task W2-T6. Context:
rows 0 to 93. The last request before the origin produced **1,436 output tokens**. The
actual answer, which none of the forecasters saw:

**row 94 was 978 output tokens.**

Here is what each forecaster said, from
`experiments/E07/out/home/telltale.db`, run `fc_01M1HHWC9DV2GYSB22HB2ZKB8W`:

| forecaster | what it does | its answer | it was wrong by |
|---|---|---|---|
| persistence | repeat the last value | 1,436 | 458 |
| rolling_median | middle of the last 8 | 697 | 281 |
| rolling_mean | average of the last 8 | 747.75 | 230.25 |
| local_drift | last value, extended along the recent slope | 1,593.50 | 615.50 |
| TimesFM-3 | a 1.3 GB foundation model, 94 rows of context, 10 covariates | 558.40 | 419.60 |

On this window the average of the last eight wins, the model is fourth of five, and
`persistence` is beaten by both. That is one window and it settles nothing on its own. Over

### What "baseline sufficient" means, and why it is not a failure

The rule was written down before the run, in design 6.12 and again in this task's brief.
It has two questions and either one is enough to stop.

First: is the model's average error more than 90 percent of the best baseline's? If yes,
the model has not earned its place. The 10 percent is the margin somebody has to be able to
notice; a 2 percent gain from a 1.3 GB checkpoint that needs torch, 200 MB of memory and a
non-commercial licence is not a gain anybody can spend.

Second: does the model beat that baseline on fewer than 60 percent of individual windows?
A model that is slightly better on average because it got lucky on three windows out of 157
is not a better forecaster; it is a better gambler.

**On every single one of the nineteen comparisons here, the first question already
answered yes.** TimesFM-3's best result anywhere is 8.44 percent better than
`rolling_median`, and its median across the twelve one-step runs is 2.25 percent WORSE. The
second question agrees in fourteen of seventeen: the model wins about half the windows,
which is what a coin looks like.

Now the part that matters. This is not the laboratory failing. It is the laboratory
working, and it is the outcome the baselines were put there to be able to produce.

Think about what the alternative looks like. Without baselines you run the model, get a
mean absolute error of 689.7 tokens, and have no way to know whether that is good. It is a
number with units. Put four one-line functions beside it and 689.7 becomes a statement: a
rolling median of the last eight requests does this job slightly better, so whatever
structure the request clock has, a model trained on a billion time series is not finding
more of it than "look at the recent middle".

That is a real finding about the DATA, and it points somewhere. Token counts per request
are close to independent draws around a slowly moving level. There is a level, which is why
`rolling_median` beats `persistence` by a wide margin. There is little else, which is why
nothing beats `rolling_median`. If you want a forecast worth acting on, the request clock
is probably not where it lives, and the change and attempt clocks (`attempts_to_land`,
`verification_cycles`) are the next place to look.

And it is cheap to have found out. The whole experiment is two minutes of CPU and no
tokens.

### The half of the rule that is missing, and what it will add

Suppose the model had won. Say it beat `rolling_median` by 15 percent on 70 percent of
windows. You still could not say the useful thing, and this is the subtle part.

A forecaster given rows 0 to 93 gets two different kinds of information at once. It learns
the SHAPE of this session: token counts around here run in the hundreds, occasionally spike
into the thousands, rarely go below fifty. And it learns the ORDER: this request came after
that one, the last three have been climbing, a compaction happened at row 61.

Only the second is a claim about time. A model that has merely learned the shape is a model
that knows the histogram, and a histogram cannot tell you what happens next; it tells you
what happens generally.

The test that separates them is the **chronology placebo**, and it is W3-T2. Cut the
context into consecutive blocks of whole rows, shuffle the blocks, and hand the forecaster
that instead. Every row is still there, every row still has all its columns together, so
the shape is untouched to the last decimal. What is destroyed is the order. Then score the
model on the shuffled context against the same model on the true one, on the same origin,
against the same actual.

If the model does just as well on shuffled rows, it learned the shape. If it does markedly
worse, it learned the order, and only then may a report say the model is using the history
of the session rather than its distribution.

There is a check on the check, and it is why this is not just an extra run. The baselines
go through the placebo too, and `persistence` MUST get worse on shuffled context: it copies
the last value, and shuffling changes which value is last. If `persistence` does not
degrade, the shuffle did not happen and the whole placebo run is void.

Until that exists, every predictive statement out of this system carries the words
**placebo pending**, and the two strongest labels design 6.12 defines cannot be written at
all. Not by policy. The function that assigns the label in `experiments/E07/decide.py` does
not take the placebo terms as arguments, so it has nothing to compute them from.
