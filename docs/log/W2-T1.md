## WHAT WAS WRONG

### Defect 1: five Bash calls counted as five subagents

Claude Code 2.1.258 emits `claude.stream.system.task_started` for every Bash call, with
payload `task_type` "local_bash" and `is_backgrounded` false. 2.1.257 did not. The
reducer keyed a subagent on any `task_started` with a task id, so capture
cap_01M1GPSMW1ZRXVADWZPF0KZ9H3 reported 5 subagents on a session whose stream holds 29
Bash and 2 Write tool_use blocks and no Task call at all.

Fixed in `activities.py` `_subagent_key`: a `task_started` whose `task_type` is
"local_bash" opens no subagent. Measured counter-example kept: S4 on 2.1.257 announces
its one real subagent with `task_type` "local_agent" (`fixtures/sources/claude/2.1.257/
S4/stream.jsonl`, the single `subtype: task_started` line) and still counts. A
`task_started` carrying no `task_type` at all is NOT refused: no version has been
measured emitting one, and refusing it would drop a subagent on a guess.

Break-and-restore: setting `_LOCAL_TASK_TYPES = frozenset()` makes
`test_a_local_bash_task_is_not_a_subagent` fail with two subagent rows in the assertion
message, and `test_s4_subagent_has_attributed_tokens` still passes. Restoring it makes
both pass.

### Finding 3: an environment assignment swallowed the command

`UV_CACHE_DIR=/x uv run pytest && git status --short` classified as `git`. The normal
form recorded the assignment's NAME with the value stripped (`UV_CACHE_DIR uv run
pytest`), `classify` could not tell that first word from an executable, found no
category for the segment and fell through to the next one.

Fixed in `commands.py`: the normal form keeps the `=` (`UV_CACHE_DIR= uv run pytest`), so
an assignment is unambiguous, and `_classify_segment` skips the leading assignments
before consulting the table. This changes stored strings, so `NORMALIZATION_VERSION` is
`cmdnorm-v2`, `FALLBACK_VERSION` is `cmdnorm-v2-fallback`, and `CLASSIFIER_VERSION` now
hashes the four classify rules beside the two tables.

### Finding 4: no stored command_norm contained "git commit"

A `git commit -m` whose message shlex refuses (an unbalanced quote) went through the
fallback, which kept one token: `git _`. 90 rows in the copied store are
`cmdnorm-v1-fallback`, and their distinct normal forms are `cd _`, `python3 _`, `git _`,
`export _`, `cp _`, `jq _`, `mkdir _`, `cat _`. A reader could not tell a commit from a
`git status`.

Fixed in `commands.py` `_fallback`: it keeps the executable plus the bare lowercase words
the same budget allows the parsed path (two), then an underscore. `git commit -m
"unbalanced` now normalizes to `git commit _` and still classifies as `git`. The words
are only kept while they match `_BARE`, so a filename or a search string still cannot
reach the store through the fallback.

### Finding 5: a session ended by the limit

The summary's new `session` block carries `is_error` and `stop_reason` as stored, off the
session_end lifecycle row that carries them, with no prose. S7 reports
`"is_error": true, "stop_reason": "stop_sequence"`; the build capture reports
`"is_error": false, "stop_reason": "end_turn"`.

A verification run's outcome was read from `success` alone. Codex S1's rollout item

# EXPLAIN FOR THE OWNER

## Why this task existed

A recorder that miscounts is worse than one that does not count. Before this change, a
session of this build reported five subagents. It spawned none. It also reported 32
"conflicts", one for every request it made, as though two of its own surfaces were
fighting. Neither number was true, and both would have gone into the first comparison
anybody ran.

## A stable-state work interval, with a real one

Start with what a recorder can see about a coding session. It sees two moving things.

The first is the shape of the change on disk. Telltale takes a snapshot of the repository
now and then and records a fingerprint of the diff: one string that is the same whenever
the change is the same. Call it the **diff fingerprint**.

The second is the last thing a check said. Whenever the agent runs a test, a type
checker, a linter or a build, Telltale records what kind of check it was, whether it
passed, and the diff fingerprint at the time. Call those three things together the
**verification signature**.

Now the idea. Walk through the session in order and look at every model request and every
tool call. Some stretch of them will happen while both of those two things sit still: the
change on disk has not moved, and the last check still says what it said. That stretch is
a **stable-state work interval**. It ends the moment either one moves.

It is not called "no progress", and that is deliberate. Reading, planning and diagnosing
are work; they just do not show up in either of the two things a recorder can see.

Here is a real one, from this session's own capture. The interval was number 4 of 5:

```
starts   09:23:22.865   uv run pytest -m integration tests/integration/test_series.py
ends     09:28:31.643   uv run mypy . ; uv run ruff check .
42 operations, 305243 ms, 4510696 tokens, ended by: verification
```

For five minutes and five seconds the agent made 42 model requests and tool calls. Three
more pytest runs happened inside that window and none of them cut it, because all four
runs share the same signature: category `test`, passing, diff fingerprint
`52039e43136f`. Same kind of check, same answer, same tree. An edit to `docs/log/W1-T5.md`
also happened inside it, at 09:26:59, and did not cut it either, because the two
snapshots taken right after that edit still report diff fingerprint `52039e43136f`: the
file was untracked, so the tracked diff did not change. The interval ends at 09:28:31
when a type check runs, because that is a different category and the signature moves.

That last detail is the sort of thing you only learn by running the thing on real data.
Three of the four snapshots in this capture carry the same diff fingerprint and different
`dirty_tree_hash` values. Had the interval keyed on the tree hash instead, the same
session would have reported more, shorter intervals, and the number would have been
counting Telltale's snapshot schedule rather than the agent's work.

## Zero and "unavailable" are different answers

Every number in the summary can be null, and null does not mean the same thing as 0.

Say a summary reports `compactions: 0`. There are two ways that could have come about.
The session might have run without ever compacting its context. Or nothing that could see
a compaction was ever wired up, and the reducer counted an empty list.

Those are different claims. The first is a measurement. The second is a measurement of
nothing at all, dressed as a measurement of zero. If both print `0`, then a comparison
between two sessions can conclude that one compacted less than the other when what
actually differed was which surfaces the launcher managed to configure.

So each number carries a word about how well it could have been seen: observed, partial,
derived or unavailable. Two rules follow from it. First, a metric takes the weakest word
among the things it needed, because a number is only as trustworthy as its least visible
input: `failed_test_runs` needs both the commands and the exit statuses, and on Claude an
exit status is derived rather than observed, so the metric reports `derived`. Second, if
the word is `unavailable`, the number becomes null no matter what the arithmetic came to,
and picks up a warning naming what was missing.

Here is that rule paying for itself. Every replayed fixture in this repository reports
`stable_state_work_intervals: null`, not 0. None of them carries a repository snapshot,
because they were recorded before the launcher took snapshots. Zero would say those
sessions worked with the tree moving constantly. Null says nobody looked.

The reverse case matters too. `unique_files_changed: 0` on the S2 fixture IS a
measurement: file paths were observable in that capture, and the agent read one file,
searched once, and changed nothing. Same digit, opposite epistemic status, and the
coverage word is what keeps them apart.

## What the tail warning means if you read failed_test_runs

The S1 fixture reports `failed_test_runs: 0`. Do not read that as "every test passed".

All three test runs in S1 are of the form `uv run pytest 2>&1 | tail -50`. When you pipe
one program into another, the shell reports the exit status of the LAST program in the
pipe. `tail` succeeds at printing whatever it is handed, so the shell reports success
whether the tests passed or not. Every surface Telltale reads gets that status, so every
surface reported the call as successful.

The captured output of the first of those three runs says "1 failed, 1 passed". A test
failed. No surface recorded it, and Telltale does not read program output, so Telltale
cannot know.

That is why the number ships with a sentence attached rather than alone:

> no test run reported a failing exit status, which is not the same as every test
> passing: a run whose command pipes the test runner into another program reports that
> program's status

Read `failed_test_runs: 0` as "no run reported a failure", never as "no run failed". The
same warning sits on `fail_to_pass_cycles`, which is built from the same readings.

There is a second version of this same trap, and it went the other way. On Codex, one
pytest run recorded an exit code of 1 and a status of "failed", while the OTel record for
the same call said `success: true`. The reducer read `success` and counted it as a pass.
Spec 13.1 defines a verification activity by its exit status, so both the summary and the
timeline now read the exit code first and fall back to `success` only when there is no
exit code. Codex S1's `failed_test_runs` went from 0 to 1, and its `fail_to_pass_cycles`
from 0 to 1: a test failed, the agent edited, the test passed. That cycle was invisible.

## What the subagent defect would have done to a comparison

This is the one worth dwelling on, because it would not have looked like a bug.

Claude Code 2.1.257 announced a subagent when one started. 2.1.258 announces something
for every Bash call as well, tagged `task_type: "local_bash"`, meaning "the agent is
running a command itself". Telltale keyed a subagent on any such announcement carrying an
id, so on 2.1.258 every Bash call became a subagent.

Now picture the comparison this project exists to support: the same task, run on two
versions of the same agent, with delegation as one of the numbers. On 2.1.257 you get the
real subagent count, near zero for most sessions. On 2.1.258 you get roughly the number
of shell commands the agent ran, which for the capture I measured was 5 and for a heavier
session would be dozens.

You would have read that as a large, consistent, reproducible increase in delegation
between two versions. It reproduces perfectly, because it is not noise. It is a rename in
a telemetry field, and it has exactly the signature of a real behavioural finding: large
effect, consistent direction, stable across repetitions.

Every guard this project has would have passed it. The cohort rule would have been
satisfied, because the two arms differ only in runtime version, which is the thing being
compared. The claim class would have been `derived`, which is correct: it IS derived from
the observations. The stochastic-variance work would have shown a tight distribution in
each arm, because the count is deterministic. Nothing in the epistemic machinery
distinguishes "the agent delegated more" from "the provider started emitting a message
type".

What caught it was not a guard. It was reading the raw stream of a session I knew had
spawned no subagents, and counting the tool_use blocks by hand: 29 Bash, 2 Write, no
Task. The fix is a single condition, and the test that holds it builds a capture out of
five `local_bash` announcements and asserts zero subagents, with S4's real
`local_agent` subagent as the case that must still count. Removing the condition makes
the first test fail and leaves the second passing, which is what tells you the test is
testing the rule and not the fixture.

The general lesson is the uncomfortable one. A provider version bump changes what the
recorder can see at the same time as it changes what the agent does, and the recorder
cannot tell those apart from inside. Any cross-version comparison needs its capability
fields diffed first, and a difference in what a surface EMITS has to be ruled out before
a difference in what the agent DID is believed.
