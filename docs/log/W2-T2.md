## WHAT WAS WRONG

Everything below was measured against the owner's own files on 2026-09-02, before any
code was written. Each one made the brief's plan wrong in a way that would have shipped
silently.

**1. A transcript is not one file per session in one directory per project.** The digest
(2.1) says `~/.claude/projects/<slug>/<session>.jsonl`. Measured over all 1806 files:
774 have that shape, 852 are `<slug>/<session>/subagents/agent-<id>.jsonl`, 65 of those
are a level deeper under `workflows/<id>`, and 115 are
`<slug>/vercel-plugin/skill-injections.jsonl`, which is not a session and names none. A
glob of `<root>/*/*.jsonl` finds 774 of 1806 files. The scan walks the tree.

**2. A subagent file carries the parent's session id.** Every line of
`agent-a0792d54357f86ac1.jsonl` names session `3724c91c-...`, the parent's, and every
line has `isSidechain: true`. The two files share no uuid at all: 3060 in the parent,
197 in the child, 0 in common. So keying a capture on the session id alone puts both in
one capture, and `measures.py` sums every `model_request` in a capture, which would put a
subagent's tokens inside the main thread's total. Spec 13.6 forbids exactly that.

**3. A resumed Codex thread writes a new file that still names the old session.** 27
session ids are spread over 50 files this way. Before the fix, the dry run reported 1452
files and 1402 sessions, and an import would have written 1402 captures and dropped 50
files as "already imported". Silently.

**4. `isSidechain` never appears on an assistant line inside a main transcript.** 10382
assistant lines over 250 files, all false. The sidechain lines are all in the subagent
files. So the brief's trap ("keep the fact, never sum their tokens") is answered by
which FILE a line is in, not by a flag inside one file.

**5. The first line of a transcript is not a session line.** 188 of 250 sampled files
open with `queue-operation`, the rest with `mode`, `ai-title`, `custom-title` or
`last-prompt`. Reading line one for the session id and the clock finds neither.

**6. There are 18 line types, not 5.** Beyond assistant, user and system: attachment,
last-prompt, mode, ai-title, atis-latch, permission-mode, queue-operation,
file-history-snapshot, file-history-delta, bridge-session (which carries
`ownerAccountUuid` and `ownerOrganizationUuid`), custom-title, agent-name, pr-link,
frame-link, cost-state.

**7. No `summary` line exists.** The digest names one. Across all 1806 files, on every
version from 2.1.219 to 2.1.257, `grep -rl '"type":"summary"'` returns 0 files.

**8. No transcript line carries a context window.** 19 of 1806 files mention
`contextWindow` and every hit is inside a tool's own output. Occupancy has no
denominator on this surface, so the capability cell is `unavailable`.

**9. `effort` is a bare string on a transcript line** (`"xhigh"`), where a hook body
spells it `{"level": ...}`. It is absent on 1506 of 10382 assistant lines.

**10. `message.usage` carries seven names the digest omits**: `server_tool_use`,
`service_tier`, `inference_geo`, `iterations`, `speed`, `output_tokens_details`, and
`cache_creation` holding `ephemeral_1h_input_tokens` and `ephemeral_5m_input_tokens`.

## WHAT CHANGED

**The transcript parser** (`providers/claude_transcript.py`, reached by
`claude.parse("transcript", line, ctx)`). One observation per assistant line with usage,
one per `tool_use` block, one per `tool_result` block, one per user prompt (length only),
one per `compact_boundary`, one per `summary`. Fifteen other line kinds become no
observation and one counted note each. The file is separate from `claude.py` for the
reason `claude_launch.py` is: `claude.py` was at 745 lines against the 800-line ratchet.

The three containers are read and never handed on whole: `message` (the prompt, the
answer, the thinking, every tool argument), `toolUseResult` (stdout, stderr,
`originalFile`, `oldString`, `newString`) and `compactMetadata`. What comes out of them
is what design 6.3 allows: usage counters, model, stop reason, tool name, `file_path`,
`command` (through `commands.normalize`), sizes, `is_error`, the compaction numbers, and
`gitOperation.commit.sha` when exactly one result block is present. The husks are still
passed to the sanitizer, which drops them by name without reading them, so
`redaction.dropped` on the row says a container arrived and went. Without that, a
transcript that carried a whole Edit and one that carried nothing look identical.

**`tool_use_result` joined `NEVER_PERSIST`** in `sanitize.py`. It is the stream's and the
transcript's spelling of `tool_response`, which is already there, and E01 measured it
carrying a secret file's contents on the stream. It was already dropped by the allowlist
gate; now it is dropped by the gate an allowlist entry cannot undo, and the drop reads
`never_persist` rather than `unknown`.

**The importer** (`importer.py`), three functions:

- `scan(root, kind, since=None, project=None) -> Iterator[Source]` walks the tree without
  following a symlink, and reads every line of every file to find the session id, the cwd,
  the first and last provider timestamps, the line count and the byte count. `--since`
  compares the first provider timestamp inside the file, never the mtime: a transcript is
  appended to on every resume, so the mtime is when the disk was written.
- `dry_run(root, kind, since, project, store=None) -> dict` counts and returns. It opens
  no database and creates none. `already_imported` is None rather than 0 when there is no
  database yet, because "no capture of this session is stored" and "there is nowhere to
  look" are different answers.
- `import_files(store, sources, level) -> dict` writes: `telltale.capture_started`, every
  line of the file parsed and sanitized and appended in batches of 500, then
  `telltale.capture_ended`, then the reducers. A capture already in the store is skipped
  whole. Two files of one run reaching one capture id are a `conflict` diagnostic and the
  second is not imported, because appending would double the first's counts.

**The capture id** is `"imp_" + sha256(provider + ":" + session)[:24]`, where `session`
is the provider's session id, and, for a file whose name does not end in that id, the
session id and the file name. That last clause is findings 2 and 3 above: it is what
gives a subagent transcript and a resumed rollout a capture of their own. Both still
carry the parent's `provider_session_id` on every row, so the link survives.

**The capture rows.** `argv_shape` is the word `backfill` (there was no launch),
`surfaces_configured` is `["transcript"]` or `["rollout"]`, and four new allowlist fields
carry the file: `source_kind`, `source_path_hash`, `source_bytes`, `source_lines`. The
path is hashed and never stored: a transcript directory name is the project's absolute
path with the separators changed. `capture_started` is stamped with the file's first
provider timestamp and `capture_ended` with its last, so `telltale sessions` shows when
the session RAN. `exit_code` and `duration_ms` are None: a transcript records what a
session did, not how its process ended.

**The CLI.** `telltale import <kind> [--root DIR] [--since DATE] [--project SLUG]
[--dry-run] [--level N]`, and `telltale sessions` gained a BACKFILL column, which reads
`argv_shape` and nothing else.

**Two table rows in `correlate.ROLES`** and nothing else in that file:
`claude.transcript.assistant` is an `assistant` and
`claude.transcript.system.compact_boundary` is a `compact_boundary`. The existing reducer
does the rest: requests are grouped by `requestId`, and a boundary that matches no OTel
compaction becomes its own episode, which on a transcript capture is every one of them.

## UNSURE OR NOT DONE

**`cache_read_tokens` is null on every imported Claude capture, and on every stream-only
capture that already existed.** `activities.py::_request` reads the four counters under
the OTel spellings (`cache_read_tokens`, `cache_creation_tokens`) for every request,
including ones built from stream or transcript messages, which spell them
`cache_read_input_tokens` and `cache_creation_input_tokens`. The file already holds the
translation table (`_STREAM_USAGE_KEYS`) and uses it only for conflict detection. The fix
is one line in `_request`; `activities.py` is W2-T1's file this wave and I did not touch
it. `fresh_input_tokens` and `output_tokens` are unaffected. The metric reports coverage
`partial` and value null rather than a wrong number, so nothing is overstated.

**A rollout-only capture reports `model_requests: 0` with coverage `partial`.** By
`measures.py::_honest`, a 0 is nulled only when coverage is `unavailable`. Whether
`partial` should also null a count over an empty set is a measures.py decision. The turn
usage is stored and correct either way.

**No `telltale.environment` observation is written for an imported capture,** so
`telltale sessions` shows an empty MODEL and RUNTIME column for backfill rows. This is
deliberate. The transcript names the model and the version on every assistant line, and
both are on the observations and in the timeline. What it does not name is the settings
hash, the tool set or the MCP servers, and an environment fingerprint built from a subset
would compare EQUAL for two sessions that differ in ways the transcript cannot see.
`experiments.repeat` refuses statistics across differing fingerprints; a fingerprint that
agrees when it should not is worse than none. If the owner wants the model in that
column, the honest route is a separate field on the capture row, not a fingerprint.

**Unreadable files are re-reported on every import.** 116 transcripts name no session,
and each run writes 116 `parse_failure` rows for them. Diagnostics are the one table with
age-based deletion, so they expire, but a real import of the owner's tree would write 116
rows now and 116 more next time. Whether to remember them is a decision I did not make.

**`--project` takes a slug and the dry run prints a hash.** The owner has to read the
slug off their own disk to use the flag, and cannot copy it from the table. That is the
cost of the rule that no project path reaches a report; it could be relaxed for terminal
output alone, which is the owner's call.

**Level 2 is accepted by `--level` and untested here.** The design defines three content
levels; the import was exercised at 1 and 0, which are the two the privacy test covers.

# EXPLAIN FOR THE OWNER

## Why this exists

You have two agents writing a diary of every session, on this machine, already. Claude
Code writes one file per session under `~/.claude/projects`; Codex writes one per session
under `~/.codex/sessions`. Together that is 4.7 GB of your own history, going back to
2025-09-25. Telltale has been recording only what happens from now on. This task reads
the past.

Nothing has been imported. The command that reads your files without writing anything is
`--dry-run`, and the two tables above are what it printed. The real import is your
decision at the wave 2 gate.

## What a backfill can and cannot see

Start with what a live capture does. When you run an agent under `telltale run`, Telltale
sets up four things before the agent starts: a stream of events the agent sends over a
local socket, a set of small programs the agent runs at fixed moments (hooks), a metrics
feed, and the agent's own printed output. Four ways of watching one session, each seeing
something the others do not.

A backfill has one. The file was written before Telltale existed on this machine, by an
agent nobody told to report anything, and it is what it is. So four kinds of fact can
never come out of an import, no matter how good the parser is:

**When the process started and stopped, and what it exited with.** The transcript records
what the session did. It does not record that the process was alive, or that it returned
2. Every imported capture reports `exit_code` and `duration_ms` as unknown, and unknown
here means empty, never zero.

**How full the context window was.** To say "this session was at 60 percent of its
window" you need the window size. Claude puts that number on one message of the live
stream and nowhere in the transcript. I checked all 1806 of your files: 19 mention the
word `contextWindow`, and every one of those is inside the output of some tool the agent
ran, which is a different number about a different thing. So for imported Claude
sessions, occupancy is not "zero", it is "not observable", and Telltale prints those
differently on purpose. Codex is the opposite: its rollout files carry
`model_context_window` (258400 on your sessions), so imported Codex sessions do have the
denominator.

**Whether a tool call succeeded.** The one surface that states it outright is the metrics
feed, which no file carries. The transcript says a result was an error, and for a shell
command the first line of the failure text is `Exit code 2`, so Telltale reads the number
out of the sentence and labels it derived rather than observed. Derived is the weaker
word and it stays weaker: a report may narrow that claim, never strengthen it.

**Anything that only a hook could have said.** Permission mode on every call, the moment
a subagent started, whether a compaction was about to happen. Some of it appears in the
transcript for some turns; the coverage block on each capture says which, per capability,
per capture. That block is not decoration. It is the difference between "this session ran
no tests" and "whether this session ran tests was not visible", and Telltale will print
`null` rather than `0` whenever it is the second.

What backfill CAN see is worth the trouble. Token usage on every model request, the model,
the request id, the tool names, the file paths, the commands, the sizes, and one thing no
live Claude surface gives you at all: how many tokens survived a compaction.
`postTokens`. Your largest session in the fixture went from 410334 tokens to 13317 in one
compaction, and only the transcript records the second number.

## What the dry-run numbers mean

Four numbers matter.

**files** is how many files the walk found. **sessions** is how many captures an import
would create. For Codex those are equal. For Claude they are not: 1817 files, 1701
sessions, and the 116-file difference is exactly the "unreadable" count.

**unreadable** is not a failure. It is 116 files that name no session anywhere in them.
Most are `vercel-plugin/skill-injections.jsonl`, which is a plugin's scratch file living
in the same directory as your transcripts. An import counts them, writes one diagnostic
row each and moves on.

**lines** and **bytes** are what would be read, not what would be written. This is the
number people get wrong. 4.7 GB is the size of your session files; it is not the size of
what would land in Telltale's database.

Here is the actual ratio, measured on the fixture. The main synthetic transcript is 31 KB
of file and becomes 36 observations. Every observation is a small object of named
scalars: token counts, a model name, a file path, a normalized command. The prompt, the
answer, the thinking, the file contents and the command output are all dropped before
anything is written. A transcript is large because it holds text; the database holds
counts of that text.

I am not going to give you a GB figure for the whole import, because I have not measured
one, and a number I invented would be the worst thing in this report. What would measure
it: import one project with `--project <slug>`, then look at the size of
`~/.telltale/telltale.db` before and after. That is a 15-second experiment and it answers
the question exactly.

The one thing I can state: the import writes only inside `$TELLTALE_HOME`, which is
`~/.telltale`. It opens no file under `~/.claude` or `~/.codex` for writing. Those are
read-only to Telltale by a rule that predates this task.

## How a probe string was proven absent

The privacy question is not "does the code look careful". It is "after an import, is the
string on the disk".

So there are planted strings. Three of them are shaped like real credentials, and they
were put into the fixture files on purpose: an AWS-shaped key, an Anthropic-shaped key,
and a private key header. There are also three long junk strings and a set of fake
identity values, an email and an account name. Every one contains the word `TELLTALEFAKE`
so that any variant can be found with one search.

They are in the fixtures in the places your real files would carry real ones: inside an
Edit's before-and-after text, inside what a `cat` printed, inside a Write's file content,
inside the prompt you typed, inside the model's reasoning, and inside a Codex rollout's
`aggregated_output`.

The test imports those files for real, through the real parser, the real sanitizer and
the real database, and then closes the database and reads the raw bytes of the file that
SQLite left on the disk. Not a query. A query answers "does the current schema show this
value", and a deleted row can still sit in a freed page or in the write-ahead log. The
bytes are the honest question, and the answer for every probe is zero occurrences.

Two details make that test mean something rather than merely pass.

First, it counts the probes in the input before it imports, and fails if the count is
zero. A fixture that quietly stopped carrying a probe would otherwise make the test pass
by having nothing to leak.

Second, it runs at both content levels: level 1, which keeps repo-relative paths, and
level 0, which keeps no path at all. A leak that hides inside a path at level 1 has
nowhere left to hide at level 0.

I also broke the parser deliberately, in the way a careless change would break it, by
copying 60 characters of a tool's output into a field the allowlist permits. The test
failed and named the probes it found: `AKIATELLTALEFAKE00001` three times, `TELLTALEFAKE`
thirty times. Then I put it back. A test that has never been seen failing is not evidence.

The mechanism behind the result, in the order it runs: the parser reads the three big
containers itself and lifts named values out, so the containers never reach the writer;
then a table keyed by observation type drops every field nobody listed, and names it; then
a hard list of field names removes what must never be stored, whatever the table says;
then every surviving string is scanned for credential shapes and bounded to 512
characters; then every path is made relative to the repository or replaced by a hash. Five
gates, and the fifth is the one that removes your home directory from anything that
mentions it.

The last check is the crude one, and I ran it anyway:

```
$ strings $TELLTALE_HOME/telltale.db | grep -c TELLTALEFAKE
0
$ strings $TELLTALE_HOME/telltale.db | grep -c /Users/wumpinihussein
0
```

That database is a throwaway one holding the two fixture imports and nothing else. Your
own `~/.telltale/telltale.db` was never a target of this check, because the probes exist
only in the fixtures: searching it for them would return zero for the wrong reason.

## What I would do next, if it were mine

Import one project first. Pick a slug from `~/.claude/projects`, run
`telltale import claude-transcripts --project <slug>`, and look at `telltale sessions`
and one `telltale show`. It costs seconds, it answers the size question with a
measurement instead of an argument, and every capture it creates can be removed with
`telltale purge <capture>` if you do not like what you see.
