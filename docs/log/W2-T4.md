### The public signatures

```python
# src/telltale/cohorts.py
VECTOR: tuple[tuple[str, tuple[str, ...]], ...]   # 6 families, 22 metrics
COHORT_KEYS = ("provider", "runtime_major", "model", "content_level")
COHORT_MIN = 10
NO_PERCENTILE = "spec 13.7: raw count and coverage, no percentile"

cohort_keys(store, capture_id) -> dict          # the four keys, backfill, reason
cohort(store, capture_id, include_backfill=False) -> list[str]
percentile(values: Sequence[float | None], own: float) -> float
vector(store, capture_id, include_backfill=False) -> dict
sides(store, a, b, include_backfill=False) -> tuple[dict, dict]

# src/telltale/report.py
vector(built) -> str
compare(a, b) -> str

# src/telltale/cli.py
vector <capture> [--json] [--include-backfill]
compare <a> <b> [--json] [--include-backfill]
```

`vector` returns `{family: {metric: {value, unit, coverage, claim_class, evidence_id,
percentile}}}`. The percentile cell is either the whole comparative Evidence as a dict
plus `n` and `n_metric`, or `{"no_cohort": K}` with K a count, or `{"no_cohort":
reason}` with reason naming what is unknown. It is never blank, never 0 and never "n/a".

`sides` returns the two halves `report.compare` prints. The difference sits on the b
half because it is b minus a.

## WHAT WAS WRONG

### The vector had to leave measures.py

With `VECTOR`, the cohort and the percentile in it, measures.py measured 799 lines
against a hook that fails a file which grows past 800. One line under a gate is not a
place to leave a file. cohorts.py is the split the brief allowed for exactly this, and
the only thing that had to cross the boundary was the decoder that turns a SQLite REAL
back into the unit its Evidence declared. That is `measures._value`, now public as
`measures.value_of`: two decoders of one column would be two answers about what a token
count is.

### report.py could not import cohorts.py

The first version had report.py import `COHORT_KEYS` to print the cohort line.
`import telltale.cohorts` then failed outright:

```
ImportError: cannot import name 'COHORT_KEYS' from partially initialized module
'telltale.cohorts' (most likely due to a circular import)
```

The cycle is cohorts -> measures -> forecast.readiness -> forecast.backtest -> report ->
cohorts. It was invisible from the CLI, which imports report first, and appeared the
moment anything imported cohorts directly. The fix removes the import: the cohort line
now prints the keys the Evidence's own `cohort` dict carries, minus the member ids and
the per-metric count. That is better than the constant anyway, because a key added to a
cohort cannot go missing from the line that describes it.

### The imported capture is missing two keys, not one

The brief predicted the imported transcript capture would be outside every cohort
"because its content level is unknown". Measured, it is missing the runtime version as
well: an imported session has no `session_start` lifecycle row carrying
`claude_code_version`, and no `telltale.environment` observation at all.

```
imp_014f8695c01cc2d3ecdaee7a {'provider': 'claude', 'runtime_major': None,
  'model': 'claude-opus-5', 'content_level': None, 'backfill': True,
  'reason': 'runtime version unknown, content level unknown'}
```

So `reason` names EVERY key that is unknown rather than the first one. A reader told only
about the content level would fix the fingerprint and find the capture still outside
every cohort. The test asserts that "content level unknown" is part of the reason, which
is what the brief asked for and what is true.

### provider is not on the capture_start row

The brief said provider is on the capture_start lifecycle activity's fields. Measured on
both a replayed and a launched capture, it is not: `activities._lifecycle_one` copies
twelve named fields onto a capture_start row and `provider` is not among them. It is on
the `capture` lifecycle row, which `activities.capture_activity` builds from the first
observation's provider column, and that row exists whether or not a launcher wrote
anything. cohorts.py reads it there, which also means a replayed capture has a provider.

### A stream-only capture loses two of its four token counters

Not fixed here, and not W2-T4's to fix. Every one of the ten fake-agent captures reports
`cache_read_tokens` and `cache_creation_tokens` as null with coverage `partial`, while
the stream really carried them:

```
$ sqlite3 telltale.db "select payload from observations
    where observation_type='claude.stream.assistant' limit 1;"
{"cache_creation_input_tokens":300,"cache_read_input_tokens":0,"input_tokens":221,...}
```

`activities._request` reads `correlate.USAGE_KEYS`, which is the OTel spelling
(`cache_read_tokens`), for both the OTel-primary and the stream-only case. A stream-only
request payload spells those two `cache_read_input_tokens` and
`cache_creation_input_tokens`, which is exactly what `correlate.STREAM_USAGE_KEYS`
exists for; `_request` does not use it. `input_tokens` and `output_tokens` survive
because both surfaces spell them the same way, which is why this has been invisible.

A real Claude capture delivers OTel as well, so its counters come off the primary record
and this does not bite. It bites a capture whose only surface is the stream: the ten
here delivered 1 of 4 configured surfaces. It is in NEXT, with the file that owns it.

### The cohort scan read every capture twice

Found by measuring rather than by reading. `cohort` called `cohort_keys` once inside the
key comparison and again for the backfill check, and each call reads that capture's
whole observation list. On a copy of the owner's own store (36 captures, 30715
observations, 40 MB) `telltale vector` took 0.42 s. With the keys read once per capture
it takes 0.31 s, of which 225 ms is still the scan. The number and what it scales with
are in the docstring of `_members`.

## WHAT CHANGED

**The family table is a constant.** `VECTOR` in cohorts.py names the six families of
spec 13.7 and the metrics each is read from: 22 entries. Spec 13.7 names the families
and not their contents, so this table is a decision taken once and written down, not a
judgement made per call. The five percentile families are
`context_token_burden`, `edit_turnover`, `verification_cycles`, `exploration_scope` and
`stable_state_work`; `compactions` is the sixth and spec 13.7 gives it a raw count and a
coverage word rather than a rank.

**Nothing is recomputed.** Every raw number in a vector is read back out of the evidence
table `measures.summarize` wrote, by metric name. A vector and a `telltale show` of one
capture cannot disagree, and a test checks all 22 cells against the rows.

**The value and the coverage come off the same row.** A row whose coverage is
`unavailable` carries a null value, and prints `-`. There is no path in this code that
turns a null into a zero.

**A percentile is an Evidence.** Built through `Evidence.comparative`, with the cohort
recorded (the four keys, n, n_metric and the sorted member ids), the member evidence ids
as its source, the weakest coverage word among those rows, two assumptions naming the
cohort rule and the backfill exclusion, and a warning when any member measured it
partially. `created_at` is the wall clock here, unlike every Evidence `summarize`
writes, because this number is a statement about the captures that were in the database
at that moment.

**A percentile is not stored.** Neither is a difference. The reason is in the module
docstring: the reducer's idempotence says two rebuilds of one capture write identical
rows, and a number that depends on which other captures are in the database cannot
promise that. `test_a_percentile_is_not_written_to_the_store` asserts that every
evidence row in the store is still `derived` after a vector and a compare have been
built.

**Four ways the percentile column can say no.** `{"no_cohort": reason}` when a cohort
key is unknown, naming every unknown key. `{"no_cohort": "backfill excluded"}` when the
capture is an import and the flag was not given. `{"no_cohort": K}` when the cohort
exists but is smaller than ten, or when fewer than ten members measured that particular
metric. `{"no_cohort": "value unknown"}` when this capture has no value to place. The
compactions family gets `{"no_cohort": NO_PERCENTILE}` when a cohort does exist, and the
general no-cohort answer when it does not, because the general one is true of the whole
vector and the reader needs it first.

**The claim class is never omitted, and there are three of them on one row.** The
CLAIM_CLASS column is the class of the raw values, which is `derived` in every capture.
The difference and the two percentiles carry their own inside their own cell:
`-144111 (comparative)`, `75.0 (comparative)`. A comparative number printed in a row
headed `derived` would be the omission design 6.13 forbids.

## UNSURE OR NOT DONE

**The backfill member filter cannot be observed today.** `--include-backfill` decides
whether an imported capture may be a member of a cohort. Every imported capture also
fails the content-level key, because no launcher recorded one, so the filter never
changes an answer: with or without the flag the imported captures here are outside every
cohort for a different reason. Both branches are exercised by the test and both are
wired, but I cannot show a case where the flag alone changes n. It would take a backfill
capture with all four keys, which nothing in this system can currently produce.

**No store-level test covers a cohort with a gap in one metric.** The rule that a null
has no rank is asserted directly on `percentile`, because the ten captures the loop
builds have identical coverage: the query
`select metric, count(*), sum(case when value is null then 1 else 0 end) from evidence
group by metric having ...` returns no metric with a mixed answer across them. So there
is no store in this repository where one member measured a metric and another did not,
and I did not invent one.

**`vector` scales with the size of the database, not the capture.** 0.31 s on 36
captures and 30715 observations, of which 225 ms is reading every observation of every
capture to find two payloads. A store ten times that size would take proportionally
longer. It is a read command and the number is small today; it is in NEXT.

**The percentile is mid-rank, and I did not test the tie rule against a second
opinion.** `100 * (below + 0.5 * equal) / n` is what the brief specified and what the
code does. Ten runs of one scripted task tie on most metrics, so most of the column is
50.0, which is the honest answer for a capture that is exactly typical of its cohort. A
reader could reasonably want the tie handled differently; that is a decision, not a
measurement, and it is stated in the docstring of `percentile`.

2. **Give store.py a reader for one observation type of one capture.** The cohort scan
   reads whole observation lists to find two payloads. `observations(capture_id,
   types=...)` would cut the 225 ms measured above to a fraction of it, and the
   `derived-writes-only-in-store` boundary means that reader belongs in store.py.
3. **Percentiles need a real cohort of real sessions.** Everything above is measured on
   ten captures of a scripted agent, whose numbers are fabricated by design. The cohort
   machinery is verified; what a percentile of a real session means is not, and the
   first ten real captures that share four keys are what would settle it.
4. **`compare` across providers is possible and probably wrong.** Nothing stops
   `telltale compare <claude capture> <codex capture>`. The difference says so in its
   assumptions, and the two coverage columns show it, but a reader could still read a
   row as a comparison of two agents. Whether to refuse it, or to warn, is an owner
   decision.

## EXPLAIN FOR THE OWNER

### The problem a number alone cannot solve

Your session used 227790 cached tokens. Is that a lot?

The question has no answer as asked. It depends on the model, on how long the session
ran, on whether the tool was reading a large repository, on which version of the agent
binary was running. A number with nothing beside it invites the reader to supply the
missing context from memory, and memory supplies whatever the reader already believed.

The fix is not a better number. It is a group of comparable sessions to put the number
next to. That group is what this task built.

### What a cohort is

A cohort is a set of captures that are alike in the ways that would otherwise explain a
difference. Design 6.11 names four ways:

- the same provider, because Claude and Codex do not count tokens the same way
- the same runtime major version, because 2.1.257 and 2.1.258 are different programs
- the same model, because a haiku session and an opus session are not comparable
- the same content level, because level 0 records less than level 1 and a metric that
  was not observable is not a metric that came out low

If two captures agree on all four, a difference between their numbers is a difference in
the work rather than a difference in the setup. If they disagree on any one of them, it
is not.

Here is a real case from this task. I ran the scripted test agent eleven times: ten with
`--model sonnet` and one with `--model opus`. Everything else was identical, down to the
repository and the seed. The ten form a cohort of ten. The eleventh forms a cohort of
one, and the code says so:

```
opus capture:  cohort: none, n=1
the ten:       cohort: provider=claude, runtime_major=fake-agent, model=sonnet, content_level=1, n=10
```

One flag on a command line, and eleven captures are not eleven comparable things.

### Why ten is a gate and not a statistic

Ten is not a sample size that makes a percentile accurate. It does not. Ten is the point
below which the code refuses to print one at all.

The difference matters. A statistic gets better gradually: nine values give you a
slightly worse estimate than ten. A gate is a yes or a no. Design 6.11 chose a gate,
and the reason is what a rank among a handful of captures actually says.

Suppose you have three captures and yours has the highest token count. The rank says
"100th percentile". Read plainly, that is "this session used more tokens than any
comparable session". Read honestly, it is "there were two other sessions and this one was
bigger than both", which is a statement about how few captures you have rather than about
your session. The number cannot carry that distinction, so the code refuses to print the
number.

Below ten you get the count instead:

```
context_token_burden  fresh_input_tokens  1341  tokens  observed  derived  no cohort (n=9)
```

The raw value is untouched. Only the comparison is withheld, and the reason for
withholding it is a number you can act on: find one more comparable capture.

### One real vector, and the percentile worked out by hand

The ten captures above each recorded a fresh input token count. In the order they ran:

```
339, 1107, 786, 1050, 1341, 942, 1245, 1575, 1098, 1440
```

The fifth is the one I asked about. Sorted, the ten are:

```
339, 786, 942, 1050, 1098, 1107, 1245, 1341, 1440, 1575
                                       ^ 1341, the one being placed
```

Seven values sit below it. One equals it, which is itself. The rule is
`100 * (below + half the ties) / n`, so `100 * (7 + 0.5) / 10 = 75.0`.

The command prints:

```
context_token_burden  fresh_input_tokens  1341  tokens  observed  derived  75.0 (comparative)
```

The half is there because ties are the normal case, not an edge case. Nine of the
twenty ranked rows in that vector read 50.0, because ten runs of one scripted task
change one file every time and search zero times every time. A rule that counted a tie
as "below" would print 0.0 for a capture that is exactly average, and a rule that
counted it as "above" would print 100.0 for the same capture. Half of the ties splits
the difference, and 50.0 for a capture identical to its cohort is the answer that reads
correctly.

The word `(comparative)` after the number is not decoration. Every number Telltale
prints carries the strength of the claim it can support. `1341` is `derived`: it was
computed from this capture's own records. `75.0` is `comparative`: it is a statement
about this capture against a named group, and it is only as good as that group. The two
sit in one row and they are not the same kind of thing, so they say so separately.

### Why a percentile is printed and never stored

Every other number Telltale computes is written to the database. Percentiles are not,
and the reason is worth following because it is the same reason the rest of the system
is trustworthy.

Telltale promises that rebuilding a capture gives you the same rows. Run
`telltale rebuild` twice and the evidence table is byte for byte what it was. That
promise is what makes a stored number checkable: you can always recompute it and see.

A percentile cannot make that promise. Watch what happens when one more capture arrives.
Before, with ten in the database:

```
fresh_input_tokens  1341  tokens  observed  derived  75.0 (comparative)
```

I then ran one more session, seed 11, which used 599 fresh input tokens. Same repository,
same model, same everything. Nothing about the capture I was asking about changed. One
`telltale rebuild` later:

```
cohort: provider=claude, runtime_major=fake-agent, model=sonnet, content_level=1, n=11
fresh_input_tokens  1341  tokens  observed  derived  77.3 (comparative)
```

By hand: eight of the eleven are now below 1341, one equals it,
`100 * (8 + 0.5) / 11 = 77.27`, which prints as 77.3.

75.0 and 77.3 are both correct. They are answers to two different questions, asked on
two different days of two different databases. If the 75.0 had been written into the
evidence table, it would sit there next to the capture id looking exactly like the
capture's own token count, and a reader six weeks later would have no way to tell that
one of those two numbers is a property of the session and the other is a property of the
database on a Tuesday.

So the code builds the percentile through the same constructor every other number goes
through, with the same checks and the same recorded sources, prints it, hands it back to
the caller, and lets it go. If you want it later, ask again and get the answer for the
database you have then.

### What "no cohort" protects the reader from

The percentile column is never blank, never zero and never "n/a". It always says
something. Here is the full list of what it can say and what each one means:

```
75.0 (comparative)                    a rank, in a cohort named above the table
no cohort (n=9)                       nine comparable captures, one short of the gate
no cohort (content level unknown)     a cohort key this capture never recorded
no cohort (value unknown)             this capture has no value to place
no cohort (backfill excluded)         an imported session, and you did not ask for those
no cohort (spec 13.7: raw count and coverage, no percentile)
                                      the compactions family, which the spec ranks by
                                      design rather than by rank
```

Every one of those is a different problem with a different fix, and each names its own.
That is the point. The alternative spellings all lose something a reader needs:

A **blank cell** reads as a rendering fault. The reader assumes the number exists and the
table dropped it, and either ignores the row or goes looking for a bug that is not there.

A **zero** is the dangerous one. `0.0` in a percentile column means "lower than every
comparable session", which is a real and interesting finding. If the code printed 0.0
when it had no cohort, then "this session was unusually cheap" and "I have no idea, there
were only three captures" would be the same nine characters on the screen. This is the
same trap the coverage words exist to close one layer down, where "0 compactions" and
"compaction was not observable here" would otherwise share a spelling.

**"n/a"** is honest and useless. It says there is no answer without saying why, so it
gives the reader nothing to do. `no cohort (n=9)` tells them they are one capture away.
`no cohort (content level unknown)` tells them the capture was replayed or imported and
no fingerprint was ever recorded for it, which is not something more captures will fix.

The same discipline runs through the compare table, which is the other half of this task.
Two captures side by side, both coverage words on every row, and a difference only where
both of them actually measured the number:

```
edit_turnover  max_diff_lines  -  -  unavailable  unavailable  -  derived  ...
```

Neither capture has a value, so there is no difference. Nothing prints `0` there, even
though `0` is what subtracting nothing from nothing feels like it should give. The two
`unavailable` words are the reason, and they are in the row so nobody has to guess.
