## WHAT WAS WRONG

**The ladder could not read the evidence it had.** `_tree_match` asked one question: does
this commit's patch against its parent equal a snapshot's diff against the same head. That
matches a snapshot taken BEFORE the commit, while the change was still uncommitted. It
cannot match a snapshot taken AFTER one, and the snapshot every capture takes at its end
is exactly that: `head` is the new commit and the diff is empty. Measured on the gate
capture `cap_01M1GPSMW1ZRXVADWZPF0KZ9H3` in a copy of the owner's store:

```
trigger        head       diff_hash   files_changed
file_mutation  e2aa6a95   52039e43…   2
file_mutation  e2aa6a95   52039e43…   2
file_mutation  e2aa6a95   52039e43…   2
capture_end    3512c938   e3b0c442…   0        <- sha256 of no bytes: the clean tree
```

**The window excluded the commits of a fast capture.** Git stores a commit date in whole
seconds. A capture starts at, say, `16:30:25.129544`, and a bash child that commits
finishes 95 ms later, so its commit is dated `16:30:25` and compared as `16:30:25.000000`
against a start of `16:30:25.129544`. It fell outside the window. I hit this on the first
end-to-end run and it produced no link at all.

**`provider_reported` is unreachable on 2.1.258.** No payload in 19313 observations of the
four 2.1.258 captures in the owner's store carries `git_commit_id`, on any surface. The
2.1.257 S8 fixture carries one (`cb10af7`, on the OTel tool result, the PostToolUse hook
and the stream), so the rung works and is exercised by a test; nothing on this version
feeds it. Whether 2.1.258 dropped the field or the compound `git add && git commit` form
hides it is still open, and the answer needs a 2.1.258 session that commits through a
tool call this system can see.

**Two "2.1.258 drift" fields were not drift.** `api_request.cost_usd_micros` and
`assistant_response.model`, `.query_source`, `.request_id` are in the 2.1.257 fixtures
this repository has held since E01:

```
$ python3 -c "…" fixtures/sources/claude/2.1.257/S4/otel_logs.jsonl
api_request         [… cost_usd, cost_usd_micros, duration_ms, effort, …]
assistant_response  [… model, query_source, request_id, response, response_length, …]
```

W0-T4 did not list them, so they had been dropped since the day the fixtures were
recorded. `hook_execution_complete` is the same story in reverse: the wave 1 gate read it
as a new event, and it has had a complete allowlist entry since W0-T4. What the gate
actually saw on it were the five identity attributes, which stay dropped by decision.

**A rebuild kept the conflicts of the reducer that no longer finds them.**
`cap_01M1GPSMW1ZRXVADWZPF0KZ9H3` carried 32 diagnostics of kind `conflict` written by the
pre-W2-T1 reducer. The current reducer finds none on that capture, and all 32 survived a
rebuild, so `telltale show` reported 32 problems that this reduction did not find.

**A capture that had never been reduced looked exactly like an empty one.** The launcher
ran no reducer. `telltale show` on a fresh capture printed nulls with `coverage {}`, which
is what a capture where nothing happened prints. That is the confusion AGENTS.md
invariant 5 exists to forbid, and it is measurable: the E04 fake-agent capture
`cap_01M1GSPD57128SJ7P6V1N9367V` has 0 activities and 0 evidence rows to this day.

## WHAT CHANGED

**`src/telltale/repo_link.py`**, new, and the first commit is only the move. Everything
about linking a commit to a capture left `repo.py`, which was 797 lines against the
800-line ratchet: `commits_since`, `_link`, `_tree_match`, `_candidates`, `_confidence`,
`_commit_facts`, `_commit_stats`, `_unresolved`, and `reported_commits` from `launch.py`,
which reads the store for the same question. The git primitives both modules run are
public in `repo.py` now (`git_stdout`, `git_line`, `git_numstat`, `sha256`, `parse_ts`,
`totals`, `DIFF_SAFE`): one argv builder, one timeout, one environment.

**`_tree_match` accepts a second shape of evidence.** A snapshot whose head is the commit
and whose diff is empty is the working tree at that commit, photographed by Telltale. The
rung is decided by the trigger of the snapshot that matched: `capture_end` and nothing
else is `tree_match_after`, any snapshot taken while the child ran is
`tree_match_during`, and a snapshot that recorded no trigger is read as the weaker of the
two. `_confidence` then takes the weaker of that and the commit's own clock, so a
snapshot from during the capture matching a commit made after it still reports
`tree_match_after`.

**The window start is floored to the whole second**, with the measurement in the
docstring. What it costs is stated there too: a commit made up to one second before a
capture can now reach a rung if a snapshot holds its tree.

**`receiver.py`: the callback carries a word, not a boolean.** `on_file_mutation` is now
`on_repo_change`, and the provider answers with the reason a snapshot is due rather than
yes or no. `providers/claude.py`'s `names_file_mutation` returns `file_mutation` for a
writing tool, `commit_command` for a Bash result whose normalized command commits, and
`vcs_state_changed` for the stream message. The reason travels through `repo.Debouncer`,
which now calls its function with the last trigger of the burst, and lands in the
snapshot's `trigger` field. Only a command that has ALREADY RUN is read: a PreToolUse
body carries the same field and the tree it describes is the one before the commit.

The command is matched in its normal form, the bounded string the store holds. W2-T1 is
what makes that work: before it, a commit with a multi-line message normalized to
`git _` and no stored command in the whole build contained the word commit.

**`allowlist.py`.** `cost_usd_micros` as a size; `model`, `query_source` and `request_id`
on `assistant_response`; and two counts on the Claude `Stop` hook. The counts are counts
because I read the 2.1.258 binary's own hook schema rather than guessing:
`background_tasks` is an array of `{id, type, status, description, command, agent_type}`
and `session_crons` an array of `{id, schedule, recurring, prompt}`. One holds a shell
command line, the other the prompt a cron will submit. The parser consumes both arrays
and stores `background_task_count` and `session_cron_count`.

**`store.py`: `rebuild` clears the capture's conflict diagnostics** in the same
transaction as the derived-table deletes, so the count after a rebuild is what this run
found. The cost is named in the code and again under UNSURE below.

**`launch.py`: the capture reduces itself.** `store.rebuild(capture_id)` runs after
`capture_ended` is appended and flushed, inside the same fail-open guard as every other
step, so a reducer that raises becomes a diagnostics row and the exit code is still the
child's. The reducers register by being imported, and the import happens there rather
than at the top of the module: the cost is paid after the child has exited.

**`cli.py`: `timeline`, `show` and `explain` refuse** a capture with no activities,
through `cli_common.refuse`, naming the command that fixes it.

**`providers/claude_drift.py`**, new. `CAPABILITIES` and `DRIFT` moved out of `claude.py`,
which crossed the 800-line ratchet: they are measurement tables rather than parser code,
the same split `allowlist.py` is to `sanitize.py`. `claude.py` re-exports both, because
the provider protocol asks a MODULE for them.

**`tests/integration/test_commit_link.py`**, new, 10 tests, each making a real commit in a
repository it creates and reading the answer out of the database a real `telltale run`
wrote.

## UNSURE OR NOT DONE

- **A commit another process made in the same worktree links to the capture.** Measured,
  and there is a test asserting it: the child sleeps and changes nothing, a second
  process commits, and the capture-end snapshot photographs a tree that IS that commit,
  so the ladder reports `tree_match_after`. The claim is true as written, "the tree at
  the end of this capture was this commit", and no field says the session did the work.
  It is still an attribution a reader will make. Spec 12.4 is the missing half:
  `repo.overlaps` marks two CAPTURES on one worktree ambiguous and an uncaptured `git
  commit` in another terminal is invisible to it. The heuristic rung is not what admits
  this commit, so making it opt-in changes nothing here.
- **`rebuild` deletes conflict diagnostics the receiver and the importer wrote.** The
  brief's premise was that `conflict` is the reducer's kind alone. It is not: `receiver.py`
  writes one when a provider session binds to a second capture, and `importer.py` when two
  files key on one capture id. Both are ingest facts and both are now deleted by a rebuild
  of that capture. Telling them apart needs a marker no row carries: a seventh diagnostic
  kind is a CHECK-constraint change and therefore a migration, and putting the observation
  id on the reducer's rows would not clear the 276 rows already in the owner's store, which
  is the thing the fix is for. I judged a wrong conflict count on every capture worse than
  losing a rare ingest row, and someone could reasonably differ.
- **Three 2.1.258 shapes are still dropped whole**, because nothing has measured what
  their fields mean: `claude.otel.retention_sweep` (11 counters about deleting old
  transcripts), `claude.stream.tool_progress`, and the system subtypes
  `background_tasks_changed` and `code_change_published`. `code_change_published` is the
  interesting one for this task's subject: it names a provider, a repo and a URL, so it
  is about a push rather than a commit, and a rung for a pushed branch is not in spec
  12.3. Left dropped and named in DRIFT.
- **`claude.otel.metric` drops `service_version` and `terminal_type`** on every record,
  which is 746 of the 1935 `unknown_field` rows in the owner's store, the single largest
  source. It predates 2.1.258 and is one line to fix (the metric entry does not include
  `_OTEL_COMMON`), and I left it alone because it is not this task's field list and
  changing what every metric row stores deserves its own measurement.
- **Whether 2.1.258 stopped sending `git_commit_id` needs a session that commits through a
  tool call.** I can say it is absent from all 19313 observations of four 2.1.258 captures.
  I cannot say whether the field is gone or whether the compound `git add && git commit`
  form the build uses hides it, because every commit in those captures was made that way.
- **A capture with two commits links only the last.** The capture-end snapshot holds one
  tree. The debounced snapshot after a commit command holds another, so a session that
  commits twice with a gap between them links both; two commits inside one two-second
  debounce window collapse into one snapshot and the earlier commit reaches no rung. Not

- **A rebase or an amend links the tip and nothing else.** Reasoned, not measured: the

- **`launch.py` is 790 lines and `allowlist.py` 798**, both against the 800-line ratchet.
  The next change to either has to move something out first. In `launch.py`,
  `link_commits` is the obvious candidate and it stayed because it builds the launcher's

## EXPLAIN FOR THE OWNER

### What was at stake

You wrap an agent session in `telltale run`, the agent makes a commit, and afterwards you
want to ask "what did that session change". If the recorder cannot tell you which commit
belongs to which session, every question downstream of that one is unanswerable. Wave 1
measured the failure: a real session made one commit and one push, and the capture
recorded no commit at all.

### Why time is not enough

The obvious answer is to look at the clock. The session ran from 09:21 to 09:29, the
commit is dated 09:27, so the session made it. That answer is wrong often enough to be
dangerous, and the specification says so in one sentence: temporal proximity alone is
never a link.

Here is why. You have four terminals open. Two of them are agent sessions in different
worktrees of one repository, you are typing `git commit` in the third, and a colleague's
`git fetch` is landing commits in the fourth. Every one of those commits is inside every
session's window. A recorder that links by time attributes all of them to all of them, and
the number it gives you is not wrong by a little.

So the system uses a **ladder**: a fixed order of kinds of evidence, strongest first, and
each commit is labelled with the highest one it can reach. Five rungs, and each is a
different sentence:

1. **explicit** - somebody stated it. `telltale run --commit abc123`. A human or an
   orchestrator said this commit belongs to this session, and a statement outranks
   everything below.
2. **provider_reported** - the agent said it. Claude Code sometimes attaches a commit id
   to the record of the tool call that made it. That is the agent naming its own work.
3. **tree_match_during** - Telltale photographed the tree, while the session was running,
   and the photograph is this commit.
4. **tree_match_after** - the same photograph, taken as the capture closed.
5. **heuristic** - nothing but the clock. Off unless you ask for it, and it says
   "heuristic" in the record so a report can refuse it.

The label is not decoration. It travels with the number into every report, so a reader can
see the difference between "the agent told us" and "we matched a tree".

### The photograph, and what was wrong with it

Rungs 3 and 4 need explaining, because they are where the work was.

While a session runs, Telltale takes what it calls a **snapshot**: it asks git what
differs between the working tree and the last commit, and keeps two things. The commit the
tree sits on, and a fingerprint of the difference, which is a sha256 of the bytes `git
diff` prints. No diff text is ever stored.

Now the trick. If the tree differs from commit P by exactly patch D, and the agent then
commits, the new commit C has P as its parent and produces exactly D. Two values Telltale
already recorded, and both come back identical from git afterwards. That is a tree match,
and it needs nothing from the agent.

The old code did only that, and it looks at the tree BEFORE the commit. The gate session
never produced a matching snapshot, for a mundane reason: after the agent's last file
edit, it changed more files by running `ruff --fix` and a pre-commit hook through Bash, and
those changes go through no tool that Telltale watches, so no snapshot was taken. The last
snapshot described a tree from four minutes and several files earlier.

But there was a second photograph nobody was reading. Every capture takes a snapshot as it
closes. That one said: the tree sits on commit `3512c938`, and there is no difference. A
tree with no difference from `3512c938` IS `3512c938`. That is not a heuristic and it is
not proximity; it is the recorder having photographed the commit itself.

So `_tree_match` now accepts either shape. And the rung follows from WHICH photograph
matched. One taken while the child was still running says the tree was seen during the
session, which is rung 3. The one at capture end sits on the boundary, so it is rung 4.
Both are honest and they are not the same claim.

### The commit from the test, and its rung

The test makes a repository with one commit in it, then runs:

```
telltale run -- bash -c 'echo x >> f && git add f && git commit -q -m one'
```

The commit that comes out is `68fd322c`, and the record says `tree_match_after`. Why the
weaker rung, when the commit was plainly made inside the capture? Because the child here
is `bash`. Bash has no hooks and no event stream; it tells Telltale nothing. No file
mutation is ever reported, so no snapshot is taken while it runs, and the only photograph
of that repository is the one at capture end. The evidence is real and it arrived at the
boundary, so the ladder says so.

A real agent session does better, and that is the second half of the change. Claude Code
reports every Bash call it finishes. When the command that finished commits, Telltale now
takes a snapshot two seconds later, WHILE the session is still running, and tags it
`commit_command`. Claude Code 2.1.258 also announces a commit on its output stream, and
that message triggers a snapshot too. Either way the photograph exists before the capture
closes, and the same commit reaches `tree_match_during` instead. There is a test for each,
using a child process that posts the same shapes a real agent posts.

One detail is worth pulling out, because it is a dependency between two tasks. The command
is matched in its **normal form**, the cleaned-up version the store keeps: values are
stripped, paths are made relative, and what survives is `echo x >> f && git add f && git
commit -q -m one`. Until W2-T1 landed a fix a fortnight of build sessions ago, a commit
with a multi-line message failed to parse and was stored as `git _`. No stored command in
the whole build contained the word "commit". This change could not have worked before
that one.

### One second, and why it is a measurement

The first end-to-end run linked nothing, and the cause is small and instructive. Git
stores a commit's date in whole seconds. The capture started at `16:30:25.129544` and the
bash child committed 95 milliseconds later, so git wrote the date `16:30:25`, which reads
back as `16:30:25.000000` and lands before the start of the window. Every commit of every
short capture was excluded.

The fix is to compare against the whole second the capture started in, not the
microsecond. That is not slack; it is refusing to assert a precision the data does not
have. It costs something real and the code says so: a commit made up to one second before
a capture can now reach a rung if a snapshot holds its tree.

### What 2.1.258 means for the fixtures recorded on 2.1.257

Two answers, and the second is the more useful one.

Claude Code 2.1.258 sends no commit id anywhere. I checked all 19313 observations of the
four 2.1.258 captures in your store, on every surface, and there is no `git_commit_id`.
The 2.1.257 fixture S8 has one. So rung 2 works, is tested, and is fed by nothing on the
version you are running: on 2.1.258 every link comes from a photograph. That is exactly
why this task existed, and it is why the fixtures still earn their place. They are the
only evidence that the rung above the tree matches works at all.

The second answer is a correction. The wave 1 gate listed four fields as 2.1.258 drift:
`cost_usd_micros` on the request event, and `model`, `query_source` and `request_id` on
the assistant-response event. They are in the 2.1.257 fixtures too. They were never drift.
They were fields W0-T4 did not list, and the allowlist had been dropping them since the
day those fixtures were recorded, on both versions, in silence except for one diagnostic
row per batch. The same goes for `hook_execution_complete`, which the gate read as a new
event and which has had a complete entry since W0-T4; what the gate saw on it were the
identity attributes, which are dropped on purpose.

The lesson is about the diagnostic rather than about the version. A field arriving that we
do not store produces a row that says so, and the gate read those rows as evidence of a
version change because they were noticed in a version-change week. The rows do not
distinguish "new from the provider" from "never listed by us"; only the fixtures do. They
are what turned a plausible story into a checkable one, and the check took one command.

The fields you would NOT want stored are dropped by decision and keep announcing
themselves: `organization_id`, `user_id`, `user_email`, `user_account_id`,
`user_account_uuid`. They identify a person, nothing here needs them, and leaving them
unlisted means one diagnostic per batch says they still arrive. If Anthropic ever stops
sending them, you will see the row disappear.

The 2.1.258 `Stop` hook is the one place where reading the version mattered, and it shows
what "allowlist a field" has to mean. It carries `background_tasks` and `session_crons`.
Both are arrays, and I read the schema out of the Claude Code binary rather than guessing:
a background task carries a shell command line and free text, and a cron carries the
prompt it will submit when it fires. Storing either array would put an agent's prompt and
a user's command into the recorder. What a reducer actually wants is the answer to "did
this session stop with work still in flight", and that is a number. So the parser consumes
both arrays and stores two counts.
