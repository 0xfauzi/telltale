## WHAT WAS WRONG

**Design 6.12 wrote a state the capture had observed as an unknown, and the exclude
policy then refused the fact along with the unknowns.** That is one defect, and it had
already been seen twice and misdiagnosed twice.

`last_verification_exit` was defined as 0 for a pass, 1 for a fail and None for "no
verification has run yet". The first two are results. The third is not missing data: the
capture saw every command the session ran and none of them was a verification, so "none
has run" is something the recorder measured. Writing it as None made a measurement
indistinguishable from an absence.

What that cost, measured. On the 175-request capture the first 106 rows carried that
None. A context window on the request clock starts at the last changepoint at or before
the origin, or at row 0 when there is none, bounded to 512 rows back; this capture has no
changepoint and 175 rows, so every window starts at row 0 and every window reads that
cell. Policy `exclude` drops a window that reads an unknown, so all 143 planned origins
were dropped, with one reason:

```
windows       FAIL    0         20      175 rows, c_min 32, H 1, stride 1: formula 143, planned 0; dropped: missing_context_value(last_verification_exit) 143
missingness   FAIL    106       0       row 0 column last_verification_exit is inside the window at origin 32; 106 unknown cells in 143 planned windows, and policy exclude drops the windows that read them
```

The other nine columns of that capture had 0 nulls each. One column, one encoding
decision, and the whole capture was unforecastable.

Two prior reports saw the symptom and called it structural rather than wrong.
`docs/log/W1-T5.md` (its UNSURE section) says `refuse` fires on essentially every capture
because row 0 is None until a test has run, and that "someone could reasonably argue that
'no verification has run yet' is a structural None rather than a gap". The wave 1
amendment in `docs/design/01-design.md` repeats it: "Under `refuse`,
last_verification_exit refuses nearly every capture because its first row is None until a
test has run; that is the rule as written, and whether a structural None should be exempt
is an open decision." Both framed the question as whether `refuse` should have an
exemption. Neither asked whether the None was true, and it was not.

Three corrections to the brief's own numbers, all in the same direction (the store is
live and this session is being recorded into it, so it grew between the brief's
measurement and mine):

- `cap_01M1HE3XS4E3S2XTSNB99C7WQT` has 168 requests on my copy, not 130, and its k is 64,
  not 130's companion value.
- `cap_01M1HE3ZCX63HRX8PAWJDYSNG6` has 83 requests, not 73.
- The other seven agree exactly, and every k agrees exactly: 106, 76, 50, 111, 30, 17, 45
  and 63 for the captures the brief names.

## WHAT CHANGED

**`src/telltale/series.py`.** The column table now has eleven entries; the two new ones
sit where `last_verification_exit` was, both with unit `flag` and both resting on
`("commands", "tool_calls")`. In the fold, `_State.last_exit: float | None` became
`_State.seen: int` and `_State.failed: int`. Both are still counters that `reset` leaves
alone, which is the same rule the old one had: the most recent verification's result is a
fact that stays true until another verification states otherwise, and so is the fact that
one has happened at all.

`_exit(success, previous) -> float | None` became `_failed(success, previous) -> int`,
with the previous-answer rule intact: `success` true gives 0, false gives 1, and anything
else leaves the previous value standing. What changed is what "anything else" can produce.
It can no longer produce None, because the run happened and `verification_seen` says so.
A verification whose success nobody stated does not flip `last_verification_failed` and
does not blank it.

Every fixture on disk states `success` on every verification_run, so the STOP condition
in the brief is not met. Measured:

```
$ sqlite3 $TELLTALE_HOME/telltale.db "select capture_id, count(*), sum(case when json_extract(fields,'$.success') is null then 1 else 0 end) from activities where activity_type='verification_run' group by capture_id"
capCS1|3|0
```

Eleven verification runs across five replayed captures, zero without a stated success. So
the previous-answer branch of `_failed` is written and untaken on every fixture, which is
the same position `_exit` was in.

**`src/telltale/forecast/__init__.py`.** One comment: the columns that are flags and
therefore not targets are now named `env_changed`, `verification_seen` and
`last_verification_failed`. `TARGETS` is unchanged.

**`docs/design/01-design.md`.** The request-clock list in 6.12 reads
`verification_seen (0/1), last_verification_failed (0/1)`. A new "Amendments from wave 2
(2026-09-02)" section states the measurement, the reasoning and the rule it adds: a state
the capture observed is a number, and None is reserved for what no surface delivered.

**Tests.** `test_series.py`: the S1 column assertion is now the two columns' expected
lists, derived by hand from S1's timeline and explained in the comment beside them; a new
test replays S7, the one fixture with a failing verification, and asserts both flags turn
together and hold; the refuse test moved to the Codex S1 replay (below); the CLI test
asserts `--policy refuse` now exits 0 on Claude S1. `test_forecast_contracts.py`: the
twelve-row hand-written fixture gained its eleventh cell and an assertion that its width
is the compiler's, so the next column change fails there rather than as an IndexError
inside `_block`; the S1 policy test is renamed and asserts both policies build.
`synthetic_series.py`: the walk writes eleven columns, with the two flags placed so that
the random draw the old column made stays in the same position, which keeps the walk
itself byte-identical (`tau 1606.4` and scaled MAD `959.2422` are unchanged).

## UNSURE OR NOT DONE

- **The all-None branch of the two new columns is unexercised on real data.** When
  `commands` and `tool_calls` are both unavailable, both columns are all None, like every
  column whose capability nobody had. `commands` and `tool_calls` are `observed` on all
  fifteen replayed fixtures (measured: the coverage map on each capture lifecycle
  activity), and the launcher captures in the build's store are Claude, which reports
  both. The branch is `_blank_unobservable`, which is shared with every other column and
  is exercised by `env_changed` on every replayed fixture, so it is one code path rather
  than a new one; that is reasoning, not a measurement of these two columns.
- **The previous-answer branch of `_failed` is never taken on any fixture.** Eleven
  verification runs, all with a stated success. The rule is carried over from `_exit`
  unchanged and is what I report rather than what I measured.
- **`last_verification_failed` is 1 on only two of the nine build captures**
  (`cap_01M1HE3ZCX63HRX8PAWJDYSNG6`, 39 rows, and `cap_01M1FW3DA7M6YK37QM4KAY308H`, 2
  rows) and on one fixture (Claude S7). `verification_seen` is 0 on all 111 rows of
  `cap_01M1GRSFRXES0N7ZJFYZ3BK84Q`: no verification ran in that session at all, which is
  now a column of 111 zeros with coverage `observed` rather than 111 unknowns.
- **Only `output_tokens` is ready, and that is a fact about the targets, not about this
  change.** On the 175-request capture, `fresh_input_tokens` and `tool_calls_since_prev`
  have scaled MAD exactly 0 and fail readiness check 7, and `output_tokens` has scaled MAD
  409.1976. Eight of ten requests carry at most 2 fresh input tokens (tau 2 by the q80
  rule), which is Claude Code's prompt-cache pattern. The registry is untouched; E07 is
  where that gets decided.
- **The backtest numbers below are not interpreted here.** The table is pasted because the
  brief asks for it and because it is the first backtest of a real capture in this
  project. Every forecaster's skill against the best baseline is at or below 0, which is a
  number E07 reads, not a conclusion I am drawing.
- **Series snapshots stored before this change are not rebuilt by anything.** The column
  schema is part of `series_id` and `REDUCER_VERSION` hashes series.py, so every capture's
  series id and reducer version changed. `series list` shows both generations, which is
  correct: they are different series. `ser_814fa076b861de7967e01405` (old) and
  `ser_4f0557ebc25d4e324f402b80` (new) are the same capture. The synthetic 200-row series
  moved from `ser_993f3f31ac47a9ec6e908a69` to `ser_77ef8de485a6869e795f2cfd`, and
  `docs/log/W1-T5.md`, `docs/log/W1-T6.md` and `docs/log/W2-T5.md` quote the old id; I have
  not edited those logs, because a log is a record of what was run at the time.
- **Six golden files changed and they are not in the brief's OWNS list.** The change is
  forced: `forecast_readiness` in the session summary counts columns, so the coverage line
  of every target moved by one. I regenerated them with `TELLTALE_GOLDEN=write` and the
  diff is exactly those eighteen lines and nothing else.
- **Nothing here ran an agent binary.** Every number was measured on replayed fixtures or
  on a copy of the store at `/tmp/w2t7before` and `/tmp/w2t7after`. `~/.telltale/telltale.db`
  was read once, with `cp`.

# EXPLAIN FOR THE OWNER

## The thing that was wrong, in one sentence

The recorder wrote something it had watched happen as though it had failed to watch, and
the forecasting side, which is careful about things nobody watched, threw the whole
session away.

That cost nine sessions. Every one of them was long enough to forecast, and every one of
them scored zero usable windows. They are all usable now, and the change is one column
becoming two.

## Unknown and known-to-be-none are different, and only one of them is a number

Start with the two words, because everything else follows from them.

**Unknown** means nobody looked, or somebody looked and could not see. A camera that was
switched off does not tell you the room was empty. If you write 0 people in the room, you
have not recorded an observation; you have recorded a guess wearing the clothes of one.

**Known to be none** means somebody looked, and there was nothing there. That IS an
observation. It is a real zero, and it is as solid as any other measurement.

Telltale has taken this seriously from the beginning. It has a word for each column that
says which kind of thing that column is. `observed` means a surface delivered it.
`unavailable` means nothing could see it. And the rule the whole system rests on is:
never zero-fill an unknown. A missing value stays as the marker for absence, which in
this codebase is Python's `None`, all the way through the model, the series and the
report.

That rule is right. What went wrong is that one column was on the wrong side of it.

## The column, and the day it made sense

The request clock is one row per request the agent made to the model. Each row carries a
handful of numbers about that moment: tokens in, tokens out, how long it took, how many
tool calls happened since the last row.

One of those columns was called `last_verification_exit`. A verification is a test run: a
`pytest`, a `make check`, anything the classifier recognises as checking the work. The
column said whether the most recent one had passed. Three possible values:

- `0`, the last test run passed
- `1`, the last test run failed
- `None`, no test has run yet

Look at that third line. Two of the three are results. The third is a different kind of
statement entirely, and it got written in the slot reserved for "we could not see".

Was that wrong? Consider what the recorder actually knew at the top of a session. It had
watched every single command. It had classified each one. None of them was a test run. So
"no test has run yet" is not a hole in the record. It is the record.

## The 106 rows

Here is the concrete case, from this build's own store.

One captured session made 175 requests to the model. It ran for a long time before it ran
its first test: 106 requests, then a `pytest`. So the first 106 rows of that column were
`None`, then 0 or 1 for the remaining 69.

Now, how a forecast gets scored. You pick a row in the middle, hand a forecaster
everything before it, ask what comes next, and compare against the row you withheld. That
slice of history is a window. Slide it forward and you get another one. The average error
over all the windows is the score.

Two rules bound it. A window needs at least 32 rows of history behind it, which is a
number fixed in the design before any data existed. And a run needs at least 20 windows
before its average means anything.

175 rows, minimum 32 of history: that is 143 possible windows. Plenty.

Now the part that matters. Where does a window's history start? At the beginning of the
session, unless the environment changed partway through, in which case it starts there
instead. This session's environment never changed. So every one of the 143 windows starts
at row 0.

And every one of them reads row 0. And row 0 says `None`.

A forecaster cannot consume an unknown, and Telltale will not invent one. So the window
gets dropped. Not some of them. All 143, for the same reason, printed by the tool itself:

```
windows  FAIL  0  20  175 rows, c_min 32, H 1, stride 1: formula 143, planned 0; dropped: missing_context_value(last_verification_exit) 143
```

143 of 143. And the other nine columns of that same session had zero holes between them.

One cell, at one corner of the table, propagated by a rule that was working exactly as
designed, took out the entire session.

## Why nobody caught it, twice

This is the part worth dwelling on, because the failure was not a bug in any function.

Two earlier tasks noticed the symptom. W1-T5, which built the compiler, wrote in its own
report that the strict policy "refuses under `--policy refuse` on essentially every
capture" and added: "someone could reasonably argue that 'no verification has run yet' is
a structural None rather than a gap, and should be exempt". The design document picked up
the same sentence in its wave 1 amendments.

Both of them framed the question as: should the policy have an exception?

That is the wrong question, and it is wrong in an instructive way. It accepts the value
and argues about the rule. The rule was fine. The value was false. "No verification has
run yet" was never a gap, so nothing needed exempting; it needed writing down correctly.

The reason it is easy to miss is that the code did exactly what it was told, the design
said exactly what the code did, and the tests asserted exactly what the design said.
Three layers of agreement, all describing the same wrong number. What broke the agreement
was running the thing on nine real sessions and reading the reason it gave for refusing
them.

## The fix: one column becomes two

The old column tried to carry three states in one number. Two of them are results and one
is a different question. So split it along that seam.

**`verification_seen`**: 0 or 1. Has any test run happened before this row?

**`last_verification_failed`**: 0 or 1. Did the most recent one fail? It is 0 when none
has run, and that is not ambiguous, because the first column tells you which kind of 0 it
is.

Same three states, no unknown. Row 0 of that session is now `verification_seen 0,
last_verification_failed 0`, which reads as "no test has run, and nothing has failed",
and both halves are true and both are measurements.

Here is S1, a small recorded fixture session, seven requests, three test runs, all
passing. Read the three columns together:

```
row  verification_runs_since_prev  verification_seen  last_verification_failed
0    0                             0                  0
1    1                             1                  0
2    0                             1                  0
3    1                             1                  0
4    0                             1                  0
5    0                             1                  0
6    1                             1                  0
```

Runs land in the gaps closing rows 1, 3 and 6. `verification_seen` turns 1 at row 1 and
never goes back, because a thing that has happened stays happened. The failure flag never
turns, because nothing failed.

And the other case, from S7, the one fixture where a test fails:

```
row  verification_runs_since_prev  verification_seen  last_verification_failed
6    1                             1                  1
7    0                             1                  1
```

Both flags turn together at row 6 and both hold at row 7. That holding is deliberate: "the
last test failed" stays true until another test says otherwise, which is the same rule the
old column had and the one part of it worth keeping.

There is a third case, which does not occur on any recorded session but has to be decided
anyway. What if a test run happened and no surface said whether it passed? Then
`verification_seen` still turns 1, because the run demonstrably happened, and
`last_verification_failed` keeps whatever it said before rather than becoming unknown. I
should be plain that this branch is written and never taken: all eleven verification runs
across all the fixtures state their result. So that is the rule I am reporting, not a
behaviour I measured.

## What it did not do

It did not make the forecasts good.

Nine sessions are now ready for one target: `output_tokens`, how much the model produced
per request. The other two registered targets fail, and they fail on something this change
cannot touch.

Readiness has a check for whether the thing you are forecasting moves at all. Its measure
is the scaled median absolute deviation, which is a spread that ignores outliers. If it is
exactly 0, the column is a constant, every trivial baseline predicts it perfectly, and
skill, which divides by the best baseline's error, has no denominator.

On the 175-request session, measured:

- `output_tokens`: 409.1976. It moves.
- `fresh_input_tokens`: 0. It does not.
- `tool_calls_since_prev`: 0. It does not.

`fresh_input_tokens` is fresh text the model had to read, as opposed to text served out of
its prompt cache. Eight of ten requests carry at most 2 of them. That is Claude Code's
caching working almost perfectly, which is good for the session and useless as a
forecasting target: there is nothing to predict about a number that is 2.

So the honest summary is: the recorder now hands the laboratory nine real series instead
of zero, and one of the three targets on them is worth forecasting. Whether a skill number
over 143 windows of a single session means anything is E07's question, and I have not
answered it. The backtest table is in VERIFY above, unread.

## The rule this adds

One line, and it is in the design document now:

> A state the capture observed is a number, and None is reserved for what no surface
> delivered.

The old rule, "never zero-fill an unknown", is untouched and still right. This is its
mirror, and the pair only works if both hold: do not write a guess where you have no
measurement, and do not write an absence where you have one.

## What else moved, and what to watch

Splitting a column changes the shape of every series, and the identifier of a series is a
hash of its shape and its contents. So every stored series has a new id. The old ones are
still in the database and `telltale series list` shows both generations, which is correct:
they are genuinely different series, and nothing rebuilds the old ones. If you look at a
series id in an older report, expect it not to resolve.

One thing surfaced that I did not fix, because it is not this task's. The strict build
policy, which stops rather than building when a column that should have been filled has a
hole, needed a real hole to test against. It used to have one for free: row 0 of the old
column. Now the only real hole on any fixture is on the Codex side, where
`request_duration_ms` is marked as observed and is empty on every single row, because no
Codex surface reports a per-request duration.

That is the same mistake this task fixed, one layer up. The coverage word claims a surface
delivered the column; no surface did. It makes a useful test and a false claim, and
somebody should take it.
