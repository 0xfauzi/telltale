## WHAT WAS WRONG

### Defect 1: the dash rule was about a character, not a shape

Design 6.4 said the normalizer keeps "every token starting with `-` with any `=value`
stripped". `commands._normalize_token` implemented that literally:

```python
if token.startswith("-"):
    return token.split("=", 1)[0], budget
```

A shell token is whatever the quoting makes it. `echo "--- sk-ant not X ---"` is ONE
token to `shlex`, it starts with a dash, and so the whole quoted string was written to
the database verbatim.

Measured on the owner's store on 2026-09-02 (1,040,662 observations at the time of the
copy). A byte scan for the E01 and E02 credential probes found **ten observation rows**,
every one of them `payload.command`:

### Defect 2: the scrub had never seen a command. The code path.

The brief asked which of two things was true, and it is the first. `sanitize._clean_str`
is where every kept string is cleaned, and its COMMAND branch RETURNED above the branch
that scrubs:

```python

        normalized, version = normalize(value, ctx, level)
        red.normalization = version
```

So a normal form was the one kept string design 6.4's patterns had never been applied
to. `_KEY_HEADER` has been in sanitize.py since W0-T2 and never had a chance to match.

The 512-character bound the brief asked about is a real second cause, and it is worth
recording because it changes where the scrub belongs. Four of the ten stored forms end
`KEY---`: the 200-character COMMAND bound cut the trailing dashes off, and

not match `-----BEGIN TELLTALEFAKE PRIVATE KEY---`. So a scrub added AFTER the bound
would have fixed six of the ten and left four. It now runs before the bound.

### Defect 3, found while verifying: the leak had reached a derived table

Not in the brief, and it is why `resanitize` also rebuilds. After the first run over the
copy the observations were clean and the byte scan still returned 6. All six were
`activities.fields.command_norm`, which COPIES the normal form out of the observation.
An activity is rebuildable from observations, so the fix is `rebuild`, which `purge`
already does for the same reason.

## WHAT CHANGED

**1. The flag shape** (`commands.py`). A dash-leading token is cut at the first `=` and
kept only if what is left matches `^--?[A-Za-z0-9][A-Za-z0-9_.:+-]{0,31}$`. Everything
else becomes `_`. `NORMALIZATION_VERSION` is `cmdnorm-v3`, the fallback
`cmdnorm-v3-fallback`.

**2. The scrub** (`commands.py`, `sanitize.py`). `normalize` now ends in `_finish`,
which joins, scrubs and then bounds, in that order, and returns how many secrets it
replaced. `sanitize._clean_str` records that count in `redaction.redacted`, which design
6.4 requires and which a command has never carried. One call site: the COMMAND branch.

**3. `telltale resanitize [capture]`** (`store.py`, `cli.py`). Rewrites every stored
command whose `normalization_version` is neither the current one nor the current
fallback, through `commands.renormalize` applied to the STORED string, then scrubs. It
writes only where a token changed: the field, the version, and
`resanitize:cmdnorm-v3` appended to `redaction.redacted`. One transaction per capture,
one `dropped` diagnostics row per capture, then a rebuild of that capture.

**4. The hook** (`.pre-commit-config.yaml`). `resanitize-is-the-only-update`: pygrep for
`UPDATE\s+observations`, allowed only in store.py, exactly like the INSERT rule.
Verified it fires: adding the string to cli_common.py fails the hook.

**5. The move** (`store_reads.py`, its own commit). store.py stood at 752 lines against
an 800-line ratchet, so the nine read helpers moved to a mixin first, with no behaviour
change. store.py is now 796.

**6. Tests** (`test_privacy.py`, no new file). Two, both posting through the real
receiver on the stream and the hook surfaces and both asserting against the bytes of the
database files after close.

### The classification check

`classify()` reads the normal form, so a rule that changes the form can change the
answer. Measured over all 88,754 stored rows that carry a `normalization_version`:
21,477 normal forms change and **0** change what `classify()` returns.

Over the committed fixtures the change is three golden timeline lines, and one of them


The first two are the leak shape. The third is the argv separator `--`, which the shape

two-entry allowlist inside a shape rule is the thing the shape exists to avoid. Every

## UNSURE OR NOT DONE

1. **A rewritten v1 row is labelled `cmdnorm-v3` and cannot fully earn that label.** v1
   stored an environment assignment as `NAME` and v2 as `NAME=`. Re-running the token
   rules over a v1 string cannot put the `=` back, so a v1 row relabelled v3 claims a
   comparability the rewrite did not restore. I followed the brief here and made the row
   say so twice: `redaction.redacted` carries `resanitize:cmdnorm-v3`, and the capture's
   diagnostics row names the version it came from. 9 of the 1154 rewritten captures are
   v1. My judgement, not a measurement: the alternative labels (a compound version, or
   leaving the version alone) each make the "second run rewrites 0" check cost a full
   scan every time, and neither would make the string more comparable than it is.

2. **`git commit -m "-TELLTALEFAKE"` still stores `-TELLTALEFAKE`.** A short quoted
   argument that begins with a dash and holds no spaces is flag-shaped, and nothing in a
   normal form distinguishes it from `-m`. The bound is 32 characters after the dashes.
   This is asserted in the test rather than left implicit, and the scrub stands behind it
   for anything that looks like a credential. Tightening it further (lowercase only, a
   known-flag list) would start throwing away real flags, and I have not measured what
   that would cost.

3. **`resanitize` rewrites 21,725 fields to fix 10.** 21,477 of the changed normal forms
   are `-`, `--`, `---` and longer dash runs becoming `_`, plus the words that were
   trapped inside a multi-word "flag". Every one of those is a real over-retention by
   the current rule, and none of them is a credential. I did not narrow the run to the
   rows holding a probe, because the leak shape is the rule and not the ten rows.

4. **The rebuild inside `resanitize` needs the reducers registered.** `Store.reducers` is
   filled when activities.py and measures.py are imported. cli.py imports measures.py, so
   `telltale resanitize` gets them, and the new test imports it for the same reason. A
   caller who imports store.py alone and calls `resanitize()` will rewrite the
   observations and silently not rebuild. `purge` has had exactly this property since
   W0-T2 and nothing catches it. Reasoned, not measured, and it is in NEXT.

5. **Stale bytes in freed pages.** After the run the byte scan on the copy is 0, so
   nothing survived in practice. I did not test the case where a rewritten payload frees
   a page whose old bytes are never overwritten. `PRAGMA secure_delete` would settle it
   and I did not turn it on, because it changes every delete in the system and that is a
   wider decision than this task.

6. **Not attempted: the real store.** The brief says the orchestrator runs `telltale
   resanitize` on `~/.telltale/telltale.db` after the merge. Nothing here touched it.

## NEXT

1. Run `telltale resanitize` on the real store after merge. Expect roughly the copy's
   numbers, larger by whatever the build has recorded since: 16 probe hits to 0, about
   70 seconds. Take a copy first; there is no undo.
2. Make a missing reducer registry an error rather than a silent no-op. `Store.rebuild`
   with `reducers == []` deletes the derived rows and writes none back, which is a data
   loss `purge` and `resanitize` both inherit.
3. Decide whether `PRAGMA secure_delete` belongs on the writer connection. It is the only
   thing that makes `purge` mean what an owner reads it to mean, and it is a measurable
   write cost that nobody has measured.
4. The scrub now runs on every normal form, so the `KNOWN_PROSE_PATH_FIELDS` exemption in
   test_privacy.py (a machine path surviving in `claude.hook.PostToolUseFailure.error`)
   is the last place a path reaches the disk unrewritten. That is a path rule, not a
   secret rule, and it is still open.

# EXPLAIN FOR THE OWNER

## Ten rows on your disk held a fake credential

Telltale records the commands an agent runs. It does not record them as typed. It
rewrites each one into a **normal form**: the program's name, a couple of subcommand
words, the option names, the file paths made relative to your repository, and an
underscore for everything else. `uv run pytest tests/test_calc.py -k zero` becomes
`uv run pytest tests/test_calc.py -k _`. The point is that two runs of the same command
produce the same string, while the search term, the filename and the message do not
survive.

On 2 September, after the backfill import, a scan of the database bytes for the fake
credentials the wave 0 experiments planted found ten rows that still held one. Every one
was a command. This explains how, what the fix is, and what it did not fix.

### First: what a shell token is, and why one can start with a dash

When you type a command, something has to decide where one argument ends and the next
begins. That job is called **lexing**, and the pieces it produces are **tokens**. Spaces
usually separate them, but quotes override that. So:

```
echo --- hello ---      is five tokens:  echo, ---, hello, ---
echo "--- hello ---"    is two tokens:   echo, "--- hello ---"
```

In the second line the quotes make one token out of eleven characters, spaces included.
That token's first character is a dash.

Now the rule Telltale was using. The design says: keep every token that starts with a
dash, throwing away anything after an `=`. The thinking was sound. An option name is a
fact about the work (`-k` means you targeted a test, `--check` means you asked for a
verification) and an option name is never a secret. So options were kept.

But the rule tested one character. It asked "does this token start with a dash", not
"does this token look like an option". A quoted string starting with a dash passed that
test, and the whole string was written down.

### The one real leaked command

Here it is, as it sits in four rows of your own launcher capture
`cap_01M1GRH92A2D99YWKC1MBF0FSC` (the stream, the two hooks and the OTel record for one
Bash call):

```
fixtures/sources/codex/0.150.1/rollout-import/2026/09/02 ) _ _ _ _ _ _ _ _ _ _ _ _ _ _
-----BEGIN TELLTALEFAKE PRIVATE KEY---
```

Read the underscores. The normalizer was working: `import` survived as a word, the
fixture directory survived as a path, a directory outside your repository became
`<outside>/e9671acd`, and everything else became `_`. Then the last part. That was a
line of a **heredoc**, a block of text handed to a command as its input, and the line
began with five dashes, so the dash rule kept it whole.

`TELLTALEFAKE` is not a real key. It is a marker string the wave 0 experiments planted
in a fixture file for exactly this purpose: a probe that cannot be a real secret and
cannot be mistaken for one, so that a test can prove the probe was removed. A test
against a fixture with no probe in it proves nothing. This was that probe doing its job,
one step later than intended.

The second version of the same failure reads even more plainly. From an imported
transcript:

```
echo --- sk-ant not TELLTALEFAKE --- ; grep -rho _ fixtures/sources/claude | sort -u ...
```

Somebody ran `echo "--- sk-ant not TELLTALEFAKE --- ..."` with the whole thing in
quotes. One token, first character a dash, kept.

### The fix, and why it is a shape and not a list

The rule is now a shape. After cutting at the first `=`, a token is kept only if it
looks like this: one or two dashes, then a letter or a digit, then up to 31 more
characters from letters, digits and `_ . : + -`.

Say it in words: an option is short, it starts with a letter after its dashes, and it
has no spaces in it.

`-k`, `-rho`, `--max-turns` and `--output-format` all pass. `--- sk-ant not TELLTALEFAKE
---` fails on the space. `-----BEGIN` fails because the third character is another dash
rather than a letter. Anything that fails becomes `_`.

I did not write a list of allowed options, and that is deliberate. A list is wrong the
day a tool adds a flag, and it is wrong in a direction you cannot see: the new flag
quietly becomes `_` and a measurement built on it goes quiet with it. A shape is wrong
only where the shape is wrong, and I can tell you exactly where that is, below.

### The second fault: a scrub that had never run

Telltale carries a set of patterns for things that look like credentials: AWS keys,
Anthropic keys, GitHub tokens, `Bearer` headers, private key headers. Any string it
keeps is checked against them, and a match becomes `<redacted:1>`.

The private key header is in that set, and has been since the sanitizer was written. It
did not fire on any of the ten rows. I read the code path rather than guessing at it:
the function that cleans a field handles commands FIRST and returns the answer
immediately, several lines above the line that scrubs. So a command was the one kind of
string that never reached the scrub. Not a weak pattern. No pattern at all.

That is now fixed, and where it runs matters. Commands are capped at 200 characters.
Four of the ten stored strings end `KEY---`, with the final dashes cut off by that cap,
and the pattern needs those dashes to match. So a scrub bolted on after the cap would
have fixed six rows and missed four. It runs before the cap.

This half is not merely a second line of defence. Paths inside your repository are kept
as written, so a credential in a filename or a URL was reaching the disk without ever
meeting a dash rule:

```
git clone https://x-access-token:ghp_TELLTALEFAKE0000@github.com/o/r
    stored, before:  git clone https:/x-access-token:ghp_TELLTALEFAKE0000@github.com/o/r
    stored, now:     git clone https:/x-access-token:<redacted:1>@github.com/o/r
```

Both halves are in the test suite, and I broke each one on its own and watched the
matching assertion fail before restoring it.

### What resanitize does, and what it leaves alone

The fix above stops new leaks. It does nothing about the rows already written, and those
are the rows that hold the probes.

There was already a way to remove data: `telltale purge <capture>` deletes a capture's
observations. It is the only deletion path in the system, and that is on purpose. Here
it was the wrong tool. Three of the ten rows sit in your own build's launcher captures,
which hold hundreds of model requests each; deleting the capture to remove one token
throws away everything the capture was recorded for. And it would not hold: the shape is
in any command that quotes an argument beginning with a dash, so the next import would
write it again.

So there is one new operation, `telltale resanitize`, and it is the only statement in
the codebase that CHANGES an observation rather than adding or deleting one. A
pre-commit hook now refuses that statement anywhere except store.py, exactly as an
older hook already refuses the INSERT statements elsewhere.

What it does, precisely:

- It reads the STORED normal form, never the original command. The original is gone; it
  was never written down, which is the whole point.
- It splits that stored string on spaces and applies today's rules to each piece. Every
  branch either keeps a piece or replaces it with `_`. It cannot put anything back.
- Then it scrubs, then it caps.
- If nothing changed, it writes nothing at all. The row keeps its old version label and
  its old redaction record.
- If something changed, it writes the new command, sets the version to `cmdnorm-v3`, and
  adds `resanitize:cmdnorm-v3` to the row's redaction list.
- One database transaction per capture, and one diagnostic row per capture saying what
  it did: `resanitize cmdnorm-v1 to cmdnorm-v3: 337 field(s) rewritten`.
- Then it rebuilds the capture's derived rows, which I will come back to.

What it does not touch: the row's identity, its timestamps, its capture, its
correlations, and any field that is not a command. And any row whose command the current
rules already agree with.

On a copy of your store it changed 21,725 command fields across 1154 captures in 69
seconds, and the byte scan went from 16 hits to 0. Run again, it changes nothing. That

### The bit I got wrong first, and what caught it

My first run left six hits behind. The observations were clean.

The six were in a different table. Telltale keeps two layers: the **observations**,
which are what a provider said and never change, and the **activities**, which are a
summary rebuilt from them. An activity for a shell command copies the normal form into a
field of its own, so rewriting the observation left the copy standing one table over.

The fix is not more rewriting. An activity is defined as rebuildable from observations,
so the answer is to rebuild, which `purge` already does after it deletes. `resanitize`
now does it too. I would not have found this by reading the code; the byte scan found
it, which is the argument for scanning bytes rather than querying rows.

### Two things this does not fix, stated plainly

**A short quoted argument that looks like an option is still kept.** `git commit -m
"-TELLTALEFAKE"` stores `-TELLTALEFAKE`. It is one dash, then letters, no spaces, under
32 characters: it is the same shape as `-m`, and no rule reading the normal form can
tell them apart. The credential patterns still run over it, so something shaped like a
GitHub token would be caught. Something shaped like a word would not. I put this case in
the test suite as an assertion rather than leaving it unsaid, so that anyone who later
believes the rule is airtight meets a test that says otherwise.

**`--` on its own is now `_`.** A bare double dash means "everything after this is a
filename, not an option". The shape refuses it, because there is no letter after the
dashes. That costs one small fact in `git diff -- pkg/calc.py`, and it changed one line
of one recorded fixture. I checked what it costs elsewhere by re-running the classifier
over all 88,754 stored commands: 21,477 of them change under the new rules, and none of
them changes what the command is classified as. Test runs are still test runs, git
commands still git.

### If you want to run it

Nothing has been done to your real store. Every number above is from a copy at
`/tmp/w2t8home`, made with `cp` and checked with SQLite's own integrity check.

There is no undo. `resanitize` removes information by design, and the original commands
do not exist anywhere to restore from. So:

```
cp ~/.telltale/telltale.db ~/.telltale/telltale.db.before-w2t8
uv run telltale resanitize
strings ~/.telltale/telltale.db | grep -c "TELLTALEFAKE\|sk-ant-api03-"
```

Expect the last line to print 0, and expect it to take about a minute and a half.
