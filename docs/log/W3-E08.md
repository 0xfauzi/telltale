# W3-E08: temporal validity on captured data

## OUTCOME

The experiment ran end to end on a copy of the owner's store and the answer is one word,
38 times: **not assessable**. Every pair failed the precondition design 6.12 sets before
any label may be written, and the failure is a property of the data rather than of the
machinery.

```
38 rows scored (36 per-capture pairs, 2 pooled), 0 valid placebos, 38 invalid
labels: {"not assessable": 38}
placebo runs that made persistence worse: median 2 of 10, range 0 to 8
median placebo persistence MAE over true-order persistence MAE: 0.8176
```

Shuffling the context makes persistence BETTER on this data, by 18 percent in the median
pair. Design 6.12 calls such a run invalid and refuses it a label, so the run that E07
labelled "baseline sufficient" 19 times is now labelled nothing at all.

**The brief's second STOP rule fired, and this report is it.** "Stop if any placebo run
reports persistence better under shuffle after you have confirmed the true rows were not
shuffled: report the pair and the numbers." It fired on the pilot pair, before anything
else was run, and it fires on all 38. The four confirmations are in WHAT WAS WRONG below,
with the numbers. I ran the remaining pairs after confirming the mechanism, because the
count of how many pairs behave this way IS the result, and stopping at one pair would
have left the experiment unable to say whether it had found a defect or a fact.

The pilot projected 49.6 minutes against a 90-minute stop threshold and the recorded
stages measured 2592.931 s (43.22 minutes); the wall clock including process start-up is
about 47 minutes.

## WHAT WAS WRONG

**The placebo makes persistence better on the real request clock, and the machinery is
not the reason.** This is the finding, and it is stated first because everything else in
the experiment is downstream of it. Four checks, each measured before any pair beyond the
pilot was run.

1. The true-order run was not shuffled. Persistence over the pilot pair's 157 retained
   origins, computed by hand from the series rows as the mean of `|y_o - y_{o-1}|`, is
   932.343949044586 tokens. The stored true-order run's persistence `mae_mean` is
   932.343949044586.
2. Only the context moved. Window for window across all 157, the placebo run carries the
   same `origin`, the same `actual` and the same `last_context` as its true-order twin.
3. The shuffle did reach the forecasters: the persistence POINT forecasts differ between
   the two runs, which can only happen if the last row of the context changed.
4. The data has no recency to destroy. Measured with no forecaster in the loop, over the
   same origins: the mean distance from `y_{o-1}` to the actuals is 932.343949044586
   tokens and from a uniformly chosen earlier row of the same context 784.4585987261147
   tokens, a ratio of 0.8413832679774284. Across all 36 pairs the median ratio is 0.9689,
   the random row is the better anchor on 20 of them, and the median lag-1
   autocorrelation of `output_tokens` is 0.0592.

`output_tokens` alternates between short tool-call turns and long text turns, so the step
from one request to the next is larger than the distance between two requests picked at
random. A shuffle that destroys recency therefore helps the one baseline whose whole
method is recency.

**Four of the brief's injected facts did not match the copy, and the copy is what was
used.**

| the brief said | measured on the copy |
|---|---|
| the store holds 3,209 captures | 3223 (`out/summary.json`) |
| `--clock attempt` gives 23 rows, `verification_passed` and `accepted` known on 18 | 29 rows, both known on 21 |
| `--clock change` gives 19 rows, the three path columns known on 4 | 23 rows, the three path columns known on 4 |
| at H = 1 the attempt clock has at most 7 origins and the change clock 4 | 13 and 7, by the same formula at the row counts above |

The direction of the conclusion is unchanged: 13 and 7 are both below k_min 20. The
counts differ because the store grew between the brief being written and the copy being
taken, which is the same reason E07's numbers and this run's differ.

**The change clock's first failing check is coverage, not windows.** The brief expected
the window count to be the refusal. It is the fourth line to fail. `subsystems_touched`,
`test_files_changed` and `dependency_delta` are `partial` (known on 4 of 23 rows), so
check (1) fails with 12 forecastable columns of 15 needed, and only then does check (2)
report 0 planned windows of 20.

**The ablation was not refused by an exception. It ran and produced nothing.** A and B
each retained 7 windows; C retained 0, because block C contains `edit_turnover_ratio`,
which is unknown on row 4, and the exclude policy drops every window that reads it. The
three variants share no origin, so the aligned set is empty. The printed report says
`origins common to A, B and C: 0  dropped for alignment: {'A': 7, 'B': 7, 'C': 0}` and
the verdict is `C diagnostic only (timesfm did not score in every variant)`.

**E07's `pairs()` can no longer be reused as it stands.** It iterates every entry of
`TARGETS`, which held three request-clock targets when E07 ran and now holds nine;
`backtest.registered` refuses a change-clock target on a request-clock series, and the
first entry in sorted order is now `attempts_to_land`, so E07's survey would raise on the
first pair of the first capture. E08 filters by the registry's own `clock` field.

**A first cut of `_repo_id` picked the wrong repository.** It took the repo_id carried by
the most captures, which on this copy is `0ee2033497...` with 762 captures: a disposable
fixture repository the test suite creates. It now reads `repo.identity(REPO_ROOT)`,
which is the function the launcher writes the field with. The value is
`d9f783b1d318c0d65ec6b86fe729f6ff1a3581983e4287a71f6510eb80d84d6c`, the sha256 of this
repository's root commit, carried by 45 captures on the copy.

**Two of the 17 pairs E07 and E08 share disagree, in the timesfm column alone.** 14 of
17 reproduce to the last bit, including tau and every baseline. `cap_01M1HE3ZCX...` gives
946.945378 where E07 recorded 947.960004, and `cap_01M1FW3DA7...` gives 1095.177935 where
E07 recorded 1094.849472; the windows, the tau and all five other forecasters are
identical in both. Repeating one of those backtests three times here gives
946.9453783222274 every time, so the model is deterministic in this environment and the
difference is between environments. E07's worktree was removed after its merge, so its
torch and timesfm versions cannot be read. The third disagreement is not a disagreement:
`cap_01M1HGVRCK...` went from 46 windows to 123 because that capture is the session that
ran E07, still recording while E07 scored it.

**`experiments/E08/run.py` reached 960 lines before it was split.** The file-length hook
fails a file that a commit ADDS already over 800. It is now four modules, cut where a
reader would cut them: what every stage needs, the request-clock stages, the pooled rows,
the lineage clocks.

## WHAT CHANGED

**`experiments/E08/shared.py`** holds what no stage can run without: the paths of the
copy, `point_home_at_the_copy` (which refuses when TELLTALE_HOME resolves to
`~/.telltale`), the JSON helpers, the forecaster factory and `constants`, which reads
every pre-registered number out of `telltale.forecast` rather than restating it. It also
imports E07's runner, and the ORDER of that import is load-bearing: E07's `run.py` reads
`SOURCE_DB` from TELLTALE_HOME at its own import time, so it has to be imported while
that variable still names the owner's store.

**`experiments/E08/run.py`** is six stages behind one `--stage` flag, each writing a file
under `out/` and each resuming from what the previous one wrote. That shape is the answer
to a constraint rather than a preference: a single call may not exceed 600 s, and the
whole run is about 47 minutes, so `--stage pairs --capture <ID>` runs one capture's pairs
per invocation and keeps an existing file rather than recomputing it. E07's `copy_store`,
`census`, `cohort_refusal`, `build_series`, `readiness_of`, `backtest_once`, `mae_table`
and `licenses` are imported and called, not copied.

**`experiments/E08/pooled.py`** concatenates every capture's retained windows per (target,
horizon) and scores them once, for the true order and for each of the ten placebo
orderings, reading the windows back out of the stored `forecast_runs` rows. One decision
here is mine rather than the design's: a pooled origin is re-keyed as
`origin + 1000000 * the capture's index`, because design 6.12 pairs a true window with
its placebo twin BY ORIGIN and origin 32 exists in every capture, so pooling without a
re-key would pair one capture's true window with another capture's placebo. The re-key is
recorded in every pooled file in the field `origin_rekey`.

**`experiments/E08/lineage.py`** builds both lineage clocks on the copy, runs readiness
for every registered target on each, records the printed checklist verbatim, and attempts
the ablation. Where the registry carries no target it computes design 6.12's check (2)
arithmetic and labels it as arithmetic: an upper bound on origins, never a verdict.

**`experiments/E08/aggregate.py`** computes the cross-run numbers the write-up states, and
two of them deliberately outside the forecasting machinery: the distance from the last
context row against the distance from a random one, and the lag-1 autocorrelation of the
target, both read straight off the series rows. If the machinery were wrong about
recency, these two would disagree with it.

**`experiments/E08/determinism.py`** re-runs one true-order backtest three times and
compares, which is what separates "the model stack differs between environments" from
"something here is not reproducible".

**`.gitignore`** re-includes E08's decision inputs for E07's reason: the store they were
computed from is the live capture database, which grew from 36 captures to 3223 between
the two runs. `census.json` is NOT re-included: it holds one row per capture and is 1.2
MB against the 500 KB `check-added-large-files` allows, so the counts the write-up quotes
from it were moved into `summary.json` instead.

## UNSURE OR NOT DONE

- **No `src/` defect was found, and one design reading deserves the owner's eye.**
  `placebo.paired` overrides the label to "not assessable" whenever the validity check
  fails, even when the baseline clause fired on the true-order numbers alone. That is
  what makes E07's "baseline sufficient" disappear here. Design 6.12 says a run whose
  placebo left persistence unharmed "is invalid", which supports the override; it does
  not say in so many words that the baseline branch, which needs no placebo, goes with
  it. The inequalities are still stored on the row, so nothing is lost, but if the owner
  reads 6.12 the other way the label for these 38 rows would be "baseline sufficient"
  and the code would need one change in `src/telltale/forecast/placebo.py`. Command that
  shows it: `uv run --extra forecast python experiments/E08/aggregate.py`, key
  `e07_baseline_only_labels`, which re-runs E07's half-rule on this run's stored rows and
  gets 35 "baseline sufficient" and 1 "not baseline sufficient at this n, placebo
  pending".
- **`placebo.sentinel` counts all ten runs, and design 6.12's placebo is the block
  shuffle.** The reading guide says the B = 1 control "is reported and is not part of the
  rule", but the validity check requires every one of the ten to be worse. It changes
  nothing here, which is measured rather than assumed: no row reaches 5 of 5 on the block
  runs alone, and the highest any row reaches is 4 (`out/aggregates.json`, key
  `n_valid_block_only`). On a dataset where the two disagreed it would matter.
- **This result is about one target on one provider.** `output_tokens` is the only target
  that passed readiness anywhere, in E07 and again here. Whether `fresh_input_tokens`
  carries recency cannot be answered from this run, because it fails the variation check
  on most captures and the window count on the rest. Whether a Codex request clock
  behaves the same way is unknown: the cohort is one provider by design 6.12's own rule.
- **The pooled rows are not stored as `forecast_runs`.** A pooled row is not a series and
  `store.py` hangs a run on a series_id, so the pooled numbers live only in
  `out/pooled/*.json`, each naming the stored run ids its windows came from. E07 made the
  same choice for the same reason.
- **This session's own capture is in the cohort and contributes nothing.**
  `cap_01M1HY0FD19ATJXFCK6Y114T9D` (W3-E08) had 27 model requests at the moment the
  snapshot was taken and fails the window check at 0 of 20. A later run of this
  experiment will include it properly, and will therefore not reproduce these numbers.
- **E07's spread tables were not recomputed.** Skill, calibration flags, WQS and lead
  time are all in the stored runs and in the per-pair files, but this experiment's
  question was the placebo, and no aggregate of them is quoted. `out/aggregates.json`
  carries what the write-up states and no more.

# EXPLAIN FOR THE OWNER

## The thirty seconds

We asked the machine to forecast how many tokens the next model request in a session
would produce, and then we asked the one question that decides whether the answer means
anything: does the forecast depend on the ORDER the requests happened in? The answer is
no, on every one of the 38 things we measured. That is not a bug and it is not a failed
experiment. It is the laboratory refusing to let us say a thing that would have sounded
impressive and been false.

## What a control is, and what this one destroys

Start with the problem rather than the machinery.

Suppose a forecaster predicts the next request's output-token count better than the crude
rule "say whatever it was last time". You will read that as "it learned how a session
unfolds". But there are other explanations, and the table cannot tell them apart. Maybe
it learned the typical SIZE of a request in this session, which is a fact about the
spread of the numbers and not about their sequence. Maybe it learned that this column
tracks another column. Neither of those is knowledge about time.

The way to separate them is to run the identical test again with the past scrambled. If
the forecaster was reading the order, scrambling destroys what it was reading and the
score collapses. If it was reading the level, scrambling changes nothing, because a
shuffled history has the same level.

The scramble has to destroy the order and nothing else, or you have tested two things at
once. So it cuts the past into consecutive blocks of two whole rows and shuffles the
blocks. That choice preserves three things on purpose.

**It keeps every row intact.** A row of this clock is one model request: its fresh
tokens, its cached tokens, its output tokens, its tool calls, all measured at the same
instant. Shuffling the columns separately would destroy the order AND the fact that these
numbers belong together.

**It keeps the question.** The row being forecast, its true value, and where in the
history we stopped are untouched. Only the material the forecaster is allowed to look at
moves. That is what lets us compare the two runs at the same place in the history rather
than comparing two different experiments.

**It keeps an alarm.** Among the crude rules is "persistence": say whatever the last row
said. It reads exactly one row of the past, the most recent one. If the scramble reached
the forecasters at all, it moved that row. So persistence must get worse. If it does not,
either the scramble never arrived, which is a bug, or the most recent row was never
special, which is a fact about the data. Either way the control has controlled for
nothing and no conclusion may be drawn from the run.

## What happened when we ran it

Persistence got BETTER.

Here is the pilot pair in full: capture `cap_01M1HE3XS4E3S2XTSNB99C7WQT`, the session that
did task W2-T6, forecasting output tokens one request ahead over 157 separate tests. The
numbers are mean absolute error in tokens, so lower is better.

```
ordering        seed   persistence
true            -      932.34
placebo_block   0      786.83
placebo_block   1      674.30
placebo_block   2      691.73
placebo_block   3      1059.70
placebo_block   4      1059.70
placebo_row     0      698.92
placebo_row     1      686.06
placebo_row     2      711.46
placebo_row     3      802.99
placebo_row     4      802.99

validity: 2 of 10 placebo runs worse -> INVALID
```

Eight of the ten scrambles made "say whatever happened last time" MORE accurate. The
report writes no label and says why.

Before believing that, I checked the four things that could have made it an artefact, and
each check is a number rather than an argument.

**Did we accidentally shuffle the true run too?** Persistence over those 157 tests, worked
out by hand from the stored rows with none of the forecasting code involved, is
932.343949044586 tokens. The stored run says 932.343949044586. They are the same to
twelve decimal places, so the true run saw the true order.

**Did only the past move?** For all 157 tests, the scrambled run records the same stopping
point, the same right answer, and the same "value of the previous row" as the true run.

**Did the scramble reach the forecasters at all?** Persistence's actual predictions differ
between the two runs, which can only happen if the last row of the material it was given
changed.

**Then why is a shuffled past better?** Because on this data the most recent request is
not a good guide to the next one. Measured with no model at all, over the same tests: the
average distance from the previous request's output tokens to what actually came next is
932.34 tokens; the average distance from a request picked at random out of the same
history is 784.46. Across all 36 pairs the median of that ratio is 0.97, and the lag-1
correlation of the column has median 0.06, which is another way of saying the same thing.

The reason is visible in the sessions themselves. A model request that fires a tool
returns a handful of tokens. A request that writes an explanation returns thousands. The
two alternate. So consecutive requests are FURTHER apart than two requests picked at
random, and "what happened last time" is a worse anchor than "what happens around here in
general". A shuffle hands persistence a random row, and a random row is the better bet.

## One pair walked through all four labels

Take the same pilot pair and ask what the rule would have said at each branch. Five
numbers do the work: E_M is the model's average error in true order, E_B the best of the
four crude rules, E_P the model's average error on scrambled pasts, W_MB the share of the
157 tests where the model beat the best crude rule, and W_MP the share where the true
order beat its own scrambled twin. Two thresholds were fixed before any of it ran: a
margin of 10 percent and a share of 60 percent.

```
E_M 689.73   E_B 670.35 (rolling_median)   E_P 661.54   W_MB 0.4968   W_MP 0.5605
```

**Not assessable** is where it actually lands, and it lands there for the reason above:
2 of 10, so the control failed. Nothing else is read.

**Baseline sufficient** is what it WOULD have been if the control had passed, and this is
worth seeing because it is E07's answer. The first clause asks whether the model beat the
best crude rule by more than 10 percent: 689.73 against a bar of 603.31, so no, it did
not. The second asks whether it won on more than 60 percent of the 157 tests: 0.4968, so
no. Either clause alone is enough to say a one-line rule did as well, and both hold. E07
labelled all 19 of its pairs this way, and re-running E07's half of the rule on this
run's stored numbers reproduces it: 35 of these 36 pairs come out "baseline sufficient".

**Temporal evolution** is the label that would license saying the model uses the sequence.
It needs the model to beat the crude rules first, which this pair did not, and then to
beat its own scrambled twin by 10 percent and on 60 percent of the tests, and to do both
in the first half of the history and in the second half separately. This pair fails at
the first hurdle, and would fail later anyway: E_P is 661.54, which is BELOW E_M, so the
model is better with the past scrambled than with it intact.

**Conditional prediction** is the label for a model that beats the crude rules for a
reason that is not the order: it reads something real in the window, and the gain survives
a shuffle. Where there are no other columns in play the report is required to add "level
prediction: the gain is distributional", which is the honest name for "it learned how big
these numbers usually are". If the control here had passed and the model had beaten the
baselines, this is where the pair would have landed, because E_P is not worse than E_M.

One pair is worth adding, because it is the only one of the 36 where the crude rules did
NOT win: task W2-T8, four requests ahead, 20 tests. There the model scored 631.81 against
the best crude rule's 731.80 and won 60 percent of the tests, which clears both clauses.
It is also the pair with the most recency in it: the distance from a random row is 2.21
times the distance from the last row, the opposite of the pattern everywhere else. And its
control still failed, at 7 of 10 rather than 10 of 10. So even the one pair where the
question got interesting cannot be answered at this number of tests.

## Why "not assessable" on the other two clocks is a count

The request clock is one row per model request, so a long session gives hundreds of rows.
The other two clocks are coarser. The attempt clock is one row per attempt at a task: this
repository has 29. The change clock is one row per change landed: 23.

The rule needs 20 separate tests before it will say anything, and a test needs a run-up of
16 rows of history before it. So the arithmetic is fixed before any data is looked at:

```
attempt clock, 1 step ahead:  29 rows - 16 run-up - 1 = 13 tests, against 20 needed
change clock,  1 step ahead:  23 rows - 16 run-up - 1 =  7 tests, against 20 needed
change clock,  4 steps ahead:                            1 test,  against 20 needed
```

Twenty tests at one step ahead would need 36 landed changes. We have 23. That is the whole
of it: no model ran, nothing failed, and the honest report is a subtraction anybody can
check. The alternative would have been to lower the 20, which is the one move the
pre-registration exists to prevent: a threshold changed after seeing that the data misses
it is not a threshold.

There are two further facts underneath that count, and both are worth knowing.

The attempt clock has no registered target at all. The registry of things that may be
forecast holds three request-clock columns and six change-clock columns and nothing on the
attempt clock, so there is no checklist to run there. I did not add one: registering a
target is a decision that changes what the laboratory is allowed to be asked, and it
belongs to whoever writes the next brief.

The change clock fails a check before it gets to the count. Three of its columns
(subsystems touched, test files changed, dependency changes) are known on 4 of its 23
rows, because they need per-file paths that commits only started carrying when W3-T4
landed. And the column the ablation would have forecast, "attempts to land", is the same
number on all 23 rows, so there is nothing in it to predict. The checklist prints both,
with the numbers, and refuses.

## The one thing to be sceptical of

This is a result about one column, on one provider, in one repository's sessions. Output
tokens on a Claude Code request clock has no useful lag-1 structure. That is measured, and
it is measured twice by two methods that do not share code. What it does not tell you is
whether some other column of the same clock does, whether a Codex session behaves the
same, or whether a coarser clock would show structure the fine one hides. Those need
different data, not a different reading of this data.

What the run did establish, and it is not nothing, is that the control works on real
input. It caught the one thing it exists to catch, on the first pair, before a single
label had been written, and it kept the system from repeating a claim that would have been
comfortable, publishable and wrong.
