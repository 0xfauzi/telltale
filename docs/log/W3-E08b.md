## WHAT WAS WRONG

**The validity check reached a label in two places, and the one that fired was the wrong
one.** `decide._label` already tried "baseline sufficient" before it looked at any placebo
term, so the rule module was right on its own. The refusal lived outside it, in
`placebo.paired`, which called `decide` and then overwrote its answer:

```python
found = decider.decide(true_run, placebos, model)
if not check["valid"]:
    found = replace(found, label=decider.NOT_ASSESSABLE, reason=check["reason"])
```

An override that can only disagree with the module holding the rule is not a second
opinion, it is a second rule. E08's write-up flagged it as a reading the owner should
decide (`docs/log/W3-E08.md`, UNSURE OR NOT DONE, first entry) and the owner chose option
(b) at the wave 3 gate on 2026-09-02. The fix is that `decide` now takes the verdict and
`placebo.paired` takes no view.

**Every place the check could reach a label, and what each one is now.** Searched with
`grep -rn valid src/telltale/forecast/ src/telltale/cli_forecast.py`, 11 hits before the
change:

| where | what it does | after |
|---|---|---|
| `placebo.py` docstring, "Persistence MUST get worse" | prose stating the refusal | says what the refusal costs: the two labels that read the placebo, and nothing else |
| `placebo.INVALID` (line 70) | the warning on every run of an invalid pair | same warning, tail reworded: it no longer claims "no label is written from it" |
| `placebo.sentinel` (5 hits) | computes `valid` | unchanged |
| `placebo.paired` line 250 | the override | deleted; the verdict is passed to `decide` |
| `placebo.paired` line 256 | appends INVALID to run warnings | unchanged |
| `placebo.report` lines 281, 284 | prints `-> valid` or `-> INVALID` | unchanged |
| `cli_forecast.py` | no hit | see below |

**`cli_forecast.py` needed no change, and that is a measurement rather than an oversight.**
`grep -n "valid" src/telltale/cli_forecast.py` returns nothing. The one decision line the
CLI prints itself is in `forecast_backtest` (line 179), and it is the NO-placebo case, not
the invalid-placebo case: a backtest with no control at all. The amendment says nothing
about that case and I did not extend it to cover it. `forecast placebo` prints
`placebos.report`, which renders the Decision, so the new label and its warning reach the
terminal without a line changing: the warning arrives as `note: placebo invalid: the
positive labels were not assessable`, asserted in the first of the two new tests.

**`decide._label` went over the complexity limit and had to be split.** Adding the one new
branch took it from 14 to 17 against complexipy's limit of 15 (measured, `uv run complexipy
src/telltale/forecast/decide.py`). The two branches that READ the placebo are now
`decide._temporal`, which is where a reader would cut it anyway: `_label` is the part of
the rule that needs no control and `_temporal` is the part that does. `_label` is 10 and
`_temporal` is 5.

**A fixture had to be built for the second test, because the obvious one cannot exist.**
The test needs a run where the control failed AND the model beat the baselines. The
natural fixture is independent draws, which have no recency for a shuffle to destroy, but
W3-T2 already measured that no multiset-reading forecaster clears delta on i.i.d. data:
best ratio 0.932 over 13 distribution families and 8 seeds (design 6.12 wave 3 amendments).
So the fixture alternates between two levels. Persistence predicts `y_{o-1}`, which on an
alternating series is always the other level, so its true-order score is the worst the
series can hand it and no permutation can beat it: 0 of 10 placebo runs come out worse, by
construction rather than by the luck of a seed. A forecaster reading `y_{o-2}` is exact,
so the baseline clause does not fire.

# EXPLAIN FOR THE OWNER

## Why you are reading this

E08 measured something real and then could not tell you about it. This change makes it
able to. Nothing about the data moved, no model ran, and the one sentence the laboratory
gained is a modest one: the forecaster does not beat a rolling median.

## Two questions, and only one of them needs a control

Start with what the laboratory is actually asked.

A forecaster produces a number. There are two different things you might want to know
about that number, and it is worth seeing that they are different before any machinery
appears.

The first question is: **is this better than something trivial?** You take four one-line
rules, run them on exactly the same history, at exactly the same moments, against exactly
the same right answers, and compare. That is a race, and both runners are on the same
track. If the model loses, it loses; there is nothing else to check.

The second question is: **is it better BECAUSE it read the order of the past?** That one
is harder, because a forecaster that has simply learned how big these numbers usually are
will also beat a bad baseline, and the table cannot tell the two apart. So you run the
identical test again with the history scrambled. If the model was reading the order, the
scramble destroys what it was reading and the score collapses. If it was reading the
level, nothing changes.

The scrambled run is the control. And a control needs its own check, because a control
that did nothing proves nothing. The check is a small alarm: among the four one-line rules
is "persistence", which says the next value will be whatever the last one was. It reads
exactly one row, the most recent. Scramble the history and that row changes, so
persistence must get worse. If it does not, either the scramble never arrived or the most
recent row was never special.

On E08's data, persistence got BETTER. On all 38 measurements. That is the finding, it was
checked four ways, and it stands.

## What that failure should cost, and what it was costing

Here is the whole of the change, in one row of real numbers.

The row is capture `cap_01M1HE3XS4E3S2XTSNB99C7WQT`, the session that built task W2-T6,
forecasting output tokens one request ahead over 157 separate tests. Errors are in tokens,
lower is better.

```
the race, in true order
  the model (TimesFM-3)                  689.7284
  the best one-line rule (rolling median) 670.3471
  the bar the model had to clear          603.3124   (10 percent better than the rule)
  share of the 157 tests the model won      0.4968   (it needed 0.60)

the control
  persistence, true order                 932.3439
  persistence, scrambled (median of 10)   749.1465   BETTER, so the control failed
```

Read the top block on its own. The model needed to come in under 603.31 and came in at
689.73. It needed to win 60 percent of the 157 tests and won 49.68 percent. It lost the
race twice over, and every number in that block was measured on the true-order history:
the scrambled runs contributed nothing to any of them.

Now the point. Under the rule as it stood, the failure in the bottom block erased the top
block. The verdict was "not assessable", meaning we may not tell you anything, including
that the model lost a race the scramble never touched.

That is what the amendment fixes. The failed control now costs exactly the two verdicts
that read it and nothing else. This row is "baseline sufficient", and it carries the
warning "placebo invalid: the positive labels were not assessable", so the thing that
failed is still on the face of the result.

## The one row where it changes nothing

That single row is why the amendment is not just a relaxation. It is the case where the
rule still refuses, and it is the only one of the 38 where the model was interesting.

## Why the rule had to be written down first

This is the part that has nothing to do with forecasting.

I already knew, before writing a line of code, roughly what the amended rule would say
about these 38 rows. E08's own aggregate said 35 of 36 would come out "baseline
sufficient". So I could have written the code, run it, seen the answer, and then written a
rule that produced it. Nobody would have been able to tell from the repository which order
it happened in, and the resulting number would be worth nothing: a threshold chosen after
seeing which side of it the data fell on is not a threshold.

So the order is in the repository as a fact rather than a claim. The amendment went into
the design document and into the code, and was committed, as
`a351cac6030ab415bc83cdc0082372f70a3bf7e6`. Only then was
`experiments/E08b/run.py` written. When it ran, it asked git which commit last touched the
file holding the rule, and wrote the answer into its output: `rule_commit a351cac...`, and
beside it the commit the tree was sitting at when the numbers were made, `head a351cac...`.
Same commit. The numbers were produced from a tree that was exactly the pre-registered
rule and nothing else.

And the prediction was stated before the run, in the write-up, in the section above the
results: 35 of 36, plus whatever the two pooled rows do. Measured: 35 of 36, and both
pooled rows came out "baseline sufficient", for 37. If it had come out 30, that would have
been a finding about the code and I would have had to report it as one rather than adjust
anything.
