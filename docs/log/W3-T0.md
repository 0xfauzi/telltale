# W3-T0 reads that scale with the capture; refused calls are not test runs

## OUTCOME

Four things landed, and every acceptance number in the brief was met.

1. **`telltale vector` on the owner's store: 11.13 s to 0.85 s**, output byte-identical.
   The acceptance was under 1.0 s. At 36 captures it is 0.030 s against a 0.245 s
   baseline, well inside the "within 2x" bound.
2. **A refused tool call is no longer a test run.** All five W2-E05 pilot captures now
   report `agent_test_runs 0, failed_test_runs 0, refused_tool_calls 3`. They reported
   3 and 3 before, for tests that never started.
3. **Stream-only captures report all four token counters.** A fake-agent capture's
   `cache_read_tokens` went from null to 15000 at coverage `observed`.
4. **The importer's diagnostics say what they are.** `importer: unparsed line kind
   <kind>: <n>`, which stops 1696 rows on the owner's store reading like queue loss.

All gates green: mypy, ruff check, ruff format, deptry, `pytest -m integration`
(172 passed), and `pre-commit run --all-files`. Three commits, as briefed.

## WHAT WAS WRONG

### The cohort scan read the whole database to compare four fields

A percentile needs a cohort, and design 6.11 defines one as every capture sharing four
keys: provider, runtime major version, model and content level. `cohorts._members`
called `cohort_keys` once per capture in the database, and `cohort_keys` read that
capture's **whole** observation list and **whole** activity list to pull four fields out.

Measured on a copy of the owner's store (3200 captures, 1044858 observations, 1.43 GB),
on 2026-09-02:

```
$ time uv run telltale vector cap_01M1HKTJB8C34SPHQYAQMHGF4W   # TELLTALE_HOME=<copy>
uv run telltale vector ... 8.74s user 1.43s system 91% cpu 11.134 total
```

Where the time went, measured by timing the reads `_members` runs:

```
captures():      0.517s  n=3200
activities():    2.302s  (344607 rows returned, 9684 of them wanted)
observations():  6.296s  (1044858 rows returned, 3247 of them wanted)
```

The query plans of those statements, before:

```
sqlite> EXPLAIN QUERY PLAN SELECT * FROM captures ORDER BY first_ts DESC;
|--CO-ROUTINE captures
|  |--SCAN o USING INDEX obs_by_capture
|  |--CORRELATED SCALAR SUBQUERY 3
|  |  `--SEARCH f USING INDEX obs_by_capture (capture_id=?)
|  `--CORRELATED SCALAR SUBQUERY 4
|     `--SEARCH f USING INDEX obs_by_capture (capture_id=?)
|--SCAN captures
`--USE TEMP B-TREE FOR ORDER BY

sqlite> EXPLAIN QUERY PLAN SELECT * FROM observations WHERE capture_id = ?
   ...> ORDER BY observation_id;
`--SEARCH observations USING INDEX obs_by_capture (capture_id=?)

sqlite> EXPLAIN QUERY PLAN SELECT * FROM activities WHERE capture_id = ?
   ...> ORDER BY started_at, activity_id;
|--SEARCH activities USING INDEX activities_by_capture (capture_id=?)
`--USE TEMP B-TREE FOR LAST TERM OF ORDER BY
```

Every plan is correct. Nothing is missing an index. The cost is entirely that the reads
return every row of every capture, and the caller throws almost all of them away.

The DDL the brief asked me to check and paste (`sqlite3 <copy> .schema observations`),
before the change:

```sql
CREATE TABLE observations (
  observation_id TEXT PRIMARY KEY, capture_id TEXT NOT NULL,
  observation_type TEXT NOT NULL, surface TEXT NOT NULL, provider TEXT NOT NULL,
  adapter TEXT NOT NULL, provider_session_id TEXT, provider_ts TEXT,
  ingest_ts TEXT NOT NULL, environment_fingerprint_id TEXT, repo_id TEXT,
  schema_version INTEGER NOT NULL,
  correlation_ids TEXT NOT NULL CHECK (json_valid(correlation_ids)),
  payload TEXT NOT NULL CHECK (json_valid(payload)),
  redaction TEXT NOT NULL CHECK (json_valid(redaction))
) STRICT;
CREATE INDEX obs_by_capture ON observations (capture_id, observation_id);
CREATE INDEX obs_by_session ON observations (provider_session_id);
CREATE INDEX obs_by_type ON observations (observation_type);
```

So an index on `observation_type` alone existed; one on `(observation_type, capture_id)`
did not.

### A refused tool call was counted as a failed test

W2-E05 ran five headless sessions against one task. Every one reports
`agent_test_runs 3` and `failed_test_runs 3`, and no test ever ran. `claude -p
--permission-mode acceptEdits` auto-accepts edits and nothing else, so each session's
Bash calls raised a permission request with nobody at the keyboard.

The reason the reducer could not tell is narrow. A permission denial arrives as a
tool_result carrying `is_error: true`, and `activities._tool_outcome` read `is_error` as
one of its three routes to `success`. A refused call and a failing test had one spelling.

The distinction was in the capture the whole time, on the stream, in two shapes:

```
$ sqlite3 <copy> "SELECT correlation_ids FROM observations
    WHERE capture_id='cap_01M1HKD4YPR80ZR2GVPNGTJ8AR'
    AND observation_type='claude.stream.system.permission_denied';"
{"message_uuid":"82123f23-...","session_id":"2761a993-...","tool_use_id":"toolu_01FuTVLfzyn1bQkwTrbwpUJM"}
{"message_uuid":"6bc1e4f4-...","session_id":"2761a993-...","tool_use_id":"toolu_01TFmpACvuVFtd36x8svMadr"}
{"message_uuid":"11c442dc-...","session_id":"2761a993-...","tool_use_id":"toolu_01Xs6simWrFQqhL1iV3m8M7q"}

$ ... claude.stream.result payload:
"permission_denials": [
  {"tool_name": "Bash", "tool_use_id": "toolu_01FuTVLfzyn1bQkwTrbwpUJM"},
  {"tool_name": "Bash", "tool_use_id": "toolu_01TFmpACvuVFtd36x8svMadr"},
  {"tool_name": "Bash", "tool_use_id": "toolu_01Xs6simWrFQqhL1iV3m8M7q"}
```

Both shapes are read, and that is a measurement rather than caution. Four of the five
pilot captures carry three of each. The fifth carries three `permission_denied` messages
and **no `claude.stream.result` observation at all**:

```

cap_01M1HKDEVQYAZ7B713281DYG8V  denied_msgs=3  result_list=3

```

Reading the result alone would have left that capture reporting three failed test runs.

Across the whole store, the `permission_denials` key is present and empty on 25 result
messages, non-empty on 4 and absent on 3. Its presence is not a marker; its contents are
the fact.

### Two token counters were null because of a spelling

`correlate.USAGE_KEYS` spells the four counters as the OTel `api_request` record does.
The stream spells two of them `cache_read_input_tokens` and
`cache_creation_input_tokens`. `STREAM_USAGE_KEYS` has recorded that since W2-T1, but
only `conflicts()` read it. So a capture with no OTel surface reported two of its four
counters as null while the numbers sat in the stored payload.

### The importer's drops read like the receiver's

The importer writes a diagnostics row of kind `dropped` for each transcript line kind it
does not parse. `dropped` is also what the store writes when its bounded queue loses
records. Those are opposite facts: one is a file this parser was never written to read,
the other is data the recorder was handed and failed to keep. 1696 rows on the owner's
store carried the first meaning under the second one's name.

## WHAT CHANGED

### 1. Typed reads, one new index, and a smaller scan

**`Reads.observations(capture_id, types=...)`** and **`Reads.activities(capture_id,
types=...)`** return only the row types a caller names. **`Reads.observations_of_type`**
asks the same question of the whole store.

One new index, in `schema.py`, and no line added to `store.py`:

```sql
CREATE INDEX IF NOT EXISTS obs_by_type_capture
  ON observations (observation_type, capture_id);
```

An existing store gets it on next open, because `Store.open` runs the whole DDL and
every statement in it is `IF NOT EXISTS`. Building it on the owner's store took 1.03 s,
once.

**The plan will not use it unless you take the sort away from the other index.** This
was the one surprise. With a plain `ORDER BY observation_id`, SQLite keeps choosing
`obs_by_capture` because that index answers the sort for free, and it does this even
when a type filter makes the other index far better. Measured, 3200 two-type reads:

```
IN (?, ?) ORDER BY observation_id
   plan: SEARCH observations USING INDEX obs_by_capture (capture_id=?)
   0.266 s
IN (?, ?)                          (no ORDER BY)
   plan: SEARCH observations USING INDEX obs_by_type_capture (observation_type=? AND capture_id=?)
   0.026 s
IN (?, ?) ORDER BY +observation_id
   plan: SEARCH observations USING INDEX obs_by_type_capture (observation_type=? AND capture_id=?)
         USE TEMP B-TREE FOR ORDER BY
   0.027 s
```

I tried three other ways to keep both the ordering and the index before settling on the
unary plus, and all three failed:

- a three-column index `(observation_type, capture_id, observation_id)`: the planner
  still chose `obs_by_capture`, 0.268 s. It also costs 1.94 s to build instead of 1.03 s.
- wrapping the filter in a subquery and sorting outside: SQLite flattens it, 0.270 s.
- `INDEXED BY obs_by_type_capture`: it works (0.029 s) and it makes the index a hard
  requirement, so a read on a store whose DDL had not run would raise instead of being
  slow. I judged that too sharp an edge for a recorder.

The plans after the change, on the copy:

```
sqlite> EXPLAIN QUERY PLAN SELECT * FROM observations
   ...> WHERE observation_type = 'telltale.environment'
   ...> ORDER BY capture_id, observation_id;
|--SEARCH observations USING INDEX obs_by_type_capture (observation_type=?)
`--USE TEMP B-TREE FOR LAST TERM OF ORDER BY

sqlite> EXPLAIN QUERY PLAN SELECT * FROM observations WHERE capture_id = ?
   ...> AND observation_type IN (SELECT value FROM json_each(?))
   ...> ORDER BY +observation_id;
|--SEARCH observations USING INDEX obs_by_type_capture (observation_type=? AND capture_id=?)
|--LIST SUBQUERY 1
|  |--SCAN json_each VIRTUAL TABLE INDEX 1:
|  `--CREATE BLOOM FILTER
`--USE TEMP B-TREE FOR ORDER BY

sqlite> EXPLAIN QUERY PLAN SELECT * FROM activities WHERE capture_id = ?1
   ...> AND (?2 IS NULL OR activity_type IN (SELECT value FROM json_each(?2)))
   ...> ORDER BY started_at, activity_id;
|--SEARCH activities USING INDEX activities_by_capture (capture_id=?)
|--LIST SUBQUERY 1
|  |--SCAN json_each VIRTUAL TABLE INDEX 1:
|  `--CREATE BLOOM FILTER
`--USE TEMP B-TREE FOR LAST TERM OF ORDER BY
```

Typed reads alone were not enough. With them the vector still took 2.6 s, because the
scan still opened two reads per capture for all 3200 captures. The rest of the win is
one idea: **content level is the only cohort key readable for every capture at once.**
It lives in the `telltale.environment` payload and nowhere else, so a capture with no
such observation has no content level, and `_matches` compares an int against None and
refuses. `cohorts._candidates` reads that one observation type across the store in a
single statement and returns the captures whose level matches. On the owner's store, 47
captures carry the observation at all, so the four-key read now runs 47 times instead of
3200. It is the same gate `_matches` already applied, taken before the expensive reads
rather than after, and `_level` is the single spelling both use so the two cannot drift.

`cohort_keys` also stopped computing the model names when the environment fingerprint
already named a model, because the answer is unused in that case.

**The timings, both stores, both branches of the code, same database each time.**

Owner's store copy, 3200 captures, 1044858 observations:

```
before:  11.134 s wall     9.70 / 9.71 / 9.90 s in process
after:    0.85 s wall      0.31 / 0.31 s in process
output:  byte-identical (diff of the two `telltale vector` runs is empty)
```

36 captures, 30708 observations, which is the shape W2-T4 measured (36 captures, 30715
observations, `vector` 0.245 s of which 0.225 s was the scan):

```
before:  0.228 / 0.196 / 0.202 / 0.200 / 0.199 s
after:   0.035 / 0.031 / 0.032 / 0.031 / 0.030 s
```

That store was built by 36 real `telltale run` captures of the scripted agent, then
grown to W2-T4's row count by posting E01's own recorded S1 OTLP body, with its
logRecords repeated, into each capture through a real receiver.

**The cost of the fifth index, on the writer.** Measured, 50000 inserts in 500-row
transactions, best of three: 0.234 s with four indexes, 0.274 s with five. That is
+16.8%, or 0.8 microseconds per observation, and it is paid on the writer thread rather
than the request thread that answers the agent.

### 2. A refused call is a refused call

`correlate.ROLES` gains `claude.stream.system.permission_denied -> permission_denied`.
`activities._denials` collects the refused tool_use ids from both shapes, keeping the
observation that named each one so the field it decides carries a source.

A refused call:

- gets `outcome: "refused"` and `executed: false` in its fields, sourced on that
  observation;
- is never typed `verification_run`, because design 6.10 defines one as a command that
  ran a check;
- **keeps its category**. The agent did ask to run a test, and dropping that would be a
  second kind of wrong.

`agent_test_runs` and `failed_test_runs` count `verification_run` activities, so they
now count executed runs by construction. I did not add a second filter in
`measures_spec13.verification`: it would be unreachable, and a check that cannot fail is
a check that stops being true without anybody noticing.

`refused_tool_calls` is a new derived Evidence in the summary's **work** block. It is
NOT in the spec 13.7 vector, which stays at 22 entries (`test_the_vector_is_22_entries`
still passes unchanged).

Its coverage needed a decision. There is no `permission_denials` capability in any
provider's CAPABILITIES table, so there was nothing to read. I keyed it on the provider
rather than on the surface name, because a Codex capture also delivers a surface called
`stream` (the exec stream) and nothing has ever measured a Codex permission denial on
it. Keying on the name alone would have reported 0 refusals for a provider Telltale has
never looked at. So the count is `unavailable`, and therefore null with a warning, for
Codex. The table lives in `measures_spec13.py` beside the number it decides, and it
reads the coverage block first so a real capability of that name would win.

`fake_agent.py --deny` reproduces the whole thing for no tokens. It adds one Bash call,
`uv run pytest`, and has it refused rather than run. A test command on purpose: that is
what separates "0 test runs and 1 refused call" from "1 failed test run".

The stream line's shape was recovered from the store rather than guessed. The stored
observation's payload is `{}`, but its `redaction` names every field the allowlist
dropped, and `provider_ts` is null:

```json
{"dropped":["tool_name:unknown","tool_use_id:unknown",
            "decision_reason_type:unknown","message_uuid:unknown"],
 "redacted":[],"truncated":[]}
```

Read with `_STREAM_CONSUMED` in `providers/claude.py`, that gives the raw line exactly:
`type`, `subtype`, `uuid`, `session_id`, `tool_use_id`, `tool_name`,
`decision_reason_type`, and no `timestamp`. The tool_result text came from the E05
transcript, read only:
`{"type":"tool_result","content":"This command requires approval","is_error":true,...}`.

### 3. Usage keys

`correlate.usage(payload, name)` reads the OTel spelling first, because a request the
OTel surface saw is measured by it and the stream's per-message numbers are the weaker
source, then the stream spelling. Absent under both is still None.
`activities._request` and `_attributed` both go through it.

### 4. Importer wording

`importer: unparsed line kind <kind>: <n>`. The `kind` column stays `dropped`, because
the vocabulary is a CHECK constraint and a seventh word is a migration.

### 5. Design amendments

`docs/design/01-design.md` gains an "Amendments from wave 3" section with 6.5 (typed
reads and the ORDER BY trap), 6.10 (refused calls) and 6.11 (`refused_tool_calls`).

## UNSURE OR NOT DONE

**A refused Read or Edit still becomes a `file_read` or a `file_edit`.** The brief
scoped this to verification runs and I kept to that scope. But the same argument applies
one type over: a refused Read did not read a file, and `unique_files_read` counts it. In
this build's data the question is untested, because all three W2-E05 refusals and the
fake agent's are Bash calls, so I have no capture where it happens. Fixing it is a
one-line change in `_tool_type`; deciding whether it should be fixed is the owner's,
because it moves `unique_files_read` and the exploration family, which W3-T1 and W3-T2
are reading this wave.

**`store.resanitize` also writes its rows under kind `dropped`.** Found while measuring
finding 3: 1154 rows on the owner's store read `resanitize cmdnorm-v2 to cmdnorm-v3: N
field(s) rewritten` under the same word the receiver uses for queue loss. It is the same
defect I was sent to fix, one file over. I did not touch it: `store.py` is DDL-only for
this task, and the fix is the same shape as the one I made in importer.py.

**`obs_by_type` is now a strict prefix of `obs_by_type_capture`, and nothing queries
it.** I grepped: no SELECT in `src/` filters on `observation_type` alone. Keeping both
costs the writer the +16.8% measured above; swapping the composite in for the single one
costs nothing at all (0.238 s against 0.237 s, best of three, same benchmark). I did not
do it, because a `DROP INDEX` is a migration and the brief bounded the observations DDL
to one `CREATE INDEX`. It is a free win whenever somebody wants it.

**The scaling test is a wall-clock test, and I could not find a better one.** What I
want to assert is "the scan read few rows". Python's sqlite3 exposes no per-statement
row counter, and instrumenting the reads would mean stubbing them, which this repository
forbids for good reasons. So the test grows a real store with real recorded bytes and
compares times, with a bound of 2.0 sitting between a measured 0.91 fixed and 3.09
broken. On a heavily loaded machine it could flake. If it does, the answer is a wider
bound rather than a deleted test.

**`_REFUSAL_SURFACES` is a provider table living in `measures_spec13.py`.** It belongs
in `claude_drift.CAPABILITIES` beside the other spec 9.1 cells. I did not put it there
because that file was outside this task's OWNS list, and a capability row is a claim
about five surfaces that I would have had to fill in for Codex without measuring any of
them. `_refusal_coverage` reads the coverage block first, so moving it later is a
deletion here and an addition there.

**I edited `tests/integration/test_experiments.py`, which is outside OWNS.** Its
constant `UNKNOWN_TO_THE_FAKE_AGENT` asserted that a fake-agent capture has no
`cache_read_tokens`, which was a description of the defect rather than of the agent.
Leaving it would have left the suite red. One entry removed, with a comment saying why
it must not come back.

**The 36-capture baseline is my own rebuild of W2-T4's shape, not W2-T4's store.** I
built 36 real launcher captures and grew them to 30708 observations to match W2-T4's
30715, then measured both branches of the code on that one store. The absolute numbers
agree with W2-T4's 0.245 s closely enough to be the same measurement, but they are not
literally the same database, and I say so rather than implying I re-ran the original.

5. **The cohort scan is still linear in the number of captures.** At 3200 captures it is
   0.31 s in process and that is fine. At 30000 it will be 3 s. The fix when it matters
   is an index on the four keys, which means materialising them, which means a table,
   which is a design change and not a tuning change.

# EXPLAIN FOR THE OWNER

## Why reading a whole capture to learn its model name gets slower with every session

Telltale can tell you how one session compares to similar ones. "Similar" has a precise
meaning: same agent, same major version of it, same model, same privacy level. Four
facts. A group of sessions matching on all four is what a percentile is taken over.

To build that group, Telltale has to ask every session in the database those four
questions. That part is unavoidable. A statement about "sessions like this one" is a
statement about all of them, so all of them get looked at.

Here is where it went wrong. Each of those four facts lives in one small record inside a
session. The model name is in one record. The privacy level is in one record. But the
only way to fetch records was "give me everything this session recorded", and a session
records hundreds of things: every model request, every file read, every command.

So to read four facts, Telltale read everything.

That is fine when there are thirty sessions. It is not fine later, and the reason is
worth being precise about: **the cost grows with two things multiplied together.** More
sessions means more sessions to check. Longer sessions means more records read per
check. Both grow as you use the tool. The command that compares one session to its peers
got slower every day, and nothing about that one session had changed.

The number: on your store, 3200 sessions and 1.04 million records, `telltale vector`
took **11.13 seconds**. Of that, 6.30 seconds was fetching 1044858 records in order to
look at 3247 of them.

The fix has two halves, and the second one is the interesting one.

The first half is obvious once you see the problem: let a caller say which kinds of
record it wants. There is now a way to ask for "just the environment record and the
launch record of this session" instead of "everything". A database index makes that a
direct jump rather than a walk.

The second half is the one I did not expect. Of the four facts, one is special. The
privacy level is written in a single record that the launcher writes once per session,
and a session without that record has no privacy level at all, which means it can never
be in anybody's group. So instead of asking 3200 sessions "what is your privacy level",
Telltale now asks the database once: "show me every privacy-level record you have". That
is one query. On your store it comes back with **47 rows**, because only 47 of the 3200
sessions were started by the launcher. The other 3199 questions never get asked.

So the expensive four-fact read now runs 47 times instead of 3200. The command went from
**11.13 seconds to 0.85 seconds**, printing byte-identical output.

One honest limit. This is still linear in the number of sessions, and it has to be. What
it is no longer is linear in how big those sessions are. At 3200 sessions it is a third
of a second of real work; at ten times that it will be a few seconds, and the fix then is
a different one that I have written down in NEXT rather than guessed at now.

## What a refused call is, and why "0 test runs, 3 refused calls" is the honest sentence

When a coding agent wants to run a command, it does not run it. It asks. Something
decides whether to allow it: usually a person, sometimes a rule. Only after the yes does
anything execute.

In experiment E05, five sessions were run with nobody watching. Each one asked to run
`uv run pytest`. Each request went to a permission prompt with no human at the other
end. The agent was told no, three times per session, and the sessions ended having
changed nothing.

Telltale reported that as **three test runs, three of them failed**, five times over.

The mistake is small and specific. When a command is refused, the agent is told so
through the same channel it would be told about a command that ran and exited badly: a
result marked "this went wrong". Telltale read that mark and concluded the test failed.

But "the test failed" and "the test never started" are completely different facts about
a session, and they point at opposite actions. The first says look at the code. The
second says look at the permissions.

The information to tell them apart was sitting in the recording the whole time. The
agent sends a separate message saying a call was refused, naming exactly which call, and
at the end of a session it lists every refused call. Nothing read those.

Now they are read. A refused call is marked as refused. It is not counted as a
verification run, because nothing was verified. It **keeps** the fact that the agent
wanted to run a test, because that is real and useful: an agent that spent its session
asking for permission is telling you something. And there is a new number in the
summary, `refused_tool_calls`, so the count is stated rather than hidden.

The five E05 sessions now read: **agent_test_runs 0, failed_test_runs 0,
refused_tool_calls 3.** That is what happened.

Two details I want you to see, because they are the difference between a fix and a
guess.

**I read both signals, not the cheaper one, and a measurement is why.** Four of the five
sessions carry both the per-call refusal messages and the end-of-session list. The fifth
carries the messages and **no end-of-session record at all**, because the session did not
finish cleanly. Had I read only the list, that session would still be reporting three
failed tests today. I only know this because I looked at all five.

**Absence is not zero, and that shaped the new number's coverage.** Telltale supports
Codex as well as Claude. Nothing has ever measured what a Codex permission denial looks
like. So for a Codex session, `refused_tool_calls` is not 0 - it is null, with a warning
saying no surface here can answer the question. Reporting 0 would claim Telltale had
looked and found nothing, and it has not looked. There was a trap here I nearly walked
into: Codex also has a data stream literally named "stream", so a rule written as "if the
stream arrived, we can see refusals" would have silently claimed Codex sessions were
never refused anything. The rule is keyed on the agent, not on the name of the stream.

## Two smaller things, and one number each

**A spelling cost you two of four token counters.** Claude reports token usage twice: in
its telemetry, and in its output stream. The two use different words for the same
number - the telemetry says `cache_read_tokens`, the stream says
`cache_read_input_tokens`. Telltale only knew the telemetry spelling. So any session
recorded without telemetry reported two of its four token counters as unknown, while the
numbers sat in the stored data unread. A test-agent capture went from
**cache_read_tokens null to 15000**, at full confidence, with no new data collected. It
was always there.

**One word was doing two jobs.** When Telltale's recorder cannot keep up, it drops
records and writes a note saying `dropped`. When Telltale imports an old transcript and
meets a line format it was never taught to read, it also wrote `dropped`. Those are
opposite: the first is data you gave Telltale and it lost, the second is data Telltale
was never written to read. On your store, **1696 rows** carried the second meaning under
the first one's name. Anyone auditing how much the recorder had lost would have counted
them. The note now says which one it is.
