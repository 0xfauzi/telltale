## WHAT WAS WRONG

**The brief's central fact about attempts was wrong, and building on it would have
produced an empty clock.** The brief says "an attempt is a capture with an
external.correlation carrying task_id and attempt" and "the launcher writes the
correlation from `--task-id X --attempt N --experiment E` (every build capture of this
repository has one: 37 launcher captures)". The launcher writes no correlation. Nothing
in `launch.py` posts to `/v1/correlations`; `--task-id`, `--attempt` and `--experiment`
go into the `telltale.capture_started` PAYLOAD (`launch._started`), and `activities.py`
does not lift them onto any activity.

Measured on the owner's store: `SELECT count(*) FROM observations WHERE
observation_type='external.correlation'` is 5 across the whole database. All five belong
to the E05 pilot, were written by `experiments._correlate`, and carry a repo_id
(`3b02bfa6...`) that is the disposable worktree the pilot made, not this repository
(`d9f783b1...`). Of the 37 captures carrying this repository's repo_id, 22 carry
`task_id` and `attempt` in `capture_started` and none carries a correlation.

So a compiler that read correlations alone would report an empty attempt lineage for the
build that produced it, which is the one lineage this task exists to fold. Both surfaces
are read instead, and both have to agree.

**Three change columns cannot be built at all.** `subsystems_touched`,
`test_files_changed` and `dependency_delta` all need per-file PATHS.
`telltale.repo.commit` carries `sha`, `parents`, `tree`, `committed_ts`, `files_changed`,
`additions`, `deletions` and `link_confidence`, and those eight keys and no others on
every commit stored. Design 6.12 forbids reading git at series-build time, so this is a
missing field and not a missing call. The three are None with coverage `unavailable`,
and `series_lineage.MISSING_FIELD` names the field each one wants. This is the STOP the
brief asked for, reported rather than worked around.

**Design 6.12's non-decreasing `row_end_ts` is not satisfiable on these clocks by the
row's own last observation.** Two measured facts. Attempts of one repository OVERLAP:
W1-T4 attempt 2 spans 01:20:41 to 01:48:46 and W1-T5 attempt 1, which starts later, ends
at 01:46:15. And an outcome about an attempt is observed after a later attempt has
closed: W2-T8 attempt 1 ended at 18:24:28, W2-E05 attempt 2 started later and ended at
18:11:22. So start order and end order already differ before any outcome exists.

**`cli.py` went over the 800-line ratchet a second time.** The import split took it from
764 to 648; adding `outcome` took it to 825. The command moved into `cli_outcome.py`,
which is a file the brief did not name. It is the same split cli_import.py is, for the
same reason, and it is called out here because it is outside the brief's OWNS list.

**`edit_turnover_ratio` is named by design 6.12 and defined by no document.** So is the
placement of an outcome that arrives late. Both decisions are stated below rather than
made silently.

**`src/telltale/series_lineage.py` (new, 769 lines).** The two lineage clocks.

- `lineage(store, repo_id)` reads every capture of the repository, splits them into

- `row_end_ts` is a running maximum, so both of `check`'s clauses hold by construction.
- A column with no capability behind it takes its coverage from its own cells:
  all None is `unavailable`, no None is `observed`, anything between is `partial`.

**`src/telltale/model.py`.** `RowMeta.flags: list[str]`, defaulted and additive. Words

**`src/telltale/cli_forecast.py`.** `series build --clock request|attempt|change

**`src/telltale/cli_outcome.py` (new).** `telltale outcome`. It resolves the repository

### Read helpers added in series.py rather than in W3-T0's files

The brief reserves `store_reads.py`, `activities.py`, `correlate.py` and `cohorts.py`
for W3-T0 this wave, so nothing there was touched. Everything the two clocks read goes
through existing public store readers: `captures()`, `activities(capture_id)` and
`observations_by_id(ids)`. The one thing that needed a decision is that
`series_lineage` reads an observation PAYLOAD (`telltale.capture_started` for the
attempt identity, `telltale.capture_ended` for `duration_ms`), where `series._cohort`
had recorded a self-imposed rule that this module reads only observation ROW columns.
That rule is now widened and said so in the design amendment: the alternative is an
attempt clock that cannot see any of the build's own attempts. The lift that would make
it unnecessary is `activities.py` putting task_id, attempt, experiment and duration_ms
on the capture lifecycle activity, which is W3-T0's file and a candidate for W4.

### Two definitions chosen here, not found

- `edit_turnover_ratio` = file_edit activities over distinct edited paths. 1.0 when
  every file was written once, growing as a file is rewritten. None when no edit named a
  path (spec 13.3's three-answer rule) and None when there was no edit: a ratio over no
  edits is undefined, not 0.
- An outcome is placed on the attempt it NAMES, not on whichever row was open when it
  arrived. Design 6.12's "outcomes about earlier rows (reverts, repairs) are recorded at
  the row where they were observed, never back-filled" is about an outcome concerning a
  DIFFERENT row; an outcome that says "attempt 1 of W2-T8 was merged" is attempt 1's own
  outcome and that is what `verification_passed`, `review_fail_count` and `accepted`
  mean. What "never back-filled" then costs is recorded honestly in `row_end_ts`: the
  running maximum shows that the row did not close until the outcome arrived.

## UNSURE OR NOT DONE

- **Three change columns are unbuildable and stay None** (`subsystems_touched`,
  `test_files_changed`, `dependency_delta`). They need a path list on the
  `telltale.repo.commit` payload. Nothing here works around it and no number is guessed.
- **The residual in `row_end_ts`.** On these two clocks an outcome cell of row i may
  have become known after row i+1 began. `row_end_ts` says so, and `check` passes
  because its claim is "everything in rows 0..i had been observed by here". A reader who
  wants strict per-row tightness does not get it on a lineage clock, and cannot: the
  columns design 6.12 chose are outcomes, which are known only later.
- **`c_min` 16 for the two clocks is not wired.** The brief puts the TargetSpec registry
  for them in W3-T2 and forbids editing `forecast/`, so nothing here declares a target,
  a horizon or a threshold on either clock. `forecast readiness` and `forecast backtest`
  will refuse an attempt or change series until W3-T2 registers one.
- **`cli_outcome.py` is a file the brief did not name.** Forced by the 800-line ratchet
  (cli.py reached 825 with the command inline). Same shape as the cli_import.py split.
- **`RowMeta.flags` touches `model.py`,** which is not in the brief's OWNS list. It is
  additive and defaulted, so every stored row_meta reads back unchanged, and it is the
  shape the brief asked for ("flagged low_confidence in row_meta").
- **The `dropped` table on the change clock lists captures that were not attempts.**
  That is factual (they are why `attempts_to_land` may be None) but it reads as noise
  beside a commit-shaped question. Worth narrowing if a reader complains.
- **The status vocabulary is a table, and a word outside it is None.** `--status` is
  free text because an orchestrator's vocabulary is its own. If the merge protocol picks
  a word `series_lineage._PASSED` / `_FAILED` do not carry, the column will be quietly
  unknown rather than wrong, and the operator finds out from the coverage word.

## EXPLAIN FOR THE OWNER

### What a clock is, and why there are three

A forecaster does not see time. It sees a table: rows in order, columns of numbers, and
the promise that row 5 comes after row 4. Everything about what those rows MEAN is
decided before the forecaster ever runs, and that decision is the clock.

A clock is a choice of what one row is.

Telltale has three because there are three genuinely different questions to ask about a
coding agent, and each has its own natural unit.

**The request clock** puts one row per model request. A session that made 175 requests
is 175 rows. This is the fine-grained view: within one session, do the tokens climb, do
the tool calls bunch up before a failure, does a compaction change what comes after it.
The unit is a heartbeat. The frame is one capture, so the key is a capture id.

**The attempt clock** puts one row per attempt at a task. If W2-T8 took three tries,
that is three rows. This is the view the orchestrator lives in: is the second attempt
cheaper than the first, does a task that needed three attempts look different from the
start, does a failed verification predict another one. The unit is a try. The frame is a
repository, so the key is a repo_id.

**The change clock** puts one row per change that actually landed. Not per attempt: per
commit that made it onto the tracked base. This is the view the codebase lives in: do
changes get bigger, do they need more attempts to land, does the verification cost per
change climb. The unit is a landed change.

The spec says something sharp about why the last two are separate (section 10.3):
factory health cannot be inferred from accepted changes alone, because a filter can
succeed at screening an increasingly bad stream. If you only look at what landed,
everything looks fine right up until nothing lands. Attempts and changes are analysed
together, so they are two clocks and not one.

They are not three views of one table. A row on the request clock and a row on the
attempt clock are different objects with different columns, different coverage and
different histories. That is why `build` takes a clock and a key rather than a filter.

### What an attempt row holds

Here is a real one, from this build's own store. It is the W2-T8 session, the one that
tightened command normalization:

```
capture cap_01M1HKTJB8C34SPHQYAQMHGF4W
attempt_of_component      1          this was the first try at W2-T8
model_requests            113        113 calls to the model
fresh_input_tokens_total  226        tokens that were NOT served from cache
compactions               0          the context never had to be summarized
duration_ms               2112728    35 minutes
verification_passed       None
review_fail_count         None
accepted                  1          merged
env_changed               0          same environment as the attempt before it
```

Two things are worth stopping on.

`fresh_input_tokens_total` is 226 for 113 requests. That is not a bug. Claude Code's
cache means that almost every request re-reads a context it has already paid for, and
the fresh tokens are just the new turn. It is the cache column that carries the volume.
The number looks wrong until you know what it is measuring, which is why the column is
named `fresh_` and not `input_`.

`verification_passed` and `review_fail_count` are None, and `accepted` is 1. All three
come from the same place: outcome records. The 1 is there because I posted one during
this task's verification. The two Nones are there because nobody has ever posted a
verification result or a review result for this session, and Telltale refuses to turn
that into a zero. A zero would say "the verification failed". None says "no verification
was ever reported". Those are different facts and the whole system is built to keep them
apart. The coverage word on the column, `partial`, is what tells a reader that the
column has real values in it AND real gaps.

### What a change row holds

Same store, the commit that landed W2-E05:

```
commit d9b15dc2a270c1dcbfc65b6d9f76303bc7cc8c96
files_changed             3
lines_added               145
lines_removed             48
subsystems_touched        None
test_files_changed        None
dependency_delta          None
attempts_to_land          1
fresh_input_tokens_total  226
cache_read_tokens_total   17943341
compactions               0
verification_cycles       7          seven test/lint/typecheck runs
edit_turnover_ratio       5.0        five edits per distinct file
stable_state_intervals    27
unique_files_read         2
env_changed               0
```

The first six columns describe the change; the rest describe the work that produced it,
summed over the attempts that landed it.

The three Nones in the middle are the honest part, and they are the thing I would most
want you to see. `subsystems_touched` wants "how many top-level directories did this
touch". `test_files_changed` wants "how many of the changed files were tests".
`dependency_delta` wants "did the lockfile move". All three need to know WHICH FILES
changed, by name.

Telltale does not have that. When it links a commit to a session it records the sha, the
parents, the tree, the timestamp, the file COUNT, the additions, the deletions and how
confident the link is. It does not record the paths. And a series is required to be
rebuildable from the store alone, which means the compiler is not allowed to shell out
to git and ask. So the three columns are None, the coverage says `unavailable`, and the
code names the field it wants. The fix is one field on one payload, in a later task. The
wrong fix would have been to run `git show --stat` at build time, which would have made
the series a function of whatever the working tree happened to be that day.

`edit_turnover_ratio` at 5.0 is a definition I had to invent. Design 6.12 names the
column and never says what it is. I chose edits divided by distinct files edited: 1.0
means every file was written once, 5.0 means files were rewritten five times on average.
That is a reasonable reading of "turnover" and it is written down in the design
amendment as W3-T1's choice, so that the next person changing it knows they are changing
a decision rather than fixing a bug.

### Why an outcome observed later is recorded where it was observed

This is the subtlest rule in the whole task, so let me build it up.

The problem: some columns of an attempt row cannot possibly be known when the attempt
ends. "Did this attempt get merged?" is answered days later by a human. "Did the review
pass?" is answered by the next session. The attempt is over; the answer arrives after.

The temptation is to just write the answer into the row when it arrives. Attempt 1 gets
merged on Thursday, so on Thursday you set `accepted = 1` on attempt 1's row and move
on. That is back-filling, and it is poison for a forecaster.

Here is why. A forecaster is trained and tested by rolling an origin through the table:
show it rows 0 to 19, ask it to predict row 20, check. The entire validity of that
exercise rests on one promise: everything in rows 0 to 19 was knowable before row 20
happened. If attempt 1's row secretly contains a fact from Thursday, and attempt 5 ran
on Tuesday, then the model predicting attempt 5 is being fed the future. It will look
brilliant and it will be worthless, because in production that cell would have been
empty.

The recorder's answer is not to hide the fact. It is to be honest about WHEN the row
closed. Every row carries `row_end_ts`, and the invariant `check` enforces is that
nothing in the row was observed after that timestamp. So when Thursday's merge decision
lands on attempt 1's row, attempt 1's row closes on Thursday, and it says so.

That creates one more problem, which is what forced the last piece. Design 6.12 also
requires `row_end_ts` to never go backwards, so that "earlier in the table" means
"earlier in time". But if attempt 1 closes on Thursday and attempt 2 closed on Tuesday,
the timestamps run backwards.

And this is not hypothetical. I measured two cases in this build's own store where the
ordering breaks before any outcome is involved:

- W1-T4 attempt 2 ran from 01:20 to 01:48. W1-T5 attempt 1 started at 01:35, inside it,
  and finished at 01:46, before it. Two sessions on one repository, overlapping. Start
  order and end order already disagree.
- W2-T8 attempt 1 ended at 18:24. W2-E05 attempt 2 started later and ended at 18:11.

So `row_end_ts` on these two clocks is a running maximum: each row's own last
observation, but never earlier than the row before it. The claim it makes is slightly
weaker and exactly true: "everything in rows 0 through i had been observed by this
moment". That is precisely what a rolling-origin backtest needs to know, and it is what
`check` tests.

The residual, which I have written into the design rather than buried: on a lineage
clock, an outcome cell in row i may have become known after row i+1 began. `row_end_ts`
is where a reader sees that. It cannot be avoided, because the columns design 6.12 chose
for these clocks ARE outcomes, and an outcome is by nature known late. What can be
avoided is pretending otherwise, and that is what the running maximum refuses to do.

### What `telltale outcome` is for

Three columns of the attempt clock come from outcome records: did the verification pass,
how many reviews failed, was it accepted. Before this task, the only thing in the entire
system that could write one was the experiment runner, `experiments.py`, when it ran a
pilot. Which meant those three columns were empty for every session this build has ever
recorded. Twenty-two attempts, three columns, all None.

`telltale outcome` is the door. One line at each gate of the merge protocol:

```
telltale outcome --kind mechanical_verification --status pass --task-id W3-T1 --attempt 1
telltale outcome --kind adversarial_review --status rejected --task-id W3-T1 --attempt 1
telltale outcome --kind merge_decision --status merged --task-id W3-T1 --attempt 1
```

It figures out which repository you are in, finds the one capture that was that attempt,
and writes the record onto it.

Two design points that are really the same point.

**It refuses rather than guesses.** If no capture carries that task and attempt, it
exits 2 and prints every attempt it did find, so a typo is visible. If TWO captures
carry it, which happens when an orchestrator retries a dispatch, it exits 2 and names
both, because there is no correct answer to "which one of these is attempt 1" and
picking the first would be inventing one. This is the house rule the codebase repeats
everywhere: absence is not zero, duplicate is not one.

**A status word it does not recognise stays unknown.** `--status` is free text, because
your orchestrator's vocabulary is yours. There is one table that turns a word into a
number: `merged`, `pass`, `approved` and friends become 1; `failed`, `rejected`,
`reverted` become 0. A word outside both lists leaves the cell None. That is deliberate.
The alternative is to guess that `deferred-to-thursday` means failure, and a guess in a
recorder is worse than a gap, because a gap is visible in the coverage column and a
guess is not.

There are two write paths because a capture may still be running. With `--receiver` it
posts to the receiver already serving that session, which is the only process holding
the database open. Without it, it opens the store itself, writes, and rebuilds the
capture so the clocks can see it immediately. Both go through the same sanitizer, and a
test asserts the two produce identical records apart from the fields that must differ.

The practical consequence: from now on, every merge decision this build makes becomes a
row in a table a forecaster can read. Right now those three columns are almost entirely
empty, and that emptiness is itself the finding: the build has been running for three
waves and has never recorded whether any of its own work was accepted.
