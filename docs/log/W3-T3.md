## WHAT CHANGED

### The split, first and on its own

`src/telltale/activities_tools.py` is new and holds the tool-call reducers: `VERIFICATION`
and the three tool-name sets, `tool_calls`, `_denials`, `_denied_ids`, `_tool_call`,

The tool block moved and the request block did not, and the reason is a seam rather than
a size. `tool_calls(capture_id, observed)` is the whole interface: `activities._activities`
calls it once and `activities._subagents` reads the ACTIVITIES it returns rather than any
function inside it. The request reducers are not separable that way. `_requests` and

argument, so moving them would either duplicate that function or make two modules import
each other.

No behaviour changed. `correlate._RULE_MODULES` gained the new file, so an edit to a
moved rule still moves `REDUCER_VERSION`; activities_codex.py reads `VERIFICATION` from
its new home. Every golden matched byte for byte and the suite was unchanged at 184.

### `commands.exit_masked`, and a verification_run that states no outcome

```python
def exit_masked(command_norm: str) -> bool:
    tokens = command_norm.split()
    separators = [token for token in tokens if token in _SEPARATORS]
    for index, segment in enumerate(_split_segments(tokens)):
        if _classify_segment(segment)[0] != "unknown":
            return any(token != "&&" for token in separators[index:])
    return False
```

The rule: the status belongs to the classified segment when that segment is last, or
when everything after it is joined by `&&`. A non-zero in an `&&` chain stops the chain
and becomes its status, so a failure cannot hide there. After `|`, `;`, `||` or `&` the
status is another program's. A redirection is not a separator, so `pytest 2>& _` is
still pytest's.

A masked verification_run carries `exit_masked: true` and states no outcome: no
`success`, and no `exit_code` read onto the row. The observation still holds whatever
the surfaces said and `telltale explain` reaches it. What the row may not do is answer
"did the check pass".

Nothing downstream needed a new mechanism. `measures_intervals.failed` already returned
None when neither field is present, so `failed_test_runs` and `fail_to_pass_cycles`
already skip such a run; `measures_spec13._stated` already returns `partial` when a run
in scope stated nothing. The only addition is the warning, over the runs each metric is
taken over.

Both providers. A Codex tool call is a shell command, so `activities_codex._tool_call`
takes the same branch. Codex S6's
`uv run pytest && git diff --check && git diff _ pkg/calc.py` is not masked and did not
move, which is the `&&` half of the rule tested on a real capture.

### The column coverage rule

`series.blank_unobservable` now reconciles a column with its coverage word in both
directions. Downwards, as before: a column whose capability was not observed is all
None. Upwards, new: a column with no value in any row is `unavailable`, whatever
capability it rests on. It rewrites the ColumnSpecs in place beside the rows it already
rewrote in place, so all three clocks get the rule from one function and
series_lineage.py did not have to move.

`series.column_report` gained a `reason` per column, `no value in any row` or
`measured for this column`.

### The index

CREATEs. It is in schema.py and not store.py, which the brief named: the DDL moved to
schema.py in W1-T5, and the DROP belongs where the CREATE it replaces was.

## UNSURE OR NOT DONE

**`telltale series build` does not print the `reason` column.** `column_report` returns
it, and `cli_forecast._COLUMN_COLUMNS` is the tuple that selects which keys
`render_table` prints. That file is W3-T2's this wave and the brief said not to edit it,
so the fix is one word in one tuple and it is not mine to make. Until then the reason is
reachable from `series.column_report` and from the test that asserts it. The verification
below shows both the CLI output and the report with the reason.

**The reason cannot say WHY a column is empty.** Once the emptiness rule fires, the
capability word it replaced is gone, so `compaction_before` on a Codex capture and
`request_duration_ms` both read `no value in any row` although the first is unavailable
because Codex never compacted and the second because no surface reports it. The coverage
block `telltale show` prints answers that question per capability, so nothing is lost,
but the column report alone cannot. I considered keeping both words on the ColumnSpec
and did not: `ColumnSpec` is one of the four durable shapes and a field on it is a
design change rather than a fix.

**The masked rule is scoped to verification_run, and a `command` row can still print a
status that is another program's.** Claude S1's timeline still reads `ok` for
`rm -rf _ && uv sync _ >& _ | tail -30`. My judgement, and someone could differ: the
`success` field on a command row is a fact about the tool call, and only a
verification_run reinterprets it as "the check passed". Widening the rule would move
`show`'s work block on captures where nothing is claiming the number means a check
passed. If the owner wants it wider, it is one condition in `activities_tools._tool_call`.

**I edited three files outside the brief's OWNS list**, none of them owned by W3-T2 or
W3-T4. `activities_codex.py`, to apply the masked rule on Codex and to read
`VERIFICATION` from its new home; `correlate.py`, one line, so `_RULE_MODULES` names the
module the rules moved into; `test_compare.py`, one docstring that pointed at
`activities._tool_outcome` by its old path. I also added a new file,
`tests/integration/test_schema.py`, because nothing in the suite asked what
`Store.open` does to a database that already exists, and a migration whose whole effect
is on an old store is otherwise deletable with the suite still green.

**W3-T0's +16.8 per cent for this index is not what I measured.** I measured 6.1 per
cent, eight interleaved pairs in one process on this machine. I did not try to reconcile
the two: they are wall-clock numbers on different runs, and I report mine because it is
the one I took.

**The selfcheck does not measure the writer.** The brief asked for its timings before
and after the index change and they are pasted below unchanged, because `_spawn` times
the eight worker threads ENQUEUING and the writer thread commits asynchronously
afterwards. Its `wall_ms` is bimodal at 8.5 or 18.8 both before and after, which is
thread scheduling. The A/B benchmark below is the number that answers the question.

**Nothing here re-measures E05's H2 statistics.** Five captures moved from
`fail_to_pass_cycles` 0 at coverage derived to 0 at coverage partial, and
`docs/experiments/E05.md` still reports the old coverage word beside its measure table.
Whoever owns that write-up should decide whether a measure that is now `partial` on all
five belongs in the demotion table at all.

# EXPLAIN FOR THE OWNER

## What a pipeline does to an exit status

Every program a shell runs hands back one number when it stops. Zero means it is
content. Anything else means it is not. That number is how the whole world decides
whether a test run passed, and it is the only thing Telltale has ever had to go on.

Now put two programs in a row and join them with a vertical bar. The bar sends the first
program's output into the second program's input. Here is the real command, the one all
five of the W2-E05 re-run sessions typed before they touched a line of code:

```
uv run pytest 2>&1 | tail -50
```

Read it left to right. `uv run pytest` runs the test suite. `2>&1` says "send the error
messages down the same pipe as the ordinary output", so nothing is lost. The bar sends
all of it into `tail -50`, which throws away everything except the last fifty lines,
because the agent only wanted the summary and not four hundred lines of traceback.

That is a sensible thing for an agent to do. It is also, for our purposes, a disaster.

The shell reports one number for the whole line, and that number is the LAST program's.
The last program here is `tail`. `tail` prints fifty lines. It succeeds. It hands back
zero. It has no opinion about the tests, has never heard of them, and would hand back
zero just as cheerfully if pytest had crashed on the first import.

So the number that came out of that line was `tail`'s zero. The agent's own transcript,
recorded in the same capture, says "1 failed, 1 passed". Telltale wrote down zero and
called it the test result.

That is not a bug in reading a field. Every surface Claude Code offers said the same
thing, and they were all telling the truth: the tool call did not error. The mistake was
one layer up. Telltale took a statement about the command line and filed it under a
question about the tests.

## Why "unknown" is the only honest word there

There were three words available and only one of them is true.

We could say the tests passed. That is what the old code did, and it is false: they
failed. Five sessions in a row reported no failing test run and no fail-to-pass cycle
about work whose whole shape was a failing test made to pass. If somebody had used those
captures to compare two models, the measure they were comparing would have been
constant zero.

We could say the tests failed. That is equally false and worse, because it invents a
failure. Some sessions really do pipe a passing test run into `tail`.

The third word is the one the recorder can actually support: we do not know. Nobody
looked. The number that came back is a fact about `tail`.

This is the same rule the rest of Telltale already runs on, applied one field further.
A capture with no compaction records reports `pre_compaction_tokens` as null and not as
zero, because zero would mean "we watched and nothing happened" when what happened is
that nobody watched. A masked exit status is the identical shape. The status exists, and
it is an answer to a different question.

So a run whose status was masked now says three things and no more. It happened, which
is why `agent_test_runs` still counts it. Its status is not the check's, which is what
`exit_masked: true` records. And nothing is known about whether the check passed, which
is why the row carries no `success` at all and the timeline prints a dash where it used
to print `ok`.

The two counts that were wrong are now right in a smaller way. `failed_test_runs` counts
the failures somebody actually saw. Its coverage word drops from `derived` to `partial`,
which is Telltale's way of saying "this number is over some of the runs and not all of
them". And a sentence sits beside it naming how many were left out: "2 of 2 verification
runs have a masked exit status". A reader who sees zero failures now also sees that
zero is a count over an empty set.

There is one thing this does not do, and I want to be plain about it. The truth for
those five captures is one fail-to-pass cycle each. Telltale still reports zero. It
reports zero with a warning and a weaker coverage word instead of zero with a strong
one, and that is the whole of the improvement. Recovering the real answer would mean
reading the captured OUTPUT of the test run and deciding what "1 failed" means, which is
reading a number out of prose, and design 6.3 has a word for that kind of evidence and a
rule about never presenting it as stronger than it is. It would also mean teaching the
recorder about pytest's output format, and then about jest's, and cargo's. That is a
different project. Saying "unknown" is free, correct, and available today.

## How the rule decides, and the one case it lets through

The rule reads the stored command and asks a single question: after the part we
classified as a test, is there anything whose status would win?

`uv run pytest` alone. Nothing follows. The status is pytest's, and the run is counted
normally.

`uv run pytest 2>&1 | tail -50`. A bar follows. The status is `tail`'s. Unknown.

`uv run pytest && git diff --check && git diff pkg/calc.py`. This is a real command from
a real Codex session in our fixtures, and it is NOT masked. The double ampersand means
"only if the previous one succeeded". If pytest fails, the chain stops right there and
the chain's status is pytest's own failure. So a failure can never hide behind `&&`, and
a zero means pytest passed and so did everything after it. That command still counts,
which is worth saying because a rule that flagged every command with an operator in it
would have thrown away good data.

The one case the rule lets through is a redirection, `pytest > out.txt`. A redirection
is not another program; it just decides where the output goes. pytest still hands back
its own number. So `>` and `2>&1` on their own change nothing, and the rule ignores
them.

All of this is read off the normalized command string, the sanitized form Telltale
stores in place of the raw command line. That was not luck. Whoever wrote the
normalizer decided to keep the operators, on the grounds that `pytest && git status` and
`pytest ; git status` are different commands and the difference is worth two characters.
That decision, made for a different reason, is the only thing that made this fix
possible without going back to the raw command, which Telltale deliberately does not
keep.

## What an index costs a recorder

The other change in this task looks unrelated and rests on the same instinct: do not pay
for something that answers nothing.

A database index is a second copy of one column, kept sorted, so that looking a value up
is a jump instead of a walk. It makes reads fast. It is not free: every single row you
write has to be written into the index too, forever, whether or not anybody ever reads
it that way.

Telltale had two indexes over the same column of the observations table. One sorted by
the observation's type. The other sorted by type and then by which capture it belonged
to. The second is the first with a tie-breaker on the end, and a sorted list by (type,
capture) is already a sorted list by type: you find every row of a type in exactly the
same jump, and then they happen to be in capture order. Anything the first index could
answer, the second answers as well or better.

I checked whether anything used the narrower one, because "nothing reads this" is the
kind of claim that is embarrassing to get wrong. Six statements in the source read the
observations table. One of them filters on the type alone, and it sorts its results by
capture and then arrival, which is precisely the wider index's order. SQLite agreed
without being asked: with both indexes present, its own query plan for that statement
names the wider one.

So the narrow index was answering nothing and charging for every write. I measured what
it charged. Fifty thousand observations, written in batches of five hundred, timed from
the first one to the writer finishing. Eight pairs of runs, alternating between the two
schemas inside a single process, because two timings taken five minutes apart on a
laptop are mostly a measurement of the laptop.

With it: 0.602 seconds. Without it: 0.568. Six per cent of the entire write path. About
two thirds of a microsecond per observation.

That number is small, and in most systems you would shrug at it. Here is why I did not.

Telltale runs alongside the agent it is recording. It is not the workload; it is the
tax. Every microsecond it spends is a microsecond somebody's real session pays, and the
person paying did not choose to. The rules for this repository put it plainly: an import
the recorder adds is a cost somebody else's session pays. An index is the same argument
in a different currency. Six per cent of the write path to answer a question nobody asks
is not a rounding error, it is a small permanent charge on every future session, and it
was going to keep being levied until somebody removed it.

One last detail, and it is the part that is easy to skip. Deleting the line that creates
the index would have stopped new databases from having it. It would have done nothing at
all for the one on your disk, which already has it and would have gone on paying
forever. So the change is a `DROP INDEX IF EXISTS` that runs every time the store is
opened. On your 1.5 gigabyte database it takes seventeen milliseconds, once, and one
millisecond on every open after that. There is no migrate command to remember and no
version number to bump, because the schema is brought up to date by the same code that
already runs on every single open.

There is also now a test for it, which there was not for any of the other schema lines.
The reason is worth stating. Every other statement in that file creates something, and
any test that opens a store proves it worked, because a missing table breaks everything.
A deletion is the opposite: its entire effect is on a database that already exists, and
every test in this suite starts from an empty file. Without a test that deliberately
puts the old index back before opening, somebody could delete the migration next month
and the whole suite would stay green while every real store went on paying.
