## WHAT WAS WRONG

**The change clock had three empty columns and no way to fill them.** W3-T1 built the
clock over this repository, measured 7 rows at the time, and left `subsystems_touched`,
`test_files_changed` and `dependency_delta` None on every one of them with coverage
`unavailable`. The same frame is 12 rows today, and was still all-None on all 12 before
this change (measured on a copy of the owner's store, below). The reason was
not a missing calculation. `telltale.repo.commit` carried eight keys (`sha`, `parents`,
`tree`, `committed_ts`, `files_changed`, `additions`, `deletions`, `link_confidence`) and
not one of them is a path, while all three columns are questions about paths. Design 6.12
forbids reading git at series-build time, so the fix had to be a field on the payload.

**Two metric attributes were thrown away on every metric point.** `claude.otel.metric`
did not allowlist `service_version` or `terminal_type`, so both were dropped and named as
unknown fields on every point Claude Code sends. W2-T6 measured this as the single
largest source of `unknown_field` rows in the owner's store: 746 of 1935.

**Two files had no room to change.** `allowlist.py` was at 798 lines and `launch.py` at
790, against a pre-commit hook that fails a Python file growing past 800.

### The commit's paths (882d112)

`repo_link._commit_stats` already runs `git diff-tree --numstat -r -M --no-commit-id
--root <sha>` to count files, additions and deletions. The path list comes out of that
same numstat, so it costs no extra git call and reads no patch body.

**The shape is three keys, not the snapshot's four, and that is a measurement.** A
snapshot's `per_file` entry carries `patch_hash` as well. I measured what a fourth key
costs over this repository's own 65 commits before choosing:

```
largest commit 04c00142, 65 files
  with patch_hash:    11020 bytes  ->  over the 8 KB bound, list cut to 48 of 65
  without:             5820 bytes  ->  fits
across all 65 commits, without patch_hash:
  largest payload      5829 bytes (65 files)
  commits over 8192 bytes: 0
```

So including the hash would truncate the list on exactly the biggest changes, which are
the rows a change clock most wants, and it would cost a second git call per commit to
read the patch it hashes. The brief's stop rule was about this: a list that cannot be
bounded without losing the truth somewhere other than the truncation flag. It can, so I
did not stop.

A merge reports `per_file` None, like the counts beside it. A path list picked from one
parent's diff is the same invented answer as a line count picked from it.

`launch.py`'s `_capped`, which cuts a per_file list to `PER_FILE_MAX` and then to what
fits the 8 KB payload bound, moved from the snapshot call site into `_Capture.emit`. Now
every launcher payload with a path list is cut by one rule, and a payload without one
passes through untouched.

### The three columns (94d3497)

`series_paths.py` is a new module holding the rules. It exists partly because
`series_lineage.py` was at 769 lines, and partly because a rule about what a path MEANS
is a different thing from the fold that turns a repository into rows. Nothing in it reads
the store and nothing in it runs git.

- `subsystems_touched`: distinct first path components, with `.` naming the repository
  root. A root file is in no directory, and 0 there would say a commit that edits
  `pyproject.toml` alone touched nothing.
- `test_files_changed`: paths with a `tests` or `test` component, or a basename matching
  `test_*.py`, `*_test.py`, `*.test.*` or `*.spec.*`. `fnmatchcase`, never `fnmatch`:
  `fnmatch` folds case on a case-insensitive filesystem, which would make `Test_x.py` a
  test file on macOS and not on Linux.
- `dependency_delta`: 1 when any changed basename is one of the 13 lockfile and manifest
  names or matches `requirements*.txt`, 0 when none is.

All three go None together, never 0, when the store does not hold the commit's paths.
Four ways to reach that: a commit recorded before this change, a merge, a list
`per_file_truncated` says is a prefix, and an entry carrying no path at all.

`MISSING_FIELD` is gone. The reason a cell is unknown now travels on the cohort as
`unknown_columns`, which `series build` prints on the line above the column table.
`column_report` lives in `series.py`, which belongs to W3-T3 this wave, and a `ColumnSpec`
carries a coverage word with no room for a sentence; the cohort is the reader-visible
place I could put the sentence without touching another task's file.

## UNSURE OR NOT DONE

- **`column_report` still prints no reason column.** The brief asked for "column_report
  naming why". `column_report` is in `series.py`, which W3-T3 owns this wave, and
  `ColumnSpec` carries a coverage word with no room for a sentence. I put the reason on
  the change-clock cohort as `unknown_columns`, which `series build` prints two lines
  above the column table, so a reader sees the word and the reason in one screen. If the
  owner wants it in the table itself, that is one field on `ColumnSpec` and one column in
  `column_report`, and it belongs to whoever holds `series.py` next.
- **`subsystems_touched` calls the repository root `.` and counts it.** This is a
  judgement and someone could reasonably differ. Design 6.12 says "distinct top-level
  directories", and a file at the root is in no directory, so 0 is a defensible reading.
  I chose 1 because a commit that edits `pyproject.toml` alone did touch something, and a
  clock that reports 0 there is reporting the same number it would report for a commit
  that changed nothing.
- **`test_files_changed` counts a `test` directory as well as a `tests` one.** Reasoned,
  not measured: `tests/` is the Python convention and `test/` the Go and Java one. The
  cost is that a directory named `test` holding something else is counted, and the same
  cost is already carried by the `*.spec.*` glob.
- **Nothing measures what these columns do to a forecast.** All three are new past
  covariates on a clock that has 14 rows in the owner's store, against design 6.12's
  `c_min` of 16 rows on this clock. Whether they carry signal is W3-T2's question and
  cannot be answered until the store holds enough change rows, most of which will only
  appear as future captures record commits.
- **Commits recorded before this change stay unknown forever, and that is deliberate.**
  Observations are immutable and append-only (AGENTS.md invariant 5 and design 6.5). The
  paths of those commits are still in git and a backfill could compute them, but writing
  them into an observation would be recording something at a time it was not observed. A
  re-link through `telltale sessions --link-commits` writes NEW observations, which is
  the sanctioned path and is what the copy verification above used.
- **The per_file bound was measured on this repository only.** 65 commits, largest 65
  files and 5829 bytes. A repository whose commits routinely touch 200 files would
  truncate, the flag would say so, and the three columns would be None on those rows. The
  behaviour is right; the frequency is unmeasured anywhere but here.
- **The `--commit` and `provider_reported` paths are untested for per_file.** A sha
  somebody states that this repository does not contain comes back with `per_file` None
  through `_unresolved`, which is the same shape as its other unknown fields, and
  `test_a_provider_reported_commit_id_outranks_every_tree` covers the payload it produces
  but asserts on `parents` rather than on the new field.

## EXPLAIN FOR THE OWNER

### Why you would want this at all

You want to ask a question like "do the changes that get reverted touch more parts of the
system than the ones that stick". To ask it you need to know what each change touched.
Telltale already knew that a session made a commit, and how many files that commit
changed, and how many lines. It did not know WHICH files. So three of the fifteen columns
on the change clock, which is the table with one row per change that landed, were empty
on every row, and had been since the clock was built.

This task filled them.

### The first question: what may a recorder keep about a commit?

A commit has two parts. There is the patch, which is the actual text that changed: the
lines you wrote, the lines you deleted, the contents of a new file. And there is the list
of paths, which is just the names of the files.

The patch is the dangerous half. It is your code, it is anything you pasted into a file,
and if a credential ever sat in a config file for one commit then the patch is where it
is. The design says so plainly: diff text is never persisted. Telltale reads a patch into
memory to hash it, then drops it.

The path list is a different kind of thing. `src/telltale/repo.py` tells you where work
happened. It does not tell you what the work was. And it is already all over the store,
because every file an agent edits arrives as a path on a hook event, goes through the
same cleaning gate, and is stored.

That gate is worth naming, because it is what makes a path safe to keep. Every path is
rewritten before storage: if it is inside the repository being recorded it becomes
relative to the repository root, and if it is anywhere else, your home directory
included, it becomes `<outside>/` and eight characters of a hash. So the store can say
"the agent read two files it should not have" without saying where those files were. I
checked that a commit's paths go through the same gate rather than assuming it: after
three commits in a repository at `/tmp/w3t4-verify/repo`, that absolute path appears zero
times in the database file and `"path":"src/a.py"` appears six times.

So: paths yes, patch no. That is the whole answer to why this was safe to do, and it is
also why it was cheap. The path list falls out of a git command Telltale was already
running to count the files.

### The second question: how big is a list of paths, really?

There is a hard limit in the design. One stored record may not exceed 8 kilobytes, and
when a record is too big the largest field in it is thrown away whole. A path list is
always the largest field, so a list that does not fit is a list that vanishes entirely.

A snapshot of the working tree, which Telltale takes while an agent works, already
carries a path list, and each entry there has four things: the path, the lines added, the
lines removed, and a hash of that file's part of the patch. Copying that shape onto a
commit was the obvious move, so I measured it against this repository's own history
before doing it.

```
largest commit here: 65 files
  with the hash:    11020 bytes  ->  does not fit; list cut to 48 of 65 files
  without it:        5820 bytes  ->  fits
```

The hash costs 64 characters per file, and it is what pushes the biggest commit past the
limit. The rejected answer is the instructive one here: had I copied the four-key shape
without measuring, the three new columns would have gone blank on precisely the largest
changes in the history, which are the changes anybody studying risk cares about most. Not
one of the 65 commits in this repository exceeds the limit without the hash; the largest
payload is 5829 bytes.

There is also a second cost I would have paid for the hash. To hash a file's part of a
patch you have to read the patch, and the command that produces a commit's path list does
not. So the hash means one more git process per commit of every capture, for a number
nothing currently reads.

When a list genuinely will not fit, it is cut and a flag called `per_file_truncated` is
set, and the file COUNT beside it stays true. That pair is what lets a reader tell a short
list from a small change.

### The third question: what do the three columns actually say?

Take one real row, this task's own first commit, `00e8ffc3`, read back out of a copy of
your store:

```
files_changed 5   lines_added 242   subsystems_touched 1   test_files_changed 0   dependency_delta 0
paths:
  src/telltale/allowlist.py            +12 -114
  src/telltale/allowlist_telltale.py  +127   -0
  src/telltale/cli.py                   +2   -1
  src/telltale/launch.py                +3  -67
  src/telltale/launch_commits.py       +98   -0
```

**subsystems_touched is 1.** Every path starts with `src`, so the change stayed in one
place. A change that spreads across `src`, `tests`, `docs` and `scripts` scores 4, and the
question the column exists to support is whether spread predicts trouble.

**test_files_changed is 0.** No path is under a test directory and none is named like a
test. That is a true and slightly uncomfortable fact about that commit: it was a pure
refactor with no test change, which is exactly the sort of thing you would want a clock to
be able to notice.

**dependency_delta is 0.** No lockfile and no manifest moved. Compare W3-T3's commit
`111ff108`, on the same day, in the same repository: 5 files, `subsystems_touched` 2,
`test_files_changed` 1. Two parts of the tree, and a test came with it.

None of these three is a judgement about quality. They are counts of what a path list
says, and the claim class on them stays where it was.

### The fourth question: why do the old commits stay blank?

Your store holds 12 change rows from before this task, and all three columns are None on
every one of them. Not zero. None.

This is the rule the whole system is built on, and it is worth being precise about why it
is not laziness. An observation in Telltale is written once and never edited. That is what
makes the store worth trusting: a row says what was seen, at the time it was seen, by the
code that was running then. Those 12 commits were recorded by code that did not look at
paths, so the honest record is that their paths were not observed.

The paths are still in git. I could compute them today and write them in. That would put a
fact into a row dated before anybody knew it, and it would make every other row in the
table slightly less believable, because you could no longer read a row as "what was
recorded at the time".

So the old rows stay unknown, and the column says `partial`, which means some rows have it
and some do not. `unavailable` means no row has it. Zero would mean the commit touched no
subsystem, which is false. Three different statements, three different spellings, and the
distinction between them is most of what this recorder is for.

There is a sanctioned way to fill them in, and I used it in the verification above.
`telltale sessions --link-commits` runs the linkage again and writes NEW observations,
dated now, by the code running now. On the copy of your store that added two commits with
paths beside the twelve without, and the column moved from `unavailable` to `partial`
exactly as it should.

### What I am least sure about

Two of the rules are judgements rather than measurements, and I would rather you knew
which.

`subsystems_touched` counts the repository root as a place. A commit that changes only
`pyproject.toml` scores 1, not 0. The design says "distinct top-level directories" and a
root file is in no directory, so 0 is a defensible reading; I chose 1 because 0 is the
same number a commit that changed nothing would get.

`test_files_changed` treats a directory called `test` as a test directory as well as one
called `tests`. That is reasoning from convention, not measurement: Python uses `tests/`
and Go and Java use `test/`. A repository with a directory named `test` that holds
something else would be miscounted.

Both are one line each to change if you disagree, and both are named in the design
amendment file so the change is not silent.
