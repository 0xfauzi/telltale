## WHAT WAS WRONG

**A pilot of one probe does not bound a suite of six, and this one did not.** The brief's
stop rule is 200,000 tokens per session. The pilot's three P1 sessions came in at 70,825,
72,643 and 72,597, a third of the bound, so the suite was started. Four of the suite's 18
sessions then crossed it: P3 at 648,183, 461,295 and 427,873 tokens and P4 attempt 2 at
227,192. Nothing crossed the 5-minute bound (the longest is 40,914 ms) and nothing crossed
the pilot's 15-minute total (25.6 s). The overrun was not visible while it happened:
`telltale experiment probe` runs all 18 repetitions inside one invocation and writes its
report at the end, so there is no moment during a suite at which a token count can stop
it. P1 is a one-grep question and P3 is a sixteen-turn trace, and no number of P1
repetitions could have said so. A pilot that bounds a suite has to run one repetition of
every probe in it. That is a change to the brief's protocol, not to the runner.

I did not stop and ask before writing this up, because by the time the bound was
measurable the spend had already happened and nothing left to do could spend more. What
I did stop is running anything further at that scale: the only session started after the
suite is the single cheapest-shaped one the privacy verification needs.

**The privacy check in VERIFY cannot be run in the form the brief specifies, and the
reason is a fact about the runner.** The brief asks for a five-word phrase from one
agent's final answer "read from the runner's stdout, not from any file". The runner's
stdout carries no agent answer: `experiments._launch` runs the child under
`capture_output=True`, so `launch._tee`'s echo goes into the buffer the scorer reads and
never reaches a terminal. W4-T1's `_launch` docstring describes the echo and is what the
brief was written from; the buffering is on the line below it. Tee'ing the runner's whole
stdout to a file confirms it: 52 lines, 6,541 bytes, zero `"type":"result"` lines.

So the check was run in the nearest form that proves the same thing: one further
`claude -p` under `telltale run` directly, which does echo, with P1's prompt at the same
`base_sha` in a detached worktree that was removed afterwards. Its answer is 54
characters and contains no five-word run of prose at all, so the grep was done with the
WHOLE answer rather than a phrase of it, which is strictly stronger. The answer was read
in the terminal and written to no file under this repository; the temporary file holding
it was deleted. That session is `cap_01M1KBEEWP5MACT5A5MV8QPWSG` under task id
`E09-verify`, experiment `E09-verify`, and it is deliberately in none of the tables: it is
not one of the 21 scored sessions and must not enter their statistics.

**Both spec files were pinned to a commit that is not `main`, and `main` moved during the
checks.** `pilot.json` and `spec.json` carried `7d825221ce4fd94fe649fdc872efe66f0acdc1c7`.
`git rev-parse main` was `e1f94c567d2e5a171535b8405ce28ca39510956d` when the key paths
were first checked and `4c4c4484e397a6c5d5f6f8f8b4901771241de8ad` a minute later, because

**This repository carries its own answer keys, and whether a session found them had to be
measured.** `experiments/E09/answer_keys.json`, `spec.json`, `pilot.json`,
`briefs/W4-E09.md` and `docs/gates/wave-4.md` are all tracked at `base_sha`, so every

write-up says so: a `grep -r` whose pattern matched inside a key file would appear as a

**P1 measures `AGENTS.md`, not `store.py`.** All six P1 sessions made exactly one Bash

is read at session start, and its fourth architecture invariant says "Every derived number
is an Evidence, and it is written through store.py". That is a real legibility property of
this repository and a fair thing to have measured, but it is not the legibility of the
source, and it is why the E10 note rules P1 out.

**The pre-registered resolvability rule does not separate power from a flat column, and
most of its verdicts are the second thing.** Of the 28 or 29 stats rows per probe, 16 to
22 are "resolvable at n = 3" only because their scaled MAD is 0: all three repetitions
recorded the identical value, so MDD is 0 and `0 <= 0.25 median` holds whatever the median
is. Only 3 or 4 rows per probe are resolvable with a real spread. E05's rule had the
clause that keeps these apart ("s = 0 means no within-condition variation observed",
neither demoted nor endorsed) and E09's does not. The rule is applied here exactly as it
was pre-registered, with the `s` column printed beside every verdict so a reader can see
which is which, and the gap is named in the write-up rather than patched after the fact.

## EXPLAIN FOR THE OWNER

### The thing being measured, before its name

Every experiment in this build so far has measured how hard an agent worked: how many
tokens, how many turns, how many files it opened. None of them asked whether it was right.
That is a gap you can drive a wrong conclusion through, and the specification says so in
one sentence: cheap behaviour with a wrong answer is not an improvement.

Here is the failure it is guarding against. You reorganize a repository and re-run a task.
Afterwards the agent uses forty per cent fewer tokens and half as many tool calls. Every
number improves. There are two ways to get that: the repository got easier to read, or the
agent gave up earlier. Effort measures cannot tell them apart, in principle, because effort
is a cost and a cost only means something next to what it bought.

A probe buys the other half. It is a question with a checkable answer, written down before
anybody runs anything: "which file writes evidence rows into the database, and what is the
function that replaces one capture's?" The answer key is a list of file paths and a list
of function names. The agent gets the question and nothing else, runs read-only in a
throwaway copy of the repository, and says something. The harness scores what it said
against the key, records the two numbers, and drops the text.

E09 is the first time that machinery has been pointed at a real repository with real
money. Six questions about this one, three runs each, eighteen sessions, plus a pilot of
three.

### One probe with its real numbers

Take P5. The question: "Which source files decide which fields of a provider's payload may
be stored and how a kept string is scrubbed? Name every file, then stop."

The key, written before the run: `src/telltale/allowlist.py`,
`src/telltale/allowlist_telltale.py`, `src/telltale/sanitize.py`. Three files.

Run 2 of 3, capture `cap_01M1KB62NRSV3Y9F7RYDTPCBCX`. The agent made five tool calls
(three Bash, two Read), took six turns, spent 192,028 tokens and 26,027 milliseconds, and
named five files: the three in the key, plus `src/telltale/allowlist_codex.py` and
`src/telltale/commands.py`.

- **Recall** is how much of the key it found: 3 of 3, so **1.000**.
- **Precision** is 3 divided by (3 found plus 2 named that exist and are not in the key),
  so **0.600**.

All three runs of P5 named the same two extra files. So the score is not noise, it is a
stable difference between what the key says the answer is and what the repository leads an
agent to say. That is a much more useful thing to have measured than a number that wobbles.

Now put it beside P4, which asks which file classifies shell commands and what the
function and the vocabulary table are called. Its three runs cost 3, 5 and 3 tool calls
and 147,446 / 227,192 / 147,296 tokens: cheaper than P5 on the median. And its median
recall is 0.667, because two of three runs named the file and the function `classify` and
never found the table `_RULES`. P4 is the cheaper probe and the less-answered one. That is
the entire argument for measuring both, in two rows of one table.

### How each number was measured, and which are not measurements

The counts of tool calls, turns and tokens come out of the recorder, from four independent
surfaces (the hook, two OTel streams and the agent's own event stream), all four of which
delivered on all 21 sessions. Cost comes from the agent's own final message. The wall time
comes from a timer the runner wraps around each child process; the capture time comes from
two lifecycle records the launcher writes; the agent reports a third duration of its own.
Those three spans are printed under three names and never added, because they measure
three different things.

Precision and recall are computed in the runner's own memory from the agent's final text
and the key, and then the text is dropped. Recall is the textbook definition. Precision is
not, and the difference matters: the textbook denominator is "everything the answer
claimed", and there is no way to count what an arbitrary sentence claimed. So the
denominator here is what the repository can recognize: a wrong path is one the answer
named that exists in the repository and is not in the key. That makes precision an upper
bound rather than an estimate, because a made-up function name is counted nowhere. It is
still the number that separates "named the one right file" from "named the right file and
four wrong ones", which is the distinction that was needed.

Two of the numbers in the tables are not measurements at all and are marked as such: 2.8
and 0.25 are the pre-registered constants from the design, and the "resolvable at n = 3"
column is arithmetic on the other columns, not an observation.

### The answer that was rejected, and why

The tempting reading of these tables is: three of six probes score a perfect 1.000, so
this repository is mostly legible. That reading is rejected in the write-up, twice, for
two different reasons.

The first is P1. Its three runs each made exactly one shell command, and each of those
commands already had `src/telltale/store.py` typed into it. The agent did not find the
file; it knew it before it looked, because `AGENTS.md` is read at the start of every
session and its fourth rule says evidence is written through `store.py`. P1's perfect score
is a measurement of the instruction file. That is a real and useful property of this
repository, and it is not a property of the source code, and a reader who takes 1.000 as
"the code is clear" has been told something the number does not say.

The second is more general. Of the twenty-eight statistics rows per probe, sixteen to
twenty-two are marked "resolvable at n = 3" only because all three runs gave the identical
value. The rule that was pre-registered says a measure is resolvable when the smallest
difference it could detect is under a quarter of its median, and when three runs agree
exactly, that smallest detectable difference is zero, so the rule says yes to everything.
That is a statement about a flat column, not about statistical power. The earlier
experiment E05 had a clause that kept those apart and E09's rule, written later, lost it.
The rule was applied here exactly as it was pre-registered, with the spread printed beside
every verdict so the flat ones are visible, and the gap named rather than quietly fixed,
because a rule edited after the numbers arrive is not a pre-registered rule.

### What this buys the next experiment

E10 asks whether a scoped refactor makes a question easier to answer. That comparison is
worthless against a question that is already answered perfectly every time: there is
nowhere to go. It is equally worthless against a question that varies wildly for reasons
nothing in the repository controls.

E09's job was to find the questions in between, and it did. P5 and P3 both find everything
the key asks for and both bring back the same extra files every single time. There is room
to improve and the improvement would be visible as a precision change, which is exactly
what an intervention should move. P1 and P2 have nowhere to go: perfect score, one shell
command, zero spread on every column.

That is the whole deliverable, and it cost 3.7 million tokens and 2.69 dollars to learn.
It also cost one thing that was not planned: four sessions ran past the token bound the
brief set, because the pilot measured the cheapest of the six questions and the suite
contained the dearest. The fix is in NEXT and it is two lines in the next brief.
