# W4-E10 before and after an AGENTS.md rewrite under matched fingerprints

## OUTCOME

E10 ran to completion: 20 sessions, 5 repetitions per arm of two probes at two commits
that differ in `AGENTS.md` and in nothing else, no session over a stop bound, and both
controlled-comparison checks passed. `docs/experiments/E10.md` is the decision file and
every number in it is traceable to `experiments/E10/out/`.

The measured result, in one line: **the instruction rewrite is followed by a large,
one-directional drop in every effort measure the protocol can label, with recall
unchanged, and by a precision drop that is an artefact of the answer key rather than a
worse answer.** On `P5-identify-the-storage-contract` the `after` arm answered with ZERO
tool calls in all five repetitions against a median of 7 in `before`, one turn instead of
2 to 9, and 36,492 tokens against a median of 235,228. On `P3-trace-show-to-store` the
median tool-call count goes 12 to 7 and cache_read_tokens 453,649 to 167,002. Cliff's
delta is -1 on eleven P3 rows, which means every `after` session is below every `before`
session on those measures. The pre-registered prediction of precision 1.000 in every
`after` repetition is FALSIFIED: in all five `after` P3 repetitions and one of five
`after` P5 ones the answer names `AGENTS.md`, which exists in the repository and is not
in the key, so the scorer counts it as a wrong path. That is written up as the result it
is, not corrected after the fact.

Two mechanisms were built first, both W4-E09's lessons turned into code. The runner now
runs REPETITION-MAJOR: round 1 is one session of every probe of every arm, then round 2,
so the first round is the pilot and a bound can act on it. And a spec may carry a `stop`
block of two positive whole numbers; after every session the runner compares that
session's wall and its token total (the sum `telltale show` prints: fresh_input +
cache_read + cache_creation + output) with the bound, and the first session over one ends
the run with the report naming the session and the bound.

## WHAT WAS WRONG

**E09's stop bound could not act, and the reason was the loop shape rather than the
bound.** W4-E09's brief set 200,000 tokens per session. Its pilot ran one probe three
times and its suite ran every remaining repetition in one invocation, so four sessions
crossed the bound and nobody could see one until the last had finished. Adding a
comparison to the end of the run would have changed nothing. What had to change is the
ORDER: with the repetition on the outside, four sessions are enough to see every probe of
every arm once, and the bound has somewhere to act. The bound and the order are one fix
and they are tested as one.

**Making the order repetition-major across the arms meant the intervention could no longer
run one arm and then the other.** `experiments_env.intervention` called
`experiments_probe.probe` twice, once per arm, and `probe` ran every repetition of one
probe before starting the next. Two `probe` calls cannot interleave. So the loop moved
into one function, `experiments_probe.suite`, which takes a list of specs and runs
`(repetition, probe, spec)` with the repetition outermost; `probe` is now
`suite([spec])[0]` and the intervention is `suite([before, after])`. This is why
`experiments_env.py` is in the diff although the brief's OWNS list does not name it: the
intervention runner lives there, and there is no way to interleave two arms without
touching the function that runs them. It is 94 changed lines by
`git diff --stat main -- src`, and no new behaviour beyond the one call.

**A stop that ends the run mid-round can leave an arm with no capture at all, and the
report would then have crashed or lied.** If the very first session crosses a bound, arm
`after` has never run. `experiments_measure.one_fingerprint` raises on an empty capture
list ("0 environment fingerprints across 0 captures"), and
`experiments_factor.assert_between` reads `captures[0]` of each arm. Both are now guarded,
and the guard is not "skip it quietly": a run stopped early has NOT failed the between-arm
assertion, it has not made one, and those are different facts. The probe report's
`environment_fingerprint_id` is None when the spec had no session, the intervention's
`fingerprint_assertion` is None when an arm has none, and the printed line says "NO
assertion was made" with the reason, with a matching warning at the top of the warnings
list. `test_a_bound_under_the_first_session_ends_the_run_and_the_report_names_it` is that
path end to end.

**`experiments_probe.py` was 684 lines against an 800-line ratchet, and the stop machinery
would have taken it to about 900.** The ratchet is a gate, not a preference, and this is
the same moment W4-T5 met when the `instructions` factor took `experiments_env.py` to 910.
The seam is real and it is not the one the runner draws: what a `stop` block may say, what
a session's token total IS, and what the report records when a bound ends a run are one
subject, and nothing in it launches a process, removes a worktree or writes. That is
`src/telltale/experiments_stop.py`. `experiments_probe.py` ends at 797, which is inside
the gate with three lines to spare, and that is worth saying out loud: the next task to
add to that file has to split it again.

**The token total a bound is compared with is not in the evidence vector.**
`cohorts.VECTOR`'s `context_token_burden` family carries `fresh_input_tokens`,
`cache_read_tokens` and `output_tokens`, and NOT `cache_creation_tokens`. The brief
defines the bound against what `telltale show` prints, which is
`measures.SUMMARY_BLOCKS`'s usage block and does carry the fourth. Using the vector would
have undercounted every session by its cache_creation, silently, in the direction that
makes a session look under the bound. So `experiments_stop.session_tokens` reads the four
evidence rows directly, and returns None with the missing names when any of the four is
unknown rather than summing the rest: a total that quietly left one out would be under
every bound for a reason the number does not show. Every one of the 20 sessions had all
four.

**The answer key could not have carried the path the intervention created.** The `after`
arm's answers name `AGENTS.md`. The scorer counts a named path that exists at `base_sha`
and is not in the key as wrong, because that is what makes precision's denominator finite,
so five `after` P3 repetitions score 0.857 instead of the predicted 1.000. The key was
pre-registered, and it was right to be: changing it now, after seeing which extra path the
`after` arm names, would be writing the rule after the result. It is reported as a
falsified prediction with the cause named, and the fix (a key that names the instruction
surface as an allowed citation) is offered as a pre-registration for a future experiment
rather than applied here.

**A per-tool row can print "unknown" where the truth is zero, and it does so in this
report.** `tool_calls.Read` and `tool_calls.Bash` on P5 show `n_b 0` and `-` for the
`after` arm. The cause is `experiments_measure._filled`, which gives a capture a tool
column only if some capture in the SAME arm used that tool, so a column no `after` session
ever used does not exist in that arm's table and the between-arm row has nothing to
compare. The `after` sessions all recorded a stream, so their Read and Bash counts are
real zeros. The row that carries it correctly is `tool_calls`, whose `after` values are
`0,0,0,0,0`. It is written up in E10.md under "What we rejected" rather than fixed:
`_filled` is not this task's to change, and the number a reader needs is on the page.

## WHAT CHANGED

`src/telltale/experiments_stop.py` (new, 171 lines). Six names and three tables. `checked`
validates a `stop` block: two positive whole numbers, an optional `basis` string carried
into the report unread, and any other key refused by name. `one_bound` refuses when the
specs of one suite carry different blocks, because a bound is a property of the suite and
one that held for a single arm would end the run at a session the other arm never had.
`session_tokens` returns the sum `telltale show` prints for a capture and the names of any
counter that was unknown. `crossed` compares a finished session with the bound, strictly
over, and returns the session's identity and the bound it passed. `record` is what the
report carries: the bounds, whether the run stopped, how many sessions were planned and
ran, the crossing, and the sessions whose token total nobody could compute.

`src/telltale/experiments_probe.py` (684 to 797). `probe` is now `suite([spec], ...)[0]`.
`suite` checks every spec and every answer key before any session starts, opens one store,
starts one receiver per spec (the receiver carries the content level and two arms may
declare two), and runs `_sessions`. `_order` is the repetition-major sequence and its
docstring says why the repetition is outermost and why, inside a round, the probe is outer
and the spec inner: the two arms' sessions for one probe are then adjacent in time, and
the pairing is by probe. `_repetition` now also returns `session_tokens` and
`session_tokens_missing`, read after the capture is written because the bound is compared
before the next session starts and the report is written after the last one. `_report`
takes the stop record, carries it under `stop`, tolerates an empty capture list, and adds
two warnings: one naming the session and bound that ended the run and saying that the n of
every table below is smaller than the spec declared, one naming any session with no token
total.

`src/telltale/experiments_env.py` (451 to 507). `stop` is an optional intervention spec
key, copied to both arm specs by `_arm_probe_spec`. `intervention` makes ONE `suite` call
with both arm specs instead of two `probe` calls. `_asserted` returns None instead of
calling `assert_between` when an arm has no capture. `_intervention_report` carries the
suite's `stop` record, allows a None assertion, and puts `_unasserted`'s sentence at the
top of the warnings when there is one.

`src/telltale/report_probe.py` (269 to 311). `_stop_line` is on every probe report and on
the intervention report, and it says one of three things: no bound in the spec so the
suite ran unbounded; the bounds and that no session crossed one; or the bounds, the
session that crossed, what it reached, and that nothing after it was started. Every form
prints how many of the planned sessions ran, and any session with no token total.
`_assertion_line` takes None and says that no assertion was made and why, which is neither
a pass nor a failure and must not print as either.

`tests/integration/test_stop.py` (new, 298 lines, 5 tests). A bound of 1 token, which is
under the floor of the scripted agent's cheapest session (506 tokens, computed in the file
from the agent's own constants rather than from a recorded run), ends a 12-session
intervention after one session; the store holds one capture and it is the one the report
names. The order test asserts all eight (task, attempt) pairs of a 2-probe, 2-arm,
2-repetition run, written out rather than derived, because deriving them from the
runner's own comprehension would assert that the code equals itself. A spec with no
`stop` reports the whole record with `bounds: None` and prints that it ran unbounded. Four
malformed blocks are refused before any session and before the database is created. And
the CLI test drives the console script and checks the written `intervention.json`.

`experiments/E10/check_numbers.py` (new, 159). E09's checker with two changes. It also
reads `experiments/E09/out/` when that directory has anything in it, and prints how many
files it read from each root, so a checkout that never ran E09 says so instead of
silently reporting E09's numbers as unmatched with no explanation. And it does not read
its own pasted output in the write-up: a record of a run is not a claim about one, and a
file that counted its own report of itself has no fixed point.

`docs/experiments/E10.md` (new, 654). The decision file. Prediction and rule quoted
verbatim before anything else, the two assertions pasted, the session order as a table,
the four repetition tables and the two between-arm tables pasted verbatim from `run.log`,
what each session actually opened, the cost per arm, what it means, what was rejected, how
sure we are per claim, and what downstream may say.

## UNSURE OR NOT DONE

- **Whether naming `AGENTS.md` in an answer is a citation or a mistake is a judgement, not
  a measurement.** The answer text is scored in the runner's process and dropped by
  design, so nothing here can quote it. What is measured is that the path appears only in
  the `after` arm, that it appears in six of ten `after` repetitions, and that no session
  in either arm opened the file. The reading in E10.md is the most natural one and it is
  labelled judgement in the "How sure we are" table.
- **P5's zero tool calls do not show that the agent verified anything.** The answer was
  correct against a key written before the run and it was produced without opening a file.
  This measurement cannot separate "it knew from AGENTS.md and was right" from "it
  repeated AGENTS.md and would have repeated it if AGENTS.md were wrong". The experiment
  that separates them is an arm whose AGENTS.md names the WRONG files. It is named in
  E10.md so nobody reads the zero as verification, and it is not run here.
- **`experiments_env.py` is in the diff and the brief's OWNS list does not name it.** The
  reason is in WHAT WAS WRONG: the intervention runner lives there and two arms cannot be
  interleaved without it. `experiments_factor.py`, which OWNS does name, needed no change
  and has none. A new source module was added for the 800-line ratchet, which OWNS does
  not name either.
- **`experiments_probe.py` is at 797 of 800 lines.** The next task to add to it must split
  it. The seam its own docstring already suggests is the SCORING (`score`, `_answer`,
  `_tokens`, `_named`, `_worded`), which is about 120 lines and does not run anything.
- **The seconds bound is implemented and is not covered by a test that crosses it.** Every
  bound must be a positive whole number, and a scripted-agent session takes about 0.4 s,
  so no legal seconds bound is under one. The token bound exercises the same comparison
  and the same stop path; what is untested is only the second entry of the `BOUNDS` table.
  Making it testable would mean a slow mode in the scripted agent, which is not this
  task's file.
- **`experiments.repeat` (the non-probe runner) has no stop bound.** The brief asked for
  it in the probe runner and the intervention, and that is what was built. A repeat
  experiment can still spend without a bound.
- **The demotion rule withholds several measures at n = 5, and the protocol cannot reach
  the n it asks for.** Design 6.12 caps scaling at `N = min(20, N_needed)`, and P5's
  `search_ops` and `unique_files_read` print `N_needed` 276. That is a fact about the
  rule, recorded rather than worked around.

## EXPLAIN FOR THE OWNER

**What was at stake.** We tell agents where to look. There is a file at the top of this
repository, `AGENTS.md`, that every session reads before it reads any code. Nobody here
had ever measured whether it does anything. If it does not, we should stop writing it. If
it does, we should know how much, because the forecasting lab wants to treat a change to
that file as a real event in a repository's history rather than as documentation.

**The experiment, in the smallest form that can answer it.** Take two questions we already
know are hard for an agent to answer about this codebase. Question one: trace
`telltale show` from where the command is parsed to where it reads the database, and name
every file on that path. Question two: which files decide what may be stored and how a
kept string is scrubbed. Now make two versions of the repository that differ in exactly
one thing: the second has a short section added to `AGENTS.md` called "Where things live"
that names, file by file, the answers to both questions. Ask each question five times on
each version. Twenty sessions. Nothing else differs: same model, same flags, same
machine, same everything.

**The hard part is proving that nothing else differs, and there are two checks because one
of them cannot see what the other can.** Before any session runs, we ask git what the two
versions differ in. It answered `AGENTS.md` and nothing else. After the sessions, we
compare the two environment records the recorder took while the agents were running.
Those records hold the model, the runtime version, the operating system, and a hash of
every instruction file. They differed in exactly one field, the instruction hashes, and
the report names the file inside that field with both hashes and both sizes: 6,197 bytes
before, 7,164 after. Neither check replaces the other. The environment record contains no
commit id at all, so it could not tell an instruction rewrite from an instruction rewrite
that also edited a module; the git check is what rules that out. And the git check cannot
see that the two runs used the same model; the environment record is what shows that.

**What happened, with one real session.** Take the storage question, run on the version
WITHOUT the new section, first repetition: capture `cap_01M1KDRG2GT1A1CY62RQSCZHJG`. The
agent ran five shell commands, opened two files (`allowlist.py` and `sanitize.py`), took
two turns, spent 235,228 tokens, and took 21.3 seconds. It got the answer right. Now the
same question on the version WITH the new section, first repetition:
`cap_01M1KDS5S35E1VRVDNV1CH1062`. The agent ran no command, opened no file, took ONE turn,
spent 36,492 tokens, and took 4.7 seconds. It got the same answer right. That happened all
five times, with no variation at all: zero tool calls, one turn, 34,679 to 36,573 tokens.
The other question did not collapse like that, but it changed shape: the sessions that had
the section ran four to six greps over the files the section names and opened one or two
of them, where the sessions without it opened up to four and ran seven to ten commands.
Discovery became confirmation.

**How the numbers were measured, and by what.** Every number above comes off a recording
the tool made while the session ran, not off a stopwatch or an estimate. Tool calls and
turns come from the agent's own output stream, counted by the recorder. Tokens are the
four counters the provider reports for every model request, summed the way
`telltale show` sums them: fresh input, cache reads, cache writes, and output. The two
scores come from a list of files somebody wrote down before any session started: recall is
how many of that list the answer named, precision is how many of the paths the answer
named are on it. The comparison between the two versions uses three statistics: the
Hodges-Lehmann shift (the typical difference between a session on one side and a session
on the other), Cliff's delta (how often one side beats the other, where -1 means always),
and an exact test that at five per side can go no lower than p = 0.008, which is what most
of the rows report. And there is a fourth number, the minimal detectable difference, which
says how small a difference five sessions per side could have separated from ordinary
run-to-run noise. Anything smaller than it is reported as "not resolved at n" and never as
"no difference", because those are different statements and only one of them is true.

**The prediction we wrote down, and how it failed.** Before any session, the brief
predicted three things: the effort would go down, the recall would stay at 1.000, and the
precision would be a perfect 1.000 on the version with the new section, because that
section names exactly the right files. Two of the three held. The third did not: on the
tracing question, all five sessions with the new section scored 0.857 instead of 1.000.
The reason is a single file name. Those answers named `AGENTS.md` itself, as the place
they learned the answer. `AGENTS.md` is a real file in the repository and it is not on the
list somebody wrote down, and the scorer's rule is that a named path which exists and is
not on the list counts against precision. That rule is not a bug. It is what stops
precision having an unbounded denominator: we can enumerate the repository's files, so we
can recognize a wrong one, and we cannot enumerate every wrong sentence an answer might
contain. What went wrong is that the list was written before anybody had seen an answer
from the new version, and it could not have anticipated an answer that cites its source.

**The answer we rejected, and why.** The tempting move is to add `AGENTS.md` to the list
and re-score. It would take one line and every number would come out as predicted. It is
the wrong move, and not by a small margin. The whole value of writing the answer down
before the run is that the run cannot change it; a key edited after seeing which extra
path the new version names is a key fitted to the result, and every number scored under it
afterwards would mean nothing. So E10 reports a falsified prediction with the cause named,
and the correct fix, a key that treats the instruction file as an allowed citation, is
offered as something to pre-register for a NEXT experiment, where it can be written down
before anybody sees an answer again.

**One more thing was built, and it is about not spending money by accident.** The previous
experiment, E09, had a spending limit written in its brief: no session over 200,000
tokens. Four of its sessions went over it and nobody found out until the whole run had
finished. The limit was not wrong; the runner could not act on it, because it ran the
first question three times, then the second question three times, and so on, so by the
time anything was checkable everything had already been spent. Two things fixed that. The
runner now goes round by round: one session of every question on every version, then the
next round. Four sessions is now enough to have seen everything once. And after every
single session it compares that session's wall time and its token total against a limit
the spec carries, and the first session over one ends the run there, with the report
naming which session and which limit. This run set the limit at twice the largest session
E09 ever produced on these two questions. Nothing crossed it. One session came close:
1,007,870 tokens on the eleventh session, which is 55 per cent more than E09's largest.
Under E09's own limit that session would have ended the run, and we would have known
within four minutes instead of at the end.
