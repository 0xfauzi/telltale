## EXPLAIN FOR THE OWNER

### The question, in one line

Telltale reads a coding-agent session and prints a summary of it. Is that summary good
enough to diagnose the session with, or do you have to read the raw log? That is what H1
asks, and until today nobody had tested it.

### How you test a thing like that without fooling yourself

You cannot ask the summary whether it is good. You have to ask a reader. So: take a real
session that already happened, show one reader only the summary, show another reader only
the raw log, ask both the same ten questions, and mark both against answers written down
in advance.

Three details do all the work.

**The answers were written first.** `experiments/E12/key.json` was built from the raw logs
by a script, before any reader existed, and I could not edit it. That is what stops the
experiment from becoming a search for a flattering scoring rule.

**Neither reader could see the other's material, or anything else.** Each reader is a
fresh `claude` session started in an empty temporary directory that holds only its own
material. I put that directory outside this repository on purpose. Claude Code walks up
from wherever it starts looking for a `CLAUDE.md` instruction file, and this repository
has one, sitting right next to the answer key. A reader started inside the repository
would have been one `cat` from the answers.

**The prompt says nothing about which session it is.** No task id, no date, no "this is
the summary arm". Both readers get the identical prompt, byte for byte. The runner checks
this itself and refuses to launch if a task id has crept in.

### One real reader, one real session

The session under review is W4-T1/1, a build session from this wave. Its raw log is
1440338 bytes. Telltale's summary of it is 34649 bytes across three files: the summary,
the timeline, and the evidence vector.

The summary reader spent 82 seconds and 149323 tokens and got 6 of 10 right.
The raw reader spent 106 seconds and 588848 tokens and got 9 of 10 right.

Here is the question that separates them, and it is the interesting one. Question 2 asks
how many pytest runs failed. The truth, from the raw log, is 6. The summary prints this:

```
"failed_test_runs": 0,
```

and, a few lines below, this:

```
"11 of 11 verification runs have a masked exit status, so this count covers only the
 runs whose outcome a surface stated ... no test run reported a failing exit status,
 which is not the same as every test passing"
```

Telltale did the right thing. It said 0 and it said, in the same document, that 0 here
means "I could not see". The reader read the number and not the sentence, and answered 0.

That is the single most useful thing this pilot produced, and it is a finding about how a
summary gets read rather than about whether it is correct. A warning that sits beside a
number is a warning that competes with the number, and the number wins. Whether that
happens on one session or on all six is what the full run would tell you. I have one
observation and I am not going to call it a pattern.

### Why I stopped

You set two limits per reader before any of this ran: ten minutes and 400000 tokens.
The raw reader spent 588848. That is 188848 over.

Where did they go? 534249 of the 588848, 91 per cent, are cache reads. The reader loaded a
1.4 MB file into its context and then made 15 requests to the model, and every one of
those requests carries the whole file again. Cached, so it is cheap per token, but it is
counted. The summary reader made 5 requests over 34649 bytes and spent 149323.

I could have made the number fit. Drop cache reads and the raw reader spent 54599, well
inside the bound, and the experiment would have carried on. I did not, and here is the
evidence that stopped me: E05's sessions are recorded in this repository with
`tokens_total` 173598 for capture `cap_01M1HQJD1PD1B6QKETVDHWDM6N`, and that capture's
four counters are 10, 156028, 16931 and 629. They add to 173598 exactly. A token total in
this repository has always included cache reads, and the 200000 bound you set for E09 was
set against that same E05 figure. Picking a different definition after seeing which one
lets the run continue is picking the answer.

So the pilot did what a pilot is for. It found that the estimate behind the bound was
wrong, before 12 sessions were spent finding out.

### What it would cost to finish

At the pilot's rates: 6 summary sessions at 149323 and 6 raw sessions at 588848, about
4429026 tokens and about 22 minutes of reviewer wall. That is arithmetic on one session
per arm, so treat it as an order of magnitude. The largest raw file in the set is W3-V/1
at 1642861 bytes, 14 per cent larger than the one measured.

Nothing is running. `experiments/E12/out/` holds the two pilot records and the material
scan; the store holds the two captures. Saying "run it" is one command and it starts
nothing until you do.

### The thing I found that you should probably fix somewhere else

The protocol's guard against a reader cheating is: look at the paths that reader opened,
and if any is outside its own directory, throw the run away. Telltale records those as
`file_read` activities.

Both readers produced zero `file_read` activities. Neither used the Read tool. Both used
`cat` and `grep` and, in the raw reader's case, a Python script over the log. Those are
recorded as commands, not as file reads. A reader that ran `cat ../../key.json` would
have sailed through the check with a clean record.

So I added a second check that reads the stored command text and flags any word in it
that names a path outside the material. On the raw reader it flagged two. Telltale stores
a path outside the repository as `<outside>/` plus eight hex characters of a hash, so
neither was readable on its face. The hash only goes one way, so I hashed candidate paths
until two matched: one was the reader's own directory, from an `ls -la`, and the other was
`/tmp/pytest_cmds.txt`, a scratch file the reader had written out of its own log and then
read back.

Neither is cheating, so I left the run standing. I did not promote my new check into the
invalidation rule either, because inventing a stricter test after seeing which arm trips
it is the same mistake as loosening the token definition, just pointed the other way. The
check reports and the report says what it found. Whether it becomes a rule is your call,
made before the next run rather than during it.

apart, before any reviewer launches, and then one session and arm at a time with the
addendum's policy after each, which is to move a launch that produced no tokens or an
`api_error` result into `out/failed/`, wait 600 seconds and try that session once more.
The gate opened at 16:28 after one failed streak, and every one of the twelve then
succeeded on its first try, so the 600-second retry never fired. The driver is
`out/driver2.py`, which is gitignored with the rest of `out/`, and it decides only whether
a launch was a session. It does not score, does not touch the key and does not read a raw
stream.

## EXPLAIN FOR THE OWNER

### What was actually tested

Telltale reads a coding-agent session and prints a summary of it. The question is whether
that summary is enough to diagnose the session with, or whether you have to read the raw
log. The pilot asked it of one session and could not answer, because the rule you set
needs six sessions in each arm before it will say anything. This run has six.

The method has not changed since the pilot. Twelve fresh Claude sessions, one per session
per arm, each started in an empty temporary directory outside this repository holding only
its own material, each given the identical prompt built from the answer key's own question
text, each marked against answers that were written from the raw logs before any reviewer
existed. The only thing that moved is the token ceiling, from 400,000 to 2,000,000, and a
ceiling decides whether a run continues. It is not part of the marking.

### The answer

Eight of the ten questions: the summary reader did as well as the raw reader. Both got 6
of 6 on the pytest count, the files-edited count, the tool-error count, the compaction
count, the subagent count, the outcome and the output-token count. On one question, "was
anything edited after the last test run", the summary reader beat the raw reader 6 to 5.

Two questions went the other way, and they are the interesting ones.

**Question 2, how many pytest runs failed.** The summary reader answered "unknown" on all
six sessions. Every test run in all six sessions pipes its output into `tail`, which
throws the exit status away, so Telltale cannot see whether they passed. Since W4-F3 it
prints null there rather than a count, and says in the warning what it could not see. Six
readers out of six read that and declined to guess. The raw reader, which can count the
failures in the log itself, got 5 of 6 right.

Under your rule that is "summary insufficient", and it should be, because the reader did
not get the number. But look at what the pilot did on the same question before W4-F3.
Telltale printed `failed_test_runs: 0` with a warning beside it saying that 11 of 11 runs
had a masked exit status. The pilot's reader took the 0 and answered 0. The truth was 6.

So the change from printing a misleading number to printing nothing turned one confident
wrong answer into six honest ones. That is the recorder's core promise working: unknown
stays unknown. The cost of keeping it is that the summary cannot answer a question the
stream can.

**Question 8, how many `git commit` calls.** The summary does not carry that count at all.
Three of six summary readers said unknown, two guessed from the timeline and got it
wrong, one was right. The raw reader got 4 of 6. There is also a defect in the question
itself, found by the pilot and confirmed here: it asks for the number of Bash calls that
ran `git commit`, and a single call whose script contains the phrase twice is one call,
not two. Four readers across the two runs counted phrases. The key counts calls and the
key is right. I did not change the question or rescore anything, because the question was
frozen before any reader existed and moving it after seeing the answers is how experiments
learn to flatter themselves.

### What it cost, and the surprise in it

Twelve sessions, 10.84 US dollars, 35 minutes of wall, 6,588,489 tokens.

The pilot said the raw arm would cost about 3.9 times the summary arm. At six sessions per
arm the ratio is 1.647, and the raw arm is actually FASTER: 138 seconds at the median
against 178. Two things account for it. The W4-F3 rebuild made the summaries larger, so
the summary readers had more to read and took more turns; and one summary reader spent 486
seconds on a single session, more than twice any other, for no reason the record explains.

Strip out the cached context and the two arms are nearly the same size: 46,686 tokens
against 51,666 at the median. Almost everything either arm spends is the same context read
again on every request, 88 per cent of a summary session and 92 per cent of a raw session.
The interesting saving from the summary is not the token bill, it is that a 38,063 byte
file fits where a 1,440,338 byte one does not.

### Why the run started late

The Anthropic API was returning 529 Overloaded when I began. Attempt 4 had already lost
three reviewer launches to it: ten retries, no answer, zero tokens, and a capture that
looks like a session until you read its stream result. I launched once at 16:12, saw the
capture take 7 retries in 50 seconds, and stopped it rather than let twelve launches fail
one after another. Then I put a gate in front of the run: three one-turn Opus calls in a
row that actually return, sixty seconds apart. The gate opened at 16:28 and all twelve
sessions then succeeded on the first try.

Those four captures are in the store and they are not sessions. They are named in the
write-up with their retry counts and their zero costs, and no arm's median includes them.
A launch that spent nothing and answered nothing would drag a cost median downward while
looking like evidence.

### The thing I found that you should fix somewhere else

Three of the six raw readers independently wrote a scratch file at `/tmp/cmds.txt`, dumped
the commands out of their own log into it, and grepped it. They ran one after another, so
each overwrote the last, and each wrote before it read. Nothing went wrong. But the
protection was accident: had two run at once, or had one read before it wrote, a reader
would have answered about a session it never saw, and the blinding check would not have
noticed, because the check looks for reads outside the material directory and `/tmp` is
outside every reader's material by design.

For W3-V/1 I could not see the write in the record at all, because it happened inside a
`python3 -c` program and the launcher stores that text sanitized. What settles it is the
reader's own answers: it said 10 failed test runs and 0 files edited, which are W3-V/1's
key values, where the session that had written that path nine minutes earlier has 6 and 6.
It read its own file.

The fix is one line in the harness, giving each reader its own temporary root, and it
belongs in a brief of its own before the next blinded study rather than in the middle of
this one.
