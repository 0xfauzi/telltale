# W4-F1: one index on evidence(capture_id), decided by measurement

Orchestrator fix, branch `task/W4-F1` from `main` at 47815c5. The wave 4 gate report
carried "needs measuring before it is decided: the writer cost of one index on
evidence(capture_id)", because W4-T2 found every per-capture evidence read to be a scan
(22 ms each, 0.75 s of every profile) and W3-T3 had dropped an index on observations
for its writer cost. This closes the question with numbers.

## OUTCOME

`CREATE INDEX IF NOT EXISTS evidence_by_capture ON evidence (capture_id)` in schema.py,
beside the table. Every store on disk gains it at its next open. One test in
tests/integration/test_schema.py asserts SQLite's own query plan for the capture-scoped
SELECT and DELETE names the index after an open of an old store, and says SCAN before.

## WHAT WAS WRONG

Nothing was wrong in the sense of a false number. The write path was paying for a scan
that nobody had noticed: `replace_evidence` and `rebuild` both begin with
`_delete_by_capture`, which is `DELETE FROM evidence WHERE capture_id = ?`, and with no
index on that column the delete walks all 129089 rows before it writes anything.

## WHAT CHANGED

The measurement, 2026-09-03, on a `.backup` copy of the owner's store (1541439488
bytes, 129089 evidence rows, 348702 activities, 3227 captures with evidence), script
kept in the orchestrator's scratchpad, arms interleaved none/index/none/index so both
share the same cache state:

| Arm | delete-and-reinsert of one capture, 41 rows, median of 10 | `profile <repo> --by subsystem`, 3 runs | `rebuild` of the 20 most recent captures through the CLI, total | index build |
|---|---|---|---|---|
| none | 16.39 ms | 1.133, 1.112, 1.115 s | 12.09 s (median 0.568, max 0.812) | - |
| index | 0.82 ms | 0.611, 0.613, 0.618 s | 10.64 s (median 0.532, max 0.572) | 0.078 s |
| none | 16.55 ms | 1.462, 1.124, 1.128 s | 11.83 s (median 0.566, max 1.023) | - |
| index | 0.81 ms | 0.620, 0.622, 0.624 s | 11.17 s (median 0.547, max 0.667) | 0.079 s |

The rebuild column is mostly process start (`uv run telltale` per capture); the
per-capture medians move by 20 to 36 ms, which is the delete. The reinsert column is the
index maintenance isolated: 41 rows inserted under the index cost less than one scan.

Break-and-restore, pasted: the test against the schema without the CREATE INDEX line
`1 failed, 1 passed in 0.33s` (FAILED
test_an_existing_store_gains_the_index_every_capture_write_reads); with it `2 passed`.
Gates in the branch worktree: 248 passed, 2 deselected; mypy 89 files clean; ruff,
format, deptry clean; pre-commit all files.

## UNSURE OR NOT DONE

- Read path timings are on a store with 3227 captures. The index's advantage grows with
  the table and the writer cost stays per row; neither was measured at another size.
- `activities` already carries `activities_by_capture`; `series_snapshots` and
  `forecast_runs` have no capture column. No other table has this shape.

## NEXT

Rebuild of the home store after W4-T3 merges runs 3227 deletes on this table; with the
index that is 3227 x 0.8 ms instead of 3227 x 16 ms. The gate report's bullet is closed
in the same commit.
