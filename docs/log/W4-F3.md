# W4-F3: unknown outcomes make a verification count None; a tool error survives a masked chain

Orchestrator fix, branch `task/W4-F3` from `main` at 4d49fa1. Two defects, both found by
the E12 pilot: a verification count printed 0 over runs whose outcome nobody observed,
and a tool call's own error was thrown away whenever the call was a shell chain whose
status belonged to another program.

## OUTCOME

Four numbers are now null rather than a count over what was visible:
`failed_test_runs`, `fail_to_pass_cycles`, `edits_after_last_successful_test` and
`post_failure_revisits`. Each asks the question of its own scope, through one function,
`measures_intervals.outcomes_known`. Coverage stays `partial` and the warning gained the
counts the null no longer prints.

A masked chain's row now carries the CALL's success, from the same three routes an
unmasked call uses, so a tool error on such a chain is recorded and printed. The exit
code stays off the row, which is W4-T3's decision and is untouched.

On the six E12 material captures, all four numbers are null on all six at coverage
`partial`, and the timeline gained 4 `failed` rows (12 to 16, one per `is_error`
tool_result that sits on a masked chain) and 109 `check masked` rows.

## WHAT WAS WRONG

**The count over nothing.** W3-T3 stopped a masked chain's exit status being read as the
check's, which was right, and then printed the count over the runs that were left, which
was not. `telltale show` for W4-T1/1 said `failed_test_runs: 0` while its own warning
said "11 of 11 verification runs have a masked exit status". The 0 is a count over an
empty set. The E12 arm S reviewer, who read only `show`, `timeline` and `vector`,
answered "0 failed pytest runs" for a session whose raw stream holds 6, and "yes, an
edit after the last pytest run" where the raw stream says no.

position it could not locate.

**The dropped tool error.** `activities_tools._tool_outcome` returned as soon as it had
written `exit_masked`, before any of the three routes that state whether the call
succeeded. So a masked chain recorded no outcome at all, and the timeline printed `-`.
Measured: 4 of the six captures' 16 `is_error` tool_result rows sit on a masked chain.
W4-T1/1's is

    uv run ruff check . && uv run ruff format --check . && uv run mypy . 2>&1 | tail -2

whose stream tool_result carries `is_error` true. The reviewer answered "0 tool errors"
for that session, and the timeline agreed with them: 74 `ok` rows, 128 `-` rows and 0
`failed` rows in 202.

## WHAT CHANGED

**`src/telltale/measures_intervals.py`.** `failed(run)` returns None when the row carries
`exit_masked`, before it reads `exit_code` or `success`. That order is the whole guard:
the row now HAS a `success`, and it is `tail`'s. New `outcomes_known(runs)` is the one
place the question "may a count be printed at all" is asked. `fail_to_pass(runs)` returns
None when it is False. `post_failure_revisits(activities)` returns None when any
verification run in the capture states no outcome. `epochs(...)` returns
`edits_after_last_success` None when an unknown run sits after the last known success, or
when no success is known and some run's outcome is not; the existing 0 survives only
where every run stated an outcome. Return types widened to `int | None`.

**`src/telltale/activities_tools.py`, `_tool_outcome` only.** The masked branch writes
`exit_masked` and falls through to the same three success routes as any other call.

**`src/telltale/measures_spec13.py`.** `failed_test_runs` is None when
`outcomes_known(tests)` is False; the other three take the None from the walks. All four
carry the `_masked` warning and take their coverage through `_stated`, which now accepts
the extra capability names a metric needs, so `edits_after_last_successful_test` and
`post_failure_revisits` still weaken on paths and commands as they did. `_stated` asks
`outcomes_known` instead of looking for a `success` or `exit_code` field, which is the
trap the brief named: with the field now present on masked rows, the old `_stated` would
have printed `observed` over a null. `_masked` gained "Of the K runs whose outcome a surface stated, J failed", counted
over the metric's own scope. The source list of a null is every run read, never the empty
list of failures.

**`src/telltale/report.py`.** `_outcome` splits into the word and the mask suffix:
`ok, check masked`, `failed, check masked`, or `check masked` alone. Unmasked rows are
byte-identical.

**`src/telltale/series.py` - outside OWNS, and here is why.** `_State.consume` reads
`fields.get("success")` off a verification_run to keep the `last_verification_failed`
column, and the change above put that field on masked rows. Left alone, a masked chain
would have cleared a real failure because `tail` exited 0. Measured on the six captures,
with the guard and without: with it, the column is identical on all six to what it was
before this branch; without it, W3-E08/1's failure is cleared five rows early, 16 rows of
`last_verification_failed` 1 becoming 11. The change is one expression, passing None for
a masked row, and it makes the column exactly what it already was. It is flagged here
because the brief did not name the file.

## UNSURE OR NOT DONE

**The Codex reducer is now asymmetric with the Claude one, and I left it that way.**
`activities_codex.py` skips its `_outcome` entirely on a masked chain, so a Codex masked
verification row still carries no `success` and its timeline row reads `check masked`
alone rather than `ok, check masked`. The brief scoped the change to
`activities_tools._tool_outcome`, and `activities_codex.py` is the Codex half of the same
reducer, so I did not touch it. Nothing in the metrics differs, because `failed()`
returns None for both. What differs is one word in the timeline and one dropped fact: a
Codex tool that errored on a masked chain records nothing, exactly as Claude did before
this branch. No Codex fixture has a masked verification run, so I have no capture that
shows the difference; measuring it needs a Codex session that pipes a check into
something. Owner's call.

**`series.py` and `test_series.py` are outside OWNS.** Both edits are argued above with
the measurement that forced them. The series one is behaviour-preserving by measurement,
not by argument.

**`_NONE_FAILED` still fires beside a null.** When every test run is masked, the warning
list holds both the masked sentence and "no test run reported a failing exit status".
The second is true of the runs that stated an outcome and is now largely redundant. I
reworded its tail rather than gating it, because dropping a warning is a change to what a
reader is told and the brief did not ask for one.

**The `epochs` rule reads "after", not "at or after".** The brief says
`edits_after_last_success` is None when an unknown run exists "at or after" the last known
success. A run AT the last known success is by definition known, so the implemented rule
is "after", plus "no known success and some run unknown". I believe those are the same
set; if the owner meant something narrower by "at", it is one line in `epochs`.

## EXPLAIN FOR THE OWNER

Here is the problem in one line: the recorder told a reviewer that no test run failed,
and six had.

Start with what a shell does with a chain of commands. When you write
`uv run pytest 2>&1 | tail -50`, two programs run. pytest runs, and its output is fed to
`tail`, which prints the last fifty lines. The shell then reports one exit status for the
whole thing, and that status is `tail`'s, because `tail` is what finished last. `tail`
almost always succeeds. So the shell says 0 whether the tests passed or failed. We call
such a run masked, and the reducer marks the row `exit_masked`.

W3-T3 found that and fixed the obvious half. Before it, the recorder read that 0 as
"pytest passed". After it, a masked run states no outcome at all. Correct, and it is
where the trouble started.

Because the counts kept counting. `failed_test_runs` was the number of test runs that
reported a failure, and after W3-T3 a masked run reported nothing, so it fell out of the
numerator. The denominator was never printed. On the E12 session W4-T1/1, all eleven test
runs were masked, so the recorder printed:

    failed_test_runs: 0

and, further down the same JSON, a warning saying eleven of eleven runs had a masked exit
status. Those two statements are in the same file. Nobody reads a warning list to find
out whether a 0 is a real 0.

The reviewer did not. Reading only `telltale show`, `telltale timeline` and
`telltale vector`, they answered "0 failed pytest runs". The raw stream-json of that
session holds 6 failing pytest runs, which is what the pre-registered E12 answer key says
(`experiments/E12/key.json`, built from the provider's own stream before any reviewer
session ran). They also answered "yes, an edit after the last pytest run", where the raw
stream says no, and "0 tool errors", where the raw stream has 1.

So: what should a count over an empty set say?

**The answer I rejected first, because it is what W3-T3 shipped: print the count over the
runs whose outcome somebody stated.** It has a real argument behind it. The number is
true. Every failure it counts really happened. It is never an overstatement. And the
coverage word was already `partial`, which is the recorder's way of saying "this is not
the whole picture".

What killed it is what the number is FOR. `failed_test_runs` is not read as "failures
among the runs we could see". It is read as "did anything fail". A person deciding whether
to trust a session's work reads 0 and stops. There is no reading of `0` at coverage
`partial` that gets them to "six tests failed and this recorder cannot see any of them".
The measured proof is the reviewer: given the true number in a warning one screen down,
they answered 0. And the coverage word cannot carry the weight, because `partial` also
means "one of eleven runs was masked and the other ten failed" - which is a number worth
printing. One word cannot mean both.

So the rule is: if any run in a number's scope has no observed outcome, the number is
null. Not smaller. Absent. This is AGENTS.md invariant 5, "unknown stays unknown, never
zero-fill", applied one level up from where it was already applied. The invariant was
already true of a single run. It was not true of a count over runs.

Four numbers depend on an outcome and all four take the rule. `failed_test_runs` and
`fail_to_pass_cycles` obviously. `edits_after_last_successful_test` less obviously, and
this one is worth a sentence: it counts the edits made after the last passing check, so
it needs to know WHERE the last passing check was. If a run after that point has an
unknown outcome, it might have been a pass, and then the count starts from the wrong
place. `post_failure_revisits` counts edits within three edits of a failing check, and an
unknown run might have been the failure that opened the window. Same shape of argument,
four times.

They are asked in one place. `measures_intervals.outcomes_known(runs)` returns true when
every run in scope states an outcome, and each metric asks it of its own scope:
`failed_test_runs` asks about the test runs, the other three about every verification
run. That is why W4-T1/1's warning says "11 of 11" for the first and "20 of 21" for the
others.

The null needs to carry what it stopped saying, or it is just a shrug. So the warning
gained a second sentence: "Of the K runs whose outcome a surface stated, J failed". On
W3-V/1 that reads "Of the 0 runs" and on W3-E08/1 "Of the 7 runs ... 2 failed". A reader
now sees the difference between a session nobody could measure and one where seven of
twenty-seven runs were legible. Both K and J are counted from the rows, never estimated.

Now the second defect, which is smaller and sharper.

The same chain that hides pytest's result does NOT hide the tool call's own result. Those
are different facts. "Did the check pass" is about pytest. "Did the tool call work" is
about the shell command as a whole, and Claude Code states it directly: the stream's
tool_result block carries `is_error`. The reducer was returning as soon as it had written
`exit_masked`, before it read any of that. So a masked chain recorded no outcome at all,
and the timeline printed a dash.

Measured on the six E12 sessions: 4 of their 16 error results sit on a masked chain, and
all four vanished. W4-T1/1's is a chain ending
`uv run ruff check . && uv run ruff format --check . && uv run mypy . 2>&1 | tail -2`,
whose tool_result is an error. The reviewer answered "0 tool errors", and the timeline
backed them up: 202 rows, 0 of them `failed`.

The fix is to mark the row masked and then read the call's outcome exactly as for any
other call. The timeline says `ok, check masked` or `failed, check masked`. Two facts,
two clauses: the call ran and exited 0, and nobody saw how the check inside it ended.
W4-T1/1's timeline now has one `failed, check masked` row where it had none.

The exit CODE stays off the row. W4-T3 decided that and I did not touch it, and the two
decisions are not in tension: an exit code on a chain is a different program's status,
while `is_error` is the tool call's own. The observation still holds the code and
`telltale explain` reaches it.

Two traps in this, both of which the brief named and both of which are real.

The first: `measures_intervals.failed` must check `exit_masked` BEFORE it reads
`success`, because after this change the row has a `success` and it belongs to `tail`.
Get the order wrong and `tail` exiting 0 reads as the tests passing, which is the exact
defect W3-T3 removed, restored by the fix for a different one. The guard is the first two
lines of the function.

The second, one level up: `_stated` decided the coverage word by looking for a `success`
or an `exit_code` field on the row. Once masked rows carry `success`, that function would
have said "every run stated an outcome" and printed coverage `observed` over a value that
had just become null. Stronger word, weaker number. It now asks the same
`outcomes_known` the values ask, so the word and the number cannot disagree.

There is a third trap the brief did not name, and I found it by running the suite.
`series.py` builds the forecasting inputs, and one of its columns,
`last_verification_failed`, reads `success` off a verification run directly. Putting
`success` on masked rows would have made a masked chain CLEAR a real failure. I measured
it on the six captures rather than reasoning about it: with the guard, the column is
identical on all six to what it was before this branch; without it, W3-E08/1's failure is
cleared five rows early, sixteen rows of 1 becoming eleven. So series.py got a one-line
guard, and it is flagged in UNSURE because the file was not in my scope.

How I know each number here. The table of six captures, the is_error counts, the
before-and-after timeline counts and the series column comparison are all measured, by
scripts run against a `.backup` copy of `experiments/E12/out/store` with the code before
and after; the commands are in VERIFY above. The reviewer's three wrong answers are from
`docs/experiments/E12.md` on `task/W4-E12`, and the true values they were wrong about are
from `experiments/E12/key.json`, which was built from the raw stream before any reviewer
session ran. The claim I have NOT measured is the one in UNSURE about Codex: no Codex
fixture has a masked verification run, so the asymmetry between the two reducers is
reasoned and not observed.

One last thing worth saying plainly. This change makes the recorder say less. Six
sessions that used to report four numbers each now report null for all four. That is not
a regression to be fixed later, it is the recorder telling the truth about what these
surfaces can see, and the honest response to it is not to soften the rule. It is to make
more chains legible - which is a capture question, not a measurement one, and it is not
this task.
