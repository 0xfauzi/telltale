# W4-T1 probe runner and correctness scoring

## OUTCOME

`telltale experiment probe <spec.json> [--out DIR]` runs a suite of fixed read-only
probes: each probe is a prompt substituted into one fixed argv, run N times, each
repetition in its own detached worktree at one pinned base commit under one environment
fingerprint. The agent's final answer is scored against an answer key of repository
paths and symbols written before the run, and the report prints the two score rows in
the same table as spec 13.7's 22 measures, because spec 14.3's last sentence is a rule
about reading and it can only be followed when both halves are on the page at once.

`telltale experiment intervention <spec.json> [--out DIR]` runs the same suite at two
commits, before and after a scoped refactor, and pairs the two arms BY PROBE. The two
arms' argv must be token-identical and their commits must differ; the post-run
fingerprint assertion is inverted for this factor and requires them to differ in NO
field, which is spec 14.3's "the environment fingerprint is held constant" written as a
check.

## WHAT WAS WRONG

**Precision as it is normally defined is not computable from an answer, and the brief
said so before I could get it wrong.** The textbook denominator is everything the answer
asserted, and there is no way to enumerate what an arbitrary sentence claimed: an agent
that writes "it is probably in the parser somewhere" has asserted something, and no
counter can say what. So precision here is `matched_keys / (matched_keys +
wrong_paths)`, where a wrong path is one the answer named, that EXISTS at base_sha, and
that the key does not carry. The repository is what makes the denominator finite.

That has a consequence worth stating plainly rather than burying: a wrongly named SYMBOL
is counted nowhere. A repository enumerates its own paths and does not enumerate the
symbols an answer could invent, so an answer that names the right file and three
functions that do not exist scores precision 1.0. The number is an UPPER BOUND on
precision, not an estimate of it, and every report says that in its assumptions. It is
still worth having: it separates "named the one right file" from "named the right file
and four wrong ones", which is the distinction spec 14.3 asks for.

**A probe condition cannot be resumed, and the repeat runner's resume would have made a
hole that looks like a measurement.** `experiments.repeat` reads attempt k back out of
the store when a capture already claims it, and that is right for it: everything its
report needs is on the capture. Nothing on a probe capture is the score. The score comes
from the agent's answer, which this runner reads and drops on purpose, so a resumed
repetition would enter the statistics with precision None and recall None while the
table beside it says n = 3. I did not discover this by running it; the shape of the
report made it visible before it could happen, which is why the fix is a refusal that
names the captures and says to purge them or use a new experiment id, and not a
`from_store` that returns a report full of holes.

**An answer key can be wrong, and a wrong key looks exactly like a failing agent.** A
key naming `src/beta.py` at a commit that does not carry it scores recall 0 in every
repetition. Nothing in the report would say why. So the key is checked against
`git ls-tree` at base_sha before anything runs and a missing path is a refusal that names
it. The cost is real and I chose it deliberately: an intervention that reuses one key
across two commits now REQUIRES the key to exist at both, so a refactor that moved the
answer refuses rather than scoring the agent down for the move. Forcing the operator to
update the key is the right way round, because only the operator knows whether the move
was the thing under test.

**The environment fingerprint cannot carry the commit, so the base_sha assertion had to
be inverted rather than extended.** Every other factor of `experiment environment` is a
field of the fingerprint payload, and the post-run check is "the arms differ in exactly
that field". base_sha is not a field there and must not become one: a fingerprint that
carried the commit would make every repository comparison a comparison of two
environments, and every commit a changepoint for every measure. So for this one factor
the arms must differ in NO fingerprint field. Measured: two commits differing by one
added source file give the same fingerprint id, so the assertion holds; and it is not
vacuous, because `instruction_hashes` IS a fingerprint field and env.py reads it out of
each arm's worktree, so a refactor that also touched AGENTS.md is caught there and named.

That leaves one gap that only a spec check can close. A spec that declares `effort` and
quietly gives its two arms different commits would pass the argv check (base_sha is not
in the argv) and pass the fingerprint check (the fingerprint has no commit), and report a
model difference while saying nothing about the two repository versions the arms actually
ran. `_one_base_sha` is that check, and it refuses naming both commits and the declared
factor.

**One thing I got wrong twice while writing the test, both times the same mistake.**
I asserted a phrase that the source string wraps across a newline
(`"Cheap behaviour with a wrong answer is not an improvement"` is `Cheap\nbehaviour ...`
in the rendered text), and I asserted `n_a == n_b == REPETITIONS` over EVERY between-arm
row when two metrics are unknown to the fake agent in both arms and correctly report
n = 0 on both sides. The second one is the more interesting: my assertion was the one
that assumed absence is zero, in a test written to check that the code does not.

## UNSURE OR NOT DONE

**Precision is an upper bound and no measurement here bounds how loose it is.** A wrongly
named symbol is not counted, so an answer that names the right file and four functions
that do not exist scores 1.0. Bounding this needs a symbol index of the repository at
base_sha, which is a language-specific parser and a much larger piece of work than this
task. Until then, a probe suite that cares about symbol precision should put the symbols
in the key and read `matched_symbols` per repetition rather than trusting the ratio.

**The between-arm warning tail is long enough that nobody will read it.** An intervention
over 28 metrics prints 37 warning lines, and two sentences account for 33 of them (the
spread-of-0 warning and the pooled-median-of-0 warning, once per metric). Those come from
`stats.compare` and the environment runner has had the same tail since W2-T3. Grouping
them by text with the metric list would make both reports readable, and I did not do it,
because changing the shape of `experiment environment`'s output was not this task's to
decide. It is a one-function change in whichever task owns it next.

**`n_needed = 0` at a spread of 0 reads as "no repetitions are needed".** It is
`stats.n_needed`'s arithmetic (`ceil(2 (2.8 * 0 / x)^2)` = 0) and it is shared with the
environment runner, so I did not change it. The probe report warns when a score column's
spread is 0, which is the case the fake agent always produces; a real agent's answers
would vary and the number would mean something. If the owner wants it to be None at
`s = 0`, that is one line in stats.py and it changes W2-T3's output too.

**Nothing here has been run against a real agent.** Every number in this report is the
scripted agent's, and its answers are fabricated by design. What is verified is the
harness: the worktrees, the correlation and outcome records, the scoring arithmetic, the
two assertions and the fact that the answer text does not reach the store. Whether a real
`claude -p` prints its final text in the `result` field of the last stream-json message
is a fact I took from the allowlist and the E01 fixtures rather than measuring today; the
runner's `_answer` skips any line it cannot parse and returns None when it finds no
usable `result`, so the failure mode if that is wrong is unknown scores and a warning
that says so, not a wrong number.

**The intervention pairs by probe but does not pair by repetition.** Repetition 1 of the
"before" arm and repetition 1 of the "after" arm are not a matched pair in any sense, and
`stats.compare` treats the two arms as independent samples, which is what design 6.12
specifies. "Paired by probe" means the comparison is made within a question. A
repetition-level pairing would need the runs to share something they do not.

**One inconsistency in the branch's history.** `docs/design/amendments/W4-T1.md` landed
whole in the first commit, so at that commit it documents an intervention runner that
arrives in the second. The branch merges as a unit and the working tree is consistent; I
mention it so nobody reading the first commit alone concludes the file is wrong.

## EXPLAIN FOR THE OWNER

### What a probe is, and why this is different from everything before it

Every experiment in this system so far has measured how an agent WORKED. Repetitions of
one task under one environment (W1-T4) tell you how much a token count moves when nothing
moves. Two arms differing in one flag (W2-T3) tell you whether a flag shifts that count
further than run-to-run noise does. Both are measurements of effort. Neither asks whether
the agent was right.

A probe asks that. It is a question with a fixed, checkable answer that a person writes
down BEFORE the run: "which file implements the thing behind this interface?", "which
tests cover this module?". The answer key is a list of repository paths and a list of
symbols. The agent gets the question as its prompt, runs read-only in a disposable
worktree at a pinned commit, and says something. The runner scores what it said against
the key.

The key is written first, and that is not a formality. A key written after seeing the
answer is not a key, it is a description of the answer, and the number it produces means
nothing. This is why the spec calls them "fixed" probes and why the runner refuses a key
naming a file that does not exist at the pinned commit: the check that the key is
answerable happens before the agent is started, when it is still an honest check.

### Why the answer is scored and the text thrown away

Two separate reasons, and they happen to point the same way.

The first is privacy, and it is the whole reason this system is trustworthy enough to run
beside somebody's real work. Telltale's design says the recorder never stores what an
agent said. Assistant text, tool results, prompts, file contents: all of it is in a list
called NEVER_PERSIST, dropped at the boundary regardless of what any provider sends. A
final answer is assistant text. If a probe runner wanted to store it "just for scoring",
it would be the first exception, and a rule with one exception is a rule with a queue
forming behind it.

The second is that the text is not the measurement. The measurement is two numbers, and
those numbers are computed from the text and a key. Once they exist, the text is a large
blob whose only remaining use is to let somebody recompute the numbers differently later,
which is exactly what a pre-registered protocol forbids.

So the runner does what a harness does: it reads its child's output in its own memory,
computes what it needs, and lets the rest go. This is the same move the repeat runner
already makes with the exit code. Nobody thinks "the exit code was stored but the process
was not" is a compromise; this is the same shape.

The verification of it is deliberately blunt. The scripted agent's answer sentence begins
"the probe answer names these files". Grepping the raw database file for that phrase
returns 0. Grepping the same file for `src/alpha.py` returns 24, because a Read tool call
does carry a file path and that IS recorded. The second number is what makes the first
one mean something: if both were 0, the test would only prove I had grepped an empty file.

### One fake probe's real numbers

Here is a run, in full, so the arithmetic is visible.

The repository at the pinned commit carries `README.md`, `src/alpha.py`, `src/beta.py`,
`src/stray.py`. The scripted agent reads two files and says:

> the probe answer names these files: src/alpha.py, src/beta.py

Two probes are scored against that one answer.

**P-exact.** Key: `src/alpha.py` and `src/beta.py`. The answer names both. Nothing else
in the repository is named. So 2 of the 2 key entries are matched, and 0 wrong paths were
named.

- recall = 2 / 2 = **1.000**. It found everything the key asks for.
- precision = 2 / (2 + 0) = **1.000**. It named nothing it should not have.

**P-narrow.** Key: `src/alpha.py` alone. The same answer names `src/alpha.py`, which is
right, and `src/beta.py`, which exists in the repository and is not in the key.

- recall = 1 / 1 = **1.000**. It still found everything the key asks for.
- precision = 1 / (1 + 1) = **0.500**. Half of what it pointed at was not the answer.

Both probes cost the agent exactly two Read calls, 107 output tokens and about 250 ms.
Every work quantity in the table is identical. The only column that separates them is
precision, and it separates them by half.

That is the case this whole task exists to make measurable, and it is worth sitting with
for a moment: if you measured only the work, you would conclude the two questions were
equally well handled. One of them was answered with a false lead attached.

### Why "cheap behaviour with a wrong answer is not an improvement" is a rule, not a slogan

The sentence is in the specification because of a failure mode that is easy to build and
hard to see.

Suppose you refactor a repository and re-run a task. Afterwards the agent uses 40 percent
fewer tokens, makes half as many tool calls and finishes in a third of the time. Every
number in the report improves. The obvious conclusion is that the refactor made the
repository easier to work in, and that conclusion is what this whole system exists to
support.

But there is another way to get those numbers: the agent gave up earlier. It read two
files instead of six, decided it had the answer, and stopped. The work fell because the
work was not done. Every measure of effort agrees the second run was better, and the
second run was worse.

You cannot tell these apart from effort measures alone, in principle, not just in
practice. Effort is a cost, and a cost is only interpretable next to what it bought. A
measurement system that reports only cost will eventually reward the cheapest way to be
wrong, and it will do so with a straight face, because every number it prints is correct.

That is why the score sits in the same table as the token counts, and why the paragraph
under every probe report says so in words. It is also why the intervention example in
this task's verification was chosen the way it was. The "after" commit costs the agent
one MORE Read and scores HALF the precision. Both numbers are in one table, three rows
apart:

```
probe_score.precision   HL_SHIFT -0.500   CLIFFS_DELTA -1   P 0.100
tool_calls.Read         HL_SHIFT +1       CLIFFS_DELTA +1   P 0.100
```

A reader who only looked at the second row would say the "after" commit made the agent
work harder. A reader who only looked at the first would say it made the agent less
accurate. Both are true, and neither is the finding. The finding is that this repository
change moved both, in directions that a report of effort alone would have had no way to
show.

One last thing about how much these particular numbers are worth. The agent here is
scripted. Its answers are fabricated and its token counts are made up. What has been
verified is the machinery: that the worktrees are made and removed, that the scores are
the ones a person computes by hand, that the two assertions refuse what they should
refuse, that the score reaches the store and the sentence does not. Whether a real agent
gets easier or harder to work with after a refactor is a question no number in this report
answers, and the first honest attempt at it needs a real probe suite and real tokens.
That is an owner decision, and it is the next one worth making.
