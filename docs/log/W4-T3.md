# W4-T3 a verification command anywhere in a chain is a verification run

## OUTCOME

Done, and measured three ways: on the 769 raw Bash commands of the six E12 streams, on
six fresh captures of those streams through the real launcher, and on a `.backup` copy
of the owner's store.

The brief named one defect. Running it found two more, both in the same place and both
fixed here, because neither could be left in without the first fix reaching the wrong
number.

1. **A chain is read whole.** A verification command anywhere in a chain makes the call a
   verification run, and the highest-priority verification category present names it
   (test, benchmark, typecheck, lint, format, build, security_scan). A chain with none of
   them keeps the old rule, the first segment with a known category. `exit_masked` is
   judged for the segment that was chosen. A new `categories` field on a verification_run
   names every verification category the chain held, so the one word the row carries
   hides none of the others.
2. **A newline is a `;`.** The normalizer marks it as one before shlex sees the line,
   which shlex cannot do: it treats a newline as whitespace. A newline inside a quoted
   string, inside a heredoc body, or after a trailing `&&`, `||`, `|`, `&`, `;` or `(` is
   not a separator.
3. **A heredoc body is data, and is replaced by `_` before the line is lexed.** Found by
   measuring the first two: they got 34 of the 51 real pytest runs and the missing 17
   were all one shape.
4. **A runner word does not spend design 6.4's two-bare-token budget.** Found the same
   way, from the brief's own test case. `uv run ruff format .` stored `uv run ruff _ .`
   because `run` and `ruff` spent the budget, so the classifier saw no `format` and no
   `check`, and `lint` and `format` were the category of NONE of the 769 Bash calls in the
   six streams while 81 of them ran ruff.

`NORMALIZATION_VERSION` is `cmdnorm-v4`, `CLASSIFIER_VERSION` is
`commands-v1-556dc49d`, and `REDUCER_VERSION` moved with them.

Files: `src/telltale/commands.py` (535 before, 650 after), `src/telltale/commands_shell.py`
(200, new: the shell scanner, split out at the 800-line ratchet),
`src/telltale/activities_tools.py` (214 before, 236 after),
`src/telltale/activities_codex.py` (410 before, 416 after),
`src/telltale/correlate.py` (one entry added to `_RULE_MODULES`, with the reason),
`tests/integration/test_commands.py` (110, new),
`tests/integration/test_capture_to_summary.py` (763 before, 687 after: three helpers

## WHAT WAS WRONG

The brief's number, and where it came from. The orchestrator read the six raw
stream-json files with `experiments/E12/make_key.py`, whose rule is its own: a command
segment, split on newlines, `&&`, `||`, `;` and `|` with heredoc bodies removed, whose
head is pytest or one of the three ways this repository invokes it. That rule finds 51
pytest executions across the six sessions. Telltale's `agent_test_runs` summed to 14.

One correction to the brief. It says 52 and gives W3-E08/1 as 3; `experiments/E12/key.json`
says 2 for that session and 51 in total. I checked the stream by hand: W3-E08/1 makes 151
Bash calls, exactly 3 of them contain the word pytest, and one of those three is a
`python3 - <<'PY'` script that rewrites a table in `docs/experiments/E08.md` and runs
nothing. The key file is right and the brief's 3 is not. Every number below is against
the key file.

Four separate rules produced the 37-run gap, and they are listed here in the order I
found them, because each was only visible once the one before it was fixed.

**One. The first segment with a category won.** `classify` walked the segments and
returned the first one the table matched. So `uv sync -q | tail -2; uv run pytest -m
integration` was a package_op, and `uv run ruff format . && uv run ruff check . && uv run
mypy . && uv run pytest -q` was a format run. Neither is a test run, so neither counts in
`agent_test_runs`, and the second is not even the most useful thing the chain did.

**Two. A newline was whitespace.** `normalize` lexes with `shlex`, and shlex is a lexer
for words: a newline is whitespace to it and vanishes. So a two-line command arrived at
the classifier as one segment. `cd /tmp/x` on the first line and `uv run pytest -q 2>&1 |
tail -5` on the second became the single segment `cd _ uv run pytest -q >& _` followed by
`| tail -5`; its head was `cd`, which the table does not know, so the old rule fell
through to the next segment and recorded the call as `shell` on the strength of the
`tail`. 303 of the 769 Bash calls in these six streams contain a newline.

**Three. A heredoc body filled the normal form.** With rules one and two fixed the count
went from 14 to 34, and the 17 still missing were almost all one shape. A `python3 -
<<'PY'` script is 3 to 5 kB, shlex lexed all of it, and the token rules turned it into
190 characters of `_`, `(` and `)`. Design 6.4 bounds a stored normal form at 200
characters, so the `uv run pytest` typed on the line AFTER the closing `PY` was cut off
the string before anything downstream could read it. 14 of the 17 were that; 2 more were
bodies whose quoting made shlex refuse the whole line into the fallback, which keeps the
executable and stops.

**Four. A runner word spent the bare-token budget.** This one came from the brief's own
test list, which asks for `categories [format, lint, typecheck, test]` on the four-part
gate chain. It does not happen, and the reason is in `normalize` rather than in
`classify`. Design 6.4 keeps the first two bare words of a segment. `uv run ruff format .`
has three before its first argument, so `run` and `ruff` were kept and `format` became
`_`. The stored string is `uv run ruff _ .`, on which the table matches neither
`("ruff", "format")` nor `("ruff", "check")`. Measured across the six streams: 81 of the
769 calls hold `uv run ruff _`, and `lint` and `format` were the category of none of them.

## WHAT CHANGED

### commands_shell.py, the shell scanner

New file, 200 lines, one public function. `with_separators(text)` returns the raw command
line with a `;` inserted after every newline the shell would read as a command boundary,
and with every heredoc body replaced by `_`. `normalize` calls it before `_lex`.

It only inserts and replaces bodies, and that is checked rather than asserted. Over the
769 real commands: removing the inserted markers reproduces the originals byte for byte
outside the bodies; none of the 259 commands it splits is left with a segment holding an
unbalanced quote, judged by an independent quote walker; and none of the 578 markers
falls inside any of the 250 heredoc bodies that `make_key.py`'s own regex finds. shlex
refuses the same 40 of 769 lines before and after the marking, so the fallback set does
not move.

It was split out of commands.py because commands.py reached 832 lines and the
`no file grows past 800 lines` hook refuses that. It is the block in the file with the
thinnest interface: one function, no imports from the rest of the module, and no idea
what a category is.

### commands.py

`_VERIFICATION_ORDER` is the seven verification categories in priority order, and
`VERIFICATION` is that tuple as a frozenset. Both live here rather than in the reducer
because the priority is a classification rule and belongs to `CLASSIFIER_VERSION`;
`activities_tools.VERIFICATION` now reads this one.

`_classified(tokens)` gives `(category, scope)` for every segment, and `_chosen(found)`
returns which segment names the chain. `classify`, `categories` and `exit_masked` all go
through the two, so they cannot drift apart about which segment they are talking about.

`categories(command_norm)` returns every category the chain held, in segment order, each
once, `unknown` left out.

`_runner_words(words)` counts the leading runner words, and both `_segment` (for the
budget) and `_strip_runner` (for the table) read it, so the normalizer and the classifier
cannot disagree about where a command starts.

`_CLASSIFY_RULES` names the new rules, which is what moves `CLASSIFIER_VERSION`:
`a-newline-is-a-separator`, `a-runner-word-does-not-spend-the-bare-token-budget`,
`highest-priority-verification-category-in-the-chain-wins` and
`otherwise-the-first-segment-with-a-known-category-wins`. `_VERIFICATION_ORDER` is in the
hash too.

### The reducers

Both halves write `categories` on a verification_run and nothing else changed.
`activities_tools.verification_categories` filters `commands.categories` to the
verification names and returns None when there are none, so `Fields.put` drops it.
`activities_codex` calls the same function, because a Codex tool call is a shell command
too.

## UNSURE OR NOT DONE

- **The rebuild after the merge will not do what the brief expects.** The brief says the
  orchestrator runs `telltale rebuild` on the home store after the merge (183 s measured
  for 3223 captures) and that this is what every capture needs. It is necessary and it is
  not sufficient: it applies the two classification changes and cannot apply the two
  normalization ones, for the reason measured above. On the six E12 captures it takes
  `agent_test_runs` from 14 to 19 of a true 51. Every capture taken from now on gets all
  four. There is no way to recover the rest short of re-importing from raw streams that
  the store never held.

- **`categories` holds only the VERIFICATION categories, and the brief can be read both
  ways.** Its trap paragraph says "record every verification category the chain held" and
  its DO list says "a helper that returns every category the chain held". I built both:
  `commands.categories` returns every category, and the reducer writes the verification
  ones. So `uv sync -q | tail -2 ; uv run pytest` gets `["test"]` and not
  `["package_op", "shell", "test"]`. If you want the wider list, it is one filter removed
  in `activities_tools.verification_categories`.

- **The priority order between `test` and `benchmark` is a judgement.** They can only
  meet in a chain that really ran both, since pytest-benchmark is resolved one rule
  further down. I put test first. Someone could reasonably differ.

- **The comment branch of the scanner earns nothing on this data.** A `#` outside quotes
  starts a comment for shlex, so the scanner has to agree with it or an apostrophe in a
  comment would swallow a newline. I loaded a second copy of the module with that branch
  removed and compared all 769 normal forms: 0 changed. It is there for correctness with
  shlex and not because these streams need it.

- **A heredoc inside a double-quoted command substitution is not seen.** `git commit -m
  "$(cat <<'EOF' <message> EOF )"` keeps whatever of the message shlex hands back, because
  the quote is read first and the whole substitution becomes one protected span.
  Disabling the quote branch alone moves exactly one normal form of the 769 and it is
  that shape. The normal form it gets is the one it had before W4-T3, so nothing
  regressed. Reading it properly means parsing `$(...)`.

- **`NORMALIZATION_VERSION` is still a constant somebody has to remember to bump.**
  `CLASSIFIER_VERSION` and `REDUCER_VERSION` are hashes of their own rules;
  `cmdnorm-v4` is a string. I kept `commands_shell.py` in `correlate._RULE_MODULES` so
  that editing the scanner at least moves the reducer version, which is what happened
  before the split, but that is a proxy. Hashing the normalizer's own rules the way
  `CLASSIFIER_VERSION` hashes the classifier's would be the real fix and is not this
  task's.

- **I did not touch `MAX_COMMAND`.** Two of the 51 need it and the change would put more
  of an arbitrary command line on disk.

- **The suite has no test for the runner-budget rule on its own.** It is covered by the
  chain test's `categories [format, lint, typecheck, test]` assertion, which fails
  without it, but there is no test named for it. I judged one assertion in the right
  place better than a second test of the same line.

## EXPLAIN FOR THE OWNER

### Why this mattered

A reviewer opened a session summary and read that your verifier session ran no tests. It
had run eleven. That is the whole of it: the recorder was wrong about the one number spec
13 exists to carry.

### The first question: where does a command end?

Everything below follows from one thing I had to work out first. When the agent types
this into its Bash tool:

```
cd /tmp/x
uv run pytest -q 2>&1 | tail -5
```

that is one tool call carrying two commands. To a shell, the newline between them is a
`;`. To the library Telltale uses to take a command apart into words, a newline is just
whitespace, exactly like a space. So the recorder saw one command whose first word was
`cd`.

It then asked its table what kind of work `cd` is. The table does not know `cd`. Under
the rule in force, it moved on to the next thing in the line, found `tail`, and recorded
the call as shell work. Not a test run. The pytest in the middle was never considered.

I want to be precise about the mistake, because it is not the obvious one. Nothing
misread pytest. The word never reached the part of the code that reads words.

### Marking the boundaries, and the three places you must not

So the fix is to mark the boundaries before the word-splitter ever sees the line. Walk
the raw text, and after each newline that really ends a command, write a `;`.

The interesting part is where a newline is NOT a boundary, and there are three.

**Inside quotes.** A commit message can have a newline in it:

```
git commit -m "one
two"
```

That is one command. Splitting it would turn a message into a command, which is the
defect W2-T1 fixed once already and I was not going to reintroduce.

**Inside a heredoc.** The agent writes small Python scripts like this constantly:

```
python3 - <<'PY'
print('uv run pytest')
PY
uv run pytest -q
```

Between `<<'PY'` and the closing `PY` is not shell at all. It is a script being fed to
Python. The line inside it that says `uv run pytest` ran nothing; it printed a string. The
line after the closing `PY` really did run the tests. One test run, not two, and not zero.

**After a dangling operator.** A chain can be typed across lines:

```
uv run ruff check . &&
uv run pytest
```

The `&&` at the end of the first line means the shell is still waiting. Treating that
newline as a `;` would break the chain apart, and it would also break the masking rule
W3-T3 added, which depends on that `&&` surviving.

I checked all three rather than trusting them. On the 769 real Bash commands in the six
sessions: the marker only ever gets inserted, never replaces anything (strip the markers
and you get the original bytes back); none of the 259 commands it split is left with a
half-quoted string in it; and none of the 578 markers landed in any of the 250 heredoc
bodies, judged by the orchestrator's own regex rather than by mine.

### The second question, which the first one exposed

With the boundaries marked, I measured again: 34 of the 51 real pytest runs. Better than
14, and still wrong.

The 17 that were missing were almost all the same shape, and the reason is a bound you
already know about. A stored command is cut at 200 characters, because an arbitrary
command line is not something a recorder should put on disk. A `python3 - <<'PY'` script
is three to five thousand characters. The word-splitter chewed through the whole script
and produced a hundred and ninety characters of placeholders, and the `uv run pytest` on
the line after the closing tag was past the 200-character cut.

Once you have said "a heredoc body is data, not shell", the answer is already written.
Replace the body with a single `_` before anything reads it. The stored string becomes:

```
python3 _ << _ _ ; uv run pytest -q
```

Thirty-five characters instead of two hundred, and the pytest survives. It is also a
privacy improvement, which is the part I did not expect. The privacy suite has a probe
that puts a fake private key header inside a heredoc; it used to store six placeholders,
one per word of the header. It now stores one, because the body is never tokenized.

### The third question, which came from your own test list

Your brief asked for one specific answer:

```
uv run ruff format . && uv run ruff check . && uv run mypy . && uv run pytest -q
```

should record `[format, lint, typecheck, test]`.

It did not, and the reason had nothing to do with chains. The recorder keeps the first two
plain words of a command, so that a filename or a search string cannot slip into the
store. `uv run ruff format .` has three plain words before its first argument. `run` and
`ruff` used them both. `format` became `_`. The stored string was `uv run ruff _ .`, and
the table that recognizes `ruff format` and `ruff check` saw neither.

Here is the number that made me fix it rather than note it. Across all 769 Bash calls in
those six sessions, `lint` and `format` were the category of zero of them. Eighty-one of
them ran ruff. Every ruff invocation in your build has been invisible to spec 13 since
the day the table was written.

The fix is one line of judgement: a word that only says "run the next thing" is not a
subcommand, so it does not spend the budget. `uv`, `run`, `uvx`, `npx`, `poetry run` are
a fixed list in the code, so nothing a person typed gets stored by this. `run` is stored
because it equals a constant.

After it, 47 of the 769 are lint.

### Now the chain rule itself, which is the easy part

With the line correctly cut into commands, the question is which one names the call. Old
rule: the first one the table recognizes. New rule: if any of them is a check, the
strongest check names it, in the order test, benchmark, typecheck, lint, format, build,
security scan. If none is, the old rule stands.

Calling that gate chain a "format run" would name the cheapest thing in it. It ran the
tests.

And because one call now stands for four kinds of checking, the row carries a second
field listing all of them. On six fresh captures of your sessions, 124 rows carry it, and
two thirds hold more than one category. `['lint', 'format']` appears 28 times. Before,
each of those was one word with the rest gone.

One more thing had to move with it. W3-T3 added a rule about when an exit status belongs
to the check: it does when the check is last, or when only `&&` follows it. That rule has
to look at the segment the classifier CHOSE, not the first one. `uv sync -q | tail -2 ;
uv run pytest` is not masked, because the pytest is last; reading the `uv sync` at the
front would have called it masked by a pipe that is nowhere near the test.

### The answer I rejected

My first instinct for the newline rule was the one line anybody would write:

```python
text.replace("\n", " ; ")
```

I did not ship it, and I can show you exactly what it costs, because I put it in and ran
the test:

```
python3 _ << _ ; print ( _ ) ; PY ; uv run pytest -q
```

That is one Python script recorded as three shell commands. The count of test runs is
still 4, so a test that only counted would have passed. What the naive rule destroys is
the truth about what the call was.

I also considered leaving the heredoc bodies alone and raising the 200-character bound
instead. I rejected that on your own ground: the bound decides how much of an arbitrary
command line goes on your disk, and raising it to fix a classification problem trades a
privacy property for a counting one. Replacing the body costs nothing and improves both.

### The thing you need to know before you rebuild

This is the part I am least comfortable delivering, and it is measured, not guessed.

Two of the four fixes are in the NORMALIZER, which runs at capture time, when the raw
command line still exists. Two are in the CLASSIFIER, which runs at rebuild time, over the
stored string.

`telltale rebuild` re-runs the classifier. It cannot re-run the normalizer, because the
raw command was never stored. That is not an oversight; it is the entire purpose of
storing a normal form.

So on your existing captures, a rebuild takes the six E12 sessions from 14 test runs to
19. The true number is 51. And 19 is not a coincidence: exactly 19 of those 51 pytest
runs were typed on a single line, so the classifier fix alone reaches all of them and
none of the rest.

Every capture taken from now on gets all four fixes. I proved that by feeding each of the
six recorded sessions back through the real launcher as a child process printing its own
bytes:

```
W4-T2/1     10 against a true 10
W4-T1/1     10 against 11
W3-E08b/1    5 against 6
W3-V/1      11 against 11
W3-E08/1     2 against 2
W3-T4/1     11 against 11
```

Four exact. The two that are short are both the 200-character bound on genuinely long
single-line chains, one 311 characters and one 355, each with pytest at the end. I named
both in the log with the command that causes them. The answer key is right and Telltale is
short, and closing that gap means deciding to store more of a command line, which is
yours to decide and not mine.
