## WHAT WAS WRONG

### The measurement, first

`experiments/E12/usage_check.py` is a stand-alone script that reads four surfaces and
computes nothing of Telltale's own. For each of the six sessions it reports: the sum over
distinct assistant message ids of the stream's `usage.output_tokens`; the result record's
`usage.output_tokens` and the sum of `modelUsage[*].outputTokens` beside it; the OTel
sum, read out of a `.backup` copy of the owner's store as the sum of `output_tokens` over
the model_request activities whose `usage_source` is `primary`; and the same
distinct-message sum over the provider's own transcript file, read only.

W4-T2/1          1902     141206      141206     141206      141206        141206.0

Four things follow from that table, and only the first was in the brief.

**The stream's per-message number is not the message's output.** Not merely a different
quantity from the OTel per-request one, which is what W2-T1 recorded. The transcript
carries the same 761 message ids as the stream does, one usage block each, and its
numbers sum to the session total exactly. Joining the two by message id: the stream's
number is strictly smaller than the transcript's on all 761, and equal on none. On
W3-T4/1 the stream's per-message values run 1 to 20 and the transcript's run 88 to 9813.

**The transcript carries final counts, so the backfill importer is right.** That is the
brief's own branch point and it closes the importer out of scope. `src/telltale/importer.py`
and `src/telltale/providers/claude_transcript.py` are unchanged.

**Only one counter is wrong.** Comparing the stream-only captures with the OTel captures
of the same six sessions, activity by activity, over 761 requests:

```
                          otel                       stream-only capture
input_tokens              340 / 178 / 134 / ...       identical on all six
cache_read_tokens         35097982 / 16700279 / ...   identical on all six
cache_creation_tokens     318963 / 296112 / ...       identical on all six
output_tokens             141206 / 122438 / ...       1902 / 912 / 636 / 1620 / 1421 / 1271

So this is a field, not a surface, and the fix has to be that narrow.

**The result record's `usage` block is not the session total.** On these six it happens to
equal `modelUsage`, which is why the brief could take either. It does not on the E01
fixtures, and that is the answer I rejected.

### The answer I rejected, and what killed it

The brief says "the capture total may come from the result record, which is the
provider's figure for the whole session". I built that first, reading
`result.usage.output_tokens`. Then I ran the same comparison over the eight E01 fixtures,
which have both surfaces, before trusting it:

```

S1        936            936        936
S2        390            390        390

`modelUsage` matches the OTel sum on all seven fixtures that have OTel, on all four
counters. `usage` matches on five.

What `usage` actually is, measured rather than guessed. S7's eight api_request records
are five with `query_source=sdk` and three with `query_source=compact`. The five sum to

of the sessions this recorder exists for. It would also have passed every test I had at
that point, because the six E12 sessions did neither.

## WHAT CHANGED

### The parser: two names where there was one

`src/telltale/providers/claude.py`.

An assistant message's usage now yields `input_tokens`, `cache_read_input_tokens` and
`cache_creation_input_tokens` unchanged, and `output_tokens_snapshot` where it used to
yield `output_tokens`.

The result message gets its own branch, `_stream_result`, which names its four counters
`main_thread_input_tokens`, `main_thread_output_tokens`, `main_thread_cache_read_tokens`
and `main_thread_cache_creation_tokens`. Its `modelUsage` is untouched: the parser has
kept it whole as `model_usage` since W0-T2, because the context window denominator is
read from it.

`_stream_flattened` no longer flattens a top-level `usage` block's four counters at all.
It kept `total_tokens`, `tool_uses` and `duration_ms`, which is what a
`system/task_progress` or `system/task_notification` message carries there. I checked
that the result message is the only one with the four: over the eight E01 fixture streams
and the six E12 streams, those three types are the only non-assistant messages with a
`usage` key at all.

`src/telltale/allowlist.py` has two usage tables where it had one, so the assistant entry
and the result entry cannot share a spelling again by accident. `output_tokens` is now an
unknown field on `claude.stream.assistant`, which means a parser that reintroduced it
would be refused by the third gate rather than believed.

### The reducer: the rule is keyed on the observation type

`src/telltale/activities.py`.

A `model_request` takes its `output_tokens` from the first observation in its group that
is not a `claude.stream.assistant`, and its `output_tokens_snapshot` from the first one
that is. Two things forced the type key rather than the obvious alternatives:

- **Not the field name.** Every stream-only capture already in a store spells the
  snapshot `output_tokens`, because that is what the old parser wrote. A rule that
  skipped the field by name would leave those captures reporting it forever, since a
  rebuild reads stored observations and cannot re-read the raw stream.
- **Not `usage_source`.** A transcript backfill capture reaches the same grouping with
  `usage_source` set to `stream`, and its per-message counts are final. Catching it would
  have broken the one surface the measurement had just cleared.

`_snapshot` reads `output_tokens_snapshot` and falls back to `output_tokens`, so a
rebuild of an old capture moves the number out of the field rather than losing it.

The `session_end` lifecycle activity built from the result message carries
`session_output_tokens`, the sum of `modelUsage[*].outputTokens` over the models named.
It is on the lifecycle row and not spread over the requests because the split across
requests is exactly what no surface stated.

### The summary: one number, three ways of not knowing it

`src/telltale/measures_spec13.usage` gains the session totals as an argument, and
`measures._session_totals` finds the lifecycle rows that carry one. `SESSION_FIELDS` has
a single entry, `output_tokens -> session_output_tokens`, because output is the one
counter a stream-only Claude capture lacks per request.

The rule: the OTel sum when every request carries one; otherwise the session figure with
coverage `partial` and a warning; otherwise null with coverage `unavailable`. The middle
case is `partial` however complete the provider's figure is, because a reader may add it
up across captures and may not place it against a request. The warning says so in words:

```
per-request output tokens were not observable on the surfaces this capture has, so this
is the provider's figure for the WHOLE session (the stream result's modelUsage) and not a
sum over the requests: the split across requests is unknown
```

`measures_intervals._tokens` returns None when any of the four counters is unknown on any
request in the interval, rather than skipping the absent one. Its own docstring begins
"every token the model requests inside this interval accounted for", and the skip kept
the word while dropping the tokens.

### The series and the checklist: no code

`src/telltale/series.py` is unchanged, and that is a finding rather than an omission. The
request-clock `output_tokens` cell reads `fields.get("output_tokens")`, which is now None,
and `blank_unobservable` already turns a column with no value in any row into
`unavailable`. Verified on a real stream-only capture in the owner's store: five rows,
five nulls, coverage `unavailable`, `column_report` reason `no value in any row`, while
`fresh_input_tokens` on the same capture stays `observed`.

The readiness checklist names the column twice over, also with no change. Check 1 on
another target prints `not forecastable: output_tokens (unavailable), request_duration_ms
(unavailable)`, and asking for a forecast whose target is output_tokens is refused before
any window is formed: `target output_tokens has coverage unavailable: a target must be
one of ['observed', 'derived']`.

### The conflict rule, restated and not changed

`correlate.COMPARABLE_USAGE` already held three counters and not four, so no conflict
diagnostic was ever written for the snapshot. W2-T1 excluded it because the two surfaces
disagreed on 333 of 333 requests. The reason is now stronger and the comments in
`activities.py` and `measures_spec13.py` say it: a snapshot taken before a message
finished is not a smaller measurement of that message's output, so the two surfaces are
not answering one question and a conflict row would be a count of requests wearing the
name of a defect. `test_usage_surfaces.py` asserts that no such row is written on the S1
replay, which has both surfaces.

## EXPLAIN FOR THE OWNER

### What was wrong, in one line

Telltale told you a session that wrote 141206 tokens of output had written 1902, and put
the word `observed` next to it.

### The number that does not mean what it says

When Claude Code runs with `--output-format stream-json`, it prints one JSON line per
thing that happens. Some of those lines are assistant messages, and each carries a small
block called `usage` with four counters in it: how many fresh input tokens the request
used, how many it read from cache, how many it wrote to cache, and `output_tokens`.

Three of those four are the request's final numbers. The fourth is not. It is a count
taken while the message was still being written, before the model had finished.

Here is a real one. In session W4-T2/1 the stream has 257 assistant records covering 170
distinct messages, and every record of one message repeats one usage block. The
`output_tokens` on those blocks run from 1 to 21 and add up to 1902. The same session's
own summary line at the end says 141206. Telltale was adding up the 170 small numbers.

You can see the same thing from a second direction, which is what made it certain rather
than likely. Claude Code writes a transcript file for every session under
`~/.claude/projects/`, and that file has a line per assistant message with its own usage
block. The message ids match the stream's, one for one, 761 of them across your six most
recent sessions. On every single one of those 761, the transcript's number is bigger than
the stream's. Not once equal. On W3-T4/1 the stream's numbers run 1 to 20 and the
transcript's run 88 to 9813, and the transcript's add up to 89125, which is what the
session says it produced.

Two surfaces describing one message, one saying 1 and the other saying 88, is not two
measurements that disagree. It is one measurement and one progress report.

### Why it only hits sessions recorded without OpenTelemetry

Telltale reads Claude through several channels at once. One of them, OpenTelemetry, sends
a record per API request with the request's real token counts. When that channel is on,
Telltale uses it and the stream is only a second opinion, so the numbers in your home
store have always been right. The E12 captures replay an archived stream and nothing
else, so the stream was the only thing there, and the snapshot was all Telltale had.

That is why the defect was invisible for four waves. It only appears when the good
channel is missing, which is exactly when you are least able to notice.

### The answer I tried first, and the fixture that killed it

The obvious fix is: if the requests cannot tell you, take the total from the session's
own summary line, which has a `usage` block of its own. I built that. The six E12
sessions all agreed with it.

Before trusting it I ran the same comparison over the eight recorded sessions in
`fixtures/`, which have both channels and so have a known right answer. Six of the eight
agreed. Two did not, and they were the two interesting ones.

S7 is the session that ran out of context and compacted three times. Its summary line
says 2714 output tokens. Its OpenTelemetry records add up to 18548. S4 is the session
that delegated work to a subagent. Its summary says 350; its records add up to 2368.

I worked out where the missing tokens went. S7 made eight requests: five ordinary ones
and three whose purpose was compaction. The five ordinary ones are 124 + 175 + 1856 + 151
+ 408, which is 2714 exactly. The three compaction ones account for the other 15834. S4
is the same rule with subagents instead of compaction: its summary counts the two
requests the main conversation made and leaves out the five its subagent made.

So the summary line's `usage` block is the main conversation's totals, not the session's.
Reading it as the session's would have under-reported every session that compacted or
delegated, which is most of your long ones. It would also have passed every test I had at
the time, because none of the six E12 sessions did either thing.

Beside that block there is a second one, `modelUsage`, listing totals per model. That one
matches the OpenTelemetry sum on all seven fixtures that have it, on all four counters.
That is where the session figure comes from now.

### What you will see

For a session recorded with OpenTelemetry, nothing changes. I rebuilt eleven captures in
your store on a copy and compared every usage number, coverage word and warning: all
identical.

For a session recorded from the stream alone, `telltale show` now says:

```
"usage": { "model_requests": 170, "output_tokens": 141206, ... },
"warnings": { "output_tokens": [
  "per-request output tokens were not observable on the surfaces this capture has, so
   this is the provider's figure for the WHOLE session (the stream result's modelUsage)
   and not a sum over the requests: the split across requests is unknown" ] }
```

The number is the session's and is right. The word beside it is `partial`, not `observed`,
because nobody counted it per request. You can add it up across sessions. You cannot ask
which request spent it, and the forecasting side enforces that rather than trusting you
to remember: the request-clock `output_tokens` column is empty on such a capture, the
readiness check prints `not forecastable: output_tokens (unavailable)`, and asking for a
forecast of output_tokens on it is refused by name.

One more number moved, and it is a smaller thing reported for the same reason.
`stable_state_tokens` is "the tokens spent inside a stretch of work where nothing
