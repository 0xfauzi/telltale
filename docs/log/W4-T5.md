## WHAT WAS WRONG

**Nothing was broken. The refusal was right and the experiment was legal, and only one
of those could stay true.** W4-T1's base_sha assertion says the two arms must differ in
no fingerprint field, and it names `instruction_hashes` in its own comment as the reason
the assertion is not vacuous. E10 rewrites AGENTS.md between the arms, so it moves
exactly that field. The tempting fix is to let base_sha ignore `instruction_hashes`,
and it is wrong twice over: it deletes the check that catches a refactor which also
touched the instructions, and it makes two different experiments share one declared
factor. A second factor keeps both statements: `base_sha` still means "nothing else
moved", and `instructions` means "the instruction surfaces moved and nothing else did".
`test_the_same_two_commits_under_factor_base_sha_are_refused_naming_the_field` is that
distinction as a test, and it passes against the un-fixed code as well as the fixed one.

**The post-run assertion cannot see the difference this factor is about.** The
fingerprint payload has no commit in it, by design (a fingerprint that carried the
commit would make every repository comparison a comparison of two environments). So the
payload of an arm at a commit that rewrote AGENTS.md and the payload of an arm at a
commit that rewrote AGENTS.md and deleted a module are the same shape: one differing
field, `instruction_hashes`. The assertion would pass and the report would say the
instruction surfaces were the only difference, which is a false statement produced by a
check that is working. That is why the pre-run diff check exists, why it runs before any
token is spent, and why breaking it (VERIFY, break 1) makes a two-factor spec run to
completion and report a comparison.

**"The field differs" names a field, not a file.** `instruction_hashes` is one mapping
over every instruction surface in play, and the operator's `~/.claude/CLAUDE.md` and
`~/.codex/AGENTS.md` are hashed into the same mapping. Both arms see identical home
files, so they never cause the difference, but they are in the value a reader is shown.
The assertion now carries `instruction_paths`: the paths inside the field whose digest
differs, with each arm's sha256 and byte count, and `None` for an arm that does not carry
the file at all. The key is on every report, empty when nothing inside the field moved,
because a key that is only sometimes there makes a reader who does not see it guess.

**The check I wrote is a restatement of env.py's behaviour, and restatements drift.** The
diff names a path in a commit; nothing is checked out while the check runs, so it cannot
ask the filesystem and has to decide by the shape of the path. env.py decides by looking
at a real worktree. Those are two statements of one rule. The surfaces themselves are
read from env.py's constants and never written out again, but the SHAPE is mine:
repository-root `CLAUDE.md` and `AGENTS.md`, and `*.md` directly inside the rules
directory, with `docs/AGENTS.md` and `.claude/rules/deep/x.md` outside it. So there is a
test that builds a directory with one file of every shape, takes a real
`env.fingerprint` of it, and asserts the set it hashed equals the set my check accepts.
The direction that matters is stated there: a surface env.py hashes and my check refuses
costs a refusal somebody can read, while a path env.py does not hash and my check accepts
would let a code change through as an instruction change.

**Two files hit the 800-line ratchet, and the second one was not in the brief.** The
brief said to split `tests/integration/test_experiments.py`, which W4-T4 left at exactly
800. `experiments_env.py` was at 707 and this factor took it to 910, which is the same
gate on the source side. The seam was already named in that file's own docstring: the
runners run one condition each and report it, and the file "only ever asks whether two
conditions differ in what they were declared to differ in". The question moved to
`experiments_factor.py` and the two runners stayed. One call site outside the file used a
moved name: `experiments/E06/run.py`, which rebuilds an E06 report from the store and
calls the between-arm assertion rather than re-implementing it. It now calls
`experiments_factor.assert_between`. I did not leave the old name behind as an alias: a
recovery script that silently kept working through a shim is a script nobody notices has
moved.

**No real agent has read either AGENTS.md.** Everything here is the scripted agent,
whose answer is a function of the paths in its argv and the files in its checkout, and
which cannot read an instruction file at all. So what is verified is the harness: the
two assertions, the diff check, the pairing and the report. Whether a real agent's
answers move across an instruction rewrite is E10's question and this task does not
touch it.

**A rewrite that only reorders bytes is a difference here.** The fingerprint compares
sha256 and byte count, so an AGENTS.md rewritten to say the same thing in a different
order is a declared instruction change like any other. That is right for a fingerprint
and it means the factor cannot tell a rewrite that changed the instructions from one
that changed the wording. Nothing in this task could decide that, and reading the two
files is the operator's job.

**The instruction surfaces of a subdirectory are not surfaces here.** env.py hashes
`CLAUDE.md` and `AGENTS.md` at the git root and at the working directory, and an arm's
working directory is the worktree root, so those two are the same directory and
`docs/AGENTS.md` is hashed by neither. If a later task lets an arm run in a
subdirectory, the shape check and the pinning test both have to learn that, and the
pinning test is what would fail.

**The `-z` in the diff is not exercised by a test.** I chose it so that a path with a
space or a non-ASCII byte arrives unquoted rather than as `"src/a b.py"`, which would
fail the shape test for a reason nobody could see. No test commits such a path. Writing
one is cheap and I did not; the reasoning is `git diff`'s documented quoting, which I
read rather than measured.

## EXPLAIN FOR THE OWNER

### What was at stake

You approved an experiment that the code refused to run, and the refusal was correct.
This task made the experiment expressible without making the refusal go away.

### The experiment, and why the machine said no

E10 asks a simple question. Take a repository, run a set of fixed questions against it
with an agent, rewrite the AGENTS.md file, run the same questions again, and see whether
the answers or the work changed. Two runs of one thing with one deliberate difference
between them. The code calls each run an ARM.

Telltale already refuses to compare two arms that differ in more than one declared way,
and it checks that twice. Once before anything runs, on the command lines: they must
differ in exactly the flag you said you were varying. Once after everything has run, on
what it calls the environment fingerprint.

The fingerprint is a short summary of the conditions a run happened under: which model,
which reasoning effort, which tools were available, and the sha256 hash and byte count of
every instruction file it could see. It deliberately does NOT contain the commit. If it
did, every comparison between two versions of a repository would also be a comparison
between two environments, and every commit would look like a change in the instrument.

So when the experiment is "the same probes at two commits", there is nothing in the
fingerprint that can show the difference, and the check inverts: the two arms must differ
in NO fingerprint field at all. That is what makes the commit the only declared
difference.

Now put E10 into that. Rewriting AGENTS.md changes an instruction file. The fingerprint
hashes instruction files. So the two arms differ in one field, the check fires, and the
experiment is refused. The refusal is the check working, on the one experiment where it
should not have.

### The answer I rejected first

The obvious fix is one line: when the factor is the commit, ignore `instruction_hashes`.

I did not do it, for a reason that is easy to see once stated. That field is the only
thing standing between a code refactor comparison and a silent second variable. If you
compare two commits of a refactor and the later one also rewrote CLAUDE.md, the agent in
the second arm was reading different instructions, and any difference you measure is two
causes tangled together. Ignoring the field would delete the only check that catches it.

The other reason is about what a report says. If both experiments declared the same
factor, the report could no longer tell you which one you ran.

So I added a second factor instead: `instructions`. Its check is the mirror image, not a
weakened copy. Where the commit factor says "differ in nothing", this one says "differ in
`instruction_hashes` and in nothing else". Every field the first one holds still, the
second one still holds still. The single field the first one forbids is the one the
second one requires. There is a test that runs the same two commits under the old factor
and confirms it is still refused; that test passes against the old code and the new one,
which is how I know I added a check rather than swapping one out.

### The hole in that, and the thing that closes it

Here is where it got interesting, and it is the part worth your attention.

Suppose someone writes a commit that rewrites AGENTS.md and, in the same commit, edits a
source file. Run the experiment. What does the fingerprint check see? One differing
field: `instruction_hashes`. Exactly what a legitimate instruction rewrite looks like.
The check passes, and the report says the instructions were the only difference, and it
is wrong.

The check cannot catch it, and no version of it could, because the fingerprint has no
commit in it and therefore cannot see a source file. A check that cannot fail on the case
you care about is not a check.

So there is now a second thing, and it runs before a single token is spent. Telltale asks
git which paths the two commits differ in, and requires every one of them to be a file
the fingerprint hashes. Here is a real refusal, from the run in VERIFY:

```
factor instructions, and before=7cd7772f79c008a0fcffe25d11e5f4b2504ba623 and
after=e2ee3e1e49e08425d6a9deddc73b09a0f9117dab differ in 2 path(s) of which
['src/gamma.py'] is not an instruction surface the fingerprint hashes
(CLAUDE.md, AGENTS.md, .claude/rules/*.md): a commit that changes code AND an
instruction file is two factors
```

No database was created, because nothing ran. That is the point of doing it first: the
alternative is finding out after ten agent sessions have been paid for.

I checked that this check is load-bearing rather than decorative by breaking it. With its
one line disabled, the two-factor spec runs to completion and reports a comparison, and
the test that expects the refusal fails. Restored, it passes.

### How the check knows what an instruction file is

It has to answer "is this path one the fingerprint hashes" while nothing is checked out,
because it is reading a list of changed paths out of git history and neither commit is on
disk. So it decides by the shape of the path, and `env.py`, which builds the fingerprint,
decides by looking at a real directory. Two ways of stating one rule, which is how rules
drift apart.

The list of files itself is not copied. The check imports env.py's own constants, so the
day somebody adds a surface there, the refusal message and the check both learn it. What
is mine is the shape: a `CLAUDE.md` or `AGENTS.md` at the top of the repository, and any
`.md` sitting directly in the rules directory. Not `docs/AGENTS.md`, and not a file
nested one level deeper in the rules directory, because a run's working directory is the
top of the worktree and env.py looks exactly one level down.

Rather than trust that, I made it checkable. A test builds a directory holding one file
of every shape, takes a real fingerprint of it, and asserts that the paths the fingerprint
hashed and the paths the check accepts are the same set:

```
hashed by env.fingerprint: {'AGENTS.md', 'CLAUDE.md', '.claude/rules/style.md'}
accepted by the diff check: {'AGENTS.md', 'CLAUDE.md', '.claude/rules/style.md'}
```

One direction of that equality matters more than the other, and the test says so. A file
env.py hashes that the check rejects costs you a refusal you can read and argue with. A
file env.py does not hash that the check accepts would let a code change through wearing
an instruction change's clothes.

### What the report tells you now

The fingerprint field holds every instruction file in play, including the two in your own
home directory, `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md`. Both arms see identical
copies of those, so they never cause the difference, but they sit in the same value. A
report that told you only "the field differs" would be naming a field when you want a
file.

So the report names the file, with both hashes and both sizes:

```
differing fields ['instruction_hashes'], expected ['instruction_hashes'];
instruction_hashes differ at AGENTS.md: before=sha256 faeca353850b, 36 bytes,
                                        after=sha256 905381088818, 73 bytes
```

36 and 73 are the two AGENTS.md files in the verification repository. The test checks
those two numbers against `len(BEFORE)` and `len(AFTER)` computed from the text it wrote,
so the fingerprint's arithmetic is compared with a second route to the same number rather
than with itself.

One line of that output deserves a warning. The between-arm table for this run says
`material environment effect` on a token count. That is not a finding. The scripted agent
picks a random seed per run and every number it invents is a multiple of that seed, and
since both arms ran identical commands the only thing left to move a token count is the
draw. At three runs per arm, the label vocabulary is describing noise, correctly.

### Two files hit a wall on the way

There is a gate in this repository that fails a commit if a Python file that was at or
under 800 lines goes over it. The brief warned me about one file: the environment tests,
which W4-T4 left at exactly 800. It did not know about the second. Adding the factor took
`experiments_env.py` from 707 lines to 910.

I split both, and the source split followed a seam the file had already described in its
own opening paragraph: the runners run a condition and report it, and the file "only ever
asks whether two conditions differ in what they were declared to differ in". The question
moved to a new file, `experiments_factor.py`, and the two runners stayed where they were.
The runners are now 451 lines and the question is 492, so the next factor has room.

One thing outside those files used a name that moved: `experiments/E06/run.py`, the
script that rebuilds an E06 report from captures already in the store. It calls the
between-arm check rather than re-implementing it, which was the right decision when it
was written. I updated its call. I chose not to leave the old name behind as a
forwarding alias, because a script that keeps working through a shim is a script nobody
notices has moved.

On the test side, three test files were each carrying their own copy of the same three
helpers (run git, open the store, run the command line). Those are now one copy each in a
shared file, which is also where the new tests get their repositories from.

### How I know each of these

- The refusal texts, the fingerprint ids, the two AGENTS.md digests and the timings:
  measured, by the commands in VERIFY, all of them against temporary repositories and a
  temporary store.
- The pre-run check costing 3.9 ms on a one-path diff and 4.4 ms on a 33-path one:
  measured, 50 calls each on this repository.
- The check being load-bearing: measured by breaking it and watching the right test fail,
  three times, each restored.
- The new tests failing against the old code: measured, in a git worktree at the previous
  commit. Four of the five fail there, each for its own reason; the fifth passes there and
  here, which is the point of it.
- The shape rule (root files and one level of the rules directory): measured against a
  real fingerprint of a directory holding one file of every shape, not read off env.py's
  code.
- `-z` on the git diff protecting a path with a space in it: reasoned from git's
  documented quoting, not measured. No test commits such a path.
- Preferring a second factor to relaxing the first: my judgement, argued above. Someone
  could reasonably say two factors is one too many; what would change my mind is a case
  where the base_sha check has never fired in anger, and it fired the day E10 was
  proposed.
