## WHAT WAS WRONG

**The orchestrator's read said 38 rows and 13 windows. It is 40 rows and 0 windows, and
the 13 is a number no run ever uses.** The brief's READ block, measured on 2026-09-03,
said "c_min on the change clock is 16 and H is 1, so origins inside the first regime are
16 to 28 (13 windows) against k_min 20". That arithmetic is right and the 13 is real, but
it is the ceiling the changepoint imposes BEFORE the missingness policy is applied. The
candidate protocol runs `ABLATION_C` as its past-only covariate set, `edit_turnover_ratio`
is in that set and is null on row 4, and every context on this series starts at row 0. So
all 13 are dropped with `missing_context_value` and the count clause (b) reads is 0.

This matters because 13 and 0 tell the owner different things. Thirteen says the data is
one merge protocol change away from being close. Zero says there are three independent
holes and the count does not move until the last of them is filled. The sensitivity
ladder under VERIFY is what settles it, and I ran it rather than reasoning about it.

**The delayed-label ceiling was one row off, and only the control could show it.** My
first `origin_ranges` computed the last origin as `N - H - 3` for `rework_within_3`. The
command computes it as the lower of `N - H` (a window needs H actual rows after it) and
`N - 3` (design 6.12's delayed label), which is `N - 3` here. On the real series both
give 0 windows so nothing would have shown it; on the 60-row control it was the
difference between 42 windows and 44, and the runner claiming 44 for a target the command
scores 42 on is a runner reporting on a run nobody makes. `last_origin` now spells the
two ceilings and takes the lower, and the control prints 42.

**`readiness.ready` on a partial list is a false pass waiting to happen.** When the
checklist refuses before check 1, the runner computes the two lines that are still
reachable through `readiness._coverage` and `readiness._windows` and reports them. My
first version then called `readiness.ready` on those two. On this repository check 1
fails, so the answer was False and correct by luck. On a series where the target's
coverage is the only failure, two passing lines out of eight would have printed
`ready: True` for a checklist that never ran six of its questions. `verdict` now takes a
`complete` flag and forces False on the partial list.

**A capture id is not an API key, and the secret scanner said it was.** Tracking the
run's output turned `pre-commit run gitleaks` red with 36 findings across `series.json`
and `summary.json`. Every one is a `cap_` or `imp_` id in the series cohort's dropped
list, which the compiler spells `{"key": ..., "reason": ...}`, and `generic-api-key`
matches a high-entropy value under a JSON member named `key`. The fix is an allowlist
entry keyed on the MATCH and never on the path, which is the rule `.gitleaks.toml`
already states for its TELLTALEFAKE entry. I verified it did not blind the scan: a Stripe
key and a generic high-entropy value planted under the same `"key"` member in the same
file are both still reported.

**The answer I rejected: reporting only that everything refused.** The refusals alone are
a true report and a useless one. A runner that printed "not assessable" for every target
would print exactly the same thing if it were broken, if the store copy were empty, if
the checkpoint had failed to load. So the run carries a synthetic control that reaches
branch (c) in the same invocation, and its whole-range numbers agree to every digit with
two independent earlier measurements. That is what separates "there is no data" from
"there is no runner". It is labelled a control on the runner everywhere it appears, its
numbers are never pooled with anything, and the write-up says in three places that they
are not evidence about any repository.

## UNSURE OR NOT DONE

**The placebo twin of a conditioned run is unconditioned, and the public interface cannot
make it otherwise.** `placebo.run` and `candidate._attach` both reach the window through
`backtest.run`'s single `prepare` hook, so only one of them can be attached at a time. So
the label design 6.12's rule produces for a conditioned run is a statement about that
run's scores under a shuffled context, not about whether the A block survives one. On
this repository no label was produced at all, so nothing rests on it here; the day a
repository clears the three blockers, this is the first thing to fix, and the fix is a
composable `prepare` rather than a change to either module's rule.

**I did not run `forecast candidate --base --head` on this branch.** W5-T1 measured that
the live path refuses on the target's coverage before it prints the extracted A block, so
on this repository it prints nothing, and the wave 5 gate carried that forward as
W5-T2's problem. Running it here would have added a refusal already on record.

**The synthetic control's two flag targets fail readiness for the same reason the real
ones do.** `merge_verification_failed` and `rework_within_3` are mostly 0 in the seeded
walk too, so their scaled MAD is 0 and only `merge_verification_ms` reaches branch (c).
The control therefore exercises branch (c) on one target rather than three. That is
enough to show the runner works and it is less than I wanted; a synthetic series with a
balanced flag would show more, and inventing one is a change to
`tests/integration/synthetic_series.py`, which is not this task's file.

**What was written to the owner's store: nothing.** Every read went through a
`sqlite3.backup` copy under `experiments/E11/out/home/`, and `TELLTALE_HOME` pointed at
the copy before the first import that could open a store. The two series snapshots and
the six `forecast_runs` rows this run wrote are in the copy, which is gitignored. This is
a deliberate difference from W5-T1, whose VERIFY steps wrote into `~/.telltale`.

**The series id moves between runs while the rows do not.** `series_id` hashes the
cohort, and the cohort holds every capture of this repository, and this session is being
recorded into the same store. Three builds within an hour, as this runner was being
finished, gave `ser_00b7979fed644291aaaa9d26`, `ser_48ed8eaa43dbcdd802f7c948` and
`ser_6cd4597d6cc75d6f51cfce26` with identical rows, identical coverage words and
identical counts: only the id and the cohort's capture list moved. The write-up says so
and cites the id whose output is in `out/`. Anybody re-running this gets a fourth id and
the same numbers, until a change lands.

## EXPLAIN FOR THE OWNER

**What we were trying to find out.** When a change is sitting there ready to merge,
there are things anybody can read off the diff before deciding: how many files it
touches, how many lines it adds and removes, how many top-level directories it reaches,
whether it changes tests, whether it moves a lockfile. Six numbers. The question this
experiment asks is whether knowing those six numbers changes a forecast of what happens
AFTER the merge: how long the verification run takes, whether it fails, whether the
change has to be reverted or repaired within the next three changes. If knowing them
changes the forecast, the advisory has something to say at the moment you decide. If it
does not, or if we cannot tell, then anything the advisory says about a candidate is
decoration.

**How the question is asked, and why it is asked twice.** The protocol runs the same
forecast twice over the same set of origins. The first run knows the history of this
repository up to the change and nothing about the change itself. The second knows the
same history plus the change's own six numbers. Everything else is identical: same
context, same origin, same model, same everything. Then you subtract. The difference
between the two is the whole answer, and the sentence that rides on every one of them
says what it is not: it measures how much the candidate's known features change the
FORECAST, and it is not the effect of merging, because only one future ever happened and
we cannot see the other one.

**What the data said, and it said no before the question got asked.** The change clock of
this repository holds 40 rows, one per landed change. To make one forecast you need a
run-up: 16 rows of history behind the origin, and every one of those rows has to have a
value in every column the model reads. Design 6.12 also says you need at least 20
forecasts before you are allowed to draw a conclusion from them, and that all 16 rows of
run-up have to come from the same environment, because a runtime upgrade in the middle of
a history is a different world and averaging across it is averaging across two things.

Three separate facts each take the count to zero.

The first is that the thing being forecast is not recorded. `merge_verification_ms` is
how long the merge verification took, and not one of the 40 changes has a number for it,
because nothing was posting a duration until W5-T1 added the flag last week. A column
with no values is not a column you can forecast. The other two are recorded, mostly, but
they are recorded as the same value every time: no merge verification has ever failed
here, and no change has been reverted. A column that is 0 forty times running has nothing
in it to predict, and the checklist has a line that says so.

The second is a hole in a supporting column. `edit_turnover_ratio` has no value on five
of the 40 rows, and one of those is row 4, near the beginning. Every run-up this series
can form starts at row 0, so every one of them crosses row 4. This system never fills a
hole with a zero or a guess, so every run-up with a hole in it is thrown away. That one
early gap costs all thirteen forecasts the history could otherwise support.

The third is the runtime upgrade. It landed at row 29, which cuts 40 rows into a block of
29 and a block of 11. The rule needs 16 rows of run-up inside one block plus 20 forecasts
on top, so a block has to hold 36 rows before it can answer anything. The first block is
closed at 29 and can never grow. The second holds 11 and grows by one every time a change
lands, so 25 more changes with no further upgrade is what it takes.

So the answer is: **we cannot tell yet, and here is exactly what makes it tellable.**
That is a real result. The alternative was to lower one of the thresholds until the
numbers fitted, which is the move the whole experiment protocol exists to stop, and the
brief named it as a trap before the run started.

**How you can tell that the machinery is not simply broken.** This is the part I would
want checked if I were reading it. A program that prints "not enough data" three times
looks the same whether the data is thin or the program is broken. So the same run also
forecasts a synthetic series: 60 rows of a seeded random walk, no repository behind it,
no claim about anything. On that series the same code, the same five forecasters and the
same model produce 44 forecasts, a paired difference, a calibration table and a decision
label. And the headline number it produces, 482.88671875, is exactly the number the
engineer who built this command measured last week and exactly the number you reproduced
independently at the wave 5 gate. Three runs, three environments, every digit the same.
The machinery works. The data is thin.

One detail from that control is worth a sentence, because it shows the conditioning
actually arriving. Four of the five forecasters are simple arithmetic baselines that
cannot read a covariate about the future, and their scores in the two runs are identical
to the last digit, exactly as they should be. TimesFM-3 is the only one whose score
moves. If all five had moved, something would be leaking; if none had, nothing would be
connected.

is about to write to turns out to be the real one. The two series snapshots and six
