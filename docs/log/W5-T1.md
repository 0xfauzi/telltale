# W5-T1 candidate features, post-merge columns, past-future covariates, forecast candidate

## OUTCOME

`telltale forecast candidate --series ID --target T` runs design 6.12's one-step
candidate protocol and prints it: two runs over the same origins, one knowing only the
history and one knowing the candidate's own diff features, the paired median difference
in MAE and pinball loss, each run's calibration, the mandatory sentence, the weights
licence, the readiness checklist and the decision label with its inequalities. With
`--base REF --head REF` it also reads one real candidate's features off `git diff
base...head` and forecasts the row that candidate would become.

Four things had to exist for that command to mean anything, and none of them did.

- `candidate.features(cwd, base, head)` reads the six columns of block A off a git diff.
  Nothing in this system read a diff before; the A block was a tuple of column names.
- The change clock gained `merge_verification_ms`, `merge_verification_failed` and
  `rework_within_3`. They existed only in the forecast registry and in the synthetic
  series, and the backtester refused them on a real series with "has no column".
- `telltale outcome --duration-ms N` is where the first of those three gets a number.
- The TimesFM adapter reads `Window.future` into `past_future_covariates`. Until this
  change nothing in `src/` read that field, so the conditioned and the unconditioned run
  were the same run under every forecaster and `candidate.py` warned that they were.

New: `src/telltale/series_outcomes.py` (226 lines, the three post-merge columns),
`tests/integration/test_forecast_candidate.py` (550, 11 tests),

## WHAT WAS WRONG

**The brief asked for a refusal that would have broken the tool it was protecting, and
the trap two paragraphs above it said why.** The task said `features` should refuse
"when head is a merge of base or base is not an ancestor". The trap said to use
`git diff base...head` with three dots, because two dots would count the base branch's
own drift as the candidate's. Those two instructions do not agree. Three dots exists
precisely for the case where the base branch has moved on since the candidate branched,
and in that case the base is NOT an ancestor of the head. A tool that refused it would
refuse every pull request older than the last push to main.

That is not hypothetical here. `main` was `9ca7adb` when this task started and is
`efd75b7` now: another session landed the W4-E12 brief addendum while I worked. The
ancestry refusal would have refused this branch's own A block, on this branch, today.

So the ancestry refusal is spelled as the one that survives both sentences: there must
be a common ancestor. `git merge-base base head` failing means the two histories share
nothing, and then `git diff` still answers by diffing one whole tree against the other,
which makes all six numbers the size of the repository rather than of a change. That is
a real failure worth a named refusal. Requiring the stronger relation is not, and I did
not implement it. This is a judgement, and the orchestrator could reasonably overrule
it; the change is one line in `candidate._merge_base`.

**A dictionary of reasons overwrites, and the first version of `unknown_columns` did.**
Each change row that leaves a post-merge cell unknown produces a sentence saying why.
I merged those into one map per column with `dict.update`, so the LAST row's reason won.
On the six-attempt lineage the test builds, row 2 posted a verification and stated no
duration, and rows 3 to 5 posted no verification at all: the map said only the second,
which tells a reader to add `--duration-ms` to an outcome that does not exist. The test
caught it on the first run. The map now carries every distinct reason a column's cells
went unknown, joined with ` | `.

**Two runs can differ on every single window and still have a paired median difference
of exactly 0.** My first assertion for the covariate-reading forecaster was that the
median of the per-origin MAE differences is not 0. It is 0. `FutureEcho` adds the
candidate's `files_changed` to a persistence forecast, so each window's MAE moves by
plus or minus that number depending on which side of the actual the forecast sat, and
the median over an even count of such numbers is the average of one of each. The mean
MAE differs, which is what the report prints. The test now asserts the thing that
actually shows the covariate arrived: window by window, the conditioned point minus the
unconditioned point equals the candidate row's own `files_changed`.

**The one-step forecast printed the licence line by crashing.** `candidate.licences`
reads the `forecasters` key that `backtest.run` puts on a scored run, and `one_step`
builds its own result dict, which had no such key. The first end-to-end run of
`--base main --head HEAD` printed the whole report and then raised `KeyError:
'forecasters'` on the last line. `one_step` now declares its forecasters the same way a
backtest does, and the licence line moved inside `one_step_report`, so there is one
renderer and one place the ADR-014 word check runs. A test asserts the line is there.

**The answer I rejected: reading the changed files' CONTENTS to describe the candidate.**
It is the obvious move. A diff carries the lines, a model could say what the change
does, and "what kind of change is this" feels more predictive than "how many files".
Three things killed it, and the third is the one that decided it. None of the six
columns needs the bytes: every one is a count over paths and numstat. Design 6.3 lists
diff text among the things this recorder never persists, so a feature built on it could
not be stored or re-derived. And a number computed from source is not the same KIND of
claim as a number counted off a diff header: the change clock's own
`subsystems_touched`, `test_files_changed` and `dependency_delta` are read from paths by
`series_paths.columns`, and if the candidate's block were computed any other way it
would not be comparable with the row it is being conditioned against. The extractor
therefore runs one `git diff --numstat -z` and never opens a file.

**A private rule I had to copy rather than call.** `backtest._chosen` picks a variant's
covariate columns and refuses one the series does not have. `candidate.one_step`
forecasts at origin N, which is one past the last row and is not a backtest window, so
it cannot go through `backtest.run`, and `backtest.py` is not this task's to edit. The
loop is duplicated in `candidate._covariates` with a comment saying so. Both read the
public `backtest.FORECASTABLE`, so the two cannot disagree about which coverage words
are allowed; what is duplicated is the loop, not the decision.

## UNSURE OR NOT DONE

**The stored candidate rows carry no decision label.** `forecast backtest` attaches one
through `placebo.unpaired` before it writes the row. `candidate.conditioned` persists
both runs itself, and this command computes the label afterwards, so the label is
printed and not stored. That is not obviously wrong, since the protocol's deliverable is
the pair rather than a verdict on either half, but `placebo.py` argues in its own
docstring that a stored run with metrics and no label is a number nothing says how
strongly to read. Closing it means changing the signature of `conditioned`, which W5-T2
is about to read, so I left it. This is my judgement and it is worth revisiting.

**`ForecastResult.covariates` does not reach the store on its own.**
`backtest._forecast_window` copies point, quantiles, wall_ms, model_ms and warnings out
of a result and drops the rest, and `backtest.py` is not this task's to edit. So the
adapter naming its past-future variates is visible to a caller holding the result, and
not in the database. I closed the gap the other way, by setting the conditioned run's
`covariates` in `candidate.conditioned`, which `backtest.persist` writes into
`scenario.covariates`. Verified below. The narrower fix in `backtest.py` is still worth
making.

**The brief said `rework_within_3` is None "on the last two" rows.** It is None on the
last THREE, and that follows from the rule the same paragraph states: 0 requires that
three following changes exist, so a row needs an index of at most N - 4 to be labelled.
I implemented the rule and the test asserts three. If the intent was two, the rule needs
rewording, not the code.

**The change clock of this repository cannot exercise the protocol.** All three
post-merge columns are `partial` or `unavailable`, so `backtest._variant` refuses them
as targets, and even with the one missing row filled the readiness `variation` check
would fail because `merge_verification_failed` is 0 on every row that has an answer.
Both refusals are pasted below. This is the data saying it has nothing to forecast, and
it is not a bug to route around. What would change it: the merge protocol posting
`--duration-ms` from now on, and posting a `revert_or_repair` when one happens. Neither
is something this task may invent, and I invented neither.

**What was written to the owner's store.** The VERIFY steps below wrote one change-clock
series snapshot, one synthetic change series and six `forecast_runs` rows to
`~/.telltale/telltale.db`. Nothing else. Every test ran under a temporary
`TELLTALE_HOME`, no agent session was started and no tokens were spent.

## EXPLAIN FOR THE OWNER

### The question this is all for

Somebody is about to merge a change. They can see the change: how many files it touches,
how many lines it adds, whether it moved a lockfile. They cannot see what happens after
they merge it. Design 6.12 asks a narrow version of that: does knowing what the diff
looks like move a forecast of what happens next, and by how much?

To answer it you need three things this system did not have. You need the facts about
the change that anybody can read before the merge. You need the facts about what
happened after, recorded as history so a forecast can be scored against them. And you
need a forecaster that can be handed the first kind while forecasting the second. This
task built all three.

### First: what can you know about a change before you merge it?

Only what the diff says. Not what the code does, because nobody has run it. So the
answer is six counts.

Two of them come straight off `git diff --numstat`, which prints one line per changed
file with the added and deleted line counts. Three more are questions about the file
PATHS: how many top-level directories were touched, how many of the paths look like
tests, and whether any of them is a lockfile or a manifest. The sixth is just how many
files there were.

Those six already existed. They are called block A, and until now they were a tuple of
column NAMES that the system read out of rows it had already built from commits that had
already landed. There was no way to compute them for a change that has not landed. Now
there is: `candidate.features(cwd, base, head)`.

Here is a real one, measured on this branch:

    COLUMN              VALUE
    files_changed       10
    lines_added         1748
    lines_removed       60
    subsystems_touched  3
    test_files_changed  2
    dependency_delta    0

Read that back into English. Ten files. About 1750 lines added and 60 removed. Three
top-level places touched: `docs`, `src` and `tests`. Two of the changed files look like
test files. No lockfile or manifest moved, so `dependency_delta` is 0.

Every one of those numbers was counted, none estimated, and VERIFY above sets each one
beside the raw `git diff --numstat` it came from so you can add the column up yourself.
`files_changed` is the number of records git printed. `lines_added` and `lines_removed`
are the sums of git's two columns. The three path numbers come from
`series_paths.columns`, which is the SAME function the change clock uses on a commit
that has already landed. That sameness is deliberate: a number computed one way before
the merge and another way after is not a number you can condition on.

### Two ways this could have gone quietly wrong, and how each is prevented

The first is which diff you take. Git has two spellings that look almost identical.
`git diff main..HEAD` compares the tip of main with the tip of your branch. If main
gained commits while you were working, those show up in your diff as REVERSALS, and your
change appears larger than it is. `git diff main...HEAD` with three dots compares from
the point where the two branches parted, which is the change you actually made.

That is not a hypothetical, and I did not have to construct it. While I was working,
another session pushed a commit to main. So on this branch, today, two dots reports 11
changed files and claims this candidate deleted 16 lines of `briefs/W4-E12.md`, a file
this branch has never touched. Three dots reports 10. The extractor uses three dots, and
a test creates exactly this situation in a scratch repository and checks that the two
spellings differ and that the extractor took the right one.

The second is a binary file. Git cannot count lines in one, so it prints `-` and `-`
where the numbers would go. The tempting move is to sum the text files and carry on. The
result is a smaller number presented with the same confidence as a complete one. So
`lines_added` and `lines_removed` go unknown for the whole diff whenever any file in it
is binary, while `files_changed` still counts the file. This is not new judgement: it is
`repo.totals`, which already made this decision for the snapshot path, reached through
the extractor rather than copied into it.

### The answer I rejected, and what killed it

The obvious richer feature is the diff CONTENT. Read the added lines, and say something
about what the change does rather than how big it is. It feels more predictive, and it
would be easy.

Three things stopped it. Two are cheap: none of the six columns needs the bytes, and the
architecture already promises that diff text is never written to the database, so
anything built on it could not be stored or rebuilt later.

The third is the one that actually decided it. The number you condition on has to be the
same KIND of number as the one in the history you score against. The change clock builds
its rows by reading paths off commits. If a candidate's features were computed from
source while the history's were counted from paths, the two would not be comparable, and
the comparison is the entire experiment. The extractor makes one git call and never
opens a file.

### Second: what happened after the merge?

Three new columns on the change clock, which is the table with one row per landed commit.

- How long the merge verification took, in milliseconds.
- Whether it failed: 1 for fail, 0 for pass.
- Whether the change was reverted or repaired soon after: 1 or 0.

None of those is something the recorder can observe. A verification is run by whoever
runs it, and Telltale only knows about it because somebody posted it, with `telltale
outcome`. So all three are read off outcomes attached to the attempt that landed the
change.

That makes "unknown" the common case, and the whole design of these three columns is
about keeping unknown separate from zero. Nobody posted a verification is not the same
as a verification that passed. Nobody stated a duration is not the same as a
verification that took no time. Each column carries None in those cases, and the series
carries a sentence saying which reason applies.

The third column has a stranger property: it cannot be known yet. "Reverted within 3"
means "within the next three changes", so the last three rows of any history have no
answer, no matter what outcomes exist. Not zero. Unknown, with a sentence saying the
window has not happened. On this repository's 38-row change clock, that is rows 35, 36
and 37.

There is one more trap in that column, and I built the test to catch it rather than
finding it by accident. Deciding whether a revert happened "before the third following
change" means comparing two timestamps. Git records a commit time in whole seconds and
writes `2026-09-03T12:34:56Z`. An activity timestamp carries microseconds and writes
`2026-09-03T12:34:56.123456Z`. Compare those as TEXT and the letter `Z` sorts after the
dot, so an event a tenth of a second earlier looks later. Both are parsed into real
timestamps before the comparison, and the test posts one revert inside the window and
one after it and checks that the second answers 0.

### Third: could any forecaster actually read the candidate?

No, and this is the part that made the protocol vacuous before today.

The protocol is two runs over the same origins. The unconditioned run sees the history.
The conditioned run sees the same history plus the candidate's six numbers, hung on the
window as what TimesFM calls a past-future covariate: a series that is known past the
point being forecast, because the diff is visible at the moment the decision is taken.

The A block was already being attached. Nothing read it. `Window.future` was written and
never looked at, so both runs came out identical and `candidate.py` printed a warning
saying exactly that. The warning was honest and the protocol measured nothing.

Two things fixed it. The TimesFM adapter now reads `Window.future` into
`past_future_covariates`, and the test suite got a small forecaster called `FutureEcho`
that adds the candidate's `files_changed` to a persistence forecast, so the protocol can
be exercised on a machine with no model installed.

Before writing the adapter code I ran a probe, because the library's behaviour here is
the kind of thing that must be measured rather than assumed. The probe is in VERIFY. It
found what I expected and one thing I did not.

The expected part: a covariate of length context + horizon, with `padding_mode="edge"`,
is accepted and changes the forecast. That cleared the brief's stop condition.

The unexpected part: a covariate of the WRONG length is also accepted. I passed one of
length 40 where 41 was correct, and one of length 104, and got three different plausible
forecasts from the same context with no warning at all. The library never says which
length it was given. So the adapter asserts the length itself and names the variate in
the message. That is the same shape as every other guard in that file, and for the same
reason: a model that answers a malformed question is worse than one that refuses.

### What this repository can and cannot say today

Here is the part where the honest answer is negative.

The change clock of this repository has 38 rows. Not one of the 127 outcomes in the
store carries a duration, because `--duration-ms` did not exist until this task, so
`merge_verification_ms` is unknown on all 38 rows. `merge_verification_failed` is known
on 37 and is 0 on every one of them: the last mechanical verification of every attempt
that LANDED a change passed. There are 22 failures in the store, and they all belong to
attempts that did not land anything. And there is not a single `revert_or_repair`
outcome anywhere, so `rework_within_3` is 0 wherever it is decidable.

So `telltale forecast candidate` on this repository refuses. It refuses twice over, and
both refusals are correct. The first is that a target with even one unknown cell is not
forecastable, which is an existing rule. The second is that a column with the same value
in every row has no variation, so every baseline predicts it perfectly and there is
nothing to compare a model against.

I want to be plain about this rather than bury it: the machinery is built and tested,
and this repository's own history cannot yet exercise it. What would change that is the
merge protocol posting a duration with each verification from now on, and posting a
revert when one happens. Neither is something this task could invent, and I invented
neither.
