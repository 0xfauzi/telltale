# W5-T2 shadow advisory

## OUTCOME

`telltale advise --head <ref> [--base <ref>] [--series <id>]` exists. It reads one
candidate's A block off `git diff base...head`, reads the decision label of the latest
stored true-order backtest of each candidate target on this repository's change series,
runs design 6.12's readiness checklist, forecasts the row the change becomes twice (once
knowing the history and once knowing the candidate), prints the whole thing on one page
and stores it as one `policy.advisory` observation in a capture of its own.

Nothing is posted anywhere. There is no `--post`, no receiver path and no network call.
The last line of every page is the sentence that says so.

Four things carry the task.

**The advisory is an observation Telltale emits about itself.** Provider `telltale`,
surface `telltale`, adapter `telltale.advise@1`, in a capture whose id is `adv_` plus 24
hex of a sha256 over (head_sha, base_sha, series_id, sorted targets, created_at). Its own
capture, never an agent's: hanging it on a capture would make a statement this system
made read as something a recorded session produced, and `telltale sessions` would print
that session's provider next to it. As its own capture it shows up in `sessions` with
provider `telltale` and one observation, and `telltale show <adv_...>` prints the stored
payload with the coverage line reading `advisory`.

**The label is read, never computed.** It is `decision.label` of the newest true-order
`forecast_runs` row for (series_id, target). Three answers, three different facts:
a `decide.py` label when the stored run carries one, `not assessable` when it carries
none, and `no assessable forecast` when nothing has scored the pair at all. The third is
a new constant because the second is a different statement: one is the rule looking at a
run and writing no label, the other is there being no run to look at.

**"Confidence" is the label plus the readiness word.** No number anywhere in this command
says how much to trust a forecast, because nothing measured one. The page prints
`<label> / <readiness>` as a column of every forecast row and every paired-difference
row, so a reader who copies one row out carries them with it.

**On this repository, every label reads `no assessable forecast` and every readiness word
reads `refused`.** That is the command working, not failing: the store holds no
true-order run for any candidate target on `ser_77b537448f7f0780ab556d92`, and W5-T1
measured why one cannot exist yet (the three post-merge columns are `partial` or
`unavailable`, and a target with holes is refused by `backtest._variant`). The A block is
stored anyway, because what is known about a change is known whether or not anything can
be forecast from it. The real page is in VERIFY below.

## WHAT WAS WRONG

Nothing was broken. What was missing was the record itself.

Spec 14.6 says that when a policy begins acting on a forecast, Telltale writes a
`policy.intervention` observation carrying `advisory_id`, the action taken and the policy
version. Design 6.3 gives that type its four fields and the allowlist has carried them
since W1. But there was no advisory anywhere in the system, so `advisory_id` pointed at
nothing: the one field that ties an intervention back to what it acted on had no
referent. `forecast candidate` (W5-T1) printed the pair and stored two `forecast_runs`
rows, and that is a laboratory result rather than a statement about one change sitting in
front of a merge decision.

Three smaller things were wrong with the shape a first attempt would take.

**A flat list would have been wrong for the per-target fields.** The brief sketched
`target ENUM` and `label ENUM` as singular and `forecast_run_ids ID (list)`. Written as
three lists parallel to `target`, one value dropped by the sanitizer moves every later
label onto a different target with nothing on the page to say so. That is exactly the
cardinality defect AGENTS.md names. They are keyed by target instead, and a key cannot
slide.

**A full sha256 would have been silently truncated.** `policy_version` is `Kind.ENUM`,
and `sanitize.MAX_ENUM` bounds an enum at 64 characters by cutting it, with only a
`truncated` note in the redaction to say so. `cnd-` plus 64 hex is 68 characters, so the
stored version would have been the digest with its last four characters removed, and two
versions differing only in that tail would be one word in the database. It is 24 hex,
which is what `series.series_id` already uses.

**`telltale show` would have printed a capture of nulls.** An advisory has no activities
and never will, so `measures.summary` would have built a summary object with every block
empty, which reads exactly like a capture that was recorded and never reduced. That is
the confusion invariant 5 forbids, so `show` is routed on the `adv_` prefix to a
different renderer that prints the payload.

## WHAT CHANGED

Two new modules, one new allowlist entry, four lines in cli.py, one new test file.

`src/telltale/cli_advise.py` (496 lines, new). `advise(args)` resolves the base (the
merge base of `--head` with the default branch, through `repo._DEFAULT_BRANCH_REFS`,
which is the list every stored `telltale.repo.identity` resolved `base_sha` through),
reads the A block through `candidate.features`, resolves the change series, builds one
block per candidate target and hands the record to `emit`. `emit` renders BEFORE it
appends, which is ADR-014's order: a page that may not be printed is a page the store may
not hold. `show(store, capture)` is the branch `telltale show` routes to on the prefix.

`src/telltale/report_advise.py` (305 lines, new). `render(record)` is the page;
`stored(row)` is what `show` prints. Everything leaves through `forecast.refuse_words`.

`src/telltale/allowlist_telltale.py`: the `policy.advisory` entry, eleven fields, beside
`policy.intervention` because it is written by the same clock.

`src/telltale/cli.py`: the import, `cli_advise.add_commands`, the dispatch entry, and two
lines in `show` that route an `adv_` id. The brief allowed one line each in the parser and
the dispatch table; the import is unavoidable and the `show` branch is DO item (3), which
cannot be reached any other way, because `show` is in cli.py and `measures.summary` is
wrong for a capture with no activities.

`tests/integration/test_advise.py` (307 lines, new): five tests over a real git
repository, the real CLI through subprocess, the real store, the real backtester and the
real sanitizer.

`docs/design/amendments/W5-T2.md`: the observation type, its allowlist, the capture id
rule, where the label and the readiness word come from, and that `policy.intervention` is
the observation a future policy writes when it ACTS.

Three decisions in the code are worth naming here because they are not obvious from the
diff.

**The forecast at origin N uses the forecasters the STORED run declared**, rebuilt by
name and device off `forecast_runs.forecasters`. Any other set would put a forecast beside
a label that was measured on something else.

**The readiness checklist runs for every candidate target**, including one with no stored
backtest. The brief scoped it to targets with a stored run. Running it for all three makes
the `readiness` field total rather than sometimes-null, and "this series cannot support a
forecast of this at all" is worth knowing exactly where nothing has been scored yet. A
target the backtester refuses to build a checklist for gets the word `refused` with the
refusal beside it, which is a different answer from every line passing.

**With no `--series`, the newest change-clock series of this repository wins**, and the
header prints its id, its row count and its build time so the choice is auditable. This is
not the "duplicate is not one" rule being waived: a rebuilt change series is a later view
of one history as it grew, not a second history. Refusing while several exist would make
the command unusable on any store that has run `series build` twice, and this repository's
store held five change series for one repo_id on 2026-09-03.

## UNSURE OR NOT DONE

**The A block of an empty diff is six zeroes and the command does not refuse it.** Run
with `--head` equal to a commit already on the default branch, `base` resolves to that
same commit, `git diff X...X` is empty, and `files_changed` is 0. That 0 is a true
measurement of an empty diff rather than an unknown, so it is not a violation of anything;
but "this candidate changes nothing" is probably a refusal somebody wants. It belongs in
`candidate.features`, which is W5-T1's file and not this task's to edit.

**`base_ref` and `head_ref` are printed as given.** `--head task/W5-T2` prints
`task/W5-T2` beside the sha it resolved to, and `--head <sha>` prints the sha twice. That
is deliberate (the ref a reader typed is what they will type again), and it does look
redundant on the page when a sha was given.

**Nothing measures how long an advisory takes.** On this repository the whole command is
dominated by opening a 1.6 GB store and running the readiness checklist three times, and
neither was timed. It needs measuring before anything runs `advise` inside a merge
protocol; the number is not in this log because nothing here measured it.

**The advisory does not know whether the series is stale.** It prints the series build
time and the row count, so a reader can see that a 40-row series built an hour ago is not
the same evidence as one built last week. It does not compare that against the repository
head, and a rule for when a change series is too old to advise from would be a threshold
nobody has measured.

## NEXT

- `policy.intervention` has an allowlist entry and no writer. The advisory it would name
  now exists, so a `telltale intervention --advisory <adv_...> --action <word>` is
  writable whenever a policy starts acting. Spec 14.6 also says the performance after
  that point is evaluated as a NEW REGIME, which means the intervention has to become a
  changepoint on the clocks, and that is the part with real design in it.
- The three post-merge columns are still `partial` or `unavailable` on this repository.
  W5-T1 named what would fix that: the merge protocol posting `--duration-ms` on every
  `mechanical_verification` outcome, and posting a `revert_or_repair` when one happens.
  Until then no candidate target on this repository is forecastable and every advisory
  here reads `no assessable forecast`.
- An advisory is not an Evidence. Nothing derived is written by this command, so
  invariant 4 is not engaged; but a reader who wants "how often did the label agree with
  what happened" is asking for a comparative number over stored advisories and their
  landed rows, and that would be an Evidence written through store.py.

## EXPLAIN FOR THE OWNER

### What this command is for

You are about to merge something. The diff is in front of you. What the machine knows,
and you may not, is what happened the last forty times a change of roughly that shape
landed in this repository: how long verification took, whether it failed, whether
somebody had to come back and fix it within the next three changes.

`telltale advise` is that question asked out loud, and answered as honestly as the
evidence allows. It prints one page. The page has three parts and they are in a
deliberate order.

### Part one: what is known

    COLUMN              VALUE
    ------------------  -----
    files_changed       6
    lines_added         1326
    lines_removed       0
    subsystems_touched  3
    test_files_changed  1
    dependency_delta    0

Six numbers, read off `git diff base...head`. Nothing else. Not the contents of any file,
not what the change does, not a summary of anything. These six are what anybody deciding a
merge can read off the diff without opening it, and that is precisely what makes them
legitimate to condition a forecast on: they are known BEFORE the thing you are forecasting
happens. W5-T1 built this part; this task reads it.

A number missing here is printed as `unknown`, never 0. If the diff had held a binary
file, `lines_added` would read `unknown`, because git says `-` there: lines are not the
unit for a binary file, and 0 lines added is a claim about a different change.

### Part two: what may be said

    target merge_verification_failed (flag)
      readiness: refused  (target merge_verification_failed has coverage partial: ...)
      label: no assessable forecast (no stored true-order backtest of this target on this series)

This is the part that comes BEFORE the forecast numbers, and putting it there is the
whole point of the page.

There are two separate questions and they are easy to confuse. The **readiness word**
answers "could this series support a forecast of this at all?" It is design 6.12's
eight-line preflight: enough windows, no holes inside them, enough context for the
baselines, a regime long enough, a chronology placebo constructible, the target actually
varying, a threshold computable. The page prints the name of the first line that failed,
or `ready`. Here it prints `refused`, which means the checklist could not even be built:
`merge_verification_failed` has holes in it on this repository, and a target with holes is
not a target.

The **label** answers a different question: "when somebody did score a forecast of this,
how did it do against four one-line rules and against a shuffle of its own history?" That
is design 6.12's decision rule, and it has four possible answers, from `not assessable`
through `baseline sufficient` (the model did not beat four trivial rules by enough) up to
`temporal evolution` (it beat them, it beat a shuffle of the past, and it did both in each
half of the history separately). The advisory does not run that rule. It reads the answer
off the stored backtest and names the run it read it from, so you can go and look.

On this repository both answers are the honest nothing. No backtest exists for any
candidate target because none can: W5-T1 measured that the store holds 127 outcome records
and not one of them carries a `duration_ms`, and that the last verification of every
attempt that actually landed a change passed, so `merge_verification_failed` is 0 on every
row that has an answer at all. A column that never varies has no forecast in it.

That is the answer, and the page says it in those words rather than printing a number.

### Part three: the two forecasts, and the thing they are not

On a series that CAN be scored, the page continues:

      RUN            FORECASTER   POINT  Q10   Q50  Q90  CONFIDENCE
      -------------  -----------  -----  ----  ---  ---  -------------------------------
      unconditioned  persistence  0.0    -1.0  0.0  1.0  baseline sufficient / variation
      conditioned    persistence  0.0    -1.0  0.0  1.0  baseline sufficient / variation

Two forecasts of the same future row. The unconditioned one knows the history and nothing
about your change. The conditioned one knows the same history plus your six numbers, hung
on the end of the window as what design 6.12 calls a past-future covariate. The difference
between them is the number people will want.

It is not what they will think it is. It measures how much the candidate's known features
move the forecast. It does NOT measure what merging the candidate does, because only one
future is ever observed and there is no counterfactual anywhere in this system. That
sentence is printed under every target block, it is stored in the assumptions of every
run, and the renderer refuses the words cause, impact and would outright: a report that
contains one of them raises an exception before anything is printed and before anything
reaches the disk.

### Why "confidence" is a phrase and not a percentage

Look at the last column of that table: `baseline sufficient / variation`. That is the
whole of what this system will say about how much to trust the number beside it. The
label, and the readiness word.

It would have been easy, and it would have felt more useful, to turn those into a number:
"confidence 62%". There is no such number. Nothing measured one. Inventing one would mean
picking a weighting between two things that are not on the same scale, and the result
would look exactly like a measurement while being an opinion of whoever wrote the
weighting.

So the two words travel together, in a column, on every single row. Not once above the
table, because a reader copies a row out of a table and the row has to carry its own
warning label.

### What is stored, and what is deliberately not

One observation, in a capture of its own, whose id starts with `adv_`. `telltale sessions`
lists it with provider `telltale`, which is the system saying: this row is a statement I
made, not something an agent did. `telltale show adv_...` prints the payload.

The payload holds the six features, the two commit shas, the series it was read against,
and per target the label, the readiness word and the id of the run the label came from. It
holds no prose, no prompt, no file path and no forecast number. If you want to check the
advisory in six months, everything you need to re-derive it is in there: the two shas
reproduce the A block, the run ids reproduce the labels.

What it deliberately does not do is go anywhere. There is no `--post`. Spec 14.6 says
forecasts stay shadow-only during primary evaluation, and the reason is not caution for
its own sake: the moment an advisory changes what somebody does, the data-generating
process has changed, and every measurement taken afterwards is a measurement of a
different system. That is why the observation a policy writes when it starts acting is a
different type, `policy.intervention`, and why it exists to be a changepoint. This command
never writes one. It is the thing a policy would act on, not the acting.

The last line of every page says so, and it is there so that the page cannot be forwarded
without it:

    This advisory is shadow: it is stored and printed and nothing acts on it.

### The one thing I would watch

The advisory picks the newest change-clock series of your repository when you do not name
one. On your store there were five of them for this repository, built over two days as the
history grew. Picking the newest is right, and the page prints its id, its row count and
its build time so you can see which one it used.

But nothing checks whether that series is stale relative to the repository head. An
advisory read off a series built last week, in a repository that has landed a dozen
changes since, is answering a question about a history that no longer exists, and it would
say so nowhere. A rule for when a series is too old to advise from is a threshold, and I
have not measured one, so there is no rule and there is no guess. Build the series before
you advise, and the page will show you when it was built.
