# W6-F1 hf cache env and advise scored-run guard

## OUTCOME

Two one-line defects W6-T1 named in its own UNSURE section are fixed, and each has a
test that fails against the un-fixed code.

`TELLTALE_HF_CACHE` set to the empty string no longer sends the checkpoint download into
the working directory. One stdlib helper, `telltale.forecast.hf_cache_dir`, is now the
only rule that decides where the cache is, and `forecast/timesfm.py` calls it.

`telltale advise` no longer mistakes a scenario row for the newest scored backtest.
`cli_advise._latest` requires `metrics["forecasters"]`, the same distinction
`forecast.scenario.calibration` already draws, so a scenario stored on an advise target
leaves the backtest's label standing and, where there is no backtest, leaves the page
saying `no assessable forecast` rather than `not assessable`.

Both were verified end to end against the real commands, not only at the unit of the
fix: the advisory page printed `label: not assessable (from fc_...,  variant
change_past_only_scenario ...)` before the change and `label: baseline sufficient (from
fc_..., variant change_past_only, ... model persistence)` after it, on the same store.

## WHAT WAS WRONG

**An environment variable set to the empty string is not an unset one.**
`forecast/timesfm.py:126` read `cache_dir or os.environ.get(CACHE_ENV)`. That `or`
guards against `None` and passes `""` straight through, huggingface_hub takes `""` as a
`cache_dir` and resolves it against the process's current directory, and the checkpoint
downloads into whatever directory the command was run from. W6-T1's implementer pulled
1.29 GB into a worktree root that way. `export TELLTALE_HF_CACHE=` and
`TELLTALE_HF_CACHE= command ...` both produce exactly this value, and neither is a typo:
they are how a shell says "no cache directory", which is the sentence the code failed to
hear.

That the two values are different cache ROOTS rather than one root spelled two ways is
measured rather than assumed. With the checkpoint present in the default cache:

    cache_dir=None -> /Users/.../.cache/huggingface/hub/models--google--timesfm-3.0-pytorch/snapshots/43046b85...
    cache_dir=''   -> LocalEntryNotFoundError: Cannot find an appropriate cached snapshot folder ...

(`snapshot_download(..., local_files_only=True)`, so the probe could not download
anything. The adapter passes `local_files_only=False`, and that is the run that fetches
1.29 GB into the relative path.)

The fix could not live in `forecast/timesfm.py`, which is why this task exists as a
separate one: that module imports numpy at line 42 and torch inside `TimesFM.__init__`,
both behind the `forecast` extra, and CI runs the default environment where a plain
`uv sync` installs neither. A test of the rule that had to import that module would be a
test CI never runs. So the name and the rule live in `telltale.forecast`, which is
stdlib, and `timesfm.py` calls the rule and re-exports the name.

**A scenario row is a true-order row with no score in it.** `cli_advise._latest` kept
every row of the pair whose `ordering` was `true` and returned the last by `created_at`.
A scenario (W6-T1) stores exactly such a row: `ordering` true, `metrics` `{}`, `decision`
null, because its origin is one past the last row of the series and there is no actual to
score against. Stored after a backtest of the same pair, it IS the newest true-order row,
so `_label` fell through to `decider.NOT_ASSESSABLE`.

The two sentences that collided are not the same sentence. `not assessable` is the
decision rule's own word for a run it looked at and could not label, usually because
there were too few windows. A scenario was never offered to the rule. Printing the
rule's word for it reports a judgement nobody made.

## EXPLAIN FOR THE OWNER

Two defects, two lines, and they are the same defect twice: a falsy value that meant one
thing being read as another.

**The first one costs 1.29 GB.**

The adapter that loads TimesFM lets you say where the model weights should be cached.
You say it with an environment variable:

    export TELLTALE_HF_CACHE=/somewhere/big

and the code that read it was:

    self.cache_dir = cache_dir or os.environ.get(CACHE_ENV)

Read that as English: "the directory the caller passed, or else whatever the variable
says". It is guarding against one thing, `None`, which is what `os.environ.get` returns
when the variable is not set at all. Then `cache_dir` is None too, `self.cache_dir` is
None, and huggingface_hub uses its own default cache under `~/.cache/huggingface`. That
is the intended behaviour and it works.

Now type this instead:

    export TELLTALE_HF_CACHE=

The variable is now SET, and its value is the empty string. `os.environ.get` returns
`""`, not None. `""` is falsy, so it survives `cache_dir or ...` and lands in
`self.cache_dir` as a directory to cache into. huggingface_hub does what you would do
with any relative path: it resolves it against wherever the process happens to be
running. So the model weights, all 1.29 GB of them, download into the directory the
command was typed in. W6-T1's implementer did this to a worktree root while verifying,
noticed, and deleted it.

Nobody types `export TELLTALE_HF_CACHE=` by accident, but everybody types it on purpose:
it is how a shell says "unset this for now". `TELLTALE_HF_CACHE= some-command` is the
same sentence for one command only. The shell has one way to say "no value"; Python
distinguishes "not set" from "set to nothing"; the `or` collapsed them in the wrong
direction.

The fix is one more `or`:

    return explicit or os.environ.get(CACHE_ENV) or None

Now three spellings of "you choose" - not passed, not set, set to nothing - all arrive at
the loader as None, and only a real path is treated as a path.

The part worth more than the fix is where it lives. The obvious place is beside its one
caller in `forecast/timesfm.py`. Put it there and no test in CI can ever run it: that
module imports numpy at the top and torch inside its constructor, both of which live
behind the `forecast` extra, and CI installs no extras. A test of the rule would need a
gigabyte of machine learning stack to check three lines of string handling. So the rule
moved one module up into `telltale/forecast/__init__.py`, which is stdlib-only by
invariant 3 in AGENTS.md, and `timesfm.py` calls it. Four tests now run on every commit,
in an environment where torch does not exist. The name `CACHE_ENV` is still importable
from `timesfm.py`, because two documents cite it there.

**The second one costs a sentence, which is worse.**

`telltale advise` prints, for each of three targets, what the stored forecasting work
says about it. To find that work it asked the runs table for the newest row of this
series and target in TRUE order - "true order" meaning the real chronology rather than
one of the shuffled placebo controls.

Last week W6-T1 added `forecast scenario`, which stores a row in the same table. A
scenario stands at the end of the series and asks a conditional question: suppose the
next four requests each make eight tool calls, what then? It is in true order. It has no
score, because there is nothing at the end of a series to score a forecast against, and
its `metrics` field is empty for exactly that reason.

So the moment somebody ran a scenario on an advise target, the advisory picked up the
scenario row, found no decision on it, and printed:

    label: not assessable

That reads as a verdict. In this system `not assessable` is the decision rule's own word
for "I looked at this run and could not label it", which normally means there were too
few windows to judge. It is a thing the rule SAYS. Here no rule had looked at anything.
A conditional forecast had been mistaken for a failed measurement, and the page reported
a judgement nobody had made, silently, in the place where the honest answer already
existed: `no assessable forecast`, which means nothing has scored this pair.

The distinction was already in the code, one file away. `scenario.calibration` looks for
a backtest to quote and requires `metrics["forecasters"]` to be there, precisely because
a scenario row would otherwise look like one. The advisory now asks the same question the
same way:

    and (row["metrics"] or {}).get("forecasters")

With a real backtest present the advisory shows the backtest's label again. With only a
scenario present it says `no assessable forecast`, which is true.

**What the two have in common.**

Empty string, empty dict. Both are falsy, both were being read as "absent", and in both
cases absent was the wrong reading: `""` is a value somebody set, `{}` is a run somebody
stored. AGENTS.md's verification section has a line for this - "Absence is not zero and
duplicate is not one" - and names it the defect class of a recorder rather than a defect
class. Two more instances of it, found by the person who wrote the code that exposed
them, reported rather than fixed in place because both lines were outside that task's
list of files, and fixed here.

That is the part of this worth keeping. W6-T1 hit both of these while verifying its own
work, wrote them down with the one-line fix for each, and did not touch either file. Both
were true, both reproduced first try, and both had a test written against them within an
hour. A report that says "I broke this and here is exactly how" is worth more than a
clean report, and the discipline that produced it is what made this task ten minutes of
thinking rather than an afternoon of archaeology.
