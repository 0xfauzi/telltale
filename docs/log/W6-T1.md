# W6-T1 scenario horizons

## OUTCOME

`telltale forecast scenario --series ID --target T --horizon H --future col=v1,...,vH
[--future ...] [--name NAME] [--forecasters a,b] [--model M] [--device D]
[--compare-with RUN_ID]` exists. It builds one window at origin N, the end of the
series, hangs each declared path on it as a past-future covariate of length n_ctx + H,
runs every named forecaster on that one window, prints the page and stores one
`forecast_runs` row whose `claim_class` is predictive and whose `scenario` column holds
the declared paths, the declarable registry, the command and the sentence.

Five things carry the task.

**There is now a registry of which covariates may carry a future path.** There was none:
`role="past_covariate"` is hardcoded in both compilers and `ColumnSpec`'s
`future_covariate` role has never been emitted, so every column was past-only by
construction and nothing said which of them could be otherwise. `DECLARABLE` is that
registry, keyed by clock: four request-clock columns and `ABLATION_A` on the change
clock. Every other column is refused with one sentence, `PAST_ONLY`: "past-only: this
column is observed, never planned". The line is about who decides the number, not about
the data: nobody sets how many output tokens a model emits, so a declared path for one
is a wish rather than a supposition.

**A scenario is not a backtest, and the row says so in three places.** Origin N is one
past the last row, so there is no actual: the window record carries `actual: null`,
`metrics` is `{}`, and the warning `no actual: a scenario has no error` says which empty
that is. Calibration is quoted from the newest stored true-order backtest of the same
(series, target, horizon, registry variant) by run id and never recomputed here; where
none exists the page says `no stored true-order backtest ... calibration is not
assessable and none is quoted`, which is always the answer at H = 8 and H = 16 because
no backtest can exist there.

**The horizon is free, and the number is measured.** `SCENARIO_HORIZONS = (1, 4, 8, 16)`
against the registry's backtested `(1, 4)`. Measured on this machine, CPU, one 80-row
window, five calls each with the checkpoint loaded once: H = 1 is 87.9 ms median and
H = 16 is 87.4 ms median. The brief's stop condition was 120 s for one H = 16 window.
The full table is in VERIFY.

**Under the baselines two scenarios are one forecast printed twice, and the page says so
twice.** `NOT_A_READER` names every forecaster that reported reading no past-future
covariate, read off `ForecastResult.covariates`. `compare` then says it again from the
numbers, which is the measurement rather than the declaration: two identical point paths
under two different declarations is what "did not read it" means. Under TimesFM the two
differ, and the real numbers are in EXPLAIN FOR THE OWNER.

**Everything ends with the sentence.** `a scenario is a conditional forecast, not a
plan`, in `assumptions` on the stored row, in `scenario.sentence` on the same row, as the
last line before the licence on every report, and as the last line of every `compare`.
`refuse_words` runs over the finished string before it is printed and over the row before
it is stored.

## WHAT WAS WRONG

Nothing was broken. What was missing was the conditional question and the registry that
bounds it.

Design 6.12 gives the laboratory four protocols and every one of them scores a forecaster
against a history that already happened: the rolling-origin backtest, the chronology
placebo, the A/B/C ablation and the one-step candidate protocol. `forecast candidate`
comes closest, and its `one_step` does stand at origin N, but it conditions on ONE thing
read off a git diff and forecasts ONE step. There was no way to ask "suppose the next
four requests each make eight tool calls" at all, and README's v0.6 gate text asks for
exactly that: "longer horizons only with explicit future-workload assumptions".

Two smaller things were wrong with the shape a first attempt would take.

**The registry did not exist, and its absence was invisible.** `Window.future` has been
in the model since W5-E11 and `forecast/timesfm.py` has read it into
`past_future_covariates` since W3. Nothing anywhere said which columns were allowed
there, so the honest default was "the caller decides", and a caller who declared a path
for `fresh_input_tokens` would have got a plausible forecast conditioned on a quantity
nobody can set. That is the class of number this system exists to refuse.

**A scenario row would have looked like a backtest row with a missing score.** The
`forecast_runs` table has one shape, and a row with `metrics = {}` and `ordering = true`
is indistinguishable from a backtest that failed to score unless the row says otherwise.
Three fields carry the distinction: `actual: null` on the window (null and not `[]`,
because "nobody observed these steps" and "these steps held nothing" are different
statements), the `NO_ACTUAL` warning, and `variant` ending in `_scenario`.

## UNSURE OR NOT DONE

**`cli_advise._latest` would pick up a scenario row.** It filters `forecast_runs` on
target and `ordering == "true"` only, so a scenario stored on a change-clock candidate
target becomes "the newest true-order run" for `telltale advise`, and `_label` then
returns `NOT_ASSESSABLE` because the row's `decision` is null. That reads as "the rule
looked and wrote no label" when in fact no rule looked. It cannot happen today (advise
runs only on the three post-merge targets, and W5-T2 measured that no true-order run for
them can exist on this repository yet), and cli_advise.py is not this task's to edit. The
one-line fix is to require `row["metrics"]` there, the same guard `scenario.stored` uses.
Named for a later task.

**An empty `TELLTALE_HF_CACHE` makes huggingface_hub cache into the current directory.**
`TimesFM.__init__` does `cache_dir or os.environ.get(CACHE_ENV)`, and an env var set to
the empty string survives that `or` as `""`, which HF resolves relative to cwd. I hit it
while verifying and downloaded 1.29 GB of checkpoint into the worktree root before
deleting it. forecast/timesfm.py is not this task's to edit; the fix is
`os.environ.get(CACHE_ENV) or None`. Named for a later task. Nothing of it is in the
commit: `git status` is clean of it and the large-file hook passes.

**32 and 64 are not in SCENARIO_HORIZONS and would cost the same.** The measurement says
the horizon is free inside the model's internal 64. They are absent because nothing has
measured whether a 32-step-ahead conditional forecast on these clocks says anything a
reader should act on, not because of cost. Stated in the amendment.

**A declared column rides in both blocks and I did not measure what that costs the
model.** The declared column appears as a past-only row over the context AND as the
context-plus-path future block, which is exactly what `candidate._attach` does with
ABLATION_A against ABLATION_C. On the request clock that is 1 target + 10 past-only + 1
past-future = 12 variates against the adapter's cap of 32. Whether feeding a column
twice changes the answer is a question about the model that E03 did not ask and this task
did not either.

**Nothing here is calibrated.** Every scenario run in VERIFY prints `calibration is not
assessable and none is quoted`, because the store held no true-order backtest of that
pair. The quoting path is exercised by the code and by nothing in the suite: the test
that would cover it needs a stored backtest of the same series, target and horizon, and
`test_forecast_backtest_label.py` already owns that fixture. Named rather than faked.

## NEXT

- Require `row["metrics"]` in `cli_advise._latest`, so a scenario row cannot be read as
  the newest scored run of a pair.
- `os.environ.get(CACHE_ENV) or None` in `forecast/timesfm.py`, so an empty
  `TELLTALE_HF_CACHE` does not cache a 1.29 GB checkpoint into the working directory.
- A test that stores a backtest first and then a scenario of the same pair, so the
  `calibration_from` quoting path is exercised rather than only the None branch.
- Decide whether 32 and 64 belong in `SCENARIO_HORIZONS`. The cost is measured and it is

  for.

## EXPLAIN FOR THE OWNER

Here is the whole thing in one example.

Your session has made 200 model requests. The last one emitted 1127 output tokens. You
are about to keep going, and you want to know roughly how big the next four responses
are. There are two ways the next stretch could go: quietly, two tool calls per request,
or busily, eight. You want a number for each.

That is a conditional forecast, and it is not a thing the laboratory could do before
today. Every protocol in it points backwards: give the forecaster a window that ends at
row 40, compare what it said against rows 41 to 44, which already happened, and score it.
There was nowhere to stand at row 200 and ask a question about row 201, because row 201
is not there to be scored against.

So `forecast scenario` stands there anyway, and pays for it by scoring nothing.

**What you type.**

    telltale forecast scenario --series <id> --target output_tokens --horizon 4 \
        --future tool_calls_since_prev=2,2,2,2 --name quiet --forecasters timesfm

and the same with `=8,8,8,8 --name busy`.

**What comes back.** Under TimesFM, on the synthetic 200-row series:

    step      quiet        busy    difference
      1    1128.0195   1127.2894      -0.7301
      2    1127.6758   1122.1992      -5.4766
      3    1121.4869   1118.1931      -3.2938
      4    1119.3171   1117.3812      -1.9359

Four numbers of difference, all of them small and all of them negative: on this series,
supposing eight tool calls per request instead of two moves the forecast of the next four
responses down, by at most 5.5 tokens out of about 1120. Half a percent.

**Now the part that matters more than the numbers.**

Read that table as "making eight tool calls per request will save you five tokens" and
you have made three mistakes at once, and the system refuses each of them somewhere.

The first is reading a forecast as a plan. Declaring a path does not arrange for it.
Nothing in this command reaches out and makes your next four requests make eight tool
calls; it supposes they do and asks what the forecaster says under that supposition. That
is why every page ends with the same line and why the line is stored on the row rather
than printed and forgotten: `a scenario is a conditional forecast, not a plan`.

The second is reading a difference between two forecasts as an effect. Only one future
gets observed. The -5.4766 at step 2 is a fact about how TimesFM responds to a covariate
you moved from 2 to 8; it is not a fact about what happens to your token bill when you
change how you work. That is the same argument `forecast candidate` already makes about
merging a change, and the reason the words cause, impact and would cannot be printed by
anything in this package.

The third is reading a small number as a precise number. Nothing here is calibrated. The
page says so in plain words, on both runs:

    no stored true-order backtest of this series, target and horizon: calibration is
    not assessable and none is quoted

If you had run `forecast backtest` on this pair first, the scenario page would print that
run's id and its coverage80 beside these numbers, quoted, so you could go and read how
well that forecaster's intervals held up at this horizon on this series. It never
recomputes one, because a calibration computed at an origin with no actual behind it is
not a calibration of anything.

**And now run the same pair under the baselines instead.**

    step      quiet        busy    difference
      1     1127.0      1127.0         0.0
      2     1127.0      1127.0         0.0
      3     1127.0      1127.0         0.0
      4     1127.0      1127.0         0.0

Zero, four times, and the page tells you why in two different ways. Before the run it
says it from what the forecasters declared: `these forecasters reported reading no
past-future covariate`. After the run `compare` says it again from the numbers:
`identical under both declarations`. The persistence baseline is `the last value, held
flat` and it has never looked at a covariate in its life. Its answer to "quiet or busy"
is the same answer because it did not hear the question.

That zero is the most useful line on the page, and it is why the command prints it twice
from two different sources. A zero difference has two possible meanings: the declaration
genuinely does not move the forecast, or nothing read the declaration. They look
identical in a table and they are opposite conclusions. So the run reports what each
forecaster SAID it read, and `compare` reports what the numbers SHOW, and when those two
ever disagree you have found something worth looking at.

**What you may and may not declare.**

    $ ... --future fresh_input_tokens=1,1,1,1
    fresh_input_tokens: past-only: this column is observed, never planned.

Four request-clock columns can carry a declared path: tool calls, files edited,
verification runs, and whether a compaction happened first. Those are settings. You can
decide to allow two tool calls or eight; you can decide to require a test run. You cannot
decide how many input tokens the model reads. That column is a record of what the session
did, and supposing a future value for it is supposing somebody else's past. Nine other
columns are refused the same way, each by name.

**The last thing, and it is a small pleasure.** Design 6.12 says TimesFM rounds every
horizon up to 64 internally, so asking for one step costs what asking for sixty-four
costs. That is usually stated as a warning. Here it is a gift: sixteen steps ahead is the
same 87 milliseconds as one step ahead, measured five times each on this machine. The
reason `SCENARIO_HORIZONS` stops at 16 is not that 32 would be slow. It is that nobody
has yet worked out what a thirty-two-request-ahead conditional forecast is for.
