# W6-T3 export, purge, retention, schema

## OUTCOME

Four commands and one round trip.

`telltale export --format jsonl|parquet --out DIR [--capture ID]` writes one file per
table plus a manifest. `telltale import export --root DIR [--dry-run]` reads the
observations back into an empty store and rebuilds the derived rows. `telltale purge
--diagnostics-older-than N` is the first caller `store.purge_diagnostics` has ever had.
`telltale doctor` grew a fourth block, `retention`, read from the real store read-only
and never part of the exit code. `telltale schema` prints the allowlist and the four
durable shapes as JSON.

On a `.backup` copy of the owner's store, 1,138,974 observations in 3,314 captures: the
jsonl export and the parquet export both wrote exactly the row counts `sqlite3
count(*)` gives, the round trip into an empty home came back with the same 1,138,974
observations across the same 100 observation types and the same 3,314 captures,
`telltale sessions` printed the same 3,314 rows, `telltale show` was byte-identical for
two captures including `reducer_version`, and a second import added 0.

Four things carry the task.

**The export writes the stored columns and invents nothing, with one deliberate
exception.** The column list comes from `PRAGMA table_info`, so it is the schema itself
and cannot drift from schema.py. The exception is `activities.claim_class`, which the
table does not have because model.py refuses any Activity that is not derived: the
export writes the constant read off `model.Activity`'s own field default, because a file
of 354,241 activity rows with no claim class beside them is a file a reader may take for
observations, and invariant 6 exists to prevent exactly that.

**The round trip carries observations only.** Activities, evidence, series snapshots and
forecast runs are never re-imported; the import calls `store.rebuild` on every capture it
created. The `derived-writes-only-in-store` hook keeps those INSERT statements in
store.py, and a rebuild is the only route that keeps the reducer version honest. It came
back exact: after rebuilding the six captures the SOURCE had never reduced, both stores
held 354,977 activities and 135,874 evidence rows, capture for capture.

**"A row that was sanitized once must pass again" is false on the real store, and
measuring why is most of this task.** 19 per cent of the owner's 1,138,974 rows fail
that rule for three reasons and none of them is a leak. WHAT WAS WRONG below has the three, and the
third is a defect in `commands.normalize` that nothing in this repository knew about.

**The gate refuses what the current rules would remove for a privacy reason, and counts
the rest.** A planted `prompt` field refuses the whole file before a row is appended; a
renamed allowlist field and a re-normalized command are counted and named on the output.
Break-and-restore is pasted below: with the gate switched off, a planted prompt lands on
the far store's disk.

## WHAT WAS WRONG

Nothing was broken. Two things were missing and one was wrong in a way nobody had looked
at.

**`export` and `schema` did not exist.** cli.py's docstring said so in as many words:
"Every other command named in the design (schema, export) arrives with the task that
implements the thing it prints."

**`store.purge_diagnostics` had no caller.** It has been in store.py since W0 as the one
age-based deletion in the system (design 6.5) and nothing in src/ or tests/ called it, so
the owner had no way to remove a diagnostics row without deleting the capture it belongs
to. Nothing reported the real store's diagnostics either: `doctor._diagnostic_kinds`
counts kinds in the THROWAWAY store its own round trip builds and then removes.

**`commands.normalize` is not idempotent on its own output.** This is the finding.

    normalize("cat /Users/someone/secret.txt")  ->  cat <outside>/8c1075f0
    normalize("cat <outside>/8c1075f0")         ->  cat < outside > <outside>/69f5ca73
    normalize("cat < outside > <outside>/...")  ->  cat < outside > < outside > <outside>/61284196

A path already reduced to `<outside>/<hex>` is re-read on the next pass as a shell
redirection, the marker is split into three tokens, and the remaining text is hashed
again into a different digest. Each pass adds a pair and changes the hash. It happens for
every command holding a path outside the repository, which on the owner's store is
37,955 rows across seven observation types; 40 more then re-truncate at MAX_COMMAND,
having been at the 512-character bound already. 37,995 rows in all.

The consequence reaches past this task. `store.resanitize` rewrites the stored commands
an older normalization version wrote, and its docstring claims idempotence in these
words: "a second run over the same store returns {}, which is the whole idempotence
claim: the rules are applied to their own output and find nothing." That claim holds only
because `_stale_captures` filters on `normalization_version NOT IN (current, fallback)`,
so a row at the current version is never re-normalized. The moment a NEW normalization
version lands, `resanitize` will walk every stored command written under the old one and
turn `cat <outside>/8c1075f0` into `cat < outside > <outside>/69f5ca73`, in place,
irreversibly, on 88,754 rows. It removes nothing (the marker is already a hash) but it
mangles the normal form and changes the hash, so two rows recording the same command
before and after would no longer compare equal, and `commands`-derived evidence would
move for a reason nothing recorded.

I did not fix it: commands.py is not this task's to edit, and the fix is a rule about how
normalize treats its own markers that wants its own measurement. It is written up here
because W6-T3 is the first thing that ran the normalizer over its own output at scale.

## WHAT CHANGED

Two new modules, one new test file, and edits to four existing files.

`src/telltale/export.py` (775 lines, new). `export(store, out_dir, fmt, capture_id)`
streams each table through one read-only cursor into `<table>.jsonl` or
`<table>.parquet` and writes MANIFEST.json. `import_export(store, root, dry_run)` is the
trip back: two passes over `observations.jsonl`, the first sanitizing every row and
writing nothing, the second appending the rows of captures this store does not hold.
`pyarrow` is imported inside `_write_parquet` and nowhere else in the package.

`src/telltale/cli_export.py` (120 lines, new). `export_command` and `schema_command`,
plus `add_commands`. `_schema()` reads the allowlist, the Kind enum, NEVER_PERSIST, the
four dataclasses, CLAIM_CLASSES and COVERAGE; it restates none of them.

`src/telltale/cli_import.py`: an `export` kind beside `claude-transcripts` and
`codex-rollouts`. `--since`, `--project` and `--level` are refused for it rather than
ignored.

`src/telltale/cli.py` (754 lines): the import, `cli_export.add_commands`, two dispatch
entries, `purge --diagnostics-older-than N` with the positional now optional, and one
line in `doctor()` that prints the retention block. That last line is one more than the
brief's "the purge flag and the two registrations only", and it is there because the
function that prints doctor's other three blocks is the only place a fourth can go.

`src/telltale/doctor.py` (381 lines): `retention()`, `_retention_block` and `_age_days`.
It is the one function in that file that returns rendered text rather than rows, because
the block is a total, a table and a sentence, and returning three things for cli.py to
reassemble would put the shape of one block in two files. Its docstring says so.

`pyproject.toml`: the `DEP002 = ["pyarrow"]` entry is deleted, as the comment at 261-262
instructed. deptry is clean with the extra installed and without it.

`tests/integration/test_export.py` (13 tests, 2 of them skipped without the `export`
extra).

### Break and restore

The gate is the only thing standing between an edited export file and the store, so it
had to be broken to show it is load-bearing. `_check_row` was made to `return []` and a
`prompt` field was planted in `observations.jsonl`:

    === gate OFF ===
    import returned: {'captures': 1, 'added': 1}
    PLANTED-SECRET-PROMPT on the far store's disk: True

    === gate RESTORED ===
    ValueError: .../out/observations.jsonl: 1 row(s) pass the sanitizer at no content
    level their capture could have been recorded at, so this file holds something the
    store would not have accepted:
      01M1M34BBZXB0T1MN4C173N9T0 (claude.hook.PreToolUse): prompt:never_persist would
      be dropped

and under pytest, with the gate off:

    E           Failed: DID NOT RAISE ValueError
    FAILED tests/integration/test_export.py::test_a_planted_prompt_refuses_the_file

## UNSURE OR NOT DONE

**A diagnostics row older than the retention window is not tested.** `store.diagnose`
stamps `now_iso()` and the store offers no clock a test may set, so the only way to make
a row two days old inside a test is to wait two days. The brief anticipated this and said
to stop and report rather than invent one, and that is what happened.
`test_purge_diagnostics_window` proves the cutoff is `now - N` and not `now` (a row
written this instant survives a one-day window), the refusal of 0, of a negative N and of
both or neither argument. The removal itself is verified by hand, above: 3,196 rows
counted by `sqlite3` and 3,196 purged. Giving the store an injectable clock is a store.py
change and store.py was not this task's to edit.

**An absolute path written by hand into a `command` field of an export file is not
caught.** The gate normalizes it to `<outside>/<hex>`, which is a changed COMMAND value,
and a changed COMMAND value cannot be a refusal while `commands.normalize` is not
idempotent. Every other leak is caught: a `never_persist` field, a matched secret, an
exceeded bound and a rewritten PATH field are refused at every content level. Closing
this one needs the normalize fix.

**A re-imported diagnostic loses its original `ingest_ts`.** `store.diagnose` is the only
public write path and it stamps its own clock, so the far store sees these rows as fresh
and `purge --diagnostics-older-than` there measures from the import rather than from the
event. The export file holds the true timestamp. Preserving it needs a write path
store.py does not have.

**232 diagnostics with no capture_id are not re-imported.** They belong to the process
that wrote them rather than to a capture, so nothing can decide whether a second import
would be recording them again. They are skipped and counted, not lost silently.

**One flaky test run.** During the first full-suite run,
`test_doctor_round_trips_every_surface_and_leaves_nothing_behind` failed once. It did not
reproduce: the same test passed alone, a repeat of the whole suite passed 297 of 297, and
15 consecutive runs of `test_doctor_setup.py` (150 tests) passed. The failing run was
concurrent with a 1.5 GB export writing to the same disk. I do not know what it was and
am not claiming it is unrelated to this change; it is recorded so the next person who
sees it has a prior.

**`import export` cannot complete a capture whose import was interrupted.** A capture
already in the store is skipped whole, which is `importer.import_files`' existing rule and
what makes a second import add 0. `telltale purge` it first.

## NEXT

1. **Fix `commands.normalize`'s idempotence, before any new normalization version
   lands.** The failure is above and it is reachable today through `store.resanitize` on
   88,754 rows the moment the version constant changes. The shape of a fix is a rule that
   makes the normalizer recognise its own `<outside>/<hex>` marker as one token, but that
   is a guess and it needs measuring against the stored commands rather than against
   examples.
2. **Give the store an injectable clock, or a test-only backdating helper beside
   `pause_writer`.** Retention is the second feature (after the drop counters) whose
   behaviour over time cannot be verified in the suite.
3. **Decide whether `advise` should rebuild its own capture.** The two `adv_` captures on
   the owner's store carry observations and no derived rows, so `telltale show` routes
   around them by prefix. The round trip reduced them, which is why the two stores
   differed until the source was rebuilt.

## EXPLAIN FOR THE OWNER

Your recorder now has a door out and a door back in, and the trip through both changes
nothing.

**Out.** `telltale export --format jsonl --out DIR` writes six files, one per table, plus
a manifest that says how many rows went into each. On your store that is 1,138,974
observations, 354,241 activities, 135,628 evidence rows, 8 series snapshots, 12 forecast
runs and 19,819 diagnostics: 1.5 GB of text. `--format parquet` writes the same rows in
238 MB, and needs `uv sync --extra export` because pyarrow is the one package that half
of this command depends on and a plain sync installs no extras. Each file holds exactly
the columns the database has, read out of the database itself so the two cannot drift
apart, with one addition: an activity row carries `claim_class: derived`, because that
column does not exist in the table (an activity is derived by definition) and a file of
354,241 rows with no claim class beside them is a file somebody will one day read as
observations.

**Back in.** `telltale import export --root DIR` puts the observations back. It does not
put the activities or the evidence back: those are computed, one file in this repository
is allowed to write them, and the import instead rebuilds each capture from the
observations it just restored. That is a stronger claim than copying them would be, and
it held: after the round trip into an empty store, all 3,314 captures came back with the
same observations of the same 100 types, `telltale sessions` printed the same table, and
`telltale show` was byte-for-byte identical on the two captures I compared. A second run
of the same import adds nothing at all.

**The interesting part is what the import checks.** Before it writes a row it runs the
payload back through the sanitizer, and the intent was simple: a row that was cleaned
once must come out of the cleaner unchanged, and if it does not, the export leaked
something. On your store that rule refuses one row in five. Three reasons, and none of
them is a leak:

The sanitizer stamps `normalization_version` into every payload holding a command. On the
second pass that stamp arrives looking like a field a provider sent, which no allowlist
lists, so it is dropped and restamped. It is the cleaner's own signature.

W4-T4 renamed four fields (`claude.stream.assistant.output_tokens` became
`output_tokens_snapshot`, and `claude.stream.result`'s usage fields moved under
`main_thread_`). 6,521 rows written before that carry the old names, which the current
table does not recognise. Those rows went through the gate that existed when they were
written. The table moved afterwards; they did not.

And the third: **the command normalizer is not idempotent.** Feed it its own output and
it changes it. `cat /Users/someone/secret.txt` becomes `cat <outside>/8c1075f0`, which is
right. Feed that back and you get `cat < outside > <outside>/69f5ca73` - it reads the
`<outside>` marker it wrote as a shell redirection, splits it into three tokens, and
hashes what is left into a different digest. A third pass adds another pair. 37,955 of
your stored rows change this way, and 40 more get re-truncated by it.

That last one is a real defect and it is not confined to the export. `telltale
resanitize` exists to rewrite stored commands through newer rules, and its docstring says
running it twice finds nothing. That is true today only because it skips any row already
at the current version. The day a new normalization version lands, resanitize will walk
88,754 stored commands and rewrite every path outside your repositories into that
mangled, re-hashed form, in place, with no way back. Nothing is disclosed by it (the
marker is already a hash) but the normal form stops being comparable to itself. I did not
fix it: commands.py belongs to another task and the fix wants its own measurement. It is
the first item under NEXT and I would not ship a normalization version change before it.

So the import's check is the one the evidence supports: it refuses anything the current
rules would remove for a privacy reason (a forbidden field, a matched secret, an exceeded
bound, a rewritten file path), and it counts and names the rest on the command's output
rather than pretending it did not happen. To show the check is real rather than
decorative I switched it off and planted a `prompt` field in the export file: the prompt
went into the store and I found the text in the database file on disk. Switched back on,
the import refuses the whole file, names the observation and the field, and writes
nothing.

**Two smaller things.** `telltale purge --diagnostics-older-than N` is the first caller
`store.purge_diagnostics` has ever had: it deletes diagnostics older than N days and
prints the count and the cutoff. On your store copy, `--diagnostics-older-than 1` removed
3,196 rows, which is the same number `sqlite3` counts for that window. It refuses 0 (0 is
"now", so it would delete everything while reading like a retention window) and refuses
negatives. And `telltale doctor` now ends with a `retention` block: how many diagnostics
your real store holds, broken down by kind, with the oldest of each and its age in days,
so you can pick N off a row. It reads your store read-only, it never writes to it, and it
can never change doctor's exit code. There is no threshold and no warning in it, because
nothing has measured what a healthy number of diagnostics looks like.

`telltale schema` prints the whole allowlist as JSON: 108 observation types with the
field names each may store and how each field is cleaned, the 33 field names that can
never be stored at any level, the four durable shapes' fields, and the claim class and
coverage vocabularies. All of it read out of the tables and the dataclasses, none of it
restated, so it cannot tell you something the code does not do.
