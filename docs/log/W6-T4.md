# W6-T4 compatibility matrix and hardening

## OUTCOME

Three things landed.

`telltale doctor --matrix` prints, for the store on this disk, one row per (provider,
runtime version) it holds captures of: how many captures, when they were first and last
seen, which surfaces delivered, and the coverage word each capability got counted across
them, followed by each provider's DRIFT list once. On the owner's store that is 75 rows
spanning Claude Code 2.1.185 to 2.1.259 and Codex 0.39.0 to 0.150.1, with 730 coverage
rows under them. It reads the real store read-only and it is never part of doctor's exit
code.

The three ways a capture fails are provoked in `tests/integration/test_hardening.py`
through the real launcher and the real fake agent, and each is now legible:

  - a held port: `telltale run` is unaffected because its receiver port is OS-chosen,
    and `telltale daemon` on a held port prints one line naming the port and the holder
    and exits 1, where before it printed 23 lines of traceback;
  - a signal: the exit codes were already right (143 and 137) and are unchanged, and
    `telltale.capture_ended` now carries `terminal`, which is `exit` or `signal N`;
  - a locked database: a run whose store is locked past the writer's retry ladder loses
    a batch, and it now says so in a `launcher` diagnostic naming the count and the state
    of the lock, which `telltale doctor` prints on a `last launcher diagnostic:` line.
    Before this it left nothing at all: no capture_ended row, no activities, no
    diagnostic.

`telltale setup claude|codex --print --daemon [--port N] [--level L]` prints a
`com.telltale.daemon` launchd plist (plutil-lint clean) and then the same provider
snippet as without `--daemon`, pointing at the same port. It is printed and never
written; `--apply` still refuses, and `~/Library/LaunchAgents` holds nothing of ours
before or after.

The child's exit code is unchanged in every measured case: 0, 143, 137, and the daemon's
1, which was already 1 as an uncaught exception.

## WHAT WAS WRONG

**Nothing read design 6.7's coverage back.** Every capture records the coverage word each
capability got, on its lifecycle activity, and that is what the forecasting side reads
per capture. There was no way to ask the store-wide question: which agent versions has
this machine captured, and what turned out to be observable on each. The answer matters
because the version is the thing that changes underneath: E01 measured Claude Code
2.1.257 and W2-T6 had to re-measure for 2.1.258, and the owner's store holds captures of
30 numbered Claude versions and 41 numbered Codex versions that nobody had counted.

**Two of the three failures left nothing behind.** Measured before any change:

    telltale daemon --port 47311, port held
      23 lines of traceback ending in OSError: [Errno 48] Address already in use
      exit 1, and the store it had already opened was never closed

    a second process holding BEGIN IMMEDIATE for 75 s while a run captured
      run exit code 0 (the child's), after 71.2 s
      3 observations on the disk: repo.identity, environment, capture_started
      no capture_ended, 0 activities, 0 diagnostics of any kind

The second is the one that matters. A capture that lost its ending is indistinguishable
from a capture nobody has reduced yet, and `telltale show` prints the same "run
`telltale rebuild`" refusal for both. The store's own record of the loss cannot be
written, because writing it needs the lock that is being held.

**A signalled child was recorded as a number that has two meanings.** SIGTERM to the
launcher gave exit 143 and `capture_ended.exit_code` 143, which is correct and is also
exactly what a child that returned 143 itself produces. Nothing on the capture said a
signal had happened.

## WHAT CHANGED

`src/telltale/doctor_matrix.py` (new, 345 lines). `matrix(store) -> list[dict]` and
`render(rows) -> str`. One row per (provider, runtime), grouped as the captures are read.
The runtime version is taken from three named sources in order (`probe` the launcher's
`--version`, `session` the stream's `claude_code_version`, `record` the version the
provider wrote into its own session file), and the row says which spoke. Design decisions
and the measurements behind them are in `docs/design/amendments/W6-T4.md` section 1.

`src/telltale/launch_health.py` (new, 94 lines). `lost(store, capture_id)` reads
`store.health()` at the end of a capture and writes the `launcher` diagnostic when
anything was lost; `lock_state(path)` is the probe that names the lock. Split out of
launch.py rather than written into it because launch.py was at 734 lines against the
800-line ratchet, and because this is the only module outside store.py that opens a
sqlite3 connection: keeping it here is what keeps that import out of the launcher.

`src/telltale/setup_daemon.py` (new, 104 lines). `plist(port, level, home, binary)` and
`binary()`. plistlib, not a formatted string: a home directory may contain `&`, and one
un-escaped path is a file launchd refuses to parse.

`src/telltale/launch.py`. `_Capture.terminal`, set in `_child` off the negative code
`Popen.wait` returns; `_ended` carries it; `_finish` gains one guarded step calling
`launch_health.lost`. No signal handling changed and no exit code changed.

`src/telltale/cli.py`. `doctor --matrix`, the `last launcher diagnostic:` line,
`setup --daemon`, and the daemon's bind failure caught and printed as one line.

`src/telltale/doctor.py`. `last_launcher()`, which reads the real store read-only and
returns the most recent `launcher` diagnostic as one line.

`src/telltale/allowlist_telltale.py`. One key: `telltale.capture_ended.terminal`, a
`Kind.ENUM`. **This file is not in the task's OWNS list.** Without the key the allowlist
gate drops the field and writes an `unknown_field` diagnostic instead, so the DO item
asking `capture_ended` to record `terminal: signal 15` cannot be met without it. It is
one line and no other task in this wave owns the file.

`tests/integration/fake_agent.py`. `--sleep SECONDS`, which idles after the init line and
before any tool call. The brief anticipated this: no existing flag makes the process
outlive its own startup, and a signal aimed at a running launcher needs it.

`tests/integration/test_hardening.py` (new, 441 lines, 8 tests). The three failure
modes, the lock probe's two answers, the probe's cost, and one test that an ordinary run
says nothing about the store, so that a diagnostic firing on every capture would not
pass.

`tests/integration/test_doctor_setup.py`. Four tests: the matrix on a store with one
capture, the matrix on a machine with no store, the plist parsed with plistlib, and
`--apply --daemon` still refusing. **This file is not in the task's OWNS list either.**
It is where "the two commands that answer questions about Telltale itself" are tested,
`--matrix` and `--daemon` are both those commands, and no wave 6 brief claims it.

`docs/design/03-capture-howto.md`. The daemon-plist section, and two paragraphs in "When
nothing was recorded" about the `last launcher diagnostic:` line and `--matrix`.

## UNSURE OR NOT DONE

**The locked-database test costs 46 s, and that is 27 per cent of the suite.** The suite
went from 118.8 s over 284 tests to 169.5 s over 296; the lock test is 45.7 s of the
difference and the rest is the eleven other new tests. The 46 s is
not a choice: `store.BUSY_TIMEOUT_MS` is 5000 and `RETRY_DELAYS_S` has five entries, so a
batch is given up 39.3 s after its first blocked attempt (measured), and a lock that does
not outlive that loses nothing to assert on. Shortening it means changing store.py, which
this task may not do and should not: the ladder is a decision about every writer.

**A locked run takes as long as the lock.** 71.2 s to finish recording a 6 s child under
a lock held throughout. Nothing here shortens it, and `Store.flush`'s 30 s and
`_submit`'s 30 s are the two other terms. Whether a recorder should wait that long for a
database somebody else is holding is a real question and it belongs to store.py.

**The matrix takes 2.95 s warm and 8.82 s cold on the owner's 1.5 GB store.** That is
acceptable for a flag somebody types, and it is 0.62 s of `captures()`, 1.90 s of 3312
per-capture lifecycle reads and 1.09 s of the claude transcript-user read. If it becomes
a problem the fix is a store read that answers "one row per capture" for an activity
type, which is store_reads.py's to add.

**`first_seen` and `last_seen` are arrival dates, not session dates.** They come from the
captures view's `first_ts`/`last_ts`, which is design 6.2's ingest clock, so on the
owner's store every imported version reads 2026-09-02: the day the import ran. The
session's own clock is on the session activity and `telltale sessions` prints it. Naming
the columns `first_ingest` would be more precise and less readable; the module docstring
says which clock it is.

**The plist is macOS only.** launchd is not on Linux, and nothing here refuses to print
the plist on a Linux machine. A systemd user unit is the same idea one platform over and
nobody has asked for it.

**`--matrix` prints 873 lines on the owner's store.** One row per (provider, runtime,
capability) is 730 of them. It is a table, so it greps, and the flag is explicit, but a
`--provider` or `--since` filter is the obvious next thing if anybody reads it twice.

## EXPLAIN FOR THE OWNER

### The question the matrix answers

You have been recording sessions for a while. Somewhere in that database are captures
made by thirty numbered versions of Claude Code and forty-one of Codex, because both ship
most days and you upgrade without thinking about it. That matters more than it sounds
like it does: what Telltale can see is a property of the version. W2-T6 measured that
2.1.258 sends no `git_commit_id` anywhere, on any surface, across 19313 observations,
where E01's 2.1.257 fixture carried one on a tool result: on that version, linking a
commit to a session can only be done from repository snapshots. The transcript files your
older sessions left behind carry token usage on every assistant line (10382 of 10382,
measured over 250 of your files) and no context window on any line at all.

So "can Telltale see compaction?" has no answer. "Could Telltale see compaction on the
captures I have of 2.1.250?" has one, and it is in the database already: `observed` on
all 416 of them. Every capture records the coverage word each capability got, at the time
it was recorded. Nothing read those back across the store until now.

    uv run telltale doctor --matrix

One row per version. Here is the shape of it, from your own store:

    claude    2.1.257     record                  37    import, transcript
    claude    2.1.259     probe                   83    external, hook, launcher, otel_logs, otel_metrics, stream

and under it, per capability:

    claude    2.1.257     context_window   unavailable 37    37
    claude    2.1.259     context_window   observed 81       81

Read that carefully, because it is the kind of thing this table is for and the kind of
thing it is easy to misread. It does not say 2.1.259 added a context window. It says the
37 captures you have of 2.1.257 were imported from transcript files, and a transcript
does not carry the session's context window, so on those captures the number is unknown;
the 83 captures of 2.1.259 were recorded live with the stream surface attached, and the
stream's result message carries it. The difference is which surfaces delivered, not which
version you ran. The `SURFACES` column beside each row is what tells you that, which is
why it is there.

The `SOURCES` column is the other thing worth knowing. Three different things can tell
you what version produced a capture and they are not the same fact:

  - `probe`: Telltale ran `claude --version` before starting the child. It is the most
    direct, and it only exists for captures made by the launcher.
  - `session`: the session said so itself, on its own output stream.
  - `record`: the version was written into the session file the provider left behind,
    which is where an imported capture gets it.

On your store: 136 captures from the probe, 7 from the session, 3147 from the record, and
22 that nothing names at all. Those 22 are their own row with a `-` for the version. They
are not folded into any version's counts, because a capture whose version nobody recorded
would otherwise add coverage words to a version it may not have come from.

### The first failure: something is on the port

Telltale has two ways to receive from an agent. `telltale run` starts a receiver for
exactly one session and lets the operating system pick a free port for it, so nothing can
be in its way. The daemon binds a fixed port, because a snippet you pasted into
`~/.claude/settings.json` names that port and it cannot change under you.

So the port failure is the daemon's alone, and until now it looked like a crash:

    Traceback (most recent call last):
      File ".../cli.py", line 678, in main
      ...
    OSError: [Errno 48] Address already in use

Twenty-three lines to say one thing. Now:

    telltale daemon: cannot bind: port 47311 held, not answering (TimeoutError).
    Address already in use. Free it, or name another port with --port.

The interesting part is the middle clause, and it is not guesswork. Before printing, the
daemon asks the port the same question `telltale doctor` asks: it opens a connection and
requests `/healthz`. Three answers are possible and each is a different problem. "held,
not answering" is a process that accepts connections and never replies, which is usually
a wedged daemon of ours. "answered by something else" is a different program on your
port. "telltale daemon" means one is already running and you have started a second.

While that port was held for the whole of a run, the run recorded normally: exit 0 and
twelve stream records. That is the design working, and the test asserts it, because "the
daemon's port is busy" must never mean "your session was not recorded".

### The second failure: a signal killed it

Two cases, and Telltale already handled both correctly. `kill <launcher>` sends SIGTERM;
the launcher passes it to the agent, waits for the agent to die, and exits 143. `kill -9`
the agent directly and the launcher exits 137. Those are 128 + 15 and 128 + 9, which is
what a shell would have reported, which is the whole promise of putting `telltale run` in
front of a command: the number does not change because you were recording.

What was missing was in the capture. 143 was stored as `exit_code: 143`, and a program
that returns 143 on its own stores exactly the same thing. There is no way back from the
number to the reason.

The kernel does tell us. Python reports a signalled child as -15 and a shell reports it
as 143, and the negative spelling is the only one that still has the signal number in it.
So the capture now stores both:

    capture_ended exit_code|terminal: 143|signal 15
    capture_ended exit_code|terminal: 137|signal 9

and an ordinary end stores `terminal: exit`. Measured on both paths, with the real
launcher, a real child and a real signal: the exit codes are unchanged at 143 and 137,
and the child was gone in both cases.

Ctrl-C is a third case and nothing about it changed. The terminal sends SIGINT to the
whole process group, so the agent already has it, and the launcher deliberately does not
send a second copy: in Claude Code the first Ctrl-C cancels the turn and the second quits
the session, so forwarding it would change what the agent does, which is the one thing
the wrapper promises not to do. The cost of that decision is that `kill -INT <launcher>`
reaches the launcher and not the agent, which docs/log/W1-T1.md states and which is still
true.

### The third failure: something else is holding the database

This is the one that was losing data quietly.

SQLite lets many readers in and one writer at a time. If another process is in the middle
of a write transaction, our writer waits. It waits well: five seconds per attempt, six
attempts, with pauses between them, and then it splits the transaction and retries each
piece of it alone, in case one piece is the problem. Measured end to end, a batch that
cannot be committed is given up **39.3 seconds** after the first blocked attempt. That is
a good ladder, and almost nothing outlasts it, which is why two `telltale run`s at once
are fine.

But something can. A `sqlite3` session left open on `telltale.db` with an uncommitted
write will hold that lock until you close the terminal. Here is what a capture looked like
when I held it for 75 seconds, measured before I changed anything:

    the run returned the child's exit code, 0
    three observations were on the disk
    no capture_ended row
    no activities
    no diagnostics anywhere

Nothing was wrong with the exit code and nothing was wrong with the agent. What was wrong
is the last line. Telltale writes a diagnostic whenever it fails, and it could not write
this one, because writing anything is precisely what it could not do. The capture that
came out reads exactly like a capture nobody has reduced yet, and `telltale show` gives
the same "run `telltale rebuild`" message for both.

The fix is a step at the very end of a capture, after the child has exited. The store
counts what it could not write, and those counters are already what `/healthz` reports;
nothing had ever read them at the end of a run. Now, if anything was lost:

    the store lost part of this capture: 1 batch(es) the writer gave up on,
    drop counters {"store":1}; the write lock on ~/.telltale/telltale.db is
    free now, so nothing here can name the cause

Two details in that sentence are deliberate.

**The count is batches, not rows.** The store gives up on a transaction, and a
transaction holds up to 500 observations. It knows how many transactions it abandoned. It
does not know how many rows were in them by the time it says so, and reporting a row
count it did not measure would be exactly the invention this project keeps refusing to
make.

**The clause about the lock is a measurement taken at that instant, not an inference.**
Telltale opens one more connection, asks for the write lock with a zero-second timeout,
and immediately lets go. If somebody else holds it, the sentence says so and names them
as the cause. If the lock is free by then, the sentence says the lock is free and that
nothing here can name the cause, which is the honest version of "I know something went
wrong and I cannot prove why". It never says "database was locked" when it did not see a
lock.

And you can find it afterwards without knowing to look:

    $ uv run telltale doctor
    ...
    last launcher diagnostic: 2026-09-03T16:59:59Z cap_01M1M3BNYJ...: the store
    lost part of this capture: 1 batch(es) the writer gave up on ...

One more measured number, because it is the cost you would actually feel. A run whose
database is locked the whole time takes as long as the lock: 71.2 seconds to finish
recording a child that ran for 6. The agent is not delayed, its output is not delayed and
its exit code is not changed; the wait is Telltale's, after the agent is gone. Making that
shorter means shortening the store's retry ladder, which is a decision about every write
in the system and not about this one case, so it has not been made here.

### The plist, and the rule it does not break

The daemon runs in the foreground, so it dies with the terminal. The macOS way to make
something start at login is a launchd agent, and Telltale will now print one:

    uv run telltale setup claude --print --daemon --port 4318

It prints the plist. It does not write it, it does not run `launchctl`, and it does not
look inside `~/Library/LaunchAgents`. That is the same rule as `telltale setup claude
--print`, and for the same reason: your machine's configuration is yours, and a recorder
that installs itself is a recorder that can outlive its own uninstall. `--apply` still
prints the refusal, `--daemon` or not.

Two things in the printed plist are worth understanding, because they are the two ways
this goes wrong for people. The path to `telltale` is absolute, and `TELLTALE_HOME` is
spelled out. launchd starts a job with almost no environment: a bare `telltale` is a job
that never spawns, and a job without `TELLTALE_HOME` records into a different database
from the one your reports read, which is worse than not recording, because it looks like
it worked.
