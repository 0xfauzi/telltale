# W7-T1 Codex request clock from rollout token_count

## OUTCOME

A Codex session now builds a request-clock series whether it was captured or imported.
Before this, per-request usage came from one surface only, `codex.otel.sse_event` with
event.kind `response.completed`. An import has no OTel surface, so on the owner's store
1,459 imported Codex captures held 149,560 `codex.rollout.event_msg.token_count`
observations, 0 `model_request` activities and a 0-row series each.

Measured on a copy of that store, on the largest of those captures:

| | before | after |
| --- | --- | --- |
| `codex.rollout.event_msg.token_count` observations | 5,736 | 5,736 |
| `model_request` activities | 0 | 5,735 |
| `series build --clock request` rows | 0 | 5,735 |
| `dropped` diagnostics | 0 | 1 |

The missing one is real and is named: a `token_count` record carrying only `rate_limits`
and no usage. It becomes no request and one diagnostic, never a zero row.

Request duration is derived on the OTel surface, from the two records that bracket one
request. S1's seven, in order: 490, 3487, 5812, 4266, 5587, 4507, 3269 ms. On the rollout
it stays None, by a rule written before the measurement and then failed by it.

Every gate is green: `uv run pytest -m integration` 381 passed 2 skipped, `uv run mypy .`

## WHAT WAS WRONG

**1. The cardinality claim in the module docstring was false.** `activities_codex.py`
said "A TURN IS NOT A REQUEST. `codex.exec.turn_completed` and the rollout's token_count
are TURN totals". The first half is right and the second confuses two fields on one
record. `info.total_token_usage` is the turn's running total. `info.last_token_usage`,
beside it, is one model request's usage.

The owner's largest rollout of the month
(`~/.codex/sessions/2026/09/01/rollout-2026-09-01T12-53-09-01a05cd0-...jsonl`, read only)
has 1 `task_started`, 2 `turn_context` and 69 `token_count` records inside that one turn,
each with its own `last_token_usage` and a `total_token_usage.total_tokens` that only
grows: 24062, 50668, 81746, 113264.

**2. The rollout's `request_usage` cell said `partial` on the strength of that claim.**
It is `observed`. Field for field on the three fixtures that carry both surfaces, each
`last_token_usage` equals exactly one `response.completed` record on the three counters
both surfaces state:

| fixture | sse `response.completed` | rollout `token_count` | with a usage mapping | paired |
| --- | --- | --- | --- | --- |
| S1 | 7 | 6 | 6 | 6 |
| S3 | 3 | 2 | 2 | 2 |
| S6 | 11 | 10 | 9 | 9 |

The brief's measurement said S6 was 10 of 10. It is 9 of 9: S6's `token_count` at
`22:57:00.814Z` has `info: null` and carries no usage at all. Its twin is the
`response.completed` at `22:57:00.813Z`, which carries no counters either, so the two
surfaces agree that this response was never counted. That is the `dropped` case, and it
is why S6's `show` diagnostics went 3 to 4.

The sse records with no rollout twin are the pre-turn one on all three (input 11437,
cached 0, output 0) and, on S6, that uncounted response.

**3. Nothing on any Codex surface times a model request, and one field looks like it
does.** `codex.websocket_request` carries a `duration_ms`. Measured on S1 it is 2, 0, 0,
0, 0, 0 and 0 ms against responses that took 490 to 5812 ms, so it times writing the
request onto the socket. `codex.api_request.duration_ms` times the `/models` HTTP call
and `codex.turn_ttft` times a turn's first token.

**4. A rollout file is per THREAD and a capture is per RUN.** This one was not in the
brief and it is the reason the leftovers are a diagnostic rather than an assumption. E02's
S2 and S4 are two runs against one Codex thread (S4 resumes S2), so the fixture holds the
SAME 38-line rollout in both directories, byte for byte, same session id
`01a05f2d-7eca-73b2-90e0-1419bfbb617c`, same first and last timestamp, five `token_count`
records spanning 22:53:36 to 22:55:54. Each scenario's OTel capture covers only its own
run: four responses for S2, one for S4. So S2 has one rollout row that pairs with nothing
and S4 has three.

The brief said to STOP if a rollout `token_count` on the fixtures pairs with no sse
response other than the 11437/0/0 record. Those four rows meet that description. I did
not stop, and I did not pair by guess: the cause is measured above, and what the code
does is exactly what DO(1) prescribes for the case, one `conflict` row naming what was
compared and never a second request. Counts are reported below and in the DRIFT entry.
The brief's premise held for S1, S3 and S6, which are the three it measured; it needed
extending to cover a resumed thread.

### The request rows

`src/telltale/activities_codex_requests.py` is new and holds the whole answer to "what is
one model request and how long did it take". It came out of `activities_codex.py` because
the 800-line hook closed that file at 819 lines; the split is at the seam this task added.

`model_requests()` reads the sse surface when it is there and the rollout when it is not.

- **sse present.** Unchanged counts (S1 7, S3 3, S6 11) and unchanged usage totals. Each
  rollout `token_count` is paired IN ORDER with the response it equals on
  `input_tokens`/`cached_input_tokens`/`output_tokens` against
  `input_token_count`/`cached_token_count`/`output_token_count`, and its observation id
  becomes provenance on that request's counters. In order because neither surface carries
  a request id, so position is the only join and a scan that never goes backwards cannot
  attach one response to two rollout rows. By equality because pairing on position alone
  would attach a rollout row to whatever response came next.
- **sse absent.** One request per `token_count`, from `last_token_usage`:
  `total_input_tokens` is the wire `input_tokens`, `input_tokens` is that minus
  `cached_input_tokens`, `cache_read_tokens` is `cached_input_tokens`,
  `cache_creation_tokens` is `cache_write_input_tokens`, plus `output_tokens` and
  `reasoning_output_tokens`. `usage_source` is
  `codex.rollout.event_msg.token_count.last_token_usage`. Model and effort come from the
  latest `turn_context` at or before the row on the provider clock, because `token_count`
  carries no turn id.
- `started_at` on a rollout request is the `token_count` timestamp, which is when the
  usage was RECORDED and not when the response completed: E02 measured it equal to the
  FOLLOWING tool output's timestamp (S1, `custom_tool_call_output` and `token_count` both
  at 22:54:30.241Z). The code says so where it sets the field.
- A `token_count` with no `last_token_usage` mapping is no request and one `dropped`
  diagnostic naming the ids. A usable one with no equal sse twin is one `conflict` row
  naming both sides. Never a zero row, never a second request.

### The duration

`duration_ms` on a Codex `model_request` is `codex.sse_event response.completed`
event.timestamp minus the `codex.websocket_request` event.timestamp paired with it by
position, and `duration_source` on the same row is `otel:websocket_request->sse_event`.
The two counts are equal in every capture that carries both (S1 7 and 7, S3 3 and 3, S6 11

## UNSURE OR NOT DONE

**1. `request_duration_ms` in a Codex series says `observed` for a derived number. W7-T3
must fix it, and it is one line.** `series._REQUEST_COLUMNS` rests that column on the
`request_usage` capability, which for a Codex capture with otel_logs is `observed`.
Filling the column therefore labels a derived number with the stronger word, which
AGENTS.md invariant 6 forbids. Measured on the S1 replay:

```
{'column': 'request_duration_ms', 'coverage': 'observed', 'nulls': 0, 'reason': 'measured for this column'}
```

It was masked before this change, because `blank_unobservable` downgrades a column with no

# EXPLAIN FOR THE OWNER

## The problem, in one sentence

Every Codex session you have ever imported produced a forecasting table with no rows in
it, because the recorder was reading the wrong field on the right record.

## What a request clock is, and why the rows were missing

The forecasting side of Telltale wants a table where each row is one model request and the
columns are what was true at that moment: how many fresh input tokens went out, how many
came back cached, how many the model wrote, how many tool calls happened since the last
request. One row per request, in the order they happened. Telltale calls this the request
clock, and it builds it from `model_request` rows in the store.

A `model_request` row has to come from somewhere. Codex writes about itself on five
surfaces, and the recorder was reading exactly one of them for token counts: an
OpenTelemetry log record called `codex.sse_event`, which Codex emits when a model response
completes. That record is good. It carries six token counters and the model name.

But it only exists while Codex is running with telemetry pointed at Telltale. When you run
`telltale import codex-rollouts`, Telltale reads the session files Codex already wrote to
disk, and those files have no telemetry in them. No `codex.sse_event`, no `model_request`
rows, no table.

On your own store: 1,459 imported Codex sessions, 0 request rows, 0 table rows, every
single one.

## The field that was being misread

Codex's own session file, the rollout, does record token counts. It writes a line like
this after each model response:

```json
{"type": "event_msg", "payload": {"type": "token_count", "info": {
  "total_token_usage":  {"input_tokens": 25100, "cached_input_tokens": 23800, "output_tokens": 610, ...},
  "last_token_usage":   {"input_tokens": 12700, "cached_input_tokens": 12800, "output_tokens": 290, ...}
}}}
```

Two counts, on one line. `total_token_usage` is the running total for the whole turn. A
turn is one thing you asked for, and Codex may make many model requests to answer it.
`last_token_usage` is the most recent request on its own.

The recorder's own comment said this record held "TURN totals", which is half right and
was enough to make the whole record look useless for per-request work. So Telltale read
`total_token_usage`, put it on a `turn` row, and left the request clock empty.

## How I know `last_token_usage` is one request

Two measurements. Neither is an argument; both are counts you can rerun.

**One.** Your largest rollout file of September has 1 `task_started`, 2 `turn_context`
records and 69 `token_count` records inside a single turn. Each has a different
`last_token_usage`, and the `total_token_usage` beside it only ever grows: 24,062 then
50,668 then 81,746 then 113,264. A running total that grows 69 times inside one turn is 69
somethings. Those somethings are model requests.

**Two, and this is the one that settles it.** Three of the recorded test sessions have
both surfaces at once: the telemetry AND the rollout, from the same run. So I could line
them up. For every rollout `token_count`, is there a telemetry record that reports exactly
the same numbers?

Yes, every time. Same input tokens, same cached tokens, same output tokens, no rounding,
no near-misses. Session S1: 6 of 6. S3: 2 of 2. S6: 9 of 9. The rollout is not a different
measurement of the session. It is the same measurement, written to a second place.

## The two records that had no partner, and why neither is a problem

Lining things up is only trustworthy if you also explain what does not line up.

**The pre-turn record.** Every session's telemetry has one extra `response.completed` with
input 11,437, cached 0, output 0, before the turn starts. Identical in all three sessions.
It is Codex loading its own instructions. The rollout does not record it. It stays a
request from the telemetry alone.

**The uncounted response.** Session S6 has a `token_count` line whose `info` is `null`,
and a telemetry record at the same instant carrying no counters at all. Both surfaces are
saying "this response was never counted". Telltale writes no row for it and one diagnostic
naming it. It does not write a row of zeros, because zero tokens and an uncounted request
are different statements, and a forecaster that cannot tell them apart will learn from the
difference.

The same thing turned up in your real store. The largest imported session has 5,736
`token_count` observations and produced 5,735 request rows. The missing one:

```json
{"rate_limits": {"primary": {"used_percent": 75.0, "window_minutes": 300}, ...}}
```

A rate-limit notice wearing the `token_count` type, with no usage anywhere in it. One
diagnostic, no row. 5,735 + 1 = 5,736.

## The thing I did not expect: a rollout belongs to a thread, not a run

Two of the seven recorded sessions, S2 and S4, would not line up. S4 had three rollout
records with no telemetry partner.

The cause: S4 is a `codex exec resume` of S2. Codex writes one rollout file per THREAD, and
appends to it. Telltale records one capture per RUN. So both fixtures hold the same
38-line rollout file, byte for byte, same session id, five `token_count` records spanning
22:53:36 to 22:55:54, while each one's telemetry covers only its own run.

The leftovers are not a disagreement about one request. They are two surfaces looking at
different stretches of time. Telltale keeps the telemetry's count, writes one diagnostic
naming what it compared, and adds no request. Adding those three to S4 would have counted
S2's turn twice across two captures of one thread.

I mention this because your brief said to stop if a rollout record paired with nothing. It
did happen, on two fixtures the brief had not measured. I did not stop, because I did not
have to guess: the cause is above, it is measured, and the code's response to it was
already what the brief specified for the case.

## How long a request took, and the answer I rejected

The request clock has a duration column. It was empty for Codex, and I wanted to fill it.

No Codex surface reports one. There is a field that looks like it does:
`codex.websocket_request.duration_ms`. On session S1 it reads 2, 0, 0, 0, 0, 0 and 0
milliseconds, against responses that took between half a second and six seconds. It is
timing how long it took to write the request onto the socket. That is a real number and it
is not the one anybody wants.

So the duration has to be derived, from two timestamps that bracket the request:
`codex.websocket_request` when it goes out, `codex.sse_event response.completed` when it
comes back. S1 has seven of each. Subtracting gives 490, 3487, 5812, 4266, 5587, 4507 and
3269 milliseconds. Those are on your timeline now.

**Then I tried to do the same from the rollout**, so that imported sessions would have
durations too. Before running anything I wrote down what would count as success: at least
90 percent of the paired responses have to agree with the telemetry answer to within 10
percent.

They did not. 14 of 17, which is 82.4 percent.

The 14 that agreed agreed to within nine tenths of one percent, which is close enough to
be the same measurement. The three that failed are all the FIRST response of a turn:

| session | rollout says | telemetry says |
| --- | --- | --- |
| S1 | 6134 ms | 3487 ms |
| S3 | 6086 ms | 3462 ms |
| S6 | 11060 ms | 4121 ms |

The reason is visible in the shape of the data. For any request after the first, the
rollout has a tool output just before it, which is a good marker for when the request
started. For the first request of a turn there is no tool output yet, so the only earlier
marker is `task_started`, and the span picks up everything Codex did to assemble your
prompt as well as the request itself.

I could have excluded the first response of each turn and passed the rule. That would be
fitting the rule to the three cases that failed it, on a sample of seventeen. So the
rollout duration stays absent, the capability table says `unavailable` for it, and the
table above is in the log so the next person can decide against the same evidence.

## The one thing in here that overstates itself

The duration column in a Codex series is labelled `observed`. It should say `derived`,
because it is a subtraction of two timestamps and not a number any surface reported.

The label comes from a table in `series.py` that says which capability each column rests
on, and that file belongs to another task running beside this one (W7-T3), which will
change the line. The number itself is not affected, and every row carrying a duration also
carries `duration_source: otel:websocket_request->sse_event` so the derivation is on the
record.

I am flagging it rather than leaving it in a diff, because the whole point of the coverage
vocabulary is that it never claims more than the layer beneath it measured, and for the
length of this merge window it does.
