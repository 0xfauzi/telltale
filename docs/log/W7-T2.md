# W7-T2: backfill environment fingerprints

## OUTCOME

Every imported session now carries an environment fingerprint built from the file it was
read out of, so `env_changed` is `observed` on a backfill capture and a mid-session model
switch is a changepoint.

On the fixture transcript, one capture, 12 request rows:

```
env_changed                   flag    past_covariate  observed     0
changepoints none
```

On a real 6560-line session re-imported into a copy of the E13 store, 1278 request rows,
before and after:

```
before:  env_changed  flag  past_covariate  unavailable  1278
after:   env_changed  flag  past_covariate  observed     0
```

On the hand-written transcript whose assistant lines change model half way, 20 request
rows:

```
env_changed                   flag    past_covariate  observed     0
changepoints 10
```

Two things were found by measuring rather than by reading, and both changed the design.
The first is that `env.fingerprint` hashes the instruction files on disk at call time,
which for a backfill would hash today's CLAUDE.md against a session that ran weeks ago;
the new constructor never touches the filesystem. That trap was named in the brief. The
second was not: Claude Code writes `<synthetic>` in `message.model` on assistant lines it
generated itself, and reading that as a model made a session that never switched report
two changepoints. Both are below.

## WHAT WAS WRONG

`series.env_column` measures the coverage of `env_changed` from the observation rows: no
row of the capture carries an environment fingerprint id and the column is `unavailable`,
every row carries one and it is `observed`, some do and it is `partial`. A changepoint is
recorded only between two known and different ids.

The launcher (`launch.py` `_environment`) calls `env.fingerprint`, emits
`telltale.environment` and binds the id, so every observation of a launched capture
carries it. The importer built one `ParseCtx` per file with `environment_fingerprint_id`
left at its default of `None` and handed that same ctx to every line, so every observation
of every imported capture had a null in that column.

Measured on a copy of `experiments/E13/out/home/telltale.db` on 2026-09-05: 1841 imported
Claude captures and 1459 imported Codex captures, all `unavailable`. Readiness check 1
refuses all 930 Claude imports with 32 or more requests on this column together with
`request_duration_ms`.

## WHAT CHANGED

### 1. `src/telltale/env.py`: a constructor that reads no disk

`backfill_fingerprint(provider, runtime_version, model, effort, surface, content_level)`
returns the same eleven payload keys `fingerprint` returns, plus the id, computed the same
way: `"env_"` plus the sha256 of the canonical JSON of the payload without the id.

Three fields are observed, because the provider wrote them into the session file:
`runtime_version`, `model` and `effort`. `capture_modes` is `[surface]` and
`content_level` is the level the import sanitized at; both are facts about the import.
The other five cannot be observed from a file and are not invented: `tool_set_hash`,
`mcp_names_hash`, `settings_hash` and `sandbox_posture` are `None`, and
`instruction_hashes` is `{}`.

`{}` and not `None` because `fingerprint` produces a mapping there and the two must hash
compatibly. The allowlist types `instruction_hashes` as `Kind.PATH` with path keys;
checked before writing anything, an empty mapping passes `_clean_dict` untouched and needs
no new Kind, so the STOP condition in the brief did not fire:

```
$ uv run python -c "sanitize('telltale.environment', {... 'instruction_hashes': {} ...}, 1, Ctx())"
{'provider': 'claude', ..., 'instruction_hashes': {}, ...}
{'dropped': [], 'truncated': [], 'redacted': []}
[]
```

A launcher capture cannot collide with an import: its `capture_modes` holds the surfaces
it configured (`["hook", "otel_logs", "otel_metrics", "stream"]`) and an import's holds one
backfill surface name (`["transcript"]` or `["rollout"]`), so the two hash differently even
when provider, version, model and effort are equal.

### 2. `src/telltale/importer.py`: a regime pre-pass

`regimes(source, settings, level)` reads the file a second time, with the same reader and
the same `_loads` `_replay` uses, and returns one entry per CHANGE of environment: the line
it starts at, the provider timestamp of that line, the id, and the payload.

- Claude: an assistant line's top-level `version`, `message.model` and top-level `effort`.
  A line that is not an assistant line names no regime and belongs to the one already
  running.
- Codex: `session_meta.cli_version` for the version and each `turn_context` for the model
  and the effort. The version is collected over the whole file and then applied to every
  turn, rather than as it is met: a `turn_context` that arrived before its `session_meta`
  would otherwise become a changepoint on a field that does not change inside a file. Only
  one small tuple per TURN is held, so the file is still streamed.
- The first regime governs from line 1. The lines before the first assistant message or the
  first `turn_context` ran in the same environment as the first one that named it, and
  leaving them unstamped would report `partial` on an otherwise complete capture.
- A file that names no version, model or effort anywhere yields no regime, emits no
  environment observation and stays `unavailable`. A fingerprint of three `None`s would be
  one id shared by every such file in the store, and a changepoint between two of them
  would be a claim about an environment nobody observed.

`_replay` walks the boundaries beside the lines. At a boundary it flushes the pending batch,
emits one `telltale.environment` observation through the existing `_emit` the first time an
id appears, and from then on parses each line with
`dataclasses.replace(ctx, environment_fingerprint_id=<id>)`, which both parsers already
stamp on every Observation (`claude._observe`, `codex.py` line 346). Flushing first is what
puts the environment row ahead, in the store and in ULID order, of every line it governs.

A session that returns to an environment it has already been in gets no second environment
row: the id is the environment, and the row would repeat a payload already stored. The
observations from there on carry the id again, and the changepoint is read off those.

`_emit` gained an optional `stamp`. An environment row stamped with the file's LAST
timestamp, which is what `_emit` used for anything that is not `capture_started`, would sort
after every line it governs.

`capture_started` and `capture_ended` carry the first and the last environment the file
recorded, which is what the launcher does with its one fingerprint. That is what makes the
null count zero rather than two.

`fingerprints`, the count of distinct ids, goes on the `capture_started` payload. Zero is a
count and not a gap: the importer always knows how many it built.

Idempotence is untouched: a capture already in the store is skipped whole before any of this
runs, and `--dry-run` still writes nothing (`test_the_dry_run_counts_the_files_and_writes_nothing`
compares the listing of `$TELLTALE_HOME` before and after).

### 3. `src/telltale/allowlist_telltale.py`: one field

### 4. `<synthetic>` is not a model

This was not in the brief. The first run of the E13 verification produced this:

```

```

Two changepoints in a session that ran on one model. The second environment row said:

```
{"model":"<synthetic>", "runtime_version":"2.1.185", ...}
```

Measured on the source transcript (2437 assistant lines): 2434 name `claude-opus-4-8` and
3 name `<synthetic>`, and all three have `isApiErrorMessage: true`, `stop_reason:
stop_sequence` and every token count zero. Measured across the whole E13 store, over the
1841 imported Claude captures: 105 assistant rows in 64 captures carry `<synthetic>`, and
all 105 have `input_tokens` 0 and `output_tokens` 0.

It is a sentinel meaning "no model produced this message", and Claude Code writes it when
it puts one of its own error messages into the transcript as if it were an assistant turn.

An assistant line naming it is now skipped in the regime pre-pass, for the same reason a
user line is: it says nothing about which model the session was using. It is NOT read as
"model not observed" either. That would be a fourth value in the model field and would
produce exactly the same two changepoints under a different name.

After the fix, the same capture:

```

changepoints none
```

## EXPLAIN FOR THE OWNER

### The question underneath this task

Suppose a session got slower half way through. Two explanations: the work got harder, or
something about the setup changed. A model swap, a version upgrade, a different CLAUDE.md
sitting in the repository. None of those show up in a diff, and none of them are in the
numbers a session produces. So a forecaster looking at a session's requests has no way to
tell "this is a harder problem" from "this is a different machine".

The fix is to record, for each request, a short string that stands for the whole setup: the
provider, the version, the model, the effort setting, hashes of the instruction files, and
so on. Same setup, same string. Anything changes, different string. That string is called an
**environment fingerprint**, and the column that says "this request's string differs from
the previous one's" is called `env_changed`.

### What was already true, and what was not

When Telltale LAUNCHES an agent, it knows all of this, because it is the thing doing the
launching. It computes the fingerprint before the child starts and stamps the id on every
observation that comes back.

When Telltale IMPORTS a session, there was no launch. The session already happened; what
exists is a file the provider wrote. The importer read that file and never filled the
fingerprint column in, so every imported capture had a null there.

The consequence, measured on a copy of the owner's E13 store: 1841 imported Claude sessions
and 1459 imported Codex sessions with `env_changed` `unavailable`, and a readiness check
that refuses 930 of the Claude ones partly on that column.

### The first question I had to answer

Could I just call the existing fingerprint function?

No, and the reason is worth holding on to. That function hashes the instruction files, and
it does it by reading them off the disk at the moment it is called. For a launch that is
right: the CLAUDE.md on disk right now is the one the agent is about to read. For a backfill
it is wrong in a way that would never announce itself. The session ran three weeks ago. The
function would read today's CLAUDE.md, hash it, and attach that hash to a session that read
a different file. Nobody would see the error. Every import run on a Tuesday would agree with
every other import run on that Tuesday, and disagree with the same import run on Wednesday.

So the new function, `backfill_fingerprint`, touches no files at all. It takes only what the
session file itself states.

### What a session file states, and what it does not

A Claude transcript is one JSON object per line. Measured on the owner's largest telltale
transcript, 2262 assistant lines: the version is on all 2262, the model is on all 2262, and
the effort setting is on 2245.

A Codex rollout puts its CLI version once, on the record it opens with, and puts the model
and the effort on a `turn_context` record at the start of each turn.

Nothing in either file says which tools were available, which MCP servers were configured,
what the settings were, or what the sandbox posture was. Those four are recorded as
`None`, which in this system means "not observed" and never "there were none". The
instruction hashes are recorded as an empty mapping, which says the same thing.

### The second question: what if the setup changed mid-session

A session can switch models. The owner does it by typing `/model`. So one file is not
necessarily one environment.

The answer is a pre-pass: before anything is written, read the file once and work out which
stretch of lines ran under which setup. Call each stretch a **regime**. Where the setup
changes, a new regime starts. The importer then writes one `telltale.environment`
observation at the start of each regime, before the lines it covers, and stamps every line
of the regime with that regime's id.

The lines before the first assistant message get the first regime too. They ran in the same
setup as the first line that named it, and leaving them blank would make the whole capture
report "partial coverage" over a hole that is not really a hole.

Concretely, on the hand-written test transcript: ten requests on `claude-opus-5`, ten on
`claude-sonnet-5`. The series comes out with 20 rows, `env_changed` observed on all 20, and
exactly one changepoint, at row index 10. Row 10 is the eleventh request, which is the first
one on the second model. That is the whole point of the column: not "something changed
somewhere", but "it changed HERE".

### The third question, which I did not know to ask

I ran the new code against a real session out of the owner's store, 6560 lines, 1278
requests, and it reported two changepoints. The session had never switched model.

The second environment row said the model was `<synthetic>`.

`<synthetic>` is what Claude Code writes in the model field when IT wrote the message rather
than a model. An API error, for instance: the CLI puts its own error text into the
transcript in the shape of an assistant turn so the conversation reads continuously, and
marks the model field with that placeholder.

Reading it as a model name produced exactly the wrong claim: the environment changed at
request 1016 and changed back at 1017.

I measured how common this is before deciding anything. On that transcript: 3 of 2437
assistant lines, all three flagged `isApiErrorMessage: true`, all three with every token
count zero. Across the entire imported half of the E13 store, 1841 Claude captures: 105
such lines in 64 captures, and all 105 have zero tokens in and zero tokens out. So it is
rare, it is real, and it affects one imported capture in twenty-nine.

There were two ways to handle it and only one is honest.

The one I rejected: read `<synthetic>` as "model not observed" and record `None`. That
sounds careful, and it is wrong. `None` is a different value from `claude-opus-4-8`, so the
fingerprint would still change, so the changepoint would still appear. It would be the same
false claim with a politer field value.

The one I took: an assistant line naming `<synthetic>` names no regime at all, exactly like
a user line. It is a message no model produced, so it says nothing about which model the
session was using, so the regime already running continues through it.

After that, the same real capture: 1278 rows, `env_changed` observed, no changepoints. Which
is the truth. That session ran on `claude-opus-4-8` under version 2.1.185 from beginning to
end.

### How I know the tests would have caught it

A test that passes against the un-fixed code is not a test, so I broke each rule and watched.

Removing the one line that binds the fingerprint id to the parse context makes three tests
fail, the clearest of them reporting `assert 15 == 0`: fifteen rows of the rollout capture
with no fingerprint, where zero is required.

Removing the `<synthetic>` rule makes the switch test fail with `At index 1 diff:

### Why the file got split

One thing here is bookkeeping rather than reasoning, and it is worth a paragraph so it is
not mistaken for design. The repository has a rule, enforced by a commit hook, that no file
may cross 800 lines. The additions took `importer.py` past it.

The cut is not arbitrary. That file already said, in its own opening paragraph, that it has
two halves: one counts what is on disk and writes nothing, the other writes. So the
counting half moved to `importer_scan.py` and the writing half stayed. The names other code
calls are re-exported from the old file, so nothing outside the two files noticed.
