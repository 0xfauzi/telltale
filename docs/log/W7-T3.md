## WHAT WAS WRONG

**One capability was answering two questions.** `request_duration_ms` rested on
`request_usage`. A surface that states the four token counters does not thereby state
how long a request took, so the column's coverage word was a claim about a different
measurement. On a Claude transcript that read `observed` (usage is observed there) for a
column with no value in any row, and `series.blank_unobservable` had to correct it back
down to `unavailable` after the fact. The correction worked, which is why nothing broke;
what was wrong is that the table said something false and a second mechanism repaired it.

**Check 1 refused captures the backtester was willing to run.** `readiness._coverage`
counted every column and refused when any one was not `observed` or `derived`. Two
columns of an imported Claude transcript can never be either: `request_duration_ms` (no
line stated one) and `env_changed` (an import emits no environment fingerprint). I
verified the count in E13's own census rather than taking it on trust:

```
rows 5934 coverage-first-failure rows 5580
distinct captures with a coverage first failure 930
Counter({'coverage: measured 9, needed 11': 5580})
Counter({'import': 5580})
```

930 imported captures, 5580 (capture, target, horizon) triples, every one stopped at the
first line of the checklist for a property of the surface rather than of the data.
Meanwhile `backtest._variant` was already dropping such a column by name, recording the
reason as a warning, and running the rest. Two parts of one system disagreed about the
same fact, and the stricter one was wrong.

**A run did not record which columns it left out.** `backtest.run` returned `covariates`
and threw the exclusions away after building a warning string from them, so a stored run
with nine covariates and a stored run with ten could not be told apart by what they
excluded. Pooling those two rows pools two different experiments.

## UNSURE OR NOT DONE

- **The derivation is measured on headless sessions and applied to interactive ones.**
  Every session in E14's cohort is a launcher capture of this build, because a launcher
  capture is the only kind with an OTel record to check against. The 930 imported
  transcripts the derivation is for are the owner's interactive sessions, where no OTel
  record exists and therefore no check is possible. What is shared between the two is the
  parser, the clock and the line structure; what is not measured is whether an
  interactive session puts a different kind of pause between the line before a request
  and the request itself. The median derived duration on the imported session I verified
  against is 12036.5 ms against 4683.5 ms on the launcher cohort, and I do not know how
  much of that difference is the session (a different model, longer prompts, an
  eight-hour day) and how much is the definition behaving differently off its cohort.
  What would measure it: a launcher capture of an INTERACTIVE session, which the
  launcher can record because it configures OTel for the child either way.
- **The `dropped` diagnostic counts, it does not name.** One row per capture saying how
  many transcript requests could derive no duration. Naming each request would be one row
  per request on a capture that has hundreds. I judged the count to be the useful fact
  and the per-request evidence to be the absent `duration_ms` field itself, which
  `telltale explain` already shows. Someone could reasonably differ.
- **Two files are at exactly 800 lines.** The ratchet fails a file that crosses the line,
  so both pass, and both are now un-addable-to. This is a hazard I created for the next
  task rather than a defect in this one.
- **`excluded` is null on stored rows written before this change.** A run rehydrated by
  `placebo.restored` (in `forecast/placebo.py`, which this task does not own) carries no
  `excluded` key, so `persist` writes null and `report` prints "not recorded". The
  correct fix is one line in `restored` copying `row["scenario"].get("excluded")`
  through, and it belongs to whoever owns that file next.
- **E13 is not edited**, as the brief requires. Its `pool` will have to key on
  `covariates` for the pooling rule in the design amendment to bind; nothing in this
  change enforces it yet, and a hook could.
- **Codex's `request_duration` row is not added here.** W7-T1 owns it. Until it lands, a
  Codex capture has no `request_duration` key in its coverage map at all, so
  `series.worst` returns `unavailable` for the column, which is the same word it carried
  before this change and the same behaviour. The six Codex goldens confirm it: their
  coverage blocks are unchanged.

## EXPLAIN FOR THE OWNER

**Why this matters.** You have 930 of your own Claude sessions on disk, imported from the
files Claude Code writes as it goes. Not one of them could be forecast, and the reason
was not the data. It was one missing column and one rule that refused rather than
excluded. Both are fixed, and the fix rests on a measurement rather than on an argument.

**The first question: how long did one request take?**

A "request" here is one round trip to the model: your session sends a prompt, the model
answers, that is one request. How long it took is one of the eleven numbers the
forecasting laboratory reads per request.

There are two places that number could come from. When Telltale launches an agent itself,
it turns on the agent's own telemetry, and the agent reports each request with a
`duration_ms` field. That is the provider stating a fact, and it is the strongest kind of
evidence this system records.

The other place is the transcript. Claude Code writes a file as it goes, one JSON line per
event, and every line carries a timestamp. It never writes a duration. But it writes the
line before the request and the lines of the answer, so a duration can be computed by
subtraction: from the last line before the request to the last line of the answer.

**Why I measured before writing any of it.** Subtracting two timestamps is easy to write
and easy to be wrong about. So I found the sessions where BOTH sources exist: 128 sessions
this build recorded through its launcher, which therefore have telemetry, and which also
wrote transcripts into `~/.claude/projects` like every other session. 6533 requests with a
provider-stated duration, 6518 of them found in the transcript by the same request id.
Then I compared the subtraction against the provider's number, request by request.

**The answer I rejected, and what killed it.** My first definition ended the request at
the assistant line that carries the token counts, which is the obvious choice because that
is the line the rest of the system already reads. It agreed with the provider on 54.7
percent of requests, and was short by 425 milliseconds at the median. The reason is in the
data: a request writes more than one line 3675 times out of 6518, because the model
answers in blocks (a bit of text, then a tool call, then more text) and each block is its
own line. The first line lands when the FIRST block finishes, not when the request does.
Ending at the last line instead gives 99.7 percent agreement and a median gap of 21
milliseconds against a median request of 4.7 seconds. That is the definition in the code.

I wrote the rule down before running: adopt it if 90 percent or more agree within 10
percent. It reached 99.7 percent. If it had reached 80, the column would still be empty
today and this report would say so.

**How the system records that the number is weaker.** Every column carries one of four
words. `observed` means a surface stated this. `derived` means we computed it from what a
surface stated. The transcript number is `derived`, the telemetry number is `observed`,
and each row also carries which of the two it came from, so nothing downstream can present
one as the other. That is not caution for its own sake: 21 milliseconds of difference is
small, but it is not nothing, and a reader who is told "the provider said 4683" when the
truth is "we worked out 4677" has been misled about where the number came from.

**The second question: what should a checklist do about a column that cannot exist?**

Before any forecast runs, eight checks ask whether the data supports one. The first check
asked: is every column either observed or derived? An imported transcript has two columns
that can never be either. The request duration was one, and that is now fixed. The other
is `env_changed`, a flag for "did the machine's environment change between these two
requests", which needs a fingerprint that Telltale takes at capture time. An import
happened in the past; there is no fingerprint to take. That column is empty by
construction and always will be.

The old rule refused the whole capture for it. I checked what that cost before changing
anything: 930 captures, 5580 combinations of capture, target and horizon, every single one
stopped at the first line. And the part that decided it was wrong: the component that
actually runs the forecast was already handling this properly. It drops such a column,
names it, records why, and runs on the rest. Two parts of the system disagreed, and the
one that refused was the one that was wrong.

The new rule distinguishes two kinds of missing, and this is the whole of the change.
"Nobody could ever see this" is a fact about the surface: exclude the column, name it, and
carry on. "Some rows have it and some do not" is a hole in something that WAS visible, and
that still refuses, because a forecast built on it would quietly drop windows for a reason
no reader of the checklist would have been told about.

**One consequence worth knowing.** A forecast run is defined by which columns it used. Two
runs with different column sets are two different experiments, and averaging them together
would be a mistake that produces a plausible-looking number. So every run now stores the
columns it excluded and why, prints them, and the design file states the rule: two runs
may be pooled only when their column lists are identical.

**What I am not sure about.** The 99.7 percent was measured on sessions this build ran
headlessly. The 930 sessions the derivation is for are sessions you ran by hand, and they
have no telemetry, which is exactly why they needed the derivation and exactly why I
cannot check it on them. The parser, the clock and the line structure are the same. Human
pauses are not. On the one interactive session I imported to verify the command works, the
median derived request is 12.0 seconds against 4.7 on the headless cohort, and I do not
know how much of that is a different kind of session and how much is the definition
behaving differently where nothing can check it. Measuring it properly means capturing one
interactive session through `telltale run`, which records both surfaces at once. That is a
small job and nobody has done it.

**Nothing here changes what you have on disk.** Reading a capture again recomputes these
rows from the observations that were already stored; no observation is rewritten, and
`~/.claude`, `~/.codex` and `~/.telltale` were never written to by any part of this work.
