# W8-E16 git-backfilled change clock: H5 and H8 on four repositories

## OUTCOME

E16 ran. Twelve (repository, target) rows, never pooled, on the change clock of four of
the owner's repositories backfilled from git with GitHub check runs. This is the first
time design 6.12's candidate protocol has had rows to be wrong on: E11 reached 0 windows
on every target, and this run scored 888 windows in its twelve unconditioned runs and
paired 841 conditioned-against-unconditioned windows over the whole origin ranges (1,682
counting each half separately).

| | E11 (2026-09-05, one repository) | E16 (2026-09-06, four) |
| --- | --- | --- |
| rows on the change clock | 40 | 657 (179, 108, 118, 252) |
| (repository, target) rows that reached a label | 0 | 12 |
| rows that reached the conditioned reading | 0 | 11 |
| labels | none | 12 x baseline sufficient |
| chronology placebo valid | 0 of 3 (control only) | 6 of 12 |
| readings | none | 10 "no measurable conditioning at this n", 1 "the candidate's features move the forecast", 1 not assessable at 18 paired windows |

All twelve passed all eight readiness lines, no window was dropped anywhere, and each
run's window count equals its checklist's planned count. No (repository, target) refused
for any reason, so neither STOP condition fired.

The pre-registered answer to the experiment's own question is therefore: on this clock
and this population, the four one-line baselines are sufficient for all three post-merge
targets, and the candidate's known features do not measurably move the forecast at this
n on ten of the eleven rows that could answer.

Gates: `uv run ruff check .` and `uv run ruff format --check .` clean, `uv run mypy .`
clean on 135 source files, `pre-commit run --all-files` all hooks passed. Output under
VERIFY.

## WHAT WAS WRONG

Nothing in `src/` was touched and nothing in `src/` needed to be. Four things about the
runner and the write-up were wrong on the way, and each is a decision worth recording.

**1. A dry run cannot ask the rule about a forecaster that did not run.** The first
stub-only run crashed with `KeyError: 'timesfm'` inside `decide._paired`, because MODEL
was a module constant naming TimesFM while `--forecasters` had left it out. Fixing it by
catching the KeyError would have produced a dry run that silently answers about a
different forecaster. `rows.choose_model` moves MODEL to the stub when the model is
absent, refuses when neither is present, and every JSON file records which one it was
under `constants.model`, so a dry run says on its own face that it is plumbing.

**2. The pre-registration leaves two clauses unresolved, and resolving them after the
numbers would have been choosing a result.** It says the reading holds when the paired
median difference is below zero "in both halves of the origin range and the conditioned
run's calibration is not flagged where the unconditioned one is not", and separately that
a (repository, target) with fewer than k_min windows is not assessable. It does not say
which pair the calibration clause reads, and it does not say which of the two runs the
k_min clause counts, although the two counts differ by construction. Both readings were
fixed in the runner's `RULE` docstring before the run, are printed above the first table
of `out/run.log`, and are stated in "What we did": calibration on the pair over the whole
origin range, k_min per question over the run that answers it, and the placebo-validity
clause on the label alone because the H8 rule reads no control.

**3. Six numbers in the first draft of the write-up were wrong, and were caught by
recomputing them from `summary.json` rather than by rereading the prose.** The placebo
was valid on 6 of 12 and the draft said 5; the H5 branches split 6 and 6 and the draft
said 5 and 7; the scored-window total is 888 and the draft said 1,036; this run wrote 45
pairs to the copied store and the draft said 51, which was the total including 6 rows the
source store already held; a claim that six of the eight flag rows had a best baseline
within 0.03 of min(p, 1 - p) is true of three of them, and the write-up now lists all
eight distances; and a claim about why some paired medians are exactly zero was an
unmeasured mechanism, replaced by the measured spread underneath one of them.

**4. `run.py` grew to 931 lines and the file-length hook rejected it.** The hook fails a
file a commit ADDS already over 800 lines, which is right: a runner with the store copy,
four lineages, the per-row protocol, the control, the printed report and a command line
in it has more than one job. It is now `run.py` (356 lines: the copy, the lineages, the
control, the report, the CLI) and `rows.py` (628: the constants and everything that turns
one lineage and one target into one answer). The split is behaviour-preserving and was
checked by re-running a row and comparing digits, then by re-running the whole experiment.

## EXPLAIN FOR THE OWNER

### The question, before any of the machinery

Somebody is about to merge a change. They can see what the change IS: how many files it
touches, how many lines it adds and removes, how many top-level directories it reaches
into, whether it touched a test, whether it moved a lockfile. Six numbers, all readable
off the diff before anything happens.

They cannot see what happens after. How long the verification run takes, whether it
fails, whether somebody has to come back and rewrite those lines within the next three
changes.

The question is whether the first six numbers help you guess the last three. That is
hypothesis 8 of the specification, and until this task it had never been asked of real
data, because the recorder had only ever seen 40 changes and every one of them was
Telltale building itself.

### Why there are rows now

A change-clock row used to require a captured session: the recorder had to have been
running when the change was made. Wave 8 broke that requirement. `telltale import
git-history` walks the first-parent history of a branch and makes one row per commit from
git alone, with the verification outcome fetched from GitHub's check runs. The process
columns of such a row (tokens spent, compactions, verification cycles) are `unavailable`,
which is a recorded word and not a zero, and they are excluded from the forecast by name.

That turned 40 rows into 657 across four repositories: telltale 179, systemap 108,
deckgen 118, kstrl 252.

### The hole that had to be dealt with first

Every post-merge column has gaps by construction. Push three commits at once and GitHub
makes one check run, on the head; the other two commits have no verification outcome at
all. On systemap, 66 of 108 commits have none.

The old rule dropped a WINDOW that contained a gap. A window is a context of at least 16
rows plus the row being forecast, and on a lineage shorter than 512 rows every context
starts at row 0, so one gap low in the column poisons nearly every window. W8-T3 changed
the rule to drop the ROW instead: a target is forecast over the rows where it is known,
in lineage order, and the run records how many rows went and which. The context then
means "the previous change with a known outcome", which the run states in its assumptions.

W8-F1 did the same for the six candidate features. `git diff --numstat` prints a dash
rather than a count for a binary file, so `lines_added` is unknown on a commit that
touched a PNG. deckgen has 27 of those. Before W8-F1 one such commit refused the whole
run; now it costs its own row and the count rides in the output as
`excluded_for_block`.

### One real row, walked through: systemap and verification duration

systemap's change clock is 108 rows. `merge_verification_ms` is known on 42 of them, so
the frame the forecast runs over is 42 rows and the run records the other 66 as excluded,
with the reason "target merge_verification_ms unknown".

**Is it worth trying at all?** The readiness checklist is eight questions, asked over
those 42 rows and not over the 108. Enough windows: 42 rows with a 16-row minimum context
at H = 1 gives 26 origins, against a floor of 20. No gaps inside any window: 0 of the 206
cells the plan reads. A long enough context for the slowest baseline: 16 rows, needs 9.
One long enough regime: 42 rows, needs 17. The target actually moves: its scaled median
absolute deviation is 155,673 ms, needs above 0. All eight pass.

**How well does anything forecast it?** Roll an origin through the 26 positions. At each
one, hand every forecaster the rows before it and nothing else, take its answer for the
next row, and compare against the row you held back. Average the absolute errors.
TimesFM-3 scores 147,525.73 ms. The best of the four one-line rules is "say whatever
happened last time", at 141,269.23 ms. The model is worse.

**Does that settle it?** The pre-registered rule asks two questions, both fixed before any
result existed. Did the model beat the best baseline by more than a tenth?
`147,525.73 > 0.9 x 141,269.23 = 127,142.31` is true, so no. Did it beat it on more than
three origins in five? It won 9 of 26, a share of 0.3462 against 0.60, so no. Either
answer alone earns the label **baseline sufficient**, and both fired.

**Did the model use the ORDER of the past?** Run it again nine more times with the context
scrambled: five runs that shuffle blocks of two whole rows, five that shuffle single rows.
Whole rows move together, so every row still holds the values it held; what is destroyed
is recency. Persistence reads exactly one row, the last one in the context, so if the
shuffle arrived at all persistence must get worse. It did, on 10 of 10 runs, so the
control is valid here. TimesFM's error on the shuffled contexts is 244,562 ms against
147,526 in true order, and it beat its own shuffled twin on 0.8846 of origins. None of
that changes the label: the rule tries the baseline clause first and never reaches the
placebo clauses once it fires.

**Now the actual question.** Run the whole thing twice more. The first run is what you
just read. The second is identical except that at each origin the model is also handed
the candidate row's own six features, reaching one row past the context because those
features are known at the moment the merge decision is taken. Pair the two runs by origin
and take the median of the differences.

Both runs are cut from one frame, and that frame also drops the 3 systemap commits whose
line counts are unreadable, so the conditioned frame is 39 rows and both runs have
identical origins. Over the whole range: 23 paired origins, median difference
-3,568.02 ms. Conditioned is better. Over the first half: 12 origins, -8,093.09 ms. Over
the second: 11 origins, -1,531.31 ms. Negative in both halves.

The calibration check asks whether the model's uncertainty bands cover reality at the
rates they claim. The unconditioned run's bands are flagged as off; the conditioned run's
are not. So the clause "the conditioned run's calibration is not flagged where the
unconditioned one is not" holds.

Both halves negative, calibration not worse: this row reads **the candidate's features
move the forecast**. It is the only one of eleven that does.

**The sentence that has to travel with that number.** The difference is between two
forecasts of one observed history. There is no world in which that change was not
merged, so there is nothing to subtract. The number says how much knowing the diff
changes the forecast, and design 6.12 requires that sentence on every output.

### The reading that was rejected, and the number that forbids it

The tempting reading is: "conditioning on the candidate's features improves the
one-step forecast of verification duration". Four other rows also have a negative median
difference over their whole origin range, and stopping there would give five rows instead
of one.

The number that forbids it is the second half. telltale's verification duration is
-193.05 ms over the whole range and -335.18 in the first half, and then +136.61 in the
second: the sign does not survive being asked of each half separately. Same for deckgen's
verification flag (-0.0045 whole, -0.2272 first, +0.0025 second) and kstrl's rework label
(-0.0667, -0.0915, +0.0024). A result that lives in one half of a history is a result
about that half, and the both-halves clause of spec 15.7 is what stops a run from
reporting it as a result about the whole.

And the one row that did survive rests on 23 paired windows, three above the floor of 20,
drawn from 39 rows after 66 exclusions. One row out of eleven at the smallest n in the
table is a thing to carry forward, not a thing to build on. The write-up says so in
"What we rejected" rather than in a footnote.

### What the twelve rows say, in one paragraph

Twelve labels, twelve times baseline sufficient. The best share of origins TimesFM won
anywhere is 0.5308, against a bar of 0.60 fixed in advance. The chronology control was
valid on 6 rows and on none of them did the run get far enough to read it, because the
baseline clause fires first every time. Ten of eleven conditioned readings say no
measurable conditioning at this n. The honest summary is that on the git-backfilled
change clock, what a change IS and what the recent history of these outcomes was do not
forecast them one step ahead better than "say whatever happened last time". The next
thing to try is what the recorder was built for and this population does not have: the
process columns, which say what the work COST, and which only a captured session
supplies.
