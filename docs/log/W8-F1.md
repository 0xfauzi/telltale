## WHAT WAS WRONG

**Check 7 measured the wrong thing on a 0/1 column.** Readiness check 7 asks whether the
target moves at all, and its number was the scaled median absolute deviation over the
rows a run would score, needed above 0. A constant target makes every baseline perfect
and leaves skill with no denominator, and `fresh_input_tokens` on capture S1, which is 2
on all seven rows, is the case it was written for. On a flag the number is 0 whatever
the base rate, for a reason that is arithmetic and not data: the median of a column
whose base rate is below a half is 0, so every absolute deviation from it is the value
itself, and the median of a list that is mostly 0 is 0. `rework_within_3_lag3` carries
37 ones over the 173 rows its frame retains here and read `variation FAIL, measured 0`.
Nothing blocked a backtest, because the backtester never calls the checklist, so E16
would have run and printed `NOT ready: variation` beside every flag target it touched.

**A hole in the candidate block refused the run instead of costing rows.** W8-T3 made
step (2) row-level for the target: a target is forecast over the rows where it is known.
The conditioning block was left at the window, where `candidate._known` refuses on an
unknown, and that refusal is right about one candidate and wrong about a run.
`git diff --numstat` prints `-` for a file whose lines it will not count, so a commit
that touched a binary file leaves `lines_added` and `lines_removed` unknown, and a count
that is partly unknown is unknown. Two of those sit at rows 0 and 5 of this repository's
lineage. Every context of a lineage shorter than MAX_CONTEXT starts at row 0, so the
whole run refused at its very first origin. E16 conditions on block A on four
repositories; one binary commit in any of them refused the run there.

**`telltale advise` could not see a holed target's run, and asked its checklist at the
wrong horizon.** A target with holes is forecast over a FRAME, whose series id is the
parent's with the suffix `:<target>`, and that is the id the run is stored under.
`_latest` looked runs up by the parent id alone. Measured here: after `forecast
backtest --target rework_within_3_lag3` and `forecast candidate` on the same pair, the
store holds three true-order runs under `ser_8362bf51029c70ecc438417d:rework_within_3_lag3`
and zero under `ser_8362bf51029c70ecc438417d`, and the advisory said there was nothing.
Separately, `cli_advise.HORIZON = 1` was a module constant and `rework_within_3_lag3` is
registered for H = 4 alone, so `backtest.registered` refused with `horizon 1 is not one
of [4]` and the page reported `refused` about the advisory's own constant.

## WHAT CHANGED

Full reasoning is in `docs/design/amendments/W8-F1.md`. Four files of source, three of
tests.

**`forecast/readiness.py`, `_variation` only.** For a target whose ColumnSpec unit is
`flag`, check 7 measures the minority share min(p, 1 - p) with p the share of 1s over
the known rows, needed above 0, and names both counts in its detail. Every other unit
keeps the scaled MAD, unchanged down to the rounding. A flag with one value present
still fails, because its minority share is exactly 0, which is the constant target the
check exists for. The unit is read off the Series column and not off `forecast.TARGETS`:
they agree on every flag today and not in general (`verification_cycles` is `cycles` in
the registry and `runs` on the series), and the column this check reads is the one in
the frame. One line outside `_variation` moved with it, the call in `check()`, because
the function needs the frame to read that word.

**`forecast/frame.py`.** `retained(series, target, columns=())` keeps a row only when
the target and every named column is known. The cohort's `excluded_reason` names each
column that cost rows and how many each cost, and reads exactly as W8-T3 wrote it when
no named column cost one. A new cohort key `excluded_by_column` holds the row keys per
column, and `for_columns(frame)` reduces it to `{count, row_keys, by_column}`. A row
missing two named columns is one row in `excluded_rows` and appears under each column,
because "how many rows went" and "which column cost a row" are two questions.
`excluded(frame)["reason"]` is now the frame's own reason rather than the constant
`target unknown`; the identity case still gets the constant, which is what
`test_forecast_ablation.py` asserts.

**`forecast/candidate.py`.** `conditioned` cuts one frame with
`retained(series, target, block)`, where `block` is the A block minus the target, and
BOTH runs of the pair are made from it, so the protocol's pairing rule holds by
construction rather than by two exclusions agreeing. The block is never narrowed. Each
run's `candidate` dict and the report's header carry `excluded_for_block`. `_known`'s
refusal is unreachable on a frame `conditioned` cut and stays as the guard behind it,
which its docstring now says. One new private helper, `_block`, is the single place a
column the series does not carry is refused; `_attach` and `advise_row` each had their
own copy of that check and now use it.

**`cli_advise.py`.** `_latest` tries the parent series id first and the suffixed frame
id after it, and returns which one answered; the id rides in the target's `run` block as
`series_id`. `HORIZON` is gone and the checklist is asked at `candidate.horizon(target)`.

**One file outside OWNS was edited, because a hook refuses the commit without it.**
`docs/README.md` indexes every document and states the log count; the
`docs-links-resolve` hook failed with `docs/design/amendments/W8-F1.md is not indexed`
and `log count (64) is not stated`. Two lines: the new amendment's row and 63 to 64.
This is the same edit W8-T3's commit made for the same reason. Nothing else outside OWNS
was touched.

**Tests.** Six new, each broken once against the un-fixed code and watched failing:

- `test_forecast_frame.py::test_a_flag_target_that_takes_both_values_passes_check_seven`
  and `::test_a_flag_with_one_value_present_still_fails_check_seven`. Broken by taking
  the flag branch out of `_variation`; both fail on the detail, and the varying one on
  `passed` and `measured` too. The 1s, the known rows and the share are counted off the
  fixture inside the test.
- `test_forecast_frame.py::test_a_named_column_costs_the_rows_it_is_unknown_on_and_not_the_run`.
  Broken by ignoring `columns`; fails with 53 rows kept where 51 were expected.
- `test_forecast_candidate.py::test_a_hole_in_the_candidate_block_costs_its_rows_and_not_the_run`.
  Broken by dropping `block` from the `retained` call; fails with the exact refusal
  W8-T3 measured, `origin 16: candidate column lines_added holds an unknown inside
  [ctx_start, o]`.
- `test_advise.py::test_a_run_stored_under_the_frames_own_id_is_found_and_named` and
  `::test_the_checklist_of_a_lagged_target_is_asked_at_the_registrys_horizon`. Broken by
  restoring the single-id lookup and the constant 1; the first fails because the label
  reads `no assessable forecast`, the second on `horizon 1 is not one of [4]` appearing
  in the page.

One existing assertion in `test_advise.py` moved and is not a regression:
`"baseline sufficient / variation"` is now `"baseline sufficient / ready"`, because
`merge_verification_failed` on that synthetic series is a flag with base rate 0.2 whose
check 7 now passes. One in `test_forecast_frame.py` moved with the reason string:
`run["excluded_rows"]["reason"]` reads `target merge_verification_ms unknown` rather
than `target unknown`.

**The length ratchet.** `forecast/candidate.py` was at 783 lines against the 800-line
limit and this work adds behaviour to it. Rather than split a file whose two halves
cannot be separated without a circular import (`report_advise.py` imports `POINT_AT`
from it and the row-N half needs `horizon`, `steps` and `licences` from the protocol
half), the additions were paid for by removing three duplications: `_limit`'s docstring
restated the module docstring's second refusal verbatim, and `_attach` and `advise_row`
each carried their own copy of the missing-column refusal that `_block` now owns.
The file is at 798. `test_forecast_candidate.py` is at 798 by the same arithmetic.

## UNSURE OR NOT DONE

**`merge_verification_ms` and `merge_verification_failed` could not be exercised on the
real lineage, and the brief's second VERIFY block was run on a different target.** Both
columns come from GitHub check runs, and the brief forbids running `gh` for anything but
`gh pr create`. With `--no-checks` the importer writes no verification outcome, so both
columns are `unavailable` on every one of the 176 rows and the backtester refuses them
before check 1. The rework outcomes do not need `gh`: `importer_git._walk` calls
`_write_rework` outside the `if slug is not None` branch that guards
`_write_verification` (src/telltale/importer_git.py, `_walk`), so `--no-checks` still
produced 37 of them. I substituted `rework_within_3_lag3`, which is the other target
whose column is `partial` and whose run is therefore stored under the suffixed frame id,
so the lookup under test is the same one. What is NOT covered by a real run here is the
`merge_verification_ms` path specifically; it is covered by
`test_advise.py::test_the_advisory_prints_the_block_the_label_and_the_sentence`, which
runs `merge_verification_failed` under the parent id, and by the new suffixed-id test.

**The advisory finds the run and still cannot print the pair, for a different reason
inside candidate.py.** Measured today:

    target rework_within_3_lag3 (flag)
      readiness: ready
      label: baseline sufficient (from fc_01M1VJ3QEK1PH7Y811A57C1TXP, ...)
      forecast: not run. target rework_within_3_lag3 has coverage partial: a target
      must be one of ['observed', 'derived']

`candidate._covariates`, which `one_step` calls to build the forecast of row N, checks
the target's coverage against `backtest.FORECASTABLE` (observed, derived), which is the
COVARIATE rule. W8-T3 split that rule in two and made `backtest.TARGET_COVERAGE`
(observed, derived, partial) the target rule, and `_covariates` was not moved with it.
The one-line fix is `FORECASTABLE` to `backtester.TARGET_COVERAGE` on that check.
`one_step` already runs over `frames.retained(series, target)`, so its context holds no
target hole. I did not make it: it is not one of this task's three DO items, it changes
what an advisory prints for every partial target at once, and the next question it
raises is whether `one_step` should cut its frame with the block too, which is a design
decision about what a refused advisory should say rather than a typo. Both are for the
coordinator.

**`candidate.one_step` still cuts its frame without the block, so the row-N forecast is
refused on a lineage with a binary commit.** `_future` reads the A block over
[ctx_start, N) off the frame and refuses on an unknown, and rows 0 and 5 are in the
frame for a target the block was not named to. The brief's item (2) names `conditioned`
and its unconditioned twin and nothing else, so I left it. It is the same fix
(`retained(series, target, a_block)` in `one_step`) and it would move
`found["origin"]`, `found["n_ctx"]` and the two existing origin assertions in
`test_forecast_candidate.py`, which the STOP line is about.

**One string that a stored run carries moved, and I judged it right rather than
measured it right.** `excluded_rows.reason` was the constant `target unknown` on every
run and is now the frame's own reason. A run whose block cost it rows and whose reason
still said only `target unknown` would be a stored row that misstates why its rows are
missing, which is the defect class AGENTS.md names. The identity case is untouched. What
I did not do is re-read every stored `forecast_runs` row in the owner's store to see
whether anything downstream matched on that exact string; nothing in this repository
does (`grep -rn excluded_rows` finds `backtest.py`, `test_forecast_ablation.py` on the
identity case, and `test_forecast_frame.py`).

**A candidate run stored after a backtest becomes the newest scored run, and the label
then reads `not assessable`.** Measured here in passing: after `forecast candidate` on
the same pair, `advise` printed `label: not assessable (from fc_01M1VHQ5RH152ZAVPS4A7HJVST,
variant change_past_only_candidate_conditioned, ...)`. That is `_latest`'s existing
"newest scored run wins" rule meeting a candidate run, which stores metrics and no
decision because `forecast candidate` does not run the decision function on either half
of its pair. Nothing about it changed today and I did not touch it: it is honest as far
as it goes (the run it names really is the newest scored one, and no rule labelled it),
but a reader who ran `forecast candidate` last will see a weaker word than the backtest
beside it earned. Whether `_latest` should prefer a run that carries a decision is the
coordinator's, and it is a change to what `advise` says rather than to what it can find.

**The two verification targets on this lineage have never been forecast by anybody.**
E16's population needs check runs on four repositories, and neither W8-T3 nor this task
has run one end to end with them. What would settle it is one import with `gh` and the
same three commands.

## NEXT

1. The one-line `_covariates` fix above, with the decision about whether `one_step`
   cuts its frame with the block. Both are inside `forecast/candidate.py` and both
   change what `telltale advise` prints on a real lineage.
2. E16 can run. Its readiness pass will now report a number about the data on every flag
   target, and its conditioned runs will not be refused by a binary commit. The
   `excluded_for_block` count per (repository, target) belongs in its results table
   beside the `excluded` count the design already asks for, because they are different
   rows and the first is a property of the block rather than of the outcome.
3. A block column with holes is excluded from the PAST-ONLY covariate list by its
   coverage word, even on a frame where it has none. That is the backtester's rule and
   E13 continuity depends on it, but it means the conditioned run reads `lines_added`
   from the future block while the unconditioned run has no `lines_added` column at all.
   Both halves of the pair are affected identically so nothing about the difference
   moves, and it is worth a sentence in E16's assumptions rather than a change here.

## EXPLAIN FOR THE OWNER

### Why any of this matters

E16 is the first experiment that can ask whether what is visible about a change before
it lands says anything about what happens after it. Three separate things stood between
it and a run, and none of them was about the data. Each one was Telltale reporting on
itself and calling the result a measurement. That is the failure this whole system is
built to avoid, so they were worth a task of their own.

### The first: a check that could not pass

Before a forecast runs, eight questions are asked of the series. One of them is: does
this quantity move at all? If it never moves, every naive guess is perfect, and "our
model beat the baseline" has no meaning because there is nothing to beat.

The way that question was answered is worth understanding, because it is a good answer
to a slightly different question. Take the middle value of the column. For every row,
measure how far it sits from that middle. Take the middle of THOSE distances. That
number is called the median absolute deviation, and it is a measure of spread that a
few wild rows cannot drag around. If it is zero, nothing moved.

Now put a yes/no column through it. Say 37 commits out of 173 were reworked. Most rows
are 0, so the middle value is 0. Each row's distance from 0 is just the row itself: 0 or
1. Most of those are 0, so the middle of them is 0 too. The check reads zero and refuses
a column that plainly takes two values.

This is not a bug in the data or in the arithmetic. It is a measure being used outside
what it measures. On a two-valued column the honest question is not "how spread out is
it" but "is the rarer of the two values ever there". So for a column whose unit is
`flag`, the check now takes the share of 1s, calls it p, and reports whichever of p and
1 - p is smaller. On this repository that is 37 / 173 = 0.2139. It is zero exactly when
one of the two values never occurs, which is the constant column the check was written
to catch, so nothing was weakened; the check now refuses the same thing for the same
reason, using a number that can tell the difference.

One detail that looks like fussiness and is not. The word `flag` is read off the SERIES
column and not off the forecast registry. The two agree on every flag today. They do not
agree in general: `verification_cycles` is called `cycles` in the registry and `runs` on
the series. Reading the word from the thing the check is actually looking at is the only
way to be sure the answer is about that thing.

### The second: one commit that stopped a whole experiment

The candidate protocol is two forecasts side by side. Both know the history. One of them
also gets six numbers about the change sitting in front of you: how many files it
touches, how many lines it adds, how many it removes, how many directories, whether it
touched tests, whether it moved a lockfile. If the second forecast is better than the
first, those six numbers carried information. If it is not, they did not. Call those six
numbers the block.

Now: `git diff --numstat` is the command that counts lines changed per file. For a
binary file, a PNG or a compiled artefact, it prints a dash, because lines are not the
unit there. So the total for that commit is partly unknown, and a total that is partly
unknown is unknown, not zero. Two commits in this repository's 176 are like that.

Until today, the protocol refused the entire run when it met one. The reasoning behind
that refusal was sound as far as it went: a candidate whose own features cannot be read
is not a candidate this protocol has anything to say about. But that is a statement
about ONE candidate, and it was being applied to the whole run. A forecast at a given
point in history reads a long stretch of rows behind it, and on a history shorter than
512 rows every one of those stretches reaches back to row zero. So a single unreadable
row near the bottom made every forecast above it unreadable too. Row 0 and row 5 here
cost all 39 of them.

W8-T3 had already solved this shape of problem for the thing being forecast. If the
outcome is unknown on a row, that row is not in the run: it is excluded, counted, and
its commit sha is recorded so a reader can name what is missing. Nothing is filled in.
The fix is to apply the identical rule to the block: a row whose features cannot be read
is not in the run either.

Two consequences are worth spelling out because they are where this could have gone
wrong.

Both forecasts must be built from the SAME set of rows. If the one with the block
excluded two rows and the one without kept them, the comparison would be between two
different histories, and the difference between them would be partly about the rows and
not about the block. So the frame is cut once, and both runs are made from it.

And the block is never narrowed. It would have been easy, and it is what W8-T3 did by
hand to get numbers at all, to drop `lines_added` and `lines_removed` and run on the
other four. But a run that quietly dropped two of six columns and still called itself
the conditioned run would be answering a different question under the same name. The
run says which rows the block cost, per column, on its own face:

    retained 172 rows  excluded_for_block 2 {'lines_added': 2, 'lines_removed': 2}

Read that carefully, because two numbers in it look inconsistent and are not. 172 rows
are in the run, out of 176. Three went because the outcome column, which carries the
label of the change three positions earlier, has no such change for the first three rows
of any history. Two rows cannot have their block read: rows 0 and 5. Row 0 is in both
groups, so the block cost the run one row the outcome had not already taken. The count 2
is "rows whose block cannot be read", which is the honest answer to "how much did the
binary commits cost me", and the count 172 is what actually ran. Adding them would be a
number about neither.

### The third: an advisory that could not find its own evidence

`telltale advise` prints one page about a change you are thinking of merging. Near the
top of that page, for each outcome, sits a word saying how strongly anything on the page
may be read. That word is not invented by the advisory. It is copied from the most
recent scored backtest of that outcome on that history, because a label the advisory
derived for itself would be a second decision rule competing with the real one.

To copy it, the advisory has to find the backtest. It looked it up by the history's
identifier. But a run over an outcome with gaps is not a run over the history: it is a
run over the subset of rows where that outcome is known, and that subset is a different
thing with a different identifier. W8-T3 gave it one: the history's identifier with the
outcome's name appended, `ser_8362...:rework_within_3_lag3`. So the run was filed under
one name and looked up under another, and the advisory said "nothing has scored this",
about a row that had been written seconds earlier.

The fix is to try both, history first. History first matters: every run that has always
worked keeps the identifier it has always had, and the second lookup only ever finds
something the first did not. The page also records which of the two answered, because
that is a fact about where the row is, not something to guess from the outcome's
coverage word.

The second half of the same page had a smaller problem with the same shape. The
readiness checklist has to be asked at a horizon, meaning how many steps ahead the
forecast reaches. The advisory asked at 1, always, because that was written into it as a
constant. One outcome cannot be forecast at 1. `rework_within_3_lag3` is deliberately
shifted: the value on any row is the label of the change three earlier. So from where
you stand, the fourth step ahead is the label of the change in front of you, and the
first three are labels of changes already made. Asked at 1, the checklist refused, and
the page printed `refused` next to the outcome, which reads as a fact about the history
and was a fact about the advisory's own constant. It now asks each outcome at the
horizon the registry gives it.

### How the numbers here were measured, and what they are not

Every number in this write-up came from running the real system against this
repository's real history in a throwaway store: 176 commits imported from git, one
series built, one checklist, one paired run, one advisory. No number was estimated.

Two things they are not. The verification outcomes (`merge_verification_ms` and
`merge_verification_failed`) come from GitHub check runs, this task was not permitted to
call GitHub, so those two columns were empty here and the advisory lookup was verified
on the rework label instead. It exercises the identical path, since it is the other
outcome whose column has gaps, but the check-run columns were not run end to end today.
And the paired difference above is 0.0: none of the five forecasters used here reads a
past-future covariate at all, so the two runs are the same run twice. The run says so in
its own warnings rather than letting a zero be read as "the block does not matter". What
would answer that question is a model that reads the block, which needs the forecast
extra and is E16's job.

### What was rejected

Two things.

The first is narrowing the block. Dropping the two line-count columns makes the run go
through with no change to any code, and it is how the numbers in W8-T3's report were
produced. It was rejected because the resulting run is not the run E16 pre-registered:
its question is whether the WHOLE block moves the forecast, and answering a smaller
question under the larger question's name is the kind of quiet substitution that makes
a laboratory's output worthless.

The second is deleting the old refusal. Once rows with unreadable blocks are out of the
frame, the check inside the protocol that refuses on one can never fire. Deleting it
would have been tidier. It stays, because the function it lives in is a hook whose
caller chooses which set of rows to run it over, and if some future caller passes a set
nobody trimmed, the choice is between refusing and inventing a number. Its docstring now
says it is unreachable and why it is still there, so the next reader does not spend an
afternoon working out whether it is dead code.
