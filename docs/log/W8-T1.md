## WHAT WAS WRONG

**1. The brief's account of `repo_id` was wrong, and the conclusion it drew survives
anyway.** The brief says "repo_id already hashes the remote". It does not. `repo._repo_id`
is the sha256 of the repository's ROOT COMMIT, falling back to the common git directory
path when there are no commits. Measured on 2026-09-06:

| checkout | repo_id | remote fingerprint |
| --- | --- | --- |
| this worktree | `d9f783b1d318c0d6...` | `3d0c195d71f1` |
| `git clone` of it into /tmp | `d9f783b1d318c0d6...` | `a6d0bab71fa9` |
| the main checkout | `d9f783b1d318c0d6...` | `3d0c195d71f1` |

So two clones of one remote land in the same capture, which is what the brief wanted, and
so does a clone whose remote is a local path. Hashing the root commit is the stronger
rule. The docstring on `resolve` carries this measurement.

**2. `external_system` was not on `external.outcome`'s allowlist.** The brief lists it
among that type's fields; the table at `allowlist_telltale.py` carried it on
`external.correlation` only, so an outcome posted with it would have dropped the field and
written an `unknown_field` diagnostic. Added, as `Kind.ENUM`. It carries no content: the
values are the two constants `github:check-runs` and `git:line-overlap`, and the remote URL
they are derived from is read into the process and dropped.

**3. `no_check_runs` and `check_run_incomplete` were refused too.** `telltale.capture_ended`
had `exit_code`, `terminal`, `duration_ms`, `surfaces_received` and `worktree_id`. Both
added as `Kind.SIZE`. They are counts, not content.

**4. `git_branch` and `git_since` are refused and are NOT recorded.** The brief said to put
them on `capture_started` "if the allowlist takes them, else nothing". It does not take
them, so the import records nothing about which branch it walked or which cutoff it used.
This is a real gap and it is in UNSURE below.

**5. `unlinked` needs no allowlist entry, and needs a `LADDER` entry that is not mine to
add.** `Kind.ENUM` in `sanitize.py` bounds a string to 64 characters and checks it against
no vocabulary, so `link_confidence: "unlinked"` stores as written. But
`series_lineage._rung` drops any commit whose `link_confidence` is not in `LADDER`, and
`LADDER` is `explicit, provider_reported, tree_match_during, tree_match_after, heuristic`.
So the 157 rows this command writes are invisible to the change clock until W8-T2 adds the
word. That is the intended split of this wave and is stated in the module docstring.

**6. The rework rate here is 0.195, not the 0.170 the brief measured.** 30 outcomes over
the 154 decided commits of this branch's 157. The brief's number was 156 first-parent
commits of `main` in the 90 days to 2026-09-06, a different and slightly smaller commit
set, measured by a script I do not have. I have not reconciled the two, and I am not
claiming either is wrong: the difference is 4 commits' worth of label on a slightly
different population. The rule implemented here is the one the brief states, and the test
pins its exact behaviour on eight commits it builds itself.

**7. `importer_git.py` reached 897 lines against the 800-line ratchet.** Cut to 799 by
compressing prose, not by removing a constraint from a comment. It now sits one line under
the gate, which is a bad place to leave a file; the split is named in NEXT.

## WHAT CHANGED

**`src/telltale/importer_git.py`** (new, 799 lines).

`import_history(store, repo_path, *, branch, since, level, checks)` and
`dry_run(...)`. One capture per repository: `importer.capture_id("git", repo_id)`, so
re-importing the same history always lands in the same place.

The walk is `git log --first-parent --format=%H%x00%ct`, oldest first. `%ct` is the same
field `repo_link._commit_facts` reads, so a commit imported here and the same commit
linked to a capture carry one timestamp, and the walk gets every commit's date without a
second git call. Each new commit becomes one `telltale.repo.commit` payload built by
`repo_link._commit_facts` and `repo_link._commit_stats` (the launcher's own two readers,
so the nine fields are the launcher's nine) plus `link_confidence: "unlinked"`.

The rework label reads `git show --first-parent --format= --unified=0 <sha>` and keeps the
added lines per file, stripped, longer than 3 characters. For each of the next three
commits it takes the removed lines under the same file, and the first non-empty
intersection is the rework: one `external.outcome` of kind `revert_or_repair`,
`component_id` the reworked commit, `external_run_id` the commit that reworked it,
`timestamp` the later commit's own. Nothing is written when no later commit hits, and
nothing when fewer than three have landed: undecided is not 0.

`_Reworks` caches at most four diffs and evicts as it walks. Without the cache each
commit's diff would be read four times; without the eviction the whole history's line sets
would be held at once, and this repository's `uv.lock` commits are tens of thousands of
lines each. Diffs decode with `errors="replace"`.

The check-run half runs `gh api repos/<owner>/<repo>/commits/<sha>/check-runs?per_page=100`
once per commit, no shell, 30 s cap, and refuses rather than guesses in five places: a
non-zero exit, a timeout, a body that is not JSON, a page shorter than the API's own
`total_count`, and a run with no `started_at`/`completed_at`. `status` is `fail` when any
conclusion is one of failure, timed_out, cancelled, action_required, startup_failure, and
`pass` only when every conclusion is one of success, neutral, skipped. Anything else writes
no outcome and names the word in a `dropped` diagnostic. `duration_ms` is
`max(completed_at) - min(started_at)` in whole milliseconds; `external_run_id` is the check
suite id when the runs agree on one and the sha when they do not.

Re-import reads back the shas under this capture in one query, appends only the new
commits, and re-evaluates the rework rule for the last three previously recorded commits,
whose windows may have closed since. An outcome is written only where none exists for that
sha. A run with nothing new writes nothing at all, not even a lifecycle row.

**`src/telltale/cli_import.py`.** The kind `git-history`, with `--repo`, `--branch`,
`--since`, `--no-checks` and `--dry-run`. `--root` and `--project` are refused for it and
the three new flags are refused for the other kinds, the way the export kind already
refuses `--since` and `--project`: a flag that silently did nothing would read as the
import having honoured it. `importer_git.check()` runs before the store is opened, so a
refusal leaves no database behind.

**`src/telltale/allowlist_telltale.py`.** Three fields: `external_system` on
`external.outcome`, `no_check_runs` and `check_run_incomplete` on `telltale.capture_ended`.

**`tests/integration/test_import_git.py`** (new). Seven tests over a repository the test
builds with `git init` and eight commits. No checked-in `.git`, and no network: every test
passes `--no-checks`.

**`docs/README.md`.** The report count, 57 to 58.

`git_since` are refused by `telltale.capture_started`'s allowlist, and the brief's rule was
to state them only if the schema already took them. `telltale.repo.identity` records the
branch the working tree was ON at import time, which is not the same as `--branch`. Adding
two `Kind.ENUM` fields would close it; a branch name is text the owner wrote, and
`repo.identity.branch` already stores one, so I do not think it raises a content question.
It is the owner's call.

**These rows are invisible to the change clock until W8-T2 lands.**
`series_lineage._rung` drops a commit whose `link_confidence` is not on `LADDER`, and
`unlinked` is not. I did not edit `series_lineage.py`: W8-T2 owns it.

**The outcomes carry no `attempt`, so `series_outcomes._rework` cannot match them yet.**
`_names` matches an outcome by `(component_id, attempt)` against the `(task_id, attempt)`

half; I have not designed how, and I flag it because a reader of this PR alone would
reasonably expect the outcomes to feed the three post-merge columns and they do not.

**A re-import that appends writes a second capture_started/capture_ended bracket.** I chose

measured it cannot be wrong, and re-stating a total nobody recounted would be inventing
one. The cost is real and named: `series_regime._capture_bounds` refuses a capture that
does not hold exactly one start and one end. It is reached only from `refuse_request`,
which returns early unless the store holds a `policy.intervention` row, and only on a
request-clock build, so no path in the tree reaches it today for a git-history capture. If
that changes, the refusal is by name rather than silent.

**The rework rate on this repository is 0.195 against the brief's 0.170.** See WHAT WAS
WRONG 6. Not reconciled.

**`importer_git.py` is at 799 lines against the 800 limit.** The next line added to it trips

## EXPLAIN FOR THE OWNER

### The problem, in one paragraph

You want to forecast what happens to a change after it is merged: how long the merge
verification took, whether it failed, and whether somebody had to come back and fix the
change within the next three commits. To fit any forecast at all, the method needs about 36
rows of history inside one stable period. Telltale had 54 rows and got zero usable
forecasts, because those 54 rows were the only commits it had ever WATCHED being made. A
commit reached the system by being linked to a recorded agent session, and Telltale has
only recorded a few dozen sessions.

But the commits themselves are not scarce. Your four repositories hold hundreds. They just
never had a session attached to them. This change reads them straight out of git.

### First question: is a commit read out of git the same kind of thing as one we watched?

No, and that difference has to survive into the data or every number built on it is a lie.

Telltale already has a five-step scale for "how sure are we that this recorded session made
this commit". At the top, the orchestrator said so explicitly. At the bottom, the commit
merely happened around the right time and the working tree looked right, which is the
weakest thing you can say and still say something. That bottom word is `heuristic`.

A commit read out of git is not at the bottom of that scale. It is not on the scale.
Nobody attempted a link and got weak evidence; nobody attempted a link at all. Those are
different statements and folding them together would let a later reader treat 157 commits
as 157 weak session links.

So there is a new word, `unlinked`, and it means exactly "no capture was ever linked to
this, by construction". It has one consequence you should know about: the part of the
system that builds the forecasting table only accepts the five words it already knows, so
right now it throws these 157 rows away. Adding the sixth word is the other task in this
wave, W8-T2. That split is deliberate, but it means this change alone does not yet move a
forecast.

### Second question: what does "somebody had to fix this change" mean, mechanically?

The label you want is "was this commit reworked". A human can read a diff and say. A
program needs a rule, and the rule has to be fixed BEFORE you look at the answers, or you
end up tuning it until it produces the rate you expected.

The rule was written down in the brief before I saw any of this repository's numbers:

> For commit i, take the lines it ADDED. Look at the next three commits. If one of them
> REMOVED, from the same file, a line that commit i added, then commit i was reworked, and
> the first such commit is the one that did it. Ignore lines of three characters or fewer.

That last clause is the whole difference between a rule and a coin flip. Almost every
commit in every repository adds a `}` somewhere and almost every later commit removes one.
Without the length bound, everything reworks everything.

There is a second, quieter half of the same clause: the lines are compared after stripping
the leading whitespace. That matters because a line's length is measured after stripping.
An indented closing bracket, `    )`, is five characters as written and one character
stripped. Under the correct rule it is dropped as evidence. Under a rule that skips the
stripping, it is kept, and then any two commits that happen to both touch a wrapped
function call in the same file look like a rework.

I built that exact case into the test fixture, because a rule you cannot break on demand is
a rule you have not tested. The fixture is eight commits. Commit 2 adds a wrapped call
spelled `assert load(`; commit 4 deletes a different wrapped call spelled
`assert compute(`. The only text they share is the indented `)`. Under the shipped rule the
overlap is empty and commit 2 is not labelled. I then changed one line of the module,
`body.strip()` to `body`, and reran:

```
E  Extra items in the left set:
E  ('f326a198597bd3b020bb04e6443e4a75dbd280f5', '1f1cb7ea13b2ed7cfb203490bd4ad39abfff64d5')
```

A rework the fixture never designed, invented out of a bracket. Then I put the line back
and the seven tests passed again.

On this repository the rule labels 30 of the 154 commits whose window has closed: a rate of
0.195. The brief measured 0.170 with the orchestrator's own script over a slightly
different set of commits. I have not reconciled the two and I am not going to pretend the
difference is nothing: it is 4 commits' worth of label. What I can say is that the rule
implemented here is the one that was written down first, and that its behaviour is pinned
commit by commit in the test.

### Third question: where does "did the verification pass" come from?

From GitHub. Every commit on `main` in your four repositories ran CI, and GitHub will tell
you, per commit, which checks ran, what each concluded, and when each started and finished.
The command asks `gh api` once per commit.

The interesting part is not the happy path. It is the four ways to get no answer, and what
the command does with each:

- The commit has no check runs. Seven of the 26 commits I tried. No outcome, counted.
- A check run has not finished. One of the 26. No outcome, counted, because the elapsed
  time of the part that HAS finished is not the duration of the verification.
- A check run concluded with a word that is neither a pass nor a fail (`stale`, or nothing
  at all). No outcome, counted, and the word itself is written into a diagnostic row so
  that the day GitHub adds a conclusion this code has never heard of, the store says so
  rather than silently dropping commits.
- GitHub returned one page and said there were more. No outcome. A truncated list would
  turn "one of these failed" into "all of these passed", which is the single worst thing
  this could do.

None of those becomes a zero and none becomes a pass. That is the same rule as everywhere
else in Telltale: a verification nobody ran is not a passing verification.

Timing, measured rather than guessed: ten calls against this repository took 345 ms at the
fastest, 410 ms in the middle, 432 ms at the slowest. So importing this repository's 157
commits with checks on is roughly a minute of network. `--no-checks` makes it zero, and the
dry run tells you how many calls an import would make before it makes any.

### Fourth question: a history grows. What happens on the second import?

Every other importer in Telltale takes a file that is finished. It computes an id from the
session, and if that id is already in the database it skips the file whole. That is right
for a transcript and wrong for a repository: tomorrow there will be more commits.

So this is the one importer that appends to an existing capture. It reads back the commit
ids already recorded under this repository's capture, and appends only what is new. Run it
twice in a row and the second run writes nothing:

```
imported 0 new commit(s) of 157 found ... 0 observations
```

There is one subtlety that took a second pass to get right. The rework label is DELAYED: a
commit cannot be labelled until three more commits have landed after it. So the last three
commits of any import are deliberately unlabelled. When you import again next week, those
three commits now have three successors, and their labels have become decidable. If the
import only looked at new commits, those three would stay unlabelled forever. So each run
also re-examines the last three previously recorded commits, and writes a label only where
none exists. There is a test that builds the eight-commit fixture, imports, adds one commit,
imports again, and asserts that the label which was undecidable the first time is present
the second.

### What I chose against

**Storing a `0` when a window has not closed yet.** This is the tempting one, because a
column of 0s and 1s is easier to feed a model than a column with holes. It is also a lie:
"no rework happened" and "not enough time has passed to know" are different facts, and a 0
merges them. The last three commits of every import carry no label at all.

**Guessing a check-run status from a partial answer.** If three checks passed and one is
still running, it is very tempting to call it a pass. It is not a pass; it is an unfinished
verification, and the commit gets nothing.

**One `capture_ended` row per repository instead of one per import run.** A capture in
Telltale normally has exactly one start and one end. Since this capture is appended to over
time, I had to pick: either write one end row whose "records received" count silently goes
out of date the moment you import again, or write a fresh bracket per run with that run's
own counts. I chose the second, because a stale number is a wrong number, and I would
rather have an unusual shape than a false count. The cost is stated in UNSURE above: one
code path in the regime module would refuse a capture with two ends, and no route in the
tree reaches it today, and if it ever does it refuses by name rather than quietly.

**Reading the file contents.** The command reads a diff, which is source code, and compares
one line to another inside the process. Nothing is kept. What reaches the database is what
Telltale already stored for a linked commit: hashes, counts, and file paths. There is a test
for exactly this. It commits three fake credentials into a file's TEXT, imports, then reads
every byte SQLite wrote to disk, including the write-ahead log, and asserts none of the
three is there while the file's PATH still is. The path has to still be there, otherwise
the test would pass against an import that stored nothing at all.
