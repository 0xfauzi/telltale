# W8-T2 uncaptured change rows: git-backfilled lineages on the change clock

## OUTCOME

The change clock now builds a row for a commit no capture landed. On this repository
that is the difference between a lineage of the commits somebody happened to record a
session for and a lineage of the repository:

| | before | after |
| --- | --- | --- |
| first-parent commits (`git rev-list --first-parent --count HEAD`) | 158 | 158 |
| rows a git-history capture of them produces | build refused | 158 |
| `series check` on that series | - | ok |
| registered targets `forecast readiness` will accept on it | 0 | 0 with `--no-checks`, 1 with check runs |

The seven columns only a capture of the session can fill read `unavailable` on such a
frame and `partial` on a mixed one, each with one sentence in the cohort saying which
half of the row is missing. The post-merge columns read outcomes that name the commit by
its sha, so a check run and a rework reach a row nothing landed.

One more column is on the clock: `rework_within_3_lag3`, the delayed rework label moved
to the row whose own commit time decided it. That is the column E16 forecasts at H = 4,
and it exists because the unlagged one carries look-ahead inside a backtest context. The
defect is recorded in `docs/design/amendments/W8-T2.md`; the compiler's cells are
unchanged.

Every gate is green: `uv run pytest -m integration` 386 passed 2 skipped, `uv run mypy .` 128
source files clean, ruff check and ruff format clean, deptry clean, `pre-commit run
--all-files` all hooks passed.

## WHAT WAS WRONG

**1. `_rung` dropped every commit a git history recorded.** `series_lineage._changes`
kept a sha only when its `link_confidence` was one of spec 12.3's five ladder words. A
history backfill writes `unlinked`, which is not on the ladder, so every one of its
commits went to `dropped` with `_NO_RUNG` and a repository with no launcher captures
built no series at all. Measured: before this change, `series build --clock change` over
a 158-commit git-history capture refused with "no commit is linked to any capture of this
repository".

**2. A capability-backed column read `observed` over rows where no capture existed.**
This is the defect I did not expect and it is the important one. Six of the seven process
columns rest on a provider capability (`request_usage`, `compaction`, `commands`,
`file_paths`), and `_specs` took their coverage word from the capability map alone. A
capability map is measured per capture. A row no capture landed belongs to no capture the
map describes.

Measured on the mixed fixture (one launcher capture, seven backfilled commits):
`fresh_input_tokens_total` came out `observed` with seven of eight cells None. Two things
follow from that word. `--policy refuse` refuses the whole build over a hole nobody can
fill (`refuse_on_gaps` refuses exactly the `observed` columns), and the readiness
checklist would have called the column forecastable when nothing could be forecast from
it.

The fix is a floor and only ever weakens: on the change clock, and only when the frame
holds an uncaptured row, the word is the worse of the capability word and the word the
column's own cells earn. On a frame of landed changes alone nothing changes, so `refuse`
keeps its teeth.

**3. Two comments claimed a mechanism that does not exist.** `series_lineage.py` said of
the `low_confidence` flag "the backtester excludes the flag by default (W3-T2)", and
`model.py`'s `RowMeta` docstring says "the backtester excludes such a row by default".
The brief asked me to search for who reads that flag and cite the result. Here it is,
`grep -rn low_confidence src/` on this branch:

```
src/telltale/series_lineage.py:74:LOW_CONFIDENCE = "low_confidence"
src/telltale/series_lineage.py:78:# and not a low_confidence rung, because nothing was guessed. A change at this rung
src/telltale/model.py:264:    numbers a forecaster may read: `low_confidence` on a change row says the commit
src/telltale/cli_forecast.py:84:    print(f"low_confidence rows {len(low)}{_named(low)}")
src/telltale/series_changes.py:228:    spec 12.3's ladder at all, so it can never also be low_confidence, and a reader
```

`cli_forecast.py:82-84` counts the flagged rows and names them. Nothing else reads a row
flag anywhere: no forecaster, no backtester, no plan. The behaviour is unchanged, which
is what the brief asked for; I corrected the comment in `series_lineage.py`, which is
mine to edit. **`model.py:264` still carries the false sentence and `model.py` is not in
OWNS, so I left it.** It should be corrected by whoever next owns that file.

**4. `_changes` picked a commit's payload arbitrarily.** With one sha recorded by two
captures, `payload = dict(rows[0]["fields"])` took whichever capture the iteration
reached first. That was harmless while two launcher captures recorded identical facts and
is not harmless with a backfill beside a launcher, whose `per_file` lists can differ. The
payload is now the earliest one recorded AT the winning rung, so a build of one store is
the same row every time.

**5. W8-T1's contract names a field the allowlist does not carry.** The contract says
each `external.outcome` carries `external_system` ("github:check-runs",
"git:line-overlap"). `external.outcome` in `allowlist_telltale.py` has no
`external_system` key, so `sanitize` drops it and reports it as an unknown field:

```
$ uv run python -c "... sanitize('external.outcome', {..., 'external_system': 'github:check-runs', ...}, 1, ctx)"
red {'dropped': ['external_system:unknown'], 'truncated': [], 'redacted': []}
unknown ['external_system']
```

Nothing in W8-T2 reads `external_system`, so this does not block me and I did not adapt
around it. **W8-T1 owns the allowlist and has to add the key, or drop the field from the
contract.** I did not treat this as the brief's STOP condition because that condition is
about W8-T1's branch, and there is no W8-T1 branch to compare against yet (see UNSURE).

The change clock moved out of `series_lineage.py`, which was at exactly 800 lines against

### `series_changes.py`: the uncaptured row

- `UNLINKED = "unlinked"` and `UNCAPTURED = "uncaptured"` (declared in
  `series_lineage.py` so `cli_forecast`'s existing `lineage.LOW_CONFIDENCE` import keeps
  its neighbours). `_rung` returns UNLINKED only when no ladder word is present, which is
  the whole of the deduplication.
- `Change.uncaptured` is rung UNLINKED **and** no landing attempt. `_flags` returns
  `[UNCAPTURED]` or `[LOW_CONFIDENCE]` or nothing, never both: a commit at the UNLINKED
  rung is at no rung of the ladder, so it can never also be a guess.
- `_change_row` adds `NO_CAPTURE` to `unknown_columns` for each of the seven
  `PROCESS_COLUMNS` on an uncaptured row. The cells were already None; what is new is the
  sentence.
- `Change.activities` includes the sha-named outcomes on an uncaptured row, so they are
  in the row's provenance and its `row_end_ts` covers them.

### `series_outcomes.py`: outcomes that name a sha

- `columns(landed, identities, closes, own=None, sha="")`. `own` is the recording
  capture's activities and is passed only for an uncaptured change; `None` means the
  captured rule, an empty list means the backfilled rule found nothing. `about(rows, sha)`
  is the filter, public because the row has to put those activities in its provenance.
- `_stamp` dates a backfilled rework by its `timestamp` FIELD, not by its activity
  position. A posted outcome's position is when the receiver stamped it and its payload
  timestamp is the same instant; a backfilled one's position is when the import ran, which
  can be months after the commit.
- `_rework` returns 0 for "no rework outcome" on both paths, and on both that rests on
  there being a name an event could have carried. `NO_IDENTITY` now reads "no capture
  landed this change and no outcome names its sha: ...".
- `deadline(times, index)` moved here from `series_lineage._deadline`; `lagged(labels)` is
  new; `POST_MERGE_COLUMNS` is four names.

### The lagged column

`rework_within_3_lag3`, appended immediately after `rework_within_3`. Row j holds change
j - 3's label. `deadline(j - 3)` IS change j's commit time, so the cell is decided by the

is what makes `series check` able to test the claim rather than take it. The reasoning and
the defect it works around are in `docs/design/amendments/W8-T2.md` section 4.

### Cohort

`providers` now includes the provider of a capture that carried a row without being an

### `forecast/backtest.py` and `forecast/readiness.py`

`series_lineage.uncaptured(series)` returns zero or one sentence and `uncaptured_keys`

assumptions in one line, and `readiness.report` prints `uncaptured N` beside the row

The two functions are separate on purpose. I wrote one at first, returning the sentence
list, and had readiness take `len` of it: the header then read `uncaptured 1` over a
frame of 158 uncaptured rows. The test caught it. Two callers wanted two different things
out of one fact and one of them was silently getting the wrong one.

# EXPLAIN FOR THE OWNER

## What was at stake

Telltale can only forecast what it has rows of. Until this change, a row on the change
clock existed only when some recorded session could be tied to the commit. This repository
has 158 commits on its main line and Telltale had rows for 40 of them. The other 118 were
not missing because nothing happened; they were missing because nobody was recording at
the time.

That is a bad way to choose a sample. The commits that got recorded are the ones made
during an agent session, which is a different population from "commits of this
repository". Any number computed over them is a number about agent sessions wearing the
label of a repository.

## The first question: is a commit nobody watched still a row?

Yes, and the reason is that a commit has two halves.

One half is what the change IS: how many files it touched, how many lines it added and
removed, how many directories, whether it touched a test, whether it touched a dependency
file. All six of those are readable from the git history months later. Nothing about them
needs a recording.

The other half is what the process was: how many tokens the model read, how many times the
context was compacted, how many verification runs there were, how many distinct files were
read. Not one of those is recoverable from a commit. If nobody was recording, they are
gone, permanently.

So the row exists, half full. The question that took the rest of the work was: how does a
row say "this half is empty, and here is why" without ever looking like it said zero?

## Three ways to say "unknown", and why all three are needed

**First: the cell.** Every one of those seven process columns is `None`. That was already
true before this change, because Telltale's counting rules already refuse to turn nothing
into zero: adding up token counts over no requests gives unknown, not 0, and a ratio of
edits per file over no edits is undefined, not 0. So no code change was needed here. Good.

**Second: the sentence.** `None` in a cell does not say why. There is a place on a series
called the cohort where a column can carry one sentence explaining its holes, and each of
the seven now carries this one:

> no capture landed this change: the row is a repository fact and the process that
> produced it was not observed

That matters because the other reasons a cell is empty are actionable and this one is not.
"No verification outcome was posted" tells you to post one. This one tells you the session
is gone.

**Third: the column's word.** Each column carries a single word saying how well it was
seen: `observed`, `derived`, `partial`, `unavailable`. This is where I found the real
defect, and it is worth walking through slowly because it is the kind of mistake that
looks like nothing.

Telltale measures, per recorded session, which facts that session's tooling could see. It
calls that a capability map. A column like `fresh_input_tokens_total` says "I rest on the
capability `request_usage`", and its word was copied straight off that map.

Now put one recorded session and seven unrecorded commits in one frame. The map says
`request_usage` was `observed`, because the one session that exists could see it. So the
column was labelled `observed` while seven of its eight cells were empty.

Two things go wrong with that. Telltale has a strict mode where a hole in a column marked
`observed` stops the build - that is the whole point of the mode, since a column that could
be seen and has a hole means something was lost. Under the old rule, strict mode would
refuse to build any git-backfilled lineage at all, over holes nobody can ever fill. And the
forecasting preflight would have called the column usable when there is nothing in it to
use.

The reason for the mistake is one sentence: **a capability map is measured per recorded
session, and a commit nobody recorded belongs to no session the map describes.** The map
simply has no jurisdiction over that row.

So the word is now the worse of the two: what the capability says, and what the column's
own cells earn. Worse only, never better. And only on frames that actually contain an
unrecorded commit, so strict mode keeps working everywhere else.

I want to flag the answer I rejected, because it is the tempting one. I could have deleted
the capability from those seven columns and let their word come purely from their cells.
That is simpler and it has no conditional in it. It is also wrong: imagine a session whose
tooling reported token counts on only some requests. The capability says `partial`. But if
every row of the frame ends up with some number in it, the cell-only rule says `observed` -
and a column has just been promoted to a stronger claim than the evidence behind it. This
system does not promote claims. So the conditional stays.

## The second question: how does a commit nobody watched get a test result?

Three of the change-clock columns are about what happened AFTER the merge: how long the
verification took, whether it failed, and whether the change was reverted or repaired soon
afterwards. Those come from outcome records that an orchestrator posts.

Before this change, Telltale found them by asking "which recorded session landed this
commit, and what was that session called?" - the outcome names a task and an attempt
number. A commit nobody recorded has no session and no name, so it could never have an
outcome.

But a git-history import writes the commit and the CI results about it into the same
place, and there they share a different name: the commit's sha. So for an unrecorded
commit, Telltale now reads the outcomes sitting alongside the commit whose `component_id`
is that sha.

One detail here is a real decision, not a translation. An outcome carries two times: when
the record arrived in Telltale, and a `timestamp` field saying when the event happened.
For a live posting these are the same instant, so nobody had to choose. For a backfill
they are months apart - the import ran today about a commit from August. The rework
question is "did a repair land within the next three commits", so the event's own time is
the only one that answers it. Telltale now uses the `timestamp` field for backfilled
outcomes, and if there is no readable timestamp it says unknown rather than guessing.

## The third question: one commit, two recorders

A commit can be written down twice - once by the live recorder that watched the session,
once by the history import that walks every commit. Two records, one commit. If that
became two rows, every count over the series would be wrong, and quietly.

The rule: one sha is one row, at the strongest claim any recorder made. "I watched this
session make this commit" beats "I found this commit in the history" every time, so the row
keeps the live recorder's numbers and does not carry the "nobody watched this" mark.

I checked this rather than trusting it. I broke the rule on purpose - made the grouping
key the commit plus the recorder instead of just the commit - and ran the test. It reported
nine rows for eight commits. Then I put it back.

While I was there I found a smaller version of the same problem. When two recorders both
described a commit, Telltale read the description that happened to come out of the database
first. Nothing guaranteed which. With two live sessions writing identical facts that never
mattered; with an import beside a live session it does, because their file lists can
differ. It now reads the description written by whichever recorder made the strongest
claim, so two builds of the same database give the same row.

## The fourth question, and the one worth your attention

One of the change-clock columns is `rework_within_3`: did this change get reverted or
repaired within the next three commits? Notice what that question needs. You cannot answer
it about a commit until three more commits have landed. The answer for commit 40 is fixed
by what happens at commit 43.

Now think about how a forecast is scored here. Telltale picks a point in the history, hands
the forecaster everything before it, asks for a prediction, and compares against what
actually came next. The point is called the origin, and the whole method depends on the
forecaster seeing nothing from at or after it.

Put those two facts together. At origin 40, the forecaster is handed rows 37, 38 and 39.
Row 37's label was fixed by commit 40. Row 38's by commit 41. Row 39's by commit 42.

The forecaster is being shown three answers that were decided by the future. That is
leakage, and it makes any score computed this way better than it should be.

Telltale already had a guard for this, but it guards the wrong side: it stops the origin
from running off the end of the history, so the thing being predicted always has a real
answer. Nothing was checking the answers inside the context.

This has never produced a wrong number, and the reason is not reassuring. Experiment E11
ran this protocol and planned zero windows - it never got far enough to read a context -
and every rework label in the store was 0 anyway. The defect was real and invisible.

**I did not change the existing column.** The brief was explicit about that, and it is the
right call: `rework_within_3` on row 40 means "commit 40 was reworked", and that meaning
should not shift. The fix is a second column beside it.

The new column, `rework_within_3_lag3`, holds on row 40 the answer about commit 37. That
sounds like bookkeeping. It is the whole fix, and here is why in one line: **commit 37's
three-commit window closes exactly at commit 40.** So the value on row 40 was settled the
moment row 40 itself happened. A context ending at origin 40 now contains only answers
that commits 39 and earlier settled. Nothing from the future.

Rather than assert that, I made it checkable. Telltale records, per row, which underlying
records the row was built from, and it has a check that refuses if any of them is dated
after the row closed. Row 40 now lists row 37's records among its own, so that check
tests the no-leakage claim directly. It passes on all 158 rows of this repository.

The experiment E16 will forecast this new column four steps ahead, which lines the fourth
step up with the origin's own commit. That is the coordinator's design, written before any
number was seen.

## What the checks actually say now

Two commands, run against this repository's real 158 commits.

`series build` produces 158 rows. Six columns read `observed` or `partial` - the diff
facts, which git still has. Seven read `unavailable` - the process facts, which are gone.
The rework column reads `partial` with exactly three empty cells, and they are the last
three commits, because the window for those has not finished. The lagged column also reads
`partial` with three empty cells, and they are the first three, because those have no
commit three places behind them. `series check`, which verifies that no row was built from
anything dated after it closed, says `ok`.

`forecast readiness` runs eight checks before any forecast is attempted. On this data, with
no CI results imported, it does not run at all - it refuses, because the thing you asked
it to forecast has no values. That refusal is correct and it is not new.

With CI results present (I generated fabricated ones purely so the checklist would have
something to print - **those durations measure nothing**), check one fails and names all
fourteen columns that cannot carry a forecast. Check two passes with 142 usable windows
against a required minimum of 20.

That 142 is the number I would draw your attention to. E11 planned zero windows on this
repository's change clock and stopped there. This is the first frame in the project that
has enough history to score a forecast on at all, and the reason is simply that it contains
the whole repository instead of the recorded slice of it.
