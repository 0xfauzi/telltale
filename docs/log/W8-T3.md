## WHAT WAS WRONG

**1. The backtester implemented half of design 6.12 step (2).** The step reads "keep
only rows where the target's coverage is observed ... drop any window containing None in
the target or a selected covariate". The first clause is about rows. Only the second was
built, and `backtest._variant` additionally refused any target whose coverage word was
not `observed` or `derived`, so a lineage's post-merge columns could not be run at all.
Measured on the 169-row lineage: `merge_verification_ms` and `merge_verification_failed`
carry 26 unknown cells, `rework_within_3` and `rework_within_3_lag3` three each.

Window-level exclusion would not have rescued them. Every context of a lineage shorter
than 512 rows starts at row 0, so a single unknown cell low in the column drops nearly
every window: the coordinator measured 16 of 146 windows kept for merge_verification_ms
and 0 of 143 for the lagged label. I did not re-measure that; I measured the other side,
which is 127 and 37 windows kept under the row-level rule on a slightly longer tree.

**2. Readiness refused a covariate the run would have excluded anyway.** W7-T3 already
found this shape for `unavailable` and fixed it there. `partial` was left failing check
1, while `backtest._variant` dropped a partial covariate by name and ran. So the
checklist refused runs the backtester was willing to make, which is the defect W7-T3
named, one word later.

**3. The candidate protocol read three rows past the origin.** `_attach` filled the
A block over `range(ctx_start, origin + horizon)`. At H = 1 that is `[ctx_start, o]`,
which is right: row o's features are known at the merge decision. At H = 4 it reads rows
o+1, o+2 and o+3, which are the next three changes. Nobody has made them. This was
invisible until now because every candidate target was H = 1; the moment
`rework_within_3_lag3` arrives at H = 4 it is look-ahead in the covariate, in a protocol
whose whole point is that the target's look-ahead was removed.

**4. The delayed-label ceiling would have double-counted.** `candidate._limit` stopped
`rework_within_3` at `o <= N - 3` because the last three rows carry no label. With rows
excluded at the frame, those rows are not in N any more, so the ceiling would have taken
three more origins whose labels ARE known.

**5. Two files were at the 800-line ratchet.** `backtest.py` and `candidate.py` were
both at exactly 800 lines, and the ratchet fails a file that crosses. The brief flagged
the first and not the second. A third file, `test_forecast_contracts.py`, crossed it
when the new tests landed there.

## WHAT CHANGED

**`src/telltale/forecast/frame.py` (new, 201 lines).** The projections a run makes of a
Series before it scores anything.

- `retained(series, target)`: the same Series with only the rows whose target cell is
  known. `row_meta` filtered the same way, changepoints remapped (a changepoint at index
  i becomes the count of retained rows below i; 0 and N' dropped), four cohort keys
  (`retained_rows`, `excluded_rows`, `excluded_row_keys`, `excluded_reason`), and
  `series_id` suffixed with `:<target>`. **When no row is excluded the parent object is
  returned**, so `retained(s, t) is s` and every hole-free run is byte-identical to the
  run it was.
- `excluded(frame)` and `assumption(frame)`: the run's record and the one sentence.
- `scored(record, steps)`: one window record cut to 1-based steps. `None` is every step.
- `edge_padded(values, horizon)`: a covariate block extended by repeating its last value.
- `threshold(series, target, c_min)`: moved here from `backtest`, because tau is q80 of
  the head of the frame a run scores and not of the series it came from.

**`backtest.py`.** `run` and `plan` operate on `retained(series, target)`. `FORECASTABLE`
is now the covariate rule and `TARGET_COVERAGE = ("observed", "derived", "partial")` the
target rule. The run record carries `excluded_rows: {count, row_keys, reason}` and, when
the count is above zero, the assumption sentence the brief specifies. `persist` writes
the record into the stored row's `scenario`. Net 796 lines, four under the ratchet.

**`readiness.py`.** Every check runs over the retained frame. Check 1 passes on a
partial covariate, names every excluded column with its word, and fails only on the
target's own coverage. The header prints `rows N  uncaptured U  retained N'  excluded k`.

**`forecast/__init__.py`.** `rework_within_3_lag3` joins `TARGETS` (change clock, flag,

**`candidate.py`.** The module-wide `HORIZON = 1` is gone; `horizon(target)` and

**The brief's STOP condition did not fire, and here is why.** It says stop if `metrics`
cannot take a step selection without changing a number on a golden or an E-file. I did
not change `metrics` at all: the step selection is `frame.scored`, a transform of the
window records that the candidate protocol applies before calling `metrics`, so the
default is every step for every existing caller and no number in any metric moved. The
two goldens above moved for a different reason, the row-level exclusion, which is the
task's own mandate.

**E13's stored numbers are not affected, and this is an argument rather than a re-run.**
E13 scored 596 (capture, target, H) triples that passed the whole checklist. Check 3
fails on any unknown cell inside a planned window, and on a series with no changepoint
every row is inside some window, so a target with a hole anywhere could not have been
ready. I did not re-run E13: it needs the owner's store and the forecast extra. What
would settle it is a re-run of its readiness pass with the two numbers compared.

**Readiness check 7 fails on a flag target whose base rate is not near a half, and this
one bites E16.** On the real lineage, `rework_within_3_lag3` reads `variation FAIL,
measured 0`: the scaled median absolute deviation of a 0/1 column whose median is 0 is
0, whatever its base rate. 34 of 169 commits carry a rework here. The same will happen
to `merge_verification_failed`. Nothing blocks a backtest (the backtester does not call
the checklist), so E16 can run and will report `NOT ready: variation` beside every flag
target. This is a real question about the check, not a defect I introduced, and it is
the coordinator's to answer before E16.

**`telltale advise` cannot see a run of a holed target, and prints `refused` for the
lagged one.** Two measured consequences, both in `cli_advise.py`, which is outside OWNS:

- `_latest` looks runs up by the parent series id, and a holed target's run is stored
  under `<parent>:<target>`. I ran `forecast backtest --target merge_verification_ms`,
  it stored a row, and `advise` still says "no stored true-order backtest of this target
  on this series". The fix is one lookup that also tries the suffixed id.
- `cli_advise.HORIZON = 1` is a module constant, so the checklist for the lagged target
  is asked at H = 1 and refuses with `horizon 1 is not one of [4]`. The fix is to read
  `candidate.horizon(target)`, which now exists.

Neither is a crash and both print an honest sentence, so I left them rather than edit a
sixth file outside OWNS.

**`forecast candidate` refuses on this repository with the default A block.** Not this
task's rule and not changed by it: a hole in the candidate's own features has always
been a refusal rather than a dropped window, because a candidate whose features cannot
be read is not a candidate the protocol says anything about. Measured here:
`lines_added` and `lines_removed` are unknown on rows 0 and 5 of the 169-row lineage
(binary-file commits), so `conditioned` refuses at origin 16 with "candidate column
lines_added holds an unknown inside [ctx_start, o]". E16 conditions on block A on four
repositories, and any binary commit in one of them will refuse the whole run. The
protocol runs at H = 4 on this lineage as soon as the block excludes those two columns,
which is how the paired numbers below were produced. What E16 needs is a decision:
either drop the window at such an origin, or narrow the block, or accept the refusal.

**A scenario over a holed target is refused later rather than earlier.** `scenario.py`
calls `backtest._variant`, which now admits a partial target, and refuses instead when
its own context reader meets the unknown cell. Different sentence, same outcome, and
scenario.py is outside OWNS. It is not run over the change clock's post-merge columns
today.

## EXPLAIN FOR THE OWNER

### The question this had to answer first

You want to know whether the size of a change tells you anything about what happens
after you merge it. To ask that, the laboratory needs a column of numbers, one per
change, saying what did happen: how long verification took, whether it failed, whether
somebody had to come back and fix it.

Here is the problem. On a real repository those columns have holes, and the holes are
not accidents. You push three commits at once and GitHub runs its checks on the last
one, so the first two have no verification time: 26 of this repository's 169 commits are
in that position. The rework label asks "did one of the next three changes undo part of
this one", and the last three commits of any history have no next three, so their answer
is not wrong, it does not exist yet. The lagged version of that label, which W8-T2 added
last week, has the mirror-image hole at the start.

So every column worth forecasting on this clock is a column with gaps. Before today the
laboratory refused all of them, and it refused them at the door: `forecast readiness`
printed one line, "coverage partial", and stopped.

### The choice, and the one I rejected

There are two honest ways to handle a gap, and the system already used one of them.

The first is to throw away the WINDOW. A window is one test: rows 0 to 15 as context,
row 16 as the answer. If any cell in it is unknown, the whole test is discarded and the
reason is counted. That is what the backtester does for a supporting column, and it is
right for a supporting column.

I rejected it for the target, and the reason is arithmetic rather than taste. The
context of a window reaches back to the start of the history unless a regime boundary
stops it, and this lineage has no boundaries. So every one of the 146 windows the
coordinator counted contains row 0, row 1, row 2 and so on. One unknown cell near the
beginning poisons nearly all of them: 16 of 146 survived for verification time, and for
the lagged label at four steps, none of the 143 did. A rule that answers "nothing is
assessable" on every real repository is not a rule, it is a wall.

The second way is to throw away the ROW. If this commit's verification time is unknown,
this commit is not part of the series for that question. The 143 commits that do have
one are, in order, and they are what the model sees.

Design 6.12 already said this, in a clause nobody had implemented: "keep only rows where
the target's coverage is observed". So the change is less an invention than a reading.

### What it costs, and where the cost is written down

Dropping a row is not free, and pretending otherwise is how a recorder starts lying. Two
things change meaning.

The first is what "the previous change" means. In the retained series the row before
origin 100 is not the commit before it in git; it is the previous commit that HAD a
verification time. Every run that excludes a row now carries this sentence in its
assumptions, and you saw it in the backtest above:

> 26 of 169 rows were excluded because the target was unknown on them; the context is
> the lineage without those rows, so the previous row means the previous change with a
> known target.

The second is that the run has to be nameable. The stored row's series id is
`ser_e899...:merge_verification_ms`, the parent series with the target appended, because
one series produces a different frame per target: 143 rows for verification time, 166
for the lagged label, 169 for anything with no holes. Two runs whose window counts
differ are not two runs of the same thing, and the id says so.

And the excluded rows are named, not just counted. `excluded_rows.row_keys` holds the 26
commit shas. You can go and look at them.

### The rule I was most careful about

If nothing was excluded, the projection returns the original object. Not a copy: the
same object.

That matters because of what would otherwise be true. Every request-clock forecast this
laboratory has ever made, including E13's 596 backtests, ran on series with no holes in
the target. If the frame had been rebuilt for them, its id would be a new id, the stored
rows would look like new rows, and the comparison with what was already measured would
be broken for nothing. Returning the parent object makes those runs identical down to
the bytes, and there is a test that asserts the object identity rather than its
contents.

Two numbers did move, and I want to be exact about them rather than bury them. Two
Codex fixtures record a summary field that includes "the longest run of rows with no
regime change". One holds 11 rows with one unknown token count; that field now reads 10.
The other went from 2 to 1. Both captures are far too short to forecast (they need 32
rows and produce zero windows), so no scored number moved and no forecast of them ever
existed. I regenerated both goldens with the documented command and the diff is three
lines.

### The second half: asking about the candidate rather than about its neighbours

The rework label has a timing problem that W8-T2 wrote down and worked around. "Did the
next three changes undo this one" cannot be answered until those three changes exist. So
the answer for change 40 is only known once change 43 lands. If a backtest at origin 43
reads change 40's label as context, it has read something decided at the moment the
origin arrives, which is a peek at the future.

W8-T2's fix was to move the label to the row where it becomes decidable: row 43 carries
change 40's answer. Now every cell in a context was settled before the context ended.

The cost is that a forecast of that column at one step ahead is a forecast about change
40, three changes ago. Useless for a merge decision. You have to ask for four steps: at
origin o, step 4 lands on the row that carries change o's own answer. Steps 1, 2 and 3
land on the three changes before it, which are somebody else's question.

So the protocol scores step 4 and nothing else, and the report says `scored on step 4 of
4` on its face. The window records keep all four steps, because you should be able to
recompute the number yourself; what is narrowed is what the metric is computed over.
That is a deliberate split, and the test recomputes the mean absolute error by hand from
the stored records and checks it against the run, then checks that the four-step number
is different, so the test cannot pass on a run that forgot to select the step.

### The bug I found on the way, which is the part I would want to know about

The conditioned run hands the forecaster the candidate's own features: how many files,
how many lines, whether tests moved. At one step ahead the code filled that block over
rows `ctx_start` to `o` inclusive, which is exactly right. Row o is the candidate, and
you can read its diff before you merge it.

At four steps the same expression, `range(ctx_start, origin + horizon)`, reads rows o+1,
o+2 and o+3. Those are the three changes after the candidate. Nobody has written them.

It was harmless while every candidate target ran at one step, and it would have become
look-ahead the moment the lagged label arrived, in the one protocol whose entire purpose
is that the target's look-ahead was removed. The block now stops at the candidate and
repeats the candidate's own values for the remaining steps, which is what the model
would have done to a short block anyway, done in the open and recorded on the run as
`future_beyond_step_1: edge-replicated from the candidate row`.

I checked this by breaking it back and watching the test fail:

```
assert [23.0, 34.0, 17.0, 30.0] == [23.0, 23.0, 23.0, 23.0]
```

The left side is three future commits' file counts leaking into a forecast. The right
side is the candidate, four times.

### One thing that is now easier and one that is now harder

Easier: `rework_within_3` used to stop its origins three rows early, by a constant, to
avoid scoring against a label that did not exist. That constant is gone, because a row
with no label is not in the frame at all. Keeping both would have thrown away three
origins whose labels are perfectly good. One protection, stated once.

Harder, and this is the honest part: `telltale advise` looks up stored runs by the
parent series id, so it cannot find a run of a holed target under its suffixed id. I ran
a backtest, it stored a row, and `advise` said "no stored true-order backtest of this
target on this series". It also asks the checklist at one step for every candidate
target, so the four-step one answers "horizon 1 is not one of [4]". Both are one-line
fixes in a file this task was told not to touch, both print an honest sentence rather
than a wrong number, and both are written up under NEXT.

### The number I could not produce

On this repository, `forecast candidate` will not run with the standard feature block,
because two of the 169 commits changed a binary file and git reports no line counts for
one. `lines_added` is genuinely unknown there, and the protocol has always refused a
candidate whose own features cannot be read, on the grounds that a conditioned forecast
which quietly dropped two of six features is the unconditioned forecast wearing the
other one's name. That rule is not mine to change here.

So the paired numbers above were produced with those two columns out of the block, and
they are shown as what they are: a run where nothing read the covariate, so the
difference is zero by construction and the run says so. Before E16 conditions on the A
block across four repositories, somebody has to decide what a binary commit does to it.
That decision needs to be made, and I did not make it.
