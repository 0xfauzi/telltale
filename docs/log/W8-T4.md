## WHAT CHANGED

### `repo_link._commit_stats` gains `first_parent`

```python
def _commit_stats(cwd, sha, parents, *, first_parent: bool = False) -> dict[str, Any]:
```

When `first_parent` is True and the commit has more than one parent, the counts and
`per_file` come from `diff-tree -r -M --no-commit-id parents[0] sha`: the diff the base
took when the merge landed on it. `--root` is left off in that case, because a merge names
both endpoints and `--root` has nothing to do.

When it is False, nothing changes. The docstring says why the two differ: on a
`--first-parent` walk the parent was picked by the walk before the function ran, so
reporting `diff-tree parents[0] sha` is no more a pick than the walk was; a merge inside a
launcher capture (a `git merge main` into a task branch) was reached with no parent
chosen, and it still reports unknown. `importer_git.commit_payload` passes True; every
other caller keeps the default.

### `series_lineage.tracked_base` and `attach`

New section in `src/telltale/series_lineage.py`.

`tracked_base(found)` returns the commits recorded by the captures whose provider is `git`
(`importer_git.PROVIDER`), indexed by sha and by tree, or None when the repository has no
such capture. None is the whole of "without a git-history import nothing changes": every
rule below is reached through a `Base`.

A tree that more than one base commit carries is excluded from the tree index and put in
`Base.ambiguous`: a revert puts one tree on a branch twice, and picking the earlier or the
later would be a link nobody made.

`attach(base, captured)` returns (sha -> the row it joins, the refusals). A sha on the
base joins itself. A sha not on the base whose tree is exactly one base commit's joins
that commit. Anything else is refused by name:

- `not on the tracked base: a commit that did not land as itself` (counted as
  `off_base_commits`);
- `two commits of the tracked base carry this tree: refusing to pick`;
- `two captured commits carry the tree of one base commit: refusing to pick`.

The last is the STOP condition of the brief made mechanical: two captured commits claiming
one base commit cancel each other rather than racing for it.

### `series_changes._changes` builds rows out of the base

`_changes` now returns `(changes, dropped, counts)` and is split into `_joined`,
`_grouped` and `_change`. The split that matters is inside `_change`:

- `rows` is every activity that reaches the row, the tree twin included. The rung, the
  landing attempts, the provenance and `row_end_ts` come from it.
- `named` is only the activities that name the ROW's sha. The payload comes from it, so
  the six repository columns are the base commit's numbers.

That second rule is the one worth arguing. A tree twin is a different commit: its diff
against its own parent is the last increment of a branch, and what landed on the base is
the squash commit's diff against the base. They are different numbers about different
commits, and the row is the second one. Where the twin and the row are the same sha there
is no twin at all, `named` is every activity, and W8-T2's rule is untouched: the launcher's
payload wins over the import's for one sha.

`Change` gains `captured_sha`, and `_flags` emits `captured_sha=<sha>` into
`RowMeta.flags`. `RowMeta` has no field for it and design 6.2 fixes its shape, so the flag
is spelled `name=value`; without it a row keyed on the base commit gives a reader no way
back to the session's own commit.

The cohort gains `collapsed_links` always, and `off_base_commits` only where there is a
base. Both sit beside `dropped` and are counted before the regime cut, because both are
facts about the lineage rather than about the retained slice.

# EXPLAIN FOR THE OWNER

## What was at stake

Your change clock is meant to be a list of the changes that landed on this repository, one
row each, so that a forecaster can learn from what happened. Before this task it was two
lists shuffled together, and the numbers on most of its rows were blank.

Both problems came from the same place: the recorder was answering a question nobody had
asked, and refusing to answer the one they had.

## First: what is a change, actually?

Start with the thing your workflow does. You work on a task branch. You make several
commits on it. Then the branch is squash-merged into main, which means git throws away
those commits and writes ONE new commit containing all their work, with a new identity.
The branch commits are not on main. They never were.

Telltale has two recorders. The launcher watches a session and records the commits that
session made - branch commits. The importer walks main's history and records the commits
that are on main - squash commits. Before this task, the change clock took both lists and
sorted them by time.

So a "lineage of main" contained 51 commits that are not on main, sitting between the 168
that are. I checked whether that overlap was partial or total, because a partial one would
mean something different: I listed main's first-parent history and compared. Zero of the
51 is on it. Not "most", not "some". None.

That is the first question this task had to answer: **which commits are the rows?** The
answer is the one the import already knows, because it walked the branch: the commits it
recorded ARE the lineage. I called that set the **tracked base** - a name for something
you already have, which is "the list of commits on main that the importer wrote down".

Everything else follows from that. A captured commit is no longer a row in its own right.
It is either something that landed on the base, or it is not.

## Second: how does a session reach the change it produced?

If the branch commits are not rows, then all the interesting information a session
produces - how many tokens it used, how many times it ran the tests, how much it rewrote
files - has nowhere to go. That would be a worse frame, not a better one.

So the second question: **when a session's commit is not on main, can we still say which
row on main is its work?**

Sometimes yes, and the reason is a detail of your own gate protocol. Before a task branch
is merged, main is merged INTO it. After that merge the branch tip contains exactly what
main will contain once the squash lands. Two different commits, two different identities,
but the same *tree*.

A tree, in git, is the exact content of the whole repository at a point in time, addressed
by a hash. Two commits with the same tree hold byte-identical file contents. It is not a
similarity score; it is equality.

So: a captured commit joins the base row whose tree equals its own. On your store that
catches 5 of the 51. Those five rows now carry the base commit's identity and position on
the clock, and the session's numbers.

The other 46 are intermediate branch commits - work in progress whose content never landed
anywhere as a unit. They are not rows. They are listed in the build's dropped table with
the sentence "not on the tracked base: a commit that did not land as itself", and counted
in the frame's summary as `off_base_commits`. Not silently discarded: this codebase's rule
is that a reader must be able to see what was refused and why.

## Third: whose numbers does a joined row report?

This is where I had to make a judgment call, so I want to state it plainly.

A row on the tracked base has two halves. The **repository half** describes the diff: how
many files changed, how many lines, which subsystems, whether a test file moved, whether a
dependency manifest moved. The **process half** describes the session: tokens, compactions,
verification runs, files read.

When a session's commit joins a base commit by tree, the two commits are different commits
with different diffs. The branch tip's own diff is the last increment of a branch. The
squash commit's diff against main is everything the task did. So:

- the repository half comes from the base commit,
- the process half comes from the session.

The row's key and its position on the clock are the base commit's, and the session's own
sha is recorded on the row as `captured_sha=<sha>` so you can always get back to it.

There is one case that looks similar and behaves differently, and it is worth knowing
about. If a session's commit IS on the base by sha - the same commit, recorded twice by
two recorders - then both recorders are describing the same diff, and the rule is the one
that was already there: the more confident recorder's numbers win. The new rule only
applies where the two recorders are describing *different* commits.

## Fourth: why were the numbers blank?

Separate problem, same shape of mistake.

When Telltale reads a commit, it asks git what that commit changed. For a normal commit
that is unambiguous. For a *merge* commit - one with two parents - "what changed" depends
on which parent you compare against, and there is no neutral answer. So `_commit_stats`
refused: for any commit with two parents it returned unknown for every count and for the
list of changed files.

That refusal is correct, and it was being applied in a place where the question had
already been answered. The importer does not wander through history; it walks
`git log --first-parent`, which follows only the first parent at every merge. On that walk
a merge is one row of main's history, and the reader is asking what main took when the
branch landed. That is `git diff-tree <first parent> <merge>`, and it is not a pick,
because the walk already picked.

I measured the cost before changing anything. On deckgen, 79 of 118 rows had no
`files_changed`. On kstrl, 100 of 252. Those are exactly the merge counts. And because the
same refusal blanked the list of changed file paths, it also blanked
`subsystems_touched`, `test_files_changed` and `dependency_delta` - three of the features
your E16 protocol conditions on. On deckgen that was 81 of 118 rows.

The fix is a keyword: `_commit_stats(..., first_parent=True)`. The importer passes it
because it walked with `--first-parent`. Nobody else does. A merge that happens inside a
recorded session - you run `git merge main` on your branch - still reports unknown,
because nothing there picked a parent. After the change, deckgen and kstrl both report
`files_changed` on every row.

I checked what is still blank, rather than assuming the fix was total. Two things, and
neither is about merges: 27 deckgen rows contain a binary file, where git reports no line
counts and the summing code refuses rather than dropping the file quietly; and 5 deckgen
and 4 kstrl commits changed so many files that the path list did not fit in the 8 KB
payload bound, where the reader refuses a truncated list rather than counting a prefix.
Both refusals are older rules working as designed.

## What the frame looks like now

On a copy of your E16 store, telltale's own change clock:

| | before | after |
| --- | --- | --- |
| rows | 219 | 168 |
| rows that are commits on main | 168 | 168 |
| rows that are not | 51 | 0 |
| rows carrying a session's numbers | 51 | 5 |
| `series check` | ok | ok |

The number that went down is the one I want you to look at hardest. `captured_rows` fell
from 51 to 5. That is not a loss of information - the 51 were never rows of main - but it
is a plain statement of how much of your repository's history has a recorded session
attached to it, and the honest answer is 3 percent.

That number is a property of the workflow, not of the recorder. It is 5 and not 51 because
the tree match only fires when a branch tip is byte-identical to what landed. If a branch
is rebased before merging, or a reviewer's change goes in on top, the trees differ and the
session cannot be attached to anything. I did not try to close that gap with a
similarity rule, because a similarity rule is a guess, and a guessed link would put one
session's tokens on another session's change.
