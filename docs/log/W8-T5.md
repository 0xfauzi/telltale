## WHAT WAS WRONG

**The question was being asked in the wrong place.** The three cells are decisions about
path strings and nothing else: `subsystems_touched` counts distinct first path components
with `.` for the root, `test_files_changed` counts paths under a test directory or named
like a test, `dependency_delta` is 1 when any path is a lockfile or a manifest. Git hands
over every one of those strings at record time. Only the STORED list is bounded.

Design 6.4 caps a payload at 8 KB, and both writers of a commit payload fit it by cutting
`per_file` to a prefix and setting `per_file_truncated` (`importer_git._capped`,
`launch._capped`). `series_paths.columns` was called at series BUILD time, over that stored
list, and it refuses a prefix. The refusal was right. Here are the five deckgen commits the
bound truncated, with what the whole list says beside what the surviving prefix says, as
(subsystems, test files, dependency):

| commit | files changed | entries kept | whole list | the stored prefix |
| --- | --- | --- | --- | --- |
| `552ef3ad3186` | 101 | 85 | (2, 0, 1) | (2, 0, 0) |
| `92e3c567bb84` | 140 | 88 | (6, 5, 1) | (4, 0, 0) |
| `6607d927f94f` | 85 | 78 | (7, 10, 0) | (6, 5, 0) |
| `f55fb868f435` | 115 | 83 | (7, 8, 0) | (5, 0, 0) |
| `b4ba2ff0d523` | 94 | 87 | (8, 22, 1) | (6, 20, 0) |

On `92e3c567bb84` the prefix says the commit changed no test file and touched no manifest.
It changed five and touched one. So reading the prefix more bravely was never the fix.

What it cost: one unknown cell makes a column `partial` (`series_lineage._measured`), and a
`partial` covariate is excluded BY NAME from every forecast variant, both in readiness
check 1 and in `backtest._variant`. Five commits out of deckgen's 118 and four out of
kstrl's 252 removed three of E16's six candidate features from every run of an experiment
whose whole question is whether those features move the forecast.

`files_changed` already had the answer to this, and had had it since W3-T4: it is the true
count whatever the bound does to the list, because it is counted before the cut.

## WHAT CHANGED

In the order the reasoning ran.

**1. `repo_link._commit_stats` folds the three cells.** It already builds the whole
`per_file` list from one `git diff-tree` numstat. It now calls
`series_paths.columns({"per_file": <that list>})` and returns the three answers beside
`files_changed`, `additions`, `deletions` and the list itself. When the list is unknown (a
merge reached with no parent chosen, a diff git could not read) the three stay None, which
is the same behaviour as before: `_STAT_FIELDS` grew, and `dict.fromkeys(_STAT_FIELDS)` is
still the one unknown answer.

The rule is `series_paths` in both places. This module owns no path rule of its own, which
is what makes the 646-commit agreement above a real check rather than a function agreeing
with itself.

**2. `path_rules_version` on the payload.** A short hash of `series_paths.py`'s source,
`paths-<12 hex>`, computed the way `correlate.REDUCER_VERSION` and `series.REDUCER_VERSION`
are. It exists because storing a cell changes what an edit to the rule does. Before, editing
`_TEST_GLOBS` or `_MANIFESTS` changed every column of every series built afterwards. Now it
changes what LATER commits store and leaves earlier rows alone, so a frame can hold cells
folded by two rules and without this field nobody could tell. On the four stores above every
row carries one value, `paths-640ac3da3d13`.

Twelve hex characters is 48 bits. What it has to separate is the number of distinct versions
of one small module a store ever holds, not an adversary.

**3. Four fields on the `telltale.repo.commit` allowlist.** The three cells as `Kind.SIZE`,
for the same reason `files_changed` is SIZE: a value that is not a number is dropped rather
than carried. `path_rules_version` as `Kind.ENUM`, a short symbolic string bounded at 64
characters, the same Kind `link_confidence` takes.

Neither fit-to-bound function needed a code change. Both rebuild the payload as
`{**payload, "per_file": kept}`, so a scalar passes the cut untouched. I checked this by
breaking the allowlist entry instead: with the four fields removed, both new tests fail with
`KeyError: 'subsystems_touched'`, which is the sanitizer dropping them.

**4. `series_paths.columns` prefers the stored cells.** All three or none, checked as types
rather than with `.get()` and a default, and `bool` excluded explicitly because it is a
subclass of `int` in Python and `dependency_delta` is a flag. When the payload does not carry
all three it falls through to the `per_file` rule, unchanged. That fallback is the live path
for every commit recorded before this task, which on the owner's store is every launcher
capture taken so far.

**5. `NO_PATHS` loses its truncation clause.** The cohort sentence named "a list the 8 KB
payload bound truncated" as a free-standing cause. It is not one any more. The sentence now
names the recorder having no list to fold, and, separately, a commit recorded before this
task whose list is absent or was truncated. I did not delete the word truncation, because
for a pre-W8-T5 row it is still true; I subordinated it under the clause that dates the row.
See UNSURE OR NOT DONE.

**6. Tests, each broken once against the un-fixed code and watched failing.**

`test_import_git.py::test_a_truncated_path_list_no_longer_costs_the_three_path_columns`
builds a repository whose second commit writes 400 files under four top-level directories,
one of them `tests/`, plus a `pyproject.toml` at the root: 401 files, past both bounds
(`PER_FILE_MAX` is 100 entries, and 401 entries of roughly 50 JSON bytes each is about
20 KB against 8 KB). It asserts `per_file_truncated` is True on the stored payload, then
that the change series reads subsystems 5 (the four directories plus the root), test files
100, dependency 1, all three `observed`, and no path column in the cohort's
`unknown_columns`.

`test_import_git.py::test_the_stored_cells_and_the_per_file_rule_agree_where_both_can_answer`
takes the eight-commit history, where nothing is truncated, and compares each row's stored

`test_series_backfill.py::test_a_truncated_list_reads_its_stored_cells_and_an_old_row_reads_its_list`

## EXPLAIN FOR THE OWNER

### The thing that was going wrong

Three of the six numbers E16 wants to forecast with were missing on exactly the commits
where they matter most: the big ones.

Not missing because nobody could compute them. Missing because of where they were being
computed.

### What the three numbers are

When Telltale records a commit, it asks three questions about the file paths that commit
touched. How many parts of the repository did it reach into, counting the top-level folder
of each path. How many test files did it change. Did it touch a file that declares
dependencies, like `pyproject.toml` or `uv.lock`, yes or no.

All three are answered by looking at the path strings and nothing else. No file is opened.
Nothing is run. `src/telltale/repo.py` and `tests/test_x.py` and `pyproject.toml` is three
paths, and from those three strings alone you get: three places touched (`src`, `tests`, and
the repository root), one test file, and yes to dependencies.

### The size limit, and where it bites

Every record Telltale stores is capped at 8 kilobytes. That is design 6.4 and it is there so
one enormous record cannot bloat the database of somebody who is only trying to record their
own coding sessions.

A commit record carries a list with one entry per changed file. A commit that touches 140
files has a list far past 8 KB. So both places that write a commit record cut that list down
until it fits, keep the first hundred-ish entries, and set a flag saying `per_file_truncated`
- this is a prefix, not the whole thing.

Now the timing. The three questions used to be answered later, when a series was built, by
reading that stored list back out of the database. And the code that answers them refuses to
work from a prefix. Deliberately, and it was right to. Here is one real commit from your
deckgen repository, `92e3c567bb84`:

- it changed 140 files
- 88 entries survived the cut
- read from the whole list: 6 places touched, 5 test files, yes to dependencies
- read from the surviving 88: 4 places touched, **0 test files**, **no** to dependencies

A wrong answer delivered confidently is worse than no answer, so the old code said "I cannot
tell" and left all three blank.

### Why blank was expensive

A forecasting column that is blank on even one row is marked `partial`, and a `partial`
column is dropped by name from every forecast run. Not down-weighted. Dropped.

Five commits out of deckgen's 118 were truncated. Four out of kstrl's 252. Those nine rows
removed three of E16's six candidate features from every single run of an experiment whose
entire question is whether those features change the forecast.

### The fix, which is a change of timing

Git knows every path at the moment the commit is recorded. The full list is sitting in
memory, before anything gets cut. So the three questions are now asked there, and the three
answers are stored on the record as three plain numbers.

Three numbers cost about forty bytes. The 8 KB limit still cuts the file list. It just no
longer takes the answers with it.

There was already a precedent for this in your own codebase, which is what told me the shape
was right: `files_changed` has worked this way since W3-T4. It says 140 for that commit even
though only 88 entries are stored, because it is counted before the cut, not derived from
what survived. Its docstring says so in one line: "files_changed stays the true count
whatever the launcher's payload bound does to the list". The three path numbers are now in
the same position.

### The answer I rejected

The obvious cheaper fix is to let the reader work from the prefix and accept that it will
sometimes read low. The table above is why I did not. On `92e3c567bb84` the prefix reports
zero test files for a commit that changed five, and no dependency change for a commit that
touched a manifest. Those are not slightly low. They are the opposite answer, and they would
be indistinguishable from a real zero in a forecast.

The second answer I rejected was recomputing the numbers inside `repo_link.py` with its own
copy of the path rule. That would have been fewer imports and one more place for the rule to
live. Two copies of a rule drift, and the check I care about most is that the old way and
the new way agree, which is only meaningful if there is one rule and two call sites.

### How I know it works

Fresh imports of your four repositories into a scratch directory under `/tmp`, then a change
series built from each. Nothing was written to `~/.telltale`.

The before and after come from the same store, built twice, with the second build told to
ignore the stored numbers. That is the honest comparison: same commits, same database, only
the rule differs.

| repository | rows | blanks before | blanks after |
| --- | --- | --- | --- |
| deckgen | 118 | 5 | 0 |
| kstrl | 252 | 4 | 0 |
| telltale | 177 | 0 | 0 |
| systemap | 108 | 0 | 0 |

The blanks were exactly the truncated commits, which is the result I expected and the one
that would have told me I had misdiagnosed the cause if it had come out differently.

Then the check that matters more. On every commit whose stored list is complete, both ways
of getting the three numbers can speak, and they must say the same thing or the change is
not "the numbers survive" but "the numbers moved". I compared them on 646 commits: 113
deckgen, 248 kstrl, 177 telltale, 108 systemap. Zero disagreements.

### One thing to know about the future

Storing an answer instead of recomputing it means an edit to the rule no longer changes old
rows. If you decide next month that a folder named `spec` counts as tests, commits recorded
after that change carry the new count and commits recorded before carry the old one, in the
same table.

So each record also carries a short fingerprint of the rule that produced its numbers,
`paths-640ac3da3d13` on all four of your repositories today. If a future frame ever mixes
two, that field is what makes it visible instead of silent.
