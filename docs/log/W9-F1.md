## WHAT WAS WRONG

**(a) The snippet was correct TOML and the wrong shape.** `_codex_snippet` printed the
four `-c` override strings verbatim, one per line:

```toml
otel.exporter={ "otlp-http" = { endpoint = "http://127.0.0.1:47399/v1/logs", protocol = "json" } }
otel.metrics_exporter={ "otlp-http" = { endpoint = "http://127.0.0.1:47399/v1/metrics", protocol = "json" } }
otel.tool_result={ max_bytes = 0 }
otel.environment="telltale"
```

Each line is a valid TOML dotted key. On its own, that document has a top-level `otel`
table. Appended to a file that already has a table header, it does not: a dotted key
after `[projects."..."]` is a key OF that table. `codex exec` under that file delivered
nothing to the daemon (otel_logs 8 before, 8 after) and printed no error; the same values
as `-c` overrides delivered 4 batches. The failure is silent, which is what makes it
worth a test rather than a note.

**(b) Five 2.1.263 shapes the allowlist had never met.** From the `unknown_field`
diagnostics of the owner's day-to-day sessions between 22:00 and 22:16 UTC:
`scratchpad_dir` on every hook event (529 occurrences); `agent_transcript_path`,
`background_task_count` and `session_cron_count` on SubagentStop (46 each);
seven fields on PostModelSwitch; a top-level `command` on PostToolUseFailure (13);
`from_mode`, `to_mode` and `trigger` on the OTel event `permission_mode_changed`.

Two of those are not provider changes at all, and calling them that would have been the
wrong fix:

- `command` on PostToolUseFailure is Telltale's own. `providers/claude.py::_lifted` runs
  on every hook body's `tool_input` and lifts `command`, `file_path`, `git_commit_id` and
  `subagent_type` out of it. PostToolUseFailure had never listed `command` or
  `file_path`, so the parser produced a field its own schema refused. Both are listed
  now.
- `background_task_count` and `session_cron_count` on SubagentStop are the counts
  `_counted` has computed on every hook body since W2-T6. 2.1.263 spreads one body into
  Stop and SubagentStop, so both events carry the arrays; only Stop had the counts
  allowlisted.

**(c) Known and refused was being reported as unknown.** Every Claude OTel record carries
`organization.id`, `user.account_id`, `user.account_uuid`, `user.email` and `user.id`
(E01 measured all five on every event of every scenario, and 2.1.263 still sends them).
Design 6.3 never persists account identity, and `providers/claude.py::_otel_payload`
deliberately left them in the payload so the allowlist gate would drop them. That gate
drops them AND names them, so each record wrote five names into an `unknown_field`
diagnostic. On the owner's evening that was 1250 occurrences of each of the five, and 41
diagnostic rows for one short session.

An `unknown_field` is a claim: this parser is behind its provider, go and look. There was
nothing to look at, and 7119 names an evening is what buries the next field a release
really does add.

## WHAT CHANGED

### The Kinds, and where each shape was read

Never guessed. Every Kind below comes from the 2.1.263 binary's own zod schema or its
runtime builder, and the last column says which.

| field | Kind | shape, and where |
|---|---|---|
| `scratchpad_dir` | PATH | the common hook-input builder returns it beside `session_id`, `transcript_path` and `cwd`: a directory |
| `agent_transcript_path` | PATH | SubagentStop schema `s()`, and the binary path-translates it exactly as `transcript_path` |
| `background_task_count`, `session_cron_count` | SIZE | counts the parser computes; the arrays themselves are content and are consumed (W2-T6) |
| `requested_model` | ENUM | `s().nullable()`, "an alias such as opus, a full id, or null" |
| `source` | ENUM | `X(["command","picker","sdk","auto","resume"])` |
| `context_tokens` | SIZE | builder: `MOn() ?? 0`, a token count |
| `prompt_cache_warm` | SCALAR | builder: `QF([])`, a boolean |
| `cache_ttl` | ENUM | `X(["5m","1h"])` |
| `estimated_cache_write_usd` | SCALAR | builder: `Math.round(d*1e4)/1e4`, USD to four places |
| `pricing` | ENUM | `X(["configured","catalog","default"])` |
| `command`, `file_path` on PostToolUseFailure | COMMAND, PATH | Telltale's own `_lifted`, same Kinds the other tool events give them |
| `from_mode`, `to_mode`, `trigger` | ENUM | emit site `bo("permission_mode_changed", {from_mode, to_mode, ...trigger})` |

`pricing` was the one the brief flagged: drop it if it is a nested object. It is not. It
is a three-value enum string, so it is stored and this is the sentence that says so.

No field's raw value turned out to be content, so nothing was added to `NEVER_PERSIST`
and the allowlist was not widened to admit any. The one content field on these shapes,
SubagentStop's `last_assistant_message`, is already in `NEVER_PERSIST` and the live

## EXPLAIN FOR THE OWNER

Three fixes, and the first one is the one worth understanding, because the thing that
went wrong is a property of the file format and not of any code.

**A TOML file has a current table, and it changes as you read down the page.**

You ran `telltale setup codex --print` and pasted what it gave you at the end of
`~/.codex/config.toml`. What it gave you was four lines like this:

```toml
otel.exporter={ "otlp-http" = { endpoint = "http://127.0.0.1:47399/v1/logs", protocol = "json" } }
```

Read on its own, that line means: there is a table called `otel`, and inside it a key
`exporter`. That is what a dotted key does. It is also exactly what codex wants, and it
is what the four `-c` overrides on the command line mean, because each `-c` is its own
tiny document with nothing before it.

Your config.toml is not nothing before it. It ends with something like:

```toml
[projects."/Users/you/some/repo"]
trust_level = "trusted"
```

A line beginning with `[` is a table header, and it does something that lasts: every key
after it belongs to that table, until the next header. So when the four lines land after
that header, `otel.exporter` does not mean "the top-level otel table". It means "a table
called `otel` INSIDE `projects."/Users/you/some/repo"`". The dot binds to whatever the
current table is, and the current table is not the root any more.

Here is the whole thing, checked with Python's own TOML parser:

```python
>>> tomllib.loads('otel.exporter = { }')                 # on its own
{'otel': {'exporter': {}}}                               # top-level otel. good.

>>> tomllib.loads('[projects."/x"]\ntrust_level = "trusted"\notel.exporter = { }')
{'projects': {'/x': {'trust_level': 'trusted', 'otel': {'exporter': {}}}}}
                                                         # no top-level otel at all.
```

Codex read that second document, found no `otel` configuration, and started normally. It
did not warn, because there is nothing to warn about: the file is valid and every key is
where the file says it is. The daemon's `otel_logs` count was 8 before your session and 8
after. The exact same values passed as `-c` on the command line delivered 4 batches.
Silence on one side, working on the other, and no error anywhere to tell them apart.

The fix is a table header of our own:

```toml
[otel]
exporter = { "otlp-http" = { endpoint = "http://127.0.0.1:47399/v1/logs", protocol = "json" } }
metrics_exporter = { "otlp-http" = { endpoint = "http://127.0.0.1:47399/v1/metrics", protocol = "json" } }
tool_result = { max_bytes = 0 }
environment = "telltale"
```

`[otel]` is absolute. It does not mean "otel inside whatever we were in"; it means "the
top-level table otel", wherever on the page it appears. That is the one property that
makes a snippet safe to append to a file whose contents we have never seen, and it is
why the header has to be pasted along with the four lines rather than skipped as
decoration.

The values are still generated, not typed. `_codex_snippet` asks `codex.launch` for the
real plan `telltale run` would use, takes its `-c` strings, and moves the `otel.` prefix
into the header. The test parses the printed snippet AND the launch plan and compares
them, so if the two ever disagree the test says so rather than a session going quiet.

**The second fix: a new Claude Code version, and the difference between two kinds of
silence.**

Telltale's allowlist is not a filter, it is the schema. A field nobody listed is dropped,
and its name is written into an `unknown_field` diagnostic. That diagnostic is a specific
claim: your provider is sending something this parser has not caught up with, go and
look. It is how you find out that a release added a field, without the recorder storing
anything it has not been told it may store.

Claude Code 2.1.263 added several. Every hook body now carries a `scratchpad_dir`;
SubagentStop carries the subagent's own transcript path and the background-task and cron
arrays that Stop already had; PostModelSwitch carries seven fields about what a model
switch costs you in re-cached context. Those are now listed, each with the treatment its
shape calls for: a path gets rewritten relative to the repository or hashed, a count is
required to be a number, a symbolic string is bounded short. None of it was guessed. The
shapes came out of the 2.1.263 binary's own schema and the functions that build these
objects, which is where W2-T6 read the Stop arrays from too.

One of the five turned out not to be Claude Code's doing at all. A `command` was showing
up on PostToolUseFailure. Claude Code does not send one: Telltale's own parser lifts
`command` and `file_path` out of every hook's `tool_input` (the container itself is
content and never stored), and PostToolUseFailure's schema entry had never listed either.
The recorder was producing a field its own schema refused. Worth saying plainly, because
"a new provider field" and "we did this to ourselves" call for different responses, and
only reading the code tells them apart.

**The third fix: known and refused is not the same statement as unknown.**

Every telemetry record Claude Code sends carries five attributes that identify you:
`organization.id`, `user.account_id`, `user.account_uuid`, `user.email` and `user.id`.
Telltale never stores account identity. That was never in doubt and it never leaked.

What was wrong is what the recorder SAID about them. They were left off the allowlist, so
the ordinary "I do not know this field" gate dropped them, and dutifully wrote all five
names into a diagnostic on every single record. Over your evening that came to 1250
occurrences of each name across 978 diagnostic rows, 7119 field names in total. 41 rows
from one short session.

Every one of those rows was saying "the parser is behind its provider, go and look" about
a thing we had already looked at and already decided. And they sat in the same list as
the rows that meant it. `claude.stream.tool_progress` really is a shape nobody has
measured; it appeared 15 times and was one line in a thousand.

So there are two lists now. `NEVER_PERSIST` is the old one: content, the containers a
prompt or a file body arrives in, dropped at every depth whatever the allowlist says.
`REFUSED` is the new one, and it holds exactly these five names. Both drop. What differs
is the word the recorder writes down afterwards. A `NEVER_PERSIST` hit reads
`never_persist`, a `REFUSED` hit reads `refused`, and neither counts toward
`unknown_field`. Here is a real row from the live session:
