# W9-T1 daemon captures bind their repository

## OUTCOME

A session started by hand inside a git checkout now carries that repository. The daemon
reads the `cwd` out of the session's first hook body, resolves the working tree root,
stores the sha256 of it as `repo_id` on every later observation, relativizes the paths,
takes the launcher's debounced snapshots, and links the session's commits on a worker
thread when SessionEnd arrives.

The live run, one Claude Code 2.1.263 haiku session in `/tmp/w9t1-live/repo` through
`telltale daemon --port 47399`, capture `cap_786c594857d404824628c2ae`, 9 s of wall time:

| PreToolUse `file_path` | `<outside>/0cc7d242` | `hello.txt` |

## WHAT WAS WRONG

Four defects, and only the first was in the brief.

**1. A daemon capture had no repository.** `Receiver.bind_capture` is the only way a
capture gets a `repo_id`, and only the launcher called it. So every observation of a
day-to-day session carried NULL, every absolute path fell outside the (absent)
repository and was hashed, no snapshot was ever taken, and no commit was ever linked.
Measured against this branch's parent with the same POSTs the new tests make: 3
observations, `repo_id` None on all three, `"cwd":"<outside>/2901f7e2"`,
`"file_path":"<outside>/c575704a"`, 0 `telltale.repo.commit`, and `sessions
--link-commits` printing `linked 0 commits in this repository`.

**2. `link_commits` would still have skipped it after the binding.** `facts()` reads
`started_at` and `repo_id` off `telltale.capture_started`, and only the launcher writes
one, so both are None for a daemon capture and the first guard in `link_commits`
returns 0 before the repo_id comparison is even reached. Binding alone would not have
made `sessions --link-commits` work.

**3. A short sha linked one commit twice.** Claude Code reports an abbreviated
`gitOperation.commit.sha`: `0881c21` on 2026-09-06, `705286a` in today's live run, seven
characters both times. `_commit_facts` resolves an abbreviation, so the stored payload
already carried the full sha. What nothing stopped was `_candidates` holding BOTH
spellings of one commit and `_link` answering for each: measured before the fix, one
commit with one matching snapshot and one short stated sha gave two
`telltale.repo.commit` payloads with the same full sha, one `tree_match_during` and one
`provider_reported`. This is a launcher defect too, not only a daemon one; it needed a
snapshot AND a short sha together, which is why no test had caught it.

**4. `link_commits` linked in the wrong repository when the ids were both None.** The
guard was `known.repo_id != identity.get("repo_id")`, and `None == None` passes it, so a
capture with no repository run from a directory that is not a checkout went on to walk
`git rev-list` there. It found nothing, so nothing was ever written; it was still asking
the wrong question.

## WHAT CHANGED

**`src/telltale/daemon_capture.py`, new, 286 lines.** `Binder(store, receiver, level,
on_bind=None)`, with four entry points the receiver calls on its request threads:
`observe` (bind on the first hook that names a cwd, start linkage on SessionEnd), `ctx`
(the bound capture's `Ctx`, or one shared empty one), `repo_changed` (forward to that
capture's debounced snapshot) and `session_ended` (hand linkage to a worker thread).
`close()` joins the workers. The capture object is the launcher's own `_Capture`, and
`_snapshot`, `_guard` and `SNAPSHOT_DEBOUNCE_S` are imported from launch.py rather than
copied, so there is one snapshot implementation and one emit path. The STOP condition
did not fire: `_Capture` is a dataclass with no child process in its constructor, which
`launch_commits.link_commits` already proved by building one, so nothing was split out
of launch.py.

Three decisions inside it worth naming.

The root is spelled the way the SESSION spells it. `git rev-parse --show-toplevel`
resolves symlinks and `sanitize.py` touches no filesystem by design, so on macOS a
session in `/tmp/w9t1-live/repo` against a root of `/private/tmp/w9t1-live/repo` would
have had every path hashed and this task would have changed nothing. `_seen_root` walks
up from the reported cwd by `--show-cdup` instead. The live run is the proof: that repo
had exactly this split, and `file_path` came out `hello.txt`.

The bind is double-checked under a lock, because two hook records of one session can
arrive together and only one may write the identity. `repo.identity` runs outside the
lock and the authoritative check is inside it; `receiver.bind_capture` is inside it too,
so there is no window in which the capture is bound here and not there.

Linkage never runs on a request thread. It flushes the store, takes the capture-end
snapshot, links, flushes again and rebuilds the capture's activities, which is the same
sequence `launch._finish` runs. The rebuild is what puts the commit on the change clock
at all: without it the commit is an observation and `repo_commit` is not an activity.

**`src/telltale/receiver.py`, +37/-6.** One call to `self._observed(...)` in `handle`,
between `_attribute` and `_ctx`; `on_record(callback)` to register it; `_observed` as a
sibling of `_maybe_mutation`, so an exception from a Binder is a diagnostic and the hook
still answers 200. `on_repo_change`'s callback widened to `(capture, trigger)`: a daemon
serves many captures at once and each has its own working tree, and the alternative was
a second parallel registration for the same event.

**`src/telltale/launch.py`, one line.** `receiver.on_repo_change(lambda _capture,
trigger: debouncer.trigger(trigger))`, the adaptation to the widened signature. launch.py
is in this brief's READS and not its OWNS; this is the only line touched, W9-F1 owns no
part of launch.py, and the alternative was a second callback on the receiver for one
event.

**`src/telltale/launch_commits.py`, +63/-22.** `link_commits(..., root: Path | None =
None)`. `_window_start` supplies the two facts a daemon capture has no
`capture_started` to carry: the first observation's arrival as the window start, and the
first non-null `repo_id` column as the repository, which is the same reading the
`captures` view already takes. The `repo_id is None` guard is defect 4.

**`src/telltale/repo_link.py`, +26.** `_resolved` maps every stated sha through `git
rev-parse --verify --quiet <sha>^{commit}` before `_candidates` sees it, so the two
spellings of one commit become one key. A sha the repository does not contain keeps its
own spelling and still reaches `_unresolved`, because the claim was made and losing it
silently would hide that it was wrong: measured, `provider_reported=["deadbee"]` still
returns one payload with sha `deadbee` and every other field None.

**`src/telltale/cli.py`, +30/-6.** The daemon builds the Binder and wires its three
methods in. `ctx_for_capture` is a forward reference to `binder`, which is safe because
nothing calls it before `receiver.start()` and there is no request thread until then.
`binder.close()` sits between `receiver.stop()` and `store.flush()`: the receiver first
so no session end can start a worker after `close()` has waited.

**`docs/design/03-capture-howto.md`.** The paragraph that said the daemon cannot know
the repository now says what it does know and what it still cannot: the environment
fingerprint and the launcher's diff.

**`tests/integration/test_daemon_capture.py`, new.** Four tests, all against a real
receiver over HTTP in derive-captures mode with a real Binder and a real temporary git
repository.

Verification that the tests test the fix. Against this branch's parent, run as a
standalone script making the same POSTs: `repo_id` None on all three observations, both
paths hashed, 0 commits, `linked 0 commits in this repository`. With `Binder.observe`
made a no-op on this branch: 3 of the 4 fail (the fourth is the outside-a-checkout case,
whose expected behaviour is exactly what the un-fixed code does, which is the point of
it). With `_resolved` removed: the short-sha test fails with `assert 2 == 1` and both
payloads printed.

## UNSURE OR NOT DONE

**The change clock's process columns are still unavailable, and this task cannot reach
them.** `series build --clock change --repo 9224de37...` prints its 1 row, with
`files_changed`, `lines_added`, `lines_removed`, `subsystems_touched`,
`test_files_changed` and `dependency_delta` all `observed` and `captured_rows` 1. But
`fresh_input_tokens_total` and the other six process columns are `unavailable`, with the
cohort's dropped list saying `cap_786c594857d404824628c2ae: no task_id and attempt: not
an attempt of this lineage`.

The cause is in `series_changes._change_row`: the process columns are folded from
`change.landed_by`, which `_landed_by` fills from `found.attempts`, which
`series_lineage._identity` fills only for a capture carrying a `(task_id, attempt)`
pair. Those come from `telltale run --task-id X --attempt N` or from a `correlation`
activity, and a session an owner starts by hand has neither. Making a capture that
RECORDED a change contribute its process numbers without being a numbered attempt of a
lineage is a change to what the change clock's rows mean, it would move every one of
E16's 657 rows, and it is not "daemon captures bind their repository". So the last
clause of VERIFY is reported unmet rather than worked around. It is the same gap the
README already names ("the agent's process is still unmeasured on the change clock ...
waits on day-to-day capture"), now half closed: the session reaches the clock, its
process does not.

**46 of the live capture's 90 observations still carry `repo_id` NULL, and that is
correct.** They are the OTel batch Claude Code exports at startup, 39
`hook_registered`, 3 `plugin_loaded`, 2 `mcp_server_connection` and 2 hook-execution
records, all of which arrive before the first hook BODY does. The repository cannot be
known before the record that names it, and an observation is immutable and append-only
(invariant 1), so backfilling them is not available. Every reader that asks a capture
for its repository takes the first non-null, which is what the `captures` view does and
what `_window_start` now does, so `sessions --repo`, `--link-commits` and the change
clock all find the capture.

**The order of SessionEnd against the last OTel export is not guaranteed.** Linkage
reads `git_commit_id` back out of the store, so a tool_result batch that arrives after
SessionEnd would be missed. It did not happen in the live run (the commit linked), and
the fallback is exactly `sessions --link-commits`, which this task also fixed. What
would measure it is a session that commits as its last action with the OTel export
interval raised; that has not been run.

**The db-bytes form of one assertion is not written as the brief asked.** "the string
'hi' is absent from the db bytes" cannot be asserted against the file: measured, a
freshly opened store already contains `b"hi"` twice, both inside the word "this" in the
schema's own comments, which SQLite keeps in `sqlite_master`. The content assertion is
made over every stored payload instead, where a leak would be, and the db-bytes
assertion is made about `b'"content"'`, the key that would carry one.

**`repo.identity` is slower on this machine than the brief measured.** The brief has 56,
45 and 48 ms; today, three runs each: 172 to 186 ms on this worktree, 81 to 102 ms on
the main checkout, 94 to 101 ms on a one-commit temporary repository. The number that
matters is the second and third, because that is what a bind costs, and the hook timeout
the snippet declares is 5 seconds (`providers/claude_launch.py`, `"timeout": 5`, seconds
and not milliseconds, and the printed snippet agrees). 100 ms against 5000 ms, paid once
per capture. I did not chase the difference; it is a busier machine and a linked
worktree, and it does not change the decision.

## NEXT

- Join a capture that recorded a change to the change it recorded, even when it is not a
  numbered attempt. That is the remaining half of H7 and it is a decision about what a
  change-clock row means, not a wiring fix.
- Codex hooks are command hooks, so a Codex daemon session sends no body carrying a cwd
  and binds nothing. Its OTel logs carry no working directory either. Whether a Codex
  daemon capture can be bound at all needs measuring before it is designed.
- A daemon capture is reduced only when linkage found a commit. A day-to-day session
  that made none still has no activities until somebody runs `telltale rebuild`.

## EXPLAIN FOR THE OWNER

Telltale has always been able to say what a session DID. Until today it could not say
where. The difference matters because the change clock is keyed on a repository: a row
is a commit that landed, and a session that is not attached to a repository cannot be
attached to a change either. So every session you started by typing `claude` in a
terminal was recorded and then sat outside the laboratory.

Here is what one of them looked like yesterday. Capture
`cap_b0be0e0da48a5a1a78bdb8fa` was a haiku session in a temporary repository that wrote
`hello.txt` and committed it. The daemon stored the hook body that announced the write:

```
"cwd":"<outside>/14fee89e", "file_path":"<outside>/0cc7d242"
```

`<outside>` is the sanitizer being honest. It is told a repository root at the start of
a capture and it rewrites any path under that root to be relative to it; a path it
cannot place, it hashes, so that "the agent touched two files somewhere" survives while
the somewhere does not. The daemon had never been told a root, so every path was
somewhere. The session also reported the commit it had just made, `"git_commit_id":
"0881c21"`, and Telltale linked nothing to it, and `sessions --link-commits` skipped the
capture entirely.

Today the same session, run live against this branch, stores this:

```
"cwd":".", "file_path":"hello.txt"
```

and one `telltale.repo.commit` with the full sha, at rung `provider_reported`, and the
change clock builds a row for it.

The idea is small. The daemon does not know where it is, but every hook body Claude Code
sends carries the session's own working directory. So the first hook of a session is
where the daemon looks: run `git` there, and if the answer is a working tree, that is
the session's repository for as long as the session lasts.

Now the part worth arguing about, because there was a wrong answer available. The
obvious thing to store is the directory. It is right there, it is what you would print,
and every later question about the session would be easy to answer with it. It was
rejected. A path is a disclosure: `/Users/<you>/Documents/code/<client>/<project>` names
you, your employer and your work, and it would sit in a database that gets exported,
copied and read by tools nobody has written yet. What is stored instead is the sha256 of
the checkout's root, which is the identity the launcher has always stored (spec 12.1),
and it answers the only question anybody asks of it: is this the same checkout as that
one. The root itself lives in the daemon's memory, for as long as the daemon runs, and
is written nowhere.

Two things fell out of building it that were not in the brief.

The first is a spelling problem that would have made the whole task a no-op on macOS.
`git rev-parse --show-toplevel` hands back the root with every symlink resolved. The
session reports its paths the way its shell spells them. On this machine those differ:
git says `/private/tmp/w9t1-live/repo` where the session says `/tmp/w9t1-live/repo`. The
sanitizer does no filesystem access on purpose, because it runs on every field of every
record and cannot afford to, so it compares the two strings and would have decided that
`/tmp/w9t1-live/repo/hello.txt` is not inside `/private/tmp/w9t1-live/repo`. Every path
would still have come out `<outside>` and the tests, which use pytest's already-resolved
temporary directory, would have passed anyway. The fix is to ask git for the root
relatively, with `--show-cdup`, and walk up from the session's own spelling. The live
run is what caught it, which is the argument for the live run.

The second is a counting bug that predates the daemon. Claude Code reports a
seven-character commit id. git happily resolves seven characters to the whole commit, so
the stored payload was always right. But the linker builds its candidate list by putting
the shas git listed for the window together with the shas the provider stated, and those
are two different strings for the same commit, so it examined the commit twice and wrote
it down twice: once as `tree_match_during`, because a snapshot matched the tree, and once
as `provider_reported`, because the provider said so. Both are true, and one commit is
still one commit. It needed a snapshot and a short sha at once, which the launcher can
produce too, so it was a launcher defect that no launcher test had happened to hit. The
fix resolves stated shas to full ones once, inside the repository, before the candidate
list is built.

How the numbers here were measured. The before column is two things: yesterday's real
capture as the brief recorded it, and a standalone script run against this branch's
parent that makes exactly the POSTs the new tests make, which printed 3 observations,
`repo_id` None on all three, both paths hashed, 0 commits and "linked 0 commits". The
after column is one live Claude Code 2.1.263 session against a daemon on port 47399 with
a temporary `$TELLTALE_HOME`, read back out of the database it wrote. The duplicate-link
count is from calling `repo_link.commits_since` directly against a two-commit repository,
once with the fix and once without. The timings are three runs each of `repo.identity`,
reported as a range and not an average, against the 5-second hook timeout that the
snippet declares and that `providers/claude_launch.py` sets.

What it does not do. A session started outside a checkout keeps `repo_id` None, and that
is the truth about it rather than a failure, so it produces no identity record and no
diagnostic. The 46 records Claude Code exports in the first moments of a session, before
any hook fires, keep NULL too: nothing can know the repository before the record that
names it arrives, and an observation is never rewritten. And the change clock still
cannot see the session's process, its tokens and compactions and verification cycles,
because a row's process numbers come from the numbered attempt that landed the change
and a session you started by hand is not one. The session now reaches the clock. Its
process is the next task.
